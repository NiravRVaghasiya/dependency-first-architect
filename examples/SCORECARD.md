# Scorecard: the same model, with and without the skill

Does the skill change how a model plans? Five fixed prompts from
[`reference/evals.md`](../reference/evals.md), each run once without the skill and once with it,
on the same model in Claude Code. Every plan was scored against the rubric in that same file by
judges who were not told which arm wrote it.

Every score on this page is generated from the raw judge scores in
[`scoring/judgments.json`](scoring/judgments.json) by [`scoring/tally.py`](scoring/tally.py).
`tally.py --check` fails if the page drifts from the raw scores, or if a committed plan
no longer matches the model output it was scored on. To re-run the whole eval yourself, use
[`scoring/run_eval.py`](scoring/run_eval.py).

## How to read this

- **Read the without-skill column. The 20s are a ceiling.** The rubric checks exactly what the
  skill asks for, so a plan that follows the skill can max it out, and every with-skill plan here
  did, with every judge. That shows the skill reliably produces what the rubric measures. It does
  not show the plans are flawless. The skeptics found small internal slips (for example, a Phase 0
  exit check that expects an alert Phase 0 doesn't define) and judged none of them worth a point; their notes
  are in [`scoring/judgments.json`](scoring/judgments.json).
- **Where the lift comes from.** Look at the *mean without* row. Without the skill, the model
  already orders work by dependency (D1) and handles failure (D8). It falls short on a thin slice
  running in production first (D2), reproducible builds and environments (D7), and tradeoffs with
  explicit flip conditions (D3). The judges' D2 rationales describe the pattern: the plans build
  one layer at a time (an offline pipeline, a broad "foundation" bundle, an infrastructure layer)
  before anything runs end to end in production, and two never describe a production deployment
  at all.
- **The lift depends on the prompt.** It is positive on every prompt. `reference/evals.md` expects
  the AI prompts (P1, P4) to show the largest lift; in this run they did not (see Totals). On P3
  the lift is mostly D9; without it, it is within the judges' own disagreement on that plan (see
  the sensitivity line and the judge spread).
- **D9 is partly a rubric artifact on non-AI prompts.** `reference/evals.md` says a non-AI plan
  earns 2 for correctly declaring the AI layer N/A. The judge prompt turns that into "0 if it never
  addresses the question", so a plan that simply never mentions AI scores 0. The sensitivity
  section shows the delta without it.
- **The audit is the stress test for the ceiling.** It is deliberately one-sided against the
  skill: skeptics could only take points away from with-skill plans, and advocates could only add
  points to plans without it.
- **One run per arm, per prompt.** Per-prompt deltas are indicative; the mean is the headline.

## Method

| | |
|---|---|
| **Model** | `claude-opus-5-5`, effort `max`, through the Claude Code CLI, every session started as `claude --bare -p`. The CLI version is recorded in [`scoring/generation.json`](scoring/generation.json). |
| **Prompts** | P1–P5 from [`reference/evals.md`](../reference/evals.md), verbatim. |
| **Without the skill** | The prompt alone. Fresh empty working directory with a meaningless name. `--bare` loads no CLAUDE.md, hooks, settings or memory. Tools: `Read` only. |
| **With the skill** | Identical, plus `SKILL.md` and `reference/` (commit `3ba6b70`) loaded as a session plugin (`--plugin-dir`) and invoked as `/dependency-first-architect <prompt>`. |
| **Judges** | 3 per plan. Each is its own `--bare` session with every tool disabled. It sees the request, the rubric and the plan text. It is not told which arm wrote the plan or the file name, and the plan's own self-score section is stripped. It returns 0–2 per dimension with a verbatim quote as evidence (structured output). |
| **Score** | Per-dimension median of the 3 judges, summed to /20. |
| **Audit** | 3 skeptics per with-skill plan (may only lower a score) and 3 advocates per plan without the skill (may only raise one). *Majority* takes the median auditor per dimension. *Any dispute* accepts every single auditor's change. The *floor* is any dispute plus dropping D9 on the non-AI prompts; the README quotes it. |

The prompts given to judges and auditors are in [`scoring/run_eval.py`](scoring/run_eval.py),
verbatim. The rubric text there is `reference/evals.md`'s, reformatted, plus explicit scoring
rules: score substance, not vocabulary; "threaded" means every phase, starting with the first
phase that builds anything; ignore self-assessments; length is not quality; and for D9 on a non-AI
request, 2 only if the plan explicitly says no AI layer applies, 0 if it never addresses it.

**Protocol check.** [`scoring/generation.json`](scoring/generation.json) records every tool call
each generator session made, with its path and whether it succeeded, plus the SHA-256 of each plan
as the model wrote it. In the sessions without the skill, every read failed: their working
directories were empty, and some made no tool calls at all. The sessions with the skill read
exactly what `SKILL.md` tells them to: `reference/plan-template.md` and `reference/evals.md`, plus
`reference/ai-systems.md` on the two AI prompts.

## Threats to validity

- **The same model family writes and judges.**
- **Judges could sometimes infer the arm.** They are not told it, but the with-skill plans have a
  recognizable shape (a gate table, a per-phase table of concerns). Some plans without the skill
  mention the empty workspace they ran in ("I couldn't find an existing project in the
  workspace"), and one with-skill plan mentions its template ("as the template says").
- **One run per arm per prompt.** There is no estimate of run-to-run variance.
- **The rubric and the skill come from the same author** and check the same things (see above).
- **Length.** The with-skill plans are longer (see Plan length). Judges are told not to reward
  length, but a longer plan has more places to show a concern.
- **`--bare` is not an everyday session.** It has a minimal system prompt and no project context.
  That is what keeps the comparison clean, but absolute scores in a full Claude Code session may
  differ. Only the Claude Code path was measured. The Cursor and Codex adapters were not.

## A discarded first run

The first attempt ran the generators and judges as Claude Code workflow subagents. That harness
relays the requesting user's brief to every subagent, and the brief described this experiment and
its hypothesis. So the "cold" runs were not cold and the judges were not blind. The whole run was
thrown away, and nothing on this page comes from it. That is why
[`run_eval.py`](scoring/run_eval.py) starts every session isolated, with only its prompt.
