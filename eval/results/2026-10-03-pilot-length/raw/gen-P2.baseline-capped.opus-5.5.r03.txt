Scope and Assumptions\n\n- **What \"tenant\" means here.** A tenant is a customer organization on the SaaS platform. The model is hierarchical (**Platform → Tenant → Account → Subscription**), so the same design also works as billing-as-a-service, where each tenant bills its own end customers.\n- **Pricing models:** flat-rate, per-seat, usage-based (metered), tiered or volume pricing, hybrid plans, prepaid credits and commitments.\n- **Coverage:** multiple currencies, tax jurisdictions and payment methods.\n- **Non-negotiables:**\n  - Money is never lost or double-charged.\n  - Every number on an invoice can be traced back to its source.\n  - One tenant's data never leaks to another, and one tenant can't slow the system down for others.\n\n## 2. High-Level Architecture\n\n```\n Product Services ──usage events──▶ [Ingestion API] ──▶ Kafka (partitioned by tenant_id)\n        │                                                   │\n        │ entitlement checks                                ▼\n        ▼                                         [Metering / Aggregation]\n [Entitlements Svc]◀──┐                                     │ (ClickHouse / TSDB)\n   (Redis cache)      │                                     ▼\n                      │   [Catalog Svc] ──▶ [Subscription Svc] ──▶ [Rating Engine]\n                      │                            │                    │\n                      └──── subscription events ───┘                    ▼\n                                                              [Invoicing Svc] ──▶ PDF/Email\n                                                                       │\n                       [Tax Svc] ◀─────────────────────────────────────┤\n                                                                       ▼\n                                  [Payments Svc] ◀──▶ PSP adapters (Stripe/Adyen/ACH)\n                                         │\n                                         ▼\n                              [Ledger (double-entry)] ──▶ Rev Rec / Reporting / GL export\n                                         │\n                                  [Dunning Svc]  [Notifications]  [Webhooks out]\n```\n\nEach box is a bounded-context service. They communicate through an event bus (Kafka) using the **transactional outbox pattern**: a service writes its state change and the outgoing event in the same database transaction, so the two can't diverge. Synchronous APIs are used only where a request needs an immediate answer, such as entitlement checks and checkout.\n\n## 3. Core Domain Model\n\n| Entity | Key fields / notes |\n|---|---|\n| **Tenant** | id, region, isolation tier, default currency, timezone, tax settings |\n| **Account** (billable entity) | tenant_id, billing contact, currency, tax IDs, payment methods (tokens only), credit balance |\n| **Product / Feature** | Catalog items. Features map to entitlements. |\n| **Plan / Price** | **Versioned and immutable.** Fields: price model (flat, per_unit, tiered, volume, package), interval, currency, meter_id. A new price creates a new version, so existing customers stay on their old price (grandfathering). |\n| **Subscription** | account_id, status (trialing, active, past_due, paused, canceled), billing anchor, term, items[] → price_version, quantity |\n| **Subscription Phase / Schedule** | Future-dated changes such as ramps, scheduled downgrades and contract renewals |\n| **Meter** | Event name, aggregation (sum, max, unique count, last value), filters |\n| **Usage Event** | idempotency_key, tenant_id, account_id, meter, value, timestamp, properties |\n| **Invoice / Line Item** | Immutable once finalized. Key Subsystems\n\n### 4.1 Usage Metering\n- **Ingestion API:** batched, authenticated per tenant, and requires an `idempotency_key`. It responds `202 Accepted` after a durable write to Kafka.\n- **Deduplication:** keyed on `(tenant_id, idempotency_key)` in a deduplication store with a TTL (Redis or RocksDB in Flink), plus a final dedupe at aggregation time.\n- **Streaming aggregation:** Flink or Kafka Streams computes running totals per (account, meter, billing period) into ClickHouse. These totals power real-time dashboards and usage-limit enforcement.\n- **Late events:** accepted up to a grace window, for example 72 hours after period close. Events after that window go into the next invoice as adjustments, or raise a credit note. Closed invoices are never edited.\n- **Snapshots:** when an invoice is generated, the aggregate is frozen as a usage snapshot so the invoice can be reproduced exactly.\n- **Raw events** are archived to object storage (Parquet) for audits and replay.\n\n### 4.2 Subscription Engine\n- Each subscription is a state machine with explicit transitions, and every transition emits an event.\n- **Proration:** mid-cycle changes create proration line items (a credit for unused time and a charge for the new plan), calculated to the second against the tenant's timezone.\n- Upgrades can either be invoiced immediately or added to the next invoice. Downgrades usually take effect at period end.\n- **Billing anchors and calendar logic** (month ends, leap years, DST) live in one well-tested library.\n- **Test clocks:** each sandbox account can have its own virtual clock, so whole lifecycles can be simulated.\n\n### 4.3 Rating and Invoicing\n- The **Rating Engine** is a pure function: `(price_version, quantity/usage_snapshot, period, discounts, credits) → line items`. Because it is deterministic and side-effect free, it is easy to test with property-based tests and to replay.\n- **Billing run scheduler:**\n  - A partitioned job queue finds subscriptions whose period ends in the next window. The query is indexed on `next_billing_at`.\n  - Work is spread across workers by hashing on tenant_id.\n  - Anchors are naturally spread out, which avoids a midnight-on-the-1st spike. Large tenants can be throttled or given dedicated workers.\n- **Invoice lifecycle:** `draft → (review window, optional) → finalized → paid | void | uncollectible`.\n  - Finalization assigns a gap-free, tenant-scoped invoice number (some jurisdictions require this).\n  - It also calls the Tax Service and writes ledger entries (AR debit, revenue/deferred revenue credit, tax liability credit).\n- **Tax:** a vendor such as Avalara, Anrok or Stripe Tax sits behind an adapter. The tax quote is stored with the invoice, and tax is committed only at finalization.\n\n### 4.4 Payments\n- **PCI scope:** card data never touches our systems. We use PSP tokenization (hosted fields or Elements), which keeps us at PCI SAQ-A.\n- **PSP adapter interface:** `authorize`, `capture`, `refund`, `createMandate`. This allows multiple PSPs, routing by region or cost, and failover.\n- **Payment intents** are a state machine, and every PSP call is idempotent (we pass our own idempotency key).\n- **Webhooks from PSPs:**\n  - Verify the signature and store the raw payload first.\n  - Process asynchronously, tolerating duplicates and out-of-order delivery.\n  - Treat the PSP as the source of truth for payment status.\n- **Daily reconciliation job:** compares PSP settlement reports against the ledger and raises alerts on any mismatch.\n\n### 4.5 Dunning and Collections\n- Retry schedules are configurable per tenant or plan. Smart retries can account for decline codes and time of day.\n- Customers are notified at each step. Card-updater services are used.\n- Escalation: `past_due` → feature restriction (through Entitlements) → suspension → cancellation, or write-off to `uncollectible`.\n\n### 4.6 Entitlements\n- Projects active subscriptions and usage into a \"what can this account do\" view: feature flags, seat limits and usage quotas.\n- Served from a Redis cache that is invalidated by subscription events, with p99 under 5 ms. Product services check it on their hot path.\n- **Fails open** for paying customers if billing is degraded, since billing should never take the product down. Every fail-open decision is logged.\n\n### 4.7 Ledger and Revenue Recognition\n- An append-only, double-entry ledger is the financial source of truth. Every entry balances to zero per transaction.\n- Revenue recognition schedules (ASC 606 / IFRS 15) are generated at finalization: subscriptions are recognized ratably, usage is recognized as consumed.\n- Exports go to the general ledger (NetSuite, QuickBooks) and the warehouse.\n\n## 5. Multi-Tenancy Design\n\n### Isolation tiers\n| Tier | Model | For |\n|---|---|---|\n| Pooled | Shared Postgres cluster, `tenant_id` on every row, **Row-Level Security** enforced | Long tail of SMB tenants |\n| Bridged | Dedicated schema or database on shared infrastructure | Mid-market tenants, data residency needs |\n| Silo | Dedicated cell (DB, workers, Kafka partitions) | Enterprise tenants, compliance requirements |\n\n### Controls that apply to every tier\n- **Tenant context** comes from the authenticated token and travels through every request and event. It is set as a Postgres session variable for RLS. Queries are never built from client-supplied tenant IDs.\n- **Composite keys and indexes** start with `tenant_id`. The tenant ID is also included in cache keys, Kafka message keys and object-storage prefixes.\n- **Cell-based deployment:** tenants are mapped to cells (regional shards) through a routing directory. This limits the blast radius of failures and supports data residency (EU or US cells).\n- **Noisy-neighbor protection:**\n  - Per-tenant rate limits on ingestion.\n  - Weighted fair queuing in the billing-run workers.\n  - Per-tenant Kafka quotas.\n  - Large tenants can be moved to their own cell.\n- **Per-tenant configuration:** branding, invoice templates, numbering sequences, dunning policies, tax settings and webhook endpoints.\n- **Encryption:** at rest and in transit. Silo tenants can have per-tenant KMS keys (BYOK). PII fields get field-level encryption.\n- **Automated isolation tests:** CI runs cross-tenant access tests that try to read data from another tenant's context and must fail.\n\n## 6. Reliability and Correctness\n\n- **Idempotency everywhere:** ingestion, API mutations (an `Idempotency-Key` header), PSP calls and event consumers (an inbox table keyed by event ID).\n- **Exactly-once effects:** we build these from at-least-once delivery plus idempotent consumers, rather than relying on exactly-once delivery guarantees.\n- **Immutability:** finalized invoices, ledger entries and price versions are never updated. They are only corrected with new entries.\n- **Audit log:** every state change records the actor, the before and after state, and a timestamp. It is stored in tamper-evident, append-only storage.\n- **Reconciliation jobs:**\n  - Usage events against aggregates.\n  - Invoices against ledger entries.\n  - Ledger entries against PSP settlements.\n  - Subscriptions against entitlements.\n  \n  Any drift pages the on-call engineer.\n- **Replayability:** raw usage plus versioned prices plus a deterministic rating engine means any invoice can be regenerated and compared.\n- **Availability targets:**\n  - Ingestion and entitlements: 99.99%.\n  - Invoicing: 99.9%. It is batch-tolerant, and a delay is acceptable while a wrong invoice is not.\n- **Disaster recovery:** Postgres with synchronous replicas and point-in-time recovery, Kafka replication factor of 3, and cross-region backups. Target RPO under 1 minute for the ledger.\n\n## 7. APIs and Integrations\n\n- Public REST API, versioned by date header, with cursor pagination and expandable objects. Includes a sandbox mode with test clocks.\n- **Outbound webhooks** (e.g. `invoice.finalized`, `payment.failed`, `subscription.updated`):\n  - Signed with HMAC.\n  - Retried with exponential backoff.\n  - Viewable in a per-tenant delivery log, with replay.\n- Customer portal: invoices, payment methods, plan changes, usage dashboards.\n- Admin console: refunds, credits, invoice adjustments with approval workflows, and impersonation with an audit trail.\n\n## 8. Technology Choices\n\n| Concern | Choice |\n|---|---|\n| Core OLTP | PostgreSQL (RLS, serializable transactions for ledger writes) |\n| Event bus | Kafka with outbox (Debezium CDC) |\n| Usage aggregation | Flink + ClickHouse |\n| Cache / entitlements | Redis |\n| Workflows (dunning, billing runs) | Temporal, which gives durable timers and retries |\n| Documents | S3 + PDF rendering service |\n| Observability | OpenTelemetry traces tagged with tenant_id. Per-tenant SLO dashboards. |\n\n## 9. Phased Delivery\n\n1. **MVP:** catalog, flat and per-seat subscriptions, invoicing, one PSP, basic dunning, ledger, pooled tenancy with RLS.\n2. **Usage:** metering pipeline, tiered and volume pricing, real-time usage dashboards, entitlements service.\n3. **Scale and compliance:** tax engine, multiple currencies, revenue recognition, cell architecture, silo tier, SOC 2 controls.\n4. **Advanced:** contracts and commitments, prepaid credits, multiple PSPs with routing, smart retries, self-serve pricing experiments.\n\n## 10. Key Trade-offs\n\n- **Correctness over latency:** invoicing is asynchronous and reconciled.
