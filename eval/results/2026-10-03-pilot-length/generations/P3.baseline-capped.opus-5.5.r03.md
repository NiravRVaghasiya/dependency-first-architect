# Sequenced Plan: CI/CD Platform for 50 Microservices

**Core principle:** Build one paved road, prove it on a few services, then migrate the rest in waves. Don't build for all 50 at once. Don't let each team build its own pipeline either.

---

## Phase 0: Discovery and Decisions (Weeks 1–3)

**Why first:** Every later choice depends on what you actually have.

1. **Inventory all 50 services.** For each one, record:
   - Language and build tool
   - Repo layout (mono or poly)
   - Current build and deploy method
   - Runtime target (Kubernetes, VMs, serverless)
   - Database dependencies
   - Owning team
   - How critical it is to the business
2. **Measure a baseline** with the DORA metrics: deploy frequency, lead time for changes, change failure rate and time to restore. You need these later to show the platform worked.
3. **Group services into archetypes.** Usually 3–6, for example "Java/Gradle REST API on K8s", "Node worker", "Python batch job". Templates target archetypes, not individual services.
4. **Make the core tooling decisions** and record each one in an Architecture Decision Record (ADR):
   - CI engine (GitHub Actions, GitLab CI, Buildkite, Tekton)
   - CD model (GitOps with Argo CD or Flux is recommended for K8s; push-based otherwise)
   - Artifact registry (ECR/GAR/Artifactory/Harbor)
   - Secrets management (Vault, cloud KMS/Secrets Manager)
   - Deployment packaging (Helm or Kustomize)
5. **Define the target end state:** "Commit to production in under 1 hour, fully automated, with gates."

**Exit criteria:** inventory done, archetypes defined, tooling ADRs approved, 2–3 pilot services picked (one simple, one complex, one with an awkward edge case).

---

## Phase 1: Foundations (Weeks 3–7)

**Why now:** Pipelines can't run without infrastructure, identity and secrets.

1. **Build infrastructure:**
   - Autoscaling ephemeral runners (for example K8s-based runners or managed runners)
   - Remote caching for dependencies and layers
   - Isolated build networks
2. **Identity:** Use OIDC federation from CI to the cloud. No long-lived credentials in pipelines.
3. **Secrets:** Centralize secrets management and inject secrets at runtime, never at build time.
4. **Artifact registry:** Set up immutable tags, retention policies and vulnerability scanning on push.
5. **Environments:** Provision dev, staging and prod with Infrastructure as Code (Terraform/Pulumi). Keep them consistent with each other and separate prod accounts or clusters.
6. **Repo standards:**
   - Branch protection
   - Required reviews
   - CODEOWNERS files
   - Conventional commits (optional)
   - A standard repo skeleton
7. **GitOps config repo(s):** Decide on one environment repo or one per team. Define the directory structure for apps and environments.

**Exit criteria:** A "hello world" service can build on platform runners, push to the registry and authenticate to the cloud with no static secrets.

---

## Phase 2: CI Golden Path (Weeks 6–10)

**Why now:** CI is lower-risk than CD and gives teams value immediately.

1. **Build reusable, versioned pipeline templates per archetype.** Use reusable workflows, GitLab includes or shared libraries. Teams reference `ci-template@v1`; they don't copy-paste it.
2. **Standard stages:**
   - Checkout → dependency restore (cached) → lint/format
   - Unit tests with a coverage report
   - Static analysis (SAST) and dependency/license scanning (SCA)
   - Container image build (reproducible, minimal base images)
   - Image scanning
   - SBOM generation
   - Image signing (Sigstore/cosign)
   - Push with an immutable tag (git SHA)
3. **Pull-request vs. main-branch behavior:** PRs get fast feedback (target under 10 minutes). Main builds produce release artifacts.
4. **Pilot** on the 2–3 chosen services. Measure build time, flaky tests and developer friction.
5. **Iterate** on the templates based on pilot feedback before scaling.

**Exit criteria:** Pilot services build fully on templates, PR feedback is under 10 minutes, and artifacts are signed and scanned.

---

## Phase 3: CD Golden Path (Weeks 9–14)

**Why now:** You need trusted artifacts (from Phase 2) before automating deploys.

1. **Standard deployment packaging:** a base Helm chart or Kustomize base per archetype covering:
   - Health probes
   - Resource limits
   - Pod disruption budgets (PDBs)
   - Horizontal autoscaling (HPA)
   - Standard labels
2. **GitOps flow:** CI updates the image tag in the config repo. Argo CD/Flux syncs dev automatically.
3. **Promotion model:** dev (automatic) → staging (automatic after tests pass) → prod (manual approval at first, automated later). Promote the *same artifact* through every stage; never rebuild per environment.
4. **Post-deploy smoke tests** in each environment.
5. **Rollback:** a git revert of the config repo, documented and rehearsed.
6. **Database migrations:** Standardize the tool (Flyway, Liquibase, Alembic). Require backward-compatible changes using the expand/contract pattern.

**Exit criteria:** Pilot services deploy to prod through the pipeline, and a rollback has been tested in staging.

---

## Phase 4: Observability and Guardrails (Weeks 12–16, overlaps Phase 3)

**Why before mass migration:** At 50 services, you can't operate blind or enforce standards by hand.

1. **Pipeline observability:**
   - Build duration
   - Failure rates
   - Queue times
   - Flaky test tracking
   - Automated DORA metric collection
2. **Deployment observability:** Annotate deploys in your APM/metrics tooling and alert on regressions after a deploy.
3. **Policy as code** (OPA/Gatekeeper/Kyverno) to enforce:
   - Signed images only
   - No `latest` tag
   - Resource limits required
   - No privileged containers
4. **Audit trail:** who deployed what, when and with which approval. Compliance needs this.

**Exit criteria:** dashboards are live, policies run in *audit* mode, and pilot services pass them.

---

## Phase 5: Migration Waves (Weeks 14–26)

**Why waves:** You build the learning curve and platform capacity step by step, and risk stays contained.

| Wave | Services | Selection | Goal |
|------|----------|-----------|------|
| 1 | ~5 | Low criticality, common archetype, willing teams | Validate the self-service onboarding docs |
| 2 | ~15 | Mixed archetypes, moderate criticality | Stress-test templates and runner capacity |
| 3 | ~25 | The rest, including critical and odd services | Full coverage; handle exceptions |
| 4 | ~5 | Legacy and outliers | Custom extensions or a documented exemption |

**For each wave:**
- Run an onboarding checklist covering repo skeleton, template reference, chart, config repo entry, secrets and dashboards.
- Run the old and new pipelines in parallel for 1–2 weeks, then cut over.
- Hold a retrospective and feed fixes into a new template version.
- Have platform engineers pair with service teams. Handoffs alone won't work.

**Exit criteria:** At least 90% of services are on the golden path, and the old pipelines are decommissioned.

---

## Phase 6: Advanced Testing and Delivery (Weeks 22–32)

**Why later:** These depend on stable basics and good observability.

1. **Contract testing** (for example Pact) between services. This is critical at 50 services, because full end-to-end suites become slow and brittle.
2. **Ephemeral preview environments** per PR for high-change services.
3. **Progressive delivery** (Argo Rollouts/Flagger): canary or blue-green releases with automated analysis against service-level objectives (SLOs) and automatic rollback.
4. **Feature flags** to separate deploying code from releasing features.
5. **Remove the manual prod gate** for services with a good track record, replacing it with automated canary analysis.
6. **Switch policies to enforce mode.**

**Exit criteria:** Critical services deploy via automated canary, and the manual approval is gone for qualifying services.

---

## Phase 7: Self-Service and Continuous Improvement (Ongoing)

1. **Developer portal** (for example Backstage) with:
   - A "create new service" scaffolder that produces a pipeline-ready repo in minutes
   - A service catalog
   - Scorecards for template version, test coverage and vulnerability state
2. **Automated template upgrades:** Renovate/Dependabot-style PRs that bump template versions across repos.
3. **Platform as a product:** a roadmap, office hours, a feedback channel and SLOs for the platform itself (runner availability, queue time).
4. **Cost management:** right-size runners, use spot instances, tune caches.
5. **Supply-chain maturity:** progress toward SLSA Level 3 provenance.

---

## Cross-Cutting Concerns (Every Phase)

- **Security:** Shift scanning left from day one, but start in warn mode so adoption isn't blocked. Tighten over time.
- **Documentation:** Each phase ships docs and runbooks. Onboarding should not depend on the platform team.
- **Escape hatches:** Teams can extend templates through defined hooks. Forking is the exception and must be justified.
- **Versioning:** Templates follow semantic versioning. Breaking changes get a deprecation window.

---

## Team and Timeline

- **Platform team:** 3–5 engineers (CI, CD/K8s, security, developer experience), plus a champion in each service team.
- **Timeline:** about 6–8 months to full migration with progressive delivery. Self-service maturity keeps improving after that.

---

## Key Dependencies (Why This Order)

```
Discovery → Foundations → CI → CD → Guardrails → Migration → Advanced → Self-service
                              ↘ Observability ↗
```

- CD needs signed, trusted artifacts from CI.
- Mass migration needs proven templates, guardrails and observability.
- Progressive delivery needs metrics and SLOs.
- Removing manual gates needs automated analysis and a stable track record.

---

## Top Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Template sprawl or forks | Versioned shared templates, extension hooks, scorecards |
| Slow pipelines hurt adoption | Caching, parallelism, a strict PR time budget |
| Flaky tests erode trust | Quarantine and tracking, owner accountability |
| Big-bang migration failure | Waves, parallel runs, pilots |
| Security gates block teams | Warn first, enforce later, with clear remediation guidance |
| Platform team becomes a bottleneck | Self-service onboarding, docs, embedded champions |

**Success looks like:** every service ships through one consistent, secure pipeline; a new service is production-ready on day one; and DORA metrics show measurable improvement over the Phase 0 baseline.
