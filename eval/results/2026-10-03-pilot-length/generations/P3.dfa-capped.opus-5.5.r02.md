# BUILD PLAN: CI/CD platform for 50 microservices

## 1. Classification and constraints
- **What:** a shared build, test, sign and deploy platform that all 50 services use to reach production.
- **Type:** infrastructure. Brownfield: I assume the services already ship some other way, and that way stays as the fallback. This is not a small build.
- **Dominant constraint:** correctness and security of what reaches production. The pipeline is the most privileged path into production.
- **Worst failure:** a compromised or misconfigured pipeline pushes unauthorized code to all 50 services at once.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Build time (CI) | p90 ≤ 10 min | ASSUMPTION (common developer-tolerance bar) | V3 |
| Commit → production lead time | p90 ≤ 30 min | ASSUMPTION | V3, then Phase 4 |
| Queue wait | p90 ≤ 2 min at peak | ASSUMPTION | V3 |
| Peak commit rate | UNKNOWN: commits/day per service, supplied by engineering managers, needed in Phase 2 | UNKNOWN | V3 |
| Platform availability | 99.5% during working hours | ASSUMPTION (a CI outage blocks deploys but leaves running services up) | Phase 4 |
| Rollback time | ≤ 5 min | ASSUMPTION | V0, V4 |
| Runner and registry cost | UNKNOWN: monthly cap, supplied by finance, needed before Phase 2 | UNKNOWN | V3 |
| Operational complexity | ≤ 4 components the platform team runs itself | ASSUMPTION (platform team size UNKNOWN) | Phase 1 |

**Missing inputs:**
- **Runtime target.** I assume Kubernetes. If it is VMs or serverless, Phase 3 changes.
- **Existing CI tool and repo layout** (mono-repo or one repo per service).
- **Compliance regime.** SOC 2 or PCI would add change-approval dependencies.
- **Platform team headcount.**

## 3. Tradeoff gates

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| CI-to-production trust boundary | R3 (a short compromise causes harm that can't be undone) | OIDC-federated short-lived credentials; CI only pushes signed images; Argo CD pulls them into production; Kyverno admission policy verifies cosign signatures | Pull-based GitOps removes production write access from CI | V2 | V2 fails, or the runtime can't enforce admission policy |
| Pipeline contract (service manifest plus versioned shared templates) | R2 (changing it is coordinated work across 50 teams; versioned templates are the seam) | One golden-path template with declared extension points | ≥ 90% of services fit without forking (ASSUMPTION) | V1 | V1 fails: ship two or three templates by service archetype |
| Build vs buy | R2 (rewriting 50 pipeline definitions takes weeks) | Buy hosted CI (GitHub Actions or the existing SCM's CI) with self-hosted autoscaled runners; Argo CD and Argo Rollouts open source | Hosted CI meets queue and cost budgets | V3 | V3 fails on cost or queue wait |
| Push vs pull deploy (sync vs async) | R2 | Async pull through GitOps; git is the system of record for desired state | Reconcile delay ≤ 3 min is acceptable | Phase 0 measurement | Lead-time budget is missed because of reconcile delay |
| Consistency vs availability of deploy state | R2 | Git is authoritative. If git or CI is down, deploys pause; an audited break-glass `kubectl` role handles emergencies | Pausing deploys is acceptable during outages | Break-glass drill in Phase 1 | Outage pauses exceed the availability budget |
| Migration and cutover | R2 (until decommission, then R3) | Onboard in waves, lowest criticality first; legacy pipeline stays the fallback; git manifests are the system of record per service once onboarded | Both pipelines can coexist per service | V5 guards decommission | A wave's rollback rate exceeds 10% |

**R1 defaults:** test framework per service → owner's choice; artifact registry → cloud-native OCI registry; template language → reusable workflows.
**N/A:** monolith vs services, because the platform is composed from bought components. Data-privacy boundary, because no personal data flows through the platform, though build logs can carry secrets (handled in §7).

## 4. Walking skeleton (Phase 0)
- **Request:** a one-line change to one low-criticality internal service reaches production, and its `/health` endpoint returns the new version string.
- **Tiers:** SCM commit → hosted CI with a self-hosted runner → unit tests → container build → cosign sign → registry → GitOps manifest repo → Argo CD → production cluster → service → `/health` response.
- **Deployed:** through the pipeline itself.
- **Logged:** CI logs and Argo events go to the central log store.
- **Monitored:** OpenTelemetry traces span the CI job through to the pod, and an alert fires on failed sync or failed deploy.
- **Rolled back:** a git revert, which Argo reconciles.
- **Who can reach it:** only internal staff call this service. The pipeline is used only by the platform team, and only for this one service until V2 passes.
- **Exit check V0:** the request succeeds with one trace across every tier. A deploy and a rollback succeed through the pipeline. An injected failure (a broken image tag) fires an alert. Build time, lead time and rollback time are recorded as baselines, not targets.

## 5. Phases

**Phase 1 — Contract and trust foundation**
- **Unlocks:** onboarding any further service.
- **Depends on:** V0.
- **Tasks, widest rework first:**
  1. Service manifest schema and template v1 (V1).
  2. OIDC federation; remove all static CI secrets.
  3. Admission policy for signatures plus provenance attestations (SLSA build level 2).
  4. Secrets manager integration.
  5. Break-glass role and drill.
  6. DORA metrics dashboard.
- **Rollback:** templates are versioned, so pin back to the previous version. Admission policy starts in audit mode and switches to enforce once V2 passes.
- **Exit check:** V1 and V2 pass; the break-glass drill is logged.

**Phase 2 — Pilot wave (5 diverse services)**
- **Unlocks:** capacity data and real onboarding cost.
- **Depends on:** V1, V2, and the cost cap from finance.
- **Tasks:**
  1. Onboard the 5 services, legacy fallback kept.
  2. Run V3 using replayed commit traffic for all 50 services.
  3. Write the onboarding runbook.
- **Rollback:** per service, switch the deploy source back to the legacy pipeline.
- **Exit check:** V3 passes; each pilot service has had ≥ 10 production deploys.

**Phase 3 — Progressive delivery**
- **Unlocks:** automatic promotion to production.
- **Depends on:** Phase 2, and SLO metrics for each pilot service.
- **Tasks:**
  1. Argo Rollouts canary steps: 5% → 25% → 100%.
  2. Prometheus analysis templates covering error rate and p99 latency.
  3. Fault-injection runs for V4.
- **Rollback:** disable Rollouts and fall back to rolling updates.
- **Exit check:** V4 passes.

**Phase 4 — Onboarding waves (remaining 45 services)**
- **Unlocks:** full coverage.
- **Depends on:** V3, V4, and owner time booked per wave.
- **Tasks:** waves of about 10 services, internal-facing first and revenue-path services last. Each wave widens only after the previous wave runs 2 weeks with a rollback rate ≤ 10%.
- **Rollback:** per service, as in Phase 2.
- **Exit check:** all 50 services deploy only through the platform; the availability and lead-time budgets are measured against their targets.

**Phase 5 — Legacy decommission**
- **Point of no return:** deleting legacy CI credentials and jobs, guarded by V5.
- **Tasks:**
  1. Freeze legacy CI to read-only.
  2. Rehearse a restore.
  3. Revoke credentials.
  4. Archive logs.
- **Exit check:** V5 passes, and no legacy credential remains valid.

## 6. Validation gates

| ID | Hypothesis | Method | Acceptance threshold | Evidence | Unlocks (if it fails) | Phase |
|---|---|---|---|---|---|---|
| V0 | A change can be deployed, observed and rolled back through every tier in production | Skeleton run plus injected failure | The §4 exit check | Trace ID, alert record and baseline sheet in the platform wiki | Phase 1 | 0 |
| V1 | One template contract fits the services as they really are | Inventory all 50 services' build needs; build 5 of the most dissimilar on template v1 | ≥ 90% fit with extension points only (ASSUMPTION) | Fit matrix in the repo | Template spec frozen at v1 (fail: archetype templates) | 1 |
| V2 | CI cannot put unauthorized code in production | Red-team: a forked-repo PR and a compromised job try to read production credentials and deploy an unsigned image | 0 successes, plus a named security lead's sign-off | Red-team report and policy test logs | Phase 2 exposure (fail: redesign the trust boundary before any onboarding) | starts 0, required before 2 |
| V3 | The platform holds load and cost at 50 services | Replay peak commit rate × 1.5 for 2 days | Queue p90 ≤ 2 min, build p90 ≤ 10 min (ASSUMPTION); cost ≤ finance cap (UNKNOWN until supplied) | Load-test report and billing export | Phase 4 scale (fail: runner pooling, caching, or re-plan build vs buy) | 2 |
| V4 | Canary analysis catches regressions | 10 injected regressions (errors, latency) on pilot services | ≥ 9/10 rolled back automatically within 5 min (ASSUMPTION) | Rollout analysis logs | Automatic promotion in Phase 4 (fail: manual promotion stays) | 3 |
| V5 | Legacy CI is safe to remove | 30 days with zero legacy runs; restore rehearsal | Zero legacy runs; rehearsal succeeds; engineering director approves | Run audit, rehearsal record and signed approval | Decommission (fail: extend coexistence) | 5 |

## 10. Deliberately deferred
- **Per-PR preview environments:** pulled forward if integration bugs dominate the incidents caught after merge.
- **Developer portal (Backstage):** pulled forward if onboarding takes more than 2 days per service.
- **SLSA build level 3 and hermetic remote builds:** pulled forward if a compliance audit or customer contract requires them.
- **Remote build cache (e.g. Bazel):** pulled forward if V3 shows build time p90 above 10 minutes.
- **Multi-region runners:** pulled forward if CI availability falls below 99.5%.
