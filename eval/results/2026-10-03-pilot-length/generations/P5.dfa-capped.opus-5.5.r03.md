# BUILD PLAN: Real-time collaborative document editor

## 1. Classification and constraints
- **What:** A browser-based rich-text editor where many users edit the same document at once and see each other's changes live. Documents are saved permanently, and access is controlled per document.
- **Type:** Software, greenfield, not a small build: it has outside users and customer content that may contain personal data.
- **Dominant constraint:** Correctness. Every copy of a document must end up identical, and no edit the server has confirmed may be lost.
- **Worst failure:** An edit the server confirmed is lost, or two users' copies silently drift apart and the user's document is corrupted.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Time for an edit to reach other editors (same region) | p95 < 200 ms | ASSUMPTION (usual threshold for feeling "live") | V4 |
| Editors per document | 50 at once | ASSUMPTION (typical team doc) | V4 |
| Total live connections | UNKNOWN: product owner supplies expected peak users before Phase 4 | UNKNOWN | V4 |
| Max document size | 10 MB | ASSUMPTION (about 200 rich-text pages) | V1 |
| RPO / RTO | RPO 0 for confirmed edits; RTO ≤ 1 h | ASSUMPTION (the product's core promise) | V2, V5 |
| Availability | 99.9% monthly | ASSUMPTION | Phase 5 SLO dashboard |
| Storage per document | ≤ 5× document size before compaction | ASSUMPTION (basis: edit-history growth) | V1 |
| Operational complexity | ≤ 3 stateful components (Postgres, object store, Redis later) | ASSUMPTION | Phase 4 review |

**Missing inputs:**
1. Is offline editing longer than a reconnect required? I assume short reconnects only. The CRDT default below supports both, so the phase order does not change either way.
2. Data-residency or enterprise compliance needs (legal/product). These could add multi-region work to Phase 1.
3. Expected scale (product).
4. A named security reviewer for V3.

## 3. Tradeoff gates

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Sync algorithm: CRDT vs OT | R3: stored edit format and history can't be changed without migrating every document | CRDT using Yjs | Converges under concurrency; memory and history growth stay within budget at 10 MB | V1 | V1 fails, then switch to OT with the server ordering edits |
| Consistency vs availability | R3: users see this behavior directly | Document content: accept edits locally, merge later. Permissions and metadata: strongly consistent in Postgres | Users accept brief divergence while an edit is in flight; they do not accept permission lag | V1, V3 | Revoked user can still write (V3 fails), then check permissions on every update |
| When the server confirms an edit | R3: a wrong default loses data | Server confirms only after the edit is committed to Postgres | Postgres write latency fits inside the 200 ms budget | V2, V4 | V4 p95 misses budget, then batch commits (group commit) and still confirm only after commit |
| Monolith vs services | R2: splitting takes weeks | Modular monolith: one sync server (Hocuspocus on Node) plus an HTTP API module | One process type handles beta load | V4 | V4 fails at target load, then split the sync tier out |
| Routing a document across servers | R2 | Each document's "room" pinned to one server (consistent hashing); Redis broadcast deferred | One server can hold the hottest document | V4 | A single document exceeds one server, then add Redis pub/sub broadcast |
| Build vs buy | R2: moving off a hosted vendor means migrating all data | Use open-source Yjs/Hocuspocus, self-hosted; don't buy a hosted service like Liveblocks | Team can run websockets in production | V0, V4 | Ops load over budget, then evaluate a hosted vendor before GA |
| Privacy boundary | R3: residency and exposed content | One region. Document content never goes into logs or traces (only document ID and sizes). Encrypted at rest | No residency requirement (UNKNOWN) | Residency input + V3 review | Residency required, then a region column per workspace and a per-region deployment |
| Document IDs and tenancy | R3: IDs end up in URLs and share links | UUIDv7 document ID; `workspace_id` on every row from the first schema | Sharing is scoped to a workspace | V3 | Cross-workspace sharing needed, then add an explicit grant table, never ID changes |

**R1 defaults:** Editor: TipTap on ProseMirror with y-prosemirror. Login: OIDC with a hosted identity provider. CI: GitHub Actions. Infrastructure: Terraform plus managed Kubernetes. Snapshots: S3.
**N/A:** Brownfield migration and AI rows don't apply (greenfield, no AI component).

## 4. Walking skeleton (Phase 0)
- **Request:** An allow-listed internal user logs in, opens document X and types "a". A second browser sees "a" within one second. Reloading shows "a" loaded from storage.
- **Tiers:** Browser (TipTap + Yjs) → TLS load balancer with websocket upgrade → Hocuspocus sync server (token checked on join) → Postgres edit log → broadcast to the second client.
- **Deploy and operations:** GitHub Actions builds the image and Terraform/Helm deploys it to production. OpenTelemetry traces run end to end, tagged with document ID and never content. Structured logs. One alert on websocket error rate. Rollback means redeploying the previous image tag.
- **Who can reach it:** Internal staff only, enforced by an allow-list at the identity provider and a feature flag. No customer documents.
- **Exit check (V0):** See §6.

## 5. Phases

**Phase 1: Data model and convergence** (the change that would force the most rework if wrong)
- Unlocks: a final stored format, so every other feature can build on it.
- Depends on: V0, plus the residency answer.
- Tasks:
  1. V1 fuzz testing and benchmarks.
  2. Specify the schema: `documents`, `doc_updates` (append-only, with a format version), `snapshots` (S3), all carrying `workspace_id`.
  3. Compaction job that turns the edit log into snapshots.
  4. Confirm-after-commit path, then V2.
- Rollback: schema changes are migrations with down scripts. There are no customer documents yet, so the schema can be redone freely until Phase 5.
- Exit check: V1 and V2 pass.

**Phase 2: Identity and access control**
- Unlocks: safe sharing.
- Depends on: Phase 1 (`workspace_id`).
- Tasks:
  1. Workspace membership.
  2. Per-document roles (owner/editor/viewer).
  3. Server rejects writes from viewers.
  4. Revoking access disconnects live sessions.
  5. Signed share links.
  6. Audit log.
  7. V3.
- Rollback: feature flag back to allow-list only.
- Exit check: V3 passes.

**Phase 3: Editing core**
- Unlocks: a usable product.
- Depends on: V1 and V3.
- Tasks, in order:
  1. Rich-text schema (headings, lists, tables, images by object-store reference).
  2. Reconnect buffer and catch-up sync.
  3. Per-user undo.
  4. Version history from snapshots.
  5. Presence and remote cursors (last: the flashiest part, and nothing depends on it).
- Rollback: each feature behind its own flag.
- Exit check: an editor-schema change survives a round trip on V1's fuzz test corpus; reconnecting after 5 minutes offline merges without loss.

**Phase 4: Scale and recovery**
- Unlocks: outside users.
- Depends on: Phase 3, plus the scale input.
- Tasks:
  1. Pin each document's room to one server across nodes.
  2. Point-in-time recovery for Postgres and versioning on the S3 bucket.
  3. V4 load test.
  4. V5 restore drill.
  5. SLO dashboards and on-call runbook.
- Rollback: back to a single node; routing is behind config.
- Exit check: V4 and V5 pass.

**Phase 5: Gradual rollout**
- Unlocks: general availability.
- Depends on: V2, V3, V4, V5, plus the legal documents.
- Tasks: open to one design-partner workspace, then 5% of signups, then 25%, then GA. Widen only after 7 days with no confirmed-edit loss and the SLO met.
- Point of no return: the first customer document. After it, schema changes require online migrations. This is guarded by V2, V3 and V5.
- Exit check: SLO at 99.9% for 30 days in the GA cohort.

| V2 | Confirmed edits survive crashes | 50 scripted editors; `kill -9` the sync server; fail over Postgres; compare every confirmed edit with stored state | 0 confirmed edits lost across 20 runs (RPO 0, ASSUMPTION) | Chaos run logs + diff report in `/bench/v2/` | Exposure (if it fails: fix the confirm path; Phase 5 waits) | 1 |

## 10. Deliberately deferred
- **Full offline-first editing:** pull forward if product confirms editing offline for more than a reconnect.
- **Multi-region:** pull forward if residency is required or V4 latency fails for users outside the region.
- **Comments and suggestion mode:** pull forward after Phase 5 starts, or if the design partner requires it.
- **End-to-end encryption:** pull forward if an enterprise contract requires it. It is R3 because it rules out server-side compaction.
- **Native mobile apps:** pull forward when web usage on mobile exceeds 20%.
- **Public API and webhooks:** pull forward on the first integration request after GA.
