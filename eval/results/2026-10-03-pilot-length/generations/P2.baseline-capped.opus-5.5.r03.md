# Multi-Tenant SaaS Billing System: Architecture

## 1. Scope and Assumptions

- **What "tenant" means here.** A tenant is a customer organization on the SaaS platform. The model is hierarchical (**Platform → Tenant → Account → Subscription**), so the same design also works as billing-as-a-service, where each tenant bills its own end customers.
- **Pricing models:** flat-rate, per-seat, usage-based (metered), tiered or volume pricing, hybrid plans, prepaid credits and commitments.
- **Coverage:** multiple currencies, tax jurisdictions and payment methods.
- **Non-negotiables:**
  - Money is never lost or double-charged.
  - Every number on an invoice can be traced back to its source.
  - One tenant's data never leaks to another, and one tenant can't slow the system down for others.

## 2. High-Level Architecture

```
 Product Services ──usage events──▶ [Ingestion API] ──▶ Kafka (partitioned by tenant_id)
        │                                                   │
        │ entitlement checks                                ▼
        ▼                                         [Metering / Aggregation]
 [Entitlements Svc]◀──┐                                     │ (ClickHouse / TSDB)
   (Redis cache)      │                                     ▼
                      │   [Catalog Svc] ──▶ [Subscription Svc] ──▶ [Rating Engine]
                      │                            │                    │
                      └──── subscription events ───┘                    ▼
                                                              [Invoicing Svc] ──▶ PDF/Email
                                                                       │
                       [Tax Svc] ◀─────────────────────────────────────┤
                                                                       ▼
                                  [Payments Svc] ◀──▶ PSP adapters (Stripe/Adyen/ACH)
                                         │
                                         ▼
                              [Ledger (double-entry)] ──▶ Rev Rec / Reporting / GL export
                                         │
                                  [Dunning Svc]  [Notifications]  [Webhooks out]
```

Each box is a bounded-context service. They communicate through an event bus (Kafka) using the **transactional outbox pattern**: a service writes its state change and the outgoing event in the same database transaction, so the two can't diverge. Synchronous APIs are used only where a request needs an immediate answer, such as entitlement checks and checkout.

## 3. Core Domain Model

| Entity | Key fields / notes |
|---|---|
| **Tenant** | id, region, isolation tier, default currency, timezone, tax settings |
| **Account** (billable entity) | tenant_id, billing contact, currency, tax IDs, payment methods (tokens only), credit balance |
| **Product / Feature** | Catalog items. Features map to entitlements. |
| **Plan / Price** | **Versioned and immutable.** Fields: price model (flat, per_unit, tiered, volume, package), interval, currency, meter_id. A new price creates a new version, so existing customers stay on their old price (grandfathering). |
| **Subscription** | account_id, status (trialing, active, past_due, paused, canceled), billing anchor, term, items[] → price_version, quantity |
| **Subscription Phase / Schedule** | Future-dated changes such as ramps, scheduled downgrades and contract renewals |
| **Meter** | Event name, aggregation (sum, max, unique count, last value), filters |
| **Usage Event** | idempotency_key, tenant_id, account_id, meter, value, timestamp, properties |
| **Invoice / Line Item** | Immutable once finalized. Each line references the price version, the usage aggregate snapshot and the proration window. |
| **Credit Note** | The only way to change a finalized invoice |
| **Payment / Refund / Dispute** | PSP reference, state machine, idempotency key |
| **Ledger Entry** | Double-entry: account, debit/credit, amount in minor units, currency, source document |

**Money rules:**
- Store amounts as integers in minor units, or as decimals with explicit scale for sub-cent usage pricing.
- Always store the currency next to the amount.
- Round only at the line-item level, using a documented rule.
- Never use floats.

## 4. Key Subsystems

### 4.1 Usage Metering
- **Ingestion API:** batched, authenticated per tenant, and requires an `idempotency_key`. It responds `202 Accepted` after a durable write to Kafka.
- **Deduplication:** keyed on `(tenant_id, idempotency_key)` in a deduplication store with a TTL (Redis or RocksDB in Flink), plus a final dedupe at aggregation time.
- **Streaming aggregation:** Flink or Kafka Streams computes running totals per (account, meter, billing period) into ClickHouse. These totals power real-time dashboards and usage-limit enforcement.
- **Late events:** accepted up to a grace window, for example 72 hours after period close. Events after that window go into the next invoice as adjustments, or raise a credit note. Closed invoices are never edited.
- **Snapshots:** when an invoice is generated, the aggregate is frozen as a usage snapshot so the invoice can be reproduced exactly.
- **Raw events** are archived to object storage (Parquet) for audits and replay.

### 4.2 Subscription Engine
- Each subscription is a state machine with explicit transitions, and every transition emits an event.
- **Proration:** mid-cycle changes create proration line items (a credit for unused time and a charge for the new plan), calculated to the second against the tenant's timezone.
- Upgrades can either be invoiced immediately or added to the next invoice. Downgrades usually take effect at period end.
- **Billing anchors and calendar logic** (month ends, leap years, DST) live in one well-tested library.
- **Test clocks:** each sandbox account can have its own virtual clock, so whole lifecycles can be simulated.

### 4.3 Rating and Invoicing
- The **Rating Engine** is a pure function: `(price_version, quantity/usage_snapshot, period, discounts, credits) → line items`. Because it is deterministic and side-effect free, it is easy to test with property-based tests and to replay.
- **Billing run scheduler:**
  - A partitioned job queue finds subscriptions whose period ends in the next window. The query is indexed on `next_billing_at`.
  - Work is spread across workers by hashing on tenant_id.
  - Anchors are naturally spread out, which avoids a midnight-on-the-1st spike. Large tenants can be throttled or given dedicated workers.
- **Invoice lifecycle:** `draft → (review window, optional) → finalized → paid | void | uncollectible`.
  - Finalization assigns a gap-free, tenant-scoped invoice number (some jurisdictions require this).
  - It also calls the Tax Service and writes ledger entries (AR debit, revenue/deferred revenue credit, tax liability credit).
- **Tax:** a vendor such as Avalara, Anrok or Stripe Tax sits behind an adapter. The tax quote is stored with the invoice, and tax is committed only at finalization.

### 4.4 Payments
- **PCI scope:** card data never touches our systems. We use PSP tokenization (hosted fields or Elements), which keeps us at PCI SAQ-A.
- **PSP adapter interface:** `authorize`, `capture`, `refund`, `createMandate`. This allows multiple PSPs, routing by region or cost, and failover.
- **Payment intents** are a state machine, and every PSP call is idempotent (we pass our own idempotency key).
- **Webhooks from PSPs:**
  - Verify the signature and store the raw payload first.
  - Process asynchronously, tolerating duplicates and out-of-order delivery.
  - Treat the PSP as the source of truth for payment status.
- **Daily reconciliation job:** compares PSP settlement reports against the ledger and raises alerts on any mismatch.

### 4.5 Dunning and Collections
- Retry schedules are configurable per tenant or plan. Smart retries can account for decline codes and time of day.
- Customers are notified at each step. Card-updater services are used.
- Escalation: `past_due` → feature restriction (through Entitlements) → suspension → cancellation, or write-off to `uncollectible`.

### 4.6 Entitlements
- Projects active subscriptions and usage into a "what can this account do" view: feature flags, seat limits and usage quotas.
- Served from a Redis cache that is invalidated by subscription events, with p99 under 5 ms. Product services check it on their hot path.
- **Fails open** for paying customers if billing is degraded, since billing should never take the product down. Every fail-open decision is logged.

### 4.7 Ledger and Revenue Recognition
- An append-only, double-entry ledger is the financial source of truth. Every entry balances to zero per transaction.
- Revenue recognition schedules (ASC 606 / IFRS 15) are generated at finalization: subscriptions are recognized ratably, usage is recognized as consumed.
- Exports go to the general ledger (NetSuite, QuickBooks) and the warehouse.

## 5. Multi-Tenancy Design

### Isolation tiers
| Tier | Model | For |
|---|---|---|
| Pooled | Shared Postgres cluster, `tenant_id` on every row, **Row-Level Security** enforced | Long tail of SMB tenants |
| Bridged | Dedicated schema or database on shared infrastructure | Mid-market tenants, data residency needs |
| Silo | Dedicated cell (DB, workers, Kafka partitions) | Enterprise tenants, compliance requirements |

### Controls that apply to every tier
- **Tenant context** comes from the authenticated token and travels through every request and event. It is set as a Postgres session variable for RLS. Queries are never built from client-supplied tenant IDs.
- **Composite keys and indexes** start with `tenant_id`. The tenant ID is also included in cache keys, Kafka message keys and object-storage prefixes.
- **Cell-based deployment:** tenants are mapped to cells (regional shards) through a routing directory. This limits the blast radius of failures and supports data residency (EU or US cells).
- **Noisy-neighbor protection:**
  - Per-tenant rate limits on ingestion.
  - Weighted fair queuing in the billing-run workers.
  - Per-tenant Kafka quotas.
  - Large tenants can be moved to their own cell.
- **Per-tenant configuration:** branding, invoice templates, numbering sequences, dunning policies, tax settings and webhook endpoints.
- **Encryption:** at rest and in transit. Silo tenants can have per-tenant KMS keys (BYOK). PII fields get field-level encryption.
- **Automated isolation tests:** CI runs cross-tenant access tests that try to read data from another tenant's context and must fail.

## 6. Reliability and Correctness

- **Idempotency everywhere:** ingestion, API mutations (an `Idempotency-Key` header), PSP calls and event consumers (an inbox table keyed by event ID).
- **Exactly-once effects:** we build these from at-least-once delivery plus idempotent consumers, rather than relying on exactly-once delivery guarantees.
- **Immutability:** finalized invoices, ledger entries and price versions are never updated. They are only corrected with new entries.
- **Audit log:** every state change records the actor, the before and after state, and a timestamp. It is stored in tamper-evident, append-only storage.
- **Reconciliation jobs:**
  - Usage events against aggregates.
  - Invoices against ledger entries.
  - Ledger entries against PSP settlements.
  - Subscriptions against entitlements.
  
  Any drift pages the on-call engineer.
- **Replayability:** raw usage plus versioned prices plus a deterministic rating engine means any invoice can be regenerated and compared.
- **Availability targets:**
  - Ingestion and entitlements: 99.99%.
  - Invoicing: 99.9%. It is batch-tolerant, and a delay is acceptable while a wrong invoice is not.
- **Disaster recovery:** Postgres with synchronous replicas and point-in-time recovery, Kafka replication factor of 3, and cross-region backups. Target RPO under 1 minute for the ledger.

## 7. APIs and Integrations

- Public REST API, versioned by date header, with cursor pagination and expandable objects. Includes a sandbox mode with test clocks.
- **Outbound webhooks** (e.g. `invoice.finalized`, `payment.failed`, `subscription.updated`):
  - Signed with HMAC.
  - Retried with exponential backoff.
  - Viewable in a per-tenant delivery log, with replay.
- Customer portal: invoices, payment methods, plan changes, usage dashboards.
- Admin console: refunds, credits, invoice adjustments with approval workflows, and impersonation with an audit trail.

## 8. Technology Choices

| Concern | Choice |
|---|---|
| Core OLTP | PostgreSQL (RLS, serializable transactions for ledger writes) |
| Event bus | Kafka with outbox (Debezium CDC) |
| Usage aggregation | Flink + ClickHouse |
| Cache / entitlements | Redis |
| Workflows (dunning, billing runs) | Temporal, which gives durable timers and retries |
| Documents | S3 + PDF rendering service |
| Observability | OpenTelemetry traces tagged with tenant_id. Per-tenant SLO dashboards. |

## 9. Phased Delivery

1. **MVP:** catalog, flat and per-seat subscriptions, invoicing, one PSP, basic dunning, ledger, pooled tenancy with RLS.
2. **Usage:** metering pipeline, tiered and volume pricing, real-time usage dashboards, entitlements service.
3. **Scale and compliance:** tax engine, multiple currencies, revenue recognition, cell architecture, silo tier, SOC 2 controls.
4. **Advanced:** contracts and commitments, prepaid credits, multiple PSPs with routing, smart retries, self-serve pricing experiments.

## 10. Key Trade-offs

- **Correctness over latency:** invoicing is asynchronous and reconciled. Only entitlements sits on the hot path.
- **Immutable records plus corrections** cost more storage but make audits and debugging much easier.
- **Pooled tenancy** is cost-efficient. The cell and silo tiers are the escape hatch for scale and compliance, so we don't need to rearchitect later.
- **Build vs. buy:** tax and payment processing are bought through adapters. Rating, the ledger and entitlements are built in-house, because they are the core differentiators and correctness risks.
