# Plan: Customer-Support RAG Chatbot over Help-Center Docs

I don't know your docs platform, ticketing system, or traffic yet, so this plan assumes a typical setup: a few hundred to a few thousand articles in a CMS like Zendesk Guide, Intercom, or Confluence, an existing human-support queue, and an English-first audience. The questions at the end cover what would change the plan.

---

## 1. Goals and Success Metrics

**Main goal:** Resolve common support questions correctly using only official docs. When the bot can't, it hands off to a human smoothly.

| Metric | Target (initial) |
|---|---|
| Answer faithfulness (claims backed by cited docs) | ≥ 95% |
| Deflection rate (sessions resolved without a ticket) | 25–40% |
| Correct escalation (hands off when it should) | ≥ 90% |
| CSAT on bot conversations | ≥ human-agent baseline minus 0.3 |
| p95 latency to first token | < 2.5 s |

Faithfulness and correct escalation are the guardrail metrics. Deflection only counts if those two hold, because a confidently wrong answer costs more than a ticket.

---

## 2. Architecture Overview

```
Help-center CMS ──► Ingestion pipeline ──► Chunk store + Vector index + Keyword index
                                                    │
User ─► Chat widget ─► Orchestrator ─► Query rewrite ─► Hybrid retrieval ─► Rerank
                            │                                                  │
                            │◄──────── LLM generation (grounded, cited) ◄──────┘
                            │
                            ├─► Guardrails (input/output)
                            ├─► Escalation → ticketing / live agent
                            └─► Logging, feedback, analytics
```

**Components:**
- **Ingestion service:** a scheduled job plus a webhook for CMS updates.
- **Search layer:** a vector database (pgvector, Pinecone, Weaviate, or OpenSearch) combined with BM25 keyword search.
- **Orchestrator:** a stateless API service that handles sessions, retrieval, prompting, and tool calls.
- **LLM:** a hosted frontier model for generation, plus a smaller, cheaper model for query rewriting and classification.
- **Chat UI:** embedded in the help center and app, with citations, thumbs up/down, and a "talk to a human" button.

---

## 3. Data Ingestion and Indexing

**Sources (in priority order):**
1. Published help-center articles
2. Release notes and known-issues pages
3. Macros or canned responses that support has approved
4. *Later, optional:* resolved tickets, mined into an FAQ that a human reviews. Never index raw tickets directly, because they contain PII and are often wrong.

**Pipeline steps:**
- **Fetch** through the CMS API. Capture the article ID, URL, title, section/category, locale, last-updated date, product/plan tags, and visibility (public vs. internal).
- **Clean:** strip navigation and boilerplate. Keep the heading hierarchy, lists, tables (convert to markdown), and code blocks. Extract alt text from images. Flag articles that depend heavily on screenshots for rewriting.
- **Chunk:** split on headings, aiming for about 300–600 tokens with about 50 tokens of overlap. Prepend each chunk with its article title and heading path (e.g., "Billing > Refunds > Annual plans"). Keep numbered step lists in one chunk.
- **Embed:** use one embedding model throughout and store the model version with each vector. Re-embed everything whenever the model changes.
- **Keep fresh:** CMS webhooks trigger re-indexing of the changed article, plus a full nightly reconciliation that deletes unpublished articles. Target: changes are live within 15 minutes.
- **Filter at query time:** use metadata (locale, product, plan tier, public/internal) so users never see content meant for another audience.

---

## 4. Retrieval

1. **Query rewriting:** a small model turns the user's latest message plus recent chat history into a self-contained search query. It also extracts filters like product or plan when they're stated.
2. **Hybrid search:** fetch the top ~30 results from both vector and BM25 search and merge them with reciprocal rank fusion. BM25 matters here because support queries often contain exact terms like error codes, SKUs, and feature names.
3. **Reranking:** a cross-encoder reranker (e.g., Cohere Rerank, bge-reranker) picks the top 4–6 chunks.
4. **Confidence check:** if the top rerank score falls below a calibrated threshold, skip generation and go to the clarify-or-escalate path. This is the main defense against made-up answers.
5. **Expand context:** optionally pull in neighboring chunks or the full short article when a chunk is part of a procedure.

**Personalization (phase 2):** if the user is logged in, pass their plan, region, and product to filter or boost results. Don't add account-specific data until the tool-use phase.

---

## 5. Generation

**System prompt rules:**
- Answer **only** from the provided context. If the context doesn't answer the question, say so and offer escalation.
- Cite sources inline (e.g., [1], [2]) using article URLs, and show them as clickable links.
- Be concise: steps first, then caveats. Match the user's language when localized docs exist.
- Never invent prices, policies, SLAs, legal terms, or UI paths.
- Ask one clarifying question when the request is ambiguous, such as when the answer differs by plan or platform.

**Output format:** structured JSON containing the `answer`, `citations[]`, a `confidence` field, and an `escalate` flag. The UI renders it, and the orchestrator acts on the flags.

**Post-generation check (optional but recommended):** a cheap verification pass confirms each claim is supported by the cited chunks. Anything unsupported gets regenerated or escalated.

---

## 6. Guardrails and Safety

**Input:**
- Detect prompt injection
- Redact PII before logging (emails, card numbers, phone numbers)
- Filter abuse and toxicity
- Steer off-topic requests back to support topics

**Output:**
- Allow only citation links to your own domains
- Hard-block certain content: no legal or medical advice, no promises of refunds or credits unless docs state the policy exactly

**Sensitive intents always go to a human.** These include account security or compromise, billing disputes, cancellations (if retention flows apply), legal or GDPR requests, outages, and complaints with strong negative sentiment. A lightweight intent classifier catches them before or alongside retrieval.

**Docs are untrusted input.** Sanitize them and don't let retrieved text override the system prompt.

---

## 7. Escalation and Handoff

**When to escalate:**
- Retrieval confidence is low
- The model sets the `escalate` flag
- A sensitive intent is detected
- The user asks for a human
- The user gives two thumbs-down in a row or rephrases the same question repeatedly

**How:** create a ticket or start a live-chat handoff carrying the full transcript, the retrieved articles, the detected intent, and a model-written summary, so the customer never has to repeat themselves.

**Outside business hours:** create the ticket and tell the user the expected response time.

---

## 8. Evaluation

**Before launch:**
- **Golden set:** 200–400 real questions taken from historical tickets and search logs, labeled with the correct article(s) and a reference answer. Include unanswerable and sensitive questions on purpose (about 20%).
- **Retrieval metrics:** recall@5 and MRR against the labeled articles.
- **Answer metrics:** faithfulness, correctness, citation accuracy, correct refusal/escalation, and tone. Score with an LLM judge calibrated against about 100 human-graded examples.
- **Red-team set:** prompt injection, jailbreaks, attempts to get competitor or pricing information, and attempts to extract PII.
- **Regression gate:** run in CI on every change to prompts, models, chunking, or the index. Block deploys that regress past set thresholds.

**After launch:**
- Have support leads review a sample of 50–100 conversations each week.
- Track thumbs up/down, escalation reasons, "no answer found" queries, and whether a ticket gets reopened after the bot "resolved" it.
- **Content-gap report:** cluster unanswered questions and send them to the docs team. This is often the most valuable output of the whole project.

---

## 9. Operations

- **Observability:** trace each conversation turn (rewritten query, retrieved IDs and scores, prompt version, model, latency, tokens, cost). Langfuse, LangSmith, Arize, or OpenTelemetry all work.
- **Cost control:** cache embeddings and frequent question→answer pairs (invalidate when the source article changes). Use the small model for classification and rewriting. Cap context size.
- **Versioning:** prompts, chunking settings, and model choices live in config with version IDs, so you can A/B test and roll back.
- **Privacy:** redact PII in logs, set a retention policy, and check your data processing agreement with the LLM vendor (no training on your data). Store data in-region if required.
- **Availability:** if the LLM fails, show plain search results and offer escalation.

## 10. Phased Roadmap

| Phase | Duration | Scope |
|---|---|---|
| **0. Discovery** | 1–2 wks | Audit docs (coverage, staleness, duplicates); pull the top 100 ticket intents; build the golden set; pick the stack |
| **1. MVP (internal)** | 3–4 wks | Ingestion, hybrid retrieval, rerank, grounded answers with citations, basic guardrails, eval harness. Support agents test it as an assistant |
| **2. Limited beta** | 3–4 wks | Public widget for 5–10% of traffic or one product area; escalation into ticketing; feedback UI; dashboards; weekly reviews |
| **3. General availability** | 2–4 wks | Full rollout; logged-in personalization; multilingual (if localized docs exist); content-gap workflow with the docs team |
| **4. Actions (optional)** | ongoing | Authenticated tools: order status, password reset links, plan details. Each needs strict permissions and confirmation steps |

**Team:** 1–2 backend/ML engineers, 0.5 frontend, a support-ops partner who owns the golden set and reviews, a docs owner, and security/privacy review at phases 1 and 2.

---

## 11. Key Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Stale or contradictory docs produce wrong answers | Docs audit in phase 0; prefer the newest article; content-gap loop; show "last updated" dates on citations |
| Made-up policies or prices | Confidence threshold, strict grounding prompt, verification pass, blocked topics |
| Users stuck in a bot loop | Always-visible human option; auto-escalate on repeated frustration |
| Prompt injection via user input or doc content | Sanitize input, separate instructions from context, restrict tools |
| Deflection looks good but customers leave unhappy | Track CSAT, reopen rates, and repeat contacts, not just deflection |
