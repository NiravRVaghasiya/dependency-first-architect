# Building a CI/CD Platform for 50 Microservices: Phased Plan

## How the plan is ordered

1. **Prove it on a few services before rolling it out to all 50.** Every pipeline pattern is tested on a small set of pilot services first.
2. **Build things in the order they depend on each other.** Each phase relies on the one before it. For example, safe canary releases need observability, and observability needs consistent deployments.
3. **Introduce checks as warnings first, then enforce them.** Teams will get around rules they didn't help shape.
4. **Run the platform as a product.** Use versioned templates, publish service levels, and measure how much teams actually use it.

**Rough timeline:** about 6–8 months with a platform team of 4–6 engineers. Several phases overlap.

---

## Phase 0: Discovery and Key Decisions (Weeks 0–3)

**Goal:** Understand the current state and make the hard-to-reverse choices up front.

- **List all 50 services.** For each, record its language, build tool, runtime (Kubernetes, VMs, serverless), owning team, how often it deploys, which services it depends on, and any compliance requirements.
- **Group services into types.** You'll usually find 4–6, such as Java/Spring on Kubernetes, Node/TypeScript, Go, Python workers, and legacy VM services. **Templates will be built per type, not per service.**
- **Record a baseline of the four DORA metrics:** how often you deploy, how long a change takes to reach production, what share of changes fail, and how long it takes to recover.
- **Make these decisions and write each one down as an architecture decision record (ADR):**
  - Monorepo or one repo per service
  - CI engine (GitHub Actions, GitLab CI, Buildkite, Tekton)
  - How deployments happen: GitOps (Argo CD or Flux) or pipelines that push changes. GitOps is recommended at this scale because it gives you audit history and detects drift.
  - Artifact registry, secrets approach, and environment layout (dev, staging, prod, plus temporary preview environments)
  - Branching model. Trunk-based development with short-lived branches is recommended.
- **Pick 3 pilot services** that cover your most common types. Include one with awkward dependencies so the hard cases show up early.

**Done when:** the decisions are signed off, the service types are defined, the pilots are chosen, and the baseline metrics are recorded.

## Phase 1: Foundations (Weeks 2–6)

**Goal:** Set up the shared infrastructure every pipeline needs.

- **Define the platform itself as code** (Terraform or Pulumi). That includes build runners, the registry, clusters, and access rules.
- **Build runners:** short-lived, autoscaling, isolated runners that support build caching. Don't share long-lived runners between teams.
- **Artifact registry:** store container images and packages under tags that never change (for example, the Git commit ID). Set retention policies.
- **Secrets and identity:** pipelines should get short-lived cloud credentials through OIDC instead of stored keys. Keep secrets in Vault or the cloud provider's secret manager. Give each service the minimum permissions it needs.
- **Repo conventions:** a CODEOWNERS file, branch protection, required reviews, and a standard repo layout.

**Done when:** a pilot service can build on the new runners and push a signed image, with no long-lived credentials stored anywhere.

---

## Phase 2: Standard CI Pipeline Templates (Weeks 4–10)

**Goal:** One reusable, versioned CI template per service type.

- **Template stages:** checkout → restore cache → lint → unit tests → build → container image → software bill of materials (SBOM) → sign (Cosign) → push → publish results.
- **Teams reference the templates; they don't copy them.** Use reusable workflows or includes pinned to a version (for example, `ci-templates@v1.4`), so improvements reach all 50 services by bumping a version number.
- **Allow controlled extension points** (extra steps before and after testing) so teams don't fork the templates.
- **Speed targets:** under 10 minutes for pull-request checks, achieved with caching, parallel tests, and builds that only rebuild what changed (especially in a monorepo).
- **Build once and promote the same artifact.** Never rebuild for each environment.
- **Apply the templates to the 3 pilots** and iterate based on the pilot teams' feedback.

**Done when:** all 3 pilots use the templates, PR checks take under 10 minutes, and the templates are documented and versioned.

---

## Phase 3: Continuous Deployment to Non-Production (Weeks 8–12)

**Goal:** Every merge to main deploys to dev and staging automatically.

- **GitOps config repo(s):** an environment folder for each service. Argo CD or Flux syncs from Git.
- **Shared deployment packaging:** a common Helm chart or Kustomize base library that sets sensible defaults for health checks, resource limits, pod disruption budgets, and security settings.
- **Automatic promotion:** when CI succeeds, a bot updates the image tag in the dev config. Moving from dev to staging is triggered by test results, through a pull request or a promotion tool such as Kargo.
- **Optional: preview environments for each pull request**, for teams that need them.

**Done when:** all 3 pilots deploy to dev and staging with no manual steps, and environment drift is detected and reported.

---

## Phase 4: Observability Before Production Automation (Weeks 10–14)

**Goal:** Collect the signals that safe production releases depend on. *This has to come before Phase 6.*

- **Standard telemetry:** OpenTelemetry instrumentation, plus default metrics covering request rate, errors, and latency for every service.
- **Deployment markers on dashboards:** record each version, commit and deploy time.
- **Platform dashboards:** DORA metrics for each service, plus pipeline length, failure rate, flaky tests and queue times.
- **Service levels for each pilot service**, which later feed automated canary analysis.

---

## Phase 5: Quality and Security Checks (Weeks 10–16, starting as warnings only)

Add these to the templates in **warning mode first**. Turn on enforcement once false positives are under control.

- **Code and dependency scanning:** static analysis (Semgrep or CodeQL), dependency and license scanning, and container image scanning (Trivy or Grype).
- **Secret detection** in pull requests and in commit history.
- **Policy as code:** OPA/Conftest checks in CI, and Kyverno or Gatekeeper at the cluster's admission step. Examples: only signed images can run, no `latest` tags, resource limits are required.
- **Build provenance:** SLSA Level 2–3 provenance records, verified before deployment.
- **Testing between services:** contract tests (for example, Pact) so services can deploy independently without a fragile end-to-end test environment. Keep a small end-to-end smoke test suite in staging.

**Done when:** checks are enforced for critical and high-severity findings, there is a documented exception process with expiry dates, and false positives are below an agreed threshold.

---

## Phase 6: Production Deployment and Progressive Delivery (Weeks 14–20)

**Goal:** Production releases that are safe, automated and easy to reverse.

- **Gradual rollouts:** canary or blue-green releases using Argo Rollouts or Flagger, with automated analysis of error rates and latency from Phase 4.
- **Automatic rollback** when the analysis fails. A rollback should mean reverting a Git commit, not running a manual procedure.
- **Approvals:** require a human only for regulated services, and keep a record of every approval. Integrate change records with ServiceNow or Jira if compliance requires it.
- **Feature flags** (LaunchDarkly, Unleash or OpenFeature) to separate deploying code from releasing features.
- **Guardrails:** deployment freeze windows, rate limits on deployments, and a documented, audited emergency "break-glass" path.
- **Run a game day:** practice a failed deployment and confirm that automatic rollback works.

**Done when:** the pilots deploy to production on demand, their median lead time is under one day, and automatic rollback has been proven to work.

---

## Phase 7: Migration Waves (Weeks 16–30)

**Goal:** Move the remaining 47 services onto the platform.

- **A migration kit:** a checklist, a codemod or CLI that generates pipeline config, a template repo, and a runbook.
- **Waves of 8–12 services, grouped by type:**
  - Wave 1: simple, stateless services that teams are keen to move.
  - Waves 2–3: the bulk of services.
  - Final wave: legacy, stateful and VM-based services, which may need custom extensions.
- **Each wave lasts about 2 weeks.** Pair a platform engineer with one champion from each service team. Hold office hours and keep a shared migration tracker.
- **Run old and new pipelines in parallel briefly, then remove the old ones.** Set a firm shutdown date for the legacy CI system.
- **After each wave, run a retrospective** and feed the lessons back into the templates.

**Done when:** all 50 services are on the platform, legacy pipelines are switched off, and every service is in the DORA dashboard.

---

## Phase 8: Self-Service and Continuous Improvement (Week 24 onward)

- **Developer portal** (Backstage or Port): a service catalog, ownership information, scorecards (test coverage, check compliance, DORA metrics), and a scaffolder that creates new services with CI/CD already set up.
- **Automated updates:** Renovate or Dependabot opens pull requests to bump template versions and base images.
- **Platform service levels:** CI availability, 95th-percentile queue time, and how quickly deployments sync.
- **Cost controls:** use spot instances for runners, tune caches, and track CI minutes per team.
- **Quarterly reviews:** developer satisfaction surveys, DORA trends, and template adoption rates.

## Common Mistakes to Avoid

- **Building custom pipelines for each service.** 50 bespoke pipelines can't be maintained. Use a few service types and versioned templates.
- **Enforcing security checks on day one.** Teams lose trust in the platform and start working around it.
- **Rebuilding artifacts for each environment.** You lose provenance and traceability.
- **Relying on a large shared end-to-end environment.** Use contract tests and gradual rollouts instead.
- **Automating production deployments before you have observability.** Canary releases without metrics are just guesses.
- **Never finishing the migration.** Without a firm date to shut down the old pipelines, you end up supporting two systems indefinitely.

## Success Metrics (6–8 Months)

- 100% of services on the standard templates
- Median lead time under 1 day, with multiple deploys per day possible for each service
- Failed-change rate under 15%, and recovery time under 1 hour
- PR checks under 10 minutes at the 95th percentile
- Zero long-lived credentials in CI, and all production images signed and verified
