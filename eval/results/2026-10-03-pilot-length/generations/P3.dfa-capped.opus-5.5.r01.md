# BUILD PLAN: CI/CD platform for 50 microservices

## 1. Classification and constraints
- **What:** A shared build, test, artifact and deploy platform that 50 services run through.
- **Type:** Infra plus software. Brownfield, because the 50 services already exist with their own pipelines (ASSUMED). Not a small build, since many teams use it and it holds production credentials.
- **Dominant constraint:** Correctness and security of what reaches production, then availability of the deploy path.
- **Worst failure:** The platform holds deploy rights to all 50 services. If its credentials are compromised, or one bad template change goes out, all 50 can be hit at once, in production.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Commit to production lead time | p50 ≤ 30 min | ASSUMPTION (a common platform goal; confirm with eng leadership) | V3 |
| Build queue wait | p95 ≤ 2 min at peak concurrency | ASSUMPTION; peak load is UNKNOWN until Phase 0 measures commit volume | V3 |
| Platform availability | 99.5% in business hours, plus a break-glass deploy path | ASSUMPTION | Phase 2 |
| Bad-release recovery | automatic rollback ≤ 10 min after canary breach | ASSUMPTION | V4 |
| CI compute cost | UNKNOWN: finance/platform owner supplies the monthly ceiling before Phase 2 | UNKNOWN | V3 |
| Operational complexity | ≤ 3 platform-owned components (CI, GitOps controller, registry) | ASSUMPTION (platform team size UNKNOWN) | Phase 1 |

**Missing inputs (most plan-changing first):**
1. Runtime target. I assumed Kubernetes. If it is VMs or serverless, the deploy tier and V4 method change, but the phase order does not.
2. Any compliance regime (SOC 2, PCI). If one applies, V2 gains named control owners and an audit-evidence retention task in Phase 1.
3. The existing CI tool and repo layout.
4. Platform team headcount and CI budget.

## 3. Tradeoff gates

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Trust boundary / credential model | R3: a short time wrong can expose production for all 50 services | OIDC federation, one role per service per environment, no long-lived secrets in CI | Cloud and registry support workload identity | V2 | V2 fails, or a provider lacks OIDC (then use a vault with ≤1 h leases) |
| Pipeline contract (shared templates vs per-service) | R2: changing it means coordinated edits across 50 repos | Versioned reusable templates with declared override points | ≥ 90% of services fit with ≤ 3 overrides (ASSUMPTION) | V1 | V1 fit < 90%: offer 2–3 archetype templates |
| Build vs buy | R2: migrating pipelines is weeks of work | Buy and compose: GitHub Actions + self-hosted autoscaled runners, Argo CD, managed OCI registry | The existing SCM is GitHub (ASSUMPTION) | V0, V3 | Not GitHub, or V3 cost fails: switch to the SCM-native CI |
| Push vs pull deploy (sync vs async) | R2: it changes the credential topology | Pull/GitOps: CI writes the image digest to an env repo and Argo reconciles. CI never holds cluster credentials | Reconcile lag ≤ 3 min | V0 baseline | Lag breaks the lead-time budget: push from a dedicated deploy job |
| Availability vs consistency of deploy state | R2 | Git is the single source of truth. A break-glass path is a manual commit to the env repo, under two-person review | Git outage is rarer than the platform SLO | Phase 2 drill | Drill exceeds RTO: add a mirrored env repo |
| Migration and system of record | R2: coexistence across teams | Wave migration. The legacy pipeline stays the fallback and keeps write rights until that service's wave exit. System of record = whichever pipeline last deployed, recorded in the env repo | Old and new pipelines can coexist per service | Phase 4 wave checks, V5 | A wave fails twice: pause and fix the template |

**R1 defaults:** build caching via remote cache; test runners stay language-native; image signing with cosign + Sigstore.
**N/A:** monolith vs services, because the services are inherited; personal-data boundary, because the platform handles code, not user data. Logs still get secret-scrubbing, see §7.

## 4. Walking skeleton (Phase 0)
- **Request:** A real commit to one low-risk internal service is built, unit-tested, pushed to the registry by digest, written to the env repo, synced to a production canary by Argo, and serves a request. A revert commit then rolls it back.
- **Tiers:** SCM → CI runner → registry → env repo → Argo CD → cluster → service → telemetry.
- **Day zero:** OpenTelemetry traces carry the commit SHA end to end, plus pipeline logs and an alert on deploy failure or sync drift. Rollback is a Git revert. Discovery also runs now: inventory all 50 services (language, build tool, deploy target, existing pipeline, who depends on each pipeline). Each entry is marked CONFIRMED or ASSUMED, and commit volume and current lead times are baselined.
- **Who can reach it:** Only the one internal service, behind its existing flag. The legacy pipeline stays the fallback, and no other team is onboarded.

**Exit check (V0):** The commit reaches production with one trace across every tier. Deploy and rollback both succeed through the pipeline. An injected failure (a broken test, or a forced sync failure) fires an alert. Lead time, queue wait and sync lag are recorded as near-zero-load baselines.

## 5. Phases

**Phase 1: Trust and contracts** (widest rework first)
- **Unlocks:** Exposure to more services (V2), and the template specification (V1).
- **Depends on:** V0 and the inventory.
- **Tasks:**
  1. OIDC roles for each service and environment; revoke the static secrets on the skeleton service.
  2. Artifact identity: immutable digests, SLSA provenance, cosign signatures.
  3. Admission policy (Kyverno) that rejects unsigned images or images without provenance, in audit mode first, then enforce.
  4. Branch protection and required reviews on the template and env repos.
  5. Pipeline contract v1 with versioned templates.
- **Rollback:** Pin the skeleton service to the previous template version and set admission back to audit mode.
- **Exit check:** V1 and V2 pass.

**Phase 2: Scale substrate**
- **Unlocks:** Concurrent load from 50 services.
- **Depends on:** V1 and V2.
- **Tasks:**
  1. Autoscaled ephemeral runners with no persistence between jobs.
  2. Remote build cache.
  3. Registry retention policy.
  4. DORA metrics dashboard.
  5. Break-glass drill.
- **Rollback:** Cap runner scale and fall back to a fixed pool.
- **Exit check:** V3 passes and the break-glass drill succeeds.

**Phase 3: Progressive delivery**
- **Unlocks:** Safe exposure of business-critical services.
- **Depends on:** V2 and V3.
- **Tasks:**
  1. Argo Rollouts canary at 5% → 25% → 100%.
  2. Analysis templates on the error rate and latency SLOs each service declares.
  3. Automatic rollback.
- **Rollback:** Disable Rollouts per service; Argo falls back to plain sync.
- **Exit check:** V4 passes.

**Phase 4: Wave onboarding** (smallest exposure first)
- **Unlocks:** All 50 services on the platform.
- **Depends on:** V4, and team time for each wave.
- **Tasks:** Waves of 4 → 10 → 15 → 20 services, lowest-criticality first. In each wave:
  1. Add the template.
  2. Run new and legacy pipelines in parallel (new is build-only) for ≥ 5 deploys.
  3. Switch deploy rights to the new path.
  4. Legacy stays callable as the fallback.
- **Rollback:** Re-enable the legacy deploy step for that service.
- **Exit check (per wave):** Every service in the wave completes ≥ 5 production deploys and 1 rollback through the platform, with lead time inside budget.

**Phase 5: Legacy decommission** (point of no return)
- **Depends on:** All Phase 4 waves, then V5.
- **Tasks:**
  1. Archive the legacy pipeline configs.
  2. Revoke legacy credentials.
  3. Delete legacy runners.
- **Rollback:** Restoring from the archive works until the credentials are revoked. Revocation is the point of no return, guarded by V5.

## 6. Validation gates

| ID | Hypothesis | Method | Acceptance threshold | Evidence | Unlocks (if it fails) | Phase |
|---|---|---|---|---|---|---|
| V0 | A change can be deployed, observed and rolled back through every tier in production | Skeleton run plus an injected failure | The §4 exit check | Trace export and pipeline run logs in the platform repo `/evidence/v0` | Phase 1 (if it fails: fix the failing tier before anything else) | 0 |
| V1 | One versioned template fits most services | Onboard 5 inventory-representative services (one per language/build archetype) to non-production | ≥ 90% of the inventory maps to the template with ≤ 3 overrides (ASSUMPTION) | Fit matrix in `/evidence/v1` | Template spec frozen at v1 (if it fails: archetype templates, then re-run) | 1 |
| V2 | A compromised PR or runner cannot reach production | Red-team test: a fork PR tries to read secrets; an unsigned image is pushed; a stolen runner token is replayed after expiry. Plus a credential audit | Zero long-lived production secrets in CI, all 3 attacks blocked, and pass sign-off from the named security lead (to be confirmed) | Test report and signed review in `/evidence/v2` | Onboarding beyond the skeleton (if it fails: no exposure; fix and re-test) | 1 |
| V3 | Runners meet queue and cost budgets at peak | Replay 2× the peak commit rate from the Phase 0 baseline for 2 h | Queue p95 ≤ 2 min and lead time p50 ≤ 30 min (ASSUMPTION); projected monthly cost ≤ finance ceiling (UNKNOWN, cannot pass until supplied) | Load-test report and cost projection in `/evidence/v3` | Runner commitment and Phase 3 (if it fails: caching and right-sizing, or the build-vs-buy flip) | 2 |
| V4 | A bad release rolls back automatically | Deploy a deliberately faulty build to a canary service, 3 runs | Rollback completes ≤ 10 min after SLO breach in 3/3 runs (ASSUMPTION), with ≤ 5% of traffic exposed | Rollout analysis logs in `/evidence/v4` | Phase 4 (if it fails: manual canary gates for critical services) | 3 |
| V5 | Legacy pipelines are safe to remove | Rehearse a restore from the archive on one service, plus usage audit | Zero legacy pipeline runs in 30 days; restore rehearsal succeeds; go/no-go from the named platform owner | Audit log and rehearsal record in `/evidence/v5` | Credential revocation (if it fails: keep legacy in read-only for 30 more days) | 5 |

## 7. Cross-cutting concerns

| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|
| 0 | Scoped deploy role, branch protection on the env repo | Commit-SHA trace across tiers, deploy alert | Pipeline-as-code, pinned action SHAs | Git-revert rollback, legacy pipeline as fallback |
| 1 | OIDC, signing, admission policy, secret scrubbing in logs | Admission-deny and auth-failure alerts | Provenance attestations, digest-only deploys | Admission audit mode before enforce |
| 2 | Ephemeral runners, network egress allow-list | Queue, cache-hit and cost dashboards | Hermetic builds, locked base images | Autoscale floor, break-glass drill |
| 3 | Rollout permissions per service | SLO analysis per canary | Analysis templates versioned with the service | Automatic rollback (V4) |
| 4 | Legacy deploy rights removed per wave | DORA metrics per service | Template version pinned per service | Per-service fallback to legacy |
| 5 | Legacy credentials revoked | Alert on any legacy invocation | Archived configs | Restore rehearsal (V5) |

## 10. Deliberately deferred
- **Developer portal (Backstage):** pull forward when onboarding friction becomes the top support ticket.
- **Ephemeral preview environments:** pull forward when integration bugs that escape staging exceed an agreed rate.
- **Multi-region runners and a mirrored env repo:** pull forward if the Phase 2 drill exceeds RTO, or if the SLO is raised.
- **Policy beyond signing (SBOM vulnerability blocking):** pull forward once V2 passes and the security lead sets thresholds.
- **Monorepo or build-graph tooling (Bazel):** pull forward if V3 shows build time dominates lead time.
