# CI/CD Platform for 50 Microservices: Build Sequence

The plan has eight phases. Each one depends on the one before it. Service migration happens in waves so mistakes surface on 3 services before they reach 50.

---

## Phase 0: Discovery and Baseline (Weeks 1–3)

**Goal:** Know what you're standardizing before you build anything.

- **Inventory all 50 services:** language, framework, build tool, repo layout, current CI, deploy target, owners, dependencies, stateful vs. stateless.
- **Group services into archetypes.** Most fleets fall into 4–6 groups, such as "Java/Gradle REST API," "Node worker," "Python ML service" and "legacy VM app." Templates are built per archetype, not per service.
- **Measure the starting point with DORA metrics:** deploy frequency, lead time, change failure rate and time to restore. Without a baseline you can't show the platform helped.
- **Interview teams** about pain points, and find 2–3 friendly pilot teams.

**Key decisions to lock in:**
- CI engine (GitHub Actions, GitLab CI, Jenkins, Buildkite, Tekton)
- Deploy model: GitOps (Argo CD or Flux) or push-based
- Runtime target (Kubernetes, ECS, serverless)
- Repo strategy: polyrepo or monorepo. This affects caching, triggers and versioning.
- Branching model. Trunk-based development is strongly recommended.

**Exit criteria:** Archetypes defined, tools chosen, pilot services picked, baseline metrics recorded.

---

## Phase 1: Platform Foundations (Weeks 3–7)

**Goal:** Build the infrastructure everything else depends on, defined entirely as code.

1. **Infrastructure as code for the platform itself** (Terraform or Pulumi). Nothing is set up by hand in a console.
2. **Identity and access:** SSO, RBAC, and OIDC federation from CI to the cloud, so there are no long-lived cloud keys in pipelines.
3. **Secrets management:** Vault or a cloud secrets manager, plus External Secrets Operator if you run Kubernetes.
4. **Artifact management:** a container registry plus package repos (npm, Maven, PyPI proxies), with retention policies.
5. **Build compute:** autoscaling ephemeral runners, kept separate for trusted and untrusted (fork/PR) workloads.
6. **Caching:** dependency caches, Docker layer caching, and remote build caching where it applies.
7. **Environment topology:** dev, staging and prod clusters or accounts, plus network boundaries between them.

**Exit criteria:** A "hello world" service can build on ephemeral runners, push to the registry and pull secrets, with no static credentials anywhere.

---

## Phase 2: Golden-Path CI Templates (Weeks 6–11)

**Goal:** Reusable, versioned pipeline templates that services call instead of copying.

**Standard CI stages, in order:**
1. Checkout, then restore cache
2. Lint and static analysis
3. Unit tests with a coverage report
4. Build the artifact or container image (multi-stage, pinned base images)
5. Security scans: SAST, dependency/SCA, secrets detection, container image scan
6. Generate an SBOM
7. Sign the image (Sigstore/cosign) and attach build provenance
8. Push with an immutable tag (git SHA, never `latest`)
9. Publish results to the PR as status checks

**Design principles:**
- **Keep templates in a central repo, versioned with semver.** Services pin a major version, and Renovate or Dependabot proposes upgrades.
- **Use a thin service config.** Each service should need only about 10–20 lines of pipeline YAML that references the template.
- **Provide escape hatches.** Allow extension points such as extra test steps without letting teams fork the whole template.
- **Watch speed from the start.** Target under 10 minutes for PR feedback. Run independent stages in parallel and only rebuild what changed.

**Pilot:** Migrate the 2–3 pilot services and pair directly with their teams.

**Exit criteria:** Pilot services run fully on templates. PR feedback is under 10 minutes, and pilot teams say they prefer it to the old setup.

---

## Phase 3: Continuous Delivery and Environment Promotion (Weeks 10–15)

**Goal:** Automated, auditable deploys that work the same way in every environment.

1. **Deployment manifests:** Helm charts or Kustomize bases per archetype, with a shared library chart for common concerns (probes, resources, labels, PodDisruptionBudgets).
2. **GitOps repo structure:** environment overlays with per-service values. CI opens a PR or commit to update the image tag, and Argo CD or Flux reconciles it.
3. **Promotion flow:**
   - Merge to main deploys to dev automatically.
   - Promotion to staging is automatic once smoke and integration tests pass.
   - Promotion to prod is automatic, or gated by an approval during early rollout.
   - **The same artifact moves through every environment. Never rebuild per environment.**
4. **Configuration management:** config is kept separate from images, and secrets are injected at runtime.
5. **Database migrations:** a standard pattern such as a pre-deploy job using Flyway or Liquibase, with backward-compatible migrations (expand, then contract).
6. **Ephemeral preview environments** per PR, optional but valuable for frontend and API-heavy services.

**Exit criteria:** Pilot services deploy to prod through GitOps with a full audit trail. Rollback is a git revert that takes effect in under 5 minutes.

---

## Phase 4: Observability and Progressive Delivery (Weeks 14–19)

**Goal:** Make deploys safe enough to run often.

- **Observability baseline:** standard metrics, logs and traces (OpenTelemetry), and dashboards for each archetype.
- **Deployment markers** in your monitoring tools, so incidents can be linked to the deploy that caused them.
- **Progressive delivery** with Argo Rollouts or Flagger: canary or blue-green, with automated analysis on error rate and latency, and automatic rollback when thresholds are breached.
- **Feature flags,** so deploying code and releasing a feature become separate steps.
- **SLO-based gates:** block promotion when a service is burning its error budget.
- **Pipeline observability:** track build duration, queue time, flaky tests and failure causes.

**Exit criteria:** A deliberately bad deploy on a pilot service is detected and rolled back automatically, with no human involved.

---

## Phase 5: Security and Compliance Hardening (Weeks 17–21, overlaps Phase 4)

- **Admission policy** with Kyverno or OPA Gatekeeper: only signed images from approved registries, no privileged containers, resource limits required.
- **Supply-chain integrity:** aim for SLSA Level 2–3 provenance, verified at deploy time.
- **Branch protection:** required reviews, required status checks, signed commits where needed.
- **Vulnerability policy:** block criticals, set SLAs for highs, and maintain an exception workflow.
- **Audit evidence:** a record of who approved each change and what it contained, automated for SOC 2 or ISO audits if those apply.

**Exit criteria:** Policies run in enforce mode (not just audit) for pilot services, with no false positives blocking teams.

---

## Phase 6: Fleet Migration in Waves (Weeks 18–34)

**Goal:** Move all 50 services over without stalling feature work.

| Wave | Services | Profile | Approach |
|---|---|---|---|
| **Pilot** | 3 | Friendly teams, simple services | Platform team pairs closely (done in Phases 2–4) |
| **Wave 1** | ~10 | Most common archetype, low risk | Platform team does the migration and teams review |
| **Wave 2** | ~25 | Remaining standard archetypes | Teams migrate themselves with docs and office hours |
| **Wave 3** | ~12 | Critical-path and high-traffic services | Careful canaries, run the old and new pipelines side by side |
| **Long tail** | ~0–5 | Legacy and unusual services | Custom adapters, or refactor, or accept an exception |

**Migration mechanics:**
- A **migration checklist** per service: tests pass, health probes defined, resource limits set, observability wired, runbook updated.
- **Run old and new pipelines in parallel** for critical services until a few clean releases have gone through the new one.
- **Automate the migration** where you can, for example a scaffolding CLI that generates pipeline config and manifests from the inventory data.
- A **migration tracker** dashboard visible to leadership.
- **Decommission old pipelines** promptly. Running two systems for a long time creates drift and doubles the support load.

**Exit criteria:** At least 95% of services are on the platform, legacy CI is shut down, and exceptions are documented with owners and dates.

---

## Phase 7: Self-Service and Continuous Improvement (Week 30 onward)

- **Developer portal** (Backstage or similar): a service catalog, "create new service" templates that are deployable on day one, and links to docs and dashboards.
- **Scorecards** per service covering template version, test coverage, vulnerability count and DORA metrics.
- **Automated template upgrades** across the fleet through bot PRs.
- **Cost controls:** runner rightsizing, cache tuning, artifact retention cleanup.
- **A feedback loop:** quarterly developer satisfaction surveys plus a public platform roadmap.
- **Ongoing DORA reporting** compared against the Phase 0 baseline.

---

## Critical Path Summary

```
Discovery → Foundations → CI Templates → CD/GitOps → Progressive Delivery → Fleet Waves → Self-Service
                              ↓ pilot          ↓ pilot          ↓ pilot
                          (Security hardening runs alongside from Phase 2 on)
```

**Total:** about 8–9 months to full fleet adoption with a dedicated platform team of 4–6 engineers. The pilot can show value within about 3 months.

---

## Common Pitfalls to Avoid

1. **Building for every case up front.** Template the top archetypes first and let the long tail wait.
2. **Copy-paste pipelines.** Copies drift right away. Insist on versioned, referenced templates.
3. **Rebuilding artifacts per environment.** This breaks the guarantee that what you tested is what you shipped.
4. **Mandating without earning trust.** Win the pilots, publish the metrics, then scale.
5. **Ignoring pipeline speed.** Slow pipelines lead to workarounds. Treat CI latency as a product metric.
6. **Turning on security gates in enforce mode first.** Start in audit mode, tune out false positives, then enforce.
7. **Leaving test quality behind.** CD is only as safe as your tests. Budget time for flaky-test cleanup and contract tests between services.
8. **No owner for templates.** The platform is a product, so give it a product owner, a roadmap and SLAs.

---

## Recommended Team Shape

- **Platform lead or product owner:** roadmap, prioritization and stakeholder management
- **2–3 platform engineers:** infrastructure, templates, GitOps
- **1 security or DevSecOps engineer:** supply chain and policy
- **1 developer experience engineer:** docs, the portal, migration support
- **Service team champions:** one per team, part-time, who act as the migration point of contact
