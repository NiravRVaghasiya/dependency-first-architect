# Plan: Customer-Support RAG Chatbot over Help-Center Docs

## 1. Classification and constraints
- **What:** A chat widget on the help center. It answers customer questions from help-center articles, cites its sources, and hands off to a human when it can't answer well.
- **Type:** AI/RAG plus software. It is brownfield because it plugs into the existing help-center CMS and ticketing, and those stay as the fallback. It is not a small build: it faces outside users and handles their personal data.
- **Dominant constraint:** correctness of answers.
- **Worst failure:** The bot states a wrong policy (refunds, pricing, security) as fact, and the customer acts on it. A close second is leaking personal data or following an injected instruction.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency | first token ≤2 s p95; full answer ≤8 s p95 | ASSUMPTION (usual chat UX) | V0 baseline, Phase 3 |
| Throughput | UNKNOWN: Support Ops supplies peak chats/hour | UNKNOWN | Phase 3 load test |
| Availability | 99.5%; if down, the widget shows "Contact support" | ASSUMPTION (the bot is not the system of record) | Phase 3 |
| AI inference cost | hard cap of 20k tokens per conversation; target cost per resolved conversation UNKNOWN (Support Ops supplies current cost per ticket before Phase 4) | ASSUMPTION / UNKNOWN | Phase 1, V4 |
| Operational complexity | 1 service + managed Postgres; existing team on call | ASSUMPTION | Phase 3 |

**Missing inputs:**
1. Are all docs public, or are some behind login or internal-only? I assume public. If some are gated, retrieval needs per-user access checks, and that becomes an R3 risk dependency in Phase 2.
2. Which ticketing system (Zendesk, Salesforce, other)?
3. Which languages?
4. Any data-residency needs?
5. Customer-facing bot vs agent-assist. I assume customer-facing. If it's agent-assist, Phase 4 becomes the full launch and V4 changes.

## 3. Key decisions
| Decision | Reversibility | Default | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Data-privacy boundary | R3: transcripts hold personal data, and a leak can't be undone | Mask personal data before logs and eval storage; keep transcripts 30 days (ASSUMPTION); never train on them | Answers don't need customer identity | V1 + Privacy reviewer sign-off | Legal sets other retention or residency rules → change the policy and pin regions |
| Hosted API vs self-host | R2: the model sits behind its own interface, and calls keep no state | Hosted API under a zero-retention agreement | The vendor signs | Legal sign-off (Phase 0 lead time) | Vendor refuses terms, or residency demands it → region-pinned or self-hosted model |
| Prompt+RAG vs fine-tune | R2 | RAG only | The docs cover most questions | V2, V3 | V3 fails on tone or format even though retrieval is correct |
| Build vs buy | R2: weeks of work wasted if wrong | Build a thin service | A vendor bot (Intercom Fin, Zendesk AI) won't meet V3 at a lower total cost | Run the same V3 eval set on one vendor bot in Phase 2 | The vendor passes V3 at lower total cost → buy |
| Index freshness (consistency) | R2: a stale policy answer causes harm | Re-index on each CMS publish, plus a full rebuild nightly; changes live in ≤1 h (ASSUMPTION) | The webhook exists | Phase 2 freshness check | The webhook doesn't exist → poll every 15 min |
| Handoff contract | R2: a coordinated change with the Support team | Bot creates a ticket with the transcript and the docs it cited | Ticketing API allows it | Phase 1 exit | Support rejects the format → change it |

**minor defaults:** one service, not microservices; synchronous streaming, not async; pgvector in managed Postgres, rebuildable from the docs; embedding model pinned to the index version (the corpus is small, so re-embedding is cheap).

**N/A:** tenancy (one company); migration or cutover (nothing is replaced; existing channels stay).

## 4. First end-to-end slice (Phase 0)
- **The one real request:** an internal staff member asks "How do I reset my password?" and gets a streamed answer citing the right article.
- **Tiers it crosses:** widget → API service → ingestion of the help-center export → embedding → pgvector search → hosted LLM → answer with citation.
- **Built in from day zero:**
  - user text and retrieved text are wrapped as data, never treated as instructions;
  - no tools;
  - hard caps on tokens and conversation length.
- **Deployed:** through CI/CD with infrastructure as code, behind a feature flag.
- **Logged and monitored:** OpenTelemetry traces cover every step, with token counts, cost and latency. Alerts fire on errors and cost.
- **Rolled back:** turning the flag off hides the widget, and the previous release can be redeployed.
- **Who can reach it:** internal staff on an allow-list only. No customer text reaches the LLM until Legal signs (§2).

V0 is the exit check (§6).

## 5. Phases
**Phase 1: Defenses and budgets**
- **Unlocks:** exposure to real users can be considered.
- **Depends on:** V0.
- **Tasks:**
  1. Mask personal data on input and in logs.
  2. Filter outputs: links only to our help-center domain, no images, no markdown links elsewhere.
  3. Run an injection test suite in CI. Plant the attacks in user messages and in test docs.
  4. Enforce per-conversation and daily cost caps, a timeout, and a degraded reply: "I can't answer that, here's how to contact support."
  5. Human handoff: billing and account questions, safety topics, low retrieval scores, and user requests for a person all create a ticket.
- **Rollback:** flag off.
- **Exit check:** V1 passes; a runaway conversation is cut off at the cap and records a metric.

**Phase 2: Retrieval and answer quality**
- **Unlocks:** answers can be trusted enough for a canary.
- **Depends on:** Phase 1, the eval set (§2).
- **Tasks:**
  1. Build the labeled eval set: about 300 real past questions (ASSUMPTION), each matched to its correct articles.
  2. Chunk by heading, combine keyword and vector search, add a reranker.
  3. Wire the publish webhook into re-indexing.
  4. Pass V2, then V3. V3 includes shadow mode: support agents see bot drafts for real tickets, but customers never do.
  5. Run the vendor comparison (§3).
- **Rollback:** each index version is kept; switch the alias back.
- **Exit check:** V2 and V3 pass; an edited article is answered correctly within 1 h.

**Phase 3: Model access and orchestration hardening**
- **Unlocks:** the bot can handle production load.
- **Depends on:** V3.
- **Tasks:**
  1. Configure a fallback model and run the eval suite against it.
  2. Run the eval suite in CI whenever a prompt, model or index changes.
  3. Keep conversation memory per session only.
  4. Load test at the throughput target from §1.
- **Rollback:** pinned prompt and model versions, rolled back via config.
- **Exit check:**
  - the fallback model passes V3's threshold;
  - the load test meets the latency budget;
  - an injected provider outage switches to the fallback model or the degraded reply.

**Phase 4: Canary and feedback**
- **Unlocks:** general availability.
- **Depends on:** V1, V3, Phase 3.
- **Tasks:**
  1. Roll out to 1% of help-center visitors, then 10%. Widening further waits for V4; then 50% and 100%.
  2. Add thumbs up/down and a "talk to a human" button.
  3. Send flagged answers to a queue that the Support lead reviews. Only reviewed corrections enter the eval set or the docs.
- **Rollback:** flag back to 0%; existing support channels are unchanged.
- **Exit check:** V4 passes; customer satisfaction for chat users is no worse than the BASELINE taken from ticket satisfaction scores.

## 9. Exceptions
None.

## 10. Deferred
- **Answers that use the customer's account (login, order lookup):** pulled forward when this is wanted. Requires per-user access checks and a new R3 boundary review.
- **Bot actions (refunds, plan changes):** when the business asks for them; requires human approval tied to each specific action.
- **Multilingual support:** when the language input says it's needed.
- **Fine-tuning:** when V3 fails on tone or format even though retrieval is correct.
- **Routing between models:** when V4 fails on cost.
- **Long-term memory:** when users repeatedly have to re-explain context across sessions.
