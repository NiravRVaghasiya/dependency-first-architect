# Plan: Autonomous GitHub Issue Triage and Resolution Agent

## 1. Classification and constraints
- **What:** A GitHub App. It receives issue webhooks, triages each issue (labels, duplicate detection, a suggested owner) and tries to resolve it by opening a draft PR from a sandbox.
- **Type:** AI-agentic software. Greenfield, running alongside existing repos and CI. Not small: it reads untrusted text, runs code and writes to repos.
- **Dominant constraint:** Correctness and safety of its writes.
- **Worst failure:** Injected issue text makes the agent leak secrets or private code, or get malicious code merged.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Triage cost | ≤ $0.05/issue | ASSUMPTION (one small-model call plus retrieval) | Phase 2 |
| Resolution attempt cost | hard cap $2, 30 tool calls | ASSUMPTION (typical agent-loop spend) | Phase 1 |
| Cost per merged PR | UNKNOWN: engineering management sets it, needed by Phase 3 | UNKNOWN | V5 |
| Triage latency | ≤ 2 min, webhook to label | ASSUMPTION (faster than a human first response) | Phase 2 |
| Resolution latency | ≤ 30 min timeout, then a "gave up" comment | ASSUMPTION | Phase 3 |
| Availability | best effort; GitHub redelivers missed webhooks | ASSUMPTION | Phase 0 |
| Ops complexity | 1 worker service, 1 sandbox pool, no pager in the pilot | ASSUMPTION | Phase 4 |

**Missing inputs:**
- Which repos are in scope, and whether they are public or private.
- The model vendor's data terms.
- Who approves security and legal questions.
- The cost-per-merged-PR budget.

**Assumption the order rests on:** we start with private internal repos. If public repos come first, V1 must be stricter and Phase 4's waves change.

## 3. Key decisions

| Decision | Reversibility | Default | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Write authority | R3: a merged malicious change can't be undone | Draft PRs from `agent/*` branches only. Never merge or push to protected branches; human review required. | Branch protection is enforced org-wide | V1 plus a branch-protection audit | V1 fails → the agent can only comment |
| Execution trust boundary | R3: secret exfiltration can't be undone | Ephemeral container (gVisor), no credentials, egress limited to package mirrors | Tests can run offline using mirrors | V2 | V2 fails → no code execution; static patch suggestions only |
| Data-privacy boundary | R3: data held by a vendor | Hosted API with zero data retention and no training on our data | The vendor offers those terms | V6 | V6 fails → self-host an open model |
| Hosted API vs self-host | R2: interface swap plus re-evaluation | Hosted, behind a model-access seam | Hosted quality is needed for resolution | V4 | V6 fails, or cost breaks V5 |
| Sync vs async | R2: queue semantics shape all workers | Webhook → durable queue → idempotent worker, keyed on the delivery ID | Retries are safe | Phase 0 replay test | — |
| GitHub App vs personal access token | R2: permission migration across repos | App with least-privilege, per-repo installation | Scopes fit the App model | Phase 0 | A needed scope is unavailable to Apps |
| Prompt+RAG vs fine-tune | R2 | Prompt+RAG | Repo context fits the model's window | V3, V4 | Retrieval stays below V3 at its ceiling |

**minor defaults:**
- Build vs buy: build a thin orchestrator on a hosted model.
- Monolith vs services: one worker plus the sandbox pool.
- Embedding model pinned per index version.

**N/A:** Consistency vs availability. GitHub is the system of record, and agent state can be rebuilt from it.

## 4. First end-to-end slice (Phase 0)
- **Request:** An allow-listed staff member opens an issue in a private sandbox repo. The agent replies with one comment containing a suggested label and a one-line summary.
- **Tiers:** GitHub webhook → ingress, which checks the HMAC signature → queue → worker → model API (through the seam) → GitHub API comment.
- **Day zero:**
  - Deployed through CI/CD with an image digest.
  - Structured logs, with one trace ID per issue event.
  - Metrics for tokens, cost and latency.
  - An alert on worker errors or queue age.
  - Rollback: redeploy the previous digest, or disable the App with the feature flag.
- **Treats input as data:** Issue text goes in a delimited untrusted block. The only tool is "post comment" to the source issue. Hard cap of 4k tokens and $0.10.
- **Who can reach it:** The sandbox repo only, and only issues from allow-listed authors.

**V0 exit check:**
- A real issue gets a comment, with one trace across every tier.
- A deploy and a rollback both succeed through the pipeline.
- A killed worker fires an alert.
- First cost and latency values are recorded as baselines.

## 5. Phases

**Phase 1: Defenses and budgets**
- **Unlocks:** Exposure on real repos (triage), and code execution.
- **Depends on:** V0.
- **Tasks:**
  1. A tool executor with an allow-list and argument validation (repo, branch prefix, label set). It, not the model, enforces the rules.
  2. Approval binding: any action outside triage needs a maintainer approval tied to that exact action hash.
  3. Close outbound paths: no URLs or images in comments, and egress restricted.
  4. Per-attempt token, cost and iteration caps.
  5. The sandbox runner.
  6. An injection suite run in CI.
- **Rollback:** The feature flag. Nothing is exposed yet.
- **Exit check:** V1 and V2 pass, and a runaway loop is cut off at the cap and emits a metric.

**Phase 2: Triage on real repos**
- **Unlocks:** Resolution design.
- **Depends on:** V1 and V6. Org approval is requested in Phase 0.
- **Tasks:**
  1. Retrieval over CODEOWNERS, contributing docs and an embedding index of past issues (for duplicates), scoped to the installing repo.
  2. Harden the model-access seam: retries, a fallback model, structured output.
  3. Measure V3 offline.
  4. Roll out in waves: one pilot repo → five repos → all in-scope repos. Each wave widens only if label override rate is ≤ 20% for a week (ASSUMPTION).
- **Rollback:** Turn off per repo with the flag. Labels can be reverted in bulk using the audit log.
- **Exit check:** V3 passes, plus triage latency is within budget.

**Phase 3: Resolution in the canary**
- **Unlocks:** A scaled rollout.
- **Depends on:** V2, V3, and V5's budget input.
- **Tasks:**
  1. Orchestration: a single-agent loop (plan → edit → run tests in the sandbox → open a draft PR linked to the issue). It only runs on issues a maintainer labels `agent-ok`.
  2. Per-issue state is kept in the PR and issue thread.
  3. Measure V4 by replaying history.
  4. Canary on one repo to measure V5.
- **Rollback:** Close the agent's PRs and delete the `agent/*` branches. Nothing merges without a human.
- **Exit check:** V4 and V5 pass, and a failed attempt always posts a "gave up" comment.

**Phase 4: Widen, route, learn**
- **Depends on:** V5.
- **Tasks:**
  1. Repo waves (as in Phase 2) for resolution.
  2. Difficulty routing (small model for triage and simple fixes).
  3. Reviewed feedback: maintainers' PR review outcomes go into the evaluation set.
  4. Public repos come last, after V1 is re-run with public-attacker cases.
- **Rollback:** Turn off per repo.
- **Exit check:** Routed quality is within 5 points of strong-only on V4's set (ASSUMPTION), at lower cost. The next evaluation improves with no regression.

## 9. Exceptions
None.

## 10. Deferred
- **Auto-merge:** pulled forward only if V4 acceptance is ≥ 90% across 3 months on low-risk labels, with security sign-off.
- **Multi-agent orchestration:** if single-loop failures trace to planning more than to execution.
- **Fine-tuning:** if V3 or V4 revisit triggers trigger.
- **Cross-repo memory:** if duplicates span repos in more than 10% of issues.
- **Public repos:** after Phase 4's V1 re-test.
