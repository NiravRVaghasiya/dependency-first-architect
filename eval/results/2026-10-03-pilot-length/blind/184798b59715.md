# Plan: Real-time collaborative document editor

## 1. Classification and constraints
- **What:** A browser editor where many people edit the same rich-text document at once. Each person sees the others' edits and cursors live.
- **Type:** Software, greenfield. Not a small build: outside users will store their own content in it.
- **Dominant constraint:** Correctness. Every copy of a document must end up identical, and no acknowledged edit may be lost.
- **Worst failure:** Edits are silently lost or copies diverge. A close second is a user reading another tenant's document.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Local keystroke echo | <16 ms | ASSUMPTION (one frame at 60 fps) | Phase 4 exit |
| Remote edit propagation | p95 <200 ms, same region | ASSUMPTION (what "live" feels like) | V2 |
| Concurrency | 50 editors per doc, 10k connections per cluster | ASSUMPTION (to confirm with product) | V2 |
| Availability | 99.9% monthly for the sync service | ASSUMPTION | Phase 5 SLO |
| RPO / RTO | 0 acked edits lost on a single-node failure; ≤5 min / ≤1 h after a regional disaster | ASSUMPTION | V1, V4 |
| Infra cost per 1k concurrent connections | UNKNOWN: product/finance supply a ceiling, needed by Phase 3 | UNKNOWN | V2 |
| Operational complexity | ≤3 stateful components (Postgres, Redis, object store) | ASSUMPTION | Phase 3 |

**Missing inputs:**
1. Is long offline editing required? The plan assumes no, only reconnects after short drops. A CRDT handles offline editing either way.
2. Expected scale.
3. Data residency or regulated content. If yes, a residency gate is added before Phase 2.
4. Who the security reviewer and legal approver are.

## 3. Key decisions (resolved up front)
| Decision | Reversibility | Default | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Sync algorithm | R3: it fixes the format every document is stored in | CRDT (Yjs) | Converges under any order of edits; metadata growth stays bounded | V1 | V1 fails, or doc load time or memory exceeds the V1 bar → server-authoritative OT (ShareDB) |
| Consistency vs availability | R3: users see this behaviour directly | Document content is eventually consistent and edits apply locally first. Permissions and metadata are strongly consistent in Postgres | Users accept a brief divergence that then converges | V1 | Users need locking or strict ordering of edits |
| Persistence model and IDs | R3: the stored data model | Append-only update log plus periodic snapshots in Postgres; UUIDv7 doc IDs; versioned content schema | A server acks an edit only after it is durably written | V1 | V1 loses edits after a crash → write-ahead acks or a different store |
| Content schema | R3: every stored doc must conform to it | ProseMirror schema (TipTap), with a version stamped on every doc and migrations | The schema can evolve without rewriting stored docs | V1 (schema migration case) | A schema migration breaks old docs |
| Tenancy and isolation | R3: a mistake exposes users' data | Shared database; `workspace_id` on every row; Postgres row-level security; authorization checked when a socket joins a doc and on every incoming edit | Row-level security plus a server-side check is enough | V3 | V3 finds a cross-tenant leak → a schema per tenant |
| Monolith vs services | R2: weeks to split | A modular monolith API, plus a separate stateless sync gateway | One deployable unit handles HTTP | Phase 3 load profile | The sync gateway and API need different scaling |
| Fan-out across nodes | R2: one infra change | Redis pub/sub keyed by doc ID | The Redis hop stays within the latency budget | V2 | V2 p95 misses → sticky routing that pins each doc to one node |
| Build vs buy | R2: data held at a vendor would make this costly to undo | Use open-source Yjs and Hocuspocus, self-hosted, rather than a hosted service such as Liveblocks | Our team can run it | V2 | Running it costs more than the hosted quote |
| Sync vs async | R2 | Edits are pushed over WebSocket. Snapshot compaction and exports run as async jobs | Async jobs never block an ack | Phase 3 | Compaction lag grows past 10 min |
| Privacy boundary | R3: personal data in docs | Docs are treated as personal data: encrypted at rest, kept in one region, and kept out of logs | No residency requirement (Missing input 3) | Legal review before Phase 5 | Residency is required → a per-region deployment |

**minor defaults:** TypeScript end to end; Kubernetes on one cloud; GitHub Actions; OpenTelemetry.
**N/A:** AI rows and brownfield rows: there is no AI component and no existing system.

## 4. First end-to-end slice (Phase 0)
- **Request:** Staff member A types into a plain text area bound to a Yjs doc. The edit appears in staff member B's browser, and it is still there after a page reload.
- **Tiers:** Browser client → TLS load balancer → stub login (SSO restricted to an internal allow-list) → sync gateway (Hocuspocus) → Postgres update log → fan-out to B.
- **Day zero:** Deployed through CI to Kubernetes with Helm and rolled back with `helm rollback`. One OpenTelemetry trace follows an edit from client send → gateway → database commit → fan-out. Logs record doc ID and size only, never content. An alert fires on sync error rate and on database write failures.
- **Who can reach it:** Allow-listed staff only, behind a feature flag. Documents are disposable test content.
- **V0** is the standard exit check: one trace across every tier, a deploy and a rollback succeed, an injected database outage fires an alert, and baseline propagation latency is recorded.

## 5. Phases
- **Phase 1: Sync engine correctness and data model**
  - Unlocks: The specification of every feature that sits on top of the sync engine.
  - Depends on: V0.
  - Tasks (in order):
    1. Final persistence schema and doc IDs.
    2. Update log plus snapshot compaction.
    3. Server acks an edit only after commit.
    4. Content schema versioning.
    5. Fuzz harness and crash-injection harness.
    6. Start the pen-test contract and the cost-ceiling request (they have lead time).
  - Rollback: Data is still disposable, so drop the test docs and redeploy.
  - Exit check: V1.
- **Phase 2: Identity, authorization, tenancy**
  - Unlocks: Exposure to anyone outside staff.
  - Depends on: V1.
  - Tasks (in order):
    1. Workspaces and per-document access lists (owner, editor, viewer).
    2. Row-level security.
    3. Authorization when a socket joins a doc.
    4. Server-side rejection of edits from viewers.
    5. Revoking access drops live sockets.
    6. Audit log.
    7. Real SSO/OIDC replaces the stub.
  - Rollback: Use the feature flag to fall back to allow-list-only access.
  - Exit check: V3 automated matrix (the pen test can finish later, before Phase 5).
- **Phase 3: Durability and scale-out**
  - Unlocks: Real documents, and more than one sync node.
  - Depends on: V1, V3 matrix.
  - Tasks (in order):
    1. Postgres synchronous replica plus point-in-time recovery (PITR).
    2. Snapshots copied to object storage.
    3. Restore drill.
    4. Redis fan-out.
    5. Load test.
    6. Horizontal autoscaling.
  - Rollback: Scale back to one node; Redis is optional on a single node.
  - Exit check: V2, V4.
- **Phase 4: Editor features (the visible part, built last)**
  - Unlocks: A usable product.
  - Depends on: V1, V2.
  - Tasks (in order):
    1. Rich-text editor (TipTap with y-prosemirror).
    2. Reconnect and resync after short drops.
    3. Version history from snapshots.
    4. Comments anchored to positions in the text.
    5. Presence and cursors (temporary state, never persisted).
  - Rollback: Each feature has its own flag.
  - Exit check: V1 fuzz suite still green on the rich-text schema; local echo <16 ms measured.
- **Phase 5: Staged exposure**
  - Unlocks: General availability.
  - Depends on: V3 (including the pen test), V4, legal sign-off.
  - Tasks (in order):
    1. Internal dogfooding on real work.
    2. One design-partner tenant.
    3. 10% of new signups.
    4. Everyone.
  - Rollback: Close the flag for new tenants. Existing data stays in its current format.
  - Exit check: At each step, 7 days with zero divergence alerts, zero lost-edit reports, and the SLO met before widening.

## 7. Cross-cutting concerns
| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|
| 0 | TLS, SSO allow-list, content kept out of logs | End-to-end trace, alerts on errors and database writes | IaC (Terraform), Helm chart, pinned lockfile | Tested Helm rollback |
| 1 | Size and rate limits on incoming edits | A divergence metric: clients report a doc state hash on resync | Fuzz runs use fixed seeds and are replayable in CI | The server acks only after commit; crash tests |
| 2 | Row-level security, authorization on every edit, audit log | Authorization-denial metrics and alerts | Authorization matrix runs as a CI test | Clients reconnect with backoff after revocation or a deploy |
| 3 | Encryption at rest, scoped access to backups | Per-doc fan-out lag, Redis health | Restore runbook kept as code | Synchronous replica, PITR, autoscaling |
| 4 | Comment and paste input sanitized (XSS), CSP | Client echo-latency real-user monitoring (RUM) | Content schema migrations versioned in the repo | Offline edit queue survives short drops |
| 5 | Pen-test fixes, incident runbook | SLO dashboards, error budget | Canary configs in git | Staged rollout with a flag kill-switch |

## 10. Deferred
- **Long offline editing:** pulled forward if product requires it (Missing input 1).
- **Multi-region active-active:** pulled forward if users in remote regions miss the 200 ms budget, or if residency is required.
- **End-to-end encryption:** pulled forward if a regulated customer needs it.
- **Suggestions and track changes:** pulled forward once V1 holds on the extended schema and users ask for it.
- **Full-text search:** pulled forward when workspaces average more than 100 docs.
- **AI writing assist:** pulled forward if it reaches the roadmap, which would add §8 defenses first.
- **Native mobile apps:** pulled forward when web mobile usage passes 20%.
