# Plan: Real-time collaborative document editor

## 1. Classification and constraints
- **What it is:** a browser editor where several users edit the same rich-text document at once, see each other's cursors, and never lose an edit.
- **Type:** software, greenfield, not a small build (outside users and user content).
- **Dominant constraint:** correctness. All copies of a document must end up identical, and no saved edit may be lost.
- **Worst failure:** copies silently diverge, or an edit the server already confirmed is lost, so a document is corrupted. Close behind: one user reading another tenant's document.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Time for an edit to reach other editors | p95 ≤ 200 ms in one region | ASSUMPTION (feels live; industry norm) | V2 |
| Local keystroke echo | ≤ 16 ms (one frame) | ASSUMPTION | Phase 4 exit |
| Concurrent editors per document | 50 | ASSUMPTION (team-sized docs) | V2 |
| Connections per sync node | 10k | ASSUMPTION (typical WebSocket server) | V2 |
| Availability | 99.9% monthly | ASSUMPTION | Phase 5 SLO alerting |
| RPO / RTO | RPO 0 for confirmed edits / RTO 1 h | ASSUMPTION | V3 |
| Storage growth | ≤ 3× plain-text size after 100k edits, with compaction | ASSUMPTION | V5 |
| Operational complexity | ≤ 3 stateful services (Postgres, Redis, object storage) | ASSUMPTION | Phase 3 review |

**Missing inputs:**
- **Full offline editing:** is it required? If yes, it strengthens the CRDT default and moves offline work earlier.
- **Expected scale:** number of documents and peak concurrent users.
- **Residency or compliance:** any data-residency or compliance rules? These could force multi-region or tenant-per-database.
- **Named security reviewer for V4:** unknown. Product or security leadership supplies one before Phase 2.

I assume a SaaS product, one region, rich text, and tolerance of reconnects (not full offline).

## 3. Key decisions

| Decision | Reversibility | Default | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Merge algorithm (build vs buy) | R3: the stored document format and client protocol depend on it | Buy Yjs, a CRDT library (copies merge automatically, no central server ordering) | Yjs converges for our ProseMirror schema; its overhead fits the budget | V1, V5 | V1 or V5 fails → switch to server-ordered operational transform (OT), e.g. prosemirror-collab |
| Consistency vs availability | R3: users see this behavior directly | Each document converges eventually (AP); an edit is confirmed only after a durable write | Users accept brief divergence during network partitions | V1, V3 | Need for strict ordering (e.g. legal redlines) → server-ordered OT |
| Storage model | R3: data model, and real documents will exist | Append-only update log in Postgres, plus periodic snapshots to S3, plus compaction | Log-then-snapshot meets RPO 0 / RTO 1 h | V3 | V3 fails → write snapshots synchronously on confirm |
| Access-control model / trust boundary | R3: a short time wrong exposes data | Per-document ACL checked when a WebSocket connects and on every update; tenant ID on every row with Postgres row-level security | Checking on connect plus a revocation broadcast is fast enough | V4 | Revocation takes > 5 s → re-check auth on every message |
| Data-privacy boundary | R3: personal content | Encrypt at rest and in transit; logs and traces carry document and user IDs only, never content | No end-to-end encryption required | Cited basis: no stated requirement | Customer requires end-to-end encryption → server becomes a blind relay (see §10) |
| Monolith vs services | R2: weeks of work | Modular monolith (API + auth + persistence) plus a separate stateless sync tier | One deployable unit is enough below 10k documents per node | Phase 3 load test | One domain's deploy cadence blocks others |
| Sync vs async | R2 | WebSocket push for edits; queued jobs for snapshots, compaction and search indexing | Queue lag doesn't affect correctness | V3 | Snapshot lag > 10 min |
| Routing documents to sync nodes | R2 | Any node accepts any document; Redis pub/sub fans updates out per document | Redis fan-out stays inside V2's latency bar | V2 | V2 fails → pin each document to one node by consistent hashing |
| Document schema evolution | R2: requires migrating documents | Versioned ProseMirror schema; documents migrate when loaded | Changes stay additive | Phase 4 migration test | A non-additive change is needed → batch migration with a rehearsal |

**minor defaults:** UI → React + TipTap. Presence and cursors → Yjs awareness messages, temporary and never stored. Infra → Kubernetes in one region. CI → GitHub Actions.

- Migration and cutover: greenfield.

## 4. First end-to-end slice (Phase 0)
- **The request:** an internal user, signed in through company SSO, types a character into a plain-text area bound to Yjs. The update is saved, and a second browser on another account sees it. A reload shows the saved state.
- **Tiers crossed:** browser → CDN/TLS load balancer → sync node (WebSocket, auth check on connect) → Redis pub/sub → Postgres update log → second client.
- **Deployment and operations:**
  - Infra is defined in Terraform, and Helm deploys through CI with a canary.
  - OpenTelemetry carries one trace from browser to database.
  - Structured logs contain IDs only.
  - Dashboards show connection count, propagation latency and failed writes.
  - A deliberately rejected write must trigger an alert.
  - Rollback is a Helm rollback, rehearsed once.
- **Who can reach it:** staff on an allow-list, behind a feature flag. Documents are disposable test documents.
- **Exit check:** V0.

## 5. Phases

**Phase 1: Convergence and durability**
- **Unlocks:** detailed editor design; a frozen storage format.
- **Depends on:** V0.
- **Tasks:**
  1. ProseMirror schema v1, bound with y-prosemirror.
  2. Convergence fuzz harness (V1).
  3. Update log, snapshots, compaction.
  4. Crash and restore drills (V3).
  5. Storage growth measurement (V5).
- **Rollback:** test documents only. Rewrite the format freely until V1 and V3 pass. After that, the format is frozen.
- **Exit check:** V1, V3 and V5 pass.

**Phase 2: Identity, access control, tenant isolation**
- **Unlocks:** sharing between users; later, external exposure.
- **Depends on:** Phase 1 (the stored data model).
- **Tasks:**
  1. Tenant and user model with Postgres row-level security.
  2. Document ACL roles: owner, editor, commenter, viewer.
  3. Viewer connections become read-only on the server.
  4. Revocation broadcast that disconnects live sessions.
  5. Share links with expiry.
  6. Audit log.
  7. Penetration test (V4).
- **Rollback:** migrations are reversible, and the feature flag disables sharing.
- **Exit check:** V4 passes.

**Phase 3: Sync tier at scale**
- **Unlocks:** sizing commitments; beta capacity.
- **Depends on:** V1, Phase 2.
- **Tasks:**
  1. Fan-out load test (V2).
  2. Backpressure and per-connection rate limits.
  3. Reconnect with resend of missing updates.
  4. Autoscaling.
  5. Redis failover drill.
- **Rollback:** Helm rollback. If V2 fails, take the consistent-hashing flip.
- **Exit check:** V2 passes.

**Phase 4: Editor experience (the visible part comes last)**
- **Unlocks:** a usable product.
- **Depends on:** V1, V2, V4.
- **Tasks:**
  1. Rich-text formatting.
  2. Presence and cursors.
  3. Version history built on snapshots.
  4. Comments.
  5. Undo for the local user only.
  6. Schema migration test.
  7. Keystroke latency profiling.
- **Rollback:** each feature has its own flag.
- **Exit check:**
  - Keystroke echo ≤ 16 ms on a mid-range laptop.
  - A v1-to-v2 schema load test passes.
  - V1's fuzz harness, re-run with the new schema, passes.

**Phase 5: Exposure rollout**
- **Unlocks:** general availability (GA).
- **Depends on:** V4, V3, V2, and the organizational items in §2.
- **Tasks:**
  1. Internal dogfooding.
  2. One design-partner tenant.
  3. 5% of signups.
  4. GA.

  Each step widens only after 7 days with no divergence alerts and the SLO met.
- **Rollback:** cohort flags. Data stays in the same format, so there is no point of no return.
- **Exit check:** 99.9% SLO held for 30 days at GA (ASSUMPTION target).

## 6. Validation checks

| ID | Hypothesis | Method | Acceptance threshold | Evidence | Unlocks (if fails) | Phase |
|---|---|---|---|---|---|---|

| V1 | Yjs plus our schema always converges | Property-based fuzz: 3–50 simulated clients; random concurrency, reordering, duplication, partitions, server restarts | 0 divergences in 10k runs / 1M edits (ASSUMPTION: correctness dominates) | Fuzz report stored as a CI artifact | Editor design (Phase 4) (fails → switch to OT, re-plan Phase 1) | 1 |
| V2 | Fan-out meets the latency budget | k6 + custom WebSocket load at 50 editors/doc and 10k connections/node, for 1 h | p95 ≤ 200 ms, 0 dropped updates (ASSUMPTION) | Load-test report plus dashboard snapshot | Phase 4, capacity commitments (fails → consistent hashing) | 3 |
| V3 | A confirmed edit is never lost | Kill sync nodes (kill -9), fail over Postgres, restore from snapshot plus log, all under load | 0 confirmed edits lost; restore ≤ 1 h (ASSUMPTION) | Chaos run log plus restore runbook | Frozen storage format (fails → synchronous snapshots) | 1 |
| V4 | No cross-tenant or cross-document access; revocation is timely | Automated ACL test matrix plus an external penetration test | 0 unauthorized reads or writes; revocation ≤ 5 s (ASSUMPTION); sign-off from security reviewer (UNKNOWN: name needed) | Penetration test report, test matrix results | Phase 5 exposure (fails → fix and retest; no exposure) | starts 2, required before 5 |

## 10. Deferred
These are not being built yet. Each comes forward when its condition is met:
- **Full offline-first editing:** a customer requirement, or ≥ 10% of sessions spending more than 5 minutes offline.
- **End-to-end encryption:** a contract requirement. That moves the trust-boundary row to a re-gate.
- **Multi-region / data residency:** a residency requirement, or p95 above 200 ms for a large region.
- **Search indexing:** usage data showing that users struggle to find documents.
- **Suggestion mode / tracked changes:** design-partner demand. It needs a re-run of V1.
- **Mobile apps:** web usage on mobile above 20%.
- **AI writing assistant:** product decision. It brings in the AI-layer defenses first.
- **Splitting the monolith into services:** the revisit trigger in the monolith-vs-services row of §3.
