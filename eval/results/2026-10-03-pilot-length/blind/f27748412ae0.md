# BUILD PLAN: Autonomous GitHub Issue Triage & Resolution Agent

## 1. Classification and constraints
- **What:** A GitHub App agent. It labels new issues, finds duplicates and asks for missing information. When a maintainer asks it to, it writes a fix in a sandbox and opens a draft PR.
- **Type:** AI-agentic plus software. Greenfield. Not small: it takes untrusted public input, writes to repos and spends money on inference.
- **Dominant constraint:** correctness and security.
- **Worst failure:** text planted in an issue, a comment or a repo file hijacks the agent. It then leaks secrets (App token, CI secrets) or pushes malicious code that gets merged.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Triage latency | ≤5 min from webhook to label | ASSUMPTION (comparable to a maintainer's first response) | Phase 2 |
| Resolve run time | ≤30 min hard timeout | ASSUMPTION (typical test-suite runtime) | Phase 1 |
| Cost per triage | ≤$0.05 | ASSUMPTION (about 10k tokens on a mid-tier model) | V5 |
| Cost per merged PR | ≤$5 | ASSUMPTION (cheaper than an hour of engineer time) | V5 |
| Monthly spend cap | UNKNOWN: the engineering lead sets it; needed before Phase 4 | UNKNOWN | V5 |
| Operational complexity | 1 worker service + 1 sandbox runner | ASSUMPTION | Phase 0 |

**Missing inputs** (assumptions are stated; what changes if each is false is in brackets):
- **Which repos are in scope.** Assumed: public repos first. [If private code is in scope, sending it to an LLM vendor needs a signed zero-retention agreement before Phase 2.]
- **Merge policy.** Assumed: the agent never merges. [If auto-merge is wanted, add an R3 gate with signed provenance.]
- **Languages and test suites.** These decide the sandbox image.
- **Named security reviewer** for V1 and V2.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Trust boundary and write scope | R3: a single bad merge or leaked secret cannot be undone | App can write issues, PRs and only `agent/*` branches; branch protection requires a human review; never merges; no secrets in its context | Containment by design holds even when an injection succeeds | V1 | V1 fails → triage becomes suggest-only, resolve is disabled |
| Code execution isolation | R3: a sandbox escape exposes secrets | Ephemeral microVM (Firecracker) with no credentials; egress only to a package mirror; destroyed after each run | Tests run without network access | V2 | V2 fails, or too many test suites need the network → read-only patch proposals with no execution |
| Autonomy level | R2: wrong public comments damage reputation but can be deleted | Triage acts on its own once V3 passes; resolve starts only on a maintainer's `/agent fix`; PRs stay drafts | Maintainers will review | V3, V4 | Maintainers reject more than 70% of PRs over 4 weeks → triage only |
| Data-privacy boundary | R3: data sitting at a vendor cannot be recalled | Public repos only; private repos wait for a zero-retention agreement | Issues and public code contain no personal data | Basis: public data only. Gitleaks secret-scan scrubbing as defense in depth | Private repos added → agreement and legal approval first |
| Hosted API vs self-host | R2: provider abstraction exists from Phase 0 | Hosted frontier model, with a cheaper fallback model | Cost fits the budget | V5 | V5 fails, or legal denies the vendor → self-host an open model |
| Prompt+RAG vs fine-tune | R2 | Prompt plus retrieval (code search, issue embeddings) | The base model is good enough | V3, V4 | V4 fails on retrieval-adequate cases → consider a fine-tune on public data |

**R1 defaults:** sync vs async → async (webhook → queue → worker); monolith vs services → one worker plus a sandbox runner; build vs buy → build the orchestration, buy the model and sandbox host; consistency → idempotent per-issue jobs keyed by `(issue, event-id)`.

## 4. Walking skeleton (Phase 0)
- **Request and response:** a real issue opened on an internal test repo gets one bot comment, "Suggested labels: …", from a single LLM call.
- **Tiers it crosses:** GitHub webhook → ingress (signature verified) → SQS queue → worker → model-access seam → GitHub API (comment only).
- **Deploy, observe, roll back:** deployed with Terraform and CI. OpenTelemetry traces each job end to end and records tokens, cost and latency. An alert fires on job failures and on spend. Rollback is a redeploy of the previous image plus an App kill-switch flag.
- **Safety in the skeleton:** the issue text is passed as delimited data. A hard 8k-token cap and a $1/day cap apply. The only permission is comment, on the allow-listed repo.
- **Who can reach it:** only the allow-listed internal repo, behind a feature flag.
- **Exit check V0:** see §6.

## 5. Phases
- **Phase 1: Defenses and budgets**
  - Unlocks: exposure to untrusted input (Phase 2) and code execution (Phase 3).
  - Depends on: V0.
  - Tasks:
    1. Build a tool executor with an allow-list of tools and schema-validated arguments; the model cannot bypass it.
    2. Add human approval: actions on the gated list need a maintainer command bound to a hash of that exact action.
    3. Close exfiltration paths: no arbitrary URLs or images in output, and comments are sanitized.
    4. Build the sandbox runner with no credentials and egress only to the package mirror.
    5. Set caps per job (tokens, iterations, time) and per day (cost).
    6. Put an injection suite in CI.
  - Rollback: the kill-switch flag, then revert the image.
  - Exit check: V1 and V2 pass. A runaway loop is cut off at its cap and emits a metric.
- **Phase 2: Triage**
  - Unlocks: live triage on a canary repo.
  - Depends on: Phase 1, V1.
  - Tasks:
    1. Retrieval: embeddings of past issues for duplicate detection, plus repo docs and CODEOWNERS.
    2. Harden the model-access layer (retries, fallback model, structured output).
    3. Shadow-run on historical issues.
    4. Go live: labels, duplicate links and requests for missing information on 1 public canary repo.
  - Rollback: turn the flag back to suggest-only and remove bot labels with a script.
  - Exit check: V3 passes. Triage latency meets its budget over 1 week.
- **Phase 3: Resolve**
  - Unlocks: draft PRs from the agent.
  - Depends on: Phase 2, V2.
  - Tasks:
    1. Orchestration as a single-agent loop: locate → plan → edit → run tests in the sandbox → open a draft PR with a trace link.
    2. Replay historical issues that already have known fixes.
    3. Canary on 1 repo, triggered only by `/agent fix`.
  - Rollback: disable the `/agent fix` command, close agent PRs and delete `agent/*` branches.
  - Exit check: V4 passes. Every PR goes through a human review, which branch protection enforces.
- **Phase 4: Scale and feedback**
  - Unlocks: org-wide use.
  - Depends on: V4, V5, and the monthly cap being supplied.
  - Tasks:
    1. Widen in waves: 1 → 5 → all public repos, with a check after each wave.
    2. Routing: a cheap model for triage, the strong model for resolve.
    3. Feedback: PR review outcomes and label corrections are reviewed, then added to the eval set.
  - Rollback: shrink the repo allow-list.
  - Exit check: V5 holds at each wave. Eval scores show no regression.

## 6. Validation gates

| ID | Hypothesis | Method | Acceptance threshold | Evidence | Unlocks (and if it fails) | Phase |
|---|---|---|---|---|---|---|
| V0 | A change can be deployed, observed and rolled back across every tier in production | Real issue on the test repo; deploy, then roll back; inject a worker crash | One trace across all tiers; deploy and rollback both succeed; the alert fires; baseline cost and latency recorded | CI run log, trace ID, alert record in the ops repo | Phase 1 | 0 |
| V1 | An injection cannot break containment | ≥150 red-team cases planted in issues, comments, repo files and test output; security reviewer review | 0 tool calls outside the allow-list, 0 unapproved writes, 0 data egress (ASSUMPTION: zero tolerance because of the worst failure); named reviewer signs off | CI suite report and signed review in the security tracker | Phase 2 exposure; if it fails: no exposure, redesign the executor | 1 |
| V2 | The sandbox does not leak | Escape and egress tests; credential scan of the sandbox environment | 0 egress to non-allow-listed hosts; 0 credentials present (ASSUMPTION: zero tolerance); reviewer signs off | Pentest report in the security tracker | Phase 3; if it fails: patches proposed without running code | 1 |
| V3 | Triage is accurate enough to act on its own | Shadow run on 300 labeled historical issues | Label accuracy ≥85%; duplicate precision ≥90% (ASSUMPTION: maintainers tolerate about 1 wrong label in 7) | Eval report in the eval repo | Live triage; if it fails: suggest-only | 2 |
| V4 | Fixes are good enough to be worth reviewing | Replay 50 closed issues against their hidden tests; then a 4-week canary | ≥20% of replays pass hidden tests; ≥30% of canary PRs merged (ASSUMPTION: about SWE-bench-level agent performance) | Replay report and PR outcome dashboard export | Phase 4; if it fails: triage only | 3 |
| V5 | Inference costs stay within budget | Canary spend metering over 4 weeks | ≤$5 per merged PR, ≤$0.05 per triage (ASSUMPTION); total under the monthly cap (UNKNOWN until supplied) | Cost dashboard export | Wider rollout; if it fails: routing first, then reduce scope | starts in 3, required before 4 |

## 9. Methodology exceptions
None.

## 10. Deliberately deferred
- **Private repos:** pulled forward once a zero-retention agreement and legal approval are in hand.
- **Auto-merge:** only if more than 80% of agent PRs merge unchanged for 3 months, and only after a new R3 gate.
- **Multi-agent orchestration:** only if V4 failures trace back to the single-agent loop.
- **Fine-tuning:** only if V4 fails while retrieval was adequate.
- **Long-term memory across issues:** only if evals show repeated mistakes that context from earlier issues would fix.
- **Self-hosted model:** if V5 fails or legal denies the vendor.
