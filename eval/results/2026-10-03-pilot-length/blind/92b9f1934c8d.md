# Plan: An Autonomous Agent That Triages and Resolves GitHub Issues

## 1. Goals and scope

**Goal:** Cut the time from "issue filed" to "issue resolved" for common, well-defined issues, while human maintainers keep control over what gets merged.

**In scope:**
- Labeling, deduplicating, and routing new issues
- Asking for missing information
- Reproducing bugs
- Opening pull requests for fixes it can make confidently: small bugs, docs, dependency bumps, test gaps, simple features

**Out of scope at first:**
- Merging without a human
- Security vulnerabilities (send to a private process)
- Architectural changes
- Anything touching secrets, CI configuration, or release pipelines

## 2. Architecture

```
GitHub Webhooks ──► Event Queue ──► Orchestrator ──► Worker Sandboxes
     ▲                                  │                  │
     │                                  ▼                  ▼
     └──── GitHub App (scoped) ◄── Policy Gate ◄── Verifier/Critic
                                        │
                                  Memory/Index Store
```

**Components:**

1. **Ingestion:** A GitHub App subscribes to `issues`, `issue_comment`, `pull_request`, and `check_run` events. Events go into a durable queue (SQS, Redis Streams, etc.) with idempotency keys so retries never produce duplicate actions.
2. **Orchestrator:** A state machine per issue (see §3). It tracks budget, attempts, and the current stage, and stores state outside the LLM context so the agent can resume after a crash.
3. **LLM agent core:** A tool-using model that runs a plan → act → observe loop inside each stage. Each stage gets a narrow toolset and its own system prompt.
4. **Sandboxed workers:** Ephemeral containers holding a clone of the repo. By default they have no network except package mirrors, plus CPU and time limits. This is where code runs, tests execute, and patches are built.
5. **Knowledge and memory:**
   - Code index: embeddings plus symbol/AST search (e.g., ctags or tree-sitter)
   - Issue/PR history index, used for dedup and precedent
   - Repo conventions file (`AGENT.md`): build commands, style, owners, no-go areas
   - Outcome log of accepted and rejected PRs, used for learning and evals
6. **Policy gate:** Deterministic code (not the LLM) that approves every outgoing write: label, comment, push, or PR. It enforces permissions, rate limits, and path restrictions.
7. **Verifier/critic:** A separate model call or rule set that reviews the patch and the reasoning before a PR is opened.

## 3. Issue lifecycle (state machine)

```
NEW → TRIAGED → (NEEDS_INFO | DUPLICATE | ROUTED_HUMAN | ACTIONABLE)
ACTIONABLE → REPRODUCING → PLANNING → IMPLEMENTING → VERIFYING → PR_OPEN
PR_OPEN → (REVISING ↔ PR_OPEN) → MERGED | CLOSED | ESCALATED
```

### Stage A: Triage (runs on every issue, cheap model)
- **Classify:** bug, feature, question, docs, or security. Assign component labels from the CODEOWNERS/path mapping and estimate severity.
- **Dedup:** Search past issues semantically. If similarity is above a threshold, comment with links and suggest closing. Don't auto-close until confidence is high and the policy allows it.
- **Completeness check:** For bugs, look for version, reproduction steps, expected vs. actual behavior, and logs. If anything is missing, post one templated, specific request and move to `NEEDS_INFO`. Re-check when the reporter replies, and mark stale after N days.
- **Security screen:** If the issue looks like a vulnerability report, stop. Notify the security owners privately and never discuss exploit details in public.
- **Actionability score:** Combines clarity, estimated impact, test coverage of the affected area, and similarity to past successful fixes. Above a threshold and in an allowed category → `ACTIONABLE`. Otherwise → `ROUTED_HUMAN` with a summary and suggested assignee.

### Stage B: Reproduce
- Build the project using the commands in `AGENT.md`.
- Turn the report into a **failing test** or a minimal reproduction script. This is the most important step, because it turns a vague issue into a target that can be checked.
- If the agent can't reproduce after a bounded number of attempts, comment with what it tried and ask targeted questions, or escalate.

### Stage C: Plan
- Locate the relevant code using symbol search, stack traces, `git blame`, and recent related commits.
- Write a short plan: root cause hypothesis, files to change, test strategy, and risk assessment.
- If the plan touches restricted paths, has more than K files or L lines changed, or changes a public API, escalate with the plan attached as a comment rather than proceeding.

### Stage D: Implement
- Work on a branch named `agent/issue-<n>`.
- Make minimal, focused diffs that follow repo style, enforced by running the formatter and linter.
- Add or keep the regression test from Stage B.
- Iterate in a loop: edit → run targeted tests → read failures → adjust. Cap it at a fixed number of iterations and tokens.

### Stage E: Verify
- Run in order:
  1. The new test, which must fail on the base branch and pass on the fix branch
  2. The full relevant test suite
  3. Lint, type checks, and build
- **Critic review:** A separate prompt checks for:
  - Fixing symptoms instead of the cause
  - Weakened or deleted tests
  - Swallowed exceptions
  - Unrelated changes
  - Leaked secrets
  - License concerns from copied code
- **Deterministic checks:**
  - Diff size limits
  - Forbidden paths (e.g., `.github/workflows`, lockfiles unless the task is a dependency bump)
  - No test files deleted
  - Secret scanning

### Stage F: Open PR
- The PR body contains:
  - A link to the issue
  - Root cause explanation
  - A summary of the change
  - How it was verified, with commands and results
  - Risks and open questions
  - Clear "automated agent" labeling
- Request review from the code owners and comment on the issue with the PR link.

### Stage G: Respond to review
- Address review comments by pushing new commits, and answer questions with evidence.
- After N revision rounds, or if a reviewer disagrees on the overall approach, stop and hand off to a human.
- When CI fails, read the logs and fix the problem if it relates to the change. If the failure is a flaky or unrelated test, report it instead.

## 4. Tooling exposed to the agent

| Tool | Stages | Notes |
|---|---|---|
| `search_issues`, `get_issue` | Triage | Read-only |
| `add_label`, `post_comment` | Triage+ | Via policy gate, rate-limited |
| `code_search`, `read_file`, `list_dir` | B–G | Sandbox |
| `run_command` | B–E | Sandbox, allowlisted commands, timeouts |
| `apply_patch` / `write_file` | D, G | Path restrictions |
| `run_tests` | B–E | Structured results |
| `git_commit`, `push_branch`, `open_pr` | F, G | Agent-prefixed branches only |
| `escalate(reason, summary)` | All | Always available |

Tools return structured, truncated outputs, such as the top failures with file:line, to keep context small.

## 5. Safety and guardrails

- **Least privilege:** A GitHub App with only issues and pull-requests write access plus contents write limited to its own branches. It has no admin rights, can't push to protected branches, and can't merge.
- **Prompt-injection defense:** Treat issue text, comments, and repo content as untrusted data. The policy gate ignores any "instructions" found in content. The sandbox has no secrets and no outbound network, so a hijacked agent has nothing to exfiltrate and nowhere to send it.
- **Human-in-the-loop:** Merging always needs human approval. Auto-closing duplicates or stale issues needs a high confidence threshold, and is reversible.
- **Budgets:** Per-issue limits on tokens, wall-clock time, and attempts. Global daily caps on PRs and comments per repo. A kill switch label (`agent:off`) and a global disable flag.
- **Transparency:** Every action is logged with its reasoning trace. All comments carry a bot signature and an opt-out mechanism.
- **Abuse resistance:** Ignore issues from brand-new accounts for code changes, or require a maintainer label such as `agent:fix` to trigger implementation.

## 6. Evaluation and metrics

**Offline:**
- Benchmark on SWE-bench-style historical issues from your own repos: past issues with known fixing commits and tests.
- Measure resolution rate, test pass rate, and diff similarity.
- Run this as a regression gate for every prompt, model, or tool change.

**Online:**
- **Triage:** label accuracy (sampled human audit), duplicate precision/recall, time to first response.
- **Resolution:** PR acceptance rate, revisions per PR, time to merge, and post-merge reverts or bug reopens (the key quality signal).
- **Cost:** tokens and compute per resolved issue.
- **Trust:** maintainer satisfaction surveys and rate of `agent:off` usage.

## 7. Rollout phases

1. **Shadow mode (2–4 weeks):** The agent triages and drafts fixes privately. Humans compare its output with what actually happened, and thresholds get calibrated.
2. **Triage live:** Labels, dedup suggestions, and info requests go public. Code fixes run only on maintainer opt-in (`agent:fix` label).
3. **Fixes on allowlisted categories:** docs, typos, dependency bumps, small bugs in well-tested modules. PRs are drafts by default.
4. **Expansion:** More categories and repos, using thresholds tuned on the outcome data. Consider auto-merge only for trivial classes like docs typos, and only with green CI plus owner opt-in.

## 8. Key risks and mitigations

| Risk | Mitigation |
|---|---|
| Plausible but wrong fixes | Require a reproduction test that fails then passes, add a critic review, and track reverts |
| Reviewer fatigue from noisy PRs | Strict actionability thresholds, daily caps, draft PRs |
| Prompt injection via issues | Untrusted-data handling, deterministic policy gate, secret-free sandbox |
| Flaky tests misleading the agent | Re-run failures and compare against the base branch before attributing them to the change |
| Large repos overflowing context | Retrieval plus symbol search, and narrow per-stage context |
| Cost blowups | Hard budgets, a cheap model for triage, and the expensive model only for implementation |

## 9. Minimal first build (MVP)

To start, build the following:
- GitHub App and webhook queue
- Triage stage (classify, dedup, info request)
- Label-triggered fix pipeline running in a Docker sandbox, with a reproduce → implement → verify loop
- Draft PR output
- Logging dashboard

Shadow-test it on one well-tested repo with clear `AGENT.md` build instructions, and expand based on measured acceptance and revert rates.
