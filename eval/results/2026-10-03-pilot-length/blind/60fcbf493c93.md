# Plan: Customer-support RAG chatbot over help-center docs

## 1. Classification and constraints
- **What:** A chat widget for customers. It answers from published help-center articles, cites them, and hands off to a human agent.
- **Type:** AI (RAG) plus software. The bot is new, but it sits on an existing help center and ticketing system. Not a small build, because it faces outside users and chats will contain personal data.
- **Dominant constraint:** correctness. Answers must be grounded in the articles.
- **Worst failure:** the bot confidently states a wrong policy (refund, pricing, security) that a customer relies on, and the company may be held to it.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency | p95 first token ≤2 s, full answer ≤8 s | ASSUMPTION (usual chat response times) | V3 |
| Availability | 99.5%; if the bot fails, the widget shows "contact support" | ASSUMPTION (the bot isn't the only support path) | Phase 4 |
| Throughput | Peak concurrent chats: comes from Support analytics, needed by Phase 4 | UNKNOWN | V3 |
| Per-request cap | 8k input / 800 output tokens, 5 turns per session | ASSUMPTION (about 6 chunks answer a typical question) | Phase 0 |
| Cost per resolved conversation | Must beat the cost of a human-handled ticket (Support Ops supplies it, needed by Phase 4) | UNKNOWN | V3 |
| Answer quality | See V2 | ASSUMPTION | V2 |

**Missing inputs:**
1. **Does the bot act on accounts** (order status, refunds)? I assume no: read-only Q&A plus handoff. If yes, an auth and tool-approval phase goes in before Phase 2, and V1 grows.
2. **Which help-center platform, and does it hold internal-only articles?** I assume only public articles get indexed.
3. **Languages:** assumed English only.
4. **"Resolved"** is assumed to mean no ticket opened within 72 h.

## 3. Key decisions

| Decision | Reversibility | Default | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| What the bot may say | R3: customers can act on what it says | Answer only from retrieved, cited, published articles; otherwise refuse or hand off. Never promise refunds or exceptions | Grounded refusal stays accurate without refusing too often | V2 | V2 fails, or out-of-scope refusals swamp the handoff queue |
| Data-privacy boundary | R3: chat PII goes to a vendor and into logs | Hosted LLM under zero-retention / no-training terms; redact PII before logging; keep transcripts 30 days (ASSUMPTION) | Legal accepts the vendor terms | V1 | Legal rejects the terms → self-hosted open-weight model behind the same interface |
| Build vs buy | R2: weeks to move content and widget | Build a thin RAG service | Vendor bots (Intercom Fin, Zendesk AI) do no better on our docs | Vendor trial on the V2 eval set, Phase 2 | Vendor passes V2 at lower cost per resolution → buy |
| Hosted API vs self-host | R2: contract plus infrastructure | Hosted API behind a provider-agnostic interface | Fits the V3 cost bar | V1, V3 | Terms refused, or V3 fails |

**minor defaults:** prompt+RAG, no fine-tuning; a single service; synchronous streaming; pgvector with a pinned embedding model (re-embedding this corpus takes hours); index synced from the CMS hourly plus a webhook on publish.
**N/A:** consistency vs availability (the bot holds no record); migration and cutover (the help center and ticketing stay as they are).

## 4. First end-to-end slice (Phase 0)
- **Request:** an employee asks "How do I reset my password?" and gets a streamed answer that cites the live article URL.
- **Tiers:** widget on a help-center page behind a feature flag → API service → retrieval over about 20 ingested public articles in pgvector → hosted LLM → answer with citations. The system prompt is kept separate; user and retrieved text go in delimited data fields, never as instructions. The §1 token caps are enforced.
- **Day zero:** blue/green deploy through CI/CD. Each request gets an OpenTelemetry trace with retrieved chunk IDs, tokens, cost and latency. Logs are redacted by default. Alerts fire on error rate and cost per hour. Rollback is flag off plus the previous release.
- **Reach:** only employees on an SSO allow-list.
- Exit check: V0.

## 5. Phases
- **Phase 1: Defenses and budgets**
  - Unlocks: any outside user. Depends on: V0.
  - Tasks:
    - Injection suite in CI, covering both user text and instructions planted in docs.
    - Output filter: no links outside the help-center domain, no markdown images, no commitments the docs don't support.
    - PII redaction.
    - Per-session cost cap, plus a timeout that falls back to "related articles + contact us".
    - Handoff that opens a ticket with the transcript, only after the user confirms.
    - Get the vendor terms signed.
  - Rollback: flag off. Exit: V1.
- **Phase 2: Retrieval and answer quality**
  - Unlocks: Phase 4. Depends on: V1 before any outside exposure; the eval-set approval.
  - Tasks:
    - Full-corpus ingest, including propagating deletes.
    - Chunk by article heading; hybrid BM25 + vector search.
    - Build a 200-query labeled set from redacted real tickets.
    - Prompt that requires citations.
    - Vendor trial (§3).
  - Rollback: versioned indexes; point the alias back. Exit: V2.
- **Phase 3: Model access and session memory**
  - Depends on: V2.
  - Tasks:
    - A fallback model that is a config switch, plus retries.
    - Memory only within a session: it expires after 24 h and is never written to the index.
  - Rollback: revert the config. Exit: the fallback model meets the V2 bar; a test shows nothing is recalled across sessions.
- **Phase 4: Canary rollout**
  - Depends on: V1, V2, Phase 3, and the two UNKNOWN inputs.
  - Tasks:
    - Logged-in visitors at 1% → 10% → 50% → 100%, holding each step at least 3 days.
    - Support reviews a daily sample.
    - Rate limits.
  - Rollback: flag to 0%. Exit: V3 passes before going past 10%.
- **Phase 5: Feedback**
  - Tasks:
    - Thumbs up/down and handoff reasons go into a review queue.
    - Reviewed fixes go into the docs or the eval set, never straight into prompts.
    - A doc-gap report goes to the content team.
  - Exit: the next eval run improves with no regressions.

## 9. Exceptions
None.

## 10. Deferred
- **Account actions (order lookup, refunds):** comes forward if more than 20% of handoffs need account data. That would need auth plus action-level approvals first.
- **Routing to a cheaper model:** comes forward if V3 fails on cost.
- **Memory across sessions:** comes forward if repeat-contact data shows it would help, and Privacy approves.
- **Multiple languages:** comes forward once non-English traffic is measured.
- **Fine-tuning:** comes forward if V2 fails even after retrieval and doc fixes.
- **Indexing internal articles:** comes forward once a visibility filter for agent-only content is built and tested.
