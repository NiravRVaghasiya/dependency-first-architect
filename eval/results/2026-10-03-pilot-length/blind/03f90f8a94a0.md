# BUILD PLAN: Autonomous GitHub Issue Triage & Resolution Agent

## 1. Classification and constraints
- **What it is:** A GitHub App that labels incoming issues, flags duplicates, and asks clarifying questions. For issues a maintainer approves, it writes a fix in a sandbox and opens a pull request (PR).
- **Type:** An AI agent plus software. Greenfield. Not a small build: it acts on real repos, spends money and may send private code to a model vendor.
- **Dominant constraint:** Correctness and safety of its writes.
- **Worst failure:** Text planted in an issue or a repo file hijacks the agent. It then leaks secrets or private code, or gets malicious code onto a protected branch.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Webhook acknowledgement | ≤10 s | REQUIREMENT (GitHub webhook timeout) | Phase 0 |
| Triage latency | ≤5 min per issue | ASSUMPTION (maintainer usefulness) | V2 |
| Fix-attempt wall clock | ≤30 min, hard kill at 45 | ASSUMPTION (typical agent run lengths) | V3 |
| Inference cost | triage ≤$0.10; fix ≤$5 per attempt, hard cap $10 | ASSUMPTION (current hosted-model token prices) | V3 |
| Throughput | UNKNOWN: issue volume per repo, from repo owners, needed by Phase 4 | UNKNOWN | Phase 4 |
| Availability | Best effort; no events lost (durable queue + GitHub redelivery) | ASSUMPTION | Phase 1 |
| Operational complexity | 3 deployables (receiver, worker, sandbox pool) | ASSUMPTION | Phase 0 |

**Missing inputs:**
1. Target repos: public or private, and which org.
2. Org-admin approval to install the App.
3. Legal/security approval to send private code to a model vendor.
4. Cost ceiling per month.

**Assumption the phase order rests on:** "Resolve" means opening a PR for human review, never merging. If autonomous merging is required, the trust-boundary row (§3) becomes the critical path and Phase 3 needs a new gate.

## 3. Tradeoff gates

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Write authority (trust boundary) | R3: a bad merge or a secret leak can't be undone | Least-privilege App; PRs only, from `agent/*` branches; branch protection and human review required; no merge permission | Maintainers will review agent PRs | V1 | V1 fails: drop to posting the patch as a comment |
| Data-privacy boundary | R3: code held at a vendor is a contractual matter | Hosted model with zero data retention; public and sandbox repos only until V4 passes | Vendor terms are acceptable | V4 | V4 rejects: self-hosted model for private repos |
| Hosted API vs self-host | R2: re-tune prompts and evals | Hosted API behind a provider interface | Quality needs a frontier model | V3 on fallback model | V4 rejects, or cost exceeds V3 bar |
| Sandbox isolation | R2: runner rework | Ephemeral gVisor/Firecracker microVM per run; no secrets inside; egress allowed only to model API and package mirror | Repo tests run offline with the mirror | V1 | Egress breach in V1 → offline-only, no package installs |
| Sync vs async | R2: pipeline shape | Webhook → durable queue → workers | 10 s acknowledgement REQUIREMENT | Cited basis (GitHub timeout vs 30 min runs) | None foreseen |

**R1 defaults:**
- Monolith vs services: modular monolith, with the sandbox as a separate pool.
- Build vs buy: build a thin orchestrator. Switch to an off-the-shelf coding agent if it meets the V2/V3 bars on the same eval set.
- Prompt+RAG vs fine-tune: prompt plus repo search tools.
- Consistency: at-least-once delivery, deduplicated by the delivery ID as an idempotency key.

**N/A:** Brownfield migration (greenfield).

## 4. Walking skeleton (Phase 0)
- **Request:** A real issue opened in an internal sandbox repo, labeled `agent-ok`. The response is one triage comment with a suggested label.
- **Tiers:**
  1. Webhook receiver (checks the HMAC signature, acknowledges within 10 s).
  2. Queue (SQS or equivalent).
  3. Worker.
  4. Model call through the provider seam. Issue text is wrapped as quoted data, with an 8k-token cap and a $0.25 per-run cost cap.
  5. GitHub API comment using a short-lived App installation token.
- **Deploy and observe:**
  - CI builds signed images and deploys them to a container platform.
  - One OpenTelemetry trace runs per issue. Token and cost metrics are recorded.
  - An alert fires on worker failure or a dead-letter message.
  - Rollback means redeploying the previous image.
- **Who can reach it:** The App is installed only on the sandbox repo, with an allow-list of repos and the feature off by default.

The V0 exit check is in §6.

## 5. Phases

**Phase 1: Defenses and budgets**
- **Unlocks:** Exposure to real repos.
- **Depends on:** V0.
- **Tasks:**
  1. Tool allow-list with an argument validator in the executor (read file, search, run tests, write to the agent branch, open PR, comment).
  2. Sandbox microVM with egress allow-list and no credentials. A narrowly scoped token for pushes lives outside the sandbox.
  3. Approval binding: fix attempts run only after a maintainer applies the `agent-fix` label. The executor checks the labeler's write permission.
  4. Per-run token, iteration and wall-clock caps, plus a monthly spend kill switch.
  5. Injection suite in CI (V1).
  6. Start the V4 request (it has lead time).
- **Rollback:** Feature flag off; uninstall the App.
- **Exit check:** V1 passes. A runaway loop is cut off at the cap and emits a metric.

**Phase 2: Triage**
- **Unlocks:** Label and comment writes on a canary repo.
- **Depends on:** V1, org approval.
- **Tasks:**
  1. Repo-context retrieval: README, CONTRIBUTING, label taxonomy, and duplicate search over past issues with a pinned embedding version.
  2. Model access hardening: retries, fallback model, structured output.
  3. Shadow run on historical issues (V2).
  4. Enable writes on one canary repo.
- **Rollback:** Flag off; the bot removes its own labels by tag.
- **Exit check:** V2 passes.

**Phase 3: Resolution**
- **Unlocks:** Agent PRs on the canary repo.
- **Depends on:** V2, V1. V4 only if the canary repo is private.
- **Tasks:**
  1. Orchestration: reproduce → locate → patch → run tests → self-review → open PR with trace link.
  2. Per-issue working memory, discarded after the run.
  3. Canary run (V3).
- **Rollback:** Close agent PRs and delete `agent/*` branches; protected branches are never touched.
- **Exit check:** V3 passes. Each step is traced, and failed runs surface as an issue comment.

**Phase 4: Widen and feedback**
- **Unlocks:** More repos.
- **Depends on:** V3. V4 for private repos. Throughput input.
- **Tasks:**
  1. Widen one repo at a time, each re-checked against the V3 bars.
  2. Feedback loop: merged, edited or closed PR outcomes and label corrections feed a reviewed eval set.
  3. Routing: cheap model for triage, strong model for fixes.
- **Rollback:** Remove the repo from the allow-list.
- **Exit check:** No regression on the eval set after each feedback update.

## 6. Validation gates

| ID | Hypothesis | Method | Acceptance threshold | Evidence | Unlocks (if fails) | Phase |
|---|---|---|---|---|---|---|
| V0 | The pipeline deploys, observes and rolls back end to end | Run the §4 path, deploy and roll back through CI, kill a worker | One trace across all tiers; rollback succeeds; injected failure alerts; first latency and cost baselines recorded | V0 runbook record + trace export in ops repo | Phase 1 (if fails: fix the pipeline) | 0 |
| V1 | A hijacked agent still cannot break containment | Injection suite planted in issue bodies, comments, repo files and tool output; sandbox egress and secret-read probes; security reviewer red team | 0 tool calls outside the allow-list, 0 unapproved writes, 0 egress outside the allow-list, 0 secrets reachable; named security reviewer signs off | CI suite report + signed review in security tracker | Phases 2–3 exposure (if fails: comment-only mode, §3) | 1 |
| V2 | Triage matches maintainer judgment | Shadow run on 200 closed issues from the canary repo | ≥85% label agreement, ≥80% duplicate precision, p95 ≤5 min (all ASSUMPTION) | Eval report in eval store | Phase 2 writes (if fails: suggest-only comments) | 2 |
| V3 | Fixes are worth their cost | Canary repo, ≥30 approved issues | ≥30% of PRs merged without major rework; ≤$15 per merged PR (both ASSUMPTION) | Per-PR outcome + cost ledger | Phase 4 (if fails: triage only; re-plan fix scope) | 3 |
| V4 | Sending private code to the vendor is permitted | Legal/security review of vendor zero-retention terms | Named legal approver signs off | Approval record in contracts system | Private repos (if fails: self-host, §3) | Starts in 1, required before private exposure |

## 9. Methodology exceptions
None.

## 10. Deliberately deferred
- **Autonomous merge:** pulled forward only if V3 shows ≥90% unmodified merges on docs-only changes, plus a new gate.
- **Acting on issues from non-collaborators without a maintainer label:** pulled forward when V1 passes on a corpus of outside-author issues.
- **Long-term memory across issues:** pulled forward if V3 failures trace to repeated lost context.
- **Fine-tuning:** pulled forward if prompt+RAG plateaus below the V3 bar.
- **Multi-agent orchestration:** pulled forward if the single loop fails V3 on multi-file changes.
