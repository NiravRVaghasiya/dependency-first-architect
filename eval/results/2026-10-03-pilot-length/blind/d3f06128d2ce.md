# BUILD PLAN: Multi-tenant SaaS billing system

## 1. Classification and constraints
- **What it is:** Subscription and usage billing for the tenants of a SaaS product. It covers plans, metering, invoices, payments, dunning and ledger.
- **Type:** Software. Greenfield. Not small, because it moves money and holds customer financial data.
- **Dominant constraint:** Correctness.
- **Worst failure:** Taking the wrong amount from a tenant, such as a double charge or charging the wrong tenant. Exposing one tenant's billing data to another is a close second.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Invoice accuracy | 0 cent-level discrepancies against an independent recompute | ASSUMPTION (basis: money correctness) | V2, V4 |
| Usage-ingest throughput | UNKNOWN. Product must supply peak events/sec per tenant; needed in Phase 2 | UNKNOWN | V3 |
| Usage-ingest latency | p99 < 200 ms to acknowledge | ASSUMPTION (keeps client SDKs non-blocking) | V3 |
| Availability | 99.9% for the billing API; invoice runs may lag ≤ 1 h | ASSUMPTION (typical SaaS SLA) | Phase 4 SLO |
| RPO / RTO (ledger) | RPO 0, RTO 1 h | ASSUMPTION (a lost ledger entry means lost money) | Phase 1 restore drill |
| Operational complexity | 1 deployable, Postgres, 1 queue | ASSUMPTION (one team) | Tradeoff gates |

**Missing inputs:**
1. **Who is billed.** I assume we bill our own tenants and are merchant of record. If tenants instead bill *their* customers, the plan needs Stripe Connect, KYC onboarding and payout reconciliation. That would add an organizational dependency at Phase 0 and a new phase before Phase 3.
2. Peak usage volume (feeds V3).
3. Tax jurisdictions and data-residency obligations (Legal/Finance).
4. The finance controller who approves go-live (V4).

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Tenancy and isolation | R3: tenant IDs sit in every row; a leak cannot be undone | Shared Postgres schema, `tenant_id` on every row, row-level security enforced by a non-owner DB role | No tenant contract requires physical isolation | V1 | V1 fails, or a contract demands a dedicated DB. Then use schema-per-tenant for that tier |
| Ledger model | R3: financial history is immutable | Append-only double-entry ledger. Money stored as integer minor units plus ISO currency. Invoices derived from the ledger | Every balance can be rebuilt from entries | V2 | V2 fails. Then serialize postings per account |
| Consistency vs availability | R3: drift between money and ledger is financial harm | Strong (serializable) consistency for ledger and payment state. Usage events are eventually consistent | Usage may lag; money may not | V2, V3 | Ingest SLO missed under the ledger's locking. Then decouple via an outbox |
| Sync vs async | R2: queue contracts span modules | Async for usage ingest and payment webhooks (queue, idempotency keys). Sync for API reads | Stripe retries webhooks | V2 | Queue lag above the invoice-run window |
| Monolith vs services | R2: splitting later is weeks of work | Modular monolith (catalog, metering, rating, invoicing, payments, ledger) with enforced module boundaries | One team; volume within one DB | V3 | V3 shows metering needs independent scaling. Then extract metering only |
| Build vs buy | R3: card data and processor lock-in carry a contractual and PCI commitment | Buy: Stripe for payments and card vault, a tax vendor for tax. Build: catalog, rating, ledger, invoicing | Our pricing logic is differentiating | Cited basis: card tokenization via hosted fields keeps us in PCI SAQ-A scope | Stripe fees or coverage unacceptable. The vault-token export seam makes this R2 |
| Data-privacy boundary | R3: exposing personal or card data | No card data on our side. Billing contacts encrypted per field. Telemetry carries tenant ID, never personally identifiable data | — | V1 plus Security review in V4 | A residency obligation surfaces. Then region-pin tenants |

**R1 defaults:** language and framework follow the team's existing stack; queue is a managed one (SQS); invoice PDFs rendered server-side.

**N/A:** brownfield migration and AI rows, because this is greenfield and has no AI component.

## 4. Walking skeleton (Phase 0)
- **The real request:** an internal test tenant calls `POST /subscriptions` on a $1 plan. That posts a ledger entry, issues an invoice, and creates a Stripe **test-mode** PaymentIntent. The webhook marks the invoice paid, and `GET /invoices/{id}` returns `paid`.
- **Tiers crossed:** API gateway (auth) → monolith modules → Postgres → queue → Stripe → webhook handler → ledger.
- **Deploy, log, monitor, roll back:** CI/CD with infrastructure as code (Terraform) does a blue/green deploy. OpenTelemetry traces carry `tenant_id` and the idempotency key. Alerts fire on webhook failures and on a ledger imbalance. Rollback is a blue/green switch, rehearsed once.
- **Who can reach it:** only an allow-listed internal tenant, behind a feature flag. Stripe stays in test mode, so no real money moves.

Exit check V0 is defined in §6.

## 5. Phases

**Phase 1: Foundations (widest blast radius)**
- **Unlocks:** every module can be specified on settled contracts.
- **Depends on:** V0.
- **Tasks:**
  1. Row-level security policies and a tenant-context middleware, then V1.
  2. Ledger schema, a money type, an idempotency-key store and a transactional outbox, then V2.
  3. A versioned public API contract (OpenAPI, v1).
  4. An append-only audit log.
  5. Backup with point-in-time recovery, plus a restore drill.
- **Rollback:** schema migrations are expand/contract and only test data exists, so the phase can be undone.
- **Exit check:** V1 and V2 pass; the restore drill meets RTO 1 h.

**Phase 2: Catalog, subscriptions, metering**
- **Unlocks:** billable inputs exist.
- **Depends on:** Phase 1, and the peak-volume input.
- **Tasks:**
  1. Plans and versioned prices; a price never changes once published.
  2. Subscription lifecycle: trial, upgrade, proration, cancel.
  3. A usage-ingest endpoint with deduplication by event ID.
  4. Aggregation per billing period.
  5. V3.
- **Rollback:** feature flags per module.
- **Exit check:** V3 passes, and proration matches the golden-file test cases.

**Phase 3: Rating, invoicing, payments**
- **Unlocks:** complete billing in shadow mode.
- **Depends on:** Phase 2, V2, and the tax-vendor contract.
- **Tasks:**
  1. Rating engine.
  2. Invoice run, idempotent per tenant and period.
  3. Tax-vendor integration.
  4. Stripe PaymentIntents and webhook reconciliation.
  5. Dunning and retries.
  6. Credits and refunds as ledger entries.
  7. Shadow billing for all tenants against an independent recompute (V4, part 1).
- **Rollback:** shadow mode charges nothing.
- **Exit check:** one full billing cycle completes in shadow.

**Phase 4: Exposure to real money (smallest first)**
- **Unlocks:** revenue.
- **Depends on:** V4, Stripe live approval, and SAQ-A sign-off.
- **Tasks:**
  1. Charge in this order: internal tenant → 1 friendly tenant → 10% of tenants → all. Reconcile each cohort before widening.
  2. Turn on the 99.9% SLO and error-budget alerts.
  3. Customer billing portal (built last).
  4. Finance reports and exports.
- **Point of no return:** the first live charge, guarded by V4. Rollback is a flag back to shadow mode, a dunning pause, and refunds through ledger entries.
- **Exit check:** each cohort reconciles to $0 difference; SLO holds for 30 days.
