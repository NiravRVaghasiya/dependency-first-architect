# BUILD PLAN: CI/CD platform for 50 microservices

## 1. Classification and constraints
- **What:** A shared build, test, sign and deploy platform for 50 existing microservices.
- **Type:** Infrastructure. Brownfield: the services already ship somehow. Not a small build: many teams, and it holds production deploy rights.
- **Dominant constraint:** Correctness and security of the deploy path.
- **Worst failure:** The pipeline is compromised or misconfigured and pushes a bad or malicious artifact to all 50 services in production at once.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Commit→prod lead time (p95) | ≤ 30 min | ASSUMPTION: a common target for 50 services | Phase 2 |
| Build queue wait (p95) | ≤ 2 min at peak | ASSUMPTION | V4 |
| Peak builds/hour | UNKNOWN: platform team pulls it from current CI history in Phase 0 | UNKNOWN | V4 |
| Automatic rollback time | ≤ 10 min from regression to the previous version | ASSUMPTION | V3 |
| Runner cost/month | UNKNOWN: finance supplies the budget before Phase 3 wave 3 | UNKNOWN | V4 |
| Operational complexity | ≤ 3 platform components run by us | ASSUMPTION: platform team of 3–5 | Phase 1 |

**Missing inputs:**
- Deploy target. I assume Kubernetes on one cloud. If it is VMs or serverless, the push-vs-pull row flips and the Phase 0 tiers change.
- Repo layout. I assume one repo per service.
- Existing CI tooling, and which jobs, scripts and secrets live in it.
- Compliance regime (SOC 2, PCI). Any change-approval rule adds an organizational dependency in Phase 0.
- Platform team size.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Build vs buy CI engine | R2: pipeline definitions spread across 50 repos | Buy hosted CI (GitHub Actions or GitLab CI) plus self-hosted throwaway runners inside the VPC | The hosted tool meets the security and network needs | Phase 0 spike: one build reaches private dependencies | Data-residency rule, or V4 cost fails |
| Push vs pull deploy | R2: changes every service's deploy | Pull (GitOps with Argo CD). CI never holds cluster credentials | Targets are Kubernetes | V0 | Targets are not Kubernetes |
| Trust boundary and credentials | R3: a compromise causes harm that can't be undone, across every service | OIDC short-lived tokens scoped to one service. Images signed with cosign; Kyverno admission accepts only signed, digest-pinned images | A per-service scope stops one repo from deploying another service | V2 | V2 fails → isolate deploy per namespace with a separate controller |
| Pipeline model | R2: coordinated change across teams | Central, versioned reusable templates that each service pins by version | One template set fits most services | V1 | V1 fails → one template family per runtime |
| Artifact contract | R2: deploy tooling and rollback depend on it | Immutable image, referenced by digest, tagged with git SHA, SBOM attached | — | Phase 1 contract review | A service can't produce an image → add a separate artifact type |
| Platform-outage behavior (availability vs safety) | R2 | Prod deploys stop when the platform is down. An audited break-glass path, owned by on-call, stays available | Outages are rare and short | Break-glass drill in Phase 2 | Outages exceed the SLO |
| Migration and system of record | R2: per service | Re-platform in waves. The old pipeline is the system of record and fallback until the service cuts over; then the GitOps repo is | Services can be moved one at a time | Wave exit checks; V5 | A wave's change-failure rate is worse than baseline → pause and fix |

**R1 defaults:** runner images → one per runtime; build cache → registry layer cache; alerts → the existing on-call tool.

**N/A:**
- Monolith vs services: we assemble components, we don't write services.
- Monorepo: inherited polyrepo layout is a constraint. Switching would cost months.
- Personal-data boundary: build logs don't hold user data. Secrets in logs are handled in §7.

## 4. Walking skeleton (Phase 0)
- **Request:** One real commit to a low-risk, stateless internal service with a willing team. The response is that service running the new version in production.
- **Tiers:**
  1. Repo
  2. Hosted CI on a throwaway runner (build, unit tests)
  3. SBOM, cosign signature, registry
  4. Automated pull request bumping the version in the GitOps repo
  5. Argo CD syncs staging, then prod
  6. Service health check
- **Deploy, observe, roll back:**
  - Pipeline events and Argo sync events go into the central log and trace system (OpenTelemetry), tagged with commit SHA.
  - An alert fires on a failed sync or failed health check.
  - Rollback is a git revert in the GitOps repo, which Argo then syncs.
  - The old pipeline stays configured for this service as fallback.
- **Who can reach it:** Only the pilot service. The new platform's prod identity is scoped to that service's namespace only. Admission runs in audit mode.
- **Also in Phase 0:** inventory the old CI's jobs, triggers and secrets, and baseline lead time and change-failure rate from its history.

**V0 exit check:**
- A commit reaches prod with one trace across every tier.
- A rollback succeeds through the pipeline.
- A broken health check fires an alert.
- First lead-time and queue-wait values are recorded as a baseline (a near-zero-load floor, not capacity).

## 5. Phases

**Phase 1: Contracts and trust boundary**
- **Unlocks:** onboarding real services.
- **Depends on:** V0.
- **Tasks, widest rework first:**
  1. Freeze the artifact contract.
  2. Build pipeline template v1: build, test, scan, SBOM, sign, promote.
  3. Set up per-service OIDC identities and GitOps paths.
  4. Switch admission from audit to enforce for the pilot.
  5. Dry-run 5 representative services, one per runtime (V1).
  6. Red-team exercise (V2).
- **Rollback:** Templates are versioned, so services pin the previous version. Admission can return to audit mode.
- **Exit check:** V1 and V2 pass.

**Phase 2: Progressive delivery**
- **Unlocks:** safe exposure of critical services.
- **Depends on:** Phase 1 and the health-metrics dependency.
- **Tasks:**
  1. Argo Rollouts canary (5% → 25% → 100%) with automatic analysis on error rate and latency.
  2. Expand-then-contract rule for database migrations.
  3. Break-glass drill.
  4. V3.
- **Rollback:** Disable automatic analysis and fall back to manual promotion.
- **Exit check:** V3 passes and the drill is logged.

**Phase 3: Migration waves (smallest exposure first)**
- **Unlocks:** all 50 services on the platform.
- **Depends on:** V1 and V2 before wave 1; V3 before wave 2; V4 before wave 3.
- **Tasks:**
  1. Wave 1: 5 low-risk services.
  2. Wave 2: 15 services.
  3. Wave 3: the remaining 30, including stateful and revenue-critical ones.
  4. For each service, disable its old pipeline trigger only after 5 successful new-path deploys.
- **Rollback:** For each service, re-enable the old pipeline. It is still configured.
- **Exit check:** For each wave, change-failure rate is at or below the Phase 0 baseline, and lead time is within budget.

**Phase 4: Decommission the old CI**
- **Unlocks:** one deploy path and lower cost.
- **Depends on:** Phase 3 and V5.
- **Tasks:**
  1. Migrate the remaining dependent jobs.
  2. Rotate every secret the old CI held.
  3. Archive its configuration.
  4. Shut it down.
- **Point of no return:** deleting the old CI's secrets and data. V5 guards it.
- **Exit check:** V5 passes.

## 6. Validation gates

| ID | Hypothesis | Method | Acceptance threshold | Evidence | Unlocks (if it fails) | Phase |
|---|---|---|---|---|---|---|
| V0 | A change can be deployed, observed and rolled back in prod through every tier | Run the pilot as in §4 | The §4 exit check | Trace ID, alert record, revert commit in the platform runbook | Phase 1 | 0 |
| V1 | One template set fits most services | Dry-run 5 representative services | ≥ 4 of 5 with parameter overrides only (ASSUMPTION) | Onboarding report in the platform repo | Wave 1 spec (fail: one template family per runtime) | 1 |
| V2 | A compromised repo or workflow can't deploy another service, use static keys, or ship an unsigned image | Red-team: a malicious pull request in the pilot repo tries cross-namespace deploy, a static-key push, and applying an unsigned image | 0 successes; security lead signs off pass/fail | Red-team report plus admission-denial logs in the security repository | Wave 1 exposure (fail: re-plan the trust boundary per §3) | 1 |
| V3 | A canary regression rolls back on its own | Inject a 5xx regression, 3 trials | 3 of 3 roll back in ≤ 10 min (ASSUMPTION) | Rollout analysis runs and alert timeline | Waves 2–3 (fail: manual promotion for critical services) | 2 |
| V4 | Runners meet queue time and cost at peak | Load test at 1.5× peak builds/hour (UNKNOWN until Phase 0 history) | p95 queue ≤ 2 min (ASSUMPTION); cost ≤ the UNKNOWN finance budget | Load-test report and cost dashboard export | Wave 3 and reserved capacity (fail: tune autoscaling or change the runner mix) | Starts in 2, required before wave 3 |

## 10. Deliberately deferred
- **Throwaway preview environments:** when more than 30% of pull requests need manual integration testing.
- **Developer portal (e.g. Backstage):** when onboarding a new service takes more than 1 day.
- **Merge queue:** when main-branch breakages exceed 2 per week on any shared repo.
- **Multi-region or multi-cluster deploy:** when a service needs an availability SLO that one region can't meet.
- **Monorepo consolidation:** when cross-service changes routinely span more than 3 repos.
