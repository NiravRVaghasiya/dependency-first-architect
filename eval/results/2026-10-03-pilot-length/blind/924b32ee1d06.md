# Build order for a real-time collaborative document editor

The main rule is to get convergence right before anything else. Every later feature (presence, offline mode, history, scaling) depends on two clients always ending up with the same document. So you build and prove the sync core first, then add networking, persistence, permissions and polish in layers.

---

## Phase 0: Key decisions (days, not weeks)

These are the expensive choices to change later, so make them first.

1. **Conflict resolution model**
   - **Recommended: a CRDT** (Yjs or Automerge). The merge logic is already proven, it works offline and peer-to-peer, and the server can just pass messages along.
   - **The alternative is OT** (Operational Transformation). It's centralized, and the server decides the order of edits. Choose it only if you need strict server authority or already have OT experience. Don't write your own transform logic.
2. **Editor framework.** ProseMirror/Tiptap, Lexical or CodeMirror. Pick one that already has bindings for your CRDT (for example, y-prosemirror).
3. **Document schema.** Decide which block and inline types you'll support (paragraphs, headings, lists, tables, images, mentions). Schema changes later mean migrating stored documents.
4. **Scope of v1.** Write down what's out, for example comments, suggestion mode and tables.

**Exit criteria:** a one-page architecture doc and a schema definition.

---

## Phase 1: Single-user editor (week 1–2)

- Editor UI with the schema, toolbar and keyboard shortcuts
- Basic save/load from local storage or a stub API
- Copy/paste cleanup (pasting rich text from other apps is a big source of bugs)

**Why first:** it tests the schema and editor choice without the complexity of networking.

**Exit criteria:** one person can write and format a document reliably.

---

## Phase 2: Local convergence harness (week 2–3), the most important phase

- Connect the editor to the CRDT document model
- Run **two or more editor instances in one process or page**, synced in memory
- Build a **randomized convergence test** (fuzz test):
  - N simulated clients make random edits
  - Messages are randomly delayed, reordered and duplicated
  - Every client must end with an identical document
- Add property tests for tricky cases: concurrent formatting, deleting text someone else is typing in, list nesting, splitting and merging blocks

**Why now:** if the document model doesn't converge, nothing built later will work. This harness also becomes your regression suite for the rest of the project.

**Exit criteria:** the fuzz test passes thousands of randomized runs in CI.

---

## Phase 3: Sync server and protocol (week 3–5)

- WebSocket server (y-websocket or Hocuspocus to start, or your own)
- Sync handshake: the client sends a summary of what it has (a "state vector"), and the server replies with only the missing changes
- Broadcast each edit to everyone else on the same document
- Heartbeats, message size limits, basic rate limiting

**Exit criteria:** two browsers on different machines edit together with no lost changes, including when the network is flaky (test with simulated latency and packet loss).

---

## Phase 4: Persistence (week 5–6)

- **Storage model:** periodic snapshots plus an append-only log of edits
- **Compaction:** regularly merge old log entries into a new snapshot so loading stays fast
- Durability rules: save an edit before confirming it to the client, or accept and document a short loss window
- Load path: snapshot + recent edits → send to client
- Also store plain text or JSON for search and previews

**Exit criteria:** restarting the server loses no confirmed edits, and large documents load within your target time.

---

## Phase 5: Identity and permissions (week 6–7)

- Authentication (OAuth/SSO or sessions); require a token on every WebSocket connection
- Per-document access control: owner, editor, commenter, viewer
- **Enforce on the server:** reject write messages from read-only clients, and re-check permissions when they change mid-session (disconnect or downgrade)
- Share links, and inviting people by email

**Why here:** permissions shape the protocol and the storage layer. Adding them after launch is painful and risky.

**Exit criteria:** security tests show a viewer can't make an edit stick, even by sending messages directly.

---

## Phase 6: Presence (week 7–8)

- A short-lived "awareness" channel, separate from the document data
- Remote cursors and selections, with names and colors
- List of who's in the document now, plus idle/away status
- Limit how often updates are sent; clean up when a connection drops

**Exit criteria:** cursors stay in the right place during heavy concurrent editing.

---

## Phase 7: Offline mode and reconnection (week 8–9)

- Save the local document copy in IndexedDB
- Queue edits while offline and merge on reconnect (the CRDT makes this mostly automatic)
- Reconnect with exponential backoff and jitter
- Show connection state in the UI: "Saved", "Offline – changes will sync", "Reconnecting"
- Handle long offline periods, and a client whose copy is older than the server's latest compaction

**Exit criteria:** edit offline for an hour on two devices, reconnect, and both documents converge with nothing lost.

---

## Phase 8: Collaborative undo/redo (week 9–10)

- Undo applies only to *your own* edits (y-UndoManager or equivalent)
- Group keystrokes into sensible undo steps
- Restore the cursor position after undo

**Why this late:** it depends on a stable document model and editor binding. Users notice a broken undo immediately, so test it thoroughly.

---

## Phase 9: Scaling and operations (week 10–12)

- **Route each document to one server node** (consistent hashing on document ID), *or* share edits between nodes with pub/sub (Redis or NATS)
- Unload inactive documents from memory and reload them on demand
- Backpressure (protection against slow clients or overload) and per-document connection limits
- **Observability:** sync latency, message rates, document size, reconnect rates, and divergence detection (compare checksums between clients and server)
- Load testing: thousands of documents, and many editors on a single popular document

**Exit criteria:** you meet target load (for example, 50 editors in one document and 10k concurrent documents) with p99 edit propagation under about 200 ms.

---

## Phase 10: Product features (week 12+, can run in parallel)

Rough priority order:
1. **Version history:** named snapshots, see changes, restore
2. **Comments:** anchored to text ranges that stay attached as text moves (relative positions)
3. Mentions and notifications
4. Export/import (Markdown, DOCX, PDF)
5. Suggestion or track-changes mode (hardest, do last)
6. Search across documents

---

## Phase 11: Hardening before launch

- Security review: XSS through pasted content, oversized or malicious edit messages, token handling
- Chaos testing: kill servers mid-edit, partition the network, drop the database
- Accessibility pass: screen reader support for remote cursors, keyboard navigation
- Backup and restore drill
- Gradual rollout behind feature flags

---

## Dependency summary

```
Decisions → Single-user editor → Convergence harness → Sync server → Persistence
                                                                   ↓
                                                             Auth/Permissions
                                                                   ↓
                             Presence ← → Offline mode ← → Undo/Redo
                                                                   ↓
                                                          Scaling/Ops → Features → Hardening
```

**Critical path:** Phases 0–5. Delays here push back everything else.

**Can run in parallel once Phase 3 is done:**
- Presence UI, as soon as sync works
- Auth/identity service, from the start, alongside the editor work
- Export/import, which only needs the schema
- Monitoring setup, as soon as there's a server

---

## Common mistakes

1. **Writing your own CRDT or OT.** Use a library unless that algorithm *is* your product.
2. **Adding auth late.** It changes the protocol and storage design.
3. **Skipping the fuzz tests.** Divergence bugs then show up in production and are very hard to reproduce.
4. **Unbounded edit logs.** Plan compaction from day one or load times will keep growing.
5. **Treating presence as document data.** Keep it on its own short-lived channel.
6. **Leaving rich-text edge cases until late.** Paste, IME (input methods for languages like Chinese and Japanese) and mobile keyboards deserve dedicated testing early.

**Rough timeline:** about 3 months to a solid v1 with a small team (2–4 engineers), assuming you use an existing CRDT library and editor framework.
