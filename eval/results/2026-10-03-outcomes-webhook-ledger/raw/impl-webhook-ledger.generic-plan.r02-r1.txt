Component Details\n151\t\n152\t**`signature`**\n153\t- Header lookup lowercases the dict keys. A missing header, or two keys that differ only in case, gives a rejection.\n154\t- Split the value on `,`, then on the first `=`. Collect `t` (must match `^\\d+$`; don't use bare `int()`, which accepts `+1`, ` 1` and `1_0`) and every `v1`. Ignore any other scheme.\n155\t- Reject if `abs(clock.now() - int(t)) > 300`. Exactly 300 is allowed.\n156\t- Compute `expected = hmac.new(secret, t_raw.encode() + b\".\" + raw_body, sha256).hexdigest()` and accept if `hmac.compare_digest` matches any `v1`. Use the `t` string **as received**, not a reformatted copy.\n157\t- Pure, with no access to the store.\n158\t\n159\t**`events`**\n160\t- Runs only after the signature has passed.\n161\t- Envelope: `id` is a non-empty str, `type` is a str, `created` is an int, `data` is a dict.\n162\t- For handled types:\n163\t  - `account_id` and `payment_id` are non-empty strings.\n164\t  - `amount` is an `int`, not a `bool` and not a float, and greater than 0.\n165\t  - `currency` matches `^[A-Z]{3}$`. It's required on payments and optional on refunds until A5 is confirmed.\n166\t- Returns `Unhandled(type)` for anything else.\n167\t\n168\t**`accounts`** (the core; no I/O)\n169\t- `apply_payment`:\n170\t  - If `payment:<pid>` already exists with the same `event_id` (and body hash), do nothing.\n171\t  - If it exists with `source=import` and the same amount and currency, do nothing; the outcome is `already_imported`.\n172\t  - Otherwise, if it exists, hold with `duplicate_payment`.\n173\t  - If the record has no currency, set it. If the currency differs, hold with `currency_mismatch`.\n174\t  - Otherwise append `+amount`. If `parked_refunds[pid]` exists, check it (same amount; currency missing or equal). Append `-amount` if it passes, or move it to `held` if not.\n175\t- `apply_refund`:\n176\t  - If `refund:<pid>` exists or `parked_refunds[pid]` exists: with the same `event_id`, do nothing; with a different one, hold with `duplicate_refund`.\n177\t  - If `payment:<pid>` exists: check amount and currency, then append `-amount` or hold.\n178\t  - If the payment is in `held`: hold with `refund_of_held_payment`.\n179\t  - Otherwise park it.\n180\t- Holds are stored in `held[event_id]`, which is idempotent.\n181\t- A negative balance is allowed and never clamped.\n182\t\n183\t**`repository`**\n184\t- Each read returns a deep copy (a JSON round-trip), so callers can't alter an in-memory `MemoryStore` by accident.\n185\t- Concurrency mode, chosen in T1:\n186\t  - **(a) CAS available:** `put_account(rec, expected_version)`. On conflict, re-read and re-apply up to 3 times, then 503.\n187\t  - **(b) No CAS:** a `threading.Lock` per `account_id` and per `event_id`, held across read-modify-write, plus a hard rule of **one Ledger process**.\n188\t- Failure behaviour: `StoreError` propagates to `service`.\n189\t\n190\t**`service`**\n191\t- Maps outcomes to statuses:\n192\t\n193\t| Outcome | Status | `status` field |\n194\t|---|---|---|\n195\t| Signature or timestamp failure | 401 | `unauthorized` (no detail) |\n196\t| Bad JSON or envelope | 400 | |\n197\t| Payload fails checks | 422 | (event stays `pending`) |\n198\t| Same id, different body | 409 | `conflict` |\n199\t| Applied / parked / ignored / held / duplicate | 200 | the outcome |\n200\t| `StoreError` | 503 | |\n201\t| Any other exception | 500 | (logged with traceback) |\n202\t\n203\t- `balance()` and `entries()` let `StoreError` propagate rather than returning a misleading 0.\n204\t\n205\t**Scaling:** not a driver. Mode (b) handles more than 100× today's volume in one process. Move to mode (a) when more than one instance is needed.\n206\t\n207\t## 8. Data Design\n208\t\n209\t| Record | Key | Fields | Writer |\n210\t|---|---|---|---|\n211\t| EventRecord | `event:<event_id>` | `event_id`, `body_sha256`, `raw_body` (UTF-8 text), `type`, `created`, `received_at`, `state` (`pending`\\|`done`), `outcome`, `last_error` | `service` via `repository` |\n212\t| AccountRecord | `account:<account_id>` | `account_id`, `currency` (null until first payment), `version`, `entries[]`, `parked_refunds{payment_id→…}`, `held{event_id→{type, reason, payment_id, amount, currency}}` | `service` via `repository` |\n213\t| Entry (inside AccountRecord) | `key` = `payment:<pid>` \\| `refund:<pid>` | `event_id`, `type`, `amount` (signed), `currency`, `payment_id`, `created`, `applied_at`, `body_sha256`, `source` (`webhook`\\|`import`) | `accounts` |\n214\t| IncidentRecord | `incident:<event_id>:<sha256>` | `event_id`, `original_sha256`, `received_sha256`, `raw_body`, `received_at` | `service` |\n215\t\n216\t- **System of record:**\n217\t  - The AccountRecord is the system of record for balances. `balance = sum(e.amount for e in entries)`, so it can't drift.\n218\t  - EventRecords hold the full raw history. That allows an account to be rebuilt by replaying events in `received_at` order, and lets future handlers backfill event types that were previously ignored.\n219\t- **Consistency:**\n220\t  - All money effects for one event touch exactly one AccountRecord in one put.\n221\t  - No cross-record transaction is needed. The event record's `pending → done` only controls whether work gets replayed, and the replay is idempotent.\n222\t- **\"Oldest first\"** in `entries()` means the order movements were applied to the account (list order). `created` is included so consumers can sort differently if they need to.\n223\t- **Access patterns:** point reads by key only. A scan (for reports and backfill) depends on what T1 finds. Without one, reports in M3 use a key list kept by `repository`.\n224\t- **Size:** about 300 bytes per entry. An account with 1,000 movements is about 300 KB. Revisit if any account goes over 2,000 entries.\n225\t- **Retention:** keep everything for 10 years *(assumption: financial record retention; Finance to confirm in M3)*. Backups come from the managed DB. A test restore plus a rebuild-from-events runs before cutover (M4).\n226\t- **Classification:** account and payment IDs and amounts are internal-confidential financial data, with no card data assumed (A6). The webhook secret is the most sensitive item and is held only in the secret manager and in memory.\n227\t- **Schema evolution:** add fields only, and readers default missing fields. Each record carries `schema: 1`. A breaking change is handled by a lazy upgrade on read, then a backfill tool.\n228\t\n229\t## 9. Key Flows\n230\t\n231\t**F1: Payment, happy path.** Signature passes → JSON parses → `event:evt_1` is absent, so it's inserted as pending → under the `acct_42` lock (or CAS), read the account (absent, so a new record) → `apply_payment` sets EUR and appends `payment:pay_9xk +2500` → put the account → mark the event done (`applied`) → 200. `balance(\"acct_42\") == 2500`.\n232\t\n233\t**F2: Refund before payment.**\n234\t1. The refund `evt_2` arrives. `payment:pay_9xk` isn't in `acct_42`, so it goes into `parked_refunds[pay_9xk]` → 200 `parked`. Balance is 0 and there are no entries.\n235\t2. The payment `evt_1` arrives. It appends +2500, finds the parked refund, checks amount and currency, appends `refund:pay_9xk -2500` (`event_id=evt_2`), and removes the parked refund, all in **one put**.\n236\t3. Result: balance 0, two entries, and no window where the payment shows without its refund.\n237\t\n238\t**F3: Failure path, `StoreError` partway through (the case the design exists for).** Writes per delivery are W1 (event pending), W2 (account), W3 (event done).\n239\t\n240\t| Fails at | State left behind | PayCo retry does | Final |\n241\t|---|---|---|---|\n242\t| W1 (did or didn't commit) | Nothing, or a pending event | Insert, or find pending with the same hash → continue | Correct |\n243\t| W2 (did or didn't commit) | Account unchanged, or already updated | `apply_*` sees the movement key with the same `event_id` → no change; otherwise applies | Correct, applied once |\n244\t| W3 | Account updated, event pending | W2 does nothing, W3 succeeds → 200 | Correct |\n245\t\n246\tEach case returns 503 to PayCo. The only visible effect is that the balance may already include the movement before PayCo hears 200, which is the correct end state anyway.\n247\t\n248\t**F4: Same id, different body.** Signature passes (the sender has the secret, or PayCo has a bug) → `event:evt_1` exists and its `body_sha256` differs → write IncidentRecord (best effort) → log at CRITICAL → 409. The account and the original EventRecord aren't touched. PayCo keeps retrying, which keeps the alert firing until someone acts. An *unsigned* conflicting body gets 401 at step 1 and never reaches the incident logic, so attackers can't flood the incident queue.\n249\t\n250\t## 10. Cross-Cutting Concerns\n264\t\n265\t**Security** (M1 unless noted). Threats and mitigations:\n266\t\n267\t1. **Forged deliveries.** HMAC-SHA256 with `compare_digest`, checked before parsing or touching the store.\n268\t2. **Replay.** The 300 s window, plus deduplication by event id inside the window.\n269\t3. **Same-id tampering or secret compromise.** 409, incident record, page. The runbook treats it as possible secret exposure and rotates the secret.\n270\t4. **Secret leakage.** The secret is injected from the secret manager. It and the signature header are never logged. Tests assert this.\n271\t5. **Resource abuse.** 64 KB body limit and edge rate limit in the HTTP layer (A7). Unsigned requests cost one HMAC.\n272\t\n273\tSecret rotation (M3): during PayCo's dual-signing window (Q2) we accept any matching `v1`. Supporting two secrets on our side is deferred, because the interface takes a single `secret`.\n274\t\n275\t**Reliability** (M1–M2). Idempotency is defined in D1–D3. There is no retry inside a request; PayCo's retries do that job. CAS conflicts get 3 attempts. The health check (provided by the HTTP layer) should do one store read. Recovery is by managed DB restore, then rebuilding accounts from EventRecords (`tools/rebuild.py`, M3).\n276\t\n277\t**Observability** (M1 logging, M3 alerts):\n278\t- One JSON log line per delivery with `event_id`, `type`, `account_id`, `outcome`, `status`, `latency_ms`, and the first 12 characters of `body_sha256`.\n279\t- Counters by outcome.\n280\t- Alerts, through the external monitoring stack:\n281\t\n282\t| Condition | Action |\n283\t|---|---|\n284\t| Any 409 | Page |\n285\t| 401 rate > 5 in 10 min | Ticket (clock skew, secret misconfiguration, or probing) |\n286\t| 503 rate > 2% over 15 min | Page in business hours |\n287\t| Any hold | Finance ticket |\n288\t| Parked refund older than 72 h | Finance ticket (the payment is probably pre-cutover or went to a different account) |\n289\t\n290\t**Performance:** about 3 store operations per delivery and well under 250 ms p95. The M2 test harness includes 10k deliveries in one run as a smoke load test. Data Design\n\n| Record | Key | Fields | Writer |\n|---|---|---|---|\n| EventRecord | `event:<event_id>` | `event_id`, `body_sha256`, `raw_body` (UTF-8 text), `type`, `created`, `received_at`, `state` (`pending`\\|`done`), `outcome`, `last_error` | `service` via `repository` |\n| AccountRecord | `account:<account_id>` | `account_id`, `currency` (null until first payment), `version`, `entries[]`, `parked_refunds{payment_id→…}`, `held{event_id→{type, reason, payment_id, amount, currency}}` | `service` via `repository` |\n| Entry (inside AccountRecord) | `key` = `payment:<pid>` \\| `refund:<pid>` | `event_id`, `type`, `amount` (signed), `currency`, `payment_id`, `created`, `applied_at`, `body_sha256`, `source` (`webhook`\\|`import`) | `accounts` |\n| IncidentRecord | `incident:<event_id>:<sha256>` | `event_id`, `original_sha256`, `received_sha256`, `raw_body`, `received_at` | `service` |\n\n- **System of record:**\n  - The AccountRecord is the system of record for balances. `balance = sum(e.amount for e in entries)`, so it can't drift.\n  - EventRecords hold the full raw history. That allows an account to be rebuilt by replaying events in `received_at` order, and lets future handlers backfill event types that were previously ignored.\n- **Consistency:**\n  - All money effects for one event touch exactly one AccountRecord in one put.\n  - No cross-record transaction is needed. The event record's `pending → done` only controls whether work gets replayed, and the replay is idempotent.\n- **\"Oldest first\"** in `entries()` means the order movements were applied to the account (list order). `created` is included so consumers can sort differently if they need to.\n- **Access patterns:** point reads by key only. A scan (for reports and backfill) depends on what T1 finds. Without one, reports in M3 use a key list kept by `repository`.\n- **Size:** about 300 bytes per entry. An account with 1,000 movements is about 300 KB. Revisit if any account goes over 2,000 entries.\n- **Retention:** keep everything for 10 years *(assumption: financial record retention; Finance to confirm in M3)*. Backups come from the managed DB. A test restore plus a rebuild-from-events runs before cutover (M4).\n- **Classification:** account and payment IDs and amounts are internal-confidential financial data, with no card data assumed (A6). The webhook secret is the most sensitive item and is held only in the secret manager and in memory.\n- **Schema evolution:** add fields only, and readers default missing fields. Each record carries `schema: 1`. A breaking change is handled by a lazy upgrade on read, then a backfill tool.\n\n## 9. Key Flows\n\n**F1: Payment, happy path.** Signature passes → JSON parses → `event:evt_1` is absent, so it's inserted as pending → under the `acct_42` lock (or CAS), read the account (absent, so a new record) → `apply_payment` sets EUR and appends `payment:pay_9xk +2500` → put the account → mark the event done (`applied`) → 200. `balance(\"acct_42\") == 2500`.\n\n**F2: Refund before payment.**\n1. The refund `evt_2` arrives. `payment:pay_9xk` isn't in `acct_42`, so it goes into `parked_refunds[pay_9xk]` → 200 `parked`. Balance is 0 and there are no entries.\n2. The payment `evt_1` arrives. It appends +2500, finds the parked refund, checks amount and currency, appends `refund:pay_9xk -2500` (`event_id=evt_2`), and removes the parked refund, all in **one put**.\n3. Result: balance 0, two entries, and no window where the payment shows without its refund.\n\n**F3: Failure path, `StoreError` partway through (the case the design exists for).** Writes per delivery are W1 (event pending), W2 (account), W3 (event done).\n\n| Fails at | State left behind | PayCo retry does | Final |\n|---|---|---|---|\n| W1 (did or didn't commit) | Nothing, or a pending event | Insert, or find pending with the same hash → continue | Correct |\n| W2 (did or didn't commit) | Account unchanged, or already updated | `apply_*` sees the movement key with the same `event_id` → no change; otherwise applies | Correct, applied once |\n| W3 | Account updated, event pending | W2 does nothing, W3 succeeds → 200 | Correct |\n\nEach case returns 503 to PayCo. The only visible effect is that the balance may already include the movement before PayCo hears 200, which is the correct end state anyway.\n\n**F4: Same id, different body.** Signature passes (the sender has the secret, or PayCo has a bug) → `event:evt_1` exists and its `body_sha256` differs → write IncidentRecord (best effort) → log at CRITICAL → 409. The account and the original EventRecord aren't touched. PayCo keeps retrying, which keeps the alert firing until someone acts. An *unsigned* conflicting body gets 401 at step 1 and never reaches the incident logic, so attackers can't flood the incident queue.\n\n## 10.
