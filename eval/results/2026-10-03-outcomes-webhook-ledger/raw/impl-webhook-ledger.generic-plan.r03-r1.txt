Component Details\n118\t\n119\t**Signature verifier.**\n120\t- Look up the header case-insensitively. If two keys differ only in case (e.g. `PayCo-Signature` and `payco-signature`), return 400.\n121\t- Split the header value on `,`, then each part on the first `=`. Require exactly one `t` matching `[0-9]{1,12}`. Don't use bare `int()`, which accepts `+1`, `1_000` and Unicode digits.\n122\t- Accept one or more `v1` values, each matching `[0-9a-f]{64}`. Checking the format first also avoids a `TypeError` that `compare_digest` raises on non-ASCII strings.\n123\t- Expected value: `HMAC-SHA256(secret, t_str.encode() + b\".\" + raw_body)`, using the **original `t` string**. Compare with `hmac.compare_digest` against each `v1`.\n124\t- Check the signature first, then `abs(clock.now() - int(t)) > 300` → reject. This is inclusive at exactly 300 s.\n125\t- Out of scope: JSON, and replay deduplication. A replay inside the 300 s window is harmless because of event-`id` idempotency.\n126\t\n127\t**Event parser.**\n128\t- `json.loads` with an `object_pairs_hook` that rejects duplicate keys, and a `parse_constant` that rejects NaN and Infinity. The top level must be an object, and `id` a non-empty string.\n129\t- For known types, check `data`: `account_id` and `payment_id` non-empty strings; `amount` with `type(x) is int` (Python treats `True` as an `int`) and `> 0`; `currency` matching `[A-Z]{3}`; `created` an int.\n130\t- Unknown types get only the envelope check.\n131\t\n132\t**Ledger rules (pure).** This is where the money logic lives, so it gets the most tests.\n133\t- `payment.succeeded`:\n134\t  - Event already in `applied_event_ids` → DUPLICATE.\n135\t  - `payment_id` already in `payments` from a different event → REJECT `duplicate_payment`.\n136\t  - Currency set and different from the event's → REJECT `currency_mismatch`.\n137\t  - Otherwise: set the currency if unset, add the entry `+amount`, record the payment.\n138\t  - If `pending_refunds[payment_id]` exists and matches on amount and currency, settle it in the same state: add a `-amount` entry and mark the payment refunded. If it doesn't match, keep it parked with `mismatch` set so the parked-refund alert fires.\n139\t- `refund.succeeded`:\n140\t  - Already applied, or already parked with the same event → DUPLICATE or PENDING.\n141\t  - Payment unknown → PARK, keyed by `payment_id`. If a different event is already parked for that payment → REJECT `double_refund`.\n142\t  - Payment already refunded → REJECT `double_refund`.\n143\t  - Amount or currency differs from the payment → REJECT `refund_mismatch`.\n144\t  - Otherwise add the entry `-amount`.\n145\t- A refund never fails for lack of balance. Negative balances are allowed and recorded, because refusing a refund would break reconciliation.\n146\t\n147\t**Repository.**\n148\t- `put_event_if_absent(id, record)` returns the record already stored, if any.\n149\t- `update_account(id, fn)`: load (document and version) → `fn` → compare-and-set. On a version conflict, retry up to 5 times, then raise `Contention`, which becomes 503.\n150\t- `StoreError` is never caught here. It goes up to the service.\n151\t\n152\t**`handle()` in outline**\n153\t\n154\t```\n155\theaders → signature.verify            → 400/401 on failure\n156\traw → events.parse_envelope           → 400 on failure\n157\tdigest = sha256(raw)\n158\ttry:\n159\t  rec = repo.put_event_if_absent(id, {digest, type, raw_body, first_seen_at})\n160\t  if rec.digest != digest: log INCIDENT (incl. canonical-JSON-equal flag) → 409\n161\t  if type not in HANDLERS: → 200 ignored\n162\t  ev = events.validate(envelope)      → on error: repo.put_anomaly(id, …) → 422\n163\t  outcome = repo.update_account(ev.account_id, λs: rules.apply(s, ev, now))\n164\t  REJECTED → repo.put_anomaly(id, …) → 422 ; APPLIED/DUPLICATE → 200 ; PENDING → 202\n165\texcept StoreError, Contention: → 503\n166\texcept Exception: log with traceback → 500\n167\t```\n168\t\n169\t**Status code policy.** Any 2xx means the effect is durable.\n170\t\n171\t| Situation | Status | `body.status` |\n172\t|---|---|---|\n173\t| Missing, duplicated or malformed signature header; malformed JSON or `id` | 400 | `bad_request` |\n174\t| Bad signature, or `t` more than 300 s off | 401 | `unauthorized` (no detail in the response) |\n175\t| Same `id`, different body | 409 | `conflict` |\n176\t| Known type that breaks a rule or fails validation | 422 | `rejected` + `reason` |\n177\t| Applied / duplicate / unknown type | 200 | `applied` / `duplicate` / `ignored` |\n178\t| Refund parked | 202 | `pending` |\n179\t| `StoreError`, compare-and-set contention | 503 | `retry` |\n180\t| Bug | 500 | `error` |\n181\t\n182\t**Failure and recovery.** Every store write is either idempotent (event record, anomaly) or conditional (account compare-and-set). Every `StoreError` returns 503, and PayCo retries. A write that raised but actually committed is caught on redelivery by `applied_event_ids`. Reads (`balance`, `entries`) let `StoreError` propagate, because returning 0 would be a wrong answer. Scaling: a compare-and-set per account means contention only on one hot account, which is negligible at this volume.\n183\t\n184\t## 8. Data Design\n185\t\n186\t| Key | Contents | Written by | Write rule |\n187\t|---|---|---|---|\n188\t| `event:{id}` | `body_sha256`, `type`, `raw_body`, `first_seen_at` | repository (via service) | put-if-absent; never updated |\n189\t| `account:{account_id}` | see below | repository (via rules) | compare-and-set on `version`; **the only write that moves money** |\n190\t| `anomaly:{event_id}` | reason, `raw_body`, `seen_at`, count | repository | overwrite with the same content (idempotent) |\n191\t\n192\t```\n193\taccount:{id} = {\n194\t  version, currency | null, balance,\n195\t  entries: [{seq, event_id, type, amount(signed), currency, payment_id, created, applied_at}],\n196\t  applied_event_ids: {...},                       # dedup lives with the money\n197\t  payments: {payment_id: {event_id, amount, currency, refunded_by | null, source}},\n198\t  pending_refunds: {payment_id: {event_id, amount, currency, created, received_at, mismatch}}\n199\t}\n200\t```\n201\t\n202\t- **System of record:** the account document for balances and entries; `event:*` for \"what PayCo sent us\".\n203\t- **Consistency:** the invariants `balance == sum(entries.amount)`, at most one refund per payment, and one currency per account all hold because they change in one atomic write. `payments` and `pending_refunds` exist from M1, so adding refunds in M2 needs no data migration.\n204\t- **Access patterns:** point lookups only; no scans on the hot path. The parked-refund alert and the reconciliation tool need to list `account:*`. If the store can't list keys, keep an `accounts_index` document (T1 decides).\n205\t- **Retention and backup:** keep everything (A9). The managed DB's backups give the restore point. **After a restore**, events that were acknowledged after the backup are gone, and PayCo won't resend them. Recovery is to run `tools/reconcile.py` against PayCo's export and replay the missing events. Write this into the runbook in M3.\n206\t- **Classification:** account IDs, amounts, currency. No card data. The secret is never stored or logged. Logs carry event IDs and outcomes, not bodies.\n207\t- **Schema changes:** the account document carries `schema: 1`. Readers accept N and N−1, and documents are upgraded when next written. Revisit splitting entries into separate records if any account passes about 10k entries or 1 MB.\n208\t\n209\t## 9. Key Flows\n210\t\n211\t**F1: Payment, normal path.** Signature OK → event record created → account compare-and-set adds +2500 and fixes the currency to EUR → 200 `applied`.\n212\t\n213\t**F2: Partial write, then redelivery (failure path).**\n214\t1. Event record written. Account compare-and-set raises `StoreError` → 503. Two cases: (a) it didn't commit; (b) it committed, but the client raised anyway.\n215\t2. PayCo retries with a fresh `t` (A2). The event record already exists with the same digest, so we continue.\n216\t3. Case (a): compare-and-set applies → 200. Case (b): `applied_event_ids` contains the ID → 200 `duplicate`. The balance is right either way.\n217\t\n218\tContrast: if we had written a \"processed\" flag first, case (a) would leave the event marked done and the money never applied.\n219\t\n220\t**F3: Refund before payment, including a race.**\n221\t1. Refund `evt_R` for `pay_9` arrives; the account has no `pay_9` → parked → 202.\n222\t2. Payment `evt_P` arrives. In the same compare-and-set it applies +2500, finds `pending_refunds[pay_9]`, checks amount and currency, and applies −2500. Entries read: payment, then refund.\n223\t3. If both arrive at once, both compare-and-set on `account:acct_42`. One loses and retries against the new state, so neither can miss the other.\n224\t\n225\t**F4: Same `id`, different body.** Signature is valid; the event record exists with a different digest → 409, log `INCIDENT`, page someone. The account isn't read or written. Every later delivery of that body gets 409 again.\n226\t\n227\t## 10. Component Details\n\n**Signature verifier.**\n- Look up the header case-insensitively. If two keys differ only in case (e.g. `PayCo-Signature` and `payco-signature`), return 400.\n- Split the header value on `,`, then each part on the first `=`. Require exactly one `t` matching `[0-9]{1,12}`. Don't use bare `int()`, which accepts `+1`, `1_000` and Unicode digits.\n- Accept one or more `v1` values, each matching `[0-9a-f]{64}`. Checking the format first also avoids a `TypeError` that `compare_digest` raises on non-ASCII strings.\n- Expected value: `HMAC-SHA256(secret, t_str.encode() + b\".\" + raw_body)`, using the **original `t` string**. Compare with `hmac.compare_digest` against each `v1`.\n- Check the signature first, then `abs(clock.now() - int(t)) > 300` → reject. This is inclusive at exactly 300 s.\n- Out of scope: JSON, and replay deduplication. A replay inside the 300 s window is harmless because of event-`id` idempotency.\n\n**Event parser.**\n- `json.loads` with an `object_pairs_hook` that rejects duplicate keys, and a `parse_constant` that rejects NaN and Infinity. The top level must be an object, and `id` a non-empty string.\n- For known types, check `data`: `account_id` and `payment_id` non-empty strings; `amount` with `type(x) is int` (Python treats `True` as an `int`) and `> 0`; `currency` matching `[A-Z]{3}`; `created` an int.\n- Unknown types get only the envelope check.\n\n**Ledger rules (pure).** This is where the money logic lives, so it gets the most tests.\n- `payment.succeeded`:\n  - Event already in `applied_event_ids` → DUPLICATE.\n  - `payment_id` already in `payments` from a different event → REJECT `duplicate_payment`.\n  - Currency set and different from the event's → REJECT `currency_mismatch`.\n  - Otherwise: set the currency if unset, add the entry `+amount`, record the payment.\n  - If `pending_refunds[payment_id]` exists and matches on amount and currency, settle it in the same state: add a `-amount` entry and mark the payment refunded.
