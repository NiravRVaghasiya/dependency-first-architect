Architecture Overview\n106\t\n107\t```mermaid\n108\tflowchart LR\n109\t  PayCo[PayCo webhooks] -->|HTTPS POST, raw bytes + headers| HTTP[HTTP layer - outside this codebase]\n110\t  subgraph Ledger process [Ledger process - trust boundary: only signed bodies pass SignatureVerifier]\n111\t    HTTP --> SVC[LedgerService.handle]\n112\t    SVC --> SIG[SignatureVerifier]\n113\t    SVC --> EVT[EventParser]\n114\t    SVC --> REPO[EventRepository]\n115\t    Q[LedgerService.balance / entries] --> REPO\n116\t    Q --> PROJ[Projection - pure function]\n117\t  end\n118\t  REPO --> DB[(Managed DB via ledgerkit store)]\n119\t  Tools[tools/: reconcile, import_history, repair, show_account] --> REPO\n120\t  Tools --> PROJ\n121\t  Finance[PayCo CSV export / monthly statement] --> Tools\n122\t```\n123\t\n124\t`handle()` works in this order:\n125\t1. Component Details\n144\t\n145\t### 7.1 SignatureVerifier\n146\t- **Steps:**\n147\t  1. Split the header on `,` into `k=v` pairs. Require exactly one `t` made of digits only.\n148\t  2. Collect every `v1` value. More than one is allowed, which supports secret rotation. Ignore other schemes.\n149\t  3. Compute `HMAC-SHA256(secret, t_str.encode() + b\".\" + raw_body)`, using the exact `t` string from the header.\n150\t  4. Compare with `hmac.compare_digest` against each `v1`, after lowercasing it. Try each configured secret.\n151\t  5. Reject if `abs(now - int(t)) > 300`. Exactly 300 s is accepted.\n152\t- **Out of scope:** it never looks inside the body.\n153\t- **Results:** `missing_signature`, `malformed_signature`, `bad_signature`, `stale_timestamp`. All of these map to `401`.\n154\t\n155\t### 7.2 EventParser\n156\t- **Parsing:** `json.loads` with `parse_constant` set to reject `NaN` and `Infinity`. The top level must be an object.\n157\t- **Envelope:** `id` is a non-empty string, `type` is a non-empty string, `created` is an integer, and `data` is an object.\n158\t- **Typed checks for payment and refund:**\n159\t  - `account_id` and `payment_id` are non-empty strings.\n160\t  - `amount` is an `int`, not a `bool`, and greater than 0.\n161\t  - `currency` matches `^[A-Z]{3}$`.\n162\t- **Unknown types:** only the envelope is validated.\n163\t- **`canonical_digest`:** `sha256(json.dumps(obj, sort_keys=True, separators=(\",\",\":\")).encode())`. Two bodies are \"the same body\" if their digests are equal (D4).\n164\t\n165\t### 7.3 EventRepository: the only writer\n166\t- **Store primitives required:**\n167\t  - `get`\n168\t  - `put`\n169\t  - `put_if_absent`. If the store doesn't provide it, emulate it as get-then-put under a process lock and accept the single-worker limit (D8).\n170\t  - Listing by account. If the store has no prefix scan, keep an index key per account, updated under the same lock.\n171\t- **Internal retry:** each store call is retried up to 3 times on `StoreError`, with 50 ms then 200 ms backoff. This is safe because every write is idempotent. After the third failure it raises to the service.\n172\t- **Methods:**\n173\t  - `insert_event(record)`: returns the record that is now stored, which may be an earlier one if another write got there first.\n174\t  - `ensure_account_entry(record)`: writes `acct:{account_id}:evt:{event_id}` with fields taken from the record. Writing it again with the same value does nothing. It is skipped for unhandled types.\n175\t\n176\t### 7.4 Projection: the business rules, as a pure function\n177\tInput: an account's handled entries. Output: `AccountView(entries, balance, pending, held)`. The result depends only on which events are present, not on the order they arrived. That is why duplicates and reordering can't change balances.\n178\t\n179\t1. Sort by `(created, event_id)`.\n180\t2. **Account currency** is the currency of the first payment in that order.\n181\t3. **For each payment:**\n182\t   - If its currency differs from the account currency: held, `currency_mismatch`.\n183\t   - If the `payment_id` was already credited with the same amount and currency: merged and not counted again. This covers PayCo duplicates under a new id and overlaps with imported history.\n184\t   - If the `payment_id` was already credited with a different amount or currency: held, `payment_id_conflict`.\n185\t   - Otherwise: an entry of `+amount`.\n186\t4. **For each refund:**\n187\t   - If no credited payment with that `payment_id` exists in this account: **pending**.\n188\t   - If the amount or currency differs from the payment's: held, `refund_mismatch`.\n189\t   - If this payment was already refunded: merged if identical, otherwise held.\n190\t   - Otherwise: an entry of `−amount`, sorted at `max(refund.created, payment.created)`.\n191\t5. `balance = sum(entry.amount)`, all in integer arithmetic.\n192\t\n193\tAn account we have never seen gives `balance = 0` and `entries = []`.\n194\t\n195\t**Accepted edge case:** the account currency is decided by `created` order. If two payments in different currencies arrive within PayCo's 72 h window in reverse order, the currency could flip. Both cases already raise a `currency_mismatch` alert for a human to resolve.\n196\t\n197\t### 7.5 LedgerService.handle\n198\t\n199\t```python\n200\th = {k.lower(): v for k, v in headers.items()}\n201\tif len(raw_body) > 64 * 1024: return 413, {\"error\": \"body_too_large\"}\n202\tr = verify(h.get(\"payco-signature\"), raw_body, secrets, clock.now())\n203\tif not r.ok: log(r.reason); return 401, {\"error\": r.reason}\n204\ttry: env = parse_envelope(raw_body)\n205\texcept Invalid as e: return 400, {\"error\": \"invalid_payload\", \"detail\": str(e)}\n206\tdigest = canonical_digest(env.obj)\n207\ttry:\n208\t    existing = repo.get_event(env.id)\n209\t    if existing:\n210\t        if existing.digest != digest: return incident(env, existing)      # 409\n211\t        repo.ensure_account_entry(existing)                               # repair partial earlier attempt\n212\t        return 200, {\"status\": \"duplicate\", \"event_id\": env.id}\n213\t    try: ev = validate(env)\n214\t    except Invalid as e: return 400, {\"error\": \"invalid_payload\", \"detail\": str(e)}\n215\t    stored = repo.insert_event(record(ev, digest, raw_body, clock.now()))\n216\t    if stored.digest != digest: return incident(env, stored)              # lost a race to a conflicting body\n217\t    repo.ensure_account_entry(stored)\n218\texcept StoreError:\n219\t    return 503, {\"error\": \"store_unavailable\"}\n220\treturn 200, {\"status\": outcome(ev), \"event_id\": env.id}\n221\t# outcome() is best-effort: applied | pending | held | ignored; it falls back to \"accepted\" if the read fails.\n222\t```\n223\t\n224\t- Unexpected exceptions are caught and return `500`, so PayCo retries.\n225\t- `incident()` logs at ERROR with both digests and a `security_incident` flag. It then writes `incident:{id}:{digest}` on a best-effort basis and returns `409 {\"error\": \"event_id_conflict\"}`. Nothing is written for the account.\n226\t- `balance()` and `entries()` call `project(repo.account_entries(id))`. They raise `StoreError` to the caller after the internal retries are used up.\n227\t- **Additions to the interface** (they don't break the brief's contract): `pending(account_id)` and `held(account_id)`, for ops.\n228\t\n229\t**Failure and recovery:** every step before a 2xx either writes nothing or is idempotent, and a duplicate delivery re-runs the idempotent steps. As long as PayCo keeps retrying, a partial failure always completes. `tools/repair.py` covers the last gap: it finds `evt:*` records without an `acct:*` entry.\n230\t\n231\t**Scaling:** fine on one worker up to at least 10 req/s. Running several workers needs a real `put_if_absent` (D8).\n232\t\n233\t## 8. Data Design\n234\t\n235\t| Record | Key | Fields | Written by | Mutability |\n236\t|---|---|---|---|---|\n237\t| EventRecord | `evt:{event_id}` | `event_id`, `type`, `digest`, `raw_body` (UTF-8 text), `account_id?`, `created`, `received_at`, `schema_version=1` | `EventRepository.insert_event` | Write-once |\n238\t| AccountEntry | `acct:{account_id}:evt:{event_id}` | `event_id`, `type`, `payment_id`, `amount` (unsigned, as received), `currency`, `created`, `schema_version` | `ensure_account_entry` | Write-once (identical rewrites allowed) |\n239\t| Incident | `incident:{event_id}:{digest}` | `received_at`, `existing_digest`, `raw_body` | `incident()` | Append-only, best-effort |\n240\t\n241\t- **System of record:** PayCo is the source of truth for money movements. Ledger's event log is our copy of it, and it can be rebuilt from PayCo's export with `tools/import_history.py`. Balances and entries are derived data and are never stored.\n242\t- **Consistency:**\n243\t  - Atomicity is only needed for a single-key write.\n244\t  - `put_if_absent` on `evt:` is the one conditional write, and it prevents conflicting bodies from racing each other.\n245\t  - No multi-key transaction is needed. If S1 finds one, we use it for the two writes, but correctness doesn't depend on it.\n246\t- **Access patterns:**\n247\t  - Get by event id (dedup).\n248\t  - List by account prefix (`balance` and `entries`).\n249\t  - Full scan for reconciliation and backfill.\n250\t  - At about 3,000 events a day, the store grows by roughly 6 MB a day, or 2 GB a year. No partitioning is needed.\n251\t- **Retention and backup:**\n252\t  - Keep the event log for 10 years (A9).\n253\t  - Use the managed DB's backups. Restore is tested once in M3.\n254\t  - The fallback for total loss is to re-import from PayCo's export.\n255\t- **Classification:** account ids, payment ids, and amounts are confidential financial data. Raw bodies are stored for audit and backfill. If S2 shows that PayCo bodies carry personal data, restrict read access to the store and stop logging bodies; we never log them anyway.\n256\t- **Schema evolution:**\n257\t  - Each record carries a `schema_version`. Changes are additive fields only.\n258\t  - New event types are added in three steps: a validator in `events.py`, a rule in `projection.py`, and a backfill. Because `raw_body` is stored, the backfill re-reads the existing `evt:` records of that type and creates `acct:` entries.\n259\t  - Any change to the projection is gated by `tools/reconcile.py --diff-projection`. It recomputes every balance with the old and the new code and lists the differences for Finance to approve.\n260\t\n261\t## 9. Key Flows\n262\t\n263\t**F1: Payment, happy path.**\n264\t1. PayCo POSTs the event. The signature is valid and `t` is within 300 s.\n265\t2. The envelope parses, and `get_event` finds nothing.\n266\t3. Typed validation passes.\n267\t4. `insert_event` and then `ensure_account_entry` succeed.\n268\t5. The service returns `200 {\"status\": \"applied\"}`. `balance(\"acct_42\")` now returns `+2500`.\n269\t\n270\t**F2: Refund before its payment.**\n271\t1. The `refund.succeeded` for `pay_9xk` is stored and indexed. The projection finds no credited `pay_9xk`, so the refund is pending. The service returns `200 {\"status\": \"pending\"}` and the balance is unchanged.\n272\t2. Later the `payment.succeeded` for `pay_9xk` arrives and is stored. The projection now pairs the two: `+2500` then `−2500`, giving a balance of 0.\n273\t3. If the payment never arrives (for example, a payment from before go-live that wasn't imported), the alert for a refund pending more than 24 h fires. The runbook says: import the missing payment from the PayCo export.\n274\t\n275\t**F3: Write fails partway through, then PayCo retries** (the main failure path).\n276\t1. `insert_event` succeeds. `ensure_account_entry` raises `StoreError` 3 times.\n277\t2. The service returns `503`. The balance doesn't yet include the event, and nothing has been counted twice.\n278\t3. PayCo retries a few minutes later, with a fresh `t` (A3).\n279\t4. `get_event` finds the record, and the digest is equal. `ensure_account_entry` succeeds and the service returns `200 duplicate`. The event is now applied exactly once.\n280\t5. A variant: `insert_event` raised but actually wrote the record. The same steps apply, because the retry sees the record.\n281\t\n282\t**F4: Same id, different body.**\n283\t1. The signature is valid and `get_event` finds `evt_1Nq3xKp`, but the digest differs.\n284\t2. The service logs a `security_incident`, writes an `incident:` record, and returns `409`. No account entry is written.\n285\t3. PayCo may retry for up to 72 h. Each retry gets `409` again, and the alert deduplicates on event id.\n286\t4. Because the body was correctly signed, the cause is either a PayCo bug or a leaked secret. The runbook starts with rotating the secret.\n287\t\n288\t**F5: Unknown type** (`dispute.created`). The event record is stored, no account entry is written, and the service returns `200 {\"status\": \"ignored\"}`. It is available for backfill later.\n289\t\n290\t## 10. They raise `StoreError` to the caller after the internal retries are used up.\n- **Additions to the interface** (they don't break the brief's contract): `pending(account_id)` and `held(account_id)`, for ops.\n\n**Failure and recovery:** every step before a 2xx either writes nothing or is idempotent, and a duplicate delivery re-runs the idempotent steps. As long as PayCo keeps retrying, a partial failure always completes. `tools/repair.py` covers the last gap: it finds `evt:*` records without an `acct:*` entry.\n\n**Scaling:** fine on one worker up to at least 10 req/s. Running several workers needs a real `put_if_absent` (D8).\n\n## 8. Data Design\n\n| Record | Key | Fields | Written by | Mutability |\n|---|---|---|---|---|\n| EventRecord | `evt:{event_id}` | `event_id`, `type`, `digest`, `raw_body` (UTF-8 text), `account_id?`, `created`, `received_at`, `schema_version=1` | `EventRepository.insert_event` | Write-once |\n| AccountEntry | `acct:{account_id}:evt:{event_id}` | `event_id`, `type`, `payment_id`, `amount` (unsigned, as received), `currency`, `created`, `schema_version` | `ensure_account_entry` | Write-once (identical rewrites allowed) |\n| Incident | `incident:{event_id}:{digest}` | `received_at`, `existing_digest`, `raw_body` | `incident()` | Append-only, best-effort |\n\n- **System of record:** PayCo is the source of truth for money movements. Ledger's event log is our copy of it, and it can be rebuilt from PayCo's export with `tools/import_history.py`. Balances and entries are derived data and are never stored.\n- **Consistency:**\n  - Atomicity is only needed for a single-key write.\n  - `put_if_absent` on `evt:` is the one conditional write, and it prevents conflicting bodies from racing each other.\n  - No multi-key transaction is needed. If S1 finds one, we use it for the two writes, but correctness doesn't depend on it.\n- **Access patterns:**\n  - Get by event id (dedup).\n  - List by account prefix (`balance` and `entries`).\n  - Full scan for reconciliation and backfill.\n  - At about 3,000 events a day, the store grows by roughly 6 MB a day, or 2 GB a year. No partitioning is needed.\n- **Retention and backup:**\n  - Keep the event log for 10 years (A9).\n  - Use the managed DB's backups. Restore is tested once in M3.\n  - The fallback for total loss is to re-import from PayCo's export.\n- **Classification:** account ids, payment ids, and amounts are confidential financial data. Raw bodies are stored for audit and backfill. If S2 shows that PayCo bodies carry personal data, restrict read access to the store and stop logging bodies; we never log them anyway.\n- **Schema evolution:**\n  - Each record carries a `schema_version`. Changes are additive fields only.\n  - New event types are added in three steps: a validator in `events.py`, a rule in `projection.py`, and a backfill. Because `raw_body` is stored, the backfill re-reads the existing `evt:` records of that type and creates `acct:` entries.\n  - Any change to the projection is gated by `tools/reconcile.py --diff-projection`. It recomputes every balance with the old and the new code and lists the differences for Finance to approve.\n\n## 9. Key Flows\n\n**F1: Payment, happy path.**\n1. PayCo POSTs the event. The signature is valid and `t` is within 300 s.\n2. The envelope parses, and `get_event` finds nothing.\n3. Typed validation passes.\n4. `insert_event` and then `ensure_account_entry` succeed.\n5. The service returns `200 {\"status\": \"applied\"}`. `balance(\"acct_42\")` now returns `+2500`.\n\n**F2: Refund before its payment.**\n1. The `refund.succeeded` for `pay_9xk` is stored and indexed. The projection finds no credited `pay_9xk`, so the refund is pending. The service returns `200 {\"status\": \"pending\"}` and the balance is unchanged.\n2. Later the `payment.succeeded` for `pay_9xk` arrives and is stored. The projection now pairs the two: `+2500` then `−2500`, giving a balance of 0.\n3. If the payment never arrives (for example, a payment from before go-live that wasn't imported), the alert for a refund pending more than 24 h fires. The runbook says: import the missing payment from the PayCo export.\n\n**F3: Write fails partway through, then PayCo retries** (the main failure path).\n1. `insert_event` succeeds. `ensure_account_entry` raises `StoreError` 3 times.\n2. The service returns `503`. The balance doesn't yet include the event, and nothing has been counted twice.\n3. PayCo retries a few minutes later, with a fresh `t` (A3).\n4. `get_event` finds the record, and the digest is equal. `ensure_account_entry` succeeds and the service returns `200 duplicate`. The event is now applied exactly once.\n5. A variant: `insert_event` raised but actually wrote the record. The same steps apply, because the retry sees the record.\n\n**F4: Same id, different body.**\n1. The signature is valid and `get_event` finds `evt_1Nq3xKp`, but the digest differs.\n2. The service logs a `security_incident`, writes an `incident:` record, and returns `409`. No account entry is written.\n3. PayCo may retry for up to 72 h. Each retry gets `409` again, and the alert deduplicates on event id.\n4. Because the body was correctly signed, the cause is either a PayCo bug or a leaked secret. The runbook starts with rotating the secret.\n\n**F5: Unknown type** (`dispute.created`). The event record is stored, no account entry is written, and the service returns `200 {\"status\": \"ignored\"}`. It is available for backfill later.\n\n## 10.
