# Sequencing a CI/CD Platform for 50 Microservices

**Core principle:** build one standard pipeline (a "paved road"), prove it on a few representative services, then move the rest over in waves. Don't write 50 separate pipelines. Each phase below has an exit gate, and a phase doesn't start until the one before it passes.

---

## Phase 0: Discovery and Decisions (Weeks 0–2)
**Goal:** know what you're standardizing before you build anything.

- **List every service:** language/runtime, build tool, deploy target, how it deploys today, owning team, criticality, and which services it depends on.
- **Group services into archetypes.** You'll usually find 3–6, such as "Java/Spring on K8s", "Node API", "Python worker" and "legacy VM service". These decide how many templates you need.
- **Map dependencies between services.** This sets migration order and shows where contract testing is needed.
- **Make the platform decisions:** CI engine, artifact registry, deploy model (GitOps vs. push), secrets manager, environment layout, versioning scheme.
- **Set baselines** using the four DORA metrics (deploy frequency, lead time, change failure rate, time to restore) so you can show improvement later.

**Exit gate:** archetypes defined, decisions written down as ADRs, and 3 pilot services chosen (different archetypes, low-to-medium criticality, teams who want to take part).

---

## Phase 1: Foundations (Weeks 2–6)
**Goal:** the shared infrastructure every pipeline depends on. Nothing else can start until this exists.

| Component | Why it comes first |
|---|---|
| Identity and access (SSO, OIDC for pipelines, no long-lived keys) | Every later component authenticates through it |
| Artifact/container registry with immutable tags | The built artifact is the hand-off between CI and CD |
| Secrets management | Pipelines can't deploy without it |
| Environments defined as code (dev/staging/prod) | CD needs somewhere to deploy to |
| Shared runners/build agents with caching | Keeps queues and costs under control at 50 services |
| Baseline observability (logs, metrics, traces) | Required later for automated rollback decisions |

**Exit gate:** a "hello world" service can be built, pushed, and deployed by hand to dev using only platform components.

---

## Phase 2: Standard CI Template + Pilots (Weeks 5–10)
**Goal:** reusable, versioned CI templates for each archetype, proven on the pilots.

1. Build steps: build → unit test → lint → software bill of materials (SBOM) and dependency/image scanning → sign artifact → publish.
2. Templates live in a central library. Services reference a pinned version instead of copying the YAML.
3. Standard conventions: trunk-based branching, PR checks, semantic or commit-SHA versioning.
4. Pilot teams use the templates for real work and report problems back.

**Exit gate:** all 3 pilots run CI only through templates, PR feedback takes under 10 minutes, and at least one template version bump has been rolled out without breaking anything.

---

## Phase 3: Continuous Delivery + Safety Nets (Weeks 8–14)
**Goal:** safe, automated path to production. **Rollback must work before anything reaches prod.**

1. Promote the same immutable artifact through dev → staging → prod. Never rebuild it per environment.
2. GitOps or a deploy controller handles each environment, and production has approval gates.
3. **Prove one-click (or automatic) rollback first**, then turn on production deploys.
4. Progressive delivery: canary or blue/green with automated analysis against the Phase 1 metrics.
5. Contract tests between services that depend on each other, plus smoke tests after each deploy.
6. Policy-as-code gates: signed images only, no critical vulnerabilities, required checks passed.

**Exit gate:** pilots deploy to prod through the platform, with at least one real automated rollback (or a drill) completed.

---

## Phase 4: Migration Waves (Weeks 12–28)
**Goal:** move the remaining ~47 services over without a big-bang cutover.

| Wave | Size | Selection rule |
|---|---|---|
| Wave 1 | ~7 | Low criticality, one or more per archetype, eager teams |
| Wave 2 | ~15 | Medium criticality, services the Wave 1 services depend on |
| Wave 3 | ~15 | High criticality, after the platform has shown stable SLOs |
| Wave 4 | ~10 | Legacy and odd cases. Decide whether to adapt, rewrite, or exempt each one |

- **Within a wave**, migrate a service's upstream dependencies before the services that call them.
- **Self-service onboarding** with a scaffolding CLI or template repo, docs, and office hours. The platform team shouldn't hand-migrate every service.
- **Between waves**, review lessons learned and update the templates before the next wave starts.
- Keep the old pipeline as a fallback for 1–2 weeks after each cutover, then retire it.

**Exit gate per wave:** every service in it deploys only through the platform, and the old pipelines are deleted.

---

## Phase 5: Hardening and Optimization (Ongoing, from about Week 20)
- DORA dashboards for each team and overall.
- Pipeline speed: test sharding, build caching, affected-service detection in monorepos.
- Cost controls on runners and ephemeral preview environments.
- Supply-chain maturity: SLSA provenance, image signing enforced at admission.
- A platform SLO, plus an internal developer portal (e.g., Backstage) for discovery.

---

## Critical Path
```
Discovery → Identity/Registry/Secrets → CI templates → CD + rollback → Pilots in prod → Waves 1→4
                     ↘ Observability ─────────────→ Progressive delivery ↗
```
**Can run in parallel:** observability alongside the CI templates, policy-as-code alongside CD, and developer-portal work at any point after Phase 2.

## Main Risks to Plan For
- **Template sprawl:** teams fork the templates. Prevent it with versioned templates and an extension-point model.
- **Prod before rollback:** keep the rollback gate firm.
- **Platform team becomes the bottleneck:** invest in self-service onboarding by Wave 1.
- **Shared database or tightly coupled services:** these may have to move together. Spot them in the Phase 0 dependency map.
- **Unrealistic timeline:** the weeks above assume a 4–6 person platform team. Adjust for your team size.
