# BUILD PLAN: Multi-Tenant SaaS Billing System

> **Interpretation:** I read this as the billing subsystem of a multi-tenant SaaS product, where we charge our tenants for subscriptions and usage. The other reading is a billing platform that other businesses use to charge their own customers. That version needs a second tenant level (merchant → end customer) and is hard to add later, so it's listed as a gate in §2 instead of being assumed.

---

## 1. Classification
- **What:** A system that keeps the price catalog, manages subscriptions, meters usage, prices it, issues invoices, collects payments and runs retries on failed payments, for many tenants that share one platform.
- **Type:** Software, plus infrastructure for usage ingestion. **No AI.**
- **Dominant constraint:** **Correctness.** Money has to be exact, fully traceable and charged exactly once. Compliance comes second (PCI scope, tax, audit trail).
- **Worst failure:** **Wrong money.** That means charging a tenant twice, using one tenant's data to bill another, or failing to record revenue without anyone noticing. All three destroy trust, and the third can go unseen for months.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **Consistency vs availability** | **Split.** The ledger, invoices and payments need strong consistency: one Postgres primary, with ledger writes in serializable transactions. Usage ingestion stays available instead: it accepts events into a durable buffer even when the core database is down, and removes duplicates later. | Contractual multi-region active-active, or data residency rules. Answer with regional **cells**: each tenant is pinned to one region and keeps a consistent ledger there. Never use a globally distributed ledger. |
| **Monolith vs services** | **Modular monolith.** One deployable with strict module boundaries (tenancy, catalog, subscriptions, metering, rating, invoicing, ledger, payments, dunning) and one Postgres. Modules talk only through their public interfaces, and a CI lint blocks imports across modules. | Usage ingestion stays above about 5k events/s, or ingestion deploys start blocking core billing deploys. Then split out **metering only**. Also flip when there are 3 or more teams with clashing release schedules. |
| **Sync vs async** | **Sync** for API changes such as creating a subscription or changing a plan: the state change and its ledger entries go in one transaction. **Async**, through a transactional outbox, for billing runs, payment attempts, tax calls, emails and webhooks. Postgres `SKIP LOCKED` workers to start; no Kafka. | Checkout needs payment confirmation inline (for example a strict SCA flow). Then add a sync charge path for that endpoint only. Move to a broker when 3 or more independent consumers need fan-out and replay. |
| **Build vs buy** | **Buy** payment processing (Stripe Payments with Elements, so cards never reach us and PCI scope stays at SAQ-A), tax (Stripe Tax or Avalara) and email (Postmark or SES). **Build** the ledger, subscriptions, rating and invoicing. The ledger is the source of truth, usage pricing will outgrow off-the-shelf models, and we don't want to depend on one processor. | If the real pricing sheet is only flat per-seat plans with no usage pricing, **buy the whole engine** (Stripe Billing, Chargebee or Orb). This plan then shrinks to integration plus a ledger copy. **Check this against the actual pricing sheet in week 1.** |
| **Tenant isolation model** | **Shared database and shared schema.** Every row has `tenant_id`, enforced by **Postgres row-level security (RLS)** using a per-transaction `app.tenant_id` setting. The app's database role is not the table owner, so it cannot bypass RLS. | An enterprise contract requires a dedicated database, or a tenant creates noisy-neighbor load. Then move that tenant into a dedicated cell with the same schema and migrations. |
| **Ledger model** | **Double-entry, append-only and immutable.** Corrections are made with reversing entries, never `UPDATE` or `DELETE` (a database trigger enforces this). Normal state tables sit beside it; this is not full event sourcing. | **Treat this as permanent.** The only flip is to full event sourcing, if a regulator or auditor needs every state rebuilt from scratch. |
| **Money representation** | `bigint` minor units plus an ISO 4217 currency code. No floats anywhere. Rounding rules (banker's or half-up, per currency) live in one place. Each price list is set in one currency; **no FX conversion**. | A tenant must be billed in a currency that has no price list. Then add an FX rate table and record the rate used on each invoice. |
| **Tenant hierarchy** | One level: **tenant = billed customer**, with billing accounts below it. | We sell billing to other businesses. Then add a merchant → customer hierarchy with per-merchant processor accounts (Stripe Connect). Decide this before Phase 1 because every table changes. |
| **Region / residency** | Single region (for example `us-east-1`) spread across zones. RPO 5 min or less, RTO 4 h or less. | The first EU-residency contract, or a region-level RTO under 1 h. Then add an EU cell. |
| **(AI) prompt+RAG vs fine-tune** | N/A: there are no model-driven features. | An AI feature is proposed. Re-run this skill for that feature. |
| **(AI) hosted API vs self-host** | N/A, same reason. | Same. |

## 3. Walking skeleton (Phase 0)

**The one real request:** `POST /v1/subscriptions` for one internal tenant (`acme-internal`) on one hard-coded plan (`starter`, $1.00/month, USD), followed by a real live-mode charge to a company card. The charge is refunded afterwards.

**Real response:** `201` with the subscription ID. Then, asynchronously: invoice `INV-0001` is finalized, Stripe charges $1.00, the `payment_intent.succeeded` webhook comes back, and the invoice is marked `paid`. The ledger ends up balanced: accounts receivable, cash and deferred revenue entries net to zero.

**Tiers it crosses:**
1. Edge: ALB with TLS and AWS WAF.
2. API: Go monolith on ECS Fargate. Authentication is a hashed, tenant-scoped API key.
3. Postgres 16 on RDS, Multi-AZ, with RLS **on**. One transaction writes `subscription`, the balanced `ledger_entries` and an `outbox` row.
4. Outbox worker (same binary, worker mode). It creates the invoice and calls Stripe with an idempotency key of `invoice_id:attempt_n`.
5. Stripe live mode.
6. Webhook ingress `POST /webhooks/stripe`. It checks the signature, removes duplicates by `event.id`, writes the payment ledger entries and marks the invoice paid.

**Deployed:** Terraform for all infrastructure. GitHub Actions builds **one** container image, identified by its digest, and promotes it from dev to staging to prod. Database migrations run through a versioned tool (Atlas or Flyway) before rollout. Rollback means redeploying the previous digest.

**Logged:** Structured JSON logs. Every line carries `trace_id`, `tenant_id`, `idempotency_key` and `module`.

**Monitored:**
- OpenTelemetry traces cover the whole path: API, DB, outbox, worker, Stripe, webhook, DB. The webhook span links back to the original trace through the payment intent's metadata.
- Request rate, errors and latency (RED metrics) per route.
- An outbox-lag gauge.
- A **ledger invariant check** every 5 minutes: debits must equal credits per tenant and currency. It pages on any imbalance.
- An hourly synthetic canary that runs the whole flow in staging.

**Exit check:** In prod, one real request produces a paid invoice. One trace spans every tier, the ledger invariant metric reads 0, and the canary passes. The refund also goes through and is recorded in the ledger.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

### Phase 1: Tenancy and money foundation
- **Unlocks:** Any real tenant and any real money record. Everything later writes into these structures.
- **Depends on:** The Phase 0 skeleton running in prod, with RLS and the ledger invariant working on one tenant.
- **Tasks (widest → narrowest):**
  1. **Tenant isolation model:** `tenant_id` and an RLS policy on every table. A CI migration lint rejects any table missing either one. A cross-tenant test suite calls every repository function with the wrong tenant context and expects zero rows.
  2. **Ledger schema hardened:** a chart of accounts per tenant (AR, cash, deferred revenue, revenue, credits, tax payable), an immutability trigger and the money type with its rounding policy.
  3. **Idempotency framework:** an `Idempotency-Key` header on every mutating endpoint, with the stored response returned on retry.
  4. **Billing account entity:** legal name, address, tax IDs, currency and billing contact. Tax and invoicing in Phase 3 depend on it.
  5. **Authentication and authorization:** tenant API keys with scopes, plus internal operator roles (`billing-admin`, `finance-readonly`).
  6. **Append-only audit log** of who changed what, with the before and after.
  7. Read-only internal admin view of tenants and ledgers.
- **Exit check:** The cross-tenant suite is green. Property-based tests with fixed seeds show that 100k random operations always leave the ledger balanced. Replaying 10k duplicate requests produces exactly one effect each. A point-in-time restore drill finishes within the 4 h RTO.

### Phase 2: Catalog and subscriptions
- **Unlocks:** Recurring charges. Invoices, usage pricing and the portal all reference these entities.
- **Depends on:** Proven tenancy, ledger and idempotency (Phase 1).
- **Tasks:**
  1. **Price and plan data contract:** prices are versioned and **become immutable once any subscription uses them**. Every invoice line will point to a `price_version_id`.
  2. **Subscription state machine:** `trialing → active → past_due → canceled | paused`. Only listed transitions are allowed, and each one posts its ledger entries in the same transaction.
  3. **Billing-period engine:** a pure function of (anchor date, interval, clock) that handles month-end, leap years and the tenant's billing time zone. The clock is injected, never read from the wall.
  4. **Proration:** daily in v1, with the calculation inputs stored next to the result.
  5. Plan change, cancel and pause APIs.
  6. Endpoint listing a tenant's plans.
- **Exit check:** Golden-file tests pass for period calculations from 2024 to 2030, including Feb 29, the 31st→30th month change and DST. A model-based test of the state machine finds no illegal transition. Every subscription change leaves the ledger balanced.

### Phase 3: Invoicing and tax
- **Unlocks:** Legally valid bills. Payments need a finalized invoice to collect against.
- **Depends on:** Subscriptions and billing periods (Phase 2) and billing accounts (Phase 1).
- **Tasks:**
  1. **Invoice data contract and numbering:** sequential numbers per tenant's legal entity, and invoices are **immutable after finalization** (enforced by trigger). Each line stores its source ledger entries and price version.
  2. **Billing-run scheduler:** idempotent per (subscription, period) through a unique constraint. Each tenant is checkpointed and the run can resume. A failure in one tenant's run doesn't stop the others.
  3. **Tax integration** (Stripe Tax or Avalara): the response is stored on the invoice, and an invoice is **never finalized without tax**. If the tax provider is down, the invoice stays a draft and is retried.
  4. Credit notes and adjustments, recorded as reversing ledger entries.
  5. PDF rendering, stored in S3 with signed URLs that expire.
  6. Invoice emails.
- **Exit check:** A shadow billing run over all subscriptions matches the ledger to the cent. Running the same period again creates **zero** new invoices. Killing the run partway through and restarting it gives identical output.

### Phase 4: Payments and collections
- **Unlocks:** Getting paid at scale and recovering failed payments.
- **Depends on:** Immutable invoices that match the ledger (Phase 3), and the Stripe path proven in Phase 0.
- **Tasks:**
  1. **Payment state machine and webhook ingestion contract:** signature check, duplicate removal by event ID, and safe handling of out-of-order events by fetching the latest state from Stripe instead of trusting the order events arrive in.
  2. **Daily reconciliation:** Stripe balance transactions compared with ledger cash entries. Any difference that can't be explained pages someone.
  3. **Retry and dunning policy:** jittered retry schedule, `past_due` transitions, grace period, and a hook to suspend the tenant's service.
  4. Refunds. Refunds above a set amount need a second person's approval.
  5. Payment-method update flow (Stripe Elements, with SCA and 3DS).
  6. Payment-receipt emails.
- **Exit check:** 14 straight days of reconciliation with zero unexplained differences on live traffic. A fault-injection suite passes: duplicate, reordered and 24 h-delayed webhooks all settle to the correct state, and a simulated processor outage leaves no double charges.

### Phase 5: Usage metering and rating
- **Unlocks:** Usage-based and hybrid pricing.
- **Depends on:** The catalog's price versions (Phase 2), invoice lines (Phase 3) and collections (Phase 4). Usage priced onto an invoice that can't be collected is worthless, so this comes after.
- **Tasks:**
  1. **Usage event schema contract:** `{tenant_id, meter, quantity, timestamp, idempotency_key, properties}`. Tenant clients integrate against this, so it is the hardest thing in the phase to change later. It is versioned from the start.
  2. **Ingestion path:** API → SQS (keeps accepting events when the database is down) → consumer → a partitioned `usage_events` table with a unique `(tenant_id, idempotency_key)`.
  3. **Aggregation:** per meter and period, with a **late-event cutoff** (for example 72 h after the period closes). Events that arrive later go into the next invoice as adjustments.
  4. **Pricing models** (tiered, volume, package, overage), versioned, as a pure function of (aggregates, price version).
  5. Usage lines added to the billing run.
  6. Usage-to-date preview API.
- **Exit check:** Replaying the raw event log for a closed period gives **identical** priced totals. A load test at 10x the expected peak passes. Ingestion keeps accepting events during a 30-minute database outage and loses none.

### Phase 6: Tenant- and operator-facing features (the visible parts, built last)
- **Unlocks:** Self-serve billing, finance workflows and integrations.
- **Depends on:** All billing data being correct and reconciled (Phases 1–5).
- **Tasks:**
  1. **Outbound event and webhook contract for tenants:** `invoice.finalized`, `payment.failed` and others. External systems build against it.
  2. **Accounting export:** mapping our ledger accounts to the general ledger in NetSuite or QuickBooks.
  3. Operator adjustment tooling, which needs a second person's approval.
  4. Revenue reporting: MRR, ARR, deferred revenue and churn.
  5. Customer billing portal: invoices, payment methods, plan changes, usage.
  6. Dashboard polish.
- **Exit check:** Finance closes one month entirely from the export with no manual fixes. Outbound webhook delivery is at least 99.9% with retries. The portal's numbers match the ledger exactly in an automated comparison.

## 7. Deliberately deferred

| Not building yet | Condition that pulls it forward |
|---|---|
| Separate metering service | Ingestion stays above about 5k events/s, or ingestion deploys block core billing deploys. |
| Kafka or other event streaming | 3 or more independent consumers need fan-out and replay of the same streams. |
| Multi-region cells and data residency | First EU-residency contract, or a region-level RTO requirement under 1 h. |
| Database per tenant | An enterprise contract requires it, or one tenant's load causes measurable noisy-neighbor impact. |
| FX conversion and multiple currencies per price list | A tenant needs billing in a currency that has no price list. |
| More than one payment processor | Authorization rate drops, a market Stripe doesn't cover, or concentration risk is flagged by finance. |
| Automated revenue recognition (ASC 606 / IFRS 15) | Audit preparation, or finance can no longer close from the accounting export. |
| Quotes, contract ramps, committed spend | Sales-led deals exceed about 20% of new ARR. |
| Real-time spend caps and entitlement enforcement | Bill-shock incidents, or customers explicitly ask for it. |
| Cloud marketplace billing (AWS or GCP) | Demand from that sales channel. |
| Columnar store (ClickHouse) for usage aggregates | Postgres aggregation misses the billing-run time limit. |
| Merchant hierarchy (billing as a service) | The tenant-hierarchy gate flips. This needs a re-plan from Phase 1. |
