# BUILD PLAN: CI/CD Platform for 50 Microservices

## 1. Classification
- **What:** A shared build, test, sign and deploy platform that takes a commit in any of 50 service repos and gets a verified artifact into production.
- **Type:** Infra. It's not an AI system, so the AI layer doesn't apply.
- **Dominant constraint:** Correctness, meaning the integrity of what ships. Scale (50 services, roughly 50 teams' daily throughput) comes second.
- **Worst failure:** The platform holds production credentials for all 50 services, so the worst outcome is an unverified or tampered artifact deployed silently across many services. A close second is the platform being down during an incident, so no team can ship a hotfix.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **Consistency vs availability** (deploy state) | **Consistency.** Git is the single source of truth for desired state. The deploy controller refuses a deploy it can't verify (bad signature, unknown digest). A documented, audited, time-boxed break-glass path covers availability. | The verify-or-refuse rule blocks a real prod hotfix more than once a quarter. Then add a pre-approved break-glass lane with automatic after-the-fact verification. |
| **Monolith vs services** (the platform itself) | **One platform, not 50 bespoke pipelines.** That means one CI system, one CD controller and one versioned golden-path template. Each service keeps only a ~10-line caller file. | More than 20% of services need template overrides that fight the default. Then split into 2–3 templates by archetype (stateless API, worker, stateful). |
| **Repo topology** (very expensive to reverse) | **Keep the existing polyrepo.** Standardize through reusable workflows. No monorepo migration. | More than 25% of PRs need coordinated changes across services, or dependency drift between services becomes the main cause of incidents. Then evaluate a monorepo with Bazel/Nx and affected-only builds. |
| **Sync vs async** (CI → CD handoff) | **Async, pull-based GitOps.** CI builds and pushes an image by digest, then commits that digest to a config repo. Argo CD pulls and reconciles. CI never holds cluster credentials. | A deploy target can't run a pull agent (Lambda, edge, vendor SaaS), or the business needs commit-to-prod under 2 minutes. Use push for those targets only. |
| **Build vs buy** | **Adopt off-the-shelf parts:** GitHub Actions with self-hosted ephemeral runners (Actions Runner Controller on Kubernetes), Argo CD, Argo Rollouts, Harbor or ECR as the registry, Sigstore cosign, Syft and Trivy, Kyverno. **Build only** the golden-path template, the promotion glue and the dashboards. | CI minute or runner cost passes an agreed budget, or orchestrator limits (concurrency, queueing) breach the lead-time SLO for 2 consecutive months. Then evaluate Buildkite or Tekton. |
| **Artifact identity** | **Build once, promote by immutable digest.** The exact bytes tested in staging are the bytes that run in prod. Environment config is injected at deploy time, never at build time. | No real flip. If a service needs build-time env config, refactor the service rather than the platform. |
| **Branching / promotion model** | **Trunk-based.** Promotion is a PR or commit to an environment overlay in the config repo (dev → staging → prod). | A regulated service needs release branches with formal sign-off. Add a release-branch lane for that service only. |
| **Deploy target** | **Kubernetes only, one deployment shape** (shared Helm chart or Kustomize base). | More than 3 services can't containerize. Add a second target type, behind the same promotion model. |
| **CI credentials** | **OIDC workload identity federation** to the cloud and the registry. No long-lived static keys anywhere. | A target doesn't support OIDC. Use short-lived Vault-issued credentials, never static secrets. |
| (AI) prompt+RAG vs fine-tune | N/A: there's no model in the system. | — |
| (AI) hosted API vs self-host | N/A: there's no model in the system. | — |

## 3. Walking skeleton (Phase 0)

**The one real request:** a merge to `main` in **one real, low-risk, stateless service** (for example an internal lookup API). The real response is that service's `/version` endpoint **in production** returning the new commit SHA.

**Tiers it crosses:**
1. **SCM:** GitHub, with branch protection on `main`.
2. **CI orchestrator:** GitHub Actions, with a plain workflow copied by hand. No template yet.
3. **Runner:** one ephemeral self-hosted runner on Actions Runner Controller.
4. **Build:** `docker buildx` produces an image with OCI labels for source SHA and run ID.
5. **Registry:** the image is pushed by digest to Harbor or ECR, authenticated through OIDC.
6. **Config repo:** CI commits `image: <digest>` to `services/<svc>/dev/`.
7. **CD controller:** Argo CD syncs dev. A human merges the promotion commit to `prod/`, and Argo CD syncs prod.
8. **Cluster and service:** pods roll and readiness probes pass.
9. **Observability:** see below.

**Day-zero deploy, logging and monitoring:**
- **Metrics:** Argo CD sync and health metrics, plus GitHub Actions workflow-run events, go to Prometheus.
- **Dashboard:** one Grafana board shows commit-to-prod lead time and deploy success/failure for this one service.
- **Logs:** runner logs ship to Loki.
- **Trace:** each deploy event carries the commit SHA, run ID and image digest, so one query links commit → build → digest → running pod.
- **Alerts:** Argo CD sync failure, and a prod app that stays degraded for more than 5 minutes.

**Exit check:**
- A real merge produces the new SHA on prod `/version`.
- The lead-time metric and the SHA → digest → pod link are visible in Grafana.
- **Rollback works:** reverting the config-repo commit restores the previous version in prod within 5 minutes.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 1: Substrate contracts and pilot set (rule of three)**
- **Unlocks:** a pipeline shape proven to generalize. A template is only specified after it has been seen working on three different stacks.
- **Depends on:** the Phase 0 skeleton running end to end in prod.
- **Tasks (widest → narrowest):**
  1. **Trust and identity model:** OIDC federation for every CI → cloud and CI → registry path. Decide who or what may promote to prod (CODEOWNERS on `prod/` overlays). Argo CD RBAC and SSO. Every later pipeline inherits this.
  2. **Artifact contract:** digest-only references, mandatory OCI labels (source repo, SHA, run ID), base-image policy (2–3 approved, pinned-by-digest base images).
  3. **Config-repo schema:** `services/<svc>/<env>/` layout, a shared Helm/Kustomize base, environment overlays. This is the deploy-state schema, and the most expensive thing to change later.
  4. **Runner fleet:** autoscaling ephemeral runners, with separate runner pools per trust tier (untrusted PRs from forks never share runners with `main` builds).
  5. **Build caching:** registry-backed BuildKit cache.
  6. **Pilot onboarding:** add 2 more services on *different stacks* (for example Go, JVM, Node), still on copied workflows.
- **Exit check:** 3 heterogeneous services go commit → prod on ephemeral runners with no static credentials anywhere (verified by a secret-scan of repos and CI settings). The common pipeline steps are identified by diffing the three copied workflows.

**Phase 2: Golden-path template and supply-chain gates**
- **Unlocks:** onboarding at scale. Every artifact is attested, so the clusters can refuse unverified code.
- **Depends on:** the Phase 1 pipeline shape, proven on 3 stacks. Nothing goes into the template until it runs in all three.
- **Tasks (widest → narrowest):**
  1. **Template interface contract:** inputs (language, test command, chart values) and outputs (digest, SBOM, provenance). Versioned with semver and pinned by tag or SHA in callers. Once 50 services call it, this is the hardest thing to change.
  2. **Signing and provenance:** cosign keyless signing, SLSA provenance (via slsa-github-generator), Syft SBOM attached as an attestation.
  3. **Cluster admission policy:** Kyverno or Sigstore policy-controller verifies signature and provenance. It starts in **audit mode**: no rigidity until it's proven.
  4. **Onboarding gate:** a service only joins once it exposes RED metrics (rate, errors, duration) and `/healthz`, because Phase 3 canary analysis depends on them.
  5. **Quality stages:** lint, unit tests, Trivy scan. Critical CVEs fail the build; high ones only warn at first.
  6. **Per-language build steps** (leaf work).
  7. **Migration:** move the 3 pilots onto the template, then onboard 7 more (10 total).
- **Exit check:** 10 services run on a pinned template version. The admission audit log shows 100% signed, attested images for onboarded services. A template upgrade rolls out through Renovate PRs without touching any service by hand.

**Phase 3: Promotion and progressive delivery**
- **Unlocks:** safe, mostly automated prod deploys, so humans stop being the rollback mechanism.
- **Depends on:** signed artifacts from Phase 2 and RED metrics on every onboarded service.
- **Tasks (widest → narrowest):**
  1. **Promotion model:** automated dev → staging and gated staging → prod promotion through config-repo PRs (Kargo or a small promotion bot). Promotion requires the *same digest* to have passed staging.
  2. **Rollback mechanism:** Argo Rollouts abort plus config-repo revert, for every service, tested.
  3. **Shared analysis templates:** Prometheus queries on error rate and p99 latency against each service's SLO.
  4. **Per-service canary tuning:** step weights and pause durations (leaf work).
- **Exit check:**
  - A deliberately bad release (injected 500s) is **auto-rolled back** in staging and in prod canary with no human action.
  - Every prod change has a traceable promotion record (who, what digest, from which staging run).

**Phase 4: Fleet rollout (services 11–50)**
- **Unlocks:** one platform and one audit trail for the whole estate, so legacy pipelines can be retired.
- **Depends on:** the Phase 3 auto-rollback, proven on 10 services.
- **Tasks (widest → narrowest):**
  1. **Database migration contract:** expand/contract only. Migrations run as a separate pre-rollout Job, with a backward-compatibility check in CI. This is required *before* any stateful service joins.
  2. **Shared dependency hygiene:** Renovate across all repos for base images, shared libraries and template versions.
  3. **Waves ordered by risk:** stateless internal services → async workers → stateful services → customer-facing critical services (payments and auth last).
  4. **Flip admission policy from audit to enforce,** cluster by cluster, after each wave is fully signed.
  5. **Decommission legacy pipelines and revoke their credentials** (leaf work, but it's what closes the risk).
- **Exit check:**
  - 50/50 services deploy through the platform, with admission **enforcing** in every prod cluster.
  - Zero legacy pipeline credentials remain (verified by a credential inventory).
  - At least one stateful service has shipped a schema change by expand/contract with no downtime.

**Phase 5: Scale, cost and self-service**
- **Unlocks:** the platform keeps up as service count and team count grow.
- **Depends on:** a stable fleet on one template (Phase 4). You can only optimize what is uniform and measured.
- **Tasks (widest → narrowest):**
  1. **Fleet-wide patch pipeline:** a base-image CVE triggers automatic rebuild and promotion across all affected services.
  2. **CI performance:** test sharding, affected-only test selection, remote cache tuning, flaky-test quarantine list.
  3. **Cost and DORA metrics per team:** runner minutes, deploy frequency, lead time, change failure rate, MTTR.
  4. **Self-service new-service scaffold:** a repo template plus a config-repo entry plus first deploy, all from one command.
- **Exit check:**
  - p50 commit-to-prod under 30 minutes.
  - A critical base-image CVE is patched across the fleet in under 72 hours.
  - A brand-new service reaches prod in under 1 day with no platform-team ticket.

## 5. Cross-cutting concerns (per phase, from the first commit)

| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|

| **1 Substrate** | Trust-tier runner isolation (fork PRs isolated); CODEOWNERS on `prod/` overlays; secret-scanning on all repos | Runner queue time, utilization and failure metrics; per-stage duration | Pinned base images by digest; pinned action versions by SHA; runner images built from code | Runner autoscaling with minimum warm pool; registry replication to a 2nd region; Argo CD state rebuildable from Git |

N/A. The system has no model, no retrieval, and no autonomous agent making decisions.

## 7. Deliberately deferred
- **Developer portal (Backstage catalog and UI):** this is the most visible piece, so it comes last. **Pull forward when** service discovery or ownership questions become a weekly incident-response bottleneck, or the team count passes about 15.
- **Monorepo / Bazel hermetic builds:** **pull forward when** the repo-topology gate flips (cross-service PRs above 25%).
- **Bit-for-bit reproducible builds (SLSA L3+ hermetic):** **pull forward when** a compliance regime or customer audit requires it (FedRAMP, SOC 2 auditor findings).
- **Per-PR preview environments:** **pull forward when** staging contention (queued promotions or env collisions) adds more than 1 hour to median lead time.
- **Multi-region active-active control plane:** **pull forward when** a platform outage blocks a prod hotfix, or platform availability drops below 99.9% in a quarter. Until then, use active-passive with replicas.
- **Feature-flag platform (OpenFeature / LaunchDarkly):** **pull forward when** teams need to decouple release from deploy beyond what canaries give (dark launches, per-tenant rollout).
- **Contract testing between services (Pact):** **pull forward when** more than 10% of staging failures are API mismatches between services.
- **Non-Kubernetes deploy targets (Lambda, VMs):** **pull forward when** the deploy-target gate flips (more than 3 services can't containerize).
- **Replacing GitHub Actions with Buildkite or Tekton:** **pull forward when** the build-vs-buy flip condition trips.
- **Chaos testing of the platform itself:** **pull forward after** Phase 4 exits, or right away if a platform incident occurs earlier.
