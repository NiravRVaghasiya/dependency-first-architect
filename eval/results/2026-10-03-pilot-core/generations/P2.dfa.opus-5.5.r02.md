# BUILD PLAN: Multi-tenant SaaS billing platform

## 1. Classification and constraints
- **What:** A multi-tenant billing platform. Each tenant is a SaaS business that sets up products and prices, subscribes its own customers, meters usage, sends invoices, and collects payment through its own PSP account.
- **Type:** Software. Greenfield (assumed). Not small: it handles money, outside tenants, end-customer personal data, and several R3 decisions.
- **Dominant constraint:** Correctness of money, then compliance (PCI DSS scope, GDPR processor duties, VAT invoicing rules).
- **Worst failure:** End customers are silently charged money they don't owe, across many tenants. That covers a double charge, a misrated invoice or a runaway retry. The harm is financial, it lands on people who never chose us, and it can't be undone by a revert. A close second is one tenant's customer data being exposed to another tenant. V5, V3/V8 and V1 guard against these.

**Missing inputs**, with the assumptions the phase order rests on:
1. **Platform or internal billing?** I assumed a platform that tenants use to bill *their* customers. If you meant billing for your own multi-tenant product, drop the PSP-connected tenant accounts, the tenant-configurable catalog, outbound webhooks and V7's per-tenant review. The ledger-first order stays the same.
2. **Who holds the funds?** I assumed tenants connect their own PSP accounts, so we never hold funds and never see a card number. If we must be merchant of record or pay tenants out, licensing, KYC and PayFac obligations become Phase 0 organizational blockers with months of lead time, and this plan has to be redone from Step 1.
3. **Greenfield?** I assumed yes. If an existing billing system is being replaced, the Phase 5 parallel run becomes the migration method for our own customers, plus a decommission gate.
4. Volumes (tenants, subscriptions, usage events): product lead, before Phase 4.
5. Jurisdictions of tenants and their customers: counsel, before Phase 2. This drives tax, retention, invoice content and data residency.
6. The SLA we sell to tenants: commercial lead, before Phase 5.
7. Pricing models in v1. I assumed flat, per-seat, and tiered/volume usage, one currency per subscription. Prepaid credits and commitments are deferred.
8. A named finance reviewer (controller or accounting advisor) to sign off V2 and V3.

## 3. Tradeoff gates (resolved up front)

| Monolith vs services | R2 | Modular monolith (ledger, catalog, subscriptions, rating, invoicing and payments as separate modules), plus a separate ingestion service because it scales and fails differently | One team | Cheap check: module-boundary lint in CI; V6 for ingestion | More than ~3 squads, or a module needs to scale on its own |

## 4. Walking skeleton (Phase 0)
- **The request:** An internal tenant, `internal-acme`, using an allow-listed API key:
  1. `POST /v1/customers`
  2. `POST /v1/subscriptions` (one flat $10/month price)
  3. `POST /v1/invoices/{id}/finalize`, which posts ledger entries (debit A/R, credit revenue) and assigns invoice number 1.
  4. An outbox worker creates a PaymentIntent in the **PSP sandbox**, using a test payment-method token (no card number touches us).
  5. A signed PSP webhook posts the cash entry.
  6. `GET /v1/invoices/{id}` returns `status: paid` with balanced ledger lines.
- **Tiers crossed:** ALB + WAF → API (modular monolith) → Postgres (RLS on, tenant_id on every row) → outbox worker → PSP sandbox → webhook receiver → ledger → API.
- **Deploy, log, monitor, roll back:**
  - Deploy: Terraform into the production AWS account. CI builds a signed image; a rolling deploy rolls back automatically on failed health checks. Migrations are expand-only, so rolling back never needs a down-migration.
  - Log and trace: OTel trace across API, worker and webhook. Structured logs carry tenant_id and request_id, with personal data redacted.
  - Alert on: API error rate and latency, outbox lag, webhook signature failures, and an hourly job that checks debits equal credits.
  - Roll back: redeploy the previous image, once, on purpose.
- **Who can reach it:** Only the internal tenant's allow-listed key. Everything else sits behind a feature flag. Money runs on the PSP sandbox (a disposable copy) until V4 and V5 pass. This follows Step 4; it is not an exception.
- **Organizational lead-time tasks started now:**
  - PSP platform application.
  - Shortlist and contract a tax vendor.
  - Engage counsel (DPA, terms, residency, retention).
  - Name the finance reviewer.
  - Book a pentest vendor.
  - Request the inputs in §1: volumes, jurisdictions, SLA.

Exit check (V0): the request succeeds with one trace across every tier; a deploy and a rollback both succeed through the pipeline; an injected failure (PSP sandbox blocked) fires the outbox-lag alert; first latency and lag values are recorded as baselines.

## 5. Phases

- **Phase 1 — Tenancy, identity and the ledger core**
  - Unlocks: specifying every tenant-scoped module and anything that posts money.
  - Depends on: V0.
  - Tasks:
    1. Tenant model with separate livemode and testmode data, the tenant→cell map, and fail-closed RLS.
    2. Tenant admin login through the IdP (SSO, MFA required); hashed API keys scoped to tenant and mode; RBAC; an append-only audit log.
    3. Ledger: chart of accounts, posting API, idempotency-key store, per-tenant invoice number allocator.
    4. API middleware: version pinning and translation layer, idempotency, pagination.
    5. A cross-tenant test harness in CI.
    6. Start the V4 data-flow documentation.
  - Rollback: no real data exists yet, so the schema can change freely. After V1 and V2 pass, schema changes are expand/contract only.
  - Exit check: V1 and V2 pass; one PITR restore into a scratch account succeeds.

- **Phase 2 — Catalog, subscriptions, rating, invoicing, tax**
  - Unlocks: complete invoices for flat and per-seat pricing.
  - Depends on: Phase 1, V1, V2; tax vendor contract; counsel's retention input.
  - Tasks:
    1. Versioned products and prices.
    2. Subscription lifecycle (trial, active, past_due, canceled, paused) with effective dating and proration.
    3. Rating engine with an injected clock, plus internal test clocks.
    4. Draft invoices that finalize into immutable records (DB grants block any UPDATE after finalization) and credit notes.
    5. Tax adapter: if the tax vendor fails, the invoice stays a draft.
    6. PDF rendering to a private, object-locked S3 bucket.
    7. Bill-run scheduler.
  - Rollback: feature flag per module; expand/contract migrations. A finalized invoice is never edited, only credited.
  - Exit check: V3 passes.

- **Phase 3 — Payments and collections.** Runs in parallel with Phase 4 if staffing allows. It comes first because it guards the worst failure and its gates have the longest outside lead time.
  - Unlocks: collecting real money, first only from the internal tenant.
  - Depends on: Phase 2, V2; PSP platform approval.
  - Tasks:
    1. PSP adapter: Stripe Connect OAuth to tenant-owned accounts, with restricted keys.
    2. Payment-method capture only through PSP-hosted fields.
    3. Automatic collection. Every PSP call uses an idempotency key derived from (invoice, attempt).
    4. Webhook dedup and handling of out-of-order events.
    5. Dunning with a hard cap on retries.
    6. A charge brake: a charge more than 3× the customer's previous invoice, or a second success on the same invoice, is held and paged.
    7. Refunds through credit notes.
    8. Nightly ledger-vs-PSP reconciliation.
  - Rollback: a flag turns off automatic collection per tenant, so invoices still go out and are collected manually. Live mode is enabled for the internal tenant only, charging a company card.
  - Exit check: V4 and V5 pass; two internal-tenant live cycles reconcile with zero differences.

- **Phase 4 — Usage metering**
  - Unlocks: usage-based and tiered pricing.
  - Depends on: Phase 2, V3; the volume input.
  - Tasks:
    1. Ingestion service and SDK, with write-only ingest keys.
    2. Dedup on the idempotency key.
    3. Raw log to S3 (tenant-prefixed, encrypted).
    4. Aggregator, tiered and volume rating, and the late-event policy.
    5. Usage preview API.
    6. A replay job that rebuilds aggregates from S3.
  - Rollback: usage prices stay behind a flag. Aggregates can always be rebuilt from the raw log.
  - Exit check: V6 passes; the replay matches live aggregates exactly.

- **Phase 5 — Tenant-facing surface and the first design partner** (exposure: one tenant first)
  - Unlocks: the first outside tenant billing its real customers.
  - Depends on: Phases 3–4, V5, V6, V7.
  - Tasks:
    1. Signed outbound webhooks with SSRF protection on tenant URLs.
    2. Tenant dashboard.
    3. Data export.
    4. Import tooling: subscriptions in; payment methods stay in the tenant's own PSP account.
    5. Email delivery.
    6. Hosted invoice page and customer portal. These are the most visible parts, so they come last.
    7. Run V8 with the design partner in shadow mode: compute invoices but send none.
  - Point of no return: the design partner turning off billing in their old system. V8 guards it, approved by the tenant's finance lead and our billing-ops lead. Until then the old system bills, and our invoices stay shadow-only.
  - Exit check: V7 and V8 pass; the first live cycle for the design partner reconciles with zero differences.

- **Phase 6 — Onboarding waves, capacity, economics, GA**
  - Unlocks: more tenants, then self-serve and GA.
  - Depends on: Phase 5, V8; volume and subscription inputs; our pricing input.
  - Tasks:
    1. Run V9 before going past 3 tenants.
    2. Onboard in waves: 1 → 3 → 10 tenants, then self-serve. Each wave starts with a parallel run.
    3. SLOs and burn-rate alerts (once the SLA input arrives).
    4. Fairness: per-tenant rate limits and queues.
    5. DR drill.
    6. SOC 2 Type I readiness.
    7. Run V10 before committing to pricing.
  - Rollback: pause the onboarding wave; the per-tenant collection flag still applies.
  - Exit check: V9 and V10 pass; the DR drill meets RPO and RTO; operational complexity is still within its budget.

## 10. Deliberately deferred
- **Revenue recognition schedules (ASC 606 / IFRS 15):** pull forward when a tenant needs them for an audit, or 3+ tenants ask.
- **EU (or other) residency cell:** pull forward when V7 finds a signed tenant that needs it.
- **Dedicated per-tenant databases:** pull forward when an enterprise contract requires one or V9 shows a noisy neighbor.
- **Second PSP and bank rails (Adyen, GoCardless/SEPA, ACH):** pull forward when a design partner's region or volume needs it.
- **Mandatory e-invoicing formats (Peppol, national clearance systems):** pull forward when a tenant bills B2B customers in a jurisdiction where counsel confirms a mandate applies.
- **Prepaid credits, commitments, quotes/CPQ:** pull forward when tenant demand shows up in onboarding.
- **Merchant of record or payouts:** pull forward only on a commercial decision, which means redoing this plan from Step 1 (licensing).
- **Splitting into microservices:** pull forward when a module needs to scale independently or the team grows past ~3 squads.
- **SOC 2 Type II:** pull forward when enterprise prospects require it. The observation window starts after Type I.
- **Self-serve tenant signup:** pull forward after wave 3 passes and V9 holds.
- **MRR and churn analytics for tenants:** pull forward on tenant demand once billing data has been stable for one cycle.
