# Build order for a real-time collaborative document editor

I read this as a request to put the build steps in order, so this is a dependency-ordered plan. The sequence is built around one rule: **decide how edits merge before you build anything else.** That decision touches every later step, and changing it later usually means a rewrite.

## Phase 0: Decisions to make first
1. **Scope:** rich text or plain text, expected number of simultaneous editors, offline support, and target platforms.
2. **How concurrent edits merge.** This is the most important decision.
   - **CRDT** (Yjs, Automerge): works offline and doesn't strictly need a central server. Use this unless you have a reason not to.
   - **OT** (operational transformation, as Google Docs does): needs a central server that puts edits in order. It's harder to get right yourself.
3. **Editor framework:** ProseMirror/Tiptap, Lexical, Slate or CodeMirror. Pick one with a proven binding to your merge approach, such as `y-prosemirror`.
4. **Document schema:** which blocks and formatting marks are allowed, and how embedded content works.

## Phase 1: Single-user base
5. **Editor UI for one user:** editing, formatting, undo/redo, all against the shared document model from step 2.
6. **Saving documents:** save and load snapshots plus the log of updates, with a document ID and metadata.
7. **Basic auth:** user identity is needed before you can track who wrote what or who can open what.

## Phase 2: Real-time collaboration
8. **Live connection:** a WebSocket server (for example `y-websocket` or Hocuspocus) with one room per document.
9. **Sync protocol:** an initial state exchange, then incremental updates and reconnection handling.
10. **Convergence testing:** fuzz tests that apply edits concurrently in random orders and check that every copy ends up identical. Run these continuously from here on.
11. **Presence:** remote cursors, selections and an active-user list. These are temporary and are not saved with the document.

## Phase 3: Reliability
12. **Offline support:** a local store (IndexedDB), queued edits and a merge when the user reconnects.
13. **Save frequency and compaction:** save regularly and take snapshots so update logs don't grow without limit.
14. **Permissions:** owner, editor, commenter and viewer roles, enforced **on the server** for every incoming update, not just in the UI.

## Phase 4: Collaboration features
15. **Version history:** named versions, viewing differences and restoring an older version.
16. **Comments and suggestions:** comments attached to text ranges that stay in place as the text around them changes, plus suggestion mode.
17. **Sharing:** invite links, sharing settings and notifications.

## Phase 5: Scale and hardening
18. **Horizontal scaling:** route each document to a specific server (sticky routing), or broadcast updates between servers through Redis or NATS.
19. **Performance:** large documents, many users in one document, lazy loading and limits on how fast clients can send updates.
20. **Security:** validate every incoming update, check against the schema, and keep an audit log.
21. **Monitoring:** sync delay, conflict and error rates, and alerts when copies stop matching.
22. **Load and chaos testing:** network splits, slow clients and server restarts while people are editing.

## Things that must happen in order
- The **merge decision (2)** comes before everything else.
- **Saving (6)** comes before the **live connection (8)**, because you need a reliable copy to sync from.
- **Convergence tests (10)** come before **offline support (12)**, because offline makes merge bugs much more likely.
- **Permissions (14)** come before **sharing (17)**.
- **Compaction (13)** comes before **version history (15)**.

## Smallest useful first release
Steps 1–11 plus server-side permission checks from step 14 give you a working, safe collaborative editor. Everything after that improves it step by step.
