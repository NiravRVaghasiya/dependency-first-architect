# BUILD PLAN: `photo-rename`, a CLI that renames a folder of photos by EXIF capture date

## 1. Classification and constraints
- **What:** a local command-line tool. It reads each photo's capture date from EXIF and renames the files in one folder to a sortable date-based name.
- **Type:** software, greenfield. One developer and no services. It isn't formally a "small" build, for two reasons. The write-safety decision is R3, and a public release would put it on other people's photos. Even so, the plan stays at three phases.
- **Dominant constraint:** correctness. Every photo must survive with its content unchanged and end up with the right name.
- **Worst failure:** a run overwrites one photo with another, or loses the record of the original names. The usual causes are two burst shots in the same second, an existing file with the target name, or a run killed halfway through. Lost image data can't be recovered, and a lost name mapping breaks links from Lightroom catalogs, `.xmp` sidecars and scripts.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Throughput | Plan 10,000 photos in < 60 s on a local SSD | ASSUMPTION: ExifTool in batch mode (one process, `-json`) reads hundreds of files per second; starting one process per file would miss this. Confirm with the V0 baseline | V0 records the floor; Phase 1 exit check |
| Data integrity | 0 files lost, overwritten or changed in content | ASSUMPTION: implied by "rename", which asks for no content change | V1 |
| Operational complexity | No services; one outside binary (ExifTool) on PATH | ASSUMPTION: one maintainer | Phase 2 exit check |

**Missing inputs** (none changes the phase order, so the plan proceeds on the stated assumptions):
1. **File formats.** Assumed: JPEG, HEIC and common RAW. If it's JPEG only, a pure-Python reader is enough and ExifTool can go (the backend flip on the R1 line).
2. **Personal tool or public release?** Assumed public. If personal, Phase 2 shrinks to tagging a release.
3. **Naming and timezone expectations.** Assumed: local wall-clock time, second precision.
4. **Target operating systems.** Assumed: Windows, macOS and Linux, including SD cards formatted as exFAT.
5. **Sidecar files.** Are `.xmp` / `.aae` sidecars or Live Photo `.mov` files present? Assumed yes.
6. **Recursion.** Assumed: one folder only, not its subfolders.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Write model | R3: an overwrite or a lost name mapping on a user's photos can't be undone | Rename in place. Build the full plan before any write; dry-run is the default and `--apply` is opt-in. Write the journal (JSONL, fsync) before the first rename. Each rename refuses to overwrite: on Windows `os.rename` already raises if the target exists; on POSIX use `os.link` + `os.unlink`, or check-then-rename where hard links aren't supported (exFAT). Add `undo <journal>` and resume | Refuse-to-overwrite renames plus the journal give zero loss on every target filesystem, including when a run is killed | V1 | V1 fails on any filesystem → the default becomes copy-into-a-new-folder (originals untouched, storage doubles) for that filesystem or for all |
| Name format | R2: once users' libraries carry these names, changing the format means renaming their folders again, and scripts may parse the names | `YYYY-MM-DD_HH-MM-SS[_NN].<ext unchanged>`. No colons (NTFS forbids them) and it sorts correctly as text. Same-second photos get `_01`, `_02`… ordered by SubSecTimeOriginal, then by original name, so the result is the same every run | Users want one flat local-time format | Cross-OS filename cases in the V1 matrix, plus the owner reviewing a dry-run on a real folder | Someone asks for another pattern → add a `--format` template; the default stays |
| Timezone | R2: changing the default renames existing libraries differently | Use the recorded wall-clock time as-is. No conversion; ignore OffsetTimeOriginal | Each folder holds photos from one timezone | V2 corpus includes travel and multi-device cases | Users merge cameras across zones, or a camera clock is wrong → add `--shift` / `--tz` |
| Sidecar files | R2: a sidecar left behind loses its link to the photo, and re-pairing is manual across the library | Files with the same base name move as a group under the same new name (`IMG_1.CR2`, `IMG_1.xmp`, `IMG_1.JPG`, `IMG_1.MOV`), dated by the primary file | Matching base names identifies sidecars | V1 cases include sidecar groups; V2 corpus includes real layouts | The corpus shows layouts the rule misses (e.g. `IMG_1.CR2.xmp`) → widen matching, or report those files instead of moving them |
| Privacy boundary | R3: leaked GPS or home location can't be recalled | Local only: no network, no telemetry. Logs and journals hold paths, dates and skip reasons only, never GPS or a full EXIF dump. The real-photo corpus is never committed | Nothing needs the network | Basis: the tool has no network code or network dependency. A Phase 0 CI test runs it with network access blocked; V2 evidence stores hashes, not photos | A feature needs the network (e.g. naming by place) → re-plan with a consent boundary |

**R1 defaults:**
- **Build vs buy → build a thin wrapper.** This decision decides whether to build at all. ExifTool alone, run as `exiftool -d '%Y-%m-%d_%H-%M-%S%%-c.%%e' '-FileName<DateTimeOriginal' DIR`, already renames without overwriting. If a one-off rename after a backup is all you need, use that and stop. The tool adds dry-run by default, a journal with `undo`, sidecar grouping and a safety harness.
- **Language → Python 3.11+**, installed with `pipx` or `uv tool`, using argparse.
- **Metadata backend → ExifTool `-json` in batch mode,** behind a `MetadataReader` interface. File names are passed in a `-@` argument file, so a name starting with `-` can't be read as an option. Flip to exifread or Pillow + pillow-heif if the outside binary is unwanted or the tool is JPEG only.
- **Date tag order → DateTimeOriginal > CreateDate > DateTimeDigitized.** Files with no date are skipped and reported. File modification time is used only with `--fallback mtime`.
- **Scope → one folder, not recursive.**

**N/A:** consistency vs availability, monolith vs services, sync vs async: it's one local process with no service and no other writers. The assumption that nothing else edits the folder during a run is covered in §10.

## 4. Walking skeleton (Phase 0)
- **Request:** `photo-rename ~/Pictures/trip` (dry-run by default) on a real folder of the owner's photos. It prints an `old → new` plan, the skipped files with reasons, and a summary line (planned / skipped / same-second suffixes). It sets an exit code: 0 = full plan, 3 = some files skipped, 2 = fatal. `--log-json run.jsonl` writes one event per file.
- **Steps it passes through:** argument parsing → folder scan → ExifTool batch read → planner (name format, same-second suffixes) → output and log. There is no write step yet: no rename code ships until V1 passes.
- **Deploy and rollback:** GitHub Actions builds the wheel and sdist on a tag and publishes to TestPyPI through trusted publishing. It's installed with `pipx` on Windows, macOS and Linux. Rollback means `pipx install photo-rename==<previous>`, practised once.
- **Monitoring:** for a CLI, "monitored" means the outcome is visible to whoever runs it: the summary, exit codes and JSON log. Two failures are injected deliberately: a truncated JPEG, and ExifTool removed from PATH. Each must give a non-zero exit and a clear message, and CI checks both.
- **Who can reach it:** the owner only, via TestPyPI. It's read-only by design.

Exit check (V0) is in §6.

## 5. Phases

- **Phase 1: Safe apply (correct dates, safe writes)**
  - **Unlocks:** `--apply` and `undo` in a release, and running on real folders.
  - **Depends on:** V0 and the defaults in §3. The corpus collection starts in Phase 0.
  - **Tasks** (the ones that would force the most rework if wrong come first):
    1. Draft the name-format spec and journal schema. The journal records `schema_version`, run id, tool version, and per rename `{src, dst, state}`.
    2. Planner. Build the whole old→new mapping before any write. Detect name clashes within the folder and against files already on disk. Compare names without regard to case and Unicode form (macOS stores accented names differently). Number same-second photos the same way every run. Handle rename cycles (A→B while B→A) and case-only renames through temporary names. Skip files already at their target name, so a re-run does nothing. Group sidecars.
    3. Date reader, checked against the V2 corpus.
    4. Write step. Write and fsync the journal, rename each file without overwriting, mark it done. Add `undo <journal>` and resuming an interrupted run.
    5. V1 harness, run in CI on throwaway copies.
    6. Exposure, smallest first: one of the owner's real folders after a full backup, then wider use.
  - **Rollback:** for code, the previous release. For a user's data, `undo` with the journal. Each run's point of no return is deleting its journal; the docs say so.
  - **Exit check:** V1 and V2 pass. The throughput target holds at 10,000 files, for both dry-run and apply.

- **Phase 2: Public release**
  - **Unlocks:** outside users.
  - **Depends on:** Phase 1, V1, V2, and the PyPI name and trusted publisher (§2).
  - **Tasks:**
    1. Freeze version 1 of the name format and journal schema.
    2. Publish to PyPI with trusted publishing and build attestations.
    3. Write the README: dry-run first, how to recover with `undo`, and a supported-format list equal to what V2 passed.
    4. Make `--version` report the ExifTool version.
  - **Rollback:** yank the release. Any 1.x release can still `undo` journals written by earlier 1.x releases.
  - **Exit check:** a clean PyPI install on all three operating systems runs the V0 request, then apply + undo on a throwaway copy, and both trees' hashes match.

## 10. Deliberately deferred
- **Video (MOV/MP4):** pulled forward when users want videos named alongside photos. The QuickTime CreateDate is stored in UTC, which needs its own V2 cases.
- **Recursive mode, or sorting into `YYYY/MM` folders:** when requested. Moving files across folders changes the journal model, so V1 runs again.
- **`--format` templates and `--shift` / `--tz`:** on the first request (flip conditions in §3).
- **Standalone binary or bundled ExifTool:** when users without Python or ExifTool (mostly on Windows) block adoption.
- **Pure-Python backend:** if the ExifTool dependency blocks adoption, or the format list turns out to be JPEG only.
- **Working out dates from file modification time by default:** never. It stays opt-in.
- **Parallel reads:** if the throughput check fails on network drives or NAS.
- **Detecting cloud-synced folders (OneDrive, iCloud, Dropbox) and warning:** when a user reports a sync client renaming files during a run, or files-on-demand downloads making reads slow.

The answers that would most change this plan are which formats you need (missing input 1) and whether the tool is personal or public (missing input 2).
