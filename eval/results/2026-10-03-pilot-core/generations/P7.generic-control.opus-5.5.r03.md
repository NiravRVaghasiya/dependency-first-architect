# Architecture and Build Plan: `photo-rename`, a CLI that renames photos by EXIF capture date

> **Context:** The workspace is empty. `README.md` confirms there is no existing code, so this is a new build. Your request was one sentence and the gaps don't change the structure, so I went ahead without asking. Every assumption is marked **[A]** and listed in Section 5.

---

## 1. Summary

- **What:** A command-line tool, `photo-rename`. It renames the photos in a folder to their capture date, for example `IMG_4821.HEIC` → `2024-05-01_14-03-22.HEIC`. The user is one technical person on their own photo library **[A]**.
- **Shape:** One Python package with a pipeline of pure, testable steps: scan → read metadata → choose date → plan → apply. EXIF reading is delegated to **ExifTool**, called once per batch rather than once per file. Renames go through a **two-phase executor with a journal**, so every run can be undone.
- **Key decisions:**
  1. **Preview by default.** Nothing is renamed without `--apply`.
  2. **ExifTool for metadata** rather than a pure-Python EXIF library, because correctness across HEIC and RAW matters more than having no external dependencies.
  3. **Two-phase rename with a journal written and fsynced before the first rename.** Phase one renames to unique temporary names, phase two to the final names. This handles name swaps, case-only renames and crashes, and makes `undo` exact.
  4. **Never guess a date.** Files with no trustworthy capture date are skipped and reported.
  5. **Never overwrite.** Name collisions get deterministic suffixes (`_01`, `_02`).
- **Milestone 1 (about 4–7 developer-days):** JPEG and HEIC in a single folder, with preview, apply, undo and crash detection. CI runs on Windows, macOS and Linux. It is checked on a copy of a real library using a hash manifest.
- **Top risks:**
  - Losing or overwriting a file. POSIX `rename()` silently replaces an existing target.
  - Picking the wrong date tag or timezone.
  - Sidecar and RAW+JPEG pairs drifting apart.
  - ExifTool installation and Unicode filename problems on Windows.

## 2. Context and Goals

- **Problem:** Photos from phones and cameras have names like `IMG_1234` or `DSC0001` that don't sort by time, collide across devices, and say nothing about when the photo was taken. Renaming them by hand doesn't scale.
- **Goals:**
  - Rename every photo that has a trustworthy capture date to a sortable date-based name.
  - Never lose, overwrite or modify file contents.
  - Make every run reversible.
- **Non-goals (v1):**
  - Moving files into date folders.
  - Editing or writing EXIF.
  - Deduplication.
  - A GUI.
  - Network shares and cloud storage.
  - Dating video files on their own merits. Videos are only renamed as companions to a photo, for example a Live Photo `.MOV` (Milestone 2).
  - Timezone normalisation.
- **Success measures:**
  - 0 files lost or overwritten, both in tests and in real use.
  - `undo` restores 100% of original names.
  - At least 99% of files that have EXIF get the date a reference reader reports.
  - A 10,000-file folder is processed in under 60 s **[A]**.

## 3. Drivers, Requirements, and Constraints

**Ranked quality attributes**

| # | Attribute | Measurable target | Why it matters |
|---|---|---|---|
| 1 | Data safety | 0 lost or overwritten files under fault injection (crash after any rename N). `undo` round-trip leaves the content hash manifest and the name set identical to before. | Photos can't be replaced. One overwrite destroys trust in the tool. |
| 2 | Date correctness | ≥99% agreement with `exiftool -DateTimeOriginal` on a real corpus of at least 2,000 files from at least 3 devices. 0 files renamed from `ModifyDate` or filesystem time unless the user opts in. | A wrong name is worse than no rename, because it misleads silently. |
| 3 | Predictability | Preview is the default. The same input always gives the same plan. Running again on renamed output gives an empty plan. | The user has to be able to trust what will happen before it happens. |
| 4 | Portability | CI passes on Windows (NTFS), macOS (APFS, case-insensitive) and Linux (ext4) **[A]**. | Filesystem behaviour differs on exactly the operations this tool performs. |
| 5 | Performance | 10,000 JPEGs in under 60 s on a laptop SSD **[A]**. | Starting a new process per file on Windows costs roughly 100 ms, so a naive design takes about 17 minutes. |

**Key functional requirements:**
- Preview, apply, and undo.
- Deterministic collision suffixes.
- A skip report that gives a reason for each skipped file.
- Optional recursion, renaming within each directory and never moving files across directories (Milestone 2).
- Sidecar and pair handling (Milestone 2).

**Constraints:**
- One developer **[A]**.
- Python 3.11+ **[A]**.
- ExifTool 12.24 or later installed on PATH. Earlier versions have the CVE-2021-22204 code-execution bug.
- No budget or compliance constraints.

**Hard parts**
1. **Rename safety.** POSIX `rename()` overwrites silently. Windows `os.rename` fails if the target exists. Case-only renames (`a.JPG` → `A.JPG`) behave differently on case-insensitive filesystems. Swaps and cycles (A→B while B→A) need temporary names. A crash midway must be recoverable.
2. **Choosing the right date.** The options are `DateTimeOriginal`, `CreateDate` and `ModifyDate`. Some files contain zero dates (`0000:00:00 00:00:00`), and cameras with a reset clock record 2000-01-01. EXIF stores no timezone unless `OffsetTimeOriginal` is present. QuickTime dates are stored in UTC.
3. **Companion files.** `IMG_1234.CR2`, `IMG_1234.JPG`, `IMG_1234.xmp`, `IMG_1234.AAE` and a Live Photo `IMG_1234.MOV` only stay linked if they are renamed together.
4. **ExifTool on Windows.** It needs the `-charset filename=utf8` option and an argument file to handle Unicode paths, and the argument file also avoids the 32k-character command-line limit.

## 6. Architecture Overview

```
                 ┌──────────────────────── photo-rename (one Python process) ───────────────────────┐
 user ──argv──►  │ cli ─► scanner ─► metadata ─────► dates ─► planner ─► report (preview / --json)  │
                 │                    │                          │                                 │
                 │                    │ subprocess,              └─► executor ◄─► journal          │
                 │                    │ arg list, no shell             │              │            │
                 └────────────────────┼────────────────────────────────┼──────────────┼────────────┘
          trust boundary ─ ─ ─ ─ ─ ─ ─│─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─│─ ─ ─ ─ ─ ─ ─ │─ ─ ─
                               exiftool (external,       photo folder (rename only)   <folder>/.photo-rename/
                               parses untrusted files)                                 journal-*.jsonl
```

Everything up to and including `planner` is read-only and deterministic. Only `executor` touches the filesystem, and it does so only after `journal` has durably recorded the full plan.

| Component | Responsibility | Owns data | Interface | Technology | Depends on |
|---|---|---|---|---|---|
| `cli` | Parse arguments, wire the pipeline, set exit codes | – | argv → exit code | `argparse` (standard library) | all |
| `scanner` | List candidate files by extension allowlist; skip dotfiles and `.photo-rename/`; find same-stem siblings | `FileRecord` list | `scan(dir, recursive) -> list[FileRecord]` | `os.scandir` | – |
| `metadata` | Read date tags in batches | raw tag dict per file | `MetadataReader.read(paths) -> dict[path, Tags \| Error]` | ExifTool, JSON output | exiftool ≥ 12.24 |
| `dates` | Choose and validate the capture date | `DateResult` | `resolve(tags) -> DateResult` | pure Python | – |
| `planner` | Build the rename plan: targets, suffixes, skips, conflicts | `Plan` | `build_plan(records) -> Plan` (pure function) | pure Python | – |
| `journal` | Write and read the durable run record; reconstruct state | `Journal` files | `write_plan`, `mark_phase`, `load`, `reconstruct` | JSONL + `os.fsync` | filesystem |
| `executor` | Two-phase apply, automatic rollback on error, undo | – (writes through `journal`) | `apply(plan)`, `undo(journal)` | `os.rename` (+ no-replace primitive if S3 says so) | journal |
| `report` | Human-readable table and `--json` output | – | `render(plan \| result)` | standard library | – |

## 7. Component Details

**`metadata` (hard part 4)**
- Runs one ExifTool process per chunk of 1,000 files:
  `exiftool -json -q -fast2 -charset filename=utf8 -DateTimeOriginal -SubSecTimeOriginal -OffsetTimeOriginal -CreateDate -FileType -@ <utf8 argfile>`.
- The command is built as an argument list with no shell. A timeout of 30 s plus 50 ms per file applies to each chunk.
- Checks the ExifTool version at startup. A missing or old ExifTool exits with code 2 and installation instructions.
- A file ExifTool can't read becomes a per-file `Error` and is skipped. If ExifTool itself crashes or times out, the run aborts **before any rename**. All metadata is read before planning starts.
- It does not interpret dates. That is `dates`' job.
- The `MetadataReader` protocol lets tests use a fake reader. It would also allow a pure-Python reader later.

**`dates` (hard part 2)**
- Precedence is `DateTimeOriginal`, then `CreateDate`, then none. `ModifyDate` is never used, because editing software changes it.
- Rejects zero dates, unparseable dates, dates before 1990, and dates more than 1 day in the future. The bounds are configurable. Each rejected file gets a reason code: `no_date`, `invalid_date` or `suspicious_date`.
- Returns the date, the tag it came from, and the sub-second value, which is used only to order collisions.
- Keeps camera-local time as recorded **[A, Q5]**.

**`planner`**
- A pure function. Each target is `strftime("%Y-%m-%d_%H-%M-%S")` plus the original extension. Colons are not used because Windows forbids them in filenames.
- Files that map to the same target get `_01`, `_02` and so on. Order is sub-second value, then original filename, so the result is deterministic.
- Removes no-ops, where the current name already equals the target, so a second run produces nothing.
- Detects conflicts:
  - A target that matches an *untouched* file. Suffixes are bumped past it.
  - A target that differs only in case from an untouched file.
  - In Milestone 1, any file with same-stem siblings is skipped with reason `has_companions`. This is safe until Milestone 2 adds grouping.

**`executor` and `journal` (hard part 1). Failure and recovery:**
1. The journal records the full plan, including tool version, run ID, directory, and for each entry the source, temporary name (`.pr-<uuid>.tmp`), destination and file identity (`st_ino`, size, `st_mtime_ns`). It is then fsynced.
2. **Phase 1** renames every source to its temporary name, then appends the marker `phase1_done` and fsyncs.
3. **Phase 2** renames every temporary name to its destination, after checking the destination doesn't exist. It then appends `phase2_done` and fsyncs.

How failures are handled:
- **Python exception mid-run** (for example a permission error): stop, automatically reverse the completed steps using the journal, and exit with code 1. The report shows which file failed.
- **Hard crash or power loss:** the next run finds a journal without `phase2_done` and refuses to continue. `photo-rename undo DIR` rebuilds each file's current location by matching file identity at the source, temporary and destination names. This works even for cycles, where matching by name alone is ambiguous. It then reverses the renames.
- **Undo** builds a reverse plan and runs it through the same executor, so undo is also journaled.
- **Fsync cost:** only 3 fsyncs per run, so journaling doesn't threaten the 60 s target.

**`scanner`, `report`, `cli`:** routine.
- Default extension allowlist: `.jpg .jpeg .heic .heif`. Milestone 2 adds RAW formats, `.png`, `.xmp`, `.aae` and `.mov`.
- Exit codes:

| Code | Meaning |
|---|---|
| 0 | Done, or nothing to do |
| 1 | Aborted, no net change |
| 2 | Usage or environment error |
| 3 | Done, but some files were skipped |
| 4 | Incomplete journal found; run `undo` |

**Scale:** not a driver beyond batching ExifTool calls. A plan for 50k files fits easily in memory.

## 8. Data Design

| Entity | Fields | System of record / writer | Lifetime |
|---|---|---|---|
| `FileRecord` | path, stem, ext, size, ino, mtime_ns, siblings | in memory / `scanner` | one run |
| `DateResult` | datetime \| None, source_tag, subsec, status, reason | in memory / `dates` | one run |
| `RenameOp` | src, tmp, dst, identity, group_id | in memory / `planner` | one run |
| `Plan` | ops[], skips[] (path, reason), conflicts[] | in memory / `planner` | one run |
| `Journal` | header {format_version: 1, tool_version, run_id, dir, started_at}, ops[], phase markers | `<dir>/.photo-rename/journal-<UTC timestamp>-<run_id>.jsonl` / only `journal` writes it | kept until the user deletes it; `undo` uses the latest by default |

- **Consistency:** there is no multi-file atomicity at the filesystem level. The journal plus file identity provides recoverability instead.
- **Photo files:** the only change is the rename. Contents and modification times are never touched.
- **Journal location:** next to the photos, so undo still works if the folder is moved. `--journal-dir` overrides this, for example for read-only folders.
- **Format evolution:** `format_version` is hard to change, because `undo` must be able to read old journals. New fields are additive only, and readers ignore unknown fields.
- **Sensitivity:** filenames and paths only. No GPS or other metadata is written to the journal or logs.

## 9. Key Flows

**F1. Preview (default):** `photo-rename ~/Pictures/Trip`
1. Scan finds 1,240 files.
2. ExifTool runs in 2 batches.
3. Dates resolve: 1,198 OK, 30 `no_date`, 12 `has_companions`.
4. The planner produces 1,150 renames and 48 no-ops, with 6 collision groups suffixed.
5. The report prints a table and a summary.
6. Exit code 3. Nothing has been touched.

**F2. Apply:** `photo-rename ~/Pictures/Trip --apply`
1. Steps 1–4 of F1 run again. Nothing is reused from an earlier preview, because the folder may have changed.
2. The journal is written and fsynced.
3. Phase 1, then the `phase1_done` marker.
4. Phase 2, then the `phase2_done` marker.
5. Post-run check: the file count in the folder equals the count before, and every destination exists with the same identity.
6. Exit code 0 or 3.

**F3. Failure: power loss during phase 2**
1. On restart, the next `photo-rename … --apply` finds a journal without `phase2_done`. It exits with code 4 and the message "run `photo-rename undo`".
2. `undo` loads the journal and locates each file by identity: 700 at their destination, 450 at their temporary name, 0 at their source.
3. It builds a reverse plan, journals it, and executes it.
4. All original names are restored. The user can then re-run `--apply`.

**F4. Failure: ExifTool times out on a corrupt file in batch 2**
- The chunk timeout fires and the run aborts with code 1 before planning. No renames have happened.
- The message names the batch and suggests `--exclude`. Milestone 2 adds a per-file retry: bisect the failed batch and skip the offending file.

## 11. Cross-Cutting Concerns

- **Security (Milestone 1):**
  - The main threat is a malicious file attacking ExifTool's parser. Mitigation: require ExifTool ≥ 12.24 and check the version at startup.
  - Command injection is prevented by passing an argument list (no shell) and putting paths in an argument file.
  - Path traversal through metadata is prevented because only parsed date numbers and fixed literals go into filenames. When the `{model}` template field arrives in Milestone 2, it is sanitised to `[A-Za-z0-9_-]`.
  - Every destination must stay in the same directory as its source; this is asserted in `executor`.
- **Reliability (Milestone 1):**
  - Covered by the journal, automatic rollback, crash recovery, the post-run check, and refusing to proceed when a journal is incomplete.
  - Every subprocess call has a timeout. There are no retries in Milestone 1.
- **Observability (Milestone 1):**
  - The report gives a reason for every skip. `--json` produces machine-readable output.
  - `-v` logs the ExifTool command line and timings. The journal doubles as an audit trail.
  - Logs and journals never contain GPS or other metadata.
- **Performance (Milestone 1 measurement, Milestone 2 tuning):** S1 times 10k files. The expected bottleneck is ExifTool I/O. If needed, Milestone 2 runs chunks in parallel with 2–4 processes.
- **Cost:** none to run.
- **Operations:** the author owns it. The README covers the undo procedure, exit codes and the no-concurrent-writers rule. There is no on-call.
- **AI-specific:** not applicable, because there are no model components.

## 14. Testing and Validation Strategy

| Risk | Test type | Where |
|---|---|---|
| Overwrite or loss (driver 1) | Hypothesis properties on the planner; fault injection at every rename step; SHA-256 manifest round-trip | Unit + integration, 3-OS CI |
| Wrong date (driver 2) | Table-driven tests on generated fixtures; S2 corpus agreement check (≥99%) | Unit; manual corpus run at M1 and M2 exits |
| Determinism (driver 3) | Same plan from shuffled input; empty plan on second run | Unit |
| Filesystem differences (driver 4) | Case-only rename, cycles, Unicode names | CI matrix (APFS case-insensitive on macOS runners, NTFS on Windows) |
| Speed (driver 5) | Timing script on 10k files | Manual at M1 exit; CI fails if 1k files take more than 15 s |

- **Blocks a release:** any CI failure, or any manifest mismatch in T9.
- **Test data:** generated fixtures plus a few licensed HEIC and RAW samples. Personal photos are never committed.

## 15. Rollout, Migration, and Rollback

- **Rollout:** there is nothing to migrate.
- **Recommended first use:** run on a copy of the folder, then on the real folder with preview first.
- **Rollback for a run:** `photo-rename undo DIR`. There is no point of no return as long as the journal is kept. After the user deletes `.photo-rename/`, undo is no longer possible, and the README says so.
- **Rollback for the tool:** `pipx install photo-rename==<previous>`. Journal v1 stays readable by every later version.

## 17. Deferred Work and Future Evolution

- **Opt-in fallbacks:** filename patterns such as `IMG_20240501_100000` or WhatsApp names, and modification time. *Trigger:* M3, or earlier if S2 shows many files without EXIF.
- **Timezone normalisation** using `OffsetTimeOriginal`, and handling QuickTime's UTC dates. *Trigger:* Q5.
- **Sorting into date folders**, **standalone video**, **`--stable` suffixes**. *Trigger:* user demand.
- **Extension points:** `MetadataReader` (a pure-Python reader), name templates in `planner`, and the extension allowlist in `scanner`.
- **Deliberate shortcut:** check-then-rename relies on no other process writing to the folder. To pay it back, adopt the OS no-replace primitives (S3 decision).
