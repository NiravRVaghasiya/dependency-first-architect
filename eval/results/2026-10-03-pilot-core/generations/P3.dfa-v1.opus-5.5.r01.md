# BUILD PLAN: CI/CD platform for 50 microservices

## 1. Classification
- **What:** A shared platform that takes each of 50 microservices from commit to build, test and signed artifact, then promotes it through environments into production with progressive rollout and automatic rollback.
- **Type:** Infra. It isn't an AI system, so the AI layer doesn't apply.
- **Dominant constraint:** Correctness. What runs in prod must be exactly what was built, tested and approved. Reliability comes a close second: if the platform is down, 50 teams can't ship, and that includes emergency fixes during an outage.
- **Worst failure:** The platform pushes a bad or tampered artifact, or a broken shared pipeline template, to many services in prod at once. One mistake breaks the whole fleet.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| Consistency vs availability | **Consistency for deploy state**: Git is the single record of what should run where, and changes are serialized through merges. **Availability for CI runners**: runners are interchangeable, and failed jobs retry. | A Git-host outage blocks an urgent production fix for longer than 30 min. Then add an audited emergency path that deploys a known signed digest without Git. This is built in Phase 3 either way, as a fallback. |
| Monolith vs services (the platform itself) | **A few off-the-shelf components connected by thin glue.** The platform is not split into microservices. Pipelines are **shared, versioned templates** that every service pins, not 50 custom pipelines. | More than 20% of services need template overrides. That means the template is wrong: split it by service archetype (stateless API, worker, stateful), not by team. |
| Sync vs async | **Async everywhere.** Pushes trigger CI through webhooks. Deploys are **pull-based**: Argo CD watches Git and brings clusters into line. CI never holds production credentials. | A deploy target can't run an in-cluster agent (VMs, serverless). For that target only, CI pushes using short-lived OIDC credentials. |
| Build vs buy | **Buy/adopt**: GitHub Actions with self-hosted, single-use runners on Kubernetes (actions-runner-controller), Argo CD plus Argo Rollouts, ECR or Harbor, Sigstore cosign, Syft/Trivy, Kyverno, Prometheus/Grafana/Loki/Tempo. **Build only the glue**: templates, onboarding automation, promotion policy. | CI minutes or runner cost exceed 2× the cost of running it ourselves, or an air-gap/compliance rule rules out SaaS. Then move to self-hosted GitLab or Buildkite. Do not build a custom orchestrator. |
| Artifact promotion model | **Build once, promote the same image digest** through dev → staging → prod. Config is injected per environment and never baked into the image. | Practically never. Only if a service has build-time per-environment config that can't be moved out. That service gets fixed; the model stays. |
| Repo layout | **Keep the current polyrepo layout**, plus **one separate GitOps config repo** organized as env/service. | Changes that must land in several services at once exceed about 15% of PRs. Then consider a monorepo. Deferred (see §7). |
| Runtime target | **All 50 run as containers on Kubernetes (EKS)**, one namespace per service. This is an assumption to check in Phase 0. | Any service isn't containerized. It goes into its own track with a push-deploy adapter and does not block the fleet. |
| Runner isolation | **One shared pool of single-use runners**, one job per pod, destroyed after the job. | A service handles regulated data (PCI/PHI). It gets a dedicated pool on separate nodes. |
| (AI) prompt+RAG vs fine-tune | N/A: not an AI system. | — |
| (AI) hosted API vs self-host | N/A: not an AI system. | — |

## 3. Walking skeleton (Phase 0)
**The one real request:** A developer merges a one-line change to `main` in **one real, low-risk, stateless service** (call it `svc-pilot`). Within 15 minutes, `curl https://svc-pilot.prod.internal/version` returns the new commit SHA.

**Tiers it crosses:**
GitHub merge → webhook → GitHub Actions → single-use runner pod → container build and unit tests → push to ECR by digest → CI opens a commit in the GitOps config repo updating the dev digest → Argo CD syncs to dev → smoke test → the same digest is committed for prod (manual approval at first) → Argo CD syncs the prod cluster → Service and Ingress → `/version` responds.

**Deployed, logged, monitored on day zero:**
- **Deployed:** The cluster, Argo CD and the runner controller are created with Terraform and Helm from Git. After bootstrap, Argo CD manages itself (the "app-of-apps" pattern). Nothing is clicked together in a console.
- **Logged:** Runner logs and Argo CD logs go to Loki. Every log line carries the commit SHA and the image digest.
- **Monitored:** Each pipeline run emits one OpenTelemetry trace (a commit → build → push → sync → healthy span chain) to Tempo. Prometheus scrapes Argo CD sync and health metrics. A Grafana dashboard shows lead time for that commit. An alert fires on a failed sync or a degraded app.
- **Deliberately not rigid:** The pipeline is a hand-written workflow file in `svc-pilot`. There are no templates yet; they get extracted in Phase 2, after there's something proven to extract from.

**Exit check:**
1. A merge reaches prod and `/version` returns the new SHA.
2. That run's trace is visible in Tempo, and its lead time shows on the dashboard.
3. One rollback works: `git revert` on the config repo brings back the old SHA in prod within 5 min.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 0: Walking skeleton.** See §3.

**Phase 1: Trust and artifact contract (the foundation everything else relies on)**
- **Unlocks:** Every later pipeline and service can rely on one fixed rule for what an artifact is, who may produce it, and where its deploy config lives.
- **Depends on:** Phase 0, which proves the path from commit to prod for one service.
- **Tasks:**
  1. **Identity and trust model.** CI authenticates to AWS and ECR through GitHub OIDC with per-repo role conditions. Remove every static credential. Argo CD gets read-only Git access.
  2. **Artifact contract.** Images are addressed by digest only, never by a moving tag. There's a required label set (service, commit, pipeline run, owner). Every image gets an SBOM (Syft) and SLSA provenance, and is signed with cosign using keyless signing.
  3. **GitOps repo layout and cluster tenancy.** Write down the `envs/<env>/<service>/` structure as an architecture decision. Each service gets its own namespace, RBAC, and resource quota. Every service will copy this structure, so getting it wrong means 50 migrations later.
  4. **Secrets delivery.** External Secrets Operator reads from AWS Secrets Manager. No secrets in Git or in CI variables.
  5. **Runner pool.** Autoscaling, a minimum pool size, and a build cache keyed on the lockfile hash.
- **Exit check:**
  - `svc-pilot` images are signed and have an SBOM and provenance.
  - Kyverno, in audit mode, reports that all prod images verify.
  - A credential scan finds zero long-lived CI secrets.
  - The repo layout decision is merged.

**Phase 2: Golden path, extracted from 3 pilots**
- **Unlocks:** A reusable, versioned pipeline that onboarding can stamp out.
- **Depends on:** Phase 1's artifact and trust contract, which the template encodes.
- **Tasks:**
  1. **Pilot set chosen for variety.** Hand-build pipelines for 2 more services that differ deliberately from `svc-pilot`: another language, and one **stateful service with a database**. Abstract only after three concrete cases exist.
  2. **Template interface and versioning.** Define inputs and outputs, version with semver, and have services pin a version. Required steps (test, scan, sign, provenance) can't be skipped. This is the widest-impact task here: all 50 services will call this interface.
  3. **Promotion model.** dev → staging → prod using the same digest. Prod accepts only digests that passed staging, enforced by policy.
  4. **Database migration contract.** Migrations follow expand/contract, run as an Argo PreSync job, and a failed migration stops the sync.
  5. **Test-stage tiers.** Unit tests on every PR, integration tests on merge, smoke tests after deploy.
- **Exit check:**
  - All 3 pilots run on template v1.x.
  - A template v1.1 upgrade rolls to the pilots by version bump without breaking any of them.
  - The template has its own contract tests in CI.

**Phase 3: Safe deploys (rollback before scale)**
- **Unlocks:** It becomes safe to put 50 services on the platform, because a bad release is caught and reversed without a human.
- **Depends on:** The Phase 2 golden path, plus per-service Prometheus metrics from Phase 0/2 to judge canaries against.
- **Tasks:**
  1. **Automated rollback.** This comes first because every deploy relies on it. It's a declarative revert path, tested on all 3 pilots.
  2. **Signature enforcement.** Kyverno moves to enforce mode in prod: unsigned or unattested images are rejected.
  3. **Progressive delivery.** Argo Rollouts canaries (for example 5% → 25% → 100%), with Prometheus analysis on error rate and p99 latency, configured by service tier.
  4. **Emergency path.** Deploy a known signed digest without Git, with two-person approval and an audit trail. Plus deploy-freeze windows.
- **Exit check:**
  - A release with an injected fault (5% 5xx) is aborted automatically within 10 min, with at most 5% of traffic exposed.
  - An emergency-path drill passes during a simulated Git-host outage.

**Phase 4: Fleet onboarding in waves**
- **Unlocks:** All 50 services on one platform, and the old CI retired.
- **Depends on:** Phases 2 and 3 proven on the pilots.
- **Tasks** (ordered by how much rework a mistake would force; customer-facing risk is handled separately by putting critical services last):
  1. **Service catalog metadata.** Each repo gets a `catalog.yaml` with owner, tier, SLO and on-call. Every service needs it, and canary analysis and alert routing read from it.
  2. **Onboarding generator.** A PR is generated from catalog metadata: workflow plus GitOps manifests. No hand-made pipelines.
  3. **Wave 1, about 10 services**, chosen to cover every language, runtime and template path. This shakes out template bugs before they spread.
  4. **Wave 2, about 25 services.**
  5. **Wave 3, the rest**, including tier-0 services (auth, payments). They get a longer overlap period and stricter canary thresholds.
  6. **Retire the old CI per service** after 2 clean weeks, and revoke its credentials.
- **Exit check:**
  - 50/50 services deploy through the platform.
  - The old CI is switched off.
  - DORA metrics (deploy frequency, lead time, change failure rate, time to restore) are visible per service.
  - A wave is paused if its change failure rate goes over 15%.

**Phase 5: Platform scale and efficiency**
- **Unlocks:** The platform stays fast and affordable as usage grows.
- **Depends on:** Real fleet load from Phase 4, so the tuning uses measured data rather than guesses.
- **Tasks:**
  1. **Platform SLOs and error budget.** p95 CI queue time under 2 min, a pipeline success rate excluding real test failures, and a deploy-latency SLO.
  2. **Vulnerability gating.** Move from report-only to blocking critical CVEs, with an exception workflow.
  3. **Automated template upgrades.** Renovate keeps all 50 services current with the template.
  4. **Runner cost.** Spot runners with retry, and a remote cache.
  5. **Flaky tests.** Detect and quarantine them.
- **Exit check:**
  - SLOs are met for 30 days.
  - At least 90% of services are on the latest major template version.
  - Cost per pipeline run is tracked and trending flat or down.

**Phase 6: Developer experience surface (the most visible part, so it's built last)**
- **Unlocks:** Self-service for teams.
- **Depends on:** A stable platform and a catalog (Phases 4–5). The portal only displays what already works.
- **Tasks:**
  1. Backstage portal backed by `catalog.yaml`.
  2. Per-PR preview environments.
  3. ChatOps for promote and rollback.
  4. A new-service scaffolder.
- **Exit check:**
  - A new service goes from scaffold to prod in under 1 day with no platform-team ticket.
  - The portal adds no new privileges; every action goes through the same audited APIs.

## 5. Cross-cutting concerns (per phase, from the first commit)

| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|
| 0 | GitHub OIDC to AWS (no static keys); branch protection on the service repo and the config repo; Argo CD has read-only Git access | One OTel trace per pipeline run; Argo CD sync and health metrics in Prometheus; lead-time dashboard; failed-sync alert; logs tagged with SHA and digest | Cluster, Argo CD and runners all built from Terraform/Helm in Git; base images pinned by digest; lockfile-based builds | `git revert` rollback run once; image push and config commit are retry-safe |
| 1 | cosign keyless signing, SBOM, SLSA provenance; Kyverno in audit mode; RBAC per namespace; External Secrets | You can look up digest → commit → pipeline run; runner queue depth and startup time metrics | Pinned toolchain images; provenance attestations; cache keyed on lockfile hash | Single-use runners (a compromised runner can't persist); registry replication/backup; minimum runner pool |
| 2 | Templates force scan, sign and secret-scan (gitleaks) steps; CODEOWNERS on the template repo | Template emits stage durations and classifies failures (infra, test or code); per-service DORA metrics | Semver-pinned templates; prod digest must have passed staging (policy-checked) | New template versions go to pilots first; expand/contract migrations; failed PreSync stops the deploy |
| 3 | Kyverno enforce in prod; emergency path needs two people and is audited | Canary analysis on service SLOs; deploy markers on dashboards; alert when a rollout aborts | Rollout strategies and analysis templates declared in Git, per tier | Automatic abort and rollback; deploy freezes; game day: kill Argo CD mid-sync and simulate a Git-host outage |
| 4 | Each onboarding PR creates a least-privilege identity for that service; old CI credentials revoked at cutover, tracked to zero | Onboarding status dashboard; old vs new pipeline comparison (duration, success) | Every pipeline generated from catalog metadata; Argo out-of-sync alert catches drift | Old pipeline kept as fallback during overlap; wave pause at 15% change failure rate; extra soak time for tier-0 |
| 5 | Critical CVEs block deploys (with exception workflow); Renovate keeps dependencies and templates current | Platform SLOs and error budget; cost per pipeline run | Cache integrity checks; scheduled rebuild-and-compare of sample images | Spot runners with retry; platform disaster-recovery drill (restore Argo CD and registry in a second region within the agreed recovery time); flaky-test quarantine |
| 6 | Portal behind SSO with RBAC and no new privilege path; preview environments in isolated namespaces with no prod data | Portal usage and preview-environment cost metrics | Preview environments use the same templates and digests as real environments | Git/CLI path still works if the portal is down; preview environments expire and get cleaned up automatically |

## 6. AI layer
**N/A.** This is an infra system with no model calls, retrieval or agents. If an AI feature is added later (for example LLM-based triage of failed builds), it gets its own plan, with input guardrails, a cost budget and human approval first.

## 7. Deliberately deferred
- **Monorepo migration.** Pulled forward if changes that must land in several services at once exceed about 15% of PRs.
- **Fully hermetic builds / SLSA L3 (Bazel, isolated builders).** Pulled forward by a compliance requirement or a supply-chain incident.
- **Active-active control plane across regions.** Pulled forward if a single-region outage blocks deploys longer than the recovery time objective, or a disaster-recovery drill misses it.
- **Feature-flag platform (deploy separately from release).** Pulled forward if teams need dark launches beyond what canaries give them.
- **Cross-service contract testing (Pact).** Pulled forward if breakage between services becomes the top cause of failed changes.
- **Merge queues.** Pulled forward if `main` breaks more than once a week in any repo.
- **Smart test selection / ML flaky detection.** Pulled forward if p95 pipeline time or CI cost misses the Phase 5 SLO.
- **Non-Kubernetes deploy adapters (VMs, Lambda).** Pulled forward the moment Phase 0's check finds a service that isn't containerized.
- **Multi-cloud.** Pulled forward only by a contract or regulatory requirement.

## 8. Eval score: 19/20 (graded by me, not independently)
1. **Dependency ordering, 2:** Trust and contract come before templates, templates before safe deploys, safe deploys before fleet onboarding, and the portal last.
2. **Walking skeleton first, 2:** One real commit reaches prod with a trace, a metric and a working rollback, before any templates exist.
3. **Tradeoff gates, 2:** Nine gates, each with a default and a measurable flip condition. The assumptions about Kubernetes and GitHub are stated as gates, not left unspoken.
4. **Blast-radius ordering, 1:** Every phase leads with its contract or interface work. But Phase 4 wave order is a judgment call: it ranks by rework risk and puts critical services last for safety. Reasonable, but arguable.
5. **Security threaded, 2:** A concrete step in every phase, from OIDC on day zero.
6. **Observability from day zero, 2:** Phase 0 has traces, metrics, logs and alerts, and every later phase adds more.
7. **Reproducibility threaded, 2:** Infrastructure as code from Phase 0, then pinning, provenance, generated pipelines and rebuild checks.
8. **Resilience threaded, 2:** Rollback in Phase 0, single-use runners, canaries, game days and disaster-recovery drills spread across phases.
9. **AI layer, 2:** Correctly marked N/A, with a note on what would trigger it.
10. **Deferred work, 2:** Nine items, each with a concrete trigger to pull it forward.

The weakest area is #4, wave ordering in Phase 4. Before Phase 4 starts, revisit it using Phase 2 and 3 data on which template paths fail most.
