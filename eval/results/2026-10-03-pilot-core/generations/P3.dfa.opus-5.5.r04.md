# BUILD PLAN: CI/CD platform for 50 microservices

**What I assumed (the order depends on these):**
- The 50 services already exist and ship through mixed pipelines today (for example, Jenkins). If this is a new build, there are no migration waves: Phase 0 stays the same, the templates are adopted when each service is created, and Phase 5 goes away.
- Most services run on Kubernetes. If many run on VMs or serverless, the pull-based deploy model does not fit them, and a push-adapter phase gets added after Phase 1.
- There is no SOX, PCI or similar audit scope. If there is, V6 turns into an auditor-mapped control with separation of duties.

---

## 1. Classification and constraints
- **What:** a shared build, test, sign and deploy path for 50 services: CI on short-lived runners, an artifact registry, GitOps continuous delivery, policy checks at the cluster door, and gradual rollouts. Each service moves off its old pipeline in waves.
- **Type:** infrastructure plus some glue software. Existing system (brownfield). Not small: about 50 teams depend on it, and it holds production deploy rights.
- **Dominant constraint:** correctness and security of the deploy path. The platform becomes a single point that can affect all 50 services at once.
- **Worst failure:** the shared pipeline gets compromised or broken and pushes a malicious or bad artifact to production across many services at once. Close behind: a platform outage that blocks a hotfix during an incident. V1 guards the first, V5 the second.

**Budgets**

## 3. Tradeoff gates (resolved up front)

**Inherited constraints (not reopened):** current source control and polyrepo layout, current clusters and cloud, current observability stack. Changing any of these costs months across all 50 teams.

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Deploy model / trust boundary (push vs pull) | R3: if CI holds prod credentials and is compromised, the harm cannot be undone | GitOps pull: Argo CD in each cluster. CI's only production-related write is a pull request that bumps the image digest in the environment repo. CI holds no cluster credentials | At least ~90% of services run on Kubernetes | V1 | V1 fails, or the inventory finds a significant set of non-Kubernetes targets → push for those through short-lived per-service OIDC roles, with the same signing |
| Consistency vs availability (policy enforcement during an outage) | R3: running fail-open for even a short window can admit a malicious image | Fail-closed admission for unsigned images. Break-glass path: a KMS key held by two named people, a pull-through registry mirror, full audit. Policy webhook runs ≥2 replicas, and system namespaces are excluded | A break-glass path is fast enough for incidents | V1 (enforcement), V5 (break-glass) | V5 misses the 60-min target → tier-1 services stay on old CI until it passes |
| Build vs buy | R2: moving 50 pipelines again takes weeks | Adopt: the CI that comes with the current source control, open-source Argo CD and Argo Rollouts, a managed registry. Build only the templates and glue | The vendor contract allows it; cost fits | V2, V3 | V3 fails on cost or queue time, or the contract is blocked → run CI on Kubernetes ourselves |
| Runner model | R2: changing the network and identity design touches every pipeline | Short-lived runners: one job per pod, destroyed after the job, autoscaled | Builds need private network access to internal package feeds and staging | V3 | V3 fails → vendor-hosted large runners with private networking |
| Pipeline contract (what all 50 repos adopt) | R2: changing it later means coordinated edits in 50 repos | Versioned, reusable pipeline templates plus a small `service.yaml` per repo. Build once, then promote the same immutable image digest through each environment. Database migrations run as a pre-sync job using expand/contract | 5 representative services fit without forking the template | V2 | V2 fails (more than 1 of the 5 needs a fork) → add extension hooks or a second template family per stack |
| Data-privacy boundary | R3: personal data or secrets leaked into build logs cannot be recalled | No production data or production secrets in CI; synthetic test data; runners have no network path to production data stores; log masking; 30-day log retention | No test needs production data today (inventory confirms) | V1 | A service needs production-like data → a masked or synthetic dataset pipeline, never raw data |
| (Brownfield) migration, coexistence, system of record | R2: reversible per service | Replatform the pipelines only; do not change the services. Exactly one authoritative deployer per service: the old CI before cutover, the environment repo after. The old deploy job is disabled, not deleted. A service's old-CI prod credentials are revoked after 10 successful deploys on the new path; from then on the fallback is break-glass | Two deployers never run at once | V0 rollback rehearsal; per-service cutover checklist | A service's cutover fails twice → it goes back to old CI and into a later wave |

**R1 defaults:**
- Custom platform service vs configuration only → configuration only.
- Deploy status → async: Argo CD reconciles and reports back as a commit status.
- Signing → cosign with a KMS key, an SBOM from syft, and SLSA provenance.
- Policy engine → Kyverno.
- Environment repo layout → one repo, a directory per service, CODEOWNERS per team.
- Template updates → version tags bumped by Renovate.

**N/A:**
- Tenancy model: one organization. Team isolation is handled by Argo CD AppProjects under the deploy-model row.
- AI rows: no AI component.

## 4. Walking skeleton (Phase 0)
**Phase 0 groundwork:**
- Inventory the old CI: deploy jobs, cron and batch jobs, artifact consumers, reused credentials. Mark each CONFIRMED or ASSUMED.
- Baseline per service: build duration, queue time, deploy frequency, change failure rate, time to restore, and CI spend.
- Start the IAM approval, the vendor contract, the budget request and the V6 approver now. They have the longest lead time.

**The real request:**
1. A merge to `main` on one low-criticality, stateless internal service, for example an internal admin API.
2. A short-lived runner builds and unit-tests it.
3. The image is pushed to the registry by digest, with an SBOM and a signature.
4. The bot commits a digest bump to the environment repo: staging first, then prod.
5. Argo CD in the prod cluster syncs it.
6. The Kubernetes rollout runs and the health check passes.
7. A green deploy status appears on the commit.

**Tiers crossed:** source control → CI and runner → registry → environment repo → Argo CD → policy controller (audit mode) → cluster → service.

**Day zero:**
- **Logged:** pipeline, Argo CD and cluster events go to the existing log stack, correlated by commit SHA and run ID.
- **Traced:** CI spans are exported over OpenTelemetry, so one trace covers the whole path.
- **Monitored:** alerts on pipeline failure, Argo CD sync failed or degraded, and runner queue time.
- **Rollback:** `git revert` of the digest bump, after which Argo CD redeploys the previous digest. Fallback: re-enable the pilot's old deploy job.

**Who can reach it:** only the platform team and the pilot repo, protected `main` only, no secrets for pull requests from forks. Admission policy runs in audit mode, scoped to the pilot namespace.

**Exit check V0:**
- A real merge reaches prod with one trace across every tier.
- A deploy and a rollback both succeed through the pipeline.
- An injected sync failure fires an alert.
- First values for queue time, duration and lead time are recorded as BASELINE floors, not as capacity.

## 5. Phases

- **Phase 1: Trust boundary and supply chain**
  - **Unlocks:** onboarding repos other than the pilot.
  - **Depends on:** V0.
  - **Tasks:**
    1. Per-repo OIDC roles, and per-service registry paths that only that repo's `main` identity can write.
    2. Protection on the environment repo: CODEOWNERS, branch protection, bot-only digest bumps.
    3. Argo CD AppProjects and RBAC per team.
    4. KMS-backed signing plus provenance.
    5. Kyverno set to enforce on the pilot namespace.
    6. Secrets from the secret manager, never stored in CI.
    7. Runner network policy: no path to production data stores.
    8. Secret scanning on logs.
    9. Audit logs sent to the SIEM.
    10. Run V1.
  - **Rollback:** policy back to audit mode through a flag; OIDC roles are additive.
  - **Exit check:** V1 passes.

- **Phase 2: Pipeline contract and runner fleet (shadow mode)**
  - **Unlocks:** production waves.
  - **Depends on:** Phase 1, V1.
  - **Tasks:**
    1. Template v1 and `service.yaml`, with the database migration step.
    2. Run them alongside the old pipelines on 5 representative services (mixed languages, one stateful with migrations, one unusual build), deploying to staging only. Prod stays on old CI.
    3. Ring rollout for template versions: pilot → wave → all.
    4. Runner autoscaling and caching.
    5. Retention policies.
    6. Run V2 and V3.
  - **Rollback:** turn off shadow runs; production is untouched.
  - **Exit check:**
    - V2 and V3 pass.
    - A bad template change, injected on purpose, stops at the pilot ring.

- **Phase 3: Wave 1 to production, plus progressive delivery and break-glass**
  - **Unlocks:** wider waves and tier-1 services.
  - **Depends on:** V2, V3.
  - **Tasks:**
    1. Cut over about 8 low-criticality services with the per-service checklist: disable the old job, auto-sync the Argo app, first deploy as a canary with manual promotion, rehearse one rollback.
    2. Add Argo Rollouts canary analysis on request-rate, error and latency metrics.
    3. Build break-glass and the registry mirror.
    4. Staff the platform on-call rotation.
    5. Run V4 and V5.
    6. Close out V6.
  - **Rollback:** per service, re-enable the old job and disable auto-sync. The old CI stays the system of record until cutover.
  - **Exit check:**
    - V4, V5 and V6 pass.
    - Each wave-1 service has at least 3 prod deploys, with change failure rate no worse than its BASELINE.

- **Phase 4: Remaining waves, smallest exposure first**
  - **Unlocks:** decommissioning the old CI.
  - **Depends on:** Phase 3; V4, V5 and V6 before any tier-1 service.
  - **Tasks:**
    1. Wave 2: about 15 medium-criticality services.
    2. Wave 3: about 15 more.
    3. Wave 4: about 10 tier-1 services, 1–2 at a time.
    4. Start each wave only after the previous wave's exit check passes.
    5. Revoke old-CI credentials after each service's 10th successful deploy.
    6. Set platform SLOs and burn-rate alerts once the UNKNOWN targets arrive.
  - **Rollback:** per service, as in Phase 3. Once credentials are revoked, the fallback is break-glass.
  - **Exit check:**
    - All 50 services deploy only through the new path.
    - Lead time measured against the target set by leadership.

- **Phase 5: Retire the old CI**
  - **Unlocks:** one deploy path; old credentials gone.
  - **Depends on:** Phase 4, V7.
  - **Tasks:**
    1. Re-home the non-deploy jobs found in the Phase 0 inventory.
    2. Export and archive the old configurations.
    3. Rehearse restoring one old job from the archive.
    4. Run V7.
    5. Delete the old CI.
  - **Point of no return:** deleting the old CI server and its data, guarded by V7.
  - **Exit check:**
    - V7 passes.
    - No traffic or credential use against the old CI for 14 days.
    - The operational-complexity budget holds.

## 10. Deliberately deferred
- **Developer portal (for example, Backstage):** when platform support requests outgrow the platform team's capacity.
- **Preview environment per pull request:** when contention for staging is measured as a delivery bottleneck.
- **Multi-cluster or multi-region fleet management (ApplicationSets):** when a second production cluster or region exists.
- **SLSA L3 hermetic builds:** when audit scope requires it, or the V1 review flags a provenance gap.
- **Blocking builds on vulnerabilities:** when the false-positive rate from warn-only mode is measured and accepted by the security lead.
- **Remote build cache service:** when V3's duration check fails or comes close to failing.
- **Automated canary for services without standard metrics:** as each service starts emitting request-rate, error and latency metrics.
