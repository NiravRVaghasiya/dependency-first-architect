# BUILD PLAN: `photo-rename`, a CLI that renames a folder of photos by EXIF capture date

## 1. Classification and constraints
- **What:** a local command-line tool. You give it a folder, and it renames each photo to its EXIF capture time (default `YYYY-MM-DD_HHMMSS[-NN].<ext>`). It writes an undo journal, and it previews by default: renames happen only with `--apply`.
- **Type:** software. Greenfield. A small build: one developer, no services, no money, and personal use assumed (see Missing inputs).
- **Dominant constraint:** correctness, meaning no photo is lost and each gets the right name.
- **Worst failure:** a rename silently overwrites another photo. The original is gone for good. On POSIX systems `os.rename` replaces an existing target without warning, and on case-insensitive file systems `IMG_1.JPG` and `img_1.jpg` count as the same name. Close second: many files get renamed to the wrong date with no way back.
- **Build vs buy:** you may not need to build this. `exiftool '-FileName<DateTimeOriginal' -d '%Y-%m-%d_%H%M%S%%-c.%%e' DIR` already covers a one-off job. This plan assumes you want what that one-liner lacks: preview by default, a journal with one-command undo, collision handling that is safe on case-insensitive file systems, and sidecar files kept with their photos.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Data safety | 0 files lost or overwritten; undo restores every name and file hash exactly | ASSUMPTION (basis: renaming must never destroy content; confirm you never want overwrite mode) | V1 |
| Date correctness | 100% agreement with an exiftool reference on files that have a capture date; 0 names built from malformed dates | ASSUMPTION (basis: one wrong date means one misfiled photo) | V2 |
| Throughput | ≤ 60 s for 5,000 photos on a local SSD | ASSUMPTION (basis: only headers are read, a few ms per file) | Phase 1 exit check |

**Missing inputs** (assumptions stated; none changes the phase order):
1. **Audience.** Assumed: you and a few others, installing from a GitHub Release. If this is a public PyPI release, the build is no longer small: add release hardening (see §10).
2. **Formats and devices.** UNKNOWN: which cameras and phones, and which of JPEG, HEIC, or RAW. You supply a sample folder before V2 can run (Phase 1).
3. **Date meaning.** Assumed: the camera's local wall-clock time, with no timezone conversion. If you shoot across timezones and want normalized times, the §3 date-semantics row flips.
4. **Videos.** Assumed out of scope. QuickTime stores `CreateDate` in UTC, which needs separate handling.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Write-safety model | R2. It would be R3 without the seam, because an overwrite is permanent; the preview, journal, and no-clobber seam is built in Phase 0, so a wrong rename can be undone | Rename in place; preview by default; write the journal entry before each rename; never overwrite (check the target case-insensitively and reserve names within the run) | Renaming in place can be made provably reversible on NTFS, APFS, ext4 and exFAT | V1 | V1 fails on any file system → use copy mode on that file system: write renamed copies to a new folder and leave the originals untouched |
| Date semantics | R2. A whole library may be renamed and synced before anyone notices; undo exists but copies made after the run don't follow it | Use `DateTimeOriginal` as written by the camera. Break same-second ties with `SubSecTimeOriginal`, then `-NN`. Ignore `OffsetTimeOriginal` for naming. A file with no valid date is skipped and reported, never guessed | You want the local time where the photo was taken | V2, plus your confirmation of Missing input 3 | You want UTC or home-timezone names → add `--tz`; V2 shows many photos with no date → add opt-in `--fallback mtime` |

**R1 defaults:**
- Language and distribution: Python 3.11+, a wheel built by CI, installed with `pipx`.
- EXIF backend: pure Python (Pillow plus `pillow-heif`) behind a `DateSource` interface. If V2 fails, switch to PyExifTool for the failing formats.
- Naming template: fixed in Phase 0; `--format` comes in Phase 2.
- Journal format: JSON Lines with a `version` field; undo stays readable for every past version.
- Data-privacy boundary: fully local, no network calls. Logs and journal hold only paths, timestamps and EXIF tag names, never GPS data or full EXIF dumps.
- Build vs buy: build (see §1); flips to the exiftool one-liner if you only need a one-off rename.

**N/A:** consistency vs availability, monolith vs services, sync vs async. It is a single local process working sequentially, with no shared state.

## 4. Walking skeleton (Phase 0)
- **Real request:** `photo-rename ~/tmp/copy-of-DCIM` on a disposable copy of about 200 real photos from your phone. It prints a plan (`old → new`, plus skips with reasons). Then `--apply` renames the files, and `photo-rename undo` puts every name back.
- **Steps it runs through:** argument parsing → folder scan (top level only; symlinks not followed) → JPEG `DateTimeOriginal` read → name planner (skips any target that already exists, compared case-insensitively) → renamer with write-ahead journal at `DIR/.photo-rename/<run-id>.jsonl` → summary and exit code.
- **Deploy:** GitHub Actions runs tests on Ubuntu, macOS and Windows; a tag builds the wheel into a GitHub Release; you install that release with `pipx install <release-wheel-url>`, as a user would.
- **Logging and monitoring** (for a CLI, this means the result is visible to whoever runs it):
  - a final summary of renamed, skipped and errored counts, with the run ID;
  - `--log-file` writes JSON Lines, one line per file;
  - exit codes: 0 = clean, 1 = some files skipped, 2 = errors.
- **Rollback:** install the previous release wheel with pipx and confirm with `--version`. On the data side, `undo`.
- **Who can reach it:** only you, and only on disposable copies. Running on originals waits for V1.
- **Exit check V0:**
  - the real folder copy is renamed and undone, and the same run ID appears in the summary, the log and the journal;
  - a release, its install, and a rollback to the previous version all succeed;
  - an injected truncated JPEG and an injected read-only file each show up as a reported error with exit code 2, with no other file affected;
  - wall time and peak memory for the folder are recorded as baselines.

## 5. Phases

- **Phase 1: Safety and date correctness**
  - **Unlocks:** running `--apply` on original folders (V1) and committing to a list of supported formats (V2).
  - **Depends on:** Phase 0 / V0.
  - **Tasks** (widest rework first):
    1. Ask for the sample folder and your answers to Missing inputs 2–4. They take the longest to arrive.
    2. Make the journal crash-safe: write an `intent` record and fsync it before each rename, then a `done` record after. `undo` and `resume` work out the state when an `intent` has no `done`.
    3. Collision policy: compare names case-insensitively; reserve names within the run; add `-NN` suffixes; on file systems with hard links, rename with `link`+`unlink` so it can't clobber, and elsewhere check then rename (single user; race documented).
    4. Parse dates strictly. Accept only `YYYY:MM:DD HH:MM:SS`; reject `0000:00:00` and anything else. Build names from parsed integers, never from raw EXIF strings, so a crafted tag can't inject `../`.
    5. Idempotence: a file whose name is already its target is a no-op, so a second run renames nothing.
    6. Add the date-semantics default from §3, plus reports per skip reason.
    7. Run V1 and V2, then measure the throughput and memory budgets.
  - **Rollback:** reinstall the previous release; `undo` for data.
  - **Exit check:**
    - V1 and V2 pass;
    - 5,000 synthetic files process within the throughput and memory budgets in §1;
    - a second run reports 0 renames.

- **Phase 2: Coverage and ergonomics**
  - **Unlocks:** everyday use on real libraries.
  - **Depends on:** V1 and V2.
  - **Tasks:**
    1. Add support for the formats V2 cleared (HEIC and RAW as found in your sample).
    2. Sidecar grouping: `.xmp`, `.AAE`, and Live Photo `.MOV` files with the same name as the photo move with it, recorded in the journal as one group that is undone all or nothing.
    3. `--format` naming template; `--recursive`.
    4. Long paths on Windows; a progress bar for large folders.
    5. Docs listing the supported formats, linked to the V2 record.
  - **Rollback:** reinstall the previous release; journals from older versions remain undoable.
  - **Exit check:**
    - V1's property suite is re-run with sidecar groups added and still passes;
    - a Live Photo pair survives apply and undo together;
    - `pip-audit` is clean.

## 10. Deliberately deferred
- **Videos** (`.MOV`/`.MP4`, `CreateDate` in UTC): when your folders contain videos you want renamed.
- **Timezone conversion (`--tz`):** when you confirm you need normalized times (§3 flip).
- **Fallback to file modification time:** when V2's report shows a meaningful share of photos without dates.
- **Sorting into `YYYY/MM` folders:** when you ask for it. It turns renames into moves across folders, so V1 must be re-run.
- **Network shares and NAS (SMB):** when you need them. V1 must first run on that file system.
- **Public PyPI release, signing, issue support:** when the audience goes beyond you. The build stops being small, and outside users are exposed only after V1 passes.
- **exiftool backend:** when V2 fails for some format.
- **Writing EXIF metadata:** never planned. The tool only reads metadata and renames files.
