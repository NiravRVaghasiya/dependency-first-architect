# BUILD PLAN: Zero-downtime cloud migration of the on-prem patient scheduling system

**Assumptions** (each one changes the plan if it's wrong):
- **(a)** The scheduling app is self-hosted, either built in-house or a vendor product you run yourselves. If the vendor offers a hosted/SaaS version, see the Build-vs-buy gate.
- **(b)** It's a single relational database behind an app tier, linked to the EHR through an interface engine (Mirth, Rhapsody or Cloverleaf) using HL7 v2 messages: SIU for scheduling, ADT for admissions and patient updates.
- **(c)** The target cloud is one you already have a HIPAA Business Associate Agreement (BAA) with.
- **(d)** The users are schedulers, the call center, clinics and the patient portal.

---

## 1. Classification
- **What:** Moving a live, clinically critical scheduling system (database, app, integrations) from on-prem to the cloud while it keeps serving users.
- **Type:** Mostly infra, with some software work (a routing layer in front of the app, cutover controls, reconciliation tooling).
- **Dominant constraint:** **Correctness, plus compliance.** Bookings must stay exactly right and patient data (PHI) must stay inside HIPAA controls. Availability comes second, and it can't be traded against correctness.
- **Worst failure:** **The two copies of the data quietly drift apart.** An appointment is lost or double-booked, or the EHR gets the wrong SIU message. A patient misses care and nothing alerts anyone. That's worse than a visible outage, because hospitals have downtime procedures for outages but nothing catches silent corruption.

> **Definition of "without downtime" (needs clinical-operations sign-off before Phase 5):** reads (schedule views, availability lookups) never stop. Bookings pause for **≤ 2 minutes** once, at the lowest-volume hour, with users warned in the UI and the call center briefed. Truly zero write pause would mean both systems accepting writes at once, and for a booking system that risks double-booking. That's the worst failure above, so this plan doesn't do it unless the flip condition below is met.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **Consistency vs availability** | **Consistency for writes.** Only one side (on-prem or cloud) accepts bookings at any moment. Authority moves in one controlled, logged step. Reads may come from a replica only while replication lag is under the threshold. | None for writes. If a network split between sites makes the system unavailable longer than downtime procedures can cover, use read-only mode plus paper downtime procedures. Never let both sides accept writes. |
| **Who accepts writes during migration** | **Single writer, moved in a ≤ 2-minute freeze** | Leadership requires literally zero write pause. Then build a write proxy that queues bookings and checks idempotency, which costs about 6–10 more weeks and needs its own rehearsals. |
| **Migration depth** | **Replatform:** same app build, same database engine, on a managed database (e.g., RDS / Azure SQL MI). Users see no UI change and need no retraining. | Database licensing on the cloud is too expensive or the engine is unsupported. Then change engines as a **separate later project**, never in the same cutover. |
| **Monolith vs services** | **Keep the monolith.** The only new piece is a thin routing layer (a reverse proxy plus DNS names) in front of it. | One function (e.g., reminders, or portal availability lookups) needs to scale independently. Split it out after Phase 6. |
| **Sync vs async** | **Async change-data-capture (CDC) replication** for data (AWS DMS / Debezium / GoldenGate, matched to the engine). **Synchronous** writes to whichever side is the single writer. HL7 stays async through the interface engine. | Replication lag p99 > 5 s during the rehearsal window, or CDC can't capture some tables (no primary key, or LOB columns). Then fix the schema or snapshot those tables during the freeze. |
| **Build vs buy** | **Buy** managed infrastructure: managed database, managed CDC, managed load balancer and firewall, the cloud key service. **Build** only reconciliation, diff tooling and the cutover runbook. | The vendor offers a certified SaaS version. Then this becomes a vendor-led data migration, but gates 1–2 and Phases 1, 4 and 5 still apply. |
| **Cloud / PHI boundary** | Your existing cloud with a signed BAA, HIPAA-eligible services only, one region inside the jurisdiction, keys you manage, **no public endpoints**. | The portal needs an internet-facing endpoint. Add a WAF-fronted public tier after a pen test (Phase 3). |
| **Hybrid connectivity** | Dedicated circuit (Direct Connect / ExpressRoute) **plus a site-to-site VPN as failover**. Order it on day 1 because circuits take 6–12 weeks to provision. | The circuit isn't delivered in time. Run Phase 0–1 over a redundant VPN, but **no write cutover over VPN only**. |
| **(AI) prompt+RAG vs fine-tune** | N/A | Not an AI system. |
| **(AI) hosted API vs self-host** | N/A | Not an AI system. |

## 3. Walking skeleton (Phase 0)
**The one real request:** a scheduler opens *"Today's appointments for Dr. X, Clinic Y."* The cloud stack serves it from replicated data, and the answer is checked against on-prem's answer for the same request.

**Tiers it crosses:**
1. Scheduler workstation → hospital DNS, using a new name you control, e.g., `sched.hosp.internal`, that points to a pass-through proxy.
2. Proxy (NGINX/Envoy, on-prem, initially just forwarding) → hybrid link → private load balancer and WAF in the cloud.
3. → The app container, the **same build hash as on-prem**, running in a read-only mode, on ECS/AKS.
4. → Login via SSO federated to hospital AD/Entra, with MFA.
5. → The managed database replica, fed by CDC from the on-prem database. Phase 0 replicates only the *appointment, slot, provider, location and patient-demographics-reference* tables.
6. → The real response goes back to 3 pilot schedulers.

At the same time, the proxy **mirrors** all real read requests of this type to the cloud and compares the cloud's answer with on-prem's. Users always get the on-prem answer, so mirrored traffic has no user impact.

**Deployed, logged, monitored on day 0:**
- **Deployed:** all of it via Terraform and a CI pipeline (landing zone, network, database, app, proxy config).
- **Logged:** OpenTelemetry traces cover proxy → app → database. Logs are structured and stripped of PHI, and go to the hospital SIEM. Who-viewed-which-patient access audit logs go to the same audit store as on-prem.
- **Monitored:** dashboards and alerts for replication lag, cloud vs on-prem diff rate, p95 latency, error rate, and a once-a-minute synthetic check.

**Exit check:** a pilot scheduler's real request gets a correct answer from the cloud in production, with a full trace, a lag metric, and a diff result visible on the dashboard. On-prem is untouched and still the only system accepting bookings.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 0: Walking skeleton** (above)
- Unlocks: proof that the hybrid link, identity, CDC, the app build and observability all work end-to-end.
- Depends on: signed BAA, landing zone, connectivity (VPN acceptable here).
- Tasks, widest first:
  1. BAA and the PHI boundary.
  2. Network and identity federation.
  3. Pass-through proxy and the DNS name.
  4. CDC for the core tables.
  5. Read-only app deploy.
  6. Request mirroring and diffing.
  7. Dashboards.
- Exit: as in §3.

**Phase 1: Data substrate (complete, provable replication)**
- Unlocks: everything after it. Nothing reads from or writes to the cloud database broadly until this is proven.
- Depends on: Phase 0 CDC working on the core tables.
- Tasks:
  1. **Dependency inventory.** Every database, file share, batch job, report, ODBC/thick client, hard-coded IP or hostname, and inbound/outbound interface. This is the widest blast radius, because a consumer you miss breaks at cutover.
  2. Freeze the schema contract (DDL changes only through migrations-as-code during the program).
  3. Extend CDC to the **full schema** and any other databases the inventory finds.
  4. **Continuous reconciliation:** per-table row counts every hour, column checksums every night, and an appointment-level comparison of slots booked per provider per day.
  5. Re-snapshot procedure, tested.
  6. Repoint the thick clients and reports found in the inventory to DNS names you control. They still resolve to on-prem.
- Exit: replication lag p99 < 5 s for **14 consecutive days**, zero unexplained reconciliation mismatches for 7 days, and every inventory item has an owner and a migration path.

**Phase 2: Integration layer in shadow**
- Unlocks: cloud-side HL7/FHIR traffic that can be switched over later.
- Depends on: Phase 1. The cloud data must be trustworthy before you compare messages generated from it.
- Tasks:
  1. Stand up the interface-engine channels in the cloud from version-controlled exports.
  2. **Inbound ADT/MPI (patient index) feeds copied** to the cloud. The cloud processes them, but the replicated data stays authoritative.
  3. Cloud **generates outbound SIU in shadow** (not sent) and compares it field by field with on-prem's real SIU.
  4. FHIR/portal API endpoints, read-only.
  5. Reminder/SMS vendor connectivity tested with a test-only sender.
- Exit: zero outbound SIU differences across all event types (S12–S15, S17, S26) for 7 days, and every interface partner has signed off on the connectivity test.

**Phase 3: Read-path cutover (progressive, reversible)**
- Unlocks: real load on the cloud, and proof that it performs as well as on-prem.
- Depends on: Phases 1–2. Replicated data is proven, and shadow comparisons are clean.
- Tasks:
  1. Lag-gated routing in the proxy: serve reads from the cloud only while replication lag is under 5 s, otherwise fall back to on-prem automatically.
  2. Canary rollout: 5% → 25% → 100% of read traffic, one department at a time, with the emergency department and surgery scheduling last.
  3. Patient-portal availability lookups (pen test first if it's public).
  4. Reports and analytics moved to the cloud replica.
- Exit: 100% of reads served from the cloud for 14 days, p95 latency at or below the on-prem baseline, no stale-read incidents, and automatic fallback exercised at least once in production.

**Phase 4: Rollback path and rehearsals (must be proven before any write moves)**
- Unlocks: the write cutover, because now it can be undone without losing data.
- Depends on: Phase 3 proving the cloud can carry production load.
- Tasks:
  1. **Reverse CDC (cloud → on-prem)**, built and validated in a production-like environment.
  2. Point-in-time restore of the cloud database, actually performed and timed.
  3. Cutover runbook as scripts, with go/no-go criteria and rollback triggers.
  4. **3 full dress rehearsals** on a production-sized copy: freeze → drain → verify → switch authority → reverse CDC → **rollback**.
  5. Game days: kill an availability zone, cut the dedicated circuit, kill the CDC task.
  6. Clinical-operations sign-off on the ≤ 2-minute freeze, the cutover date, and the downtime-procedure standby.
- Exit: 3 rehearsals in a row finish within time (freeze ≤ 2 min, rollback ≤ 15 min, zero data loss confirmed by reconciliation), the dedicated circuit is live, and the sign-off is recorded.

**Phase 5: Write-authority cutover**
- Unlocks: the cloud becomes the system of record.
- Depends on: Phase 4 exit. A proven rollback path is required.
- Tasks, in rehearsed order. This order is dictated by the procedure, not by blast radius.
  1. Change freeze; no other changes allowed, including EHR upgrades or template edits.
  2. Command center staffed (IT, clinical ops, interface team, vendor).
  3. The app shows a "read-only" banner, and in-flight writes drain.
  4. Confirm lag = 0 and checksums match.
  5. Flip the authority flag, so the cloud accepts writes and on-prem becomes read-only.
  6. Start reverse CDC.
  7. Switch outbound SIU to the cloud engine and quiesce the on-prem engine.
  8. Smoke-book a test patient, then release the banner.
  9. Hypercare for 72 h.
- Exit: write freeze ≤ 2 min; booking volume within ±10% of the same hour last week; zero interface NACKs (rejected messages) above baseline; reverse-CDC lag < 5 s; no rollback trigger hit in 72 h.

**Phase 6: Stabilize, replace DR, decommission**
- Unlocks: shutting down on-prem.
- Depends on: Phase 5 stable for 30 days, **and** a replacement DR proven. On-prem is your DR until then.
- Tasks:
  1. Cross-region backup/restore DR with a target RPO ≤ 5 min and RTO ≤ 4 h, tested.
  2. Run reverse CDC for 30 days, then retire it.
  3. Archive on-prem data under records retention and legal hold.
  4. Sanitize media (NIST 800-88) and collect certificates of destruction.
  5. Remove proxy fallback routes.
- Exit: a DR restore drill passes, on-prem is powered off with no consumers left (checked against the Phase 1 inventory), and the risk analysis is updated.

## 6. AI layer
**N/A.** This isn't an AI or agentic system. If AI features come later (e.g., no-show prediction, slot optimization), they're deferred below.

## 7. Deliberately deferred
- **Database engine change (e.g., Oracle → Postgres).** Do it when licensing cost justifies it, as its own project after Phase 6. Never in the same cutover.
- **Splitting the monolith into services.** Do it when one function shows a scaling or release-speed bottleneck after Phase 6.
- **Active-active multi-region.** Do it when an RTO under 1 h is required, or a regional outage causes a clinical incident. It also requires solving the single-writer problem.
- **Truly zero write pause (queuing write proxy).** Build it if clinical leadership rejects the ≤ 2-minute freeze in Phase 4 sign-off.
- **Replacing HL7 v2 with native FHIR integration.** Do it when the EHR vendor or partners require FHIR, or the interface engine reaches end of life.
- **New features** (self-scheduling expansion, waitlist automation, AI no-show prediction): only after Phase 6. Migration and features must not change at the same time.
- **Public portal tier.** Only if the portal must hit the cloud directly from the internet. It then gets a pen test and a WAF in Phase 3.
