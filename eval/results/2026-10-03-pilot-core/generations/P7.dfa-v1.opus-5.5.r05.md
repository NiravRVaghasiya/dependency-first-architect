# BUILD PLAN: `photodate`, a CLI that renames photos by EXIF capture date

> **Before building anything:** if this is a one-off job, ExifTool can already do it:
> `exiftool "-FileName<DateTimeOriginal" -d "%Y-%m-%d_%H%M%S%%-c.%%e" DIR`
> The plan below is for a tool that's safer than that one-liner. It adds a dry-run by default, an undo journal, sidecar-aware grouping, deterministic collision handling and a fixed naming contract. If you don't need those, use the one-liner and stop here.

---

## 1. Classification
- **What:** A local CLI that scans a folder, reads each photo's capture timestamp from EXIF, and renames files to a sortable date-based name.
- **Type:** Software (single-process CLI). Not infra, not AI.
- **Dominant constraint:** **Correctness and data safety.** Speed and scale come second.
- **Worst failure:** **Losing a file or a file's identity without being able to undo it.** This can happen by overwriting on a name collision, by a crash halfway through a batch that leaves a mix of old and new names, or by breaking sidecar links (`.xmp` from Lightroom, `.aae`, Live Photo `.mov`). The second worst failure is **wrong dates applied silently**, from bad timezone handling or falling back to file mtime.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| Consistency vs availability (all-or-nothing vs best-effort batch) | **Consistency.** Plan, then apply, with a write-ahead journal. Stop on the first apply error. `undo` restores the exact original names. | Users with large libraries complain that one bad file stops the run. Then add `--continue-on-error`, which still journals every file. |
| Monolith vs services | **Monolith.** One Python package and one process. | N/A in practice. It would only flip for a background watch-folder daemon or a GUI, both deferred. |
| Sync vs async | **Synchronous and sequential** for everything. | Reading metadata for 10k files takes more than 2 minutes on a network drive. Then parallelise **reads only**. Renames always stay sequential and journaled. |
| Build vs buy (metadata parsing) | **Buy.** ExifTool runs as a subprocess in `-stay_open` batch mode. It covers JPEG, HEIC, RAW (CR2/CR3/NEF/ARW/DNG) and video. **We build** only the planner, the safety layer and the UX. | Install friction ("I don't have ExifTool") becomes the top complaint. Then add a pure-Python backend (`exifread` + `pillow-heif`) behind the same `DateSource` interface, and accept narrower format coverage. |
| Language / distribution | **Python 3.12, installed with `pipx`, dependencies locked with `uv`.** | Non-technical Windows users are the main audience. Then ship a PyInstaller single binary through winget/Scoop, or consider a Go rewrite. |
| **Naming contract** (expensive to reverse: users' libraries end up depending on it) | `YYYY-MM-DD_HHMMSS[_NN].<original ext>`. No colons, so it's legal on Windows. It sorts lexically. The extension keeps its original case. | Real demand for other formats. Then add a `--format` template. The default stays frozen as contract v1. |
| **Time semantics** | Use `DateTimeOriginal` **as the local wall-clock time recorded**, with no conversion. | Multi-camera or multi-timezone trips need correct interleaving. Then add opt-in `--normalize-tz` using `OffsetTimeOriginal`. |
| Missing-date policy | **Skip the file and report it.** Never fall back to mtime silently, because copies reset mtime. | Users ask for it explicitly. Then add opt-in `--fallback=mtime`, tagged as such in the plan and journal. |
| Default mode | **Dry-run by default.** The tool prints the plan, and `--apply` is required to change anything. | Users find it annoying in practice. Even then, keep dry-run as the default and add a config option. |
| In-place vs copy | **In-place rename within the same directory.** Renames are atomic on one filesystem. | Users want to keep the originals untouched. Then add `--copy-to DIR`. |
| Telemetry / privacy | **No network calls at all.** EXIF contains GPS and device serial numbers. | None. This is a hard boundary. |
| (AI) prompt+RAG vs fine-tune | N/A: no AI component. | — |
| (AI) hosted API vs self-host | N/A: no AI component. | — |

## 3. Walking skeleton (Phase 0)
**The one real request:** `photodate rename ./fixture --apply` on a folder holding one real camera JPEG.
**The real response:** `IMG_4021.JPG` becomes `2023-07-14_183205.JPG`. A JSON summary `{"scanned":1,"renamed":1,"skipped":0,"errors":0}` is printed, and the exit code is 0.

**Every tier it crosses:**
1. **CLI parsing** with `argparse` (stdlib; no framework until one is needed).
2. **Scanner:** lists regular files only, top level only, no symlinks.
3. **`DateSource` adapter:** an ExifTool subprocess that reads `DateTimeOriginal`.
4. **Planner:** computes the target name.
5. **Applier:** a **no-replace rename**. On POSIX this is `os.link` then `os.unlink`, which fails atomically if the target exists. On Windows it is `os.rename`, which already fails if the target exists. Filesystems without hardlinks, such as FAT/exFAT on SD cards, fall back to an exists-check plus rename, and the small race this leaves is documented.
6. **Reporter:** a log line plus the summary.

Even the skeleton can never overwrite a file.

**Deployed:** pushing a tag makes GitHub Actions build the wheel and publish `0.0.1` to TestPyPI. A release job then runs `pipx install` on clean **Windows, macOS and Linux** runners and executes the request above against the checked-in fixture.
**Logged:** one structured line per file on stderr (`src`, `dst`, `tag_used`, `action`), with `--log-format json` for machines.
**Monitored:** this is a local tool with no telemetry by design, so monitoring means three things:
- the release smoke job across all three OSes, which fails the release if it breaks;
- stable exit codes: 0 = ok, 1 = partial, 2 = usage error, 3 = aborted, 4 = dependency missing;
- `photodate --version`, which reports both the tool and ExifTool versions.

**Exit check:** on all three OS runners, the installed release renames the fixture correctly, exits 0, and its JSON log line and summary appear in the CI artifacts.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 0: Walking skeleton** (above)
- Unlocks: a real, releasable path to build everything else on.
- Depends on: nothing.
- Exit check: as stated in section 3.

**Phase 1: Safety substrate and contracts**
- Unlocks: running safely on real folders with many files.
- Depends on: Phase 0 proving that reading, planning, renaming and reporting work end to end on all three OSes.
- Tasks (widest first):
  1. **Plan schema v1 as data.** It is JSON, versioned, and made of **groups** of members, even though every group has one member for now. Sidecars arrive in Phase 3, and building groups in now avoids a schema break later. Everything downstream depends on this.
  2. **Naming contract v1 spec plus golden tests.** Collision suffixes `_01`, `_02`… are assigned in a deterministic sort order of (datetime, subsec, original name).
  3. **Batch-wide collision resolution.** Names are deduplicated inside the plan, comparing case-insensitively for NTFS and APFS. Rename chains and cycles (A→B while B→A) are handled with two-phase temporary names.
  4. **Write-ahead journal.** Each entry is fsync'd *before* its rename. It is stored as `.photodate-journal-<ts>.jsonl` in the folder itself, so undo still works if the folder is moved. This comes with `photodate undo` and `photodate resume`.
  5. **Idempotency.** A file whose name already matches its own date, with or without a suffix, is a no-op, so a rerun changes nothing.
  6. **Dry-run plan printer**, shown as a diff-style `old → new` table. This is the default mode.
- Exit check: **Hypothesis** property tests on randomly generated folders prove four things. File count and content hashes are preserved. No overwrite ever happens. `undo` restores the exact original names. A second run is a no-op.

**Phase 2: Date-extraction correctness**
- Unlocks: trusting the dates on real-world, messy files.
- Depends on: Phase 1. A wrong date is only recoverable because of the journal and undo, so the safety substrate must come first.
- Tasks (widest first):
  1. **Tag precedence policy:** `DateTimeOriginal`, then `CreateDate`/`DateTimeDigitized`, then (for video) QuickTime `CreateDate`, which is **UTC by spec**. Videos get a warning in the plan that their time may not line up with the photos' local time. If no tag is found, the file is skipped.
  2. **Strict date validation.** Reject `0000:00:00 00:00:00`, blanks and partial dates. Warn on future dates. Filenames are built **only from the parsed datetime's digits**, never from raw tag text.
  3. **`SubSecTimeOriginal`** is used only to order bursts, not in the name (see deferred).
  4. **Fixture corpus** of real files: iPhone HEIC, Canon CR3, Nikon NEF, Sony ARW, DNG, PNG without EXIF, a stripped JPEG, a corrupt JPEG, and an MP4. Each has a checksum manifest.
  5. **Switch ExifTool to `-stay_open` batch mode**, with a per-file timeout.
- Exit check: every fixture gives the expected date or the expected skip reason. Tests pass with the CI clock set to `TZ=Pacific/Auckland` and `TZ=America/Los_Angeles`, which proves no dependence on the host timezone.

**Phase 3: Grouping and sidecars**
- Unlocks: safe use on Lightroom, iPhone and RAW+JPEG libraries.
- Depends on: Phase 1's group schema and Phase 2's date policy, which decides whose date the group takes.
- Tasks (widest first):
  1. **Grouping rule:** files sharing a stem in the same directory form one group (`.HEIC` + `.MOV` + `.AAE`, `.CR3` + `.JPG` + `.xmp`).
  2. **Group date authority:** the primary image wins. If the members' dates disagree by more than 2 seconds, the plan flags it as a conflict.
  3. **Group-atomic apply:** if any member fails to rename, the members already renamed are rolled back.
  4. **Orphan sidecars**, such as an `.xmp` with no image, are reported and left alone.
- Exit check: on the Live Photo and RAW+JPEG+XMP fixtures, every group gets renamed together. A fault injected on the second member leaves the group fully original.

**Phase 4: Scale and UX**
- Unlocks: everyday use on big libraries.
- Depends on: Phases 1–3 being correct. Speed is optimised only once correctness is locked.
- Tasks (widest first):
  1. **Opt-in `--recursive`**, with each directory treated as its own collision namespace.
  2. **`--continue-on-error`** (the flip of gate 1), still fully journaled.
  3. Memory-bounded streaming plan for more than 50k files.
  4. **Path robustness:** Windows long paths (`\\?\`), Unicode/NFC vs NFD names on macOS, read-only files, network drives.
  5. Progress bar and per-stage timings.
- Exit check: a generated 50k-file corpus (fixed seed) finishes in under 5 minutes on a CI runner. Peak RSS stays under 200 MB. All Phase 1 property tests still pass.

**Phase 5: Harden what has proven stable, and distribute**
- Unlocks: a public 1.0.
- Depends on: Phases 1–4 being stable for at least two minor releases with no schema changes.
- Tasks (widest first):
  1. **Freeze naming contract v1 and plan/journal schema v1 under semver.** Any change from here on is a major version.
  2. Trusted Publishing to PyPI, signed releases (Sigstore) and an SBOM.
  3. Homebrew, Scoop and winget packages.
  4. A `photodate doctor` command that checks the environment, ExifTool version and filesystem capabilities such as hardlink support.
  5. Docs, including the one-liner alternative.
- Exit check: 1.0 is installed from each channel on clean machines and passes the Phase 0 smoke test, plus a kill-mid-run-then-undo test.

## 5. Cross-cutting concerns (per phase, from the first commit)

| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|
| 0 | No `shell=True`. Paths go to ExifTool through an `-@` argfile, so a filename starting with `-` can't be read as an option. No network calls. | Per-file structured log line, JSON run summary, stable exit codes, versions in `--version`. | `uv.lock`, pinned Python 3.12, ExifTool version pinned in CI, three-OS matrix. | No-replace rename from the first commit. Missing ExifTool fails closed with exit 4. |
| 1 | Path containment: every target must be a bare name in the same directory, with no separators and no `..`. Symlinks are never followed. The journal is user-only (0600). | The dry-run plan table is the main visibility tool. Journal entries double as an audit log. | Plan output is byte-identical for identical input because of the deterministic sort. Golden-file tests. | Write-ahead fsync'd journal, `undo`/`resume`, and Ctrl-C finishing the current rename cleanly before stopping. |
| 2 | EXIF values are treated as untrusted. Names come only from parsed digits. Malformed files are fuzzed (`atheris`). ExifTool calls have a per-file timeout. | Each file records which tag it used and whether an offset was present. The summary includes a histogram of skip reasons. | Fixture corpus with a checksum manifest. Tests run under several `TZ` values. | A corrupt or hanging file is skipped and reported; it doesn't abort the batch. |
| 3 | Grouping never reaches outside the scanned directory, and the stem match is exact. | Group report showing members, the date authority and conflicts. | Group fixtures checked in with their expected plans. | Group-atomic apply with rollback of partially renamed members. |
| 4 | Recursion refuses to cross filesystem boundaries or follow symlinked directories. | Progress bar, per-stage timings (scan/read/plan/apply), `--verbose`. | Benchmark corpus generated from a fixed seed. | 5 | Signed artifacts, SBOM, hash-pinned dependencies, Trusted Publishing (no long-lived tokens). | `doctor` command and an opt-in local diagnostic bundle that is never uploaded. | Reproducible wheel builds (`SOURCE_DATE_EPOCH`). | Fault-injection CI that kills the process mid-run, then checks that `undo` restores a byte-identical tree. |

## 6. AI layer
N/A: there is no AI or agentic component. Dates come from metadata, not from inferring them out of image content.

## 7. Deliberately deferred
- **`--format` naming templates.** Pull forward when several users ask for a specific alternative format. Contract v1 stays the default.
- **`--normalize-tz`** using `OffsetTimeOriginal`. Pull forward on reports that multi-timezone or multi-camera ordering is wrong.
- **`--fallback=mtime`.** Pull forward when users explicitly want dates for scans or screenshots without EXIF, and even then only as opt-in and tagged.
- **Sub-second time in names.** Pull forward if burst shooters find `_NN` suffixes too unclear.
- **Sorting into date folders (`YYYY/MM/`) or `--copy-to`.** Pull forward when users want to keep originals or organise rather than just rename.
- **Duplicate detection by content hash.** Pull forward if collision reports show many byte-identical files.
- **Parallel metadata reads.** Pull forward per the sync/async flip: 10k files taking more than 2 minutes.
- **Pure-Python backend or single binary.** Pull forward per the build-vs-buy and distribution flips.
- **Writing or fixing EXIF dates.** Not planned. It changes the tool's risk profile from rename-only to editing file contents, and `exiftool -AllDates+=` already does it.
- **GUI or watch-folder daemon.** Pull forward only with a non-CLI audience. This would also trigger the monolith re-check.
