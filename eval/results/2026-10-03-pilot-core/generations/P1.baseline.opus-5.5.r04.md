# Plan: Customer-Support RAG Chatbot over Help-Center Docs

I don't know your stack, doc platform or volume yet, so this plan is vendor-neutral and lists its assumptions. The questions at the end are what I'd need to make it specific.

---

## 1. Goals & success criteria

**Primary goal:** Answer customer questions correctly from help-center content, cite the source, and hand off to a human when it can't.

| Metric | Target (starting point) |
|---|---|
| Answer correctness (graded on a test set) | ≥ 85% |
| Faithfulness (claims backed by the retrieved docs) | ≥ 95% |
| Retrieval recall@5 (right article in top 5) | ≥ 90% |
| Deflection rate (resolved without a ticket) | Measure the baseline first, then aim for +15–30% |
| Bad-escalation rate (answered when it should have escalated) | < 3% |
| p95 latency to first token | < 2 s |
| CSAT on bot conversations | ≥ the current human-first-response CSAT |

**Non-goals for v1:** account-specific actions (refunds, password resets), multi-turn troubleshooting flows, and anything that needs the customer's own data. These come later, through tools or APIs.

## 2. Architecture

```
Help-center CMS ──► Ingestion ──► Chunk + enrich ──► Embed ──► Index (vector + keyword)
                       ▲                                              │
              webhook / nightly sync                                  ▼
User ──► Chat UI ──► Orchestrator ──► Query rewrite ──► Hybrid retrieve ──► Rerank
                         │                                              │
                         │◄──── Generate answer with citations ◄────────┘
                         │
                         ├──► Guardrails (grounding check, PII, policy)
                         ├──► Escalate to human (ticket + transcript)
                         └──► Logging / feedback / eval
```

### 2.1 Ingestion
- **Sources:** the help-center articles (Zendesk, Intercom, Confluence, Markdown or similar). Optionally add macros or canned replies, release notes, and the public FAQ.
- **Exclude** internal-only articles, drafts, and anything with agent-only notes. Filter on article visibility metadata.
- **Sync:** use a CMS webhook on publish, update or delete, plus a nightly full reconciliation. Deletes must remove chunks from the index.
- **Store metadata per article:** `article_id, title, url, section/category, product, plan_tier, locale, updated_at, visibility`.

### 2.2 Chunking
- Chunk by **document structure** (H2/H3 sections), not fixed tokens. Aim for about 300–800 tokens with a small overlap.
- Add the **article title and section path** to every chunk, e.g. "Billing > Invoices > Downloading an invoice". This helps retrieval a lot.
- Keep numbered step lists and tables intact. Never split a procedure in the middle.
- Optionally, generate a few likely questions per chunk ("hypothetical questions") to improve matching against how customers actually phrase things.

### 2.3 Indexing & retrieval
- **Hybrid search:** dense embeddings plus BM25/keyword search. Keyword search matters for error codes, feature names and SKUs, which embeddings handle poorly.
- **Metadata filters:** locale, product, and plan tier (if known from the session).
- **Query rewriting:** turn the conversation into one self-contained search query, so "how do I do that on mobile?" becomes "how to export invoices in the mobile app".
- **Reranking:** use a cross-encoder or a reranker API to cut about 30–50 candidates down to the top 5–8.
- **Store options:** pgvector if you already run Postgres. Otherwise OpenSearch/Elasticsearch (which does hybrid natively), or a managed vector DB. For help-center scale (usually under 10k articles), pgvector or OpenSearch is plenty.

### 2.4 Generation
- **System prompt rules:**
  - Answer only from the provided context.
  - Cite article URLs.
  - If the context doesn't contain the answer, say so and offer escalation.
  - Never invent steps, prices, policies or timelines.
  - Match the brand's tone and the user's language.
- **Structured output:** `{answer, citations[], confidence, should_escalate, escalation_reason}`.
- **Format:** short answer first, then steps, then links to the full articles.
- **Model choice:** a mid-tier model is usually enough when retrieval is good. Use a stronger model only for hard or low-confidence cases if cost matters.

### 2.5 Guardrails & escalation
- **Escalate when:**
  - retrieval scores are low or confidence is low
  - the user asks for a human
  - the topic is sensitive: billing disputes, legal, security incidents, account deletion, outages
  - the user is frustrated (sentiment), or the same question comes back twice
- **Handoff:** create a ticket with the full transcript, the retrieved articles, and the bot's draft answer, so agents don't start from zero.
- **Prompt-injection defense:** treat retrieved text and user text as data, not instructions. The bot should have no tools that can take actions in v1.
- **PII:** redact card numbers, SSNs and similar data before logging. Set a log retention policy.
- **Grounding check:** optionally run a cheap second pass that checks each claim against the context. It can block the answer or route it to escalation.

## 3. Evaluation (build this before tuning)

1. **Golden dataset (200–500 questions):** take them from real historical tickets and chat logs, and label each with the correct article(s) and a reference answer. Include:
   - common questions (about 60%)
   - long-tail questions (about 20%)
   - questions the docs can't answer, where the right behavior is to escalate (about 10%)
   - adversarial or off-topic questions and prompt injection (about 10%)
2. **Offline metrics:**
   - retrieval: recall@k and MRR
   - generation: correctness, faithfulness, citation accuracy, and whether it escalated correctly
   - Use an LLM-as-judge, calibrated against about 50 cases graded by humans.
3. **Regression gate:** run the eval in CI for any change to prompts, chunking, models or the index. Block a release if a metric drops.
4. **Online metrics:**
   - thumbs up/down
   - "did this resolve your issue?"
   - escalation rate, and whether a ticket gets reopened within 72 hours of a bot answer
5. **Weekly review:** sample about 50 conversations, look at failures, and fix the cause. Most fixes will be **doc gaps**, so send them to the docs team.

---

## 4. Operations

- **Freshness:** monitor ingestion lag and alert if an updated article isn't re-indexed within N minutes.
- **Observability:** trace each request with its query, rewritten query, retrieved chunks with scores, prompt, output, latency and cost. Langfuse, LangSmith or OpenTelemetry all work.
- **Content-gap report:** list questions with low retrieval scores or that escalated, clustered by topic. This is one of the most useful outputs for the docs team.
- **Cost controls:** cache answers to frequent questions (invalidate when the source article changes), set token budgets, and rate-limit per session.
- **Versioning:** version the prompts, embedding model and chunking config. Changing the embedding model means a full re-index.

## 5. Phased rollout

| Phase | Duration (est.) | Deliverables |
|---|---|---|
| **0. Discovery** | 1 wk | Doc inventory, ticket analysis (top intents), golden set v1, metric baselines |
| **1. Prototype** | 2 wks | Ingestion, hybrid retrieval, generation with citations, offline eval passing the targets |
| **2. Internal pilot** | 2 wks | Support agents use it as an "agent assist" draft tool. Collect corrections and expand the golden set |
| **3. Limited external beta** | 2–4 wks | 5–10% of traffic or one product area. Escalation flow live, dashboards, weekly review loop |
| **4. GA** | ongoing | Full traffic, multiple locales, A/B tests on prompts and retrieval |
| **5. v2** | later | Authenticated context (plan, account state), tool use (order status, resets), proactive in-app help |

Starting with **agent assist** (phase 2) is the lowest-risk path. Agents catch bad answers before customers see them, and their edits become training and eval data.

---

## 6. Key risks & mitigations

| Risk | Mitigation |
|---|---|
| Docs are outdated or contradictory | Content-gap report, an owner for each article, and preferring the newer `updated_at` when chunks conflict |
| Made-up policies or prices | Strict grounding prompt, grounding check, always escalating on billing or legal topics |
| Customers stuck in a bot loop | An always-visible "talk to a human" button, and auto-escalation after 2 failed turns |
| Wrong answers for a different plan or product version | Metadata filters, and asking a clarifying question when it's ambiguous |
| Prompt injection via user input | No action tools in v1, input/output filters, red-team cases in the eval set |
| Multilingual quality | Multilingual embeddings, filtering by locale, falling back to translating English docs, and a separate eval per language |

## 7. Open questions

These change the concrete choices above:
1. **Doc platform and volume:** which CMS, how many articles, which locales?
2. **Existing stack:** cloud provider, existing Postgres or Elasticsearch, preferred LLM vendor, any data-residency rules?
3. **Channel:** a web widget, an in-app chat, or inside an existing tool (Zendesk or Intercom messenger)? This decides how escalation works.
4. **Authentication:** will we know who the user is (plan, product), or is it anonymous?
5. **Ticket data:** can we use historical tickets and chats to build the eval set and find the top intents?
6. **Compliance:** PII, GDPR or HIPAA limits on logging and on sending data to an LLM provider?
7. **Ownership:** who owns doc fixes coming from the gap report, and who reviews conversations each week?
