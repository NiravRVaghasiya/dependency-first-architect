# BUILD PLAN: Autonomous GitHub issue triage and resolution agent

## 1. Classification and constraints
- **What:** A GitHub App agent with two jobs. It triages new issues (labels, finds duplicates, asks for missing repro details, suggests an owner). On issues that maintainers opt in, it tries a fix and opens a **draft PR from a fork**. A human always merges.
- **Type:** AI/agentic plus software/infra. The agent itself is new, but it plugs into existing repos, CI, bots and branch protection, so those parts follow brownfield rules. Not a small build: it reads input from outside users, spends money, acts on code, and has R3 trust-boundary decisions.
- **Dominant constraint:** Correctness of what the agent does to code, within strict security limits.
- **Worst failure:** Text planted in an issue, comment, repo file or test output takes over the agent. It then either (a) leaks secrets or private code through sandbox network access, CI, or a public comment, or (b) slips a backdoor into a PR that gets merged and shipped. Neither can be undone. V1, V2 and V3 guard against it.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|

| Monthly spend ceiling | $1,000 through Phase 4. The ceiling for wider rollout is UNKNOWN: the budget owner supplies it before Phase 5 | ASSUMPTION (safety ceiling at canary volume) / UNKNOWN | Phase 1, V7 |
| Cost per merged agent PR | UNKNOWN. The budget owner sets the value of a resolved issue; needed before Phase 4 | UNKNOWN | V7 |
| Triage latency | p90 ≤15 min from issue opened to label/proposal | ASSUMPTION (basis: well under the human time-to-first-label, which is measured in Phase 0) | V5 |
| Throughput | Plan for 3× the peak day of issues. The peak day comes from 90 days of history on the target repos | BASELINE (measured in Phase 0) | Phase 2 |
| GitHub API rate | ≥5,000 requests/hour per installation | REQUIREMENT (GitHub's documented App rate limit) | Phase 2, Phase 5 |
| Availability | No events lost (a polling sweep catches missed webhooks); p99 handled within 1 h | ASSUMPTION (GitHub keeps working for people if the agent is down) | Phase 2 |
| Reviewer burden | Median ≤20 min of maintainer review per agent PR | ASSUMPTION (above this, the agent costs more maintainer time than it saves) | V7 |
| Operational complexity | 3 deployables (agent service, action executor, sandbox pool) plus a queue and Postgres; business-hours on-call | ASSUMPTION | Phase 0 |

**Missing inputs:**
1. **Which repos, and who can file issues.** I assume public repos with outside authors, the worst case. If the repos are internal only, the order stays the same and V3 gets easier.
2. **What "resolve" means.** I assume it means "open a draft PR for human review." If you want auto-merge, that adds an R3 gate and a later phase (see §10).
3. **Languages, build systems and test coverage of the target repos.** Repos without runnable tests can't be checked by V6 and stay triage-only.
4. **Approval from security/legal** to send private code and issue content to a model provider (V4).
5. **Named people:** a budget owner, a security reviewer, and the maintainers of the canary repo.
6. **Whether issues contain personal data** such as reporter emails or logs with PII.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Trust boundary and where credentials live | R3: a leaked secret can't be taken back | The model loop and code execution run in a throwaway sandbox (gVisor/Firecracker) with **no GitHub token and no cloud credentials**. Network is denied by default except a read-only package-registry proxy. All GitHub writes go through a separate **executor** that holds the App key and accepts only typed actions | Sandbox isolation plus a registry proxy is enough for builds and tests | V1 | V1 fails, so the agent produces patches only and tests run only in fork CI |
| Autonomy ceiling | R3: merged bad code ships downstream | The agent never merges, approves, closes PRs, or edits `.github/workflows`. The App has no `workflows`, `administration` or merge rights. Branch protection requires human review | Human review catches what gets past V3 | V2 | Only through the deferred auto-merge gate (§10) |
| Where the agent pushes | R3: a branch in the base repo runs CI with secrets on agent-written code | Push to a bot-controlled **fork org**. PRs come from forks, so CI runs without secrets and first-time-contributor workflow approval stays on | Target repos don't expose secrets to fork PRs | V1 (fork-CI secret probe), plus the Phase 0 inventory | A repo that needs `pull_request_target` with PR code checked out is excluded until fixed |
| Data-privacy boundary (provider) | R3: content sent to a provider can't be recalled | Hosted API under zero-retention, no-training terms. Public repos first. Traces are classified at the repo's visibility (private: access-controlled, 30-day retention) | Provider terms satisfy security/legal | V4 | V4 refused, so private repos use a self-hosted open-weight model or stay out of scope |
| Cross-repo isolation | R3: private content posted on a public issue is a leak | Each run is scoped to one repo: credentials, sandbox clone, a per-repo index partition, and per-repo memory | Scoping holds even when an injection succeeds | V3 (cross-repo cases) | Any cross-repo leak in V3, so one App installation and one deployment per visibility class |
| Triage write autonomy | R2: wrong labels/comments are public, but cheap to fix | Shadow mode, then label classes that pass V5 apply on their own. **Comments always need approval** | Maintainer judgment can be the ground truth | V5 | A class falls below the V5 threshold, so it goes back to suggest-only |
| Build vs buy (fix engine) | R2: prompts and evals carry over; executor and policy are custom | Build a thin tool loop on a hosted model API. In V6, run an off-the-shelf coding agent (e.g. GitHub Copilot coding agent) through the same replay | Custom control over the trust boundary is worth the build cost | V6 comparison | The bought agent meets the V6 bar, passes V1-equivalent controls (no secrets, firewalled network, cannot merge), and costs ≤ ours: buy it for fixes and keep our triage |
| Hosted API vs self-host | R2: the model seam is swappable by config | Hosted frontier model behind a model gateway | Cost and data terms are acceptable | Phase 2 exit (fallback model swapped in by config) | V4 refused or V7 cost fails |

**R1 defaults (cheap to reverse):**
- Sync vs async: async (webhook → queue → workers).
- Monolith vs services: one agent service plus the executor and sandbox pool (the split is forced by the trust-boundary row).
- Consistency: GitHub is the system of record. The agent database holds only derived state; delivery is at-least-once with idempotency keys.
- Prompt+RAG vs fine-tune: prompt+RAG.
- What triggers a fix: a maintainer applies the `agent:attempt` label.
- Orchestration: a single agent with a tool loop.

**N/A:** No migration strategy, cutover or system-of-record transition: nothing moves; the agent joins existing repos as a new contributor.

**Constraints inherited from the repos:** GitHub.com as the platform; each repo's CI, branch protection and label set. Changing any of these needs that repo's maintainers to agree.

## 4. Walking skeleton (Phase 0)
- **Request:** A team member opens a real issue on the disposable repo `<org>/agent-sandbox`. The response is a label applied by the agent, with a trace ID in the audit log.
- **Tiers it crosses:**
  1. GitHub webhook.
  2. Ingress, which checks the HMAC signature and the author allow-list.
  3. Queue (SQS or similar).
  4. Triage worker.
  5. Sandbox: a read-only clone with network denied, which lists the repo's files as context.
  6. Model gateway. Issue text goes in as a delimited data block, never as instructions. Hard caps: 20k tokens and $0.25.
  7. Executor: one typed action, `add_label`.
  8. GitHub API.
  9. OpenTelemetry traces, metrics and alerts.
- **Deploy and rollback:** Terraform plus a GitHub Actions pipeline deploy pinned image digests. Rollback means redeploying the previous digest. There is a global pause flag and the App can be suspended.
- **Monitoring:** Alerts fire on dead-letter queue depth, worker error rate, and cost-cap hits.
- **Who can reach it:** The App is installed **only** on the sandbox repo, and only issues from allow-listed team members are processed. No other repo, outside author, or write path exists yet.
- **Also in Phase 0:**
  - Start the organizational items: App/fork-org approval, the V4 review, and naming the budget owner, security reviewer and canary maintainers.
  - Inventory the target repos (`pull_request_target` usage, branch protection, bots, label sets), marking each finding CONFIRMED or ASSUMED.
  - Baseline 90 days of issue volume and human time-to-first-label from the GitHub API.
- **Exit check (V0):** see §6.

## 5. Phases
- **Phase 1: Defenses and budgets**
  - Unlocks: writes outside the sandbox repo; issues from outside authors.
  - Depends on: V0.
  - Tasks, widest blast radius first:
    1. Trust boundary: network-denied sandbox, registry proxy, no credentials inside, fork org (V1).
    2. Executor policy: typed-action allow-list; approval tied to a hash of the exact action; App permissions file without merge, workflows or admin rights (V2).
    3. Output filter: no external URLs or images and no secrets/PII in agent comments or PR bodies; a blocked-path list (`.github/`, CODEOWNERS, release config); new dependencies flagged for reviewers.
    4. Injection suite in CI (V3).
    5. Full caps, monthly ceiling, and tested kill switch.
  - Rollback: config and image rollback. No external writes exist yet.
  - Exit check: V1, V2 and V3 pass. A forced runaway loop gets cut off at its cap and emits a cost metric.
- **Phase 2: Triage on one canary repo**
  - Unlocks: real triage value; autonomous labels per class.
  - Depends on: Phase 1, V2, V3, and a named canary maintainer.
  - Tasks:
    1. Per-repo index of issues and CODEOWNERS (retrieval).
    2. Model gateway with structured JSON output and a fallback model (model access).
    3. Per-issue state store (memory).
    4. Offline evaluation on historically labeled issues.
    5. Shadow mode on the canary repo: proposals are logged and maintainers grade them.
    6. Turn on label classes that pass V5. Comments stay approval-gated.
  - Rollback: per-repo pause; remove the agent's labels with one script.
  - Exit check: V5 passes. Duplicate-issue retrieval scores hit@5 ≥ 80% (ASSUMPTION) with no results from other repos. Swapping to the fallback model is a config change and stays within 5 points on the triage eval (ASSUMPTION). The polling sweep recovers a dropped webhook.
- **Phase 3: Fix engine, offline only**
  - Unlocks: the decision to commit to a fix canary.
  - Depends on: V1 and Phase 2.
  - Tasks:
    1. Code search in the sandbox (ripgrep plus a symbol index).
    2. Tool loop (read, search, edit, run tests, submit) under the Phase 1 caps.
    3. Replay harness that pins commit, image, model and prompt.
    4. Run V6, including the buy comparison.
    5. Draft-PR path, tested only against the sandbox repo.
  - Rollback: nothing is exposed; just drop it.
  - Exit check: V6 passes. Every failed attempt is recorded as "could not resolve" with its trace.
- **Phase 4: Fix canary**
  - Unlocks: evidence of what a merged agent PR costs.
  - Depends on: V6, the canary maintainers' agreement, and the budget owner's cost target.
  - Tasks:
    1. Fix attempts run only on issues where a maintainer applied `agent:attempt`.
    2. Draft PRs come from the fork org, and each PR body links its attempt trace.
    3. Measure V7 over ≥50 PRs and ≥4 weeks.
  - Rollback: per-repo pause; a script closes open agent PRs; a monthly-ceiling breach pauses the agent automatically.
  - Exit check: V7 passes, with no V1/V3-class incident in the audit log.
- **Phase 5: Widen, route, learn**
  - Unlocks: more repos, lower cost, gains over time.
  - Depends on: V7, plus V4 for any private repo.
  - Tasks:
    1. Onboard one repo at a time, public first, each after its inventory checklist.
    2. Private repos only after V4.
    3. Routing: a small model for triage, a strong model for fixes.
    4. Feedback loop: maintainer corrections and PR review outcomes enter the eval sets only after review.
  - Rollback: pause per repo; uninstall the App from that repo.
  - Exit check: each new repo runs 2 weeks of shadow triage before going live. Routed triage stays within 2 points of the strong model at lower cost (ASSUMPTION). The eval improves after feedback with no regression.

## 10. Deliberately deferred
- **Auto-merge:** pull forward if one narrow class (e.g. docs fixes) is merged unchanged ≥95% of the time for 3 months in V7 data and a named owner approves. It would need its own R3 gate.
- **Fix attempts without the opt-in label:** pull forward when V7 passes and the budget owner sets a wider spend ceiling.
- **Auto-closing duplicates or stale issues:** pull forward when duplicate precision is ≥95% over a full V5 window.
- **Unapproved triage comments:** pull forward when maintainers approve ≥95% of comments unedited over 4 weeks.
- **Fine-tuning:** pull forward when prompt+RAG stops improving across 2 eval cycles and V4 allows training data use.
- **Multi-agent orchestration:** pull forward when traces show planning causing more than 30% of failed fix attempts.
- **Fixes that span several repos:** pull forward when more than 10% of opted-in issues need changes in more than one repo.
- **Self-hosted model:** pull forward if V4 is refused or V7 fails on cost.
- **GitHub Enterprise Server support:** pull forward when a repo hosted there is in scope.
