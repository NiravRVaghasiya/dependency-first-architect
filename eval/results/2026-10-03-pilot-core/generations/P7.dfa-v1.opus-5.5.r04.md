# BUILD PLAN: `photoname`, a CLI that renames photos by EXIF capture date

## 1. Classification
- **What:** A local command-line tool. It reads the capture date from each photo's metadata and renames the files in place, for example to `2024-07-14_183205.jpg`.
- **Type:** Software. A single-user CLI working on the local filesystem. No server, no network and no AI.
- **Dominant constraint:** Correctness. This tool changes files that can't be replaced, and it may run on thousands of them at once.
- **Worst failure:** Silent data loss. One photo overwrites another when two names collide, or a crash halfway through leaves the folder half-renamed with no way back. A wrong date is the second-worst failure, because the name looks right and nobody notices.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| Consistency vs availability (here: all-or-nothing vs best-effort) | **Plan first, then run.** Build the full rename plan and check it before any file is touched. A write-ahead journal records each rename so a partial run can be undone or resumed. A planning error stops the run with zero renames. | Folders get so large (>200k files) that holding the whole plan in memory is a problem. Then switch to streaming batches, each with its own journal. |
| Monolith vs services | **One package, two internal modules:** `core` (pure logic) and `cli` (I/O and arguments), kept apart from day one. | A GUI, a Lightroom plugin or other library users appear. Then publish `core` as its own package. |
| Sync vs async | **Synchronous and sequential renames.** Metadata is read in one batched `exiftool` process. | Reading 10k files takes more than 30s on a reference SSD. Then parallelize the reads only. Renames always stay sequential and journaled. |
| Build vs buy (metadata parsing) | **Buy: ExifTool**, version ≥ 12.24 so the CVE-2021-22204 fix is included. It is called through `-json -stay_open` batch mode from Python 3.12. It handles JPEG, HEIC, RAW (CR2/CR3/NEF/ARW/DNG), PNG and MOV/MP4, which no pure-Python library covers. | Users won't install an outside program, or a single self-contained binary becomes a requirement. Then move `core` to Rust with `nom-exif`, which is supported because `core` is pure logic with a clear contract. |
| Language / distribution | **Python 3.12**, packaged as a wheel and installed with `uv tool install` or `pipx`. | Same trigger as above (single-binary requirement). Then use Rust or Go. |
| Time semantics (permanent: names last forever) | **Use the camera's local wall-clock time exactly as recorded** (`DateTimeOriginal`). No time-zone conversion. `OffsetTimeOriginal` is logged but not applied. | A meaningful number of users have multi-time-zone sets that sort wrongly. Then add opt-in `--normalize-tz=UTC`. Never make it the default, because that would silently change names. |
| Name format (permanent: changing it means renaming everything again) | **`YYYY-MM-DD_HHMMSS[_NN].<original ext>`.** It sorts correctly, contains no colons (so it is safe on Windows) and keeps the original extension's case. | Users ask for other layouts. Then add a `--format` template, but the default never changes. |
| Files with no EXIF date | **Skip them and report them.** File modification time is never used silently, since it is often the copy date rather than the capture date. | Users ask explicitly. Then offer opt-in `--fallback=mtime`, with the date source shown in the report. |
| Default mode | **Dry run.** Nothing is renamed without `--apply`. | None planned. This is a safety feature. A config file could let users opt out per folder later. |
| AI gates (prompt+RAG vs fine-tune, hosted vs self-host) | **N/A.** No model is involved. Dates come from deterministic metadata. | Not applicable. |

## 3. Walking skeleton (Phase 0)
For a local CLI, "production" means the released package installed on a real machine and run against a real folder.

- **The one real request:** `photoname ./fixtures/one --apply` on a folder holding **one real JPEG**.
- **The real response:** the file becomes `2019-03-02_101530.jpg`, the tool prints a summary line (`1 renamed, 0 skipped, 0 errors`), and the exit code is `0`.
- **Every tier it crosses:**
  1. CLI parsing (`argparse`).
  2. Folder scan (sorted, non-recursive, symlinks not followed).
  3. Metadata adapter (one `exiftool -json -DateTimeOriginal` call).
  4. Planner (date → name).
  5. Executor: write the journal first, then do a **no-overwrite rename**. On Windows, `os.rename` already refuses to replace an existing file. On POSIX, use `os.link` + `os.unlink`, falling back to an existence check plus rename on FAT/exFAT cards, which don't support hard links.
  6. Reporter (stdout summary plus a log file).

  Even this one-file version refuses to overwrite and stops before any rename if anything fails, because overwriting is the worst failure.
- **Deployed:** GitHub Actions builds the wheel on every tag. A CI job installs **that built wheel** with `uv tool install` on Windows, macOS and Linux, then runs the request above on a fixture folder.
- **Logged:** JSON-lines log in the platform log directory (`platformdirs`). Each run has a `run_id`, and each file gets an event: `{path, date, source_tag, target, outcome}`.
- **Monitored:** There is no telemetry on purpose, because photo metadata contains GPS and personal data. "Monitoring" here means three things:
  - Clear exit codes: 0 = ok, 1 = some files skipped, 2 = stopped, nothing changed, 3 = partial run, see journal.
  - A summary at the end of every run.
  - The CI smoke test on the installed artifact on all three operating systems, which fails the release if it breaks.
- **Exit check:** On all three operating systems, the released wheel installed fresh renames the fixture correctly. A log line with a `run_id` exists, a journal file exists, and running the same command again with an existing target file refuses with exit 2 and changes nothing.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 0 — Walking skeleton** (described above)
- Unlocks: a working path from argument parsing to rename, including the no-overwrite guarantee and the release pipeline.
- Depends on: nothing.
- Exit check: as in §3.

**Phase 1 — Date extraction (getting the input right)**
- Unlocks: a trustworthy date for every file. Everything after this assumes it.
- Depends on: Phase 0's metadata adapter and pipeline working end to end.
- Tasks (widest → narrowest):
  1. **The `CaptureDate` data contract.** It holds a naive local datetime, optional sub-seconds, an optional offset, and `source_tag`. The planner, journal and reports all use it, so changing it later would mean rework everywhere.
  2. **Tag priority:** `DateTimeOriginal` → `CreateDate` → `QuickTime:CreateDate` for video. Video dates are UTC by spec, so they are converted and marked.
  3. **Rejecting bad values.** `0000:00:00 00:00:00`, empty strings, dates before 1990 or after now+1 day, and unparseable text all become an explicit `Undated(reason)`. A wrong date is never guessed.
  4. **Format coverage.** A fixture collection with ExifTool sample files plus our own: JPEG, HEIC (iPhone), CR3/NEF/ARW/DNG, PNG, edited JPEGs with stripped EXIF, and a corrupt file.
  5. **Batching.** One `-stay_open` ExifTool process per run instead of one per file.
- Exit check: golden tests pass on all three OSes. Every fixture is marked dated or undated, with the expected `source_tag` and reason.

**Phase 2 — Planner (pure function: files + dates → validated rename plan)**
- Unlocks: a plan that is provably safe for the executor to run.
- Depends on: the Phase 1 `CaptureDate` contract.
- Tasks (widest → narrowest):
  1. **Plan checks.** No two targets match after case-folding (APFS and NTFS ignore case). No target matches an existing file outside the plan. Windows reserved names and path length are checked. Any failure stops the run before a single rename.
  2. **Deterministic collision handling.** If sub-seconds exist, they break ties. Otherwise files get `_01`, `_02`… ordered by (sub-second, original name), so the same input always gives the same output.
  3. **Idempotence.** A file that already has its correct name is a no-op, so running the tool twice changes nothing the second time.
  4. **Cycles and swaps** (a→b, b→a) are found and marked for two-phase renaming.
  5. **Validating every generated name** against a strict regex. Names should only ever come from dates, and this keeps it that way.
- Exit check: property-based tests (Hypothesis) show the plan never maps two files to one name, gives the same result every time, does nothing on a second run, and never targets an existing outside file. This runs over 10k generated folders.

**Phase 3 — Executor hardening and undo**
- Unlocks: safe use on real libraries with thousands of files.
- Depends on: the proven Phase 2 plan.
- Tasks (widest → narrowest):
  1. **Write-ahead journal.** The full plan is written and fsynced (forced to disk) before the first rename. Each completed step is appended and fsynced.
  2. **Two-phase rename for cycles** using unique temporary names (`.photoname-tmp-<run_id>-N`).
  3. **`photoname undo <journal>`** and **automatic resume** after Ctrl-C, a crash or power loss.
  4. **Errors on single files** (permission denied, file locked on Windows) are skipped, recorded in the journal, and the run continues. They never stop the run halfway.
  5. **Companion files.** `.xmp`, `.aae` and Live Photo `.MOV` files with the same name stem are renamed together with their photo.
- Exit check: a fault-injection test kills the process at a random rename step 100 times. After each kill, both `undo` and resume produce a set of `(name, sha256)` pairs identical to the original or the planned final state.

**Phase 4 — User-facing features (the visible part, built last)**
- Unlocks: everyday use.
- Depends on: Phases 1–3 being proven. Each feature is a thin layer over a safe core.
- Tasks (widest → narrowest):
  1. `--json` machine-readable output. Scripts will depend on this format, so it is fixed first.
  2. `--format` template, which feeds into Phase 2's checks.
  3. `--recursive`.
  4. Opt-in `--fallback=mtime`.
  5. Dry-run table output, progress bar, colours.
- Exit check: for every fixture, the dry-run output exactly matches what `--apply` actually does (a test compares them). The README walks through a first run.

**Phase 5 — Distribution hardening**
- Unlocks: installation by people who don't use Python.
- Depends on: Phase 4 having a stable CLI surface.
- Tasks (widest → narrowest):
  1. PyPI publishing through Trusted Publishing.
  2. `photoname doctor`: checks the ExifTool version (≥ 12.24), filesystem capabilities (hard-link support) and log location.
  3. Scoop/Homebrew manifests.
- Exit check: on clean VMs (Win/macOS/Ubuntu), install from public channels, run `doctor` (green), then complete one full rename and undo cycle.

## 7. Deliberately deferred
- **Sorting into date folders (`YYYY/MM/`):** pull forward if users ask for organizing, not just renaming. It needs separate rules for moving across folders and filesystems.
- **Time-zone normalization (`--normalize-tz`):** pull forward when multi-time-zone sorting problems are reported (see gate).
- **Parallel metadata reading:** pull forward if 10k files take more than 30s to read (see gate).
- **Duplicate detection by content hash:** pull forward if collision reports show many files that are actually identical.
- **Single-binary Rust port:** pull forward if requiring an ExifTool install becomes the top reason people can't install it.
- **Separate library package / GUI:** pull forward when a second user of `core` appears.
- **Network and cloud storage (SMB, Google Drive mounts):** pull forward once the journal's guarantees have been checked on network filesystems. Their rename semantics differ.
- **Telemetry:** deferred indefinitely. It would only be considered as opt-in and anonymous, with no metadata at all, because of the privacy risk.
