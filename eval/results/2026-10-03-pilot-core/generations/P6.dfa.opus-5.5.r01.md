# BUILD PLAN: Moving the patient scheduling system from on-premises to the cloud with no downtime

## 1. Classification and constraints
- **What:** Move the hospital's patient scheduling system (app servers, database, batch jobs and interface connections) into a cloud provider without any planned scheduling outage. The data includes patient health information (PHI).
- **Type:** Infrastructure plus software. It's a change to an existing system, not a new build, and it's large: it handles regulated health data, involves several hard-to-reverse decisions and affects clinics, the call center and outside parties.
- **Dominant constraint:** Availability, closely followed by correctness. No booking can be lost or doubled.
- **Worst failure:** During the transition, an appointment is lost, double-booked or silently different between the on-prem and cloud copies. This happens if two databases accept writes at once ("split brain") or if a cutover drops transactions. The result is missed or clashing patient care that nobody notices. Gate V6 guards against this.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|

**Missing inputs** (the first two could change the order of phases):
1. **How the app is built, and who makes it.** I assume a hospital-operated, three-tier system: a browser or thin client, app servers, and one relational database (SQL Server or Oracle). Scheduling messages (HL7 "SIU" messages) go through an on-premises interface engine.
   - If it's a **thick client talking directly to the database**, a new phase is needed before the database move: publish the client through Citrix or virtual desktops near the cloud database.
   - If it's a **vendor product with a vendor-hosted option**, buying hosting from the vendor may replace most of this plan (see the build-vs-buy line in §3).
2. **What "no downtime" means to clinical operations.** If even a ≤ 30 s write pause is unacceptable, the cutover design is re-planned (see the flip condition on the consistency row in §3).
3. Database engine, data size and peak volumes. Phase 1 measures these.
4. Which cloud provider, and whether there is already a landing zone (a pre-configured cloud environment with security guardrails) and a business associate agreement (BAA, the HIPAA contract with the provider).
5. Whether the schedules include 42 CFR Part 2 substance-use programs or state-protected categories (behavioral health, HIV). If so, access rules and logging get tighter.
6. Jurisdiction. I assume US and HIPAA; GDPR or state residency laws would add dependencies.
7. Named people for the cutover go/no-go and decommission approvals.

**Low-risk defaults (easy to reverse):**
- **Build vs buy:** buy. Use the engine's own replication and the hospital's existing monitoring and security log system (SIEM), plus cloud-native monitoring. A vendor-hosted version of the app, if one exists, should be compared before Phase 2.
- **Infrastructure as code:** Terraform.
- **Tracing:** OpenTelemetry.
- **Cutover window:** the lowest-volume window measured in Phase 1. It must avoid month-end and EHR change freezes.

**Not applicable:**
- Monolith vs services, and sync vs async: no re-architecture during the move. HL7 stays asynchronous through the existing interface engine.
- AI decisions: there is no AI component.

## 4. Walking skeleton (Phase 0)

Phase 0 is the thinnest real path through every target tier, run once in production with test data before anything else is built.

- **The real request:** An allow-listed IT scheduler, on a hospital workstation, books an appointment for the hospital's designated **test patient** on a **test resource** (e.g. "ZZTEST CLINIC", so no real slot is used). The request goes through one cloud app node.
- **The real response:**
  - The booking is confirmed.
  - The HL7 scheduling message reaches the EHR on the test patient's record.
  - The test rows appear in the cloud database.
- **Tiers it crosses:**
  1. Workstation
  2. Internal cloud load balancer (allow-list)
  3. Cloud app node (same build as on-prem)
  4. VPN link
  5. On-prem primary database (the system of record)
  6. On-prem interface engine
  7. EHR
  8. A filtered change-capture feed carrying only test-patient and test-resource rows
  9. Cloud database instance (schema only, plus test rows)
- **Deployed:** Infrastructure via Terraform through the pipeline. The app node image is built from the current release.
- **Logged:** Logs and traces go to the SIEM and a monitoring workspace inside the PHI boundary.
- **Monitored:**
  - A synthetic test-patient booking runs every 5 minutes.
  - Alerts on link status, replication lag and errors on the app node.
- **Rolled back:** Remove the node from the load-balancer pool and drop the change-capture feed. The on-prem path is never changed.
- **Who can reach it:** Only allow-listed IT accounts with MFA. No real PHI reaches cloud storage, because the change-capture filter passes test IDs only. A scan confirms zero rows from other patients. The BAA and security review must be in hand first (§2).

**Exit check (V0):**
- The test booking succeeds, with one trace across every tier.
- A deploy and a rollback succeed through the pipeline.
- Cutting the change-capture feed or the app node fires an alert.
- First values are recorded as baselines: link round-trip time, booking latency through the cloud node, and lag of the filtered feed. These are a floor measured at near-zero load, not a measure of capacity.

## 5. Phases

- **Phase 1: Discovery, baselines and PHI controls**
  - **Unlocks:** Real PHI in the cloud (after V2), the choice of which tier moves first (V3), and the cutover spec inputs (V1).
  - **Depends on:** V0.
  - **Tasks:**
    1. Order the circuits if not done already (they have the longest lead time).
    2. Build the dependency inventory from four sources: 30 days of database connection audits, network flow logs, the interface engine's route list, and the job scheduler. Mark each item CONFIRMED and give it an owner (V1).
    3. Through the existing change process, add performance monitoring (APM) to the on-prem app. Baseline latency, peak throughput, the lowest-volume window and current recovery figures.
    4. Run the latency-tolerance test (V3).
    5. Obtain the vendor's support and licensing statement.
    6. Get the definitions from clinical ops and the CIO: "no downtime", RPO/RTO and availability target.
    7. Update the HIPAA risk analysis, apply PHI controls and run a penetration test (V2).
    8. Ask third parties to allow-list the cloud outbound IPs.
  - **Rollback:** Nothing on-prem changes beyond adding monitoring, which is removed through the change process if needed.
  - **Exit check:** V1, V2 and V3 pass. The RTO/RPO targets are in hand.

- **Phase 2: Full replica and read-only consumers**
  - **Unlocks:** Fidelity and capacity evidence, and moving read-only workloads off the on-prem system.
  - **Depends on:** V2. Starts after V1 is drafted.
  - **Tasks:**
    1. Remove the Phase 0 change-capture feed.
    2. Set up the engine's own replication to the cloud. On-prem remains the system of record; copying runs on-prem → cloud.
    3. Start daily reconciliation (V4).
    4. Run the load test on an isolated copy of the database restored inside the PHI boundary (V5).
    5. Move read-only consumers to the cloud replica one at a time, lowest-risk first (e.g. reporting ETL first, the data warehouse last). Each move is a DNS or connection-string change.
  - **Rollback:** Point consumers back to on-prem and drop the replica.
  - **Exit check:**
    - V4 and V5 pass.
    - Each moved consumer's output matches its last on-prem run (row counts and totals).

- **Phase 3: App tier in the cloud, one clinic at a time** (if V3 passed)
  - **Unlocks:** Real users on cloud app nodes before the database switch.
  - **Depends on:** V3, V1, Phase 2, and third-party allow-listing done.
  - **Tasks:**
    1. Scale cloud app nodes into the pool. They still use the on-prem primary.
    2. Move users in waves by load-balancer weight: IT, then one low-volume clinic, then groups of clinics, then the call center last.
    3. Repoint any app-originated feeds as each wave goes.
    4. Copy the batch jobs to the cloud and keep them disabled.
    5. Run the circuit-failover drill (V7, part 1).
  - **If V3 failed:** This phase runs copied ("shadow") read traffic against the cloud app and replica only. The real move happens in Phase 4.
  - **Rollback:** Per wave, shift load-balancer weight back to the on-prem nodes. The system of record stays on-prem.
  - **Exit check:**
    - Each wave holds p95 latency within budget for 5 business days, compared with the on-prem nodes.
    - No increase in HL7 errors or backlog.

- **Phase 4: Database primary switch (the cutover)**
  - **Unlocks:** The cloud becomes the system of record.
  - **Depends on:** V4, V5, V6 and V7 passed. The circuits are live. Go/no-go sign-off from the named approvers.
  - **Tasks:**
    1. Freeze schema changes and pause the batch jobs.
    2. Confirm replication lag is within threshold.
    3. Drain writes and switch roles, so the cloud is primary.
    4. Fence the old primary so it cannot accept writes: set it read-only and revoke the app's write access. Verify a write attempt is rejected.
    5. Start copying cloud → on-prem.
    6. Drain the remaining on-prem app nodes.
    7. Enable the batch jobs in the cloud.
    8. Run a test booking end to end and reconcile.
    9. Hold heightened monitoring for 72 h, with downtime procedures staffed on standby.
  - **Rollback:** The rehearsed failback (switch roles back to on-prem) stays available until V8. The point of no return is decommissioning, not this switch.
  - **Exit check:**
    - Reconciliation shows zero mismatches.
    - Write pause and errors within budget.
    - All inventory feeds verified flowing.

- **Phase 5: Stabilize and decommission**
  - **Unlocks:** Exit from the on-prem system and the end of dual-running cost.
  - **Depends on:** Phase 4. V8 before any destruction.
  - **Tasks:**
    1. Run a disaster-recovery test in the cloud: backup restore and a zone failover within the RTO.
    2. Buy reserved capacity (after V5 and the finance budget).
    3. Decide whether to keep an on-prem read-only replica for downtime reports (see §10).
    4. Archive a final backup under the records-retention policy.
    5. After V8, sanitize media to NIST SP 800-88 and keep the destruction certificate.
  - **Rollback:** Failback is possible until V8. After V8 there is no rollback; that is the point of no return.
  - **Exit check:**
    - V8 passes.
    - 30 days of availability against the target set in Phase 1.

## 10. Deliberately deferred
- **Modernizing or refactoring the scheduling app:** pulled forward after V8, as a separate plan.
- **Moving the interface engine to the cloud:** pulled forward if the hospital decides to leave its on-prem data center.
- **Cross-region disaster recovery:** pulled forward if the RTO set in Phase 1 requires surviving the loss of a whole region.
- **A permanent on-prem read-only replica for downtime reports:** decided in Phase 5, and pulled forward if the V7 link-loss drill shows the paper procedures aren't enough.
- **Autoscaling and cloud-native services instead of the moved VMs:** pulled forward if V5 sizing or finance's cost budget shows the moved VMs are too expensive.

I assumed a three-tier, hospital-operated system under US HIPAA. If it's a thick client or a vendor-hosted product (missing input 1 in §1), tell me and I'll re-plan the order of phases.
