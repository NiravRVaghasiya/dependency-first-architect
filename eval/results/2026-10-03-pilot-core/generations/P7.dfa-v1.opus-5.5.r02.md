# BUILD PLAN: `photorename`, a CLI that renames photos by EXIF capture date

## 1. Classification
- **What:** A local, single-user CLI. It reads each photo's EXIF capture timestamp and renames files in a folder to a sortable date-based name. It can show the changes first and undo them afterward.
- **Type:** Software (local CLI). No services, no network, no AI.
- **Dominant constraint:** Correctness. Speed matters very little next to "don't wreck my photo library."
- **Worst failure:** Lost data. That could be a silent overwrite when two photos map to the same name, or a crash halfway through a run that leaves files with mixed names and no way back. Wrong dates are bad but fixable if undo exists. Overwritten files are not. So the plan builds the rename-safety layer before anything else, including date-reading accuracy.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **Build vs buy (the whole tool)** | **Check "buy" first.** `exiftool '-FileName<DateTimeOriginal' -d %Y-%m-%d_%H%M%S%%-c.%%e DIR` already does the core job, and `-testname` gives a preview. Build only for what that one-liner lacks: preview-then-apply as the default, a journal and an `undo` command, guaranteed no-overwrite on every OS, and a `pipx install` with no Perl needed. | If the user is fine running a one-liner without undo, **stop here and ship a documented exiftool alias.** |
| Build vs buy (EXIF parsing) | Buy: pure-Python `exifread`, read-only. It covers JPEG, TIFF-based RAW (CR2/NEF/ARW/DNG) and HEIC in recent versions. All reads go through a small `DateSource` interface. | Formats it can't read reliably (CR3, MP4/MOV, odd RAW) show up in the fixture tests → switch to running `exiftool -j -n` behind the same interface. |
| Language and distribution | Python 3.12, installed with `pipx` from a built wheel. | Users without Python, or a "single binary" requirement → PyInstaller builds per OS, or a Go port (the reading/planning/renaming split makes porting easy). |
| Consistency vs availability (here: all-or-nothing vs best-effort) | **Plan everything, then apply.** The full rename plan is built and checked first. If any conflict can't be resolved, nothing is renamed. Renaming then goes file by file, and each rename is written to the journal *before* it happens. A true transaction across many files isn't possible on a filesystem, so the journal plus `undo` stands in for one. | None expected. Partial success without a journal is never acceptable. |
| Monolith vs services | One process with four internal modules: `scan → read → plan → apply`. Splitting it into services would be absurd. | N/A for this tool. |
| Sync vs async | Fully sequential. | Reading EXIF dominates run time on folders over ~20k files or on network shares → use a thread pool for **reading only**. Renaming always stays sequential. |
| **Naming format (a contract with users' libraries)** | `YYYY-MM-DD_HHMMSS[_NN].<original ext>`. It sorts correctly as text, is legal on Windows (no colons), and keeps the extension's case. `_NN` breaks ties within the same second, ordered by `SubSecTimeOriginal` and then the original filename. | Users ask for other layouts → add a `--format` template (Phase 4). The default never changes once released. |
| Date source and missing dates | Use `DateTimeOriginal`, then `DateTimeDigitized`, then `DateTime`. No timezone conversion: the camera's local time is used as recorded. Files with no usable date are **skipped and reported**, never given a guessed date. | The user explicitly opts in with `--fallback=mtime`. Trips across timezones with several cameras → `--shift ±HH:MM` (deferred). |
| Data-privacy boundary | Fully local. No network calls and no telemetry, ever. | N/A. Nothing in the tool's purpose needs data to leave the machine. |
| (AI) prompt+RAG vs fine-tune; hosted vs self-host | N/A, not an AI system. | — |

## 3. Walking skeleton (Phase 0)
For a local CLI, "production" means **the wheel built by CI, installed with `pipx` on a real machine, run against a real folder (a copy at first).**

- **Request:** `photorename ~/Pictures/trip` (preview is the default) → prints `IMG_0412.JPG → 2024-07-14_093012.JPG`. Then `photorename ~/Pictures/trip --apply` renames the files and writes `.photorename-journal.jsonl` in that folder.
- **Every tier it crosses:** CLI argument parsing → scan (one folder, `.jpg` only, no subfolders) → read (`DateTimeOriginal` from one tag) → plan (the list of renames) → apply (a no-overwrite rename plus a journal entry) → summary report.
- **No overwriting from day one, even in the skeleton:** before each rename, check that the target doesn't exist and refuse if it does. Python's `os.rename` behaves differently by OS: on POSIX it silently replaces an existing file, on Windows it raises an error. So the tool never relies on it alone. The check-then-rename gap is acceptable for a single-user tool and is closed in Phase 1.
- **Deployed:** GitHub Actions runs on Windows, macOS and Linux, builds the wheel and runs the end-to-end test against a 3-photo fixture folder.
- **Logged and monitored:** structured log lines on stderr (`--verbose` for detail). Exit codes: `0` all renamed, `1` some files skipped, `2` aborted. A one-line summary (`renamed=3 skipped=0 conflicts=0`). The journal is the record of every rename. CI fails if any OS is red.

**Exit check:** the wheel built by CI, installed with `pipx` on all three OSes, renames a real 3-photo folder correctly. The journal exists, the exit code is `0`, the summary counts are right, and a second run reports `renamed=0` (already named).

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 0: Walking skeleton** (above).

**Phase 1: Rename-safety layer (plan, apply, undo)**
- *Unlocks:* every later feature can run without risking data, and mistakes like wrong dates become undoable.
- *Depends on:* Phase 0's working end-to-end path and journal.
- *Tasks (widest blast radius first):*
  1. Freeze the `RenamePlan` record: `src, dst, timestamp, date_source_tag, status, reason`. Version the journal format (`"v":1`), because a later `undo` must still read old journals.
  2. Resolve conflicts before applying anything:
     - the target already exists on disk;
     - two files in the same batch map to the same name;
     - names that differ only in case, on case-insensitive filesystems (NTFS, APFS default);
     - swaps and cycles (A→B, B→A), handled by renaming to temporary names first and then to final names.
  3. Write each journal entry and flush it to disk before its rename. Add `photorename undo DIR`, which replays the journal backwards and resumes cleanly after a crash halfway through.
  4. Make reruns safe: files already in the target format are left alone.
  5. Close the overwrite gap: create a hard link that fails if the target exists, then remove the original name. On FAT/exFAT (SD cards), which have no hard links, fall back to check-then-rename.
- *Exit check:* property-based tests (Hypothesis) on generated folders that include collisions, case clashes and cycles:
  - the file count never changes;
  - the set of SHA-256 content hashes never changes;
  - `undo` restores the original names exactly;
  - killing the process at a random rename and running `undo` gets back to the original state.

**Phase 2: Date-reading accuracy**
- *Unlocks:* names you can trust across real camera and phone formats.
- *Depends on:* Phase 1. Every reading failure must be expressible as a `skipped` status with a reason, and any wrong date must be undoable.
- *Tasks (widest blast radius first):*
  1. Tag order and parsing: reject `0000:00:00 00:00:00`, blank or garbled dates and impossible dates. Use `SubSecTimeOriginal` to break ties.
  2. Format coverage: JPEG, HEIC, DNG, CR2, NEF, ARW. Each one either has a passing reference test or is explicitly marked unsupported.
  3. Opt-in `--fallback=mtime`. Every fallback is labelled in the output so it isn't mistaken for a real EXIF date.
- *Exit check:* a fixture set of ≥30 real files from ≥6 devices, plus deliberately corrupted files, matches checked-in expected outputs. Corrupt files produce `skipped`, never a crash.

**Phase 3: Folder traversal and scale**
- *Unlocks:* real libraries: nested folders and thousands of files.
- *Depends on:* Phases 1 and 2 (safe renaming and correct dates for a single folder).
- *Tasks:*
  1. Traversal rules: `--recursive`; never follow symlinks; ignore hidden files and the tool's own journal; skip non-image files.
  2. Interruption: Ctrl-C finishes the current rename, flushes the journal and exits `2`.
  3. Environment failures: a file vanishes mid-run, a file is read-only, permission is denied, or a network drive is slow. Each is handled per file without stopping the run.
  4. Sidecar *detection*: warn when `IMG_0412.HEIC` has a matching `.MOV` (iPhone Live Photo), `.AAE` or `.XMP` file that would be orphaned. Detect and warn only; actually renaming them together is deferred.
  5. A progress bar on stderr for runs over 500 files.
- *Exit check:* a generated 20k-file nested tree takes under 60 s to preview on a laptop SSD. A Ctrl-C test at a random point leaves a journal that `undo` fully reverses.

**Phase 4: User-facing surface (leaf work)**
- *Unlocks:* customization and nicer output.
- *Depends on:* the frozen naming contract and stable behaviour from Phases 1–3.
- *Tasks:*
  1. A `--format` template, checked so it can only produce legal filenames.
  2. `--json` plan output for scripting.
  3. A coloured preview table and a `--yes` flag.
  4. Shell completions and a man page.
- *Exit check:* the CLI's output is snapshot-tested, invalid templates are rejected before any file is read, and a release built from a git tag is published to PyPI.

## 5. Cross-cutting concerns (per phase, from the first commit)

| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|
| 0 | Only parsed date digits ever go into filenames, never raw EXIF text. The target path must stay in the source folder. No network calls. | Structured stderr logs, exit codes 0/1/2, summary counts, the journal as a record of every rename. | Lockfile with hashes (`uv lock`), pinned Python version, CI on 3 OSes, fixture folder in the repo, files processed in sorted name order. | Never overwrite; refuse a missing or unreadable folder; one bad file can't stop the run. |
| 1 | Journal file created with user-only permissions; `undo` refuses journal entries that point outside the folder (a tampered journal can't redirect it). | Every planned rename has a status and a reason code (`conflict_existing`, `case_clash`, `cycle`). | Tie-breaking is deterministic, so the same input always gives the same plan. Property-test seeds are recorded. | Journal written before each rename, resume after a crash, `undo`, temporary names for cycles. |
| 2 | Photos from untrusted sources can carry malicious EXIF: cap the bytes read per file, catch all parser errors per file, and fuzz the reader with mutated JPEG/HEIC files. | Per file: which tag supplied the date; counts per tag; fallbacks clearly labelled. | Reference outputs in the repo; exact `exifread` version pinned. | Corrupt or unsupported files → `skipped` with a reason, never a crash. |
| 3 | Never follow symlinks, so the tool can't be tricked into renaming files outside the folder. | Progress bar; time spent scanning, reading, planning and applying; sidecar warnings. | Traversal order is sorted and identical on every OS, checked by CI. | Ctrl-C safety; vanished, read-only and permission-denied files handled per file; network-share timeouts. |
| 4 | Templates can't contain `/`, `..` or reserved Windows names (`CON`, `NUL`, …). | `--json` output, plus `--log-file` for long runs. | Releases built only from tagged commits; wheel hashes published. | `undo` reads journals from older versions (format version checked, with a migration test). |

## 7. Deliberately deferred
- **Renaming sidecars together** (`.MOV` Live Photo pairs, `.AAE`, `.XMP`). *Brought forward if* Phase 3's warnings fire on more than a few percent of real user folders. With iPhone libraries they will, so this is likely the first thing added after v1.
- **Videos (MP4/MOV dates).** *Brought forward if* users want to rename mixed media. This triggers the switch to exiftool.
- **Timezone shift / `OffsetTimeOriginal` handling.** *Brought forward if* users merge photos from several cameras across timezones.
- **Moving files into `YYYY/MM/` folders.** *Brought forward if* asked for. This is a different, riskier operation (moving across folders) and needs its own safety review.
- **Parallel EXIF reading.** *Brought forward if* Phase 3's benchmark is over 60 s, or on network shares.
- **Standalone binaries (PyInstaller/Go).** *Brought forward if* users without Python ask for it.
- **Duplicate detection by content hash.** *Brought forward if* users report duplicate copies from imports.
- **Writing EXIF, a GUI, config files.** *Brought forward if* there's clear demand. None of them affects whether renaming is safe.
