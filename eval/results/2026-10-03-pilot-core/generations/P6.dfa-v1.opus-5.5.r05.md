# BUILD PLAN: Zero-downtime cloud migration of the hospital patient scheduling system

**Assumptions** (I don't know these about your system yet; Phase 0, task 1 confirms them, and any difference changes the gates below):
- **Database:** a single relational database (SQL Server or Oracle) that is the scheduling system's source of truth.
- **Clients:** some scheduling screens may connect straight to the database rather than going through an application server.
- **Integrations:** run through an existing interface engine (Mirth, Rhapsody or Cloverleaf), using HL7 v2 scheduling messages (SIU) and patient admit/update messages (ADT).
- **Regulation:** US HIPAA. Outside the US, use the local equivalent (GDPR, NHS DSPT, etc.).

---

## 1. Classification
- **What:** Moving a live, critical patient scheduling system (app, database, integrations, batch jobs) from on-premises servers to a cloud tenant while staff keep booking appointments.
- **Type:** Mostly infrastructure, plus software. It's a data migration and traffic cutover, not a rewrite.
- **Dominant constraint:** Correctness, under compliance. A slot is a single physical resource (a provider, room or MRI machine). Even a brief mismatch between the two databases can double-book a patient or lose an appointment. Every step also has to meet HIPAA.
- **Worst failure:** The on-prem and cloud copies silently drift apart, so appointments are lost or double-booked and nobody notices until patients don't arrive or two arrive for one slot. This is worse than an outage: hospitals have paper procedures for outages, but nothing catches silent drift.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **What "zero downtime" means** (set this first, it drives everything else) | Reads never go down. Writes pause for **30 seconds or less**, once, at cutover. During that pause the proxy holds incoming writes and replays them, so users see a slow save, not an error. No dual-primary databases. | Clinical leadership requires literally no write pause → active-active with conflict resolution. That's much more costly and riskier, so it needs its own plan. |
| Consistency vs availability | **Consistency first for bookings.** There is one writable database at any moment. The cloud database is synchronously copied across availability zones. If the network splits, clinics get read-only cached schedules and fall back to the hospital's existing paper downtime procedures. | Sites with unreliable links (e.g. rural clinics) need to book while offline → add site-local tentative bookings that reconcile later, but only for resources not shared across sites. |
| Migration method | **Change data capture (CDC), one database writing at a time.** The on-prem database is the primary and streams every change (Debezium / AWS DMS / GoldenGate, or SQL Server replication) to a cloud replica. After cutover, the stream is reversed (cloud → on-prem) to allow rollback. **The application never writes to both databases.** | None. Having the application write to both is ruled out for a patient-safety system. |
| Cutover granularity | **One switch of the writable database** for everything. Read traffic, integrations and batch jobs move earlier, one consumer at a time. | The Phase 1 dependency map shows the data splits cleanly by site, with no shared providers, rooms or equipment → cut over site by site. |
| Rehost vs replatform vs re-architect | **Rehost the app tier** (same OS and binaries on cloud VMs). **Move the database to a managed service running the same engine** (RDS / Azure SQL Managed Instance). No code changes during the migration. | The vendor won't support the managed database, or a feature the app needs is missing → run the same engine on cloud VMs instead. |
| Monolith vs services | **Keep the monolith as it is.** The only new part is a strangler proxy in front of it. | The system has run stably in the cloud for 2 quarters and one part (e.g. reminders) needs to scale on its own → extract that part behind the proxy. |
| Sync vs async | **Booking stays synchronous** against the writable database. **Integrations stay asynchronous**: outbound SIU and ADT go through interface engine queues, and SMS reminders run as queued jobs. | Phase 2 measures p95 clinic → cloud booking time above **300 ms** → move the client tier next to the database (see next row). Don't make booking asynchronous. |
| Chatty client placement | Clinic workstations reach the cloud app over private links. | Phase 2 shows a thick client making hundreds of database round trips per screen, so screens get noticeably slower → serve that client through VDI/Citrix hosted in the same cloud region as the database. |
| Build vs buy | **Buy the substrate:** a HIPAA-eligible cloud with a **signed BAA**, a managed database, managed CDC and the existing licensed interface engine. **Build only** the proxy rules, the reconciliation checks and the cutover runbook. | The scheduling vendor offers a hosted/SaaS version under a BAA that supports your integrations → compare moving to that against migrating yourselves before Phase 1 starts. |
| Region / disaster recovery | One in-country region across several availability zones. Asynchronous disaster-recovery copy in a second region: **up to 5 minutes of data loss, back up within 1 hour**. | The risk assessment or regulators need a lower data-loss limit → upgrade the disaster-recovery tier. |
| Network | **Two redundant dedicated private links** (Direct Connect / ExpressRoute) on separate physical paths, plus an encrypted VPN as a backup. **No PHI on the public internet.** | None. This is required. |
| AI gates | **N/A.** No AI component is being built. | — |

## 3. Walking skeleton (Phase 0)

**The one real request:** a **read-only "provider's day schedule"** for **one pilot clinic's waiting-room display board** (or one provider's read-only "my day" view).
- It's a real production consumer with real PHI.
- If it's wrong, the harm is small: no bookings happen from that screen.

**Tiers it crosses:**
1. Clinic workstation or display board.
2. Hospital LAN.
3. **Strangler proxy** (HAProxy/NGINX/F5, or a database-protocol proxy if clients connect straight to the database). It sits on-prem and is first deployed as a pass-through.
4. Dedicated private link.
5. Cloud internal load balancer with a web application firewall.
6. Cloud app tier (rehosted, set to read-only).
7. **Cloud database replica**, kept current by CDC from the on-prem primary.
8. The same path back.

**Freshness guard:** if the replica falls more than **5 seconds** behind the primary, the proxy quietly sends the request to on-prem instead.

**Deployed:**
- All cloud resources are defined in Terraform (landing zone, network, database, app tier, proxy config) and rolled out through a pipeline with a change-approval gate.
- Nothing is changed by hand in the cloud console.

**Logged:**
- An OpenTelemetry trace ID is created at the proxy and carried through the cloud tiers.
- PHI-access audit events go to the hospital SIEM.
- Logs never contain PHI in plain text; they use tokenised MRNs.

**Monitored on day zero:**
- **Replication lag**, alert at more than 5 seconds.
- **Shadow-diff rate**: the proxy also sends the same request to on-prem and compares the answers. Alert on any difference.
- p95 latency.
- Fallback count.
- Health of the private links.

**Exit check:** the pilot display board shows schedules served by the cloud for 7 days. There are traces from start to finish, a lag metric and a diff metric on a dashboard, zero unexplained diffs, and a forced test proves the fallback to on-prem works.

## 4. Phases (ordered by dependency; widest blast radius first within each)

**Phase 0 — Substrate and walking skeleton**
- Unlocks: everything else. It proves the network, identity, compliance boundary and replication path actually work.
- Depends on: nothing. This is the base.
- Tasks:
  1. **Find out how clients connect** (HTTP to an app server, or straight to the database). This decides how the proxy is built, so it has to come first.
  2. **Sign the BAA, classify the data, and get the risk assessment approved.**
  3. **Set up a HIPAA landing zone:** separate accounts for prod and non-prod, customer-managed encryption keys, logs that can't be altered, and guardrail policies.
  4. **Connect on-prem Active Directory to Entra ID/Okta**, with MFA and break-glass accounts.
  5. **Commission the two private links and the backup VPN.**
  6. **Build the IaC pipeline.**
  7. **Put the proxy in place as a pure pass-through and confirm nothing changes for users.**
  8. **Start CDC on just the tables the skeleton needs.**
  9. **Serve the skeleton read path.**
- Exit check: the walking skeleton exit check above.

**Phase 1 — Full replication, dependency map, and indirection**
- Unlocks: trustworthy cloud data, plus knowing every consumer that will have to move.
- Depends on: Phase 0 proving that CDC, the network and the proxy work.
- Tasks:
  1. **Freeze schema changes** (every DDL change goes through the CDC-aware process). An untracked change silently breaks replication.
  2. **Extend CDC to all tables.** Handle identity columns and sequences, large objects, triggers, and time zones / clock sync. Also handle soft-delete semantics.
  3. **Run continuous reconciliation:** row counts and per-partition checksums every 15 minutes, with full-table checksums nightly.
  4. **Map every dependency:**
     - HL7 SIU (S12, S14, S15) and ADT feeds
     - patient portal and IVR/call centre
     - SMS reminders, billing/registration, reporting and the data warehouse
     - database links and file drops
     - **printers** (appointment slips, labels)
     - nightly batch jobs (no-show marking, waitlist, reminders)
     - hard-coded IP addresses
  5. **Replace hard-coded IPs and hostnames with DNS names** that have short TTLs, so later cutovers are DNS changes and not code changes.
- Exit check: **14 days in a row with zero unexplained reconciliation differences**, p99 lag under 2 seconds, every dependency mapped and assigned an owner, and nothing still pointing at a raw IP.

**Phase 2 — Move reads (except booking reads), shadow everything else**
- Unlocks: proof of cloud performance under real load. Most read traffic leaves on-prem.
- Depends on: Phase 1's proof that the data is correct.
- Tasks:
  1. **Set the read-your-writes rule.** Slot-availability searches used for booking, and any session that wrote in the last 60 seconds, **always read from the writable database**. Otherwise a scheduler could book a slot, not see it on the replica, and double-book it.
  2. **Mirror 100% of read traffic and compare the answers.**
  3. **Load-test at the real peak** (Monday 8 a.m. call-centre surge, ×2).
  4. **Measure how chatty the thick client is over the private link** (this triggers the VDI gate if needed).
  5. **Move non-booking reads one consumer at a time:** display boards → reporting/warehouse extracts → portal "my appointments" → scheduler UI view-only screens.
- Exit check: diff rate is 0 across all mirrored reads, p95 is within budget at 2× peak, and every non-booking reader has been served from the cloud for 7 days with the on-prem fallback still available.

**Phase 3 — Prepare integrations and batch jobs (cloud side passive)**
- Unlocks: the cloud being able to act as the writable system the moment it's promoted.
- Depends on: Phase 1's dependency map and Phase 2's proven cloud app tier.
- Tasks:
  1. **Make sure only one copy of each batch job can run**, using a leader lock tied to whichever database is writable. Otherwise patients get duplicate reminder SMS or no-shows are marked twice.
  2. **Set up interface-engine routes to and from the cloud app**, disabled for now, with a test message validated in non-prod.
  3. **Point printers and file drops at the cloud endpoints**, again disabled for now.
  4. **Make sure paper downtime reports (offline schedule printouts) can be produced from the cloud.**
- Exit check: in a staging environment with a prod-sized, masked copy of the data, a full synthetic day replays end to end. That covers booking, rescheduling and cancelling, SIU going out, ADT coming in, reminders sent exactly once, and slips printed. All of it has to match on-prem's output.

**Phase 4 — Rehearse, then switch the writable database**
- Unlocks: the cloud becomes the system of record.
- Depends on: Phase 3's proof that integrations work, and a rehearsed runbook.
- Tasks:
  1. **Do at least 2 full rehearsals in staging and 1 game day** where failures are injected on purpose: a link drop mid-switch, CDC stalling, the promotion failing.
  2. **Brief nursing supervisors, the ED and the call centre**, and have paper downtime procedures on standby even though they shouldn't be needed.
  3. **Run the production cutover in a low-volume window** (e.g. Sunday 03:00). The ED books follow-ups 24/7, so this keeps the write pause small but doesn't eliminate it. Steps:
     - (a) Confirm lag is under 1 second.
     - (b) The proxy starts holding writes, with a 30-second cap.
     - (c) Set the on-prem database to read-only.
     - (d) Let CDC drain, then confirm the final log position matches and the checksums on the busiest tables agree.
     - (e) Promote the cloud database.
     - (f) **Start reverse CDC (cloud → on-prem).**
     - (g) Switch the proxy's write route, the interface-engine routes and the batch-job leader lock.
     - (h) Release the held writes.
     - (i) Make one synthetic booking end to end.

     Each step has an abort rule. Before step (e), abort means setting on-prem back to writable, which takes under 60 seconds.
- Exit check: the write pause was 30 seconds or less, no held write was lost (count the writes in and out of the hold queue), the synthetic booking produces the correct SIU, and the first hour of reconciliation is clean.

**Phase 5 — Hypercare, rollback window, then retire on-prem**
- Unlocks: shutting down the on-prem system and the steady-state cloud setup.
- Depends on: Phase 4's successful cutover.
- Tasks:
  1. **Keep reverse CDC running and on-prem warm for 30 days** as a tested rollback path.
  2. **Run the first disaster-recovery failover to the second region** and confirm the 5-minute data-loss and 1-hour recovery targets.
  3. **Remove the 'temporarily disabled' on-prem routes.**
  4. **Retire on-prem:** take a final encrypted archive under the hospital's records-retention policy, get a certificate of media destruction, and update the BAA/asset register.
- Exit check: 30 days with no rollback, a passed disaster-recovery test, compliance has signed off on retirement, and on-prem has been powered off.

## 7. Deliberately deferred
These are decisions to not build yet, each with what would pull it forward:

| Deferred | Pull forward when |
|---|---|
| Re-architecting into microservices or containers / Kubernetes | 2 stable quarters in the cloud, and one part needs to scale or ship on its own schedule. |
| A FHIR Appointment/Slot API to modernise integrations | A partner or regulator (e.g. interoperability rules) requires FHIR scheduling. |
| Active-active multi-region | Clinical leadership requires recovery under 1 hour, or the zero-write-pause gate flips. |
| Moving the interface engine to the cloud | Most HL7 endpoints are already in the cloud, so the on-prem hop becomes the bottleneck. |
| Offline booking at individual sites | The consistency gate flips for sites with unreliable links. |
| Cost optimisation (reserved capacity, right-sizing) | 90 days of steady-state usage data. Optimising before cutover adds risk and saves nothing. |
| AI features (no-show prediction, smart overbooking) | The migration is done and leadership wants them. They would then need their own AI-layer plan. |
| Changing database engines (e.g. Oracle → Postgres) | A licence-cost case after the migration. Never at the same time as the migration. |
