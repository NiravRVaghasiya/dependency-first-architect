# BUILD PLAN: Real-time card-transaction fraud detection

**Assumptions that set the phase order** (the request didn't say; each one changes the plan if it's wrong):
- **A1. Issuer-side, inline scoring.** I assumed we're the card issuer (or its processor) and that we score each authorization before it's approved or declined. If instead we only score after authorization (alerts, no declines), the sync-vs-async row in §3 flips, V4 relaxes to seconds, and Phase 5 becomes "alerts to analysts". If we're an acquirer or merchant, the main action becomes 3DS step-up instead of decline, and fraud labels come from the gateway.
- **A2. Brownfield.** I assumed an authorization host and an existing rules-based fraud engine (vendor or in-house) are already running. If there's no existing engine, Phase 2 must first build and validate a pinned fallback rule set, and V3/V7 compare against network-provided scores instead.
- **A3. PCI DSS applies**, plus an internal model-risk policy. The jurisdiction is unknown (see Missing inputs).

## 1. Classification and constraints
- **What:** A scoring service in the authorization path that returns approve / step-up / decline / approve+alert, fed by streaming per-card features, with a loop that turns fraud outcomes into labels for retraining.
- **Type:** Software, data infrastructure and a classical ML model (no LLM). Brownfield. Not a small build: it touches money, card data and customers.
- **Dominant constraint:** Latency. Each decision must fit inside the authorization time window, and the decision must stay correct within that limit.
- **Worst failure:** A bad model, threshold or feature change goes out to the whole portfolio and declines legitimate cardholders at scale within minutes. V6 guards against this. A close second is raw card numbers (PANs) leaking into the pipeline; V2 guards against that.

**R1 defaults:** online store is Aerospike (or Redis Enterprise) behind a feature-fetch interface; scorer in Java; Kubernetes with Argo CD; MLflow model registry; lake on S3 with Iceberg; per-segment decision-mode flags in versioned config.
**N/A:** prompt+RAG vs fine-tune and hosted LLM vs self-host (no LLM); tenancy (single issuer, unless Missing input 2 says otherwise); data residency (pending Missing input 3).

## 4. Walking skeleton (Phase 0)
- **Request:** a $1 card-not-present authorization on an issuer test card in the production test BIN range. A second test card is forced to score high.
- **Path:**
  1. The auth-host adapter (inside the CDE) tokenizes the PAN.
  2. It calls the scorer synchronously over gRPC with an 80 ms timeout. The scorer reads one feature (transaction count per token) from the online store and applies a constant rule.
  3. The response is logged by the auth host and ignored, because the mode is "shadow".
  4. The scorer publishes the scored event to Kafka. A Flink job increments the counter in the online store, and a sink writes the decision log to S3.
  5. The high-score card creates a case in the existing case-management test queue.
- **Deploy:** Terraform for infrastructure; Argo CD for the scorer and Flink; the adapter goes through the auth host's own change process.
- **Rollback:** Argo rollback for the scorer, and `fraud_scorer_mode=off` at the auth host, which takes seconds.
- **Observability:** OpenTelemetry trace from the adapter through the scorer and Kafka (trace context in message headers) to Flink. Prometheus metrics for latency, timeouts, fallbacks and consumer lag, with Grafana dashboards and PagerDuty alerts. Logs carry tokens only.
- **Who can reach it:** only the allow-listed test BIN range, and the scorer's output never changes a decision. Real cardholder traffic waits for V2.
- **Also in Phase 0:** confirm the things that use the existing engine's outputs (the §2 rows); record BASELINES for auth-host processing time, peak authorizations per second, and the existing engine's decline and alert rates; start the organizational items (QSA, data-access approval, model risk, on-call staffing).
- **Exit check (V0):** see §6.

## 5. Phases

- **Phase 1: Contracts and the PAN boundary**
  - Unlocks: real traffic in shadow mode, the historical extract, and specifying features.
  - Depends on: V0.
  - Tasks:
    1. Event schema and identifiers (V1).
    2. Harden tokenization and key management; deploy DLP scanners on topics, logs, traces and the lake; network segmentation; QSA review (V2).
    3. Scoring API contract v1 with contract tests.
    4. Extract 12–24 months of history through the same tokenizer into Iceberg, with point-in-time correctness.
    5. Finance and fraud ops confirm the uplift bar and cost ceiling; compliance confirms retention.
    6. After V2, widen the shadow mirror: one BIN range first, then all traffic.
  - Rollback: shrink the mirror back to test BINs. If DLP finds a PAN, stop and purge the affected topic or partition.
  - Exit check: V1 and V2 pass; shadow traffic reaches 100% with the timeout rate inside the V4 assumption.

- **Phase 2: Defenses and budgets in the authorization path, plus an offline feasibility check (two parallel tracks)**
  - Unlocks: committing to build, and specifying the feature platform within the latency budget.
  - Depends on: Phase 1, V1, V2, and the data-access approval.
  - Track A tasks:
    1. Hard timeout and fallback to the existing engine.
    2. Kill switch.
    3. Decision config as a signed, versioned artifact with two-person approval.
    4. Per-segment circuit breaker on the shadow would-decline rate.
    5. Validate inputs from untrusted fields (merchant name, MCC, device data).
    6. Load test (V4).
    7. Shadow-mode rehearsal of V6.
  - Track B tasks:
    1. Label pipeline: confirmed fraud claims and fraud chargeback reason codes, with label-maturity windows.
    2. Offline baseline features.
    3. Out-of-time backtest of a gradient-boosted model against the existing engine. Transactions the existing engine declined are evaluated separately, because they never get outcome labels (V3).
  - Rollback: config revert. Nothing is live yet.
  - Exit check: V3 and V4 pass; the V6 shadow rehearsal passes.

- **Phase 3: Feature platform**
  - Unlocks: online features that match training.
  - Depends on: V1, V3 (build), V4.
  - Tasks:
    1. One feature-definition repo that generates both the Flink (online) and Spark (offline, point-in-time) jobs.
    2. Online store with replicas.
    3. Backfill long windows from the lake.
    4. Missing-feature defaults.
    5. Rebuild drill for the RTO.
    6. Online/offline parity check (V5).
  - Rollback: the scorer pins the previous feature-set version.
  - Exit check: V5 passes; the rebuild drill meets the ≤ 15 min RTO.

- **Phase 4: Model serving, orchestration and shadow champion/challenger**
  - Unlocks: the evidence for going live.
  - Depends on: V5, V3.
  - Tasks:
    1. Model registry; signed artifacts loaded into the scorer process.
    2. Reason codes.
    3. Rules-plus-model policy: hard rules (e.g. blocked card) override; score bands map to approve / step-up / decline / approve+alert.
    4. Score-drift monitoring.
    5. Analysts review a sample of alerts that only the new model raised.
    6. Shadow on 100% of traffic (V7).
    7. Submit the model-risk package (V8).
    8. Get the false-decline appetite from fraud ops.
  - Rollback: pin the previous model version; it's still shadow only.
  - Exit check: V7 and V8 pass, and the false-decline appetite is in hand.

- **Phase 5: Live decisions, smallest exposure first**
  - Unlocks: fraud-loss reduction.
  - Depends on: V6, V7, V8, the on-call rota and runbooks.
  - Tasks:
    1. V6 rehearsal on live internal cards.
    2. Exposure ladder, assigning cards by a hash of the card token: internal cards → 1% of one low-risk BIN segment → 5% → 25% → 100% of that segment → the next segments. V9 gates each step.
    3. Then enable the step-up band for card-not-present through the existing ACS.
  - Rollback: per-segment flag back to the existing engine within seconds; the breaker reverts automatically. Because labels lag, there's a 60-day review after each step, and a step can be rolled back afterwards.
  - Exit check: V9 passes at every step, and the fallback rate stays ≤ budget.

- **Phase 6: Feedback and retraining**
  - Unlocks: keeping performance up as fraud patterns shift.
  - Depends on: Phase 5 at ≥ 1 full segment.
  - Tasks:
    1. Automated label maturation.
    2. Analyst dispositions enter the labels only through review.
    3. Scheduled retraining, then registry, then shadow (V7 method), then canary (V9 method).
    4. Drift and attack-pattern alerts.
  - Rollback: the current production model stays unless a candidate passes.
  - Exit check: one retrained model is promoted end to end, with no manual steps besides the approvals.

## 10. Deliberately deferred
- **Decommissioning the existing engine.** Pull forward when the new model has run at 100% for 2 full label cycles with the V9 limits holding, and a contract renewal decision is due. It then gets its own gate: a rehearsal, a named approver, and a pinned fallback rule set.
- **Sequence or graph models for fraud rings.** Pull forward when V7 error analysis shows ring or sequence fraud is the top loss and V4 has headroom.
- **Per-segment models (routing).** Pull forward when the single model trails the existing engine in one segment by more than the uplift bar.
- **Long-horizon cardholder profiles.** Pull forward when V7 error analysis points to gaps in behavior baselines.
- **Counterfactual exploration** (approving a tiny capped share of would-be declines to measure them). Pull forward when retraining shows bias from missing labels; needs risk-appetite approval.
- **Third-party device fingerprinting.** Pull forward when card-not-present fraud is the largest loss category.
- **Multi-region active-active scorer.** Pull forward when the auth host itself runs active-active, or a scorer SLO breach is recorded.
- **Online learning.** Pull forward when drift outpaces the Phase 6 retraining cadence.
- **Multi-tenant isolation.** Pull forward if Missing input 2 says we're a processor serving several issuers.
