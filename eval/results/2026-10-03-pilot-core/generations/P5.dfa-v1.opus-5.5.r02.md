# BUILD PLAN: Real-time collaborative document editor

## 1. Classification
- **What:** A browser-based rich-text editor where many users edit the same document at once, see each other's cursors, and get version history, comments, search and export.
- **Type:** Software, with a significant infrastructure part: a stateful real-time sync tier. There are no AI features.
- **Dominant constraint:** **Correctness.** Every copy of a document must end up identical, and no saved edit may be lost. Latency comes second: a remote user should see an edit within about 200 ms at p95.
- **Worst failure:** Silent data loss or divergence. That means an edit the server confirmed disappears, or two users permanently see different versions of the "same" document without anyone noticing.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **How concurrent edits merge: CRDT vs OT** | **CRDT (Yjs).** It merges edits made offline or during a network split without a central sequencer. | A requirement for one server-ordered history with per-edit server approval (for example, legal-grade track changes). Or merge metadata exceeding about 3× the document's content size on typical documents after compaction. **Must be settled before Phase 1 locks the data format.** |
| **Consistency vs availability** | **Split by data type.** Document *content* favours availability: edits keep working offline or during a split and merge later. *Permissions, workspace membership and billing* favour consistency: they live in Postgres as the single source of truth. A permission revocation disconnects the affected sessions within 5 s. | A compliance customer requires revocation to be instant and guaranteed. Then every incoming edit is checked against permissions synchronously, at a latency cost. |
| **Monolith vs services** | **Modular monolith.** One repo and one container image, run in three roles: `api` (stateless HTTP), `sync` (stateful WebSocket) and `worker` (background jobs). | A module needs its own deploy schedule or team ownership. Or one role's scaling profile starts harming another's, for example export CPU starving sync. |
| **Sync vs async** | **Edit path:** the client applies the edit locally first. The server **writes it durably to Postgres before acknowledging it** (synchronous), then broadcasts it to other users immediately. **Side effects** run through a job queue (pg-boss on Postgres): snapshots, search indexing, notifications, export. | Postgres write time exceeds 50 ms at p95, or write throughput saturates. Then edits are written first to Redis Streams with replication and copied to Postgres in batches. The ack-after-durable rule stays. |
| **Build vs buy** | **Buy or adopt:** Yjs, TipTap/ProseMirror, an auth provider (WorkOS or Auth0 for login and SSO), managed Postgres (RDS, spread across availability zones), S3, Sentry, Grafana/OpenTelemetry. **Scaffold:** Hocuspocus as the first sync server. **Build:** permission rules, the storage layer, document ownership across servers, and the product itself. | Hocuspocus's hooks can't express per-message permission checks or the per-document ownership lease (Phase 2). Then replace it with a custom server built on `y-protocols`. |
| **Server can read content vs end-to-end encryption** | **The server can read content.** That makes search, export, server-side validation and content permissions possible. | Regulated customers require that the server never sees content. This is effectively irreversible after Phase 1, because it changes storage, validation, search and export. Decide before the data format is locked. |
| **Data residency / regions** | **One region spread across availability zones.** `tenant_id` is on every row from the first commit, so tenants can later be split into separate regional deployments. | The first customer with an EU (or other) data-residency requirement, which triggers per-region deployments. Or more than 20% of edit sessions see over 250 ms p95 latency. |
| (AI) prompt+RAG vs fine-tune | **N/A.** The system has no model features. | An AI writing assistant is added to scope. Re-run this plan with the AI layer. |
| (AI) hosted API vs self-host | **N/A.** Same reason. | Same. |

## 3. Walking skeleton (Phase 0)
**The one real request:** A signed-in user opens document `/d/{id}` and types "hello". A second user in another browser sees "hello" appear. Either user reloads the page and "hello" is still there.

**Tiers crossed:**
1. **Browser:** a minimal TipTap editor (paragraph and text only) bound to a Yjs document, served from a CDN.
2. **Auth:** the auth provider's sign-in issues a short-lived token.
3. **Load balancer:** an AWS ALB, upgraded to secure WebSocket (WSS), with routing pinned to the document.
4. **`sync` role:** Hocuspocus verifies the token when the connection opens and checks that the user may access this document.
5. **Postgres:** the edit is appended to a `doc_updates` log (`tenant_id, doc_id, seq, update_bytes, user_id, ts`). The server acknowledges only after the write commits.
6. **Broadcast:** the edit goes out to the second client.
7. **`api` role:** a single `GET /docs/:id` endpoint returns the document's metadata.

**Deployed:** Terraform builds the infrastructure. GitHub Actions builds the image, runs tests and database migrations, and does a rolling deploy to ECS on every merge to `main`. A staging environment is identical to production because it uses the same Terraform modules.

**Logged and monitored on day zero:**
- **Traces:** OpenTelemetry runs from the browser through the sync server to Postgres, with `doc_id`, `user_id` and `trace_id` on every span and log line.
- **Metrics:** `ws_connections`, `update_persist_ms`, `update_broadcast_ms`, `ack_failures_total`.
- **Dashboard and alerts:** one Grafana dashboard. One page-out alert fires on any `ack_failures_total` increase or on `update_persist_ms` p95 above 100 ms.
- **Errors:** Sentry on both client and server.

**Exit check:** in production, user B sees user A's edit, and it survives a reload. The trace shows every hop, and the persist and broadcast metrics are on the dashboard. Killing the sync task mid-session loses no acknowledged edit (verified by a script).

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 0 — Walking skeleton** (above).

**Phase 1 — Document substrate: data format, storage, permissions, merge correctness**
- **Unlocks:** every feature that stores or changes document content.
- **Depends on:** Phase 0 proving, in production, that an edit can be persisted and broadcast.
- **Tasks (widest first):**
  1. **Document data contract.** Fix the Yjs update encoding and a versioned ProseMirror schema (`schema_version` stamped on every document). Define how the schema evolves: add-only node types, and unknown nodes are kept intact rather than dropped. Getting this wrong means rewriting every stored document.
  2. **Storage model.** Use the append-only `doc_updates` log plus periodic snapshots (`doc_snapshots`: merged state and its version vector) in S3/Postgres. A compaction job runs in the `worker` role. Postgres row-level security filters every table by `tenant_id`.
  3. **Permission model.** Workspace → document access lists with four roles: owner, editor, commenter, viewer. Checks happen when a connection opens **and on every incoming edit**: edits from viewers or commenters are rejected on the server. A permission change disconnects affected sessions.
  4. **Sync protocol details.** Use the Yjs sync handshake (the two-step exchange of version info and missing edits). Presence data (cursors, who's online) goes on a separate channel and is never stored. The client keeps an offline queue in IndexedDB (`y-indexeddb`), and reconnects with backoff plus jitter.
  5. **Convergence harness.** Simulate 5+ clients making random concurrent edits under random network splits, delays and reorderings. Assert that all states end up byte-identical. Run it in CI.
  6. **Harden what is now proven.** Freeze the v1 schema and the storage format. Leave everything else flexible.
- **Exit check:**
  - 10,000 fuzz runs with recorded random seeds all converge.
  - Killing the sync server or Postgres during an edit (with failover to the replica) loses no acknowledged edit.
  - A viewer's crafted WebSocket edit is rejected and logged.
  - Restoring a backup to a chosen point in time on staging reproduces the documents.

**Phase 2 — Scaling the real-time tier across servers**
- **Unlocks:** many documents and many users per document, plus deploys and node failures with no downtime.
- **Depends on:** Phase 1 proving single-server merge correctness and durability.
- **Tasks (widest first):**
  1. **Document ownership model.** Exactly one sync server owns each document at a time, via a lease in Redis with a fencing token so an old owner can't keep writing. The owner holds the document in memory and is the only server writing it to Postgres. This decides how failures behave across the whole tier.
  2. **Routing.** Connections go to the owning server via consistent hashing on `doc_id` at the routing layer, or a redirect handshake. Redis pub/sub broadcasts edits across servers if routing misses.
  3. **Failover.** When a lease expires, a new owner rebuilds the document from snapshot plus log tail, and clients resume using version vectors.
  4. **Backpressure and limits.** Cap edit size and rate per connection. Cap connections per document. Batch broadcasts for very busy documents.
  5. **Graceful drain on deploy.** A server releases its leases and tells clients to reconnect.
  6. **Load test** with k6 plus a custom WebSocket client.
- **Exit check:**
  - 500 concurrent editors on one document, and 50,000 documents open.
  - Remote edit appears within 200 ms at p95 in the same region.
  - Killing a node gets clients reconnected and synced in under 5 s, with no lost acknowledged edits.
  - A rolling deploy drops no sessions.

**Phase 3 — Core editing features**
- **Unlocks:** a product people can use day to day.
- **Depends on:** Phase 1's schema-evolution rules (proven by migration tests) and Phase 2's scaled sync.
- **Tasks (widest first):**
  1. **Schema extensions:** headings, lists, tables, code blocks, links, images. These touch stored data, so each ships through the Phase 1 evolution rules.
  2. **Media pipeline:** pre-signed S3 uploads, content-type checking, a malware scan worker, and image resizing.
  3. **Sharing:** workspace documents, invites, and share links with unguessable tokens and expiry.
  4. **Presence:** live cursors and selections over the presence channel.
  5. **Document list and workspace navigation UI.**
  6. **Leaf work:** toolbar, keyboard shortcuts, slash menu.
- **Exit check:**
  - A corpus of production-shaped test documents passes migration tests for each schema version.
  - An old client opening a document with new node types keeps the content intact; the client is gated on version and forced to refresh.
  - Pasting malicious HTML from the XSS corpus produces no script execution.

**Phase 4 — History, comments, notifications**
- **Unlocks:** review workflows and recovery from mistakes.
- **Depends on:** Phase 1's snapshot and log replay, and Phase 3's stable rich-text schema (which comment anchors attach to).
- **Tasks (widest first):**
  1. **Version history.** Named and automatic snapshots. A restore is applied as a *new forward edit*, never a destructive rewrite.
  2. **Comments data model.** Comments anchor to text through Yjs relative positions so they survive edits. Threads and resolve state are stored in Postgres and checked against permissions.
  3. **Notifications.** Mentions and comment replies go through the queue to email and in-app delivery, with idempotent consumers and a dead-letter queue (DLQ) for failed messages.
  4. **Audit log** of permission changes, restores and share-link creation.
  5. **Leaf work:** history UI with a diff view, and mention autocomplete.
- **Exit check:**
  - Replaying the log to any version reproduces the stored snapshot byte for byte.
  - Comment anchors survive 1,000 fuzzed edits around them; orphaned anchors are detected and shown, not lost.
  - Killing a notification worker mid-batch produces neither duplicate nor lost notifications.

**Phase 5 — Search, import/export, and other leaf features**
- **Unlocks:** finding documents and moving content in and out.
- **Depends on:** Phase 4's snapshots (the source data) and the Phase 1 permission model.
- **Tasks (widest first):**
  1. **Search index.** Postgres full-text search first; OpenSearch is deferred. Indexing runs in the background from snapshots, partitioned by tenant and filtered by permissions at query time.
  2. **Export** to PDF, DOCX and Markdown, rendered by headless Chromium in isolated `worker` containers.
  3. **Import** from DOCX and Markdown, converted into the schema and sanitized.
  4. **Leaf work:** templates, word count, print styles.
- **Exit check:**
  - A user never sees a search result for a document they can't access (permission test matrix).
  - The index can be rebuilt from snapshots alone.
  - Exports match golden-file tests.
  - Search lag is under 30 s at p95.

## 6. AI layer
**N/A.** This system has no model, retrieval or agent parts. If an AI writing assistant is added, re-run this plan. Prompt-injection defense (document content is untrusted input), cost and latency budgets, and human approval of AI edits would then come before any capability work.

## 7. Deliberately deferred
- **Active-active across regions.** Pull forward when a customer requires data residency, or more than 20% of sessions see over 250 ms p95 edit latency. `tenant_id` on every row keeps the split into regional deployments open.
- **End-to-end encryption.** Pull forward only through the tradeoff gate, before Phase 1 is frozen. Adding it later conflicts with server-side search, export and validation.
- **Suggestion / track-changes mode.** Pull forward when customers ask for review workflows. It depends on Phase 4's anchoring and may trigger the CRDT-vs-OT flip.
- **Permissions on individual blocks or sections.** Pull forward when an enterprise deal requires it. It reworks the Phase 1 permission model, so it needs re-planning.
- **OpenSearch / semantic search.** Pull forward when Postgres full-text search exceeds 500 ms p95 or the corpus passes about 10 million documents.
- **Splitting into microservices.** Pull forward when a role needs its own deploy schedule or team ownership (see the monolith gate).
- **Custom sync server replacing Hocuspocus.** Pull forward when its hooks block the Phase 1 per-edit permission checks or the Phase 2 ownership lease.
- **Native mobile apps, and offline across the whole app** (beyond single documents). Pull forward when mobile reaches about 25% of sessions or a field-use customer needs it.
- **Public plugin / extension API.** Pull forward when the schema has gone two releases without breaking changes and a partner asks for it.
- **SCIM user provisioning and advanced SSO admin.** Pull forward with the first enterprise deal. The auth provider already supports both, so this is configuration more than building.
- **AI writing assistant.** Pull forward with a product decision, then re-run this plan with the AI layer.
