# BUILD PLAN: `photo-rename`, a CLI that renames a folder of photos by EXIF capture date

## 1. Classification and constraints
- **What:** A local command-line tool. It reads each photo's EXIF capture date, plans a new name such as `2024-07-14_153012.jpg`, shows the plan, and then renames the files with an undo log.
- **Type:** Software (CLI you don't operate); greenfield; small build (one developer, no outside service, no money, no regulated data). It does touch irreplaceable personal files.
- **Dominant constraint:** Correctness, meaning no photo is ever lost or overwritten.
- **Worst failure:** A name collision or a crash in the middle of a run overwrites a photo, or leaves the folder half-renamed with no way back.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Data safety | 0 files lost, overwritten or changed in content; undo restores the exact original names | ASSUMPTION (these are irreplaceable personal photos, so any loss is unacceptable) | V2 |
| Throughput | Dry run of 10,000 JPEGs on a local SSD in under 60 s | ASSUMPTION (the tool reads only file headers; a typical import folder has 1k–10k files) | V0 records the baseline; Phase 2 exit check |
| Resource use | Peak memory under 200 MB, not growing with folder size | ASSUMPTION (header-only reads; the plan holds only names and dates) | Phase 2 exit check |
| Operational complexity | One installable package, no services, no network; at most one outside binary (only if V1 switches to exiftool) | ASSUMPTION (one developer) | Phase 2 exit check |

**Missing inputs** (the first one decides whether to build at all):
1. **Reusable tool or one-off?** If you only need this once, don't build anything. exiftool already does it: `exiftool -d '%Y-%m-%d_%H%M%S%%-c.%%e' '-TestName<DateTimeOriginal' DIR` previews the renames, and replacing `TestName` with `FileName` applies them. *My assumption:* you want a tool you'll reuse on every import. Its value over exiftool is safety: preview by default, collisions refused, crash-safe undo.
2. **File formats and devices** (iPhone HEIC, RAW formats, videos?). This shapes the V1 test set and maybe the EXIF library choice. You supply it before Phase 1.
3. **Operating systems to support.** This decides how the safe rename is done on each OS and which systems CI tests on. You supply it before Phase 1.
4. **Naming format.** You confirm it from the Phase 0 preview output.
5. **Is the folder managed by Lightroom or Apple Photos, or does it have sidecar files** (.xmp, .aae)? Renaming outside a catalog breaks its file references. *My assumption:* plain folders. The tool will refuse to run inside a `.photoslibrary` bundle.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| How writes are made safe | R3 (gated for harm: one overwritten photo can't be recovered) | Rename in place in two steps: plan everything first, then execute. | Which date, and time-zone handling | R2 (wrong dates get baked into names across a whole library; the undo log limits the damage) | Use `DateTimeOriginal`, falling back to `DateTimeDigitized`. | Naming format | R2 (once libraries are renamed, a change means renaming them again and breaks "already renamed" detection) | `YYYY-MM-DD_HHMMSS[_NN].<original ext>`. `_NN` numbers photos taken in the same second, ordered by sub-second time and then by original name. | Sortable names with second precision suit you | Your sign-off on the Phase 0 preview | You need another format → add `--format` templates (§10) |

**R1 defaults:**
- Build vs buy → build a thin safety layer, unless missing input 1 says one-off, in which case use exiftool.
- Python 3.11+ installed with `pipx`; `argparse`; `pytest` with `hypothesis`; undo log as JSON Lines.
- Not recursive by default; extensions keep their original case (changing only the case of a name is risky on case-insensitive file systems).

**N/A:**
- Monolith vs services, sync vs async, consistency vs availability: it is one local process doing renames in order, and batch consistency is covered by the write-safety row.
- Data-privacy boundary: nothing ever leaves the machine. "No network I/O" is enforced from Phase 0 (§7).

## 4. Walking skeleton (Phase 0)
- **Real request:** `photo-rename ~/Pictures/2024-import` on a real folder. It responds with an old → new plan table, a summary (to rename / no date / collision / error) and an exit code: 0 = all OK, 1 = some files skipped, 2 = fatal error.
- **Tiers it crosses:** argument parsing → directory scan (no symlink following) → EXIF read → planner (name + collision check) → output and JSONL log. The executor exists but runs **only in CI against a temporary copy**.
- **Deploy, log, monitor, roll back:**
  - Pushing a tag makes CI build the wheel and publish `0.1.0` to TestPyPI. You install it with `pipx install`, as a user would.
  - "Monitoring" means the run's summary, its exit code and a `--log` JSONL file are visible to whoever runs it.
  - Rollback means publishing `0.1.1`, then reinstalling the pinned `0.1.0`.
- **Who can reach it:** only the developer and allow-listed testers, from TestPyPI. Real folders are **read-only (preview only)** because `--apply` refuses real folders until V2 passes.

Exit check (V0) is in §6.

## 5. Phases

**Phase 1: Safe write path**
- **Unlocks:** Renaming real folders.
- **Depends on:**
  - V0
  - V1 (required before task 3)
  - Naming sign-off
  - OS list and sample files (missing inputs 2–3)
- **Tasks:**
  1. Freeze the plan model and the undo-log format. Undo, resume and "already renamed" detection all build on these.
  2. Run V1 on the test set. Settle the EXIF library and the date rules.
  3. Write a rename that never overwrites, per OS:
     - Linux: `renameat2(RENAME_NOREPLACE)`, or link + unlink as a fallback
     - macOS: `renamex_np(RENAME_EXCL)`
     - Windows: `MoveFileEx` without the replace flag
  4. Handle swaps and loops through temporary names. Check for collisions case-insensitively.
  5. Write each step to the undo log and flush it to disk before renaming. Add `photo-rename undo LOG` and `resume LOG`.
  6. Add pre-run checks: the folder is writable, it isn't a `.photoslibrary`, and no unfinished log is lying around.
  7. Build the V2 test suite in the CI OS matrix.
  8. After V2 passes, turn on `--apply` for real folders, smallest exposure first:
     1. the developer's own backed-up folder
     2. up to 3 allow-listed testers
- **Rollback:** `undo` reverses any run from its log. A bad release is rolled back by reinstalling the previous pinned version.
- **Exit check:** V1 and V2 pass, and one real-folder apply → undo round trip gives back the original names exactly.

**Phase 2: Coverage and 1.0 release**
- **Unlocks:** Public release on PyPI.
- **Depends on:** Phase 1 (V2 passed).
- **Tasks:**
  1. Running the tool again on a renamed folder does nothing.
  2. Sidecar files with the same base name (`.xmp`, `.aae`, `.thm`) are renamed in the same logged step as their photo.
  3. Opt-in `--fallback mtime`, with each such file marked in the output.
  4. `--json` output for scripts.
  5. Extend the V2 suite to cover sidecars.
  6. Publish 1.0 to PyPI through automated publishing.
- **Rollback:** Yank the release on PyPI; users reinstall the previous pinned version. Renames are still reversible through their logs.
- **Exit check:**
  - A second run on a renamed folder produces zero operations.
  - Sidecar pairs stay matched in the V2 suite.
  - The throughput, memory and complexity targets in §1 are met against the V0 baseline.

## 10. Deliberately deferred
- **Videos and Live Photo pairs.** QuickTime `CreateDate` is in UTC, so they need their own time-zone rules. *Pulled forward when* you list video as a format you need (missing input 2).
- **Time-zone conversion using `OffsetTimeOriginal`.** *Pulled forward when* you mix photos from several time zones in one folder and want them in one timeline.
- **Recursive mode.** *Pulled forward when* your import folders are nested.
- **Custom `--format` templates.** *Pulled forward when* the naming sign-off asks for anything other than the default.
- **Reading files in parallel.** *Pulled forward when* the V0 baseline suggests a dry run of your largest folder would miss the throughput target.
- **Standalone binary (PyInstaller).** *Pulled forward when* a user can't install Python or `pipx`.
- **Writing or fixing EXIF dates.** *Pulled forward when* V1 finds devices with wrong clocks you want corrected. Even then it would be a separate, separately gated feature, because it modifies file contents.
