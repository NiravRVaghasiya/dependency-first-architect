Classification\n- **What:** A browser-based rich-text editor where several users edit the same document at once and see each other's changes and cursors live. Includes accounts, sharing, permissions, history and durable storage.\n- **Type:** Software, with a significant infrastructure part (a tier holding long-lived WebSocket connections and fanning out messages). No AI in scope.\n- **Dominant constraint:** **Correctness.** Every user must end up seeing the same document, and every edit the server has confirmed must survive. Latency comes second: edits should reach other users in under 100 ms (p95) within one region.\n- **Worst failure:** **Silent divergence or loss of confirmed edits.** Two users see different documents, or text the server confirmed disappears. Users will put up with slowness; once they stop trusting the document, they leave.\n\n## 2. Tradeoff gates (resolved up front)\n\n| Decision | Default (chosen now) | Flip condition |\n|---|---|---|\n| **Merge algorithm: CRDT vs OT** (the hardest to reverse, because it fixes the stored format) | **CRDT using Yjs.** Edits apply locally first and merge automatically. It works offline and has a mature ecosystem (y-prosemirror, Hocuspocus). | Typical documents carry more than 10 MB of CRDT history that compaction can't reclaim, or the product needs edit semantics CRDTs handle badly (e.g. strict server-defined ordering) → switch to OT (ShareDB). This must be decided **before Phase 1 locks the data contract**. |\n| **Consistency vs availability** | **Split by data type.** Document content favours availability: edits apply locally at once and all copies converge. Permissions, document metadata and tenant data favour strong consistency and live in Postgres. | A regulated workflow needs edits in one strict order or locked sections (legal sign-off) → add a server-assigned sequence or lock just for those documents. |\n| **Monolith vs services** | **Modular monolith.** One repo and one image, run as two processes: an HTTP API and a WebSocket sync server. The server confirms an edit only after it is durably written to the update log. Compaction, history snapshots, export and indexing run on a queue. | p95 write latency exceeds 50 ms → batch writes into ~20 ms group commits. Never confirm an edit before it is durably stored. |\n| **Build vs buy** | **Buy** login (WorkOS or Auth0). **Use open-source** Yjs, TipTap/ProseMirror and Hocuspocus. **Build** permissions, persistence, the message envelope and the divergence detector. Walking skeleton (Phase 0)\n\n**The one real request:** A signed-in user opens `/d/:id` and types \"hello\" into a **plain-text** shared field (`Y.Text`, not rich text yet). A second browser signed in as another user with access sees \"hello\" appear live. Reloading either browser shows \"hello\", loaded from Postgres.\n\n**Tiers it crosses:**\n1. **Browser client:** React, Yjs and the y-websocket provider, served as static files from a CDN.\n2. **Auth provider:** WorkOS or Auth0 login, which issues a short-lived JWT.\n3. **Load balancer:** must support WebSocket upgrades and idle timeouts of at least 60 s.\n4. **Sync server:** Node with Hocuspocus. On connect it checks the JWT and a hard-coded permission check against one table.\n5. **Postgres:** tables `documents`, `doc_updates` (append-only) and `doc_acl`. An edit is confirmed only after it is written to `doc_updates`.\n6. **Second client:** receives the broadcast and renders it.\n\n**Deployed, logged and monitored on day zero:**\n- **Deploy:** Terraform builds the environment (Fly.io or ECS). One container image with two process roles. CI on every merge to main: build → test → deploy to staging → manual promote to production.\n- **Logs:** structured JSON with `trace_id`, `doc_id`, `user_id`, `conn_id`. Document content is never logged.\n- **Traces:** OpenTelemetry spans covering client send → sync server receive → Postgres write → broadcast. The receiving client reports when it rendered the edit, which gives the true end-to-end time.\n- **Metrics:** open WebSocket connections, edit write latency, client-reported edit-to-remote-render latency (p50/p95), reconnect rate, auth rejections.\n- **Alerts:** none of these is wired before day zero: an uptime check on the WebSocket endpoint, p95 propagation over 250 ms, and write error rate over 0.1%.\n\n**Exit check:** In production, user B's browser renders user A's typing. One trace shows all the hops. The propagation-latency metric appears on a dashboard. Killing the sync server and restarting it loses nothing that was confirmed, and the client reconnects on its own.\n\n## 4. Phases (ordered by dependency; within a phase, widest blast radius first)\n\n### Phase 1: Data and identity substrate (the contracts everything else stores against)\n- **Unlocks:** Every later feature, because they all read or write the document format, the permission model or the wire protocol.\n- **Depends on:** Phase 0 proving that a Yjs update can round-trip through auth, the sync server and Postgres in production.\n- **Tasks (widest → narrowest):**\n  1. **Document data contract.** A ProseMirror/TipTap schema v1 stored as a `Y.XmlFragment`. Start minimal: paragraph, heading 1–3, bulleted and numbered lists, bold, italic, link. Every document records its `schema_version`, and there is a forward-migration hook. Changing this later means migrating every stored document, so it comes first.\n  2. **Tenant and permission model.** Workspace → document → role (owner, editor, commenter, viewer). Row-level security on every table. The sync server checks permissions **on every incoming message, not only at connect**, so a viewer's edits are dropped.\n  3. **Wire protocol envelope.** The Yjs sync protocol wrapped in an envelope carrying `protocol_version`, with a server-side rule for rejecting clients that are too old.\n  4. **Storage model.** Append-only `doc_updates` plus a `doc_snapshots` table, and a compaction job that merges the log into a snapshot and trims it.\n  5. **Revocation semantics.** Edits from a user whose access was revoked are rejected and never broadcast. This is documented as a product decision.\n- **Exit check:**\n  - A seeded fuzz test with 50 simulated clients making 10k random concurrent edits ends with byte-identical document states.\n  - Rebuilding a document from snapshot plus log equals the live state.\n  - Cross-workspace reads fail under row-level security in an automated test.\n  - A viewer's edit is dropped and logged.\n\n### Phase 2: Sync correctness under failure\n- **Unlocks:** Running more than one sync server and deploying without losing edits. It also makes the rich-text work in Phase 3 safe to build.\n- **Depends on:** The proven data contract and storage model from Phase 1.\n- **Tasks (widest → narrowest):**\n  1. **Confirmation and durability rules.** Clients keep unconfirmed edits locally and resend them after a reconnect. Duplicate resends are harmless because Yjs updates can be applied more than once.\n  2. **Fan-out across servers.** Redis pub/sub (the Hocuspocus Redis extension) is added, and two or more sync servers are proven to converge.\n  3. **Reconnect and resync.** After a reconnect, client and server exchange only the missing changes (state-vector diff), not the whole document.\n  4. **Divergence detector.** Clients periodically send a hash of their document state.
