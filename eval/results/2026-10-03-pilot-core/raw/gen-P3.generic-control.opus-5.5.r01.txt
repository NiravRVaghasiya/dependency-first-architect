Instead I've built the plan on a set of defaults, listed in §5. The four defaults that matter most are: the services **already run on Kubernetes**, the source is on **GitHub**, there is **one repo per service**, and a **platform team of about 4 engineers** does the work. If any of these is wrong, the plan changes in a big way. The questions at the end say how.\n\n---\n\n## 1. Summary\n\n- **What's being built:** a shared build-and-deploy platform. Every one of the ~50 services goes from commit to production through the same audited, reversible path. Product teams get their changes out faster and more safely, and the platform team has one system to maintain instead of 50 sets of scripts.\n- **Shape:** CI runs on **GitHub Actions** using central, versioned *reusable workflows* (shared pipeline definitions that service repos call). Each build produces one signed container image. Deployment uses **GitOps** (the cluster pulls its desired state from a Git repo): a central `deploy-config` repo says which image runs in which environment, and **Argo CD** applies it to the dev, staging and prod clusters. A release moves between environments by committing the *same image digest* into the next environment's folder.\n- **Key decisions:**\n  1. **GitOps (pull) instead of CI running `helm upgrade` (push).** CI never holds prod credentials, every prod change is a Git commit, and rollback is `git revert`.\n  2. **The platform contract is narrow:** \"produce a signed image in our registry, deploy through `deploy-config`.\" The standard pipelines (\"golden paths\") cover the common cases. Unusual services can build however they like, as long as they meet the contract. This is what makes moving all 50 possible.\n  3. **Build once, promote the same digest.** No rebuilding per environment.\n  4. **Two Argo CD instances:** one for non-prod and one inside prod. This limits how far a mistake can spread.\n  5. **Move services in waves,** archetype by archetype, starting with the most common, simplest kind. One service at a time switches its prod deploys over, and the old pipeline stays available until the end.\n- **Milestone 1 (3–5 weeks):** one real, low-risk production service goes commit → dev → staging → prod through the new platform, with a rollback demonstrated and timed. In the same milestone, four spikes check the riskiest unknowns: database migrations, build speed, private network access from CI, and environment config baked into images. A full inventory of all 50 services is also done.\n- **Top risks:** migration speed depends on product teams having time (the critical path); the long tail of unusual services; the database-migration pattern; and security reviews holding up prod access for Argo CD.\n- **Total timeline:** roughly **17–25 weeks** for 4 platform engineers plus 0.5–3 days of effort per service from the owning team. This is a rough guide, not a commitment.\n\n## 2. Context and Goals\n\n- **Problem (assumed):** today the 50 services ship through a mix of Jenkins jobs, shell scripts and manual `kubectl`/`helm` steps. Each team maintains its own. Rollback is ad hoc, nobody can easily answer \"what is running in prod and who approved it,\" security scanning is patchy, and every new service copies someone else's pipeline.\n- **Goals:**\n  - All 50 services deploy to prod only through the platform.\n  - A standard new service gets a working pipeline in under an hour.\n  - Rollback takes one action and finishes within 5 minutes.\n  - Every prod change can be traced to a commit, a reviewer and a signed image.\n- **Non-goals:**\n  - Rewriting service code beyond what it takes to externalise config.\n  - Owning each team's integration test suites. The platform provides the hook to run them, not the tests.\n  - Building a developer portal (Backstage) or per-PR preview environments. Both are deferred (§17).\n  - Multi-cloud or multi-region deploy orchestration.\n  - Infrastructure provisioning for application teams (databases and queues) beyond what CD needs.\n- **Success measures:** the four DORA metrics (standard delivery measures), measured per service from M2 onwards, compared with a baseline collected during the M1 inventory:\n  - deployment frequency\n  - lead time for changes\n  - change failure rate\n  - time to restore\n\n  Also: the number of services onboarded each week, and product-team satisfaction from a two-question survey after each wave.\n\n## 3. These are hard to change later and slowed down by security review.\n5. **Adoption.** Product teams have to spend time on this. If the templates are too rigid, teams won't move. If they're too loose, they won't be standard.\n\n## 4. Current State\n\n**Nothing inspected:** the workspace is empty. Component Details\n\n**`platform-workflows`.**\n- **What it holds:**\n  - `build-<lang>.yml` for each supported language: checkout, dependency cache, test, `docker buildx` with a registry cache, Trivy scan, syft SBOM, cosign keyless signing, and push with the tag `sha-<gitsha>`.\n  - `publish.yml`: the escape hatch for custom builds. It signs and pushes an image the team built itself.\n  - `promote.yml`: writes to `deploy-config` through `deploy-bot`.\n- **What it does not do:** run integration suites (teams pass in a `smoke-test-command`), or deploy to clusters.\n- **Versioning:** tagged `v1.x.y`. Services pin `@v1`, and Renovate keeps the pins up to date.\n- **Breaking changes:** a breaking change means `v2`, released with migration notes, with `v1` supported for 8 weeks.\n- **Hardening:** third-party actions are pinned by SHA, `permissions:` is minimal by default, and `pull_request_target` is never used.\n- **Failure:** a bad template release is caught by the fixture repos (§14) before teams' Renovate bumps land.\n\n**`deploy-config`.**\n- **Layout:** `envs/<env>/<service>/values.yaml` (image digest plus environment values) and `envs/<env>/<service>/chart.yaml` (pinned chart version).\n- **App creation:** an Argo CD ApplicationSet with a Git directory generator creates one Application per folder. Onboarding a service means adding folders.\n- **Write rules:**\n  - `deploy-bot` writes to dev and staging directly.\n  - Prod changes go through a PR with CODEOWNERS set per service folder, so the owning team approves.\n  - Branch protection requires the `validate` check (kubeconform plus Helm schema) to pass.\n- **Load:** about 250 commits/day at peak (50 services × about 5 promotions). That's fine for Git. Conflicts are handled by rebase-and-retry in `promote.yml` (3 attempts).\n\n**Argo CD (two instances).**\n- `argocd-nonprod` runs in the staging cluster and manages dev and staging. `argocd-prod` runs in the prod cluster and only reads `envs/prod/`.\n- Login uses the organisation's identity provider (SSO). There is one AppProject per team, which limits each team to its own namespaces.\n- **Sync settings:**\n  - Dev and staging auto-sync with self-heal.\n  - Prod auto-syncs after the PR merges, so the PR is the gate.\n  - Automatic pruning is off in prod until M3.\n- **If Argo CD is down,** running workloads keep serving and only new deploys stop. Recovery is a Terraform/Helm reinstall: its state lives in Git.\n\n**Shared chart `platform-charts/service`.**\n- **What it renders:** a Deployment (rolling update with `maxUnavailable: 0`, required readiness and liveness probes, required resource requests), Service, an optional HPA (horizontal pod autoscaler) and Ingress, a PodDisruptionBudget, an `ExternalSecret`, and an optional pre-sync migration Job (see §9 Flow D).\n- **Escape hatch:** `extraManifests`, or a team-owned chart, as long as it passes Kyverno.\n\n**Runners.** GitHub-hosted runners are the default, using 4-core runners for container builds. ARC on a non-prod cluster is used only if spike S2 or S3 shows we need it: for private network access or for slow builds.\n\n**Kyverno.** Three policies:\n1. Images must come from our registry and carry a valid cosign signature.\n2. No `:latest` tag.\n3. Resource requests must be set.\n\nEach policy starts in **audit** mode and switches to **enforce** per namespace once the service is onboarded (M3), then cluster-wide (M4).\n\n## 8. Data Design\n\n| Entity | System of record | Writer(s) | Retention |\n|---|---|---|---|\n| Service metadata | `service.yaml` in the service repo | Owning team | Life of the service |\n| Pipeline definition | `platform-workflows`, `platform-charts` | Platform team | Git history |\n| Pipeline run and logs | GitHub Actions | GitHub | 90 days (GitHub default). Prod-relevant run metadata exported to long-term logs for 1 year (assumed audit need). |\n| Artifact (image, SBOM, signature) | Container registry | CI only, via OIDC role | Keep the last 30 per service, plus anything deployed to prod in the last 12 months (lifecycle rule) |\n| Desired deployment state | `deploy-config` | `deploy-bot` (dev/staging), human-approved PR (prod) | Git history, kept indefinitely: this is the audit trail |\n| Actual deployment state and sync history | Argo CD (derived from Git) | Argo CD | Rebuildable from Git |\n| Deploy events and DORA metrics | Existing metrics/logging stack | Argo CD notifications plus a GitHub webhook collector | 13 months |\n| Secrets | Cloud secret manager | Service owners (through IaC or the console with audit logging) | Per secret policy |\n\n- **Consistency:** `deploy-config` is the single source of truth, and Argo CD only reads it. Promotions are serialised per service and environment using a GitHub Actions `concurrency: deploy-<svc>-<env>` group, so the newest run wins.\n- **No secrets in Git.** `values.yaml` holds secret *references* only. GitHub secret scanning with push protection is on for all repos.\n- **Schema evolution:** the `values.schema.json` file in the shared chart is versioned with the chart. New fields must have defaults.\n\n## 9. Key Flows\n\n**A. PR feedback (target p90 ≤ 10 min).**\n1. A PR is opened and the service's `ci.yml` calls `build-<lang>.yml@v1`.\n2. The workflow runs tests, a buildx build (registry cache, nothing pushed), a Trivy scan (report-only until M3) and `service.yaml` validation.\n3. Status checks are posted back to the PR.\n\n**B. Merge → prod.**\n1. On merge to `main`, the image is built once, pushed as `sha-<gitsha>`, then given an SBOM and signed. The digest `sha256:…` is the output.\n2. `promote.yml` (env=dev) uses `deploy-bot` to commit the digest to `envs/dev/<svc>/values.yaml`.\n3. `argocd-nonprod` syncs. The workflow waits for Healthy (timeout 10 min), then runs the service's `smoke-test-command` against dev.\n4. On success, the same steps repeat for staging.\n5. On staging success, `deploy-bot` opens a PR to `envs/prod/<svc>/` with a link to the change log and the staging results. CODEOWNERS asks the owning team to approve.\n6. On merge, `argocd-prod` syncs. The Notifications controller sends a deploy event (service, digest, commit, approver) to the metrics stack and the team's channel.\n\n**C. Failure path: a prod deploy turns out bad.**\n1. **New pods fail readiness.** Because `maxUnavailable: 0`, the old pods keep serving and the rollout stalls. Argo CD marks the app Degraded and a notification alerts the owning team's on-call.\n2. **New pods pass readiness, but the error rate rises.** The service's existing alert fires, and deploy-event annotations on its dashboards point to the cause.\n3. **Rollback:**\n   - On-call runs `gh workflow run rollback.yml -f service=<svc> -f env=prod`. This opens and auto-approves a revert PR, using a dedicated emergency-approver rule, back to the previous digest. Alternatively, they run `git revert` by hand.\n   - Argo CD syncs the previous digest.\n   - Target: ≤ 5 min from decision to old version serving. This is measured in T11.\n4. **If a non-reversible schema migration ran**, rolling back the image is safe only because of expand/contract (see D). This is the reason D is a spike in M1.\n\n**D. Database migration (pattern checked by spike S1).**\n1. The chart renders a `migrate` Job as an Argo CD `PreSync` hook, using the same image and the service's own tool (Flyway, Liquibase, Alembic, etc.).\n2. If the Job fails, the sync fails, the Deployment doesn't change and the old version keeps serving.\n3. The rule is expand/contract. Each release's migrations must stay compatible with the previous image version. Destructive changes ship in a later release. A PR-time lint check in `build-<lang>.yml` flags `DROP`/`RENAME` for supported tools.\n\n**E. Failure path: GitHub Actions or GitHub is down.**\n- Running services are unaffected.\n- **If only Actions is down:** humans can commit digests to `deploy-config` directly through a PR. Argo CD still pulls.\n- **If all of GitHub is down:** a platform on-call engineer can use Argo CD's \"rollback to previous synced revision\" for an emergency rollback only.\n- Both paths are documented in `platform-docs/runbooks/break-glass.md` and tested in T13.\n\n## 10. Cross-Cutting Concerns\n\n**Security (M1 basics, M3 enforce).**\n- **Identity:**\n  - GitHub OIDC to a cloud role. The role can push to the registry only and is scoped by repo and branch claim.\n  - `deploy-bot` GitHub App can write only to `deploy-config` contents and PRs.\n  - Argo CD uses SSO with RBAC per team.\n- **Top threats:**\n  1. **Compromised CI deploys to prod.** CI has no cluster credentials, prod needs an approved PR, and branch protection plus CODEOWNERS guard `envs/prod/`.\n  2. **Malicious dependency or image.** Trivy (blocks on critical CVEs from M3, with an expiring exceptions file), SBOM, signatures and Kyverno verification.\n  3. **Workflow injection.** Actions pinned by SHA, least-privilege `permissions:`, no `pull_request_target`, fork PRs get no secrets, and untrusted inputs are never interpolated straight into `run:` lines.\n  4. **Secret leakage.** ESO from the secret manager, no secrets in Actions except the minimal bootstrap, and push protection on.\n  5. **Argo CD takeover.** No public endpoint for `argocd-prod`, SSO only, local admin disabled, and audit logs shipped out.\n\n**Reliability (M1 runbooks, M2 SLO dashboard).**\n- Platform SLO: 99.5% CI success rate excluding test failures, and ≤ 15 min for a merge to reach Healthy in dev.\n- Every wait step in a workflow has a timeout. `promote.yml` retries with backoff (it's idempotent: writing the same digest twice does nothing).\n- Deploys are safe by default: `maxUnavailable: 0`, required readiness probes and PDBs.\n\n**Observability (M1 deploy events, M2 dashboards, M3 DORA).**\n- Argo CD notifications plus a GitHub `workflow_run` webhook feed deploy and pipeline events (service, environment, digest, commit, approver, duration, result) into the existing metrics/logging stack.\n- Dashboards: pipeline duration p50/p90 per service, failure rate per template version, and the four DORA metrics.\n- Alerts:\n  - to the platform team: CI success rate below 95% over 1 h; Argo CD unable to reach Git or a cluster\n  - to the owning team: an app Degraded for more than 10 min\n\n**Performance and capacity (spike S2 in M1, check in M3).**\n- Expected peak: about 40–60 concurrent jobs during working hours.\n- Likely bottleneck: container builds of large JVM services. Mitigations are registry layer caching, dependency caching, and 4–8 core runners for heavy builds.\n- Check: run the slowest five builds after each template change and track p90.\n\n**Cost (M2 tagging, M3 review).**\n- Rough estimate: about 200k Actions minutes/month at about $0.008–0.016/min comes to about $1.6–3.2k. Registry storage is under $100. Argo CD, Kyverno and ESO add about $300–600 of cluster capacity. Total about $2–4k/month.\n- Controls: cancel superseded PR runs (`concurrency: cancel-in-progress`), registry lifecycle rules, a monthly Actions spend alert at $4k, and resources tagged `team=platform,component=cicd`.\n\n**Operations (M1 runbooks, M2 support model).**\n- **Platform team** owns the templates, `deploy-config` structure, Argo CD, Kyverno and ESO. Business-hours support goes through a `#platform-help` channel with a weekly rotating \"platform shield\" engineer. Off-hours they cover only \"Argo CD prod down,\" which pages the platform on-call.\n- **Product teams** own their deploys, rollbacks and smoke tests.\n- Runbooks in `platform-docs/runbooks/`: `rollback.md`, `break-glass.md`, `argocd-recovery.md`, `onboarding.md`.\n\n**AI-specific concerns:** not applicable, because no AI components are part of this platform.\n\n## 12. It signs and pushes an image the team built itself.\n  - `promote.yml`: writes to `deploy-config` through `deploy-bot`.\n- **What it does not do:** run integration suites (teams pass in a `smoke-test-command`), or deploy to clusters.\n- **Versioning:** tagged `v1.x.y`. Services pin `@v1`, and Renovate keeps the pins up to date.\n- **Breaking changes:** a breaking change means `v2`, released with migration notes, with `v1` supported for 8 weeks.\n- **Hardening:** third-party actions are pinned by SHA, `permissions:` is minimal by default, and `pull_request_target` is never used.\n- **Failure:** a bad template release is caught by the fixture repos (§14) before teams' Renovate bumps land.\n\n**`deploy-config`.**\n- **Layout:** `envs/<env>/<service>/values.yaml` (image digest plus environment values) and `envs/<env>/<service>/chart.yaml` (pinned chart version).\n- **App creation:** an Argo CD ApplicationSet with a Git directory generator creates one Application per folder. Onboarding a service means adding folders.\n- **Write rules:**\n  - `deploy-bot` writes to dev and staging directly.\n  - Prod changes go through a PR with CODEOWNERS set per service folder, so the owning team approves.\n  - Branch protection requires the `validate` check (kubeconform plus Helm schema) to pass.\n- **Load:** about 250 commits/day at peak (50 services × about 5 promotions). That's fine for Git. Conflicts are handled by rebase-and-retry in `promote.yml` (3 attempts).\n\n**Argo CD (two instances).**\n- `argocd-nonprod` runs in the staging cluster and manages dev and staging. `argocd-prod` runs in the prod cluster and only reads `envs/prod/`.\n- Login uses the organisation's identity provider (SSO). There is one AppProject per team, which limits each team to its own namespaces.\n- **Sync settings:**\n  - Dev and staging auto-sync with self-heal.\n  - Prod auto-syncs after the PR merges, so the PR is the gate.\n  - Automatic pruning is off in prod until M3.\n- **If Argo CD is down,** running workloads keep serving and only new deploys stop. Recovery is a Terraform/Helm reinstall: its state lives in Git.\n\n**Shared chart `platform-charts/service`.**\n- **What it renders:** a Deployment (rolling update with `maxUnavailable: 0`, required readiness and liveness probes, required resource requests), Service, an optional HPA (horizontal pod autoscaler) and Ingress, a PodDisruptionBudget, an `ExternalSecret`, and an optional pre-sync migration Job (see §9 Flow D).\n- **Escape hatch:** `extraManifests`, or a team-owned chart, as long as it passes Kyverno.\n\n**Runners.** GitHub-hosted runners are the default, using 4-core runners for container builds. ARC on a non-prod cluster is used only if spike S2 or S3 shows we need it: for private network access or for slow builds.\n\n**Kyverno.** Three policies:\n1. Images must come from our registry and carry a valid cosign signature.\n2. No `:latest` tag.\n3. Resource requests must be set.\n\nEach policy starts in **audit** mode and switches to **enforce** per namespace once the service is onboarded (M3), then cluster-wide (M4).\n\n## 8. Data Design\n\n| Entity | System of record | Writer(s) | Retention |\n|---|---|---|---|\n| Service metadata | `service.yaml` in the service repo | Owning team | Life of the service |\n| Pipeline definition | `platform-workflows`, `platform-charts` | Platform team | Git history |\n| Pipeline run and logs | GitHub Actions | GitHub | 90 days (GitHub default). Prod-relevant run metadata exported to long-term logs for 1 year (assumed audit need). |\n| Artifact (image, SBOM, signature) | Container registry | CI only, via OIDC role | Keep the last 30 per service, plus anything deployed to prod in the last 12 months (lifecycle rule) |\n| Desired deployment state | `deploy-config` | `deploy-bot` (dev/staging), human-approved PR (prod) | Git history, kept indefinitely: this is the audit trail |\n| Actual deployment state and sync history | Argo CD (derived from Git) | Argo CD | Rebuildable from Git |\n| Deploy events and DORA metrics | Existing metrics/logging stack | Argo CD notifications plus a GitHub webhook collector | 13 months |\n| Secrets | Cloud secret manager | Service owners (through IaC or the console with audit logging) | Per secret policy |\n\n- **Consistency:** `deploy-config` is the single source of truth, and Argo CD only reads it. Promotions are serialised per service and environment using a GitHub Actions `concurrency: deploy-<svc>-<env>` group, so the newest run wins.\n- **No secrets in Git.** `values.yaml` holds secret *references* only. GitHub secret scanning with push protection is on for all repos.\n- **Schema evolution:** the `values.schema.json` file in the shared chart is versioned with the chart. New fields must have defaults.\n\n## 9. Key Flows\n\n**A. PR feedback (target p90 ≤ 10 min).**\n1. A PR is opened and the service's `ci.yml` calls `build-<lang>.yml@v1`.\n2. The workflow runs tests, a buildx build (registry cache, nothing pushed), a Trivy scan (report-only until M3) and `service.yaml` validation.\n3. Status checks are posted back to the PR.\n\n**B. Merge → prod.**\n1. On merge to `main`, the image is built once, pushed as `sha-<gitsha>`, then given an SBOM and signed. The digest `sha256:…` is the output.\n2. `promote.yml` (env=dev) uses `deploy-bot` to commit the digest to `envs/dev/<svc>/values.yaml`.\n3. `argocd-nonprod` syncs. The workflow waits for Healthy (timeout 10 min), then runs the service's `smoke-test-command` against dev.\n4. On success, the same steps repeat for staging.\n5. On staging success, `deploy-bot` opens a PR to `envs/prod/<svc>/` with a link to the change log and the staging results. CODEOWNERS asks the owning team to approve.\n6. On merge, `argocd-prod` syncs. The Notifications controller sends a deploy event (service, digest, commit, approver) to the metrics stack and the team's channel.\n\n**C. Failure path: a prod deploy turns out bad.**\n1. **New pods fail readiness.** Because `maxUnavailable: 0`, the old pods keep serving and the rollout stalls. Argo CD marks the app Degraded and a notification alerts the owning team's on-call.\n2. **New pods pass readiness, but the error rate rises.** The service's existing alert fires, and deploy-event annotations on its dashboards point to the cause.\n3. **Rollback:**\n   - On-call runs `gh workflow run rollback.yml -f service=<svc> -f env=prod`. This opens and auto-approves a revert PR, using a dedicated emergency-approver rule, back to the previous digest. Alternatively, they run `git revert` by hand.\n   - Argo CD syncs the previous digest.\n   - Target: ≤ 5 min from decision to old version serving. This is measured in T11.\n4. **If a non-reversible schema migration ran**, rolling back the image is safe only because of expand/contract (see D). This is the reason D is a spike in M1.\n\n**D. Database migration (pattern checked by spike S1).**\n1. The chart renders a `migrate` Job as an Argo CD `PreSync` hook, using the same image and the service's own tool (Flyway, Liquibase, Alembic, etc.).\n2. If the Job fails, the sync fails, the Deployment doesn't change and the old version keeps serving.\n3. The rule is expand/contract. Each release's migrations must stay compatible with the previous image version. Destructive changes ship in a later release. A PR-time lint check in `build-<lang>.yml` flags `DROP`/`RENAME` for supported tools.\n\n**E. Failure path: GitHub Actions or GitHub is down.**\n- Running services are unaffected.\n- **If only Actions is down:** humans can commit digests to `deploy-config` directly through a PR. Argo CD still pulls.\n- **If all of GitHub is down:** a platform on-call engineer can use Argo CD's \"rollback to previous synced revision\" for an emergency rollback only.\n- Both paths are documented in `platform-docs/runbooks/break-glass.md` and tested in T13.\n\n## 10. Cross-Cutting Concerns\n\n**Security (M1 basics, M3 enforce).**\n- **Identity:**\n  - GitHub OIDC to a cloud role. The role can push to the registry only and is scoped by repo and branch claim.\n  - `deploy-bot` GitHub App can write only to `deploy-config` contents and PRs.\n  - Argo CD uses SSO with RBAC per team.\n- **Top threats:**\n  1. **Compromised CI deploys to prod.** CI has no cluster credentials, prod needs an approved PR, and branch protection plus CODEOWNERS guard `envs/prod/`.\n  2. **Malicious dependency or image.** Trivy (blocks on critical CVEs from M3, with an expiring exceptions file), SBOM, signatures and Kyverno verification.\n  3. **Workflow injection.** Actions pinned by SHA, least-privilege `permissions:`, no `pull_request_target`, fork PRs get no secrets, and untrusted inputs are never interpolated straight into `run:` lines.\n  4. **Secret leakage.** ESO from the secret manager, no secrets in Actions except the minimal bootstrap, and push protection on.\n  5. **Argo CD takeover.** No public endpoint for `argocd-prod`, SSO only, local admin disabled, and audit logs shipped out.\n\n**Reliability (M1 runbooks, M2 SLO dashboard).**\n- Platform SLO: 99.5% CI success rate excluding test failures, and ≤ 15 min for a merge to reach Healthy in dev.\n- Every wait step in a workflow has a timeout. `promote.yml` retries with backoff (it's idempotent: writing the same digest twice does nothing).\n- Deploys are safe by default: `maxUnavailable: 0`, required readiness probes and PDBs.\n\n**Observability (M1 deploy events, M2 dashboards, M3 DORA).**\n- Argo CD notifications plus a GitHub `workflow_run` webhook feed deploy and pipeline events (service, environment, digest, commit, approver, duration, result) into the existing metrics/logging stack.\n- Dashboards: pipeline duration p50/p90 per service, failure rate per template version, and the four DORA metrics.\n- Alerts:\n  - to the platform team: CI success rate below 95% over 1 h; Argo CD unable to reach Git or a cluster\n  - to the owning team: an app Degraded for more than 10 min\n\n**Performance and capacity (spike S2 in M1, check in M3).**\n- Expected peak: about 40–60 concurrent jobs during working hours.\n- Likely bottleneck: container builds of large JVM services. Mitigations are registry layer caching, dependency caching, and 4–8 core runners for heavy builds.\n- Check: run the slowest five builds after each template change and track p90.\n\n**Cost (M2 tagging, M3 review).**\n- Rough estimate: about 200k Actions minutes/month at about $0.008–0.016/min comes to about $1.6–3.2k. Registry storage is under $100. Argo CD, Kyverno and ESO add about $300–600 of cluster capacity. Total about $2–4k/month.\n- Controls: cancel superseded PR runs (`concurrency: cancel-in-progress`), registry lifecycle rules, a monthly Actions spend alert at $4k, and resources tagged `team=platform,component=cicd`.\n\n**Operations (M1 runbooks, M2 support model).**\n- **Platform team** owns the templates, `deploy-config` structure, Argo CD, Kyverno and ESO. Business-hours support goes through a `#platform-help` channel with a weekly rotating \"platform shield\" engineer. Off-hours they cover only \"Argo CD prod down,\" which pages the platform on-call.\n- **Product teams** own their deploys, rollbacks and smoke tests.\n- Runbooks in `platform-docs/runbooks/`: `rollback.md`, `break-glass.md`, `argocd-recovery.md`, `onboarding.md`.\n\n**AI-specific concerns:** not applicable, because no AI components are part of this platform.\n\n## 12. Rollout, Migration, and Rollback\n\n- **Rollout:** by archetype in waves (§12).
