Core Domain Model\n\n```\nTenant (account)\n ├── BillingProfile (currency, tax IDs, address, timezone, invoice settings)\n ├── PaymentMethod (PSP token only, never raw PAN)\n ├── Subscription\n │    ├── status, billing_anchor, current_period_start/end, cancel_at\n │    └── SubscriptionItem → PriceVersion (quantity for seats)\n ├── UsageEvent (raw) → UsageAggregate (per meter, per period)\n ├── Invoice (draft | open | paid | void | uncollectible)\n │    └── InvoiceLine (price_version_id, qty, unit_amount, period, tax lines)\n ├── CreditNote, CreditGrant (prepaid/promotional credits)\n └── LedgerAccount (AR, cash, credits, deferred revenue …)\n\nProduct → Price → PriceVersion (immutable once used)\nMeter (event_name, aggregation: sum|count|max|unique_count|last)\n```\n\n### Invariants\n\n1. **Money is stored as integer minor units plus an ISO currency code.** Never use floats. Use decimals with explicit rounding rules for sub-cent unit prices such as $0.0004/API call, and round once at the invoice line.\n2. **Price versions are immutable.** Changing a price creates a new version. Existing subscriptions keep their version until they are migrated on purpose. Grandfathering then works by default.\n3. **Finalized invoices are immutable.** Corrections are made with credit notes or a new invoice, never by editing.\n4. **The ledger is the source of truth for balances.** It is double-entry and append-only, and every entry has a `source_type/source_id` (invoice, payment, refund, credit note). Balances are derived from it and can be cached, but they are always rebuildable.\n5. **Every write API accepts an `Idempotency-Key`.** Store `(tenant_id, key) → response` for at least 24 hours.\n\n---\n\n## 4. Multi-Tenancy Strategy\n\n| Concern | Approach |\n|---|---|\n| Data isolation | `tenant_id` on every row, enforced with **Postgres Row-Level Security** plus a tenant-scoped DB session (`SET app.tenant_id`). Defense in depth: also enforce it in the repository layer. |\n| Deployment model | **Pooled** by default (shared schema). **Silo** option (dedicated DB/cell) for enterprise or regulated tenants. Abstract this behind a tenant→cell routing table from day one. |\n| Noisy neighbors | Per-tenant rate limits at the gateway. Usage Kafka topics partitioned by `tenant_id`, with hot tenants moved to dedicated partitions. Per-tenant concurrency caps in the billing scheduler. |\n| Configuration | Per-tenant settings: billing timezone, invoice numbering sequence, dunning policy, tax behavior, branding. |\n| Encryption | Encrypt PII at rest. For Model B, use per-tenant data keys (KMS envelope encryption) so a tenant can be crypto-shredded. |\n| Model B extras | Two-level tenancy (`platform_tenant_id`, `customer_id`), per-tenant PSP credentials (e.g. Stripe Connect accounts), per-tenant webhooks and API keys, and strict per-tenant export/audit. |\n\n**Cell architecture at scale:** group tenants into cells. Each cell has its own DB, workers and Kafka partitions, with a global control plane for routing and the catalog. This limits the blast radius of an outage and lets you scale horizontally.\n\n---\n\n## 5. Key Flows\n\n### 5.1 Usage Metering Pipeline\n```\nProduct → POST /usage {tenant, meter, value, timestamp, idempotency_key}\n       → validate + enqueue to Kafka (ack fast, durable)\n       → Dedup worker (key: tenant+idempotency_key, Redis/RocksDB w/ TTL ≥ late window)\n       → Aggregation store (ClickHouse): aggregates by tenant/meter/hour\n       → At period close: Rating Engine queries aggregates for [period_start, period_end)\n```\n- **Event time vs. ingest time:** bill on event time. Allow a configurable **late-arrival window** (e.g. 24–72 hours) before the period is finalized. Events that arrive later go into the next invoice as adjustments rather than mutating a closed one.\n- Keep raw events in S3/Parquet so you can **re-rate** after pricing bugs and handle customer disputes (\"show me my calls\").\n- Show customers near-real-time usage from the aggregates, labeled as an estimate.\n\n### 5.2 Billing Clock (Scheduler)\n- Each subscription has `next_action_at`. Sharded workers poll with `SELECT … FOR UPDATE SKIP LOCKED WHERE next_action_at <= now()`, or use a durable workflow engine such as **Temporal**. Temporal is a strong fit for long-running lifecycle logic like trials, dunning and scheduled changes.\n- Actions: renew, end trial, apply a scheduled plan change, close a usage period, finalize a draft invoice, run a dunning step.\n- **Anchor dates:** store them in UTC and compute periods in the billing profile's timezone. Clamp month-end dates (a Jan 31 anchor becomes Feb 28/29, then returns to Mar 31).\n- **Test clocks:** let a subscription run against simulated time. This is essential for testing a year of lifecycle behavior in seconds.\n\n### 5.3 Invoice Generation\n1. Create a **draft** invoice with recurring lines (in advance), usage lines (in arrears), and proration lines from mid-cycle changes.\n2. Apply discounts, then credits (credit grants draw down in a defined priority order and by expiration).\n3. Call the tax service and **snapshot the tax calculation** on the invoice, so a later recalculation never changes history.\n4. Keep the draft open for a review window (e.g. 1 hour, or longer for enterprise/manual review).\n5. **Finalize:** assign a sequential invoice number (gapless per tenant/legal entity where law requires it), render the PDF, post ledger entries (Dr AR / Cr Revenue or Deferred Revenue / Cr Tax Payable), and emit `invoice.finalized`.\n6. Trigger payment if the subscription auto-charges. Otherwise send the invoice with net terms.\n\n### 5.4 Proration\n- Pick **one** policy per tenant and document it: `create_prorations` (credit unused time, charge new time), `none`, or `always_invoice` (bill immediately).\n- Compute proration by seconds, or by days in the billing timezone, against the **old and new price versions**.\n- Downgrades usually take effect at period end. Upgrades take effect immediately. Make this a config setting, not code.\n\n### 5.5 Payments and Dunning\n```\nInvoice open → PaymentIntent (idempotency key = invoice_id + attempt_no)\n  → PSP → sync result OR async webhook\nWebhook → Inbox table (unique on psp_event_id) → processor → ledger + invoice status\n```\n- **Inbox pattern** for PSP webhooks: dedupe on event ID and process in order per object, so out-of-order delivery is handled.\n- **Outbox pattern** for publishing your own events: write them in the same DB transaction as the state change, then relay them.\n- **Dunning:** configurable retry schedule (e.g. days 1, 3, 5, 7). Retry smartly by decline code: never retry hard declines, and use the PSP's smart retry and card account updater where available.
