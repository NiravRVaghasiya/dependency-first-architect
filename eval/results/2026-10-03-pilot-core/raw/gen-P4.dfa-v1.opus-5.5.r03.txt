Walking skeleton (Phase 0)\n**The one real request:** a person opens an issue in a dedicated sandbox repo (`org/agent-sandbox`). Within 60s the agent applies exactly one label from an allow-list (`bug | feature | question | docs`) and posts one comment, \"Triaged as `bug` by issue-agent (trace: …)\".\n\n**Tiers crossed:**\n1. GitHub sends an `issues.opened` webhook.\n2. **Receiver** (FastAPI on Cloud Run / ECS Fargate) verifies the `X-Hub-Signature-256` HMAC and inserts `{delivery_id, installation_id, payload}` into Postgres. A unique constraint on `delivery_id` dedupes retries. It returns 202.\n3. **Worker** dequeues the job, mints an installation token, and re-reads the issue from the GitHub API (no trust in a stale payload).\n4. **LLM call** with a hardcoded prompt. The issue text goes in a delimited untrusted-data block. Output is forced to a JSON schema `{label: enum}`. Hard caps: 2k output tokens, 30s timeout.\n5. **Policy check:** the label must be in the allow-list, or nothing is written.\n6. **GitHub write:** add the label and the comment. Record an audit row.\n\n**Deployed, logged, monitored on day zero:**\n- Terraform for all infra. The container image is built in CI and pinned by digest. The GitHub App private key lives in a cloud KMS / secret manager.\n- An OpenTelemetry trace per delivery (`trace_id` derived from `delivery_id`) spans receiver → queue → worker → LLM → GitHub.\n- Metrics: `webhook_to_action_seconds`, `llm_tokens_total`, `llm_cost_usd`, `jobs_failed_total`, `queue_lag_seconds`.\n- One dashboard and one alert (job failure rate > 10% over 15 min → page).\n- A **global kill switch** (`AGENT_WRITES_ENABLED` flag, checked before every GitHub write) exists from the first commit.\n\n**Exit check:** an issue opened by a human in prod gets the label and comment. Its trace shows every tier, and the latency and cost metrics appear on the dashboard. Flipping the kill switch stops the next write.\n\n## 4. Phases (ordered by dependency; widest blast radius first within each)\n\n**Phase 0 — Walking skeleton** (above).\n\n**Phase 1 — Contracts and identity substrate**\n- **Unlocks:** every later capability; they all write through these contracts.\n- **Depends on:** Phase 0 (a deployed path that proves webhook → worker → GitHub write).\n- **Tasks (widest → narrowest):**\n  1. **Permission model:** finalize the GitHub App scopes, create the bot-owned fork, and set branch protection so the bot cannot push to upstream branches. AI layer\n\n1. **Prompt-injection / guardrail defense** (Phase 2)\n   - **Untrusted inputs:** issue bodies, comments, repo files, test output, retrieved issues. All are placed in delimited data blocks and never in system instructions.\n   - **Trust tiers:**\n     - Anyone: triage only.\n     - Triage+ permission or a maintainer label: resolution allowed.\n     - Write permission: approvals count.\n   - **Allow-lists:** tools are fixed (`search_code`, `read_file`, `edit_file`, `run_tests`, `submit`); arguments are schema-validated and paths stay inside the repo root.
