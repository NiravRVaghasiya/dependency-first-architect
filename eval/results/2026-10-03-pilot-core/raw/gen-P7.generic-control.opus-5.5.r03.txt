Component Details\n\n**`metadata` (hard part 4)**\n- Runs one ExifTool process per chunk of 1,000 files:\n  `exiftool -json -q -fast2 -charset filename=utf8 -DateTimeOriginal -SubSecTimeOriginal -OffsetTimeOriginal -CreateDate -FileType -@ <utf8 argfile>`.\n- The command is built as an argument list with no shell. A timeout of 30 s plus 50 ms per file applies to each chunk.\n- Checks the ExifTool version at startup. A missing or old ExifTool exits with code 2 and installation instructions.\n- A file ExifTool can't read becomes a per-file `Error` and is skipped. If ExifTool itself crashes or times out, the run aborts **before any rename**. All metadata is read before planning starts.\n- It does not interpret dates. That is `dates`' job.\n- The `MetadataReader` protocol lets tests use a fake reader. It would also allow a pure-Python reader later.\n\n**`dates` (hard part 2)**\n- Precedence is `DateTimeOriginal`, then `CreateDate`, then none. `ModifyDate` is never used, because editing software changes it.\n- Rejects zero dates, unparseable dates, dates before 1990, and dates more than 1 day in the future. The bounds are configurable. Each rejected file gets a reason code: `no_date`, `invalid_date` or `suspicious_date`.\n- Returns the date, the tag it came from, and the sub-second value, which is used only to order collisions.\n- Keeps camera-local time as recorded **[A, Q5]**.\n\n**`planner`**\n- A pure function. Each target is `strftime(\"%Y-%m-%d_%H-%M-%S\")` plus the original extension. Colons are not used because Windows forbids them in filenames.\n- Files that map to the same target get `_01`, `_02` and so on. Order is sub-second value, then original filename, so the result is deterministic.\n- Removes no-ops, where the current name already equals the target, so a second run produces nothing.\n- Detects conflicts:\n  - A target that matches an *untouched* file. Suffixes are bumped past it.\n  - A target that differs only in case from an untouched file.\n  - In Milestone 1, any file with same-stem siblings is skipped with reason `has_companions`. This is safe until Milestone 2 adds grouping.\n\n**`executor` and `journal` (hard part 1). Failure and recovery:**\n1. The journal records the full plan, including tool version, run ID, directory, and for each entry the source, temporary name (`.pr-<uuid>.tmp`), destination and file identity (`st_ino`, size, `st_mtime_ns`). It is then fsynced.\n2. **Phase 1** renames every source to its temporary name, then appends the marker `phase1_done` and fsyncs.\n3. **Phase 2** renames every temporary name to its destination, after checking the destination doesn't exist. It then appends `phase2_done` and fsyncs.\n\nHow failures are handled:\n- **Python exception mid-run** (for example a permission error): stop, automatically reverse the completed steps using the journal, and exit with code 1. The report shows which file failed.\n- **Hard crash or power loss:** the next run finds a journal without `phase2_done` and refuses to continue. `photo-rename undo DIR` rebuilds each file's current location by matching file identity at the source, temporary and destination names. This works even for cycles, where matching by name alone is ambiguous. It then reverses the renames.\n- **Undo** builds a reverse plan and runs it through the same executor, so undo is also journaled.\n- **Fsync cost:** only 3 fsyncs per run, so journaling doesn't threaten the 60 s target.\n\n**`scanner`, `report`, `cli`:** routine.\n- Default extension allowlist: `.jpg .jpeg .heic .heif`. Milestone 2 adds RAW formats, `.png`, `.xmp`, `.aae` and `.mov`.\n- Exit codes:\n\n| Code | Meaning |\n|---|---|\n| 0 | Done, or nothing to do |\n| 1 | Aborted, no net change |\n| 2 | Usage or environment error |\n| 3 | Done, but some files were skipped |\n| 4 | Incomplete journal found; run `undo` |\n\n**Scale:** not a driver beyond batching ExifTool calls. A plan for 50k files fits easily in memory.\n\n## 8. Data Design\n\n| Entity | Fields | System of record / writer | Lifetime |\n|---|---|---|---|\n| `FileRecord` | path, stem, ext, size, ino, mtime_ns, siblings | in memory / `scanner` | one run |\n| `DateResult` | datetime \\| None, source_tag, subsec, status, reason | in memory / `dates` | one run |\n| `RenameOp` | src, tmp, dst, identity, group_id | in memory / `planner` | one run |\n| `Plan` | ops[], skips[] (path, reason), conflicts[] | in memory / `planner` | one run |\n| `Journal` | header {format_version: 1, tool_version, run_id, dir, started_at}, ops[], phase markers | `<dir>/.photo-rename/journal-<UTC timestamp>-<run_id>.jsonl` / only `journal` writes it | kept until the user deletes it; `undo` uses the latest by default |\n\n- **Consistency:** there is no multi-file atomicity at the filesystem level. The journal plus file identity provides recoverability instead.\n- **Photo files:** the only change is the rename. Contents and modification times are never touched.\n- **Journal location:** next to the photos, so undo still works if the folder is moved. `--journal-dir` overrides this, for example for read-only folders.\n- **Format evolution:** `format_version` is hard to change, because `undo` must be able to read old journals. New fields are additive only, and readers ignore unknown fields.\n- **Sensitivity:** filenames and paths only. No GPS or other metadata is written to the journal or logs.\n\n## 9. Key Flows\n\n**F1. Preview (default):** `photo-rename ~/Pictures/Trip`\n1. Scan finds 1,240 files.\n2. ExifTool runs in 2 batches.\n3. Dates resolve: 1,198 OK, 30 `no_date`, 12 `has_companions`.\n4. The planner produces 1,150 renames and 48 no-ops, with 6 collision groups suffixed.\n5. The report prints a table and a summary.\n6. Exit code 3. Nothing has been touched.\n\n**F2. Apply:** `photo-rename ~/Pictures/Trip --apply`\n1. Steps 1–4 of F1 run again. Nothing is reused from an earlier preview, because the folder may have changed.\n2. The journal is written and fsynced.\n3. Phase 1, then the `phase1_done` marker.\n4. Phase 2, then the `phase2_done` marker.\n5. Post-run check: the file count in the folder equals the count before, and every destination exists with the same identity.\n6. Exit code 0 or 3.\n\n**F3. Failure: power loss during phase 2**\n1. On restart, the next `photo-rename … --apply` finds a journal without `phase2_done`. It exits with code 4 and the message \"run `photo-rename undo`\".\n2. `undo` loads the journal and locates each file by identity: 700 at their destination, 450 at their temporary name, 0 at their source.\n3. It builds a reverse plan, journals it, and executes it.\n4. All original names are restored. The user can then re-run `--apply`.\n\n**F4. Failure: ExifTool times out on a corrupt file in batch 2**\n- The chunk timeout fires and the run aborts with code 1 before planning. No renames have happened.\n- The message names the batch and suggests `--exclude`. Milestone 2 adds a per-file retry: bisect the failed batch and skip the offending file.\n\n## 10. Component Details\n\n**`metadata` (hard part 4)**\n- Runs one ExifTool process per chunk of 1,000 files:\n  `exiftool -json -q -fast2 -charset filename=utf8 -DateTimeOriginal -SubSecTimeOriginal -OffsetTimeOriginal -CreateDate -FileType -@ <utf8 argfile>`.\n- The command is built as an argument list with no shell. A missing or old ExifTool exits with code 2 and installation instructions.\n- A file ExifTool can't read becomes a per-file `Error` and is skipped. If ExifTool itself crashes or times out, the run aborts **before any rename**. All metadata is read before planning starts.\n- It does not interpret dates. That is `dates`' job.\n- The `MetadataReader` protocol lets tests use a fake reader. It would also allow a pure-Python reader later.\n\n**`dates` (hard part 2)**\n- Precedence is `DateTimeOriginal`, then `CreateDate`, then none. `ModifyDate` is never used, because editing software changes it.\n- Rejects zero dates, unparseable dates, dates before 1990, and dates more than 1 day in the future. The bounds are configurable. Each rejected file gets a reason code: `no_date`, `invalid_date` or `suspicious_date`.\n- Returns the date, the tag it came from, and the sub-second value, which is used only to order collisions.\n- Keeps camera-local time as recorded **[A, Q5]**.\n\n**`planner`**\n- A pure function. Each target is `strftime(\"%Y-%m-%d_%H-%M-%S\")` plus the original extension. Colons are not used because Windows forbids them in filenames.\n- Files that map to the same target get `_01`, `_02` and so on. Order is sub-second value, then original filename, so the result is deterministic.\n- Removes no-ops, where the current name already equals the target, so a second run produces nothing.\n- Detects conflicts:\n  - A target that matches an *untouched* file. Suffixes are bumped past it.\n  - A target that differs only in case from an untouched file.\n  - In Milestone 1, any file with same-stem siblings is skipped with reason `has_companions`. This is safe until Milestone 2 adds grouping.\n\n**`executor` and `journal` (hard part 1). Failure and recovery:**\n1. The journal records the full plan, including tool version, run ID, directory, and for each entry the source, temporary name (`.pr-<uuid>.tmp`), destination and file identity (`st_ino`, size, `st_mtime_ns`).
