Component Details\n\n- **MetadataReader.**\n  - Uses `DateTimeOriginal`, then `DateTimeDigitized`. Also reads `SubSecTimeOriginal`.\n  - Rejects empty values, all-zero values, and anything that won't parse as a date.\n  - Catches every parser exception per file and returns `Missing(reason)`, so one corrupt file can't stop the run.\n  - Reads headers only and never opens files for writing.\n  - Defined as a `Protocol`, so an `ExifToolReader` (using `exiftool -json` in batch mode) can replace it without touching anything else.\n- **Planner.** This is where the hard logic lives.\n  - It works on `(file, capture_time)` pairs plus the set of all names already in the folder, compared case-insensitively.\n  - **Stable names:** if a file's current name is already `base` or `base_N` for its own timestamp, it is left alone. This is what makes re-runs do nothing.\n  - **Occupied names:** a candidate name is taken if any file currently in the folder has it, even a file that is about to be renamed. This rules out rename chains and cycles, at the cost of sometimes adding a suffix that wasn't strictly needed.\n  - **Suffix order:** suffixes go in order of (sub-second, original file name). This is deterministic.\n  - It does no I/O. It doesn't see the folder itself. It only receives the set of existing names from the Scanner.\n- **Executor.**\n  - Before each rename, it checks that the source still exists and that the target is free (case-insensitively), then calls `os.rename`.\n  - On Windows, `os.rename` itself refuses to overwrite. This rules out rename chains and cycles, at the cost of sometimes adding a suffix that wasn't strictly needed.\n  - **Suffix order:** suffixes go in order of (sub-second, original file name). This is deterministic.\n  - It does no I/O. It doesn't see the folder itself. It only receives the set of existing names from the Scanner.\n- **Executor.**\n  - Before each rename, it checks that the source still exists and that the target is free (case-insensitively), then calls `os.rename`.\n  - On Windows, `os.rename` itself refuses to overwrite. On POSIX the remaining check-then-rename race is accepted, because we assume nothing else writes to the folder.\n  - Case-only renames go through a temporary name if Spike B shows they're needed.\n  - **On any OS error it stops.** The journal is left complete up to that point. The user can then re-run, which picks up where it stopped because re-runs skip finished files, or run `undo`.\n- **Journal.**\n  - Before the first rename it writes a header with the tool version, start time and folder.\n  - After each successful rename it appends `{\"from\",\"to\"}`, then flushes and `fsync`s.\n  - The file sits in the photo folder as `.photo-rename-YYYYMMDD-HHMMSS.jsonl`, and the Scanner excludes it.\n  - **Undo** reverses the recorded steps from last to first. It refuses to restore a name that is now taken, and finally appends `{\"undone\": true}`.\n- Scaling isn't a driver. Everything is one pass and in memory.\n\n## 8. Data Design\n\n- **Entities** (frozen dataclasses in `model.py`):\n  - `SourceFile` (path, name, ext, group stem)\n  - `CaptureTime` (naive datetime, subsec, source tag)\n  - `RenameOp` (src, dst)\n  - `Skip` (file, reason: `NO_DATE`, `UNREADABLE`, `ALREADY_NAMED`, `UNSUPPORTED`)\n  - `Plan` (ops, skips)\n- **System of record:** the filesystem for names and the journal for history. The Executor is the only component that writes to either. There is no database.\n- **Consistency:** each rename is atomic. A run as a whole is not, so the journal plus undo, together with re-runs being safe, provide recovery.\n- **Retention:** journals stay until the user deletes them. Deleting a journal means that run can no longer be undone, and the README says so.\n- **Sensitivity:** EXIF can contain GPS coordinates and serial numbers. The tool never logs or stores them. Journals contain only file names.\n- **Schema evolution:** journal lines carry `\"v\":1`, and later versions must still read v1.\n\n## 9. Key Flows\n\n1. **Dry run (default):** `photo-rename D:\\Photos\\Trip`\n   1. Scan the folder.\n   2. Read each file's capture time.\n   3. Build the Plan.\n   4. Print the table and a summary, for example \"812 to rename, 14 already named, 3 skipped (no date)\".\n   5. Exit with code 0. Nothing changes on disk.\n2. **Apply:** `--apply`\n   1. Build the same Plan as the dry run (it's deterministic).\n   2. Show the summary and ask `Rename 812 files? [y/N]`, unless `--yes` was given.\n   3. Write the journal header.\n   4. For each operation: check preconditions, rename, append to the journal and fsync.\n   5. Print the summary and exit with code 0.\n3. **Failure path: interrupted run.** The disk is pulled out at operation 400 of 812.\n   1. The rename for operation 401 raises `OSError`.\n   2. The Executor stops, prints \"400 of 812 renamed; journal at …; run again to continue or `photo-rename undo`\", and exits with code 3.\n   3. Running again finds 400 files already correctly named, skips them, and plans 412.\n   4. Running `undo` instead restores the 400 renamed files to their original names, last to first.\n4. **Failure path: corrupt or date-less file.** The reader returns `Missing(UNREADABLE)` or `Missing(NO_DATE)`. The file appears under \"Skipped\", stays untouched, and the run continues.\n\n## 10.
