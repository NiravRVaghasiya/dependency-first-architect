# Plan: Real-time card-transaction fraud detection

## 1. Classification and constraints

The request leaves out three inputs that would change the order of phases. Rather than stop, I assumed the following. Each line says what changes if the assumption is wrong.
- **A1, our role.** We are a card issuer (or issuer-processor) deciding authorizations. If we are an acquirer or merchant instead, the decision point moves to the gateway or checkout, and PCI scope and label sources change.
- **A2, inline decisions.** "Real-time" means the score affects the approve/decline decision during authorization. If you only want alerts after authorization, V4 and V5 become exit checks and Phase 2 gets much smaller.
- **A3, brownfield.** An authorization host and an existing fraud system ("incumbent": rules engine or vendor score) already run in production. If not, there is no fallback decision, so V4 must fall back to a static rules floor and V7 has no baseline to beat.

- **What:** a streaming pipeline that scores each card authorization within the authorization deadline. It returns approve, step-up or decline with reason codes, and learns from fraud labels (chargebacks, cardholder fraud reports, analyst outcomes).
- **Type:** software, streaming data infrastructure, and a predictive ML model (not generative or agentic). Brownfield. Not a small build: it handles real money and regulated data (PCI DSS, personal data).
- **Dominant constraint:** latency under a hard authorization deadline. Decision correctness is a close second, and PCI DSS shapes the trust boundaries.
- **Worst failure:** the new path wrongly declines legitimate transactions at scale, through a bad model, a bad rule push, or failing closed on timeout. Cardholders get stranded at tills, and that harm cannot be undone. Guarded by V4. The second worst is the card number (PAN) leaking into pipeline stores, guarded by V2.

**Missing inputs:**
- A1, A2 and A3 above.
- 12–18 months of history joinable to fraud labels (tested by V1).
- The scheme timeout value.
- Jurisdiction: data residency, the model-risk regime (e.g. SR 11-7 or the EU equivalent), GDPR Art. 22 on automated decisions, and PSD2 transaction-risk-analysis exemptions if in the EU.
- ML and streaming staffing (needed for the build-vs-buy row).
- The Head of Fraud's uplift target and risk appetite.

**minor defaults:**
- Model family: gradient-boosted trees (LightGBM), served via ONNX Runtime.
- Online store: Aerospike or Redis behind an interface (rebuildable from the log).
- Event log: Kafka with replication factor 3 across availability zones.
- Retraining: monthly.
- Tooling: MLflow registry, OpenTelemetry, Prometheus/Grafana, Argo CD, Terraform.

**N/A:**
- Prompt+RAG vs fine-tune, and hosted vs self-hosted LLM: there is no LLM.
- Tenancy: single issuer (ASSUMPTION).
- Rehost/replatform/refactor: the incumbent is not migrated; the new capability runs alongside it.

## 4. First end-to-end slice (Phase 0)

- **Real request:** a small real purchase on an allow-listed staff test card. The scheme authorization request reaches the auth host. The auth host sends the incumbent's normal response to the network. It also gets the new path's shadow decision (score, reason code, model `stub-0`) and writes it to its audit record.
- **Tiers:**
  - auth-host hook (sync call, 80 ms timeout, token-only payload)
  - scoring service (stub rule over one feature: card transaction count in 24 h)
  - online state store, updated by a Flink job reading the Kafka event topic (fed by the auth-host tap)
  - decision-log topic sunk to the warehouse
  - one test case in the existing case-management tool
  - one test fraud report on the same transaction from the dispute system, joined by network transaction ID (ASSUMED test mode; otherwise moves to Phase 3)
- **Deploy, log, monitor, roll back:**
  - Terraform and Argo CD deploy signed images. The auth-host hook ships through its own change-board release, flag off by default.
  - One OpenTelemetry trace keyed to the auth message ID. Logs carry tokens only and are classified as cardholder-data-environment data.
  - Alerts fire on scoring timeouts.
  - Rollback is an Argo CD revert plus the auth-host flag.
- **Who can reach it:** only allow-listed test-card tokens. The incumbent decides every transaction.

Exit check (V0): see §6.

## 5. Phases

**Phase 1: Event substrate and data boundary (shadow, async only)**
- **Unlocks:** real tokenized traffic for features, replay and load tests.
- **Depends on:** V0, V1.
- **Tasks:**
  1. Discover dependents: the incumbent, case management, the dispute system, cardholder alerting, warehouse feeds. Mark each CONFIRMED or ASSUMED.
  2. Freeze event schema v1 and the decision-log schema (score, reason codes, model and rule versions, feature-vector hash, latency, fallback flag).
  3. Put PAN-boundary controls and continuous data-loss-prevention (DLP) scanning in place and complete the DPIA, then run V2 on the staff cohort.
  4. Run the tap on one auth-host node (V3), then all nodes. Widen mirrored traffic from staff cards to one BIN range to all.
  5. Set retention TTLs once Compliance supplies the figure.
  6. Build replay tooling and record a tokenized traffic corpus.
- **System of record:** the auth host. Sync runs one way, auth host to event log.
- **Rollback:** tap flag per node; purge topics. Nothing affects decisions.
- **Exit check:** V2 and V3 pass; consumer lag < 1 s at peak.

**Phase 2: Decision-safety defenses and budgets**
- **Unlocks:** inline calls at scale and, later, enforcement.
- **Depends on:** Phase 1, V2, V3.
- **Tasks:**
  1. Get the scheme timeout value.
  2. Build fallback in the auth host: hard timeout, incumbent decision on any error, kill switch per segment.
  3. Build a policy layer:
     - restricted action set
     - decline caps
     - a circuit breaker comparing the new decision rate with the incumbent's, per segment
  4. Add ingress validation, an adversarial test suite (card testing, threshold probing, malformed fields) and generic response codes, so the score can't be reverse-engineered from responses.
  5. Enforce four-eyes approval in the pipeline for rule, threshold and model changes.
  6. Build a load harness on the replay corpus (V5).
  7. Run fault injection and a production game day on the staff cohort (V4).
- **Rollback:** everything is behind flags.
- **Exit check:** V4 and V5 pass.

**Phase 3: Features, entity state, labels**
- **Unlocks:** model training.
- **Depends on:** Phase 2, V1, V5 (the feature budget).
- **Tasks:**
  1. Get the uplift target from the Head of Fraud.
  2. Build features in Flink:
     - velocity per card, account, merchant, device, MCC and country
     - deviation from the card's normal spend
     - merchant risk
     - incumbent and network scores
  3. Build the online state store keyed by token.
  4. Backfill by replaying history through the same job.
  5. Build the label pipeline (disputes, fraud reports, analyst outcomes, each with a maturity date).
  6. Check parity (V6) and run the burst-attack replay.
  7. Start the V8 documentation.
- **Rollback:** state is derived and can be rebuilt from the log. Nothing is enforced.
- **Exit check:** V6 passes; a state rebuild drill finishes within RTO.

**Phase 4: Model and decision orchestration (shadow at full traffic)**
- **Unlocks:** enforcement.
- **Depends on:** Phase 3, V4, V5, V6.
- **Tasks:**
  1. Train an out-of-time GBDT, register it, and serve it in-process.
  2. Orchestrate rules, then model, then policy, then reason codes.
  3. Widen the inline shadow call from one node to all.
  4. Run the backtest and 30-day shadow (V7).
  5. Submit for V8.
- **Rollback:** revert the model version in the registry; inline-call flag per node.
- **Exit check:** V7 passes; V5 re-run with the production model passes.

**Phase 5: Enforcement canary and human-in-the-loop**
- **Unlocks:** live fraud prevention.
- **Depends on:** V4, V7, V8; case-management and alerting APIs.
- **Tasks:**
  1. Fix the 2% control holdout.
  2. Wire referrals to the analyst queue and step-up through existing SMS or app alerts. Write outcome lists (confirmed-fraud devices and merchants) only from confirmed outcomes.
  3. Enforce in this order: staff cohort, then 1% of tokens in one segment, then 5%, 25%, 100%.
     - Pick the first segment where the step-up flow exists (e.g. card-not-present).
     - Each step runs ≥ 7 days including a weekend peak.
     - Each step must pass the cohort checks: incremental declines within cap, false-positive ratio ≤ BASELINE, complaints ≤ control, latency within budget.
- **Rollback:** per-cohort flag back to the incumbent, plus the automatic breaker. No point of no return, because the incumbent is kept.
- **Exit check:** all traffic except the holdout is enforced, with every step's checks passed.

**Phase 6: Feedback and retraining**
- **Unlocks:** sustained model quality.
- **Depends on:** Phase 5 with ≥ 60 days of matured labels.
- **Tasks:**
  1. Review labels before training (friendly fraud, analyst error).
  2. Retrain monthly from reproducible snapshots.
  3. Evaluate each challenger with the V7 method, using the holdout to correct selection bias.
  4. Promote with four-eyes approval plus the model-risk change process.
  5. Add drift alerts (population stability index, PSI).
- **Rollback:** the previous champion stays in the registry.
- **Exit check:** one full cycle (retrain, evaluate, promote or reject) completes with lineage recorded.

## 10. Deferred

- **Retiring the incumbent (point of no return).** Pull forward when the new path has run at 100% for ≥ 2 quarters with V7 thresholds holding, or when the vendor contract comes up for renewal. It then needs its own gate: rehearse the static-rules-floor fallback, a go/no-go threshold, approval from the Head of Fraud and CRO, and contract termination named as the point of no return.
- **Segment models and routing (card-present, card-not-present, ATM).** Pull forward when one segment trails the others on V7 metrics by an agreed margin.
- **Graph / fraud-ring features.** Pull forward when ring-driven losses make up a material share of fraud.
- **Deep sequence models.** Pull forward when the GBDT plateaus across two retrain cycles.
- **Multi-region active-active.** Pull forward when the business commits to an availability target that single-region multi-AZ cannot meet.
- **3DS/ACS (online card-authentication) step-up integration.** Pull forward if we run the ACS and card-not-present fraud dominates.
- **LLM analyst assistant.** Pull forward when analyst queue load becomes the bottleneck. It would bring the full generative-AI defenses.
