# BUILD PLAN: `photorename`, a CLI that renames a folder of photos by EXIF capture date

## 1. Classification and constraints
- **What:** A local command-line tool. It reads each photo's EXIF capture date and renames the file to a sortable, date-based name. It can preview the changes first (dry run) and undo them afterwards.
- **Type:** Software. Greenfield. A small build: one developer, no outside service, no money flow, and no regulated data. Photos do contain personal data such as GPS location, but they never leave the machine.
- **Dominant constraint:** Correctness.
- **Worst failure:** A rename overwrites or loses a photo, which may be the only copy. Close behind it: a partial run leaves the folder half-renamed with no way back.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Data integrity | 0 files lost or overwritten; file count and file bytes are the same after a run as before | REQUIREMENT (the request says "renames": a rename keeps every file and its bytes) | V1, V3 |
| Recovery | One `undo <run-id>` restores every original name after a run that finished or was interrupted | ASSUMPTION (basis: without undo, a mistake is permanent) | V1 |
| Throughput | 10,000 photos planned and renamed in ≤ 2 min on a local SSD | ASSUMPTION (basis: ExifTool in batch mode reads headers at hundreds of files per second, and a typical phone dump is a few thousand files). The baseline is recorded in V0. SD cards and network drives will be slower | Phase 1 exit |
| Operational complexity | No services to run; one pipx package plus ExifTool on the user's PATH | ASSUMPTION (that users can install ExifTool; confirm with you) | V0 |

**Missing inputs** (none of these change the phase order):
1. **Formats in scope.** JPEG only, or also HEIC, RAW (CR2/CR3/NEF/ARW/DNG), or video? You supply this; Phase 1 needs it to build the V2 test set. Default: JPEG and HEIC.
2. **Sidecars and catalogs.** Do you use `.xmp` sidecars, iPhone `.aae` edit files, Live Photo `.mov` pairs, or a Lightroom or Apple Photos catalog? Renaming files that a catalog manages breaks the catalog's links. You supply this; Phase 1 needs it.
3. **Operating systems and filesystems.** Windows, macOS, Linux? exFAT SD cards? NAS or SMB shares? This sets the V1 test matrix. Default: all three OSes, plus exFAT.
4. **Naming and time-zone preference.** Default: camera-local time with no time-zone conversion.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| How renames are executed, and what stays consistent | R3: if wrong, photos are overwritten, which cannot be undone | 1. Build the whole plan first. 2. Detect collisions inside the plan and against files already in the folder, including names that differ only by letter case. 3. Write each journal entry and flush it to disk before doing that rename. 4. Rename each file atomically without ever overwriting: hard-link then unlink on POSIX, `os.rename` on Windows (it fails if the target exists). Where hard links aren't supported (exFAT), check that the target doesn't exist, then rename. 5. The batch as a whole is not atomic; undo and resume cover a partial run | No other process writes to the folder during a run. Each primitive refuses to overwrite on every target filesystem | V1 | V1 fails on some filesystem. Then on that filesystem, either refuse `apply` or switch to copy, verify the hash, then delete |
| Naming scheme and date source | R2: once users have renamed whole libraries, changing the scheme means renaming them all again | Name format `YYYY-MM-DD_HH-MM-SS.ext`: hyphens because Windows forbids colons, and the original extension is kept. Date from `DateTimeOriginal`, then `CreateDate`, otherwise skip and report the file. Camera-local time. Same-second collisions get `_01`, `_02`, … in `SubSecTimeOriginal` order, then by original name. Files already named correctly are left alone | You want chronological names, and a file with no EXIF date should be left alone rather than guessed | V2; your sign-off on the dry-run sample in V3 | You want UTC or the offset in the name, or a fallback to file modification time |
| Data-privacy boundary | R3: EXIF holds GPS location, and leaked location can't be taken back | Fully local and no network code. The log and journal record only paths and the date tags used, never GPS or other EXIF. Test photos have GPS stripped (`exiftool -gps:all=`) before they are committed | Nothing needs the network | Cited basis: the code has no network path. A CI test runs the tool with networking disabled and checks the logs for GPS fields | Any feature that needs the network (update check, telemetry). It becomes opt-in and gets its own gate |

**R1 defaults:**
- Language and distribution: Python 3.11+, installed with pipx or `uv tool`, wheels built by GitHub Actions with trusted publishing.
- EXIF reader: use ExifTool rather than writing a parser, via one `exiftool -json` batch call, behind a `MetadataReader` interface.
- Default mode: dry run; real renames need `--apply` plus a confirmation prompt.
- Scope: the top-level folder only.

**N/A:**
- Monolith vs services: it's one process.
- Sync vs async: it's sequential local I/O, and ExifTool batching covers throughput.
- Consistency vs availability: there is no distributed state; per-file consistency is covered in the first row.
- Brownfield and AI rows: greenfield, no AI component.

## 4. Walking skeleton (Phase 0)
- **The one real request:** `photorename ~/Pictures/2024-trip`, a dry run on one real folder.
- **The response:**
  - a table of planned renames, e.g. `IMG_0412.JPG → 2024-07-14_09-31-02.JPG`;
  - skipped files with reasons;
  - a summary line such as `412 planned, 3 skipped (no EXIF date), 0 conflicts`;
  - the exit code;
  - the path of the run log.
- **Tiers it crosses:**
  1. argument parsing;
  2. folder scan;
  3. ExifTool subprocess;
  4. name planner;
  5. reporter (screen output and a log in the per-user state folder, located with `platformdirs`);
  6. executor, stubbed read-only. It refuses to rename, because the guard (V1) doesn't exist yet.
- **Deploy:** pushing tag `v0.0.1` makes GitHub Actions run the tests and publish the wheel. The tool is installed with `pipx install` on clean Windows, macOS, and Linux CI runners and on your machine.
- **Rollback:** reinstall the previous version (`pipx install photorename==<prev>`) and yank the bad release. Rehearsed once, from `v0.0.2` back to `v0.0.1`.
- **Logging and monitoring:** whoever runs the tool sees the result directly:
  - every log starts with a run ID, the tool version, and the ExifTool version;
  - errors on individual files are counted and reported, and the run continues;
  - exit code 2 if any file errored, 3 if ExifTool is missing.
- **Who can reach it:** you and the developer only, through a pre-release version. It can't change anything because no code path writes to the folder.

Exit check (V0): see §6.

## 5. Phases

- **Phase 1: Safe apply and undo**
  - Unlocks: real renames (`--apply`) and `undo`.
  - Depends on: Phase 0 (V0); missing inputs 1–3.
  - Tasks, in order (widest blast radius first):
    1. Define the plan and journal format, with a `schema_version` field, a run ID, and the old path, new path, and status of each file. Undo and resume depend on this.
    2. Build the no-overwrite rename primitive for each OS and filesystem.
    3. Add collision and cycle detection to the planner: case-only clashes on case-insensitive filesystems, existing targets, and same-second bursts. A rename cycle aborts the run.
    4. `--apply`: a confirmation prompt that shows the summary, then journal-first renames.
    5. `undo <run-id>` and `resume <run-id>` after an interrupted run.
    6. Sidecars: rename `.xmp`, `.aae`, and Live Photo `.mov` files that share the photo's base name together with it, per missing input 2.
    7. Run V1 and V2.
    8. Measure throughput against the budget.
  - Rollback: any rename can be reversed with `undo`, using the journal. The release can be reverted by reinstalling the previous version. Later versions must still be able to undo older journals; the schema version makes that possible.
  - Exit check: V1 and V2 pass, and the throughput result is recorded next to the V0 baseline.

- **Phase 2: Real-library rollout and 1.0** (smallest exposure first)
  - Unlocks: renaming your full library, and a public 1.0 release.
  - Depends on: Phase 1 (V1, V2); your verified backup.
  - Tasks, in order:
    1. You confirm the backup.
    2. Dry run across the library; you review it.
    3. `apply` on a full copy of the library, then check hashes, run `undo`, then run `apply` again.
    4. `apply` on one real folder.
    5. `apply` on the remaining folders.
    6. Publish 1.0. The README covers backups, `undo`, and catalog warnings.
  - Rollback: `undo <run-id>` for each run, as long as its journal is kept. **Point of no return:** deleting the journal, or importing the renamed files into a catalog. Guarded by V3 and a README warning.
  - Exit check: V3 passes, and you can see a 1.0 install on all target OSes.

## 10. Deliberately deferred
- **Fallback to file modification time or a date in the filename, for files without EXIF.** Pulled forward if V3 shows many skips and you want them named anyway.
- **Time-zone normalization** (`OffsetTimeOriginal`, GPS time). Pulled forward if you mix photos taken in different time zones and want them in true chronological order.
- **Video files.** QuickTime `CreateDate` is stored in UTC, so videos need their own rules in V2. Pulled forward when videos are in scope.
- **Recursive mode and sorting into `YYYY/MM/` folders.** Pulled forward when your library is nested or you ask for it. Moving files between folders brings new collision risks, so it would extend V1.
- **A standalone binary without ExifTool** (bundled, or a pure-Python reader). Pulled forward when users can't install ExifTool.
- **Renaming that keeps a Lightroom or Apple Photos catalog in sync.** Pulled forward if missing input 2 shows your photos live in a catalog.
