# BUILD PLAN: Autonomous GitHub issue triage and resolution agent

## 1. Classification and constraints
- **What:** An agent that reads new GitHub issues, triages them (labels, duplicates, missing information, routing), and, when a maintainer asks, tries a fix in a sandbox and opens a draft pull request (PR) for a human to review and merge.
- **Type:** AI agent plus software. The service is new, but it runs inside an existing GitHub org with its own workflows, bots, labels and branch protection, so the brownfield rules apply. This is not a small build: it reads untrusted input, spends money and acts on real repos.
- **Dominant constraint:** Correctness and safety of the agent's actions.
- **Worst failure:** An injected issue (or a repo file or test output) steers the agent into leaking secrets or private code, or into getting malicious code toward a default branch. That is supply-chain damage that cannot be undone. V2 guards it, and so do Tradeoff rows 1–3.

**Missing inputs.** I planned on stated assumptions rather than stopping to ask. The first two would change the phase order:
1. **Which repos are in scope.** I assumed internal repos first and public repos last (Phase 7). If only internal repos are in scope, Phase 7 and V6 drop. If public repos come first, V6's controls move into Phase 1.
2. **What "resolve" means.** I assumed it means a draft PR that a human merges, and the agent cannot merge. If autonomous merging is required, it needs a new R3 tradeoff row and its own gate, and every phase after Phase 5 is re-planned.
3. Which model providers are approved, and on what data-use terms (V1).
4. Whether a label taxonomy exists, and whether repos have tests that run in a container. Repos without runnable tests are excluded from fixes.
5. The monthly budget and engineer-hour cost (V5).
6. Who approves agent comments in each repo. I assumed users with maintain permission or CODEOWNERS.

## 3. Tradeoff gates

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| 1. Credential model | R3: this is the trust boundary; a broad leaked token compromises the org | A GitHub App. Each job mints its own installation token, scoped to one repo. On the base repo the token gets `issues:write`, `pull_requests:write`, `contents:read`, and nothing else (no `workflows`, admin or secrets). So it cannot push to or merge into the base repo. | Installation tokens can be scoped by repo and permission and expire after 1 h (platform basis) | V2: merge and push attempts must return 403 | A required action needs broader permission → a separate App, with every use approved |
| 2. Where code runs | R3: a leaked secret or code cannot be recalled | One throwaway sandbox per job (gVisor or Firecracker), holding no credentials. Outbound network is denied except a package-registry proxy. The clone and the push happen outside the sandbox, in the executor. | Tests can run without network access to secrets | V2 | V2 fails → turn off test execution (patches only) until it passes |
| 3. Where agent PRs come from | R3: a branch in the base repo would hand CI secrets to model-written code | Branches are pushed to a separate forks org, so agent PRs are fork PRs. Fork PRs run CI without secrets, and their workflows need maintainer approval to run. | Fork-PR protections hold in every repo that receives agent PRs | V2 (a canary secret placed in CI must stay unreached); Phase 0 inventory | A repo's real tests need secrets → a maintainer triggers CI only after reviewing the diff |
| 4. How much the agent does without a human | R3: public comments and pushed code are seen at once and cannot be unseen | Reads run on their own. Labels run on their own only per label, after V3. Comments need approval bound to the exact text. Fix attempts start only when a write-permission user applies `agent:attempt`, and result in draft PRs only. Merging is never done by the agent. | A maintainer requesting the attempt plus a draft PR is enough human gating for code | V3 (labels), V4 (PRs) | A comment class reaches ≥ 95% approval as written over 200 comments (ASSUMPTION) → that class may run on its own |
| 5. Data-privacy boundary | R3: data held by a vendor cannot be recalled | Private code goes to a hosted model only under enterprise terms (no training, fixed retention, approved region). Repos classified as regulated or secret are excluded. | Approved terms exist for at least one capable provider | V1 | V1 fails → self-host an open-weight model, or limit scope to public repos |
| 6. Hosted API vs self-host | R2: weeks to re-tune prompts and evals | A hosted frontier model behind a provider interface, with a fallback model | Hosted quality and cost beat self-hosting at this volume | V4 (also run on the fallback model) | V1 fails, or V5 fails on cost |
| 7. Build vs buy (the fix loop) | R2: weeks of integration either way; the safety layers are needed regardless | Build a thin orchestrator. Score one hosted coding agent (e.g. GitHub Copilot coding agent) on the V4 set. | Owning the loop is what lets rows 1–4 be enforced | V4 comparison run | The bought agent is within 5 points of our fix rate (ASSUMPTION) and fits rows 1–5 → buy the fix loop; keep triage and the safety layers |
| 8. Prompt+RAG vs fine-tune | R2: fine-tuning ties us to one provider's base model, and training on private code is R3 | Prompt plus per-repo retrieval | Retrieval supplies the repo context the model lacks | V3 / V4 | Quality plateaus below the bar after retrieval tuning, and V1 permits training |
| 9. Duplicate deliveries (consistency) | R2: duplicate public comments or PRs are visible; the ledger schema feeds audit | At-least-once processing. Each action has an idempotency key (issue + action + payload hash) and each issue has a lock. The Postgres ledger is the system of record for agent actions; GitHub stays the system of record for issues. | Each GitHub write can be made idempotent | Phase 1 exit check | Duplicates appear in the ledger audit → add an outbox with reconciliation |

**R1 defaults:**
- Monolith vs services → one service with two process types (webhook receiver and worker); the sandbox pool is separate only because of row 2.
- Sync vs async → async (forced by the 10 s webhook timeout).
- Queue → a Postgres table read with `SKIP LOCKED`.
- Vector store → pgvector in the same Postgres.
- Approval UI → an internal dashboard, with Slack notifications.

**N/A:** Migration, cutover and rollback-to-old-system: there is no old system to replace. Tenancy: one org only (it reopens if this becomes a product for other orgs; see §10).

## 4. Walking skeleton (Phase 0)
- **The one real request:** A team member opens the issue "Typo in README: 'recieve'" in `org/agent-skeleton` (private, synthetic content). The agent applies `type:docs` and opens a draft PR from the forks org with a one-line fix, the test output, and a trace ID in the PR footer.
- **Tiers crossed:**
  1. GitHub webhook
  2. Receiver (HMAC signature check, acknowledge within 10 s)
  3. Postgres queue
  4. Worker (issue lock, idempotency key)
  5. Model call through the provider interface (issue text wrapped as untrusted data, output must match a schema, hard token cap)
  6. Sandbox (the repo's test command on the patched tree, no credentials, no outbound network)
  7. Executor (mints the token; label, fork push, draft PR)
  8. Ledger row
  9. OpenTelemetry trace across all of the above
- **Deploy, log, monitor, roll back:**
  - Infrastructure as code (Terraform) and a CI pipeline that builds, signs and deploys the image by digest.
  - Rollback means redeploying the previous digest.
  - Structured logs and traces go to a store with the same access rules as source code.
  - Alerts fire on dead-letter jobs, a job failure rate above 0, and cost-cap hits.
  - A global kill switch flag turns off all writes.
- **Who can reach it:** The App is installed only on `org/agent-skeleton`. The executor's repo allow-list holds that repo only, and only team members file issues there.

Exit check V0: §6.

## 5. Phases

- **Phase 0: Walking skeleton plus inventory**
  - Unlocks: Phase 1.
  - Depends on: nothing.
  - Tasks:
    1. Start the organizational items: org-owner approval for the App and the forks org; V1 review; a request to maintainers for the taxonomy and a labeled set for V3.
    2. Inventory the existing org through the API and code search: workflows triggered by `issues`, `issue_comment` or `labeled`; `pull_request_target` workflows; existing bots; branch protection; fork-PR approval settings. Mark each finding CONFIRMED or ASSUMED.
    3. Baseline 90 days of issue volume and time to first response.
    4. Build the skeleton in §4.
  - Rollback: redeploy the previous image digest, or uninstall the App.
  - Exit check: V0 passes, and the inventory is complete.

- **Phase 1: Defenses and budgets**
  - Unlocks: real repos (Phase 2).
  - Depends on: V0.
  - Tasks, widest rework first:
    1. Per-job scoped tokens (row 1).
    2. A tool executor with an allow-list and schema-checked arguments: `add_label` (taxonomy only), `propose_comment`, `read_file`, `search_code`, `run_tests`, `propose_patch`, `open_draft_pr`. The model never holds a token.
    3. Sandbox hardening (row 2): gVisor, CPU, memory and time limits, registry proxy only.
    4. Diff policy: deny `.github/**`, `CODEOWNERS` and CI config; flag new dependencies; run secret scanning on diffs and all outbound text; cap size.
    5. Outbound text filter: only allow-listed URLs, no images, no mass @-mentions.
    6. Approval service: approvals bound to a hash of action, repo and payload. The approver's permission is checked through the API. `agent:attempt` counts only if a write-permission user applied it.
    7. Budget caps: per job (triage $0.05, attempt $5), at most 40 tool steps, 45 min wall clock, a per-repo daily cap and a global daily cap.
    8. Loop and abuse guards: ignore bot senders, including the agent itself; limit agent actions per issue per day; back off on secondary rate limits.
    9. A sweep that recovers missed webhooks; point-in-time recovery for the ledger.
    10. An injection suite in CI plus a red-team session (V2).
  - Rollback: each control is reverted through the pipeline; nothing is exposed beyond the skeleton repo.
  - Exit check: V2 passes. A runaway loop is cut off at its cap and emits a cost metric. A redelivered webhook produces no duplicate action.

- **Phase 2: Retrieval, model access, triage in shadow mode**
  - Unlocks: Phase 3, and Phase 4 (via its dataset).
  - Depends on: V1, V2, the org-owner install approval.
  - Tasks:
    1. Install on the first wave of internal repos with the executor in dry-run mode: decisions go to the ledger only.
    2. Build a per-repo index of issues (with labels and the PRs that closed them), `CODEOWNERS`, the taxonomy and code symbols. Pin the embedding model in the index version. Retrieval is limited to the issue's own repo.
    3. Harden model access: retries, a fallback model, and repair-or-fail parsing of structured output.
    4. Write the triage prompt: type and component, a suggested priority, duplicate candidates, missing-information requests, and detection of security reports, which go to a private channel and are never repeated publicly.
    5. Run V3: historical replay plus 2 weeks in shadow.
    6. Build the V4 dataset (lead time).
  - Rollback: turn the flag off or uninstall; shadow mode makes no GitHub writes.
  - Exit check: V3 is complete. Retrieval finds the true duplicate in the top 5 for ≥ 0.80 of maintainer-marked duplicate pairs (ASSUMPTION). API usage stays under the limits at the Phase 0 peak hour.

- **Phase 3: Triage canary on internal repos**
  - Unlocks: real triage value and correction data for Phase 6.
  - Depends on: V3 (per label), and the Phase 0 inventory confirming which labels have side effects (those labels are excluded).
  - Tasks:
    1. Opt in one repo through `.github/agent.yml`, then widen through the internal wave.
    2. Labels that passed V3 are applied on their own; the rest are suggested only. Comments go through approval.
    3. Build a bulk label-revert tool driven by the ledger.
    4. Record maintainer relabels as feedback events.
  - Rollback: turn off the per-repo flag, then revert the agent's labels from the ledger.
  - Exit check: In each repo, maintainers override ≤ 10% of the agent's labels (ASSUMPTION, matching V3) over 2 weeks before the next repo is added. p95 triage latency meets its budget. No security report is ever repeated publicly.

- **Phase 4: Fix loop offline (memory and orchestration)**
  - Can run in parallel with Phase 3.
  - Unlocks: Phase 5.
  - Depends on: Phases 1–2.
  - Tasks:
    1. Container recipes per repo.
    2. A single-agent loop (find → reproduce → edit → test → summarize) with a trace for each step; failed steps are retried or reported, never dropped.
    3. Memory: a scratchpad per job, and a history of earlier attempts on the same issue built from facts the executor checked (test results), never from issue text copied verbatim. Nothing is shared across repos.
    4. Run V4, including the build-vs-buy comparison and the fallback model.
  - Rollback: none needed; nothing is exposed.
  - Exit check: V4 passes.

- **Phase 5: Fix canary**
  - Unlocks: Phase 6.
  - Depends on: V4; V2 re-run against the fix tools; Phase 0 inventory confirming the repo has no `pull_request_target` workflow that checks out PR code and requires approval for fork-PR workflows.
  - Tasks:
    1. Start with one opted-in internal repo, limited to the issue classes that passed V4.
    2. Draft PRs carry the trace link, test evidence and cost.
    3. Maintainers log review time in the PR template.
    4. After 2 weeks with no policy violations, widen to 3–5 repos.
    5. Run V5 for 4 weeks.
  - Rollback: turn the flag off, close agent PRs from the ledger, and uninstall the App from the forks org.
  - Exit check: V5 passes. No policy violations (diff policy, egress, approvals).

- **Phase 6: Routing, feedback, internal rollout**
  - Unlocks: org-wide internal use, then Phase 7.
  - Depends on: V5.
  - Tasks:
    1. A router: a cheaper model for triage and a strong model for fixes, escalating on low confidence.
    2. Feedback: each month, reviewed corrections and PR outcomes are added to the V3/V4 sets. A prompt change ships only if the eval improves with no regression elsewhere.
    3. Roll out in waves of about 25% of opted-in repos.
    4. Write the on-call runbook.
  - Rollback: per-wave flags.
  - Exit check: The routed setup scores within 2 points of the strong model on the V3/V4 sets and costs less. Operational complexity stays within budget.

- **Phase 7: Public repos**
  - Unlocks: OSS repos.
  - Depends on: V6.
  - Tasks:
    1. A separate App installation that cannot reach private repos, which removes the private-data part of the leak path.
    2. Triage-only on one public repo first. Comments always need approval. Fixes are triggered by maintainers only.
    3. Rate limits per issue author; issues from first-time authors get triage only.
  - Rollback: uninstall, and delete agent comments from the ledger. Seen content cannot be unseen, which is why comments stay approval-gated.
  - Exit check: No violations over 4 weeks on the canary public repo.

## 10. Deliberately deferred
- **Autonomous merging.** Pull forward when stakeholders require it and at least 6 months of agent PRs show a revert rate below a threshold set by a named approver. It needs a new R3 row and gate.
- **Comments without approval.** Pull forward per comment class when row 4's flip condition holds.
- **Fine-tuning.** Row 8's flip condition.
- **Self-hosted model.** Rows 5/6 flip conditions.
- **Multiple agents.** When single-loop V4 scores plateau and traces show separable sub-tasks.
- **Long-term memory across repos.** When V4 failures trace to missing org-wide conventions. It needs its own poisoning review.
- **A real message broker or split services.** When Postgres queue latency breaks the triage latency budget.
- **Multiple tenants (selling to other orgs).** If productized: tenancy becomes an R3 decision and the plan restarts at Step 1.
- **Fixes for issues flagged as security reports.** Only once there is a private-fork workflow with the security team's sign-off.
