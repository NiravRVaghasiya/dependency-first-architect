# Building a CI/CD Platform for 50 Microservices: A Phased Plan

**Assumptions:** the services run in containers on Kubernetes (or something similar), you have a platform team of 4–6 engineers, and the services use a mix of languages. Adjust if any of these don't fit.

**Main principle:** build one "golden path" and prove it on a few services before migrating the rest. Don't build 50 custom pipelines, and don't build the whole platform before anyone uses it.

---

## Phase 0: Discovery and Decisions (Weeks 1–3)
**Goal:** know what you have and make the decisions that are expensive to change later.

- **Catalog all 50 services:** language, build tool, test coverage, where it deploys, current pipeline, owner, how critical it is, and what it depends on.
- **Group services into archetypes.** Most teams end up with 3–6, for example Java/Gradle, Node, Go, Python, frontend, and a few special cases.
- **Measure DORA metrics now** (deploy frequency, lead time, change failure rate, time to restore). You need this baseline to show the platform helped.
- **Make the key decisions:**
  - CI engine: GitHub Actions, GitLab CI, Tekton or Jenkins
  - CD model: GitOps with Argo CD or Flux is recommended, or push-based
  - Repo strategy: one repo or one repo per service
  - Environment model: which environments exist and how releases are promoted between them
  - Branching strategy: trunk-based is recommended

**Done when:** the catalog is complete, archetypes are defined, decisions are written up as ADRs (architecture decision records), and the baseline metrics are recorded.

## Phase 1: Foundations (Weeks 3–8)
**Goal:** the shared infrastructure every pipeline depends on.

- Define the platform itself as code (Terraform, Pulumi or similar) from day one.
- Set up CI runners with autoscaling, ephemeral runners and build caching.
- Set up an artifact and container registry with retention policies.
- Handle identity and secrets: OIDC from CI to the cloud (no long-lived keys) and a secrets manager such as Vault or the cloud provider's.
- Create a GitOps config repo structure and install Argo CD or Flux in non-production clusters.
- Write base container images and Dockerfile standards for each archetype.

**Done when:** a "hello world" service can be built, pushed and deployed to dev entirely through the platform.

## Phase 2: Golden Path CI (Weeks 6–12, overlapping Phase 1)
**Goal:** reusable, versioned pipeline templates.

- Build one template per archetype covering lint, build, unit tests, dependency scanning (SCA), a software bill of materials (SBOM), container build, image signing (cosign) and push.
- **Version the templates** (for example `ci-templates@v1.2`) so updates can be rolled out on purpose. Use Renovate or Dependabot to bump the version across services.
- Keep each service's pipeline config down to roughly 10–20 lines that call the shared template.
- **Pilot with 2–3 services** that are typical of their archetype, have willing owners and are not business-critical.

**Done when:** the pilot services run CI only through the templates, and their owners would recommend it.

## Phase 3: Continuous Delivery (Weeks 10–16)
**Goal:** automated, auditable deployment and promotion.

- Standardize how deployment config is packaged, using Helm charts or Kustomize bases per archetype.
- Automate promotion: CI updates the image tag in the GitOps repo for dev, then promotion to staging and prod happens through a PR or policy.
- Add progressive delivery (Argo Rollouts or Flagger) with canary or blue-green releases.
- Roll back automatically when SLOs or error rates breach thresholds.
- Extend the pilot services all the way to production.

**Done when:** the pilot services deploy to prod through the platform with automatic rollback, and the team has run a rollback drill successfully.

## Phase 4: Quality and Security Gates (Weeks 14–20)
**Goal:** shift checks earlier without blocking delivery.

- Add SAST, image vulnerability scanning and secret detection.
- Add contract tests (such as Pact) between services, which matters a lot once you have 50 of them, plus integration tests in short-lived environments.
- Enforce policy as code (OPA/Gatekeeper or Kyverno), for example: signed images only, no `:latest` tags, resource limits required.
- **Introduce gates in warn-only mode first**, then make them blocking once false positives are tuned out.
- Aim for SLSA supply-chain level 2–3: build provenance and attestations.

## Phase 5: Migration Waves (Weeks 16–32)
**Goal:** move all 50 services onto the platform.

| Wave | Services | Selection criteria |
|------|----------|--------------------|
| Pilot | 3 | Done in Phases 2–3 |
| Early adopters | ~10 | Willing teams, one or two per archetype, low to moderate risk |
| Bulk | ~30 | Grouped by archetype, 5–8 per sprint |
| Complex | ~7 | Legacy, stateful, unusual tooling, or the most critical services |

- Hold a retrospective after each wave and feed the fixes back into the templates before the next wave.
- Provide migration tools: a scaffolding CLI or generator, a runbook, and office hours.
- Run the old and new pipelines side by side for each service until there have been about 5 successful prod deploys on the new one.
- Shut down the legacy pipelines after each wave so you don't end up maintaining both systems indefinitely.

## Phase 6: Self-Service and Optimization (Weeks 24 onward, ongoing)
- Launch a developer portal (Backstage or similar) with templates for creating new services, a service catalog and pipeline status.
- Add dashboards for DORA metrics, pipeline duration, flaky tests and runner cost.
- Set up preview environments for each pull request.
- Treat the platform as a product: give it SLOs, an on-call rotation, a changelog, a roadmap and a feedback channel.

---

## Critical Path and Parallel Work

```
Discovery → Foundations → Golden-path CI → CD → Pilot in prod → Migration waves
                              ↘ Security gates (warn-only → blocking) ↗
                                        Observability/DORA (start early, keep going)
```

## Common Mistakes to Avoid
- **Migrating the hardest services first.** Start with representative, low-risk ones.
- **Letting every team customize their pipeline.** Allow extension points, not forks of the templates.
- **Unversioned shared templates.** One bad change can break all 50 services at once.
- **Blocking security gates on day one.** Teams will lose trust and look for workarounds.
- **No baseline metrics.** Without them you can't show the platform was worth it.
- **Building every feature before the pilot.** Ship a thin version end to end first.

**Rough total:** 6–9 months to full migration, with the first service in production on the platform around week 12–16.
