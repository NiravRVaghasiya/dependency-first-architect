# Architecture and Build Plan: `photo-rename`, a CLI that renames photos by EXIF capture date

## 1. Summary

- **What is being built:** a cross-platform command-line tool. It reads each photo's EXIF capture date (the date the camera recorded when the shot was taken) and renames the files in a folder to a sortable name such as `2024-05-12_14-03-22.jpg`. It is for one person or a small group of technical users organising their own photo folders.
- **Shape:** one Python package that installs with `pipx`. It runs in a fixed pipeline: **Scanner → MetadataReader → Planner → Executor**. The Planner is a pure function, so it can be tested exhaustively. Every change on disk goes through a write-ahead **Journal** first, which makes every run reversible.
- **Key decisions:**
  1. Write it in Python. Read EXIF with the pure-Python `exifread` library, kept behind a `MetadataReader` interface so an ExifTool backend can be added if the coverage spike calls for it.
  2. Split planning from applying. `preview` never touches the disk. `apply` shows the plan and asks for confirmation before doing anything.
  3. Never overwrite a file. Collisions get suffixes (`_01`, `_02`), and file names are compared case-insensitively on every OS.
  4. Write a journal entry before each rename, and provide an `undo` command that is safe to run more than once.
  5. Rename **groups** of files that share a base name (for example `IMG_0042.CR2`, `IMG_0042.JPG` and `IMG_0042.xmp`) together, so pairs stay paired.
- **First milestone:** a working `preview` / `apply` / `undo` for JPEG and HEIC on Windows, macOS and Linux in CI, plus a spike that measures how many EXIF dates are read correctly on a real photo corpus. Finished when it has been demonstrated on a copy of a real folder.
- **Top risks:**
  - The EXIF library may not cover some formats (RAW, especially Canon's CR3).
  - Overwrite and case-sensitivity rules differ between operating systems.
  - A run could be interrupted halfway.
  - Cloud-synced folders (OneDrive, iCloud) may download files when they are read and produce sync conflicts.

**Before building:** if this is a one-off job, ExifTool can already do it in one command: `exiftool "-FileName<DateTimeOriginal" -d "%Y-%m-%d_%H-%M-%S%%-c.%%e" DIR`. This tool is worth building only if you want what ExifTool doesn't give by default: a preview that is the default, an undo, RAW and JPEG pairs kept together, case-safe collision handling, and clear reports on skipped files. The plan below assumes you do.

## 2. Context and Goals

- **Problem:** cameras and phones produce names like `IMG_4821.JPG` and `DSC00017.ARW`. These don't sort by time, they clash across devices, and they say nothing about the photo. Renaming by hand doesn't scale, and generic batch renamers use the file's modified time, which copying or editing changes.
- **Goals:**
  - Rename every file that has a readable capture date to a name based on that date.
  - Never lose, overwrite or change the contents of a file.
  - Make every run undoable.
- **Non-goals:**
  - Changing file contents or metadata.
  - Moving files into folders such as `YYYY/MM`.
  - Recursing into subfolders (deferred).
  - Reading video dates from QuickTime metadata.
  - Converting time zones.
  - Correcting a camera clock that was set wrong (deferred).
  - A graphical interface.
  - Duplicate detection.
- **Success measures:**
  - The user's real folders are renamed with **0 misnamed files and 0 overwrites**.
  - Every skipped file appears in the report with a reason.
  - `undo` restores the original set of names exactly.

## 3. Drivers, Requirements, and Constraints

**Ranked quality attributes**

| # | Attribute | Measurable target | Why it matters |
|---|---|---|---|
| 1 | Data safety | 0 overwrites and 0 content changes. Every `apply` can be fully reversed by `undo`, including after a crash. Verified by property tests and fault-injection tests. | These are irreplaceable personal photos. One overwritten file outweighs every benefit. |
| 2 | Date correctness | On the spike corpus, 100% agreement with ExifTool on `DateTimeOriginal` for supported formats. A file whose date can't be read is **skipped and never guessed**. *(assumption)* | A wrong name is worse than no rename, because it silently scrambles the timeline. |
| 3 | Cross-platform behaviour | Same results on Windows (primary, *assumption*), macOS and Linux. CI passes on all three. | Windows, macOS and Linux disagree on whether a rename may overwrite and on whether names are case-sensitive. |
| 4 | Ease of use | Installs with one command (`pipx install`). The default command is harmless. Output is readable. | It's a personal tool and shouldn't need a manual. |
| 5 | Performance | `preview` of 10,000 JPEGs on a local SSD in under 60 s *(assumption)*. | Large folders are plausible. Nothing beyond "not annoying" is needed. |

**Key functional requirements:**

- `preview DIR`, `apply DIR` and `undo DIR`.
- Date priority: `DateTimeOriginal`, then `DateTimeDigitized`, otherwise skip. `--fallback mtime` uses the file's modified time instead; it is opt-in and arrives in M2.
- Default name format `YYYY-MM-DD_HH-MM-SS` plus the original extension, with deterministic collision suffixes.
- Running the tool twice changes nothing the second time.

**Constraints:**

- Greenfield project.
- Assumed: one developer working part-time, Python 3.10 or later.
- No budget is needed and there is nothing to host.

**Hard parts:**

- **EXIF coverage across formats.** HEIC and RAW containers vary, and some cameras write empty or `0000:00:00` dates.
- **No-overwrite renaming across OSes.** On POSIX systems (Linux, macOS), `os.rename` silently replaces an existing target. On Windows it refuses. On NTFS, APFS and exFAT, `A.JPG` and `a.jpg` count as the same name.
- **Partial runs.** A crash, a file locked by antivirus or Explorer, or a pulled SD card can leave the folder half-renamed.
- **Name cycles and collisions.** A target name may already be taken by another file that is itself due to be renamed. Burst shots taken in the same second must get suffixes in a stable order.

## 6. Architecture Overview

```
                 untrusted input: file names + image bytes
                ┌──────────────────────────────────────────┐
 user ──► cli ──► Scanner ──► MetadataReader ──► Planner ──► Report (stdout)
           │     (list,       (ExifReadBackend;   (pure fn:
           │      group by     ExifToolBackend     groups+dates
           │      stem)        if spike demands)   → Plan)
           │                                          │
           │                                    apply │ (after confirm)
           │                                          ▼
           └──────── undo ──────────────────────► Executor ──► filesystem (os.rename)
                                                      │
                                                      ▼
                                       Journal: DIR/.photo-rename/<run-id>.jsonl
```

All three commands start with the CLI. For `preview` and `apply`, the Scanner lists candidate files and groups them by base name. The MetadataReader extracts a capture date for each group, and the Planner turns groups and dates into a `Plan` without touching the disk. `preview` stops after printing the Report. `apply` prints the same report, asks for confirmation, and then hands the Plan to the Executor. The Executor writes an entry to the Journal before every rename. `undo` sends the Journal back through the Executor in reverse.

| Component | Responsibility | Owns data | Interfaces | Tech | Depends on |
|---|---|---|---|---|---|
| `cli` | Parse arguments, run the pipeline, set exit codes | — | `photo-rename preview\|apply\|undo DIR [opts]` | `argparse` | all |
| `scanner` | List files, filter by extension, skip dotfiles, symlinks and `.photo-rename/`, group by base name | `SourceFile`, `Group` (in memory) | `scan(dir, exts) -> list[Group]` | stdlib `os.scandir` | filesystem |
| `metadata` | Get a capture date for a group, or a reason it couldn't | `CaptureDate` | `MetadataReader.read(path) -> CaptureDate \| Skip` | `exifread` 3.x | `exifread` |
| `planner` | Work out target names, collisions, no-ops, cycles and skip reasons | `Plan`, `PlanEntry` | `build_plan(groups, dates, existing, fmt) -> Plan` | pure Python | none (no I/O) |
| `executor` | Apply or undo a plan safely | renames on disk | `apply(plan, journal)`, `undo(journal)` | `os.rename` | `journal`, filesystem |
| `journal` | Write-ahead log of every rename step | `.photo-rename/*.jsonl` | `begin()`, `intent()`, `done()`, `read()` | JSON Lines (one JSON record per line), `fsync` | filesystem |
| `report` | Old → new table, skipped files with reasons, summary counts | — | human-readable text on stdout | stdlib | — |

## 7. Component Details

**metadata.** Reads tags with `exifread.process_file(f, details=False)`. It uses `DateTimeOriginal`, falls back to `DateTimeDigitized`, and also reads `SubSecTimeOriginal` for ordering. It rejects empty values, `0000:00:00 00:00:00` and strings it can't parse, and returns `Skip(reason)` in those cases. It never uses IFD0 `DateTime`, which records when the file was last edited, not when the shot was taken. It does not convert time zones or guess dates. Any exception the parser raises is caught for that file and turned into a `Skip`, so one corrupt file can't abort a run. For a group, it reads the first member with an image extension, in a fixed order: JPEG/HEIC, then RAW, then others.

**planner.** This is the heart of the correctness work. It does no I/O, which makes property testing practical. It follows these rules:

1. Target stem = `format(date)`. All name comparisons use case-folded strings (strings normalised so case doesn't matter).
2. Groups with the same target stem are sorted by (sub-second, original stem). The first keeps the plain stem; the rest get `_01`, `_02` and so on.
3. A target already used by a file that isn't moving gets the next suffix.
4. A group already at its target is a no-op. This is what makes a second run change nothing.
5. A target held by a file that is itself moving is a cycle. In M1 it is skipped with the reason "cycle". From M2 it is resolved with a temporary hop (rename to a temp name first).
6. A rendered name containing a path separator, `..`, a character Windows doesn't allow in file names, or a reserved Windows name (such as `CON`) is rejected.

**executor.** Each group is applied as a unit. For each step (`from → to`):

1. Write an `intent` record to the journal and `fsync` it.
2. Check `os.path.lexists(to)`.
3. Call `os.rename`.
4. Write a `done` record.

If any step in a group fails, for example with `PermissionError` on a locked file, the steps already done for that group are reverted, the failure is reported, and the run moves on to the next group. Unexpected errors such as `OSError` with a disk-gone errno stop the run, and the user is told to run `undo`. Exit codes: `0` = everything renamed or a no-op, `1` = some files were skipped or failed, `2` = usage error or the run was aborted.

**journal.** Files go in `DIR/.photo-rename/<UTC-timestamp>.jsonl`. The first line is a header (`{"v":1,"run":…,"dir":…}`). After that come step records `{"seq":n,"group":…,"from":…,"to":…,"state":"intent|done"}` and, at the end, an `{"undone":true}` marker. Records hold bare file names only, never paths.

**undo.** Processes steps from the last one back to the first:

- If `to` exists and `from` does not, rename it back.
- If `from` exists and `to` does not, the step never happened, so skip it.
- If both or neither exist, report a conflict and leave the files alone.

At the end it appends `undone`. Running `undo` a second time does nothing. By default it uses the latest run; `--run ID` picks another.

**scanner and report.** Routine code. The scanner does not recurse. Extensions are matched case-insensitively. In M1 the list is `.jpg .jpeg .heic .heif`; M2 adds RAW formats, `.xmp`, `.aae` and `.mov` as group members.

## 8. Data Design

- **Entities:**
  - `SourceFile(name, stem, ext)`
  - `Group(key=casefold(stem), members[])`
  - `CaptureDate(dt naive, subsec, source_tag)`
  - `PlanEntry(group, new_stem, steps[(from,to)], status, reason)`
  - `JournalRecord`
- **System of record:** the filesystem holds the current names. The journal holds the rename history and is written only by the executor. Everything else exists in memory for one run.
- **Consistency:** each rename is atomic within a single directory. Writing the intent record before the rename means a crash at any point can be recovered by `undo`. Groups are atomic on a best-effort basis (completed steps are reverted on failure).
- **Retention:** journals are kept until the user deletes them. `.photo-rename/` is small, roughly 200 bytes per file renamed.
- **Classification:** EXIF can contain GPS location and camera serial numbers. The tool never logs or stores any EXIF field except the date. Journals contain only file names.
- **Evolution:** the journal header carries `"v":1`. `undo` refuses versions it doesn't know, and new fields are only ever added.

## 9. Key Flows

1. **Preview (default, safe):** `preview DIR` → scan → read dates → plan → print the table and the skipped list → exit. **Nothing is written, not even the journal directory.**
2. **Apply:** `apply DIR` → the same pipeline, worked out fresh, so a stale preview is never trusted → print the plan → "Rename 412 files in 398 groups? [y/N]" (skipped with `--yes`) → create the journal → executor runs each group → print a summary with the path to the journal.
3. **Failure path (crash or locked file, then undo):** at step 57 of 400 the process is killed, between writing `intent` and finishing `os.rename`. The journal has 57 `intent` records and 56 `done` records. The user runs `undo DIR`. Working backwards, step 57 is undone if the rename went through and skipped if it didn't; steps 56 to 1 are reverted. The folder ends up with exactly its original names. A file locked by antivirus during `apply` reverts only its own group and is reported as `failed: PermissionError`; the other groups carry on.
4. **Second run:** `apply DIR` on a folder that is already renamed gives a plan where every entry is a no-op. Burst suffixes come out the same because the sort order (sub-second, then stem) is stable. The tool reports "0 to rename" and creates no journal.

## 11. Cross-Cutting Concerns

- **Security (M1):**
  - *Hostile file crashes the parser:* `exifread` is pure Python, exceptions are caught per file, and nothing is ever executed.
  - *Path traversal through rendered names or a tampered journal:* names are validated as bare file names with no separators or `..` and checked against the Windows character and reserved-name rules. `undo` rejects records that fail the same check.
  - *Symlinks pointing outside the folder:* skipped.
  - *Privacy:* GPS and serial numbers are never logged.
- **Reliability (M1):** journal-before-rename, idempotent undo, group-level revert, and per-file error isolation. There is no network and therefore nothing to time out.
- **Observability (M1):**
  - The report shows a summary of renamed, no-op, skipped (with reasons) and failed files.
  - `--verbose` logs each file and the source tag of each date to stderr.
  - The journal serves as the audit trail.
- **Performance (M2):** `details=False` reads headers only. A benchmark test runs on 10,000 generated JPEGs. Reading files in parallel is deferred unless the target is missed.
- **Cost:** none. It runs locally.
- **Operations:** the maintainer is the developer, and support is through repository issues. README sections cover: back up first, how undo works, and cloud-sync folders.

## 14. Testing and Validation Strategy

- **Unit tests:** `metadata` parsing rules and `scanner` filters.
- **Property tests (Hypothesis):** the four `planner` invariants in T8. These cover driver 1 at the planning level.
- **Fault injection:** `executor` and `journal` crash and recovery tests (T10). These cover driver 1 at the execution level.
- **End-to-end tests:** subprocess tests on generated folders, run on 3 OSes. These cover driver 3.
- **Corpus check:** the S1 corpus compared against ExifTool as the source of truth. This covers driver 2. It stays outside CI if the photos are private, and a small set of sample images with clear licences is committed instead.
- **Benchmark (M2):** a 10k-file run that is reported rather than gating releases.
- **Release gate:** ruff, all tests and the wheel smoke test pass on all 6 CI jobs.

## 15. Rollout, Migration, and Rollback

- **Rollout:** install from git with `pipx`, try it on a copied folder, then on real folders. The README recommends a backup before the first `apply`. No feature flags are needed beyond `preview` being the default.
- **Migration:** none. No existing system is being replaced.
- **Rollback:** `photo-rename undo DIR` reverses any run. Rolling back stops being possible once the user deletes `.photo-rename/` or renames or moves the files again by other means; `undo` then reports conflicts rather than guessing. To remove the tool itself, run `pipx uninstall`.
