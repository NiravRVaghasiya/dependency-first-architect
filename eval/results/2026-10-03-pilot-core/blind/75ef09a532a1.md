# Plan: Real-Time Collaborative Document Editor

## 1. Classification
- **What:** A browser-based rich-text editor where several users edit the same document at once and see each other's changes and cursors live. Includes accounts, sharing, permissions, history and durable storage.
- **Type:** Software, with a significant infrastructure part (a tier holding long-lived WebSocket connections and fanning out messages). No AI in scope.
- **Dominant constraint:** **Correctness.** Every user must end up seeing the same document, and every edit the server has confirmed must survive. Latency comes second: edits should reach other users in under 100 ms (p95) within one region.
- **Worst failure:** **Silent divergence or loss of confirmed edits.** Two users see different documents, or text the server confirmed disappears. Users will put up with slowness; once they stop trusting the document, they leave.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| **Merge algorithm: CRDT vs OT** (the hardest to reverse, because it fixes the stored format) | **CRDT using Yjs.** Edits apply locally first and merge automatically. It works offline and has a mature ecosystem (y-prosemirror, Hocuspocus). | Typical documents carry more than 10 MB of CRDT history that compaction can't reclaim, or the product needs edit semantics CRDTs handle badly (e.g. strict server-defined ordering) → switch to OT (ShareDB). This must be decided **before Phase 1 locks the data contract**. |
| **Consistency vs availability** | **Split by data type.** Document content favours availability: edits apply locally at once and all copies converge. Permissions, document metadata and tenant data favour strong consistency and live in Postgres. | A regulated workflow needs edits in one strict order or locked sections (legal sign-off) → add a server-assigned sequence or lock just for those documents. |
| **Monolith vs services** | **Modular monolith.** One repo and one image, run as two processes: an HTTP API and a WebSocket sync server. They share the auth and permission modules. | The sync tier needs its own release schedule, a single node exceeds ~20k connections, or team ownership splits → separate the sync service. |
| **Sync vs async** | **Synchronous where durability matters, async everywhere else.** Edits apply locally right away and spread to others asynchronously. The server confirms an edit only after it is durably written to the update log. Compaction, history snapshots, export and indexing run on a queue. | p95 write latency exceeds 50 ms → batch writes into ~20 ms group commits. Never confirm an edit before it is durably stored. |
| **Build vs buy** | **Buy** login (WorkOS or Auth0). **Use open-source** Yjs, TipTap/ProseMirror and Hocuspocus. **Build** permissions, persistence, the message envelope and the divergence detector. Skip managed hosted sync (Liveblocks, Tiptap Cloud) to keep ownership of the data. | Fewer than 3 engineers and under 3 months to market, with no data-residency requirement → use Liveblocks or Tiptap Cloud. |
| **Message fan-out across sync servers** | **Redis pub/sub between stateless sync servers.** Any node can serve any document, and the load balancer stays simple. | Redis CPU or bandwidth becomes a bottleneck, or documents regularly have more than 100 simultaneous editors → route each document to one node by consistent hashing. |
| **Persistence model** | **Append-only update log plus periodic compacted snapshots, both in Postgres.** | Snapshots regularly exceed 1 MB → move snapshots to S3 and keep a pointer in Postgres. |
| **Tenancy isolation** | **Shared database** with a `workspace_id` on every row, enforced by Postgres row-level security. | An enterprise contract requires physical isolation or data residency → one database (or region) per tenant. |
| **Can the server read document content?** | **Yes.** Encrypted at rest with KMS. This is what makes server-side export, search and history possible. | A contract requires zero-knowledge (end-to-end) encryption → must flip **before Phase 1**, because it changes storage, search and export. |
| (AI) prompt+RAG vs fine-tune | N/A: no AI features in scope. | An AI writing assistant is requested → re-plan with the AI layer. |
| (AI) hosted API vs self-host | N/A: no model is used. | Same as above. |

## 3. First end-to-end slice (Phase 0)

**The one real request:** A signed-in user opens `/d/:id` and types "hello" into a **plain-text** shared field (`Y.Text`, not rich text yet). A second browser signed in as another user with access sees "hello" appear live. Reloading either browser shows "hello", loaded from Postgres.

**Tiers it crosses:**
1. **Browser client:** React, Yjs and the y-websocket provider, served as static files from a CDN.
2. **Auth provider:** WorkOS or Auth0 login, which issues a short-lived JWT.
3. **Load balancer:** must support WebSocket upgrades and idle timeouts of at least 60 s.
4. **Sync server:** Node with Hocuspocus. On connect it checks the JWT and a hard-coded permission check against one table.
5. **Postgres:** tables `documents`, `doc_updates` (append-only) and `doc_acl`. An edit is confirmed only after it is written to `doc_updates`.
6. **Second client:** receives the broadcast and renders it.

**Deployed, logged and monitored on day zero:**
- **Deploy:** Terraform builds the environment (Fly.io or ECS). One container image with two process roles. CI on every merge to main: build → test → deploy to staging → manual promote to production.
- **Logs:** structured JSON with `trace_id`, `doc_id`, `user_id`, `conn_id`. Document content is never logged.
- **Traces:** OpenTelemetry spans covering client send → sync server receive → Postgres write → broadcast. The receiving client reports when it rendered the edit, which gives the true end-to-end time.
- **Metrics:** open WebSocket connections, edit write latency, client-reported edit-to-remote-render latency (p50/p95), reconnect rate, auth rejections.
- **Alerts:** none of these is wired before day zero: an uptime check on the WebSocket endpoint, p95 propagation over 250 ms, and write error rate over 0.1%.

**Exit check:** In production, user B's browser renders user A's typing. One trace shows all the hops. The propagation-latency metric appears on a dashboard. Killing the sync server and restarting it loses nothing that was confirmed, and the client reconnects on its own.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

### Phase 1: Data and identity substrate (the contracts everything else stores against)
- **Unlocks:** Every later feature, because they all read or write the document format, the permission model or the wire protocol.
- **Depends on:** Phase 0 proving that a Yjs update can round-trip through auth, the sync server and Postgres in production.
- **Tasks (widest → narrowest):**
  1. **Document data contract.** A ProseMirror/TipTap schema v1 stored as a `Y.XmlFragment`. Start minimal: paragraph, heading 1–3, bulleted and numbered lists, bold, italic, link. Every document records its `schema_version`, and there is a forward-migration hook. Changing this later means migrating every stored document, so it comes first.
  2. **Tenant and permission model.** Workspace → document → role (owner, editor, commenter, viewer). Row-level security on every table. The sync server checks permissions **on every incoming message, not only at connect**, so a viewer's edits are dropped.
  3. **Wire protocol envelope.** The Yjs sync protocol wrapped in an envelope carrying `protocol_version`, with a server-side rule for rejecting clients that are too old.
  4. **Storage model.** Append-only `doc_updates` plus a `doc_snapshots` table, and a compaction job that merges the log into a snapshot and trims it.
  5. **Revocation semantics.** Edits from a user whose access was revoked are rejected and never broadcast. This is documented as a product decision.
- **Exit check:**
  - A seeded fuzz test with 50 simulated clients making 10k random concurrent edits ends with byte-identical document states.
  - Rebuilding a document from snapshot plus log equals the live state.
  - Cross-workspace reads fail under row-level security in an automated test.
  - A viewer's edit is dropped and logged.

### Phase 2: Sync correctness under failure
- **Unlocks:** Running more than one sync server and deploying without losing edits. It also makes the rich-text work in Phase 3 safe to build.
- **Depends on:** The proven data contract and storage model from Phase 1.
- **Tasks (widest → narrowest):**
  1. **Confirmation and durability rules.** Clients keep unconfirmed edits locally and resend them after a reconnect. Duplicate resends are harmless because Yjs updates can be applied more than once.
  2. **Fan-out across servers.** Redis pub/sub (the Hocuspocus Redis extension) is added, and two or more sync servers are proven to converge.
  3. **Reconnect and resync.** After a reconnect, client and server exchange only the missing changes (state-vector diff), not the whole document.
  4. **Divergence detector.** Clients periodically send a hash of their document state. The server compares it with its own copy, raises an alert on mismatch and forces a full resync. **This is the alarm for the worst failure.**
  5. **Graceful drain.** On deploy or scale-in, servers tell clients to reconnect elsewhere and finish pending writes before shutting down.
  6. **Limits.** Per-connection caps on message size and rate, and a maximum document size.
- **Exit check:**
  - A chaos test (kill a sync server mid-edit, partition Redis for 30 s, restart Postgres during a failover) loses zero confirmed edits.
  - The divergence alarm fires when a fault is deliberately injected, and stays at zero in normal runs.
  - A rolling deploy under load causes no lost edits.

### Phase 3: Collaborative rich-text editor
- **Unlocks:** The actual product experience.
- **Depends on:** The data contract (Phase 1) and sync proven under failure (Phase 2).
- **Tasks (widest → narrowest):**
  1. **Bind TipTap to the shared document** via y-prosemirror, replacing the Phase 0 plain-text field. Phase 0 test documents are migrated.
  2. **Paste handling restricted to the schema.** Pasted HTML is parsed only into allowed nodes, which removes XSS vectors. Link targets are sanitised (no `javascript:` links).
  3. **Per-user undo.** Yjs UndoManager tracking only local changes, so undo never removes a collaborator's text.
  4. **Presence.** Live cursors, selections and an avatar list, sent over the ephemeral awareness channel and **never persisted**.
  5. **Editor polish.** Toolbar and keyboard shortcuts.
- **Exit check:**
  - Two users applying formatting to overlapping ranges at the same time converge.
  - Undo by user A never reverts user B's edits (automated test).
  - An XSS paste corpus such as the OWASP cheat-sheet payloads produces no executable content.
  - In-region p95 propagation stays under 100 ms with 5 editors.

### Phase 4: Document lifecycle, sharing and history
- **Unlocks:** Real multi-user use beyond a hard-coded document.
- **Depends on:** The permission model (Phase 1), snapshots (Phase 1) and the working editor (Phase 3).
- **Tasks (widest → narrowest):**
  1. **Live permission changes.** When a user is downgraded or removed, the server pushes the new role to their open connections, or disconnects them, within 1 s.
  2. **Sharing.** Invite by email, link sharing with a choice of role, and an audit log of every permission change.
  3. **Version history.** Named snapshots, a preview, and **restore implemented as a new forward edit**, so history is never rewritten.
  4. **Document lifecycle.** Create, rename, soft delete with 30-day restore, and a document list.
- **Exit check:**
  - A removed user's open tab can no longer edit within 1 s.
  - Restoring a version converges for all connected clients.
  - Every permission change appears in the audit log.

### Phase 5: Scale and hardening of what has proven load-bearing
- **Unlocks:** General availability under real load.
- **Depends on:** Phases 2–4 running in production long enough to show where the real bottlenecks are. Only components that have proven load-bearing get hardened here.
- **Tasks (widest → narrowest):**
  1. **Load test** at the targets: 10k concurrent connections and 50 editors on one document. Compare against the fan-out gate (Redis vs routing documents to one node) and flip it if measurements require.
  2. **Compaction tuning.** Move snapshots to S3 if they cross 1 MB.
  3. **Load shedding.** Per-document connection caps and overload responses that ask clients to back off and retry later.
  4. **Tune the Postgres connection pool and write batching** (group commit).
- **Exit check:** At target load, p95 propagation stays under 100 ms and the divergence alarm stays at zero. The written SLO error budget (e.g. 99.9% of edits confirmed within 500 ms) is met for 2 weeks.

### Phase 6: Features at the edges
- **Unlocks:** Feature parity with competitors.
- **Depends on:** The stable editor, permissions and history.
- **Tasks (widest → narrowest):**
  1. **Comments.** Anchored with Yjs relative positions so they survive concurrent edits. This touches the data model, so it comes first.
  2. **Offline editing.** y-indexeddb stores the document locally, and a queue of unsynced edits is sent on reconnect. Phase 1's revocation rule applies.
  3. **Export** to Markdown, PDF and DOCX as async jobs that can be retried safely.
- **Exit check:**
  - Comments stay attached to their text after 1k random concurrent edits around them.
  - Edits made during 1 h offline merge cleanly.
  - Export output matches the editor's rendering on a set of reference ("golden") documents.

## 5. Cross-cutting concerns (per phase, from the first commit)

| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|
| **0** | JWT checked on WebSocket connect; TLS everywhere; secrets in a secrets manager; document content never logged | OpenTelemetry traces across all hops; edit-to-remote-render latency, connection and write metrics; JSON logs with trace IDs; 3 alerts | Terraform for all infrastructure; lockfiles; images pinned by digest; one CI pipeline from staging to production | Client reconnect with exponential backoff and jitter; edits confirmed only after a durable write; health checks |
| **1** | Postgres row-level security for workspace isolation; permission check on every message; old protocol versions rejected | Metrics for permission denials, schema-version distribution and compaction runs/duration | Seeded fuzz test (a failing seed can be replayed); versioned database and schema migrations | Daily Postgres point-in-time-recovery restore drill; rebuild-from-log tool tested |
| **2** | Per-connection rate and size limits; Redis protected with auth and TLS | **Divergence detector alarm**; reconnect-storm and resync metrics; Redis lag metric | Chaos tests scripted in CI with a fixed seed; anonymised replay of a document's update log reproduces sync bugs | Unconfirmed edits resent after reconnect; graceful drain; tested Redis partition and Postgres failover |
| **3** | Paste and HTML handling restricted to the schema; link sanitising; Content Security Policy headers | Client error reporting (Sentry) with editor state redacted; metrics for local edit time and render time | Deterministic browser tests (Playwright) with 2 clients against a fixed fixture document | Editor error boundary that keeps unsynced local edits and reloads cleanly |

## 6. AI layer
**N/A.** There are no AI or agent features in scope. If an AI writing assistant is added later, re-run the plan with the AI layer: guardrails, cost and latency budget, and human-in-the-loop gating come first, and AI suggestions must arrive as reviewable proposals, never as edits applied straight into the shared document.

## 7. Deferred
- **End-to-end encryption.** Pull forward if a contract requires zero-knowledge. This would have to happen *before* Phase 1 (see the gate).
- **Multi-region active-active.** Pull forward when p95 latency for users outside the region exceeds 150 ms, or a data-residency contract is signed.
- **Suggestion mode / track changes.** Pull forward once comments (Phase 6) are stable and customers ask for review workflows. It extends the data contract, so it needs a schema version bump.
- **Tables, embeds, images.** Pull forward when the core schema has been stable for one release cycle. Each one needs a schema migration.
- **Full-text search across documents.** Pull forward when users have more than ~200 documents each, or search is the top request. It would be an async indexer on the queue.
- **Notifications and @mentions.** Pull forward after comments ship and engagement data shows a need.
- **Peer-to-peer sync over WebRTC.** Pull forward only if server bandwidth cost dominates. Yjs leaves this option open.
- **Splitting into microservices, and routing each document to one node.** Pull forward on the revisit triggers in Section 2.
- **Native mobile apps and a public API or plugins.** Pull forward once the web product hits its SLO and there is clear demand.
