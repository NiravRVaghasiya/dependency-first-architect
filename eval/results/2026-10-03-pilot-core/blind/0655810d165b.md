# photoname: Architecture and Build Plan

*A command-line tool that renames a folder of photos by their EXIF capture date*

---

## 1. Summary

- **What:** `photoname` is a cross-platform Python command-line tool. It renames the photos in one folder, along with their related files, to their capture time. For example, `IMG_4021.HEIC` and `IMG_4021.MOV` become `2024-07-14_18-03-22.heic` and `2024-07-14_18-03-22.mov`. *Assumed user:* one technical person, or a few, tidying a personal photo library, mainly on Windows.
- **Shape:** one Python process that runs **scan → read metadata → plan → preview → apply**. The planner works only in memory and decides every rename before anything on disk changes. The executor then applies that plan and writes a **journal** (a record of every rename) as it goes, so any run can be undone.
- **Key decisions:**
  1. Read metadata with **ExifTool** (a widely used free metadata reader), called once for the whole folder. It sits behind a `MetadataReader` interface. Pure-Python libraries were rejected because HEIC, RAW and video coverage matter more than avoiding an extra install.
  2. **Dry run is the default.** Nothing changes on disk unless you pass `--apply`.
  3. **Every apply is journaled, uses two-phase renames, and is all-or-nothing.** If anything fails, the tool rolls the whole run back automatically.
  4. **Camera clock time is used as recorded.** Photos get no timezone conversion. Only video timestamps, which are stored in UTC, get special handling.
  5. **Files with no trustworthy date are skipped and listed.** The tool never guesses silently.
- **First milestone (M1, 2–4 developer-days):** JPEG renaming works end to end, with the preview table, `--apply`, collision suffixes, the journal and `undo`. CI passes on Windows, macOS and Linux. M1 also includes three half-day spikes (short, time-boxed experiments) on formats, filesystems and video time.
- **Top risks:** overwriting files or losing original names; wrong dates on videos; filesystem quirks such as case-insensitive drives, exFAT SD cards and OneDrive/iCloud placeholder files.
- **Check this first:** `exiftool "-FileName<DateTimeOriginal" -d %Y-%m-%d_%H-%M-%S%%-c.%%e DIR` already does the basic rename. A custom tool is only worth building for **preview, undo, keeping Live Photo and RAW+JPEG pairs together, and safe re-runs**. If you don't need those, use the one-liner and skip this plan.

## 2. Context and Goals

- **Problem:** Camera file names (`IMG_4021`, `DSC_0001`, `PXL_2024…`) don't sort by time across devices. They also repeat across cameras and clash when folders are merged. Today the options are renaming by hand or running ExifTool one-liners, which can't be undone and can split Live Photo pairs.
- **Goals:**
  - Rename every file that has a reliable capture date to a sortable name: `YYYY-MM-DD_HH-MM-SS[_NN].ext`.
  - Never overwrite or lose a file, and make every run reversible.
  - Keep related files under the same base name: Live Photo HEIC+MOV pairs, RAW+JPEG pairs, and `.xmp` / `.aae` sidecar files (small files holding edits or metadata).
  - Make re-runs safe: running the tool again on a finished folder changes nothing.
- **Non-goals:**
  - Sorting files into `YYYY/MM` folders.
  - Searching sub-folders (deferred).
  - Writing or fixing metadata, including correcting a camera clock (deferred).
  - Removing duplicates, a GUI, cloud photo libraries, and watching folders for new files.
- **Success measures:** a 5,000-file mixed folder from the user's own devices renames with no unexplained skips. `undo` then restores exactly the original file listing. The user goes on to run it on the real library.

## 3. Drivers, Requirements, and Constraints

**Ranked quality attributes**

| # | Attribute | Measurable target | Why it matters |
|---|---|---|---|
| 1 | Data safety | 0 files overwritten or lost. Every rename is recorded in the journal before it happens. `undo` restores the original names exactly. A run interrupted by a crash or power loss can always be recovered. | Original names can't be recovered any other way, and the photos are irreplaceable. |
| 2 | Date correctness | 100% of the test-corpus files get their expected name. 0 silent guesses: files without a date are skipped and the reason is shown. | A wrong name is worse than no rename, because it gives a false order forever. |
| 3 | Portability | Runs on Windows 10/11, macOS 13+ and Ubuntu 22.04+, including paths with non-ASCII characters. Install takes 5 minutes or less *(assumption)*. | The user is on Windows, and photos come from mixed devices and drives. |
| 4 | Performance | Plans 10,000 files in 60 s or less on a local SSD *(assumption)*. | Libraries hold thousands of files. Speed only needs to be bearable. |
| 5 | Evolvability | A new naming template or date-source rule can be added, with a test, in under an hour. | Naming is a personal preference and likely to change. |

**Key functional requirements**

- Preview the renames, then apply them.
- Undo a run.
- Add suffixes when two files would get the same name (for example, burst shots taken in the same second).
- Group related files and rename them together.
- Report every skipped file with its reason.
- Accept a custom naming template.

**Constraints**

- No team was named. *Assumed:* 1 developer who knows Python, working part-time, with no budget.
- Python 3.11 or later.
- ExifTool is a runtime dependency. It is free and has a Windows `.exe`.

**Hard parts**

- **Rename safety:**
  - The original name is the one piece of information you can't get back.
  - Renames can form chains (A→B while B→C).
  - On case-insensitive filesystems (Windows, and macOS by default), a change of letter case only (`.JPG` → `.jpg`) needs special handling.
  - On Linux and macOS, Python's `os.rename` silently overwrites an existing file.
- **Extracting dates:**
  - Several date tags can be present: `DateTimeOriginal`, `CreateDate` and `ModifyDate`.
  - Some files store fractions of a second.
  - Some files have no EXIF at all, such as screenshots and images sent through WhatsApp.
  - Video timestamps are stored in UTC, not camera local time.
- **Grouping related files:** Live Photo and RAW+JPEG pairs must keep matching names, or photo apps stop treating them as pairs.
- **Platform quirks:**
  - Paths with non-ASCII characters on Windows have to be passed to ExifTool correctly.
  - exFAT drives and network (SMB) shares may behave differently on rename.
  - OneDrive and iCloud placeholder files download themselves when they are read.

## 6. Architecture Overview

```
 user shell:  photoname DIR [--apply] [--format …]     photoname undo DIR
     │
┌────▼──────────────── photoname (one Python process) ─────────────────┐
│  cli ─► scan ─► metadata ─► plan ─► report (dry-run table / summary) │
│                    │          │                                      │
│                    │          └─► execute ─► journal (write)         │
│                    │                 ▲                               │
│                    │           undo ─┘ (reads journal, probes disk)  │
└────────────────────┼─────────────────┼───────────────────────────────┘
   subprocess, no shell│ argfile + -json   │ os.rename, os.stat
 ═══ trust boundary ═══▼═══════════════════▼═══════════════════════════
               exiftool binary      DIR/ photos + DIR/.photoname/journal-*.jsonl
```

**How the parts fit together.** The flow is strictly one-way:

1. `scan` lists the files and groups them by base name (the "stem").
2. `metadata` reads every capture date with a single ExifTool call.
3. `plan` is pure logic with no input/output. It turns the groups and dates into a validated `Plan`.
4. `report` prints the plan. With `--apply`, `execute` carries it out and records it in a journal.
5. `undo` reverses a run using that journal.

**Trust boundary.** File contents and metadata are untrusted. Only date values that pass a strict pattern check ever end up in file names.

**Components**

| Component | Responsibility | Owns data | Interface | Technology | Depends on |
|---|---|---|---|---|---|
| `cli` | Parse arguments, wire the stages together, set exit codes | none | Shell commands; exit codes 0 / 1 / 2 / 3 | `argparse` | all |
| `scan` | List regular files (skipping symlinks and hidden files) and group by stem | `SourceFile`, `PhotoGroup` | `scan(dir) -> list[PhotoGroup]` | stdlib | — |
| `metadata` | Get the capture time for each file | `CaptureTime` | `MetadataReader.read(paths) -> dict[path, CaptureTime \| None]` | ExifTool subprocess | exiftool |
| `plan` | Choose dates, build names, resolve clashes, detect already-named files, check the plan is safe | `Plan`, `RenameOp`, `Skip` | `build_plan(groups, times, template) -> Plan` | stdlib | — |
| `report` | Show the dry-run table and summaries | — | `render(plan)` | stdlib | — |
| `execute` + `journal` | Apply the plan with two-phase renames, roll back on failure, undo | Journal files | `apply(plan)`, `undo(dir)` | stdlib | filesystem |

## 7. Component Details

**`scan`** lists `DIR` without searching sub-folders. It skips symlinks, `.photoname/` and dotfiles. It groups files by stem, ignoring letter case, so `IMG_1.HEIC`, `IMG_1.MOV`, `IMG_1.AAE`, `IMG_1.xmp` and `IMG_1.HEIC.xmp` form one group. In M1 every group holds a single file, but the data shape is already a group so that M2 doesn't need a rewrite. `scan` does not read file contents.

**`metadata` / `ExifToolReader`**

- Makes one subprocess call per run, with no shell, and passes the file paths through an argfile (`-@ file`). This avoids the roughly 32k-character command-line limit on Windows. `-charset filename=utf8` handles non-ASCII paths.
- Requests these tags: `DateTimeOriginal`, `SubSecTimeOriginal`, `OffsetTimeOriginal`, `CreateDate`, `Keys:CreationDate` (Apple video, which includes the offset), and `QuickTime:CreateDate`, plus `-api QuickTimeUTC`. Spike S1 confirms the exact list.
- Parses values with a strict pattern (`YYYY:MM:DD HH:MM:SS`). It rejects `0000:00:00` and years before 1990 or in the future, and records which tag supplied the date.
- **Failure handling:** if ExifTool is missing, the tool exits with code 2 and shows install instructions. The subprocess has a timeout that scales with the number of files. A file that ExifTool can't read returns `None` and is skipped with a reason.
- The ExifTool version is logged, and a minimum version is set after S1.
- **Not its job:** this component doesn't build names.

**`plan`** (where the logic lives; pure and heavily tested)

- **Choosing the date:**
  - For photos: `DateTimeOriginal` (+ subseconds), then `CreateDate`, then skip.
  - For videos: `Keys:CreationDate` (local time with offset), then `QuickTime:CreateDate` converted from UTC to the machine's local time zone. The second case is flagged `tz_assumed` and shown in the preview.
  - If `--fallback mtime` is set, the file's modified time is used and labelled as such.
- **Groups:** the date comes from the primary file in the group, with image preferred over video over RAW. If the members' dates differ by more than 2 s, a warning is shown.
- **Name:** the date is formatted with `--format` (default `%Y-%m-%d_%H-%M-%S`), and each member keeps its own extension, lowercased.
- **Clashes:** groups with the same base name are sorted by (subsecond, original name). The first gets the base name; the rest get `_01`, `_02`, and so on. Clashes are compared ignoring letter case.
- **Already named:** if a file's current stem already equals `base` or `base_NN` for its own date, it is skipped. This makes re-runs change nothing, and existing names stay stable when new files are added later.
- **Safety checks (the run aborts if any fails):**
  - Every target name is unique, ignoring case.
  - No target matches an existing file that isn't itself being renamed in this plan.
  - Every target is a single path component with no `/ \ : * ? " < > |`.
  - No target is a Windows reserved name such as `CON` or `NUL`.

**`execute` + `journal`**

1. If `DIR/.photoname/` holds an unfinished journal, refuse to run and tell the user to run `photoname undo DIR`.
2. Check each source file again (size and modified time). If anything changed since planning, abort.
3. Write the journal header. It contains every operation (`src`, `tmp`, `target`, and the file's identity: `st_ino`/`st_dev`, falling back to size + mtime). Flush it to disk with `fsync` **once**.
4. **Phase 1:** rename each `src` to `.<uuid>.photoname-tmp` in the same folder.
5. **Phase 2:** rename each temp file to its `target`. First check that the target doesn't exist (`os.path.lexists`); on Windows `os.rename` also refuses to overwrite.
6. Write a `complete` marker.

Progress lines are added to the journal as each rename happens, but they aren't flushed to disk one by one. Recovery doesn't depend on them: `undo` finds each file by checking `src`, `tmp` and `target` against the identity stored in the header. This approach handles chains and avoids around 20,000 disk flushes.

**Failure:** any exception triggers an automatic rollback in reverse order, and the tool exits with code 1. If the rollback itself fails, it exits with code 3 and prints the journal path and the files that need manual attention.

**`undo`** reads the most recent journal. It moves each file back after checking its identity. If something is unclear, such as an unknown file now sitting at the original name, it skips that file and reports it.

**Not its job:** `execute` doesn't make decisions. It only carries out a plan that has already been checked.

## 8. Data Design

- **Entities:**
  - `SourceFile`: path, extension, size, modified time in nanoseconds, file ID.
  - `PhotoGroup`: stem, primary file, members.
  - `CaptureTime`: naive local datetime, subseconds, source tag, `tz_assumed` flag.
  - `RenameOp`: group, src, tmp, target, identity.
  - `Plan`: operations, skips with reasons, warnings.
  - `Journal`: header with `version: 1`, tool version, folder, timestamp and the full list of operations; progress lines; an end marker (`complete` or `rolled_back`).
- **Where the truth lives:** the filesystem holds the files. Journals are written only by `execute` and read only by `undo`. There is no database.
- **Consistency:** each run is all-or-nothing.
- **Retention:** journals stay in `DIR/.photoname/` indefinitely. They are small, about 300 bytes per file. A command to prune them is deferred.
- **Sensitive data:** photos can contain GPS coordinates and other personal metadata. The tool reads only date tags. Logs and journals contain only file names. Test fixtures have GPS stripped (`exiftool -gps:all=`).
- **Format changes:** the journal format carries a `version` field, and `undo` refuses versions it doesn't know.

## 9. Key Flows

**F1: Preview (the default).** `photoname D:\Photos\2024-trip`

1. Scan finds 1,214 files in 1,180 groups.
2. One ExifTool call reads all the dates.
3. The planner produces 1,150 renames, 22 files already named, and 8 skips (5 with no EXIF, 3 unreadable).
4. The tool prints a table (`old → new`, date source, flags) and the summary.
5. Nothing on disk changes.

Running the same command after an apply reports 0 renames.

**F2: Apply.** `photoname D:\Photos\2024-trip --apply`

1. The tool rebuilds the plan, prints the summary, and asks `Rename 1,150 files? [y/N]` (`--yes` skips the prompt).
2. The journal header is written and flushed to disk.
3. Phase 1 runs, then phase 2, then the `complete` marker is written.
4. The tool prints: `Renamed 1,150. Undo with: photoname undo D:\Photos\2024-trip`.

**F3: Failure — a file is locked on Windows.** During phase 2, `IMG_0042.tmp → 2024-07-14_18-03-22.jpg` raises `PermissionError` because the image is open in another app.

1. `execute` stops at once.
2. It reverses every phase-2 rename already done, then every phase-1 rename, using the journal.
3. It writes `rolled_back` to the journal and exits with code 1: `Rolled back; close the program using IMG_0042.jpg and re-run.`

The folder is now exactly as it was before the run.

**F4: Failure — interrupted by power loss or killing the process.**

1. The next `photoname DIR` run finds a journal with no end marker and refuses to plan.
2. `photoname undo DIR` uses the identities in the header to find each file, whether it is at its original name, its temp name or its target. It moves each one back and reports any file it couldn't place.

## 11. Cross-Cutting Concerns

- **Security** (local tool, single user, built in M1):
  - ExifTool runs without a shell, and paths are passed through an argfile, so there is no command injection.
  - EXIF strings never flow into names; only parsed date digits do.
  - The `--format` output is checked to be a single safe path component, which prevents path traversal.
  - Symlinks are never followed.
  - Dependency scanning: `pip-audit` in CI (M1).
- **Reliability:** covered by D4 and §7. All-or-nothing runs, recovery by checking file identity, an ExifTool timeout, a re-check of each file before applying, and refusal to run while an unfinished journal exists (M1).
- **Observability:**
  - The dry-run table and summary.
  - `-v` writes structured log lines to stderr.
  - The journal acts as an audit trail.
  - `--json` outputs the plan as JSON (M3).
  - Clear exit codes: 0 success, 1 rolled back, 2 setup or usage error, 3 manual action needed.
- **Performance:** the bottleneck is ExifTool reading files, about 20–40 s for 10,000 files *(estimate, measured in S1 and M2)*. If needed, the `-fast2` option reads less of each file. Renames are cheap. Memory is under 50 MB for 20,000 files.
- **Cost:** none to run. ExifTool and Python are free.
- **Operations:** the user runs the tool themselves, so there is no on-call. The README has a "something went wrong" section: run `undo`, explain exit code 3, and say how to read the journal (M3).
- **AI-specific concerns:** not applicable; no model is involved.

## 14. Testing and Validation Strategy

- **Unit and property tests** (`plan`, `scan`, parsers): cover the date and naming rules (driver 2), safety checks and re-run behaviour (driver 1). They use Hypothesis to generate random sets of names and dates, including clashes and chains.
- **Fault-injection tests** (`execute`): an `os.rename` failure at every step, and a kill at a random step followed by `undo`. These guard driver 1 and block any release.
- **Integration tests with real ExifTool:**
  - Generated fixtures: tiny files tagged by ExifTool.
  - A golden corpus from M2 onward: one real sample per format from A2, GPS stripped, cloned and re-tagged to create edge cases. The expected names live in `tests/fixtures/expected.json`.
- **Cross-platform:** the CI matrix runs on Windows, macOS and Linux for driver 3. The exFAT and SMB results come from the S2 manual run.
- **Performance:** `scripts/make_corpus.py` generates 10,000 tagged JPEGs, and a manual timing is recorded in M2 (driver 4). This doesn't block CI.
- **What blocks a release:** ruff, every pytest suite on all three OSes, and pip-audit with no high-severity findings.

## 15. Rollout, Migration, and Rollback

- **Rollout:**
  1. The author runs it on a *copy* of a real folder (M2 exit).
  2. Then on the real library.
  3. Then shares it through `pipx install git+…@v0.x`, moving to PyPI in M3.
- **Migration:** none; no older system exists.
- **Rolling back renames:** `photoname undo DIR`. The point of no return is deleting `.photoname/`, or moving or renaming files by hand after a run. `undo` detects this through the identity check and reports the files it can't restore instead of guessing.
- **Rolling back the tool itself:** `pipx install photoname==<previous>`. Journals with a version number keep older journals readable.
