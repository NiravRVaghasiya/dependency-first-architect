# BUILD PLAN: Moving the patient scheduling system from on-premises to the cloud with no downtime

**Assumptions this plan rests on.** Each one says what changes if it is false.
- **(a) The app has a server tier.** I assume it is a web or app-server app on one relational database (SQL Server assumed) that only the hospital runs. If instead desktop clients connect straight to the database, moving users in groups first (Phase 2) means moving Citrix/VDI hosts instead, or skipping straight to the flip in Tradeoff 4.
- **(b) HL7 messaging stays as it is.** HL7 v2 messages go through an on-premises interface engine to an on-premises EHR, and both stay where they are.
- **(c) A cloud provider is chosen.** The hospital's enterprise agreement already names a provider that will sign a BAA. If no provider is chosen, that choice becomes an R3 gate in front of Phase 0.
- **(d) "No downtime" allows a short write pause.** It means reads never stop and writes may pause for a few seconds at the database switch while clients retry. If even that is not allowed, Tradeoff 2 reopens. That would mean two databases both taking writes, which risks double-booking.

## 1. Classification and constraints
- **What:** move a live, PHI-bearing (HIPAA-protected patient data) scheduling application and its database from on-premises to a cloud provider. Schedulers, the call center, clinics, the patient portal and HL7 interfaces keep working throughout.
- **Type:** infrastructure plus software. Brownfield. Not a small build: it holds regulated data, has R3 decisions and many teams.
- **Dominant constraint:** availability, with correctness close behind.
- **Worst failure:** two databases both accepting writes at the switch, or replication losing writes. Either loses, duplicates or double-books appointments, and patients miss care or show up to conflicting slots. PHI exposure in the cloud comes second; V2 guards it.

**Inherited constraints** (this move does not change them; each line gives the cost to change):
- **Single application:** the app stays one unit, not split into services. Changing that is a re-architecture project.
- **Database engine and schema:** both stay. A different engine means a schema port and re-certification.
- **HL7 v2:** messages still go through the existing interface engine. Changing that means re-testing every interface with the EHR and outside vendors.
- **Staff logins:** they stay on the existing Active Directory / SSO. Changing that is a new trust boundary for all staff.
- **EHR:** it stays on-premises.
- **Downtime procedures:** the hospital's existing paper/business-continuity procedures stay the last-resort fallback.

## 3. Tradeoff gates

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| System of record while both sites exist | R3: two databases taking writes gives double-bookings that cannot be undone | Exactly one writable database at all times: on-premises until the switch, cloud after. Replication runs one way. The old side is fenced read-only. | Only the app and the interface engine write to the database | V1, V6 | V1 finds a direct writer that cannot be re-pointed during the switch: the switch waits until it can. |
| Consistency vs availability | R3: a split brain harms patients | Consistency. Synchronous copies across zones inside the region, async to on-premises/disaster recovery. ## 4. Walking skeleton (Phase 0)
- **The one real request:** an allow-listed IT analyst uses the cloud-hosted app instance to book, then cancel, an appointment. It is for the designated production test patient (ZZTEST), in a test resource and clinic, in the live schedule.
  - **Response:** a booking confirmation.
  - **HL7 messages:** a new-appointment and a cancellation message reach the EHR's test-patient record.
- **Tiers it crosses:** workstation → hospital network → VPN or circuit → internal cloud load balancer → cloud app VM (AD login through domain controllers in the cloud) → back over the link → on-premises production database (the system of record) → interface engine → EHR.
- **Deploy:** the infrastructure-as-code and app-artifact pipeline only, with no manual steps.
- **Batch jobs:** turned off on the cloud node. Only one node may run them, so it stays on-premises.
- **Logging:** app, load-balancer and database audit logs go to a log store and the SIEM inside the BAA boundary. That store is classified as PHI.
- **Monitoring:** a synthetic test-patient transaction every 5 min, with an alert when it fails.
- **Rollback:** redeploy the previous artifact through the pipeline. Taking the node off the allow-list removes the whole path.
- **Who can reach it:** only allow-listed IT staff, on a separate internal hostname with no user DNS entry. It is deployed only after V2 passes.
- **Exit check (V0):**
  - the real request succeeds, with one trace across every tier;
  - a deploy and a rollback both succeed through the pipeline;
  - stopping the app service fires the alert within 5 min;
  - booking p95, database round trips per booking and link round-trip time are recorded as baselines.

## 5. Phases

**Phase 0: Discovery, baselines, landing zone, skeleton**
- **Unlocks:** Phase 1.
- **Depends on:** nothing earlier. V2 must pass before the skeleton touches production.
- **Tasks:**
  1. Start the organizational items: BAA, circuit order, vendor support statement, CAB plan, sign-off on the "no downtime" definition, retention period, disaster-recovery RPO/RTO.
  2. Start flow capture on the app and database servers. It runs through a month-end (V1).
  3. Inventory everything that depends on the system: HL7 appointment and patient-registration feeds, portal, SMS/IVR reminders, billing, warehouse ETL, direct database readers (reporting tools), file drops, printers and kiosks, hardcoded IPs, batch jobs. Mark each CONFIRMED or ASSUMED.
  4. Put on-premises monitoring agents in place through the existing CAB process. Record baselines.
  5. Build the landing zone in infrastructure as code: accounts, network, policies locking to the region and blocking public IPs, keys, logging to the SIEM, admin access with MFA and just-in-time elevation (PIM).
  6. Pass V2.
  7. Build the skeleton (§4).
- **Rollback:** take the cloud node off the allow-list. Nothing on-premises changes.
- **Exit check:** V0 and V2 pass; V1 capture is running.

**Phase 1: Data foundation**
- **Unlocks:** Phase 2 and switch rehearsals.
- **Depends on:** V0, V2.
- **Tasks:**
  1. Provision the cloud database with infrastructure as code.
  2. Seed it from a backup.
  3. Start one-way replication, on-premises → cloud.
  4. Run a daily reconciliation: row counts plus per-table hashes, and no PHI in the output.
  5. Check that time zone, collation and encoding match. Cloud VMs default to UTC, so appointment times could shift.
  6. Turn on point-in-time recovery backups and run a restore test.
  7. Build and test reverse replication in non-production.
  8. Run V4 and V5 on a production-sized copy.
- **Rollback:** drop the replica. The on-premises system of record is untouched.
- **Exit check:** V4 and V5 pass. V3 is running (14-day window).

**Phase 2: Living with both systems (app tier moves in groups)**
- **Unlocks:** Phase 3.
- **Depends on:** V1, V4, V5. V3 must pass before Phase 3.
- **Tasks**, smallest exposure first:
  1. Prepare the integrations ahead of time: vendors allow-list the cloud IPs, and the interface engine has its cloud endpoints defined but off.
  2. Move read-only reporting consumers to the replica: one report first, then the rest.
  3. Move user groups to the cloud app tier in this order: IT → one low-volume clinic → one department → call center → everyone. Each group stays ≥ 3 business days, including a Monday peak. A group widens only if its error rate and p95 are within budget and help-desk tickets are flat.
  4. Batch jobs stay on the one on-premises node that runs them.
  5. Run V6 rehearsals on a production-sized restored copy with a test interface engine.
- **Rollback:** send a group back to the on-premises app tier by changing the load-balancer weight. Takes minutes.
- **Exit check:**
  - 100% of users are on the cloud app tier (if V4 passed);
  - V3 and V6 pass;
  - application releases and schema changes have been frozen since the first rehearsal.

**Phase 3: Database switch** (an irreversible operation; see E1)
- **Unlocks:** Phase 4.
- **Depends on:** V3, V6, CAB approval and the clinical go/no-go.
- **Tasks:**
  1. Pick a low-volume window from the baseline (for example Sunday 02:00).
  2. Have downtime-procedure staff on standby.
  3. Run the checks at T-24h.
  4. Put the app tier into a short "hold writes" state while reads continue.
  5. The interface engine queues messages instead of sending them.
  6. Confirm replication lag is 0 and the final reconciliation is green.
  7. Promote the cloud database to primary.
  8. Fence on-premises: make it read-only and revoke the app's database logins.
  9. Start reverse replication.
  10. Re-point the database listener DNS.
  11. Move the batch jobs, still on a single node, to the cloud.
  12. Turn on the interface engine's cloud endpoints and drain its queues.
  13. Resume writes.
  14. Run the test-patient smoke test.
  15. Reconcile HL7 message counts.
  16. Rotate credentials.
  17. Start 14 days of close support.
- **Rollback:** reverse switch using the same runbook while reverse replication is healthy. The abort criteria are fixed in the V6 runbook.
- **Exit check:**
  - the post-switch reconciliation shows 0 lost or duplicated appointments;
  - HL7 counts match;
  - SLOs are at baseline for 14 days.

**Phase 4: Settle in, disaster recovery, decommission**
- **Unlocks:** the end state.
- **Depends on:** Phase 3, the disaster-recovery RPO/RTO input, and V7 before the point of no return.
- **Tasks:**
  1. Set up in-country cross-region disaster recovery and run a drill.
  2. Right-size against the cost budget.
  3. Confirm no traffic still reaches on-premises.
  4. Archive and run a restore test.
  5. Pass V7.
  6. Stop reverse replication. This is the point of no return.
  7. Decommission, with media sanitized to NIST 800-88.
- **Rollback:** none after task 6. V7 guards it.
- **Exit check:** V7 passes, and the cost is within the Finance budget.

## 10. Deliberately deferred
- **Splitting the app into services, or moving to platform services.** Pulled forward when the app is stable in the cloud for 90 days and a business case exists.
- **Moving the interface engine or the EHR to the cloud.** Pulled forward by a separate program decision; it would need its own inventory.
- **Active-active across regions.** Pulled forward if the disaster-recovery RPO/RTO cannot be met with warm standby.
- **Reserved capacity or savings plans.** Pulled forward after 30 days of cost data after the switch, checked against the Finance budget.
- **Autoscaling.** Pulled forward if V5 or real peaks exceed the fixed sizing.
- **Changing the database engine.** Pulled forward if the vendor or licensing forces it; that would be a new plan.
- **New patient-facing features.** Pulled forward after V7; they stay frozen until then.
