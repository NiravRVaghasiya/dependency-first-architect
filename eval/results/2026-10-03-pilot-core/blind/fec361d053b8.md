# Plan: CI/CD platform for 50 microservices

**Assumptions this plan rests on. If any is wrong, the phase order changes, so please confirm:**
1. **The 50 services already exist and ship through older pipelines.** If they don't, there are no migration waves, Phase 4 becomes onboarding, and V5/V6 go away.
2. **Every service deploys to Kubernetes.** If some don't, the deploy-model row in §3 changes for them.
3. **The code lives on GitHub.**
4. **No audit regime (SOX/SOC 2/PCI) is confirmed yet.** If one applies, approval separation and change-record evidence move into Phase 2.

---

## 1. Classification and constraints
- **What:** A shared build, test, sign and deploy path (golden path) that 50 existing services move onto in waves. It replaces their separate pipelines.
- **Type:** Infrastructure plus some software (pipeline templates and policy code). Brownfield. Not small: many teams, an R3 trust-boundary decision, and it deploys to production for real users.
- **Dominant constraint:** Correctness and security of what reaches production. Production availability comes second, because one shared deployer can hit all 50 services at once.
- **Worst failure:** The platform becomes the way an unreviewed or malicious artifact reaches production across many services, either through a compromised CI job, credential or pipeline definition, or through a template bug pushed to the whole fleet. Guarded by V1, plus release rings for template changes (Phase 2).

## 3. Key decisions

|---|---|---|---|---|---|

| Platform shape (monolith vs services) | R2: 50 repos follow its interface | One shared golden path (versioned reusable workflows plus Argo CD), with a documented escape hatch. | Build vs buy (CI engine and runners) | R2: moving CI systems takes weeks | GitHub Actions on GitHub-hosted runners, managed registry, Argo CD. ## 4. First end-to-end slice (Phase 0)
- **Request and response:** A real commit merged to one low-criticality, stateless service with a willing owner. It is built, signed (audit mode only), pushed to the registry by digest, synced to staging and smoke-tested. Then the same digest is promoted by an environment-repo PR and synced to prod. A real user request to that service returns the new version in a response header.
- **Tiers:** GitHub → Actions workflow v0 → OIDC → managed registry → environment repo → Argo CD (staging, then prod) → service → existing metrics stack.
- **How it runs on day zero:**
  - Platform built with Terraform through its own pipeline.
  - Pipeline and Argo events go to metrics, with deploy markers on the service's dashboard.
  - Alerts fire on failed sync, degraded health or a failed pipeline, and page the platform on-call.
  - Rollback: `git revert` in the environment repo. Full fallback: detach the Argo app without deleting anything and re-enable the frozen old pipeline.
- **Who can reach it:** Only this one service is allow-listed. Argo is scoped to that service's namespace. The service's users are the same users as before. No other team can use the templates yet. Branch protection and review rules are kept as strict as the old path.
- **Also in Phase 0 (read-only or organizational):**
  - Inventory all 50 services: stack, deploy target, secrets, tier, owner.
  - List everything that depends on the old CI, each marked CONFIRMED or ASSUMED.
  - Measure the baselines in §1.
  - Request the CI budget, the security review date and the audit-regime answer.

**V0** = the standard exit check: a real deploy and a rollback through the pipeline, one trace across every tier, an injected failure (a bad image tag in staging) fires an alert, and first values are recorded as low-load baselines.

## 5. Phases

**Phase 1 — Trust boundary and supply chain** (most rework if wrong: all 50 services inherit it)
- **Unlocks:** exposing the platform beyond the skeleton (via V1).
- **Depends on:** V0.
- **Tasks:**
  1. OIDC from CI to the cloud; remove every long-lived credential.
  2. CODEOWNERS and required reviews on workflow files, templates and environment-repo paths. Fork PRs get no secrets.
  3. One Argo CD project per team.
  4. Keyless cosign signing plus SLSA provenance. Admission policy enforced in prod for migrated namespaces, audit-only elsewhere (so services not yet migrated aren't blocked).
  5. Secret manager plus External Secrets, push protection, log masking.
  6. Write and rehearse the break-glass procedure.
  7. Secret scan of the history of all 50 repos; rotate whatever it finds.
- **Rollback:** put admission back in audit mode; re-enable old credentials (kept sealed until V6).
- **Exit check:** V1.

**Phase 2 — Template contract and capacity**
- **Unlocks:** template 1.0 and committing to runners (via V2, V3).
- **Depends on:** Phase 1, the budget input.
- **Tasks:**
  1. Define the template interface (`service.yaml`: owner, tier, profile, test commands) and language profiles that cover ≥ 80% of the inventory.
  2. Version templates with semver, keep N-1 working, roll out bumps through Renovate.
  3. Release rings for template changes: pilot repos → 10% → all.
  4. Run V2 with 3 mixed pilots: the most common stack, an unusual one, and one with DB migrations.
  5. Run V3.
- **Rollback:** pilot repos pin the previous template version or go back to their old pipeline.
- **Exit check:** V2, V3.

**Phase 3 — Deploy safety and platform resilience**
- **Unlocks:** tier-1 migration (via V4).
- **Depends on:** V2.
- **Tasks:**
  1. Automatic health checks and rollback.
  2. Argo Rollouts canary for tier-1 profiles.
  3. Per-service lead time, deploy frequency, failure rate and restore-time dashboards.
  4. Argo CD and policy controller in HA, registry replication, a retention rule that never deletes a digest that has run in prod.
  5. Game days for CI, Git and registry outages.
  6. DR test: rebuild the platform from Terraform within the RTO.
  7. Run V4.
- **Rollback:** turn off auto-rollback or canary per profile.
- **Exit check:** V4, game day and DR targets met, operational-complexity cap held.

**Phase 4 — Migration waves** (smallest exposure first)
- **Unlocks:** the whole fleet on the platform.
- **Depends on:** V1, V2; V3 before wave 2; V4 before wave 3.
- **Waves:** wave 1 = 5 low-criticality services; wave 2 = about 20; wave 3 = the rest, tier-1 last.
- **Before each service cuts over:** secrets moved and scan clean; new pipeline run in shadow next to the old one for 1 week with matching test results; team briefed.
- **At each cutover:** freeze the old pipeline, Argo takes ownership, enforce admission in that namespace, revoke the old pipeline's prod credentials only after the V5 window.
- **Rollback:** per service, re-enable the old pipeline (the system of record goes back to it).
- **Exit check:** V5 per wave.

**Phase 5 — Shut down the old CI**
- **Depends on:** V5 for all waves.
- **Tasks:**
  1. Move or retire every old-CI dependent from the inventory.
  2. Export build and audit records to the archive.
  3. Power off the old CI for 2 weeks (still reversible).
  4. Run V6, then delete.
- **Point of no return:** deleting the old CI and its credentials, guarded by V6.

## 10. Deferred
- **Developer portal (Backstage):** pull forward when the fleet passes about 100 services or teams struggle to find services.
- **Per-PR ephemeral environments:** pull forward when V5 shows integration bugs driving change failures (§3 flip).
- **ARC self-hosted runners:** pull forward when V3 fails or tests need private network access.
- **Blocking builds on critical CVEs from SBOMs:** pull forward once the scanner's false-positive rate has been measured on 2 waves.
- **Merge queues:** pull forward when main-branch breakage on any service goes above about 1 in 20 merges.
- **Per-team cost showback:** pull forward when runner spend passes 80% of budget.
- **Multi-region active-active platform:** pull forward when a region outage blocking deploys breaks a stated RTO.
