# BUILD PLAN — Real-time collaborative document editor

## 1. Classification and constraints
- **What:** A browser-based rich-text editor where several users edit the same document at once and see each other's changes live. It is offered as multi-tenant SaaS (workspaces, sharing, permissions).
- **Type:** Software. Greenfield. Not small: outside users, customer content, and R3 decisions on the consistency model, data model, tenancy and trust boundary.
- **Dominant constraint:** Correctness. Every copy of a document must end up identical, and an edit the server has confirmed must never be lost.
- **Worst failure:** A confirmed edit is silently lost, or copies of a document stay different, and users find out only later. The close second is a user reading or writing a document in another tenant. V2 guards the first and V3 the second.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|

| Latency: remote edit visible to other editors | ≤ 150 ms p95, same region, server-side portion ≤ 50 ms | ASSUMPTION (roughly where users stop seeing it as "live") | V4 |
| Latency: document open | ≤ 2 s p95 for a p95-sized doc | ASSUMPTION (typical SaaS page-load expectation) | V4 |
| Throughput: editors per doc | 50 concurrent editors, 500 viewers | ASSUMPTION (team-document use; tens of thousands is a different architecture) | V4 |
| Throughput: concurrent active docs and connections | UNKNOWN. Product supplies the peak forecast. Needed at the start of Phase 3 | UNKNOWN | V4 |
| Availability / SLO | 99.9% monthly for the sync service (editing continues locally during an outage) | ASSUMPTION (common SaaS tier) | V5 |
| RPO / RTO: confirmed edits | RPO 0. Unconfirmed edits are buffered on the client and resent | ASSUMPTION (a confirmation has to mean "saved") | V2 |
| RPO / RTO: region loss | RPO ≤ 5 min, RTO ≤ 1 h | ASSUMPTION (managed Postgres PITR capability) | V2 restore drill, V5 |
| Storage cost | Stored bytes per doc ≤ 3× its compacted snapshot | ASSUMPTION (Yjs history growth with periodic compaction) | V4 |
| Cost per active editor per month | UNKNOWN. Product/finance supplies it from the price point. Needed before Phase 5 | UNKNOWN | V5 |
| Operational complexity | ≤ 4 runtime components (web/API, sync, Postgres, Redis) plus object storage, with one on-call rotation | ASSUMPTION (team-size basis) | Phase 3 review |

**Missing inputs.** The plan assumes the following. Each one changes the phase order if it is false:
- **No end-to-end encryption required.** If E2EE is required, the server can no longer check or compact content. That rewrites Phase 1 and Phase 2 and removes server-side search.
- **Offline means minutes to hours, not days.** If long offline work is required, local persistence and conflict handling move into Phase 1.
- **No regulated data (HIPAA/PCI).** If there is, a BAA or other compliance agreement becomes an organizational blocker before real content reaches Phase 1.
- **Peak scale forecast:** UNKNOWN, from product, before Phase 3.
- **Data residency:** UNKNOWN, from legal or product, before the Phase 1 data model.
- **Named V5 approvers:** UNKNOWN. An engineering lead and a product owner need to be named.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Consistency model for document content (CRDT vs OT) | R3: every stored doc and the wire protocol take this format | **Yjs CRDT** with the y-prosemirror binding. The server relays and stores edits but does not decide their order | Yjs plus our schema converges under reordered, duplicated and delayed messages and reconnects; edit-history growth fits the budgets | V1, V4 | V1 finds a divergence that can't be fixed in the binding → Automerge or a server-sequenced OT design (re-plan Phase 1). V4 memory or storage over budget → stronger snapshot and garbage-collection strategy first, then a model flip |
| Consistency vs availability | R3: what revocation means is visible to customers | **Content favours availability**: local edits are always accepted and merged on reconnect. **Permissions and metadata favour consistency**: Postgres is the source of truth | Customers accept that a revoked user keeps the copy already synced to their device, but the server rejects anything they send after revocation | V3 | A contract or legal requirement for strict revocation → turn off local caching for restricted docs |
| Document persistence model | R3: the data model of every stored doc | **Append-only Yjs update log plus compacted snapshots in Postgres** (snapshots over 1 MB go to S3). The server confirms an edit only after the commit. IDs are UUIDv7. Each doc carries `tenant_id` and `schema_version` | Commit-before-confirm fits the 50 ms server latency budget; log plus snapshot rebuilds the exact state | V2, V4 | V2 fails → redesign the write path before any real content. Commit latency breaks V4 → batch commits per doc (the confirm still waits for the commit) |
| Tenancy and isolation | R3: isolation leaks can't be undone | **Shared Postgres** with `tenant_id` and row-level security on every table. Tenant is checked when the connection opens | No early customer needs dedicated infrastructure | V3 | An enterprise contract requires dedicated infrastructure → a per-tenant database or cell |
| Trust boundary and where authorization is enforced | R3: a bypass exposes or corrupts customer content | **The sync server checks permissions when the connection opens and on every message.** A viewer's write is dropped and logged. Tokens are short-lived and scoped to one doc | The client is untrusted | V3 | Never weakened. An E2EE requirement means re-planning |
| Data-privacy boundary | R3: leaked content can't be recalled | **Document content never goes into logs, traces, analytics or error reports.** Telemetry holds IDs, sizes and hashes only. Encryption at rest with KMS; TLS in transit | Vendors in the telemetry path never need to see content | V3 (includes a log and trace scan) | An E2EE requirement, or a vendor that can't be kept away from content → replace the vendor |
| Monolith vs services | R2: two deployables to merge or split | **Two deployables:** a web/API modular monolith and a sync service | Long-lived WebSocket connections scale differently from request/response traffic | V4 shows the two scale independently | Running two deployables costs more than it gains at the observed load → merge them |
| How edits reach users on other sync nodes | R2: topology change, no data migration | **Hocuspocus Redis extension (pub/sub)**: any node can serve any doc | Pub/sub delay and holding each doc in memory on several nodes fit V4 | V4 | V4 latency or memory fails → route each doc to one node by hashing its doc ID |
| Build vs buy | R2: the Yjs format moves between hosts, but a managed vendor would hold the data | **Adopt open source and run it ourselves:** Yjs, TipTap/ProseMirror, Hocuspocus. No managed sync vendor | The team can run a WebSocket fleet within the on-call budget | V4 plus the Phase 3 operations review | V4 fails, or on-call load goes over budget → a managed Yjs host (Y-Sweet or Liveblocks), only after a DPA |
| Editor schema changes and client versions | R2: schema changes need a doc migration and coordinated client releases | **Minimal ProseMirror schema v1.** The protocol version and the minimum client version are checked when the connection opens; clients below it are read-only | An old client that doesn't know a new node type would otherwise delete it | Phase 1 check: add a node type while old and new clients are connected; old clients are refused writes and no content is lost | A schema change can't be rolled out without loss → put new node types behind per-doc flags |

**R1 defaults:**
- React for the UI.
- Managed Postgres and Redis (AWS RDS, ElastiCache).
- Containers on ECS or Kubernetes.
- GitHub Actions for CI/CD; Terraform for infrastructure.
- OpenTelemetry into Grafana or Datadog.
- An OIDC IdP (Auth0, Okta or Cognito).
- LaunchDarkly or an in-house tool for feature flags.
- Async job queue for compaction, history and export, kept off the confirm path.

**N/A:** AI rows (no AI component); brownfield rows (greenfield).

## 4. Walking skeleton (Phase 0)
- **Request:** An internal user signs in with SSO and opens a test document. They type a paragraph and press Enter. The edit appears within a moment in a second signed-in browser. After reloading either browser, the text is still there.
- **Tiers:**
  1. Static web client (TipTap, Yjs) served from a CDN.
  2. Load balancer carrying the secure WebSocket.
  3. Sync service (Hocuspocus), which runs one inline permission check against the API.
  4. Web/API service for doc create, list and token issue.
  5. Postgres, holding the update log as a table.
  6. IdP, for OIDC sign-in.
- **Deploy:** A GitHub Actions pipeline builds each container image once and moves it from staging to production. Terraform builds all infrastructure. Database migrations only add things during this phase.
- **Logs:** Structured logs carry the trace ID, doc ID and edit size, never content.
- **Monitoring:** One OpenTelemetry trace runs from the browser through sync to Postgres and back. A dashboard shows WebSocket connections, confirm latency and commit errors. Alerts fire on the sync error rate and on failed health checks.
- **Rollback:** Redeploy the previous image through the pipeline.
- **Runs on unvalidated defaults:** a single sync node, no compaction, nothing hardened.
- **Who can reach it:** Only employees on an SSO allow-list, behind a feature flag. Test documents only, with a written "no real content" rule until V2 passes.
- **Exit check (V0):** One real edit succeeds with a single trace across every tier. A deploy and a rollback both succeed through the pipeline. Killing the sync node fires an alert. The first baselines are recorded: confirm latency, remote-edit latency and doc-open time at near-zero load.

## 5. Phases

- **Phase 1: Data contracts and the correctness core**
  - **Unlocks:**
    - Writing detailed designs for anything that stores or reads docs.
    - Dogfooding with real internal content once V2 passes.
  - **Depends on:**
    - V0.
    - The data-residency answer.
  - **Tasks** (widest rework first):
    1. Tenancy and identity model: tenants, users, memberships, roles; `tenant_id` plus row-level security everywhere.
    2. Document data model (the persistence row in §3): docs, update log, snapshots with state vectors, `schema_version`.
    3. Wire protocol v1, with protocol and minimum-client version checks when the connection opens.
    4. ProseMirror schema v1, plus the schema-change check from §3.
    5. Commit-before-confirm write path. The client keeps unconfirmed edits in IndexedDB and resends them on reconnect.
    6. Convergence fuzz harness in CI (V1).
    7. Fault-injection durability suite, point-in-time backups and a restore drill (V2).
    8. Async compaction. The log is cut back only after checking that the snapshot equals a replay of the log.
  - **Rollback:** Before real content, drop and recreate the schema. **Point of no return:** the first real content stored in format v1. V1 and V2 guard it, and both must pass first.
  - **Exit check:**
    - V1 and V2 pass.
    - The schema-change check passes.
    - Client-reported state hashes show zero divergence over one week of dogfooding.

- **Phase 2: Authorization, sharing and tenant isolation**
  - **Unlocks:** Starting V3. Sharing features.
  - **Depends on:**
    - Phase 1 (identity and tenancy model).
    - The pen-test contract (signed during Phase 1).
  - **Tasks:**
    1. One permission policy used by both API and sync: workspace roles plus doc ACL (owner, editor, commenter, viewer).
    2. Enforcement when the connection opens (doc-scoped token, TTL ≤ 5 min) and on every message (viewer writes dropped and logged).
    3. Revocation pushed to the sync nodes, which disconnect or downgrade the user. Fallback: the permission is re-checked on token refresh.
    4. Share links: scoped, expiring, revocable.
    5. Audit log of access and permission changes.
    6. Rate limits per connection and per tenant; caps on edit and document size.
    7. Isolation test suite and a scanner for content in logs and traces, both in CI.
    8. External pen test.
  - **Rollback:** Policy changes are code changes and get reverted. Share links are behind a flag.
  - **Exit check:** V3's automated part passes. The pen-test sign-off may arrive later but must land before Phase 5.

- **Phase 3: Scaling the sync tier and keeping it up**
  - **Unlocks:** Hardening the topology. Capacity for beta.
  - **Depends on:**
    - Phase 1.
    - The peak forecast (first task of this phase).
  - **Tasks:**
    1. Get the forecast from product.
    2. Run several sync nodes with the Redis extension.
    3. Graceful drain on deploy. Clients reconnect with jittered backoff and resend pending edits.
    4. Load generator that replays realistic edit traces.
    5. Evict idle docs from memory; batch commits per doc.
    6. Set per-node capacity and autoscaling.
    7. SLOs with burn-rate alerts.
    8. Disaster-recovery runbook and drill for region loss.
    9. Operations review against the complexity budget.
  - **Rollback:** A topology flag sends traffic back to a single node, which is acceptable before beta.
  - **Exit check:**
    - V4 passes.
    - The DR drill meets the region-loss RPO/RTO.

- **Phase 4: Collaboration features (internal, behind flags)**
  - **Unlocks:** The feature set for beta.
  - **Depends on:**
    - V1 and V2 (data model).
    - Phase 2 (permissions for each feature).
    - V4 (the budgets each feature must stay within).
  - **Tasks** (widest rework first; the flashiest come last):
    1. Version history on snapshots. A restore is applied as a new edit, so history only moves forward.
    2. Comments stored in Postgres, anchored to Yjs relative positions, with the commenter role enforced.
    3. Per-user undo (Y.UndoManager).
    4. Async export (Markdown, PDF).
    5. Presence, live cursors and selections: Yjs awareness, temporary and never stored. Share-link viewers see no emails.
  - **Rollback:** Each feature has its own flag.
  - **Exit check:**
    - V1 harness extended to comment anchors and restore, and still passes.
    - V4 re-run with all features on, and still passes.
    - A presence outage does not block editing.

- **Phase 5: Staged exposure, from design partners to GA**
  - **Unlocks:** General availability.
  - **Depends on:**
    - V2, V3 (including the pen-test sign-off) and V4.
    - Terms of service, DPA and privacy policy.
    - An on-call rotation.
    - The cost target.
  - **Tasks:**
    1. Tenant-level flag, then widen: 1 design-partner tenant → 5 → open beta.
    2. Canary releases of the web client by session percentage, protected by the minimum-version check.
    3. Status page and support runbooks.
    4. Measure cost per active editor.
    5. V5 go/no-go for GA.
  - **Rollback:**
    - Tenant flag off; tenants can export their data.
    - Client version rollback.
    - No new point of no return here; format v1 was already committed at Phase 1 under V1 and V2.
  - **Exit check:** V5 passes.

## 10. Deliberately deferred
- **Days-long offline work with a UI for resolving conflicts.** Pull forward if a customer needs it. That moves local persistence into Phase 1.
- **End-to-end encryption.** Pull forward if a contract requires it. The phase order would be re-planned first, since it changes the R3 trust boundary.
- **Suggestions or track changes.** Pull forward once beta feedback ranks it in the top 3 asks.
- **Full-text search.** Pull forward when the docs-per-workspace count makes finding documents a top support issue. It also needs its own permission-filtered index.
- **DOCX import and export.** Pull forward on design-partner demand.
- **Multi-region active-active, or per-region data residency.** Pull forward on a residency requirement, or if V5 shows region-loss RTO isn't acceptable.
- **Enterprise SSO/SCIM and dedicated tenancy.** Pull forward on the first enterprise contract that requires it (the tenancy flip in §3).
- **Native mobile apps.** Pull forward when mobile web sessions exceed 20% and complaints follow.
- **Public API and webhooks.** Pull forward when an integration partner commits. It becomes an R3 public contract at that point.
- **AI writing assistance.** Pull forward on a product decision. It adds the AI-layer defenses (injection, cost, human-in-the-loop) before any capability.
