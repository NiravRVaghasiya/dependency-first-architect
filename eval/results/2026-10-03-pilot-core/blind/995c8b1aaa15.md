# BUILD PLAN: Real-time card fraud detection

## 1. Classification
- **What:** A system that scores each card authorization inline before the approve/decline decision. It recommends approve, decline, step-up or review, and logs every decision so models can be trained on it later.
- **Assumptions (confirm these):** The scoring happens on the issuer or processor side, inside the existing ISO 8583 authorization flow. Some past transactions and chargebacks are available. Peak volume is a few thousand transactions per second. If you are a merchant or payment provider, the call moves to pre-authorization at checkout, but the build order stays the same.
- **Type:** Mostly software and infrastructure (streaming, low-latency serving), plus a **predictive ML** part. It is not generative or agentic: no LLM, no tool-using agent.
- **Dominant constraint:** **Latency.** There is a hard p99 limit inside the authorization window. PCI-DSS compliance is a fixed boundary that is never traded away.
- **Worst failure:** The fraud system breaks card authorization itself, through timeouts that stall approvals or a bad rule or model that declines good customers at scale. Missing some fraud costs money; blocking every customer causes an outage and makes the news.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| Consistency vs availability | **The decision path favors availability.** If a feature read times out, use a default value, mark the decision "degraded" and keep scoring. **Per-card hot counters are strongly consistent per key** (single partition per card, atomic increment in the request path). Cross-entity totals (merchant, device, IP) are eventually consistent, a few seconds behind. | Backtests or incidents show card-testing or burst attacks getting through because merchant/device totals are stale. Then move those counters into the synchronous path. |
| Fail-open vs fail-closed (scorer timeout or error) | **Fail open to a minimal rules set compiled into the auth host.** If that also fails, fall back to the issuer's existing stand-in limits. Never block authorization on the fraud system. | Loss analysis shows one segment (for example card-not-present over $X on cards younger than 30 days) loses more while failing open than the cost of declining it. Make only that segment fail closed. |
| Monolith vs services | **One scoring service** that fetches features, runs rules and runs the model in the same process. The **streaming feature pipeline** (Flink) is a separate runtime because it has to be. No separate model-serving service. | Model size or framework mix breaks in-process serving (for example a GNN), or the model team needs to deploy independently. Then split out model serving (Triton/KServe) behind the same contract. |
| Sync vs async | **Synchronous only for the decision:** auth host → scorer → response. **Everything else is async:** feature aggregation, the decision log, labels, case management and retraining. | The p99 limit can't be met with inline scoring even after tuning. Then move to post-authorization monitoring: act by blocking the card's *next* transaction. This prevents less fraud and must be accepted explicitly. |
| Build vs buy | **Buy the infrastructure:** managed Kafka (MSK/Confluent), managed Flink, Redis or Aerospike. **Buy signals:** network scores (Visa Advanced Authorization, Mastercard Decision Intelligence) used as features. **Build** the scoring service, features and models, because those are what set you apart. | Fewer than about 2 data scientists, or no labeled history. Then buy a vendor platform (Featurespace, Feedzai) and plug it in behind the **same scoring API contract**, so the choice can be reversed. |
| Model family | **Rules first, then gradient-boosted trees** (LightGBM) trained on tabular features. | GBDT stops improving and fraud rings or sequence patterns make up a large share of missed losses. Then evaluate graph or sequence models. See Deferred. |
| Training-data source | **Train on features logged at the moment of the decision** ("log-and-wait"). This removes training/serving skew by design. Historical backfill uses the same feature code. | Not expected to flip. Logging served features is the cheapest way to avoid skew. |
| Data-privacy boundary (PCI) | **The full card number never enters the scoring service, feature store, lake or models.** Only an HMAC token (key held in an HSM) plus BIN and last 4 digits get through. This keeps most of the system out of PCI cardholder-data-environment scope. | A qualified security assessor rules that the token setup brings the systems back into scope. Then re-segment the network rather than widening access to card numbers. |
| (AI) prompt+RAG vs fine-tune | **N/A:** no LLM. The model is a supervised classifier trained on labeled transactions. | — |
| (AI) hosted API vs self-host | **N/A as stated.** The model is self-hosted in process, because of the latency limit and because card data can't leave the boundary. A hosted model API is ruled out. | — |

## 3. Walking skeleton (Phase 0)
**The one real request:** A real production authorization request (ISO 8583 `0100`) for 1% of traffic, scored in **shadow mode**. It is scored and logged, but the result is never acted on.

**Tiers it crosses:**
1. **Auth host (existing).** A new scoring client library converts the transaction to a canonical draft and tokenizes the card number. It calls the scorer with a **hard 75 ms timeout**; on timeout it returns "no opinion".
2. **mTLS gRPC call** to the **scoring service** on Kubernetes, in its own network segment.
3. **Redis:** one feature, the card token's transaction count over 24 hours, incremented atomically in the request path.
4. **One rule:** amount above a threshold and count above N → recommend REVIEW.
5. **Response** `{score, recommendation, reason_codes[], ruleset_version, model_version=null, latency_ms, degraded}` goes back to the auth host. The auth host logs it and **ignores it**.
6. **Decision event** goes to Kafka, then a Kafka Connect sink writes it to S3 as Iceberg tables, queryable from Trino or Athena.

**Day-zero deploy, logging and monitoring:**
- CI builds an image pinned by digest. Terraform defines the infrastructure. Deploys go out behind a feature flag (sample rate) that also works as a kill switch.
- Structured JSON logs, with a CI test that fails if anything matching a card-number pattern (Luhn check) appears.
- OpenTelemetry traces across auth host → scorer → Redis.
- Prometheus RED metrics (rate, errors, duration). A dashboard shows p50/p99 latency measured at the *auth-host client*, timeout rate and the recommendation mix.
- Alerts: p99 above 50 ms, timeout rate above 0.5%.

**Exit check:** Real production authorizations are scored in shadow. One trace spans all three tiers, the p99 metric is on the dashboard, and the decision events can be queried in the lake. Auth outcomes are confirmed **unchanged**: same approval rate, same auth latency as before the change.

## 4. Phases (ordered by dependency; within each phase, widest blast radius first)

### Phase 1: Data contracts and event substrate
- **Unlocks:** Features, rules and models can all rely on stable keys and schemas, and any day of traffic can be replayed.
- **Depends on:** Phase 0 running in production. Real traffic shows which fields actually arrive and how reliably.
- **Tasks:**
  1. **Tokenization and privacy boundary:** HSM-backed HMAC tokens and a key-rotation plan. Every key in every store comes from this, so it goes first.
  2. **Canonical transaction event schema** (Protobuf in a schema registry, BACKWARD compatibility), including the mapping from ISO 8583 fields and the split between event time and processing time.
  3. **Decision-log contract:** transaction ID, token, **the full feature vector as served**, ruleset and model versions, score, action, reason codes, latency and degraded flags. This *is* the future training set.
  4. **Label contract:** sources (chargebacks, cardholder fraud claims, customer-confirmed genuine, analyst dispositions), label event time vs report time, and how revisions are handled (for example a chargeback that is later reversed).
  5. **Topic layout:** partition by card token, retention, Iceberg landing tables, dead-letter topics.
  6. **Historical load:** put past transactions and chargebacks into the same Iceberg tables via the canonical schema. This starts the label clock now, because chargebacks take 30 to 120 days to mature.
  7. **Replay harness:** re-run a recorded day through the scorer in staging.
- **Exit check:** Replaying one production day gives identical decision logs on two runs. CI rejects an incompatible schema change. At least 99.9% of decisions join to their source transaction event.

### Phase 2: Streaming feature pipeline
- **Unlocks:** Behavioral signals (velocity, profiles), the basis for both rules and models.
- **Depends on:** Phase 1 contracts and tokens, and the replay harness.
- **Tasks:**
  1. **Entity keys and feature registry (feature definitions as code):** card token, account, merchant ID, hashed device fingerprint, hashed IP /24. Naming and versioning rules.
  2. **Online store layout:** Redis Cluster or Aerospike key design, TTLs, memory sizing at 3× peak. One batched read per score.
  3. **Hot counters in the request path:** atomic increments of count and amount per card over 1 and 10 minutes. These catch card-testing bursts that stream lag would miss.
  4. **Flink windowed aggregates:** 1h/24h/7d/30d per card, merchant and device; distinct merchants per card; merchant fraud rates. Event-time processing with watermarks.
  5. **Batch profile features:** typical amount, home country and usual merchant categories (MCCs) per card.
  6. **Backfill:** the *same* feature code in Flink batch mode over historical Iceberg data, to build training data before enough logs exist.
  7. **Individual feature additions** (the narrowest work).
- **Exit check:**
  - Features recomputed offline match the logged features for more than 99.5% of sampled decisions.
  - Streaming feature freshness p99 is under 2 s.
  - Scorer p99 stays within budget with all features fetched.
  - A game day with Redis killed: the scorer degrades and sets the degraded flag, and authorization is unaffected.

### Phase 3: Rules engine and going live (the first enforcement)
- **Unlocks:** Real fraud prevention, and fast labels from customer confirmations.
- **Depends on:** Phase 2 features proven in shadow, and the Phase 1 replay harness for backtests.
- **Tasks:**
  1. **Action contract** with the auth host and customer communications:
     - Actions are APPROVE / DECLINE / STEP_UP / APPROVE_AND_ALERT / QUEUE.
     - DECLINE maps to an ISO response code (for example 59, suspected fraud).
     - STEP_UP means a 3DS challenge for card-not-present.
     - This touches network messages, customer experience and operations, so it is the widest task.
  2. **Enforcement controls:** global and per-rule kill switches, per-segment enforcement flags, a ramp of 1% → 10% → 100%, and automatic rollback when the decline rate is anomalous.
  3. **Rules engine:** rules as code (CEL expressions evaluated in process), versioned, with two-person (maker-checker) review on every change.
  4. **Backtest harness:** run a candidate ruleset over replayed history and report decline rate, $ fraud caught on labeled history, and false-positive proxies.
  5. **Initial ruleset:** card testing, impossible travel, a new card at high-risk merchant categories, mismatches with the network score.
  6. **Customer confirmation loop:** an SMS or push "Was this you?" that produces labels within days instead of months.
  7. **Analyst case queue:** reuse or buy a case tool if you can (leaf work).
- **Exit check:**
  - Rules enforce on 100% of traffic after the ramp.
  - The change in decline rate stays within the band agreed with risk.
  - The customer-confirmed false-positive rate is reported weekly.
  - Kill-switch drill: enforcement is off in under 1 minute with zero auth errors.

### Phase 4: Labels and training substrate
- **Unlocks:** Honest model training and evaluation.
- **Depends on:** The Phase 1 label contract and historical load, the Phase 3 live policy (decisions made under a known, logged policy), and **calendar time** for labels to mature.
- **Tasks:**
  1. **Label policy:** what counts as fraud, the maturity window (90 days for chargebacks, 7-day fast proxies) and how conflicting sources are resolved. This defines what the model optimizes, so it is the widest task.
  2. **Point-in-time training-set builder:** joins features as logged at decision time to labels known as of a cutoff date. No leakage.
  3. **Selection-bias policy:** declined transactions never get labels. Choose one of:
     - A risk-approved randomized holdout: 0.1–0.5% of would-be rule declines below a $ cap are approved and monitored.
     - A documented reject-inference approach.

     Either needs risk and compliance sign-off.
  4. **Evaluation spec:** value-weighted recall at a fixed decline rate or alert budget, impact on approval rate, results by segment (card-present vs card-not-present, region), and **time-based splits only**.
  5. **Rules baseline:** score the current ruleset against the evaluation spec. This is the bar a model has to beat.
- **Exit check:** Rebuilding a dataset from the same snapshot ID gives identical output. A leakage test finds no features dated after their decision. The rules baseline is published against the evaluation spec.

### Phase 5: ML model (the flashy part, built last on purpose)
- **Unlocks:** Better catch rate at the same decline rate.
- **Depends on:** The Phase 4 datasets and baseline, Phase 2 feature parity, and Phase 3 enforcement controls (ramp, kill switch).
- **Tasks:**
  1. **Score and policy integration contract:** rules can override; per-segment score thresholds; a process for setting thresholds. This is widest because it changes what DECLINE means.
  2. **Model registry with lineage** (MLflow): artifact hash, dataset snapshot ID, feature version, code SHA, seed, library versions.
  3. **In-process serving:** LightGBM compiled with Treelite or ONNX Runtime. At load time, check that the model's expected feature schema matches the served features. Refuse to load on a mismatch.
  4. **Train the GBDT** on logged and backfilled features. Evaluate against the rules baseline on time-split data.
  5. **Shadow (2–4 weeks) → canary → ramp,** compared on fast-matured labels.
  6. **Reason codes:** TreeSHAP top contributing features mapped to analyst-facing codes. The field already exists in the Phase 1 decision log.
- **Exit check:**
  - The model beats the rules baseline at an equal decline rate, both on a held-out time period and in live shadow.
  - p99 stays within budget with the model on.
  - Rollback by pinning the previous model in the registry is drilled at under 5 minutes.

### Phase 6: Feedback, drift and the retraining loop
- **Unlocks:** Keeping up with attacks without hand-built models.
- **Depends on:** The Phase 5 model in production, plus the Phase 4 pipelines reused as they are.
- **Tasks:**
  1. **Live performance and drift monitoring:** PSI per feature, score distribution, decline-rate alerts per segment, and performance measured on matured labels.
  2. **Retraining pipeline** (Argo/Airflow) reusing the Phase 4/5 code. Promotion requires beating the champion on the evaluation spec *and* human sign-off (model risk management; SR 11-7 applies if you are a US bank).
  3. **Label feedback:** analyst dispositions and customer confirmations, weighted by source, with anomaly checks on labels from each source (defense against insider label poisoning).
  4. **Emergency rule hotfix path:** minutes, versus days for a retrain. This is the first response to a new attack.
  5. **Threshold recalibration cadence.**
- **Exit check:**
  - A scheduled retrain → shadow → promote cycle completes with only the sign-off done by hand.
  - Drift injected in a game day triggers an alert.
  - The emergency rule deploy is drilled at under 15 minutes.

## 6. AI layer
**N/A as defined.** This system uses predictive ML (a supervised classifier), with no LLM and no agent. Nothing reads untrusted text as instructions, there are no token costs, and no tool calls run on their own. Where the same concerns apply, they are already built into the phases above:

| Concern from the AI layer | Where it lives here |
|---|---|
| Guardrails (adversarial input) | Phase 5: input clamping, limited reason-code exposure. Phase 6: label-poisoning checks |
| Latency budget | Phase 0 onward: a 50 ms p99 scoring limit and a 75 ms client timeout |
| Human-in-the-loop | Two-person review on rules (Phase 3); human-gated model promotion (Phase 6); the analyst queue |
| Retrieval / memory | Feature store and per-card profiles (Phase 2) |
| Model access | In-process serving with the registry and load-time schema check (Phase 5) |
| Feedback | Labels and retraining loop (Phases 4 and 6) |

If an LLM is ever added (see Deferred), the full AI layer applies. Merchant descriptors and customer messages would then be untrusted text.

## 7. Deliberately deferred
- **Graph or GNN features for fraud rings** (shared devices, mule accounts). Pull forward when ring-linked fraud is a material share of losses the GBDT misses.
- **Sequence models over transaction history** (transformers). Pull forward when the GBDT has stopped improving *and* there is p99 headroom of at least 20 ms.
- **A separate model-serving tier** (Triton/KServe). Pull forward when in-process serving breaks on model size or framework, or deploy schedules collide.
- **A commercial feature store** (Tecton/Feast). Pull forward when there are more than ~200 features, or several models or teams share features.
- **Multi-region active-active scoring.** Pull forward when the auth host itself goes multi-region; until then, multi-AZ plus fail-open.
- **Online learning.** Pull forward when attack patterns change faster than the retrain cycle and emergency rules can't keep up.
- **The randomized holdout,** if risk declines it in Phase 4. Pull forward when model performance on rule-filtered data visibly decays.
- **LLM-assisted analyst tools** (case summaries). Pull forward when analyst throughput is the bottleneck; this brings in the full AI layer.
- **Adjacent scope** (account takeover on digital channels, AML, acquirer-side fraud, consortium data sharing). Pull forward when it is chartered as a separate program, reusing the Phase 1–2 substrate.
