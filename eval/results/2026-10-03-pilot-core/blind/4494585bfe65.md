# Plan: Real-time card-transaction fraud detection

**Assumptions I made because the prompt didn't say:**
- We are an issuer or processor, scoring authorization requests inline before approving them.
- The authorization switch already exists.
- The fraud decision gets **p99 ≤ 50 ms** end-to-end, inside the switch's own timeout. Confirm this with the switch team.
- There is ≥12 months of historical authorization and chargeback data.

If you are a merchant or payment provider instead, the connection point changes but the order of work stays the same.

---

## 1. Classification
- **What:** An inline service that decides approve, decline, step-up (3DS/OTP) or send to review for each card authorization. Around it sit a streaming feature pipeline, a decision log, a label feedback loop and a case queue for fraud analysts.
- **Type:** Mostly software and infrastructure (streaming, low-latency serving), plus a **predictive ML** model. It does not use an LLM and is not agentic.
- **Dominant constraint:** **Latency and availability** in the authorization path, with **correctness** of decisions close behind (fraud losses vs. falsely declined customers). PCI DSS compliance limits everything.
- **Worst failure:** The fraud system becomes a dependency that can take authorizations down. If it is slow or down, legitimate cards get declined or timed out at scale. The close second is a silent failure where the model "approves everything" and nobody notices for days.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| Consistency vs availability | **Availability for the decision path.** Score with features that may be milliseconds stale, and never block an authorization waiting for counters to agree. **Strong consistency for the decision log and labels** (durable, append-only, idempotent). | Measured fraud loss caused by stale counters (e.g., burst attacks inside the lag window) exceeds an agreed basis-point threshold. Then make the velocity counters for those keys strongly consistent. |
| Sync vs async | **Hybrid.** Synchronous gRPC call from switch to decision service, because an answer is needed. Everything else is async through Kafka: feature updates, logging, case creation, labels, retraining. | p99 can't meet the budget after optimisation. Then move to post-authorization detection plus automatic card blocking, accepting first-transaction losses. |
| Monolith vs services | **One decision service** (rules plus model in-process), **one stream-processing job group**, **one case-management app**. No service per rule or per model. | More than two teams need independent deploys, or the parts need to scale more than 10× differently. |
| Build vs buy | **Buy the substrate:** managed Kafka (MSK/Confluent), managed Flink, Redis Enterprise or Aerospike, Vault/KMS. **Build the decision logic, features and model**, because they are the differentiator. Use the card networks' risk scores (Visa Advanced Authorization / Mastercard Decision Intelligence) as **input features** from day one. | Fewer than about 3 fraud/ML staff, or less than 6 months of labelled history. Then buy a vendor engine (Featurespace, Feedzai) and keep only the skeleton and decision log. |
| Rules vs ML (stands in for the "prompt+RAG vs fine-tune" gate) | **Rules first** (Phases 0–3), with ML layered on once labels have matured. Rules stay as guardrails above the model. | Rules hit a precision ceiling. That means they can't catch more fraud without falsely declining more good customers, or rule count passes about 200 and maintenance becomes the bottleneck. |
| Model serving (stands in for "hosted API vs self-host") | **Self-hosted, in-process** gradient-boosted trees (LightGBM exported to ONNX/Treelite) in the decision service. No network hop, and nothing leaves the PCI scope. | Deep sequence or graph models that need GPUs. Then move to a separate model server (Triton) with its own latency budget. |
| Data-privacy / PCI boundary | **The full card number (PAN) never enters the pipeline.** It is tokenized at ingress (keyed HMAC, keys in an HSM/KMS). Every key, feature and log uses the token. | Network tokens become the main identifier. Then re-key, which is why the token is an abstract `card_key`. |
| Region topology | **Single region, multiple availability zones,** for Phases 0–4. | The availability SLA or a regulator requires surviving a region loss. Then go active-active with velocity counters kept local to each region (see Deferred). |
| LLM-specific gates | **N/A.** No generative model is in the decision path. | Revisit if an LLM is added for analyst assistance (see Deferred). |

## 3. First end-to-end slice (Phase 0)

**The one real request:** a live production authorization, in **shadow-inline mode**. The switch really calls the decision service and gets a real answer back. For now it logs that answer and does not act on it, so customers carry no risk.

**Tiers it crosses:**
1. **Authorization switch:** a new gRPC client call with a hard **50 ms timeout**. If it times out, the authorization proceeds as it does today.
2. **Ingress adapter** inside the PCI zone: tokenizes the PAN into a `card_key`.
3. **Decision service** (Kotlin/Go on Kubernetes): reads **one feature**, the card's authorization count in the last hour, from **Redis**. It applies **one rule** (e.g., count > 10 → REVIEW) and returns `{decision, score, reason_code, ruleset_version, latency_ms}`.
4. The decision service publishes request and decision to **Kafka** (`auth.events`, `auth.decisions`), with schemas in a schema registry.
5. A **Flink job** consumes `auth.events` and updates that one counter in Redis.
6. A **Kafka Connect sink** writes decisions to an **Iceberg decision log** on S3.
7. A REVIEW decision drops a row into a **minimal case queue**, even a Postgres table with a bare list view.

**Deployed:** Terraform for all infrastructure, plus a CI/CD pipeline (build → test → container image signed and pinned by digest → Argo CD). A feature flag controls `shadow | enforce` per BIN range.

**Logged and monitored:**
- OpenTelemetry trace across switch → decision service → Redis → Kafka.
- Dashboard: p50/p99 latency, timeout rate, decision mix, Kafka consumer lag, counter freshness.
- Alerts: timeout rate > 0.1%, p99 > 40 ms, Flink job down.

**Exit check:** A real production authorization produces a decision in under 50 ms at p99. It shows up as one trace, a dashboard metric, a row in the Iceberg log and, if it was REVIEW, a case. It runs over 24 hours of full traffic without breaking the timeout SLO.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

### Phase 1: Data contracts and the event backbone
- **Unlocks:** Everything downstream (features, labels, training, audit) can rely on stable, replayable data.
- **Depends on:** The Phase 0 skeleton moving real events end-to-end.
- **Tasks:**
  1. **Authorization event contract** (Protobuf, compatibility enforced in CI). Contents:
     - keys: `card_key`, `account_key`, `merchant_id`, `device/terminal_id`
     - event-time timestamp
     - merchant category code (MCC), whether the card was present, entry mode, amount and currency
     - **idempotency key** (auth ID plus retry semantics)
     - links between an authorization and its reversals, advices and clearing records

     This is the widest impact: every feature, label join and model depends on it.
  2. **Decision contract:** decision, score, reason codes, ruleset/model version, feature snapshot hash, latency. Every decision becomes auditable and replayable.
  3. **Label contract and ingestion, started now:** chargebacks with fraud reason codes, cardholder fraud claims, analyst outcomes, joined on auth ID. Chargebacks mature 30–120 days later, so **the clock on ML starts the day labels start flowing.** That is why this sits in Phase 1, not Phase 4.
  4. **Historical backfill** of 12+ months of authorizations and chargebacks into the same schemas and the Iceberg log.
  5. Dead-letter queue (DLQ) and a reprocessing tool for malformed events.
- **Exit check:**
  - A breaking schema change fails CI.
  - 30 days of history replayed through the pipeline gives byte-identical decision-log rows across two runs.
  - Labels join to authorizations at ≥98%.

### Phase 2: Feature layer (streaming and offline, one set of definitions)
- **Unlocks:** Rules and models with real signal. Training data that matches what serving sees.
- **Depends on:** Stable event contract and replayable log (Phase 1).
- **Tasks:**
  1. **Entity keys and time-window semantics:** event time, bounded lateness watermark (e.g., 5 s), exactly-once Flink with checkpoints. Getting this wrong silently corrupts every feature.
  2. **Features defined once as code,** compiled to both the Flink streaming job and an offline batch job that rebuilds each feature as of the exact transaction time, so training never sees the future.
  3. Core features:
     - velocity counts and amount sums per card, merchant and device (1 min / 1 h / 24 h / 30 d)
     - distance and speed from the previous transaction's location
     - first time this card has used this merchant or MCC
     - card-not-present ratio
     - share of failed authorizations (catches card testing)
     - card-network risk score
  4. Defaults for missing features, with an explicit `feature_missing` flag passed to the decision.
- **Exit check:**
  - Online and offline feature values disagree on < 0.1% of a replayed day.
  - Feature read p99 < 5 ms.
  - Feature freshness p99 < 2 s.

### Phase 3: Rules-based decisioning, enforced on a narrow slice
- **Unlocks:** Real fraud prevention, and the first measured false-positive and fraud-catch rates.
- **Depends on:** Trusted features (Phase 2) and an auditable decision log (Phase 1).
- **Tasks:**
  1. **Decision policy and fallback matrix**, the widest item here.
     - Outcomes: approve, decline, step-up or review.
     - Behaviour by risk tier when the system degrades: fail open for low-value and card-present transactions, step-up or decline for high-value card-not-present in high-risk merchant categories.
     - Sign this off with the risk and ops owners before writing rules.
  2. **Rules engine as versioned code:**
     - rules expressed declaratively and evaluated in-process
     - two-person review for every change
     - a per-rule kill switch
  3. **Replay harness:** evaluate any rule change against 90 days of history (catch rate, false positives, decline rate) before it ships.
  4. Move shadow → enforce for one BIN range, using a few high-precision rules (card-testing bursts, impossible travel). Then widen.
  5. Case queue v1: reason codes shown to analysts, and SLA timers.
- **Exit check:**
  - Enforced on ≥25% of traffic.
  - Added authorization latency p99 ≤ 50 ms.
  - Measured false positives per true fraud is at or under the agreed ratio.
  - No unexplained jump in decline rate over 2 weeks.

### Phase 4: ML model (shadow → challenger → champion)
- **Unlocks:** A better trade-off between fraud caught and good customers declined than rules can reach.
- **Depends on:** Matured labels (Phase 1 clock), matching features (Phase 2), decision policy and replay harness (Phase 3).
- **Tasks:**
  1. **Training-set construction** (widest item).
     - Features rebuilt as of each transaction time.
     - A label-maturity cutoff, e.g., exclude the last 60 days.
     - **Selection-bias handling:** declined transactions never get an outcome. Use step-up outcomes, analyst labels and a small, risk-capped randomized control group, approved by Risk.
  2. Train LightGBM. Track experiments in MLflow, keyed by Iceberg snapshot ID, code SHA and seed. Evaluate on a time-based split using:
     - precision at fixed recall
     - the dollar cost curve (fraud loss vs. false-decline cost)
  3. Export to ONNX/Treelite and load in-process. Model inference p99 ≤ 5 ms. Rules stay as hard overrides above the model.
  4. Shadow scoring for 4 weeks, then a champion/challenger traffic split. Set thresholds per segment from the cost curve.
- **Exit check:**
  - On 4 weeks of matured labels, the challenger beats rules-only at equal or lower false-decline rate.
  - Latency budget holds.
  - Rollback to rules-only takes < 1 minute through config.

### Phase 5: Feedback loop and fraud operations
- **Unlocks:** A system that keeps up with fraudsters' changing tactics instead of decaying.
- **Depends on:** Champion model in production (Phase 4).
- **Tasks:**
  1. **Label feedback pipeline:**
     - analyst dispositions and cardholder confirmations go into the label store, with provenance
     - label edits are audited
  2. **Drift monitoring:**
     - population stability index (PSI) per feature and on the score
     - fraud rate by segment
     - alerts on drift or sudden spikes
  3. **Retraining pipeline:** monthly at first, gated by a human-approved eval report. No auto-promotion.
  4. Case-management tooling for analysts: bulk actions, link analysis on shared device or merchant.
  5. Threshold-tuning playbook tied to the business cost of fraud vs. false declines.
- **Exit check:**
  - A retrain runs reproducibly from pinned inputs.
  - A synthetic drift injected in staging fires the drift alert.
  - Analyst labels show up in the next training set.

### Phase 6: Scale and peak readiness
- **Unlocks:** Surviving peak days (Black Friday at 3–5× normal transactions per second) and component loss.
- **Depends on:** The complete pipeline (Phases 0–5).
- **Tasks:**
  1. Capacity model and load test at 5× peak through the real path.
  2. Chaos drills: kill a Redis shard, a Kafka broker, a Flink task manager, and run with an availability zone down.
  3. Tune autoscaling and pre-warm before known peaks.
  4. Disaster-recovery runbook, including rebuilding Redis state from the Kafka log.
- **Exit check:**
  - 5× peak holds p99 ≤ 50 ms.
  - Every chaos drill ends in the expected fallback, with no authorization outage.
  - Recovery time from a full Redis loss ≤ 15 min.

## 6. AI layer (adapted: predictive ML, not LLM/agentic)
There is no LLM here, so prompt-injection, retrieval and agent orchestration don't apply literally. The ordering rule still does: **defenses and budgets come before the model**. Here is how each sublayer maps to this system:

1. **Guardrail defense → adversarial and poisoned input:**
   - detect card-testing probes
   - rules act as hard overrides above the model
   - label-provenance audit

   *Exit:* a replayed card-testing burst is blocked by rules even when the model scores it low.
2. **Cost and latency budget:** 50 ms end-to-end, with ≤ 5 ms for the feature read and ≤ 5 ms for the model, each enforced by timeout. *Exit:* an injected Redis delay triggers degraded mode, never a timeout at the switch.
3. **Human in the loop:** REVIEW decisions go to analysts. Model promotions and threshold changes need human sign-off. *Exit:* a promotion can't deploy without a signed eval report.
4. **Retrieval → feature store** (Phase 2). *Exit:* online and offline agree to < 0.1%.
5. **Model access → in-process ONNX scorer** behind an interface (Phase 4). *Exit:* the model is swapped through config without code changes.
6. **Memory → per-card, per-merchant and per-device state** in Redis, rebuildable from Kafka. *Exit:* state is rebuilt within the recovery-time target.
7. **Orchestration → rules then model then policy,** evaluated in order inside the decision service. *Exit:* every decision's trace shows each step.
8. **Routing → champion/challenger and per-segment thresholds.** *Exit:* the traffic split is logged and the challenger's metrics are visible.
9. **Feedback → labels, drift checks and retraining** (Phase 5). *Exit:* analyst labels measurably change the next model's evaluation.

## 7. Deferred
- **Multi-region active-active.** Pull forward if the SLA or a regulator requires surviving a region failure, or if single-region availability falls below target.
- **Deep sequence or graph models (GNN for fraud rings) and GPU serving.** Pull forward if gains from the tree model level off and link analysis shows organised rings sharing devices or merchants.
- **Commercial feature store (Tecton/Feast).** Pull forward if more than about 3 teams write features or online/offline drift keeps recurring.
- **Automatic model promotion and online learning.** Pull forward if drift moves faster than monthly retraining and 6+ human-gated releases have passed cleanly.
- **Real-time cardholder confirmation ("Was this you?" push).** Pull forward once step-up infrastructure is stable and false declines dominate customer complaints.
- **LLM-assisted case summaries for analysts.** Pull forward if analyst throughput becomes the bottleneck. This would trigger the full LLM AI layer: merchant names and notes are untrusted text, so injection defense comes first.
- **Consortium or third-party fraud data.** Pull forward when card-network scores plus our own features reach their limit.
- **Other payment rails (ACH, instant payments).** Pull forward on a product decision. The event contract is designed to be rail-agnostic.
