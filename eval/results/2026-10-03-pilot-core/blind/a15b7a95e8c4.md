# Plan: CI/CD platform for 50 microservices

## 1. Classification
- **What:** A shared build, test, sign, promote and deploy platform that 50 microservices run on. It replaces 50 separate pipelines.
- **Type:** Infra. There are no AI components.
- **Dominant constraint:** Correctness and integrity of what reaches prod. Scale (50 services × 3 environments, with many commits a day) comes second.
- **Worst failure:** The platform pushes an unverified or compromised artifact to prod across many services at once. A shared platform multiplies impact, so one bad template or one leaked credential can affect all 50 services. Close behind: the platform is down and nobody can ship a hotfix.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| Consistency vs availability | **Consistency for deploy state.** Git is the single source of truth for what runs where (GitOps). If the CD controller finds diverged or uncertain state, it stops rather than guessing. Builds favor availability: they retry and can run on any runner. | Git-host outages block hotfixes more than once a quarter. Then add an audited break-glass deploy path. Git still stays canonical. |
| Monolith vs services (the platform itself) | **One shared platform:** one versioned library of reusable workflows and one CD controller. Not 50 bespoke pipelines. | More than about 20% of services need escape hatches the templates can't express. Then split templates by archetype (stateless, stateful, batch) instead of adding flags. |
| Repo topology (for the 50 services) | **Keep the current polyrepo layout.** Services pull in the shared template library by pinned version. | Cross-repo atomic changes become frequent (more than about 1 per week blocked on coordination). Then evaluate a monorepo with Bazel or Nx. |
| Sync vs async | **CI is synchronous and gates PR merge. CD is asynchronous and pull-based:** Argo CD reconciles from the config repo, so CI never holds prod credentials. | Some deploy targets can't run a pull agent (Lambda, legacy VMs). Those get push deploys using short-lived OIDC credentials, scoped per target. |
| Artifact model | **Build once and promote the same immutable image digest** through dev, staging and prod. Environment differences live only in config overlays. | Effectively never. If a service needs a rebuild per environment, fix the service. |
| Build vs buy | **Buy or adopt:** GitHub Actions (CI), Argo CD (CD), a managed registry (ECR or GHCR), Sigstore/cosign (signing), Kyverno (admission policy), Trivy (scanning). **Build only the glue:** templates, the promotion policy, the `service.yaml` contract and onboarding automation. | Hosted CI minutes cost more than the total cost of running our own runners, or compliance requires air-gapped builds. Then move to self-hosted ephemeral runners (Actions Runner Controller). |
| Deploy target | **Kubernetes, with one cluster per environment.** This is stated as an assumption, not left silent. | An inventory shows more than about 10% of services on a different target. Then add a target-abstraction step to the CD layer before fleet onboarding (Phase 4). |
| (AI) prompt+RAG vs fine-tune | N/A: there is no AI component. | — |
| (AI) hosted API vs self-host | N/A: there is no AI component. | — |

## 3. First end-to-end slice (Phase 0)
For CI/CD, the "request" is a commit and the "response" is that commit running in prod and serving real traffic.

- **The real request:** Merge a one-line change to one real, low-risk, stateless service, picked as service #1.
- **Tiers it crosses:**
  1. GitHub (branch protection on `main`)
  2. CI runner
  3. Container build (base image pinned by digest)
  4. Unit tests
  5. Push to registry by digest
  6. Keyless cosign signature
  7. Bot PR bumping the digest in the `deploy-config` repo
  8. Argo CD syncs to **staging**
  9. Smoke test
  10. Promotion PR (human approves)
  11. Argo CD syncs to **prod**
  12. Kubernetes readiness check
  13. The service returns the new version on `/version`
- **Deployment:** The platform's own pieces (registry, Argo CD, IAM roles, OIDC trust) are created with Terraform from a `platform-infra` repo. No click-ops, even on day zero.
- **Logging and monitoring on day zero:**
  - Every pipeline stage emits an OpenTelemetry span, with commit SHA and digest as attributes.
  - Argo CD metrics go to Prometheus.
  - Deploy events appear as annotations on the service's Grafana dashboard.
  - An alert fires on a failed Argo sync or a failed pipeline on `main`.
  - Lead time (commit to prod) is recorded as the first DORA metric.
- **Exit check:**
  - The merged change is serving in prod.
  - One trace shows every stage from commit to prod.
  - The lead-time metric is visible on a dashboard.
  - A `git revert` in `deploy-config` rolls prod back, and that rollback has been demonstrated, not just assumed.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

**Phase 0: First end-to-end slice.** See Section 3.

**Phase 1: Trust and contract substrate**
- **Unlocks:** Any service can be described to the platform, and every artifact can be traced to its origin.
- **Depends on:** The Phase 0 path running end to end in prod.
- **Tasks** (widest impact first):
  1. **Identity and authorization model.** OIDC federation from CI to the cloud, with no static keys anywhere.
     - Role split: CI can only push to the registry. Argo can only deploy. Humans have no direct write access to prod.
     - If this is wrong, every later phase gets rewired, so it goes first.
  2. **Artifact contract.**
     - Images are referenced by digest. Tags are informational only.
     - Every image gets an SBOM (Syft) and SLSA provenance.
     - Every image is cosign-signed.
  3. **Service contract (`service.yaml`).** Each service declares owner, tier (1–3), archetype, build entrypoint, test entrypoint, health endpoint and whether it is stateful. The file is validated against a JSON Schema.
  4. **Layout of the `deploy-config` repo.** Structure is `apps/<service>/{base,overlays/{dev,staging,prod}}` using Kustomize.
  5. **Ephemeral runners.** A fresh runner per job. Self-hosted runners only where tests need private network access.
- **Exit check:**
  - Service #1 is rebuilt using only OIDC, and every static CI secret has been deleted.
  - Kyverno verifies signatures in **audit** mode and reports 100% of prod images signed.
  - `service.yaml` validation fails a PR when a required field is missing.

**Phase 2: Golden-path templates and a pilot group of 5 services**
- **Unlocks:** Services with different shapes can onboard without writing platform code.
- **Depends on:** The Phase 1 contracts, proven on service #1.
- **Tasks** (widest impact first):
  1. **Versioning and rollout for the templates themselves.**
     - The reusable workflow library is semver'd, and consumers pin to a version.
     - Renovate opens the version-bump PRs.
     - New template versions go to 1 service, then the pilot group, then everyone.
     - A template change reaches all 50 services, so this mechanism comes first.
  2. **Database migration pattern for stateful services.**
     - Migrations run as a separate job that must finish before rollout.
     - Expand/contract only, so the previous version still runs against the new schema.
     - A wrong pattern here means data loss, so it comes before the language-specific work.
  3. **Build archetypes.** Pick 5 pilot services that cover at least 3 languages, plus one stateful service and one batch job.
  4. **Build caching.** Layer cache plus a dependency proxy or mirror.
  5. **PR checks.** Lint, unit tests, Trivy scan, secret scan.
- **Exit check:**
  - All 5 pilot services deploy to prod through the templates with zero per-service pipeline code.
  - One template release has gone 1 → 5 services and been rolled back, with rollback proven.
  - One stateful migration has shipped with the old version still serving.

**Phase 3: Promotion, policy and safe rollback**
- **Unlocks:** Prod deploys are safe enough to let the fleet onboard.
- **Depends on:** Templates proven on varied services, and signing and provenance proven in audit mode.
- **Tasks** (widest impact first):
  1. **Promotion policy as code.** Only a digest that is signed, has provenance, passed tests and passed staging can be promoted. The policy is evaluated in the promotion PR check.
  2. **Switch Kyverno to enforce in prod.** Unsigned images or images without provenance are rejected at admission.
  3. **Automated rollback.**
     - Argo health checks plus error-rate and latency checks after deploy.
     - On failure, a bot reverts the change in `deploy-config`.
  4. **Approval rules by tier.** Tier 1 needs two-person approval. Tiers 2–3 auto-promote after staging soak.
  5. **Deploy freeze switch and audited break-glass path.**
- **Exit check:**
  - A deliberately broken release is reverted automatically within 5 minutes.
  - An unsigned image is rejected in prod.
  - A break-glass deploy works and raises an alert.

**Phase 4: Fleet onboarding (5 → 50)**
- **Unlocks:** The whole organization is on one paved path, and the legacy pipelines are retired.
- **Depends on:** The promotion and rollback safety net from Phase 3.
- **Tasks** (platform work widest first):
  1. **Onboarding automation.** A scaffolder opens a PR containing `service.yaml`, the workflow call and the Argo app. It also generates the service catalog from `service.yaml`.
  2. **Capacity for 50 services × 3 environments (about 150 Argo apps).**
     - Runner autoscaling with a minimum warm pool.
     - Concurrency limits per repo.
     - Handling for GitHub API rate limits.
     - Argo CD in HA mode, with controller sharding if needed.
  3. **Onboarding waves.** Tier 3 first, then tier 2, then tier 1. This is a deliberate exception to "widest first": the waves validate the platform, so the lowest-risk services go through it first.
  4. **Legacy cleanup.** Delete each old pipeline and revoke its credentials as each service cuts over.
- **Exit check:**
  - 50 of 50 services are on the platform.
  - Zero legacy pipelines or credentials remain.
  - p95 commit-to-staging time is under 15 minutes.
  - The platform has been restored from Terraform and Git in a disaster-recovery drill.

**Phase 5: Progressive delivery and optimization**
- **Unlocks:** Safer tier-1 releases, faster CI and cost control.
- **Depends on:** Trustworthy per-service metrics and SLOs, which only exist once the fleet emits them uniformly (Phase 4).
- **Tasks** (widest impact first):
  1. Argo Rollouts canaries for tier-1 services, with automated analysis against SLO metrics.
  2. Flaky-test detection and quarantine.
  3. Test-impact analysis. It falls back to the full test suite if it is uncertain.
  4. DORA dashboard and cost-per-pipeline reporting.
- **Exit check:**
  - Tier-1 services ship through canaries that abort automatically.
  - Change-failure rate and MTTR are reported weekly.

## 5. Cross-cutting concerns (per phase, from the first commit)

N/A. This is a pure infra system with no model, retrieval or agent components. If the platform later adds AI features (for example LLM-generated PR summaries or failure triage), run this skill's AI layer for that feature, starting with guardrails and budgets.

## 7. Deferred
- **Ephemeral preview environments per PR.** Pull forward when review or QA cycle time becomes the top bottleneck and the cluster cost per preview is approved.
- **Monorepo migration (Bazel or Nx).** Pull forward when the repo-topology gate's revisit trigger fires.
- **Multi-region or multi-cluster CD (ApplicationSets across clusters).** Pull forward when prod goes multi-region.
- **Self-hosting all runners.** Pull forward when the build-vs-buy gate's revisit trigger fires (cost or air-gap requirements).
- **Canaries for tier-2 and tier-3 services.** Pull forward per service once it has a defined SLO and a clean metrics history.
- **A full developer portal (Backstage).** For now, a catalog generated from `service.yaml` is enough. Pull forward when teams report discoverability or ownership problems that the generated catalog can't solve.
- **Bit-for-bit hermetic builds (Bazel or Nix).** Pull forward when compliance requires SLSA Level 4 or reproducibility audits.
- **A custom pipeline DSL or orchestrator.** Not planned. Pull forward only if GitHub Actions reusable workflows provably can't express a pattern that more than 10 services need.
