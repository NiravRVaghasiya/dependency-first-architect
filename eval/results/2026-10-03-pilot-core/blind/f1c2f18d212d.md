# Plan: Real-time collaborative document editor

## 1. Classification
- **What:** A browser-based rich-text editor where several users edit the same document at the same time, see each other's changes in under a second, and never lose an edit.
- **Type:** Software. There's some infra work for the stateful WebSocket tier. No AI.
- **Dominant constraint:** Correctness. Every copy of a document must end up identical, and any edit the server has confirmed must survive. Latency comes second.
- **Worst failure:** Silent loss or silent divergence. A user sees "Saved", but the edit is gone after a reload, or two users end up permanently looking at different documents. Users stop trusting the product after that, and the damage can't be undone after the fact.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| **Concurrency model: CRDT vs OT** (the costliest to reverse, because the stored document format follows it) | **CRDT (Yjs).** Edits apply locally first, all copies are guaranteed to converge, and short offline periods are tolerated. No central sequencer needed for correctness. | Switch to OT with a server-side sequencer if the product needs server-validated edits that a CRDT can't express (hard locking, schema-enforced invariants, edit approval workflows). Decide before Phase 1 ends. After that it means migrating every stored document. |
| Consistency vs availability | **Available with eventual convergence for editing; strong durability for confirmations.** Clients keep editing during short partitions and converge afterwards. The server confirms an update only after it is durably committed to Postgres. "Saved" means committed. | If users need to see a single global order (legal redlining, audit-exact ordering), add a server-assigned sequence number to the log. That's an extension, not a rewrite. |
| Monolith vs services | **One codebase, two process roles:** a stateless HTTP API (docs, sharing, auth callbacks) and a stateful sync server (WebSockets). They share one repo, one build and one database. | Split further only when one area needs its own scaling or release cadence. Example: export or search load starts hurting sync latency. |
| Sync vs async | **Hybrid, chosen per path.** Committing an update to the log is synchronous, before the confirmation goes out. Broadcasting to other clients, compaction, export and notifications are asynchronous. | Make commits async (batched group-commit) only if Postgres commit latency pushes confirmation p99 above 300 ms at target load. Even then, "Saved" waits for the batch to commit. |
| Build vs buy | **Adopt:** Yjs, y-protocols, ProseMirror/Tiptap, Hocuspocus as the sync-server base. **Buy:** identity provider (OIDC, e.g. Auth0/WorkOS/Keycloak), managed Postgres, object storage. **Build:** the per-update commit-and-confirm extension, authorization, compaction and history. | Build a custom sync server if Hocuspocus's hooks can't enforce confirm-after-commit, or if its memory per document exceeds budget (more than ~50 MB for a 1 MB document). |
| Server can read content vs end-to-end encryption | **The server reads plaintext,** encrypted at rest and in transit. Search, export, history rendering and server-side validation all depend on this. | A regulated or zero-access customer requirement. That turns the server into a blind relay and removes server-side search and export. It's architectural, so decide it before Phase 5. |
| History retention | **Keep the raw update log forever** and compact it into snapshots *alongside* the log, never by deleting it. Yjs garbage collection removes deleted content, so the log is the only source for full history. | Storage cost passes budget (e.g. more than $X per workspace per month). Then age out updates older than N days into coarser periodic snapshots and accept coarser history. |
| Document-to-node placement | **Every client of a given document connects to the same sync node,** via consistent-hash routing on the document ID. One node is enough until Phase 3. | Very hot documents (more than ~500 concurrent editors) need cross-node fan-out over Redis/NATS pub/sub. |
| Authorization granularity | **Permissions per document** (owner / editor / commenter / viewer), plus workspace membership. | An enterprise requirement for permissions on individual sections. With one CRDT per document that means splitting documents into Yjs subdocuments. It's expensive, so flag it during sales and don't retrofit it quietly. |
| (AI) prompt+RAG vs fine-tune | N/A: no AI features in scope. Adding any brings in the AI layer (see §7). | — |
| (AI) hosted API vs self-host | N/A: no model in scope. | — |

## 3. First end-to-end slice (Phase 0)
**The one real request:** User A opens `/d/<id>` and types "hello". User B, in another browser, sees "hello" in under 500 ms. We restart the sync server, both users reload, and "hello" is still there because it was read back from Postgres.

**Tiers crossed:**
1. **Browser:** Tiptap/ProseMirror with Yjs and a minimal schema (doc → paragraph → text), using the *real* CRDT library rather than a stub.
2. **Static hosting/CDN** serves the client bundle.
3. **OIDC login:** one test user per browser, with real JWT issuance from the bought identity provider.
4. **Load balancer** terminates TLS and upgrades the connection to a WebSocket.
5. **Sync server** (Hocuspocus base):
   - checks the JWT and a hardcoded document permission;
   - applies the update;
   - **appends it to `update_log` in Postgres;**
   - **sends a confirmation only after the commit;**
   - broadcasts it to the other connected client.
6. **Postgres** has an `update_log(doc_id, seq, client_id, clock, bytes, user_id, ts)` table. Loading a document replays its log.
7. **Client "Saved" indicator:** shows "Saved" only when every local update has been confirmed.

**Deployed:** The CI pipeline (GitHub Actions) builds one container image and Terraform provisions prod: one sync/API container on ECS or Fly, managed Postgres with point-in-time recovery turned on, and a CDN. Every merge to `main` deploys to prod.

**Logged:** Structured JSON logs carrying `doc_id`, `conn_id`, hashed `user_id` and `trace_id`.

**Monitored:**
- OpenTelemetry trace for each update: receive → apply → commit → confirm → broadcast.
- Metrics: active connections, confirmation latency p50/p99, commit error count, broadcast latency.
- Dashboard, plus alerts on any commit error and on confirmation p99 above 500 ms.

**Exit check:** The "hello" scenario passes in prod, including the server restart. Its trace is visible end-to-end, and the confirmation-latency metric shows on the dashboard.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

**Phase 1: Data contracts (document schema, storage model, permission model, wire protocol)**
- **Unlocks:** Everything after it. All later code reads and writes these shapes.
- **Depends on:** Phase 0. The real CRDT edit → commit → reload path has been proven in prod.
- **Tasks (widest first):**
  1. **Document schema v1 plus schema versioning.**
     - Define the ProseMirror node and mark set: headings, lists, marks, links. Tables and media come in Phase 6.
     - Store a `schema_version` on each document. Old documents are migrated forward when they're opened.
     - Rule: clients preserve unknown node types and never drop them, so a mix of client versions can't destroy content.
     - Why first: every stored document has this shape.
  2. **Storage model.**
     - Tables: `workspaces`, `documents`, `update_log`, `snapshots`, `memberships`, `doc_acl`.
     - `tenant_id` on every row, with Postgres row-level security enforcing it.
  3. **Permission model.** Roles are owner/editor/commenter/viewer, checked in two places:
     - when the WebSocket connects;
     - on every incoming message: the server drops sync and update messages from read-only connections and records the denial.
     - Long-lived sockets re-check permission every 5 minutes. Revoking access closes the socket within 60 s.
  4. **Wire protocol envelope.** A protocol version, plus our confirmation message and an optional trace ID, wrapped around y-protocols. Servers reject unsupported versions with an "upgrade client" code.
- **Exit check:**
  - A golden set of documents loads and migrates correctly in CI.
  - A viewer's attempted write is rejected on the server and counted. A cross-tenant read returns zero rows under row-level security.
  - An old client and a new client edit the same document without losing content.

**Phase 2: Convergence and durability hardening**
- **Unlocks:** Trustworthy "Saved". Scaling out and feature work become safe.
- **Depends on:** The Phase 1 storage model and wire protocol.
- **Tasks (widest first):**
  1. **Idempotent append.** Deduplicate on `(doc_id, client_id, clock)` so retried updates are never applied twice.
  2. **Reconnect and resync.**
     - Exchange state vectors and send only the missing updates.
     - The client keeps unconfirmed updates in IndexedDB until they're confirmed, so they survive a tab crash.
  3. **Snapshot compaction.**
     - Write a snapshot, rebuild the document from it, and check that the rebuilt content hash matches the full log replay. Only then mark it as current.
     - Never delete log rows (see the history-retention gate).
  4. **Divergence detector.**
     - Clients report a hash of the rendered ProseMirror JSON, plus their state vector, every N seconds.
     - If a client's hash differs from the server's at the same state vector, the client is forced to resync and an alert fires.
  5. **Limits.** Maximum update size, per-connection rate limits, and backpressure on slow consumers.
- **Exit check:**
  - A seeded property-based fuzz suite runs 10,000 random multi-client edit sequences with dropped, reordered and duplicated messages and server kills mid-commit. Every confirmed update survives, and every copy plus the stored state ends up identical.
  - A backup restore drill succeeds.

**Phase 3: Scaling out the sync tier**
- **Unlocks:** Real user load, and deploys that don't kick editors off.
- **Depends on:** Phase 2. The log is proven to be the source of truth, so any node can rebuild any document.
- **Tasks (widest first):**
  1. **Routing.** Consistent-hash routing of documents to sync nodes at the load balancer or a thin router. A routing miss gets a redirect.
  2. **Node failover.** When the node holding a document dies, clients reconnect to the new owner, which rebuilds the document from snapshot plus log tail.
  3. **Graceful drain on deploy.** Stop accepting connections, hand off documents, then close sockets with a reconnect hint.
  4. **Hot-document fan-out over pub/sub,** behind a feature flag. Only if load tests trigger the placement gate.
  5. **Capacity plan** from load tests: connections and documents per node.
- **Exit check:**
  - A k6 load test reaches the target (e.g. 10,000 concurrent connections, 2,000 active documents) with confirmation p99 under 300 ms.
  - Killing a node mid-edit causes zero confirmed-update loss and recovers in under 5 s.
  - A rolling deploy under load causes zero divergence alerts.

**Phase 4: Presence and awareness**
- **Unlocks:** The "collaborative" feel: live cursors, selections, who's here.
- **Depends on:** Phase 3 fan-out and routing. Presence travels the same path but is never stored.
- **Tasks (widest first):**
  1. **Awareness channel** (y-protocols awareness) with a payload schema, size cap and throttle of 10 messages/s per client.
  2. **Identity shown in presence.** Respect the permission model: anonymous link viewers see display names only, never emails.
  3. **Remote cursors and selections** in the editor UI.
  4. **Avatars bar and idle/away states.**
- **Exit check:**
  - A Playwright test with 5 browser contexts shows correct cursors.
  - A killed client's cursor disappears within 30 s.
  - Presence traffic adds less than 10% to confirmation p99.

**Phase 5: Collaboration features**
- **Unlocks:** Review workflows.
- **Depends on:** The Phase 2 log (history), the Phase 1 permission model, and Phase 4 identity in the editor.
- **Tasks (widest first):**
  1. **Version history and restore.**
     - Rebuild any point in time from the log.
     - Restore is written as a *new forward update*, never a rewrite of the log, so it can be undone and audited.
     - Why first: it touches the log's meaning.
  2. **Comments and threads.** A new entity, anchored to text positions that survive concurrent edits (Y.RelativePosition). If the anchored text is deleted, the comment is shown as detached rather than lost.
  3. **Per-user undo/redo** (Y.UndoManager tracking only local changes).
  4. **Sharing UI and @mentions.** Invite, share links with roles, mention notifications that respect permissions.
  5. **Audit log** for permission changes and restores.
- **Exit check:**
  - History rebuilt from the golden logs matches recorded checkpoints.
  - Restore can be undone.
  - Comments survive a fuzz test of concurrent edits around their anchors.
  - A mention never notifies a user who lacks access.

**Phase 6: Rich content and polish (the flashy leaf work)**
- **Unlocks:** Feature parity and a polished feel.
- **Depends on:** Every phase above. These are leaves.
- **Tasks (widest first):**
  1. **Media upload pipeline.**
     - Signed upload URLs to object storage, content-type sniffing, size limits, malware scan.
     - Image nodes are added to the schema as v2, which exercises the migration path from Phase 1.
  2. **Tables,** as another schema change.
  3. **Paste handling.** HTML paste is sanitized and mapped onto the schema.
  4. **Export** to Markdown, DOCX and PDF as a sandboxed async job.
  5. Templates, keyboard shortcuts, slash commands, visual polish.
- **Exit check:**
  - Schema v1 → v2 migration passes on the golden documents.
  - An XSS paste and upload test suite passes.
  - Keystroke-to-render p95 stays under 16 ms on a 50-page document.
  - Export success rate is at least 99.5% with a p95 under 10 s.

## 6. AI layer
N/A: there are no AI or agent features in scope. If AI features are added (e.g. AI writing help), run Step 6 then. Guardrails, cost/latency budget and human approval come before any model access. The "server can read content" gate also becomes a data-privacy boundary.

## 7. Deferred
- **Full offline-first editing (days offline, conflict review UI).** Pull forward when a mobile app is planned or offline use shows up in feedback. The CRDT gate already makes this feasible.
- **Multi-region active-active sync.** Pull forward when more than 20% of users see round-trip p95 above 150 ms, or a data-residency requirement appears.
- **Permissions on individual sections.** Pull forward when an enterprise contract requires it. It means restructuring documents into Yjs subdocuments, so price it accordingly.
- **End-to-end encryption.** Pull forward on a zero-access compliance requirement. It flips the plaintext gate and removes server-side search and export.
- **Full-text search across documents.** Pull forward when the median workspace passes ~200 documents, or "can't find doc" becomes a top-3 support issue.
- **Suggestion / track-changes mode.** Pull forward when editorial or legal customers ask for it. Re-check the OT/sequencing revisit trigger first.
- **Native mobile apps.** Pull forward when mobile web sessions pass 25% and retention lags.
- **Further service decomposition.** Pull forward on the monolith gate's revisit trigger.
- **Plugin/extension API.** Pull forward when the schema has been stable (no breaking change) for 2 consecutive quarters, so we don't freeze a contract early.
- **Email digests and rich notifications beyond mentions.** Pull forward when engagement metrics justify them.
