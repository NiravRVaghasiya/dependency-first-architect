# Plan: Moving the hospital's patient scheduling system to the cloud with no planned downtime

## 1. Classification and constraints
- **What:** Move a working, on-premises patient scheduling system (an app tier plus one database, with its interfaces and batch jobs) into a cloud tenancy the hospital controls. Users must not lose scheduling at any point.
- **Type:** Infrastructure migration of existing software that already holds real patient data (brownfield). Not a small build: it holds regulated health data, crosses several teams and has a cutover that is hard to reverse.
- **Dominant constraint:** Correctness first, then availability. Users must see no outage, and no booking may ever be lost or duplicated.
- **Worst failure:** A booking is silently lost or double-booked during coexistence or cutover, for example because two databases accept writes at once ("split brain"). The result is a missed or delayed patient visit that nobody notices until the patient arrives or fails to. V3 and V4 guard against this. Exposure of patient data in the new environment is the second worst; V2 guards against it.

**Inherited constraints (not changing during the move; cost to change is a separate project):**
- the application code and version (feature freeze, security patches only);
- the database engine and schema;
- HL7 interface contracts;
- the hospital directory (AD) identities;
- the hospital-wide interface engine, which stays on-premises;
- the existing downtime procedures.

**Missing inputs (most plan-changing first), with what I assumed:**
1. **Is it a vendor product or built in-house, and does the vendor support cloud hosting and licence portability?** I assumed we run it and the vendor supports cloud hosting. If not, the "build vs buy" row in §3 flips: either the vendor hosts it (a re-plan from Step 1) or licensing changes the economics.
2. **How do clients connect: through an app tier, or desktop clients straight to the database?** I assumed through an app tier. If clients go straight to the database, Phase 2 (moving users in groups) is impossible. The plan would then become a database-first cutover, with remote desktop (Citrix/VDI) or the app moving at the same moment.
3. **What exactly does "without downtime" mean?** I assumed a write pause of ≤ 60 s is acceptable. If it must be literally zero, two databases would have to accept writes at once. That is the worst failure, so I would push back on that requirement instead of designing for it.
4. **Which rules apply?** I assumed HIPAA (US) and an in-country cloud region.
5. **The full list of interfaces and batch jobs.** Built in Phase 0; currently all ASSUMED.
6. **The cloud provider, and whether a business associate agreement (BAA, the HIPAA contract with the provider) already exists.**

## 4. First end-to-end slice (Phase 0)
- **Real request:** in production, an IT scheduling analyst books and then cancels an appointment for the designated test patient (e.g. "ZZTEST, Patient") on a test resource in a test department. The confirmation and the cancellation both come back, and the normal scheduling (SIU) message reaches the EHR through the interface engine. Every hop carries one correlation ID.
- **Tiers crossed:**
  - analyst workstation;
  - the hospital load balancer (a routing rule matched on an AD group or a separate host name);
  - private circuit or VPN;
  - one cloud app node (patient data only in transit; interface-sending and batch jobs **disabled**, so they stay single-instance on-premises);
  - the on-premises production database, through a least-privilege login;
  - the on-premises interface engine;
  - the EHR.
- **Deployed:**
  - The landing zone and app node are built from Terraform through the pipeline.
  - The app build is the same version as on-premises, from a pinned image.
  - Before that, a dependency inventory lists every interface, batch job, report extract, printer or label server, call-centre phone integration, reminder vendor, portal, warehouse extract and AD/SSO dependency, each marked CONFIRMED or ASSUMED (checked against connection logs and firewall flows).
  - The live on-premises path is baselined through its own CAB change: performance monitoring (APM) agent and database query statistics turned on.
- **Logged and monitored:**
  - Load balancer, app and database audit logs go to the SIEM. They are classified as patient data and scrubbed of SQL parameters.
  - Synthetic book/cancel checks run on both paths. Alerts go to the existing on-call.
- **Rolled back:** redeploy the previous image through the pipeline, and remove the routing rule (the on-premises path is the fallback for everyone).
- **Who can reach it:** only allow-listed IT analysts, behind the routing rule. No clinical users, and no patient data at rest in the cloud.
- **Exit check (V0):**
  - one traced book/cancel succeeds across every tier;
  - a deploy and a rollback succeed through the pipeline;
  - stopping the cloud app service fires an alert and the load balancer pulls the node;
  - per-transaction latency, network round-trip time and database round trips per transaction are recorded as near-zero-load baselines, alongside the on-premises BASELINE.

## 5. Phases

- **Phase 1: Trust boundary, data replication, capacity proof**
  - Unlocks: patient data at rest in the cloud; clinical user groups in Phase 2; the rehearsals for Phase 3.
  - Depends on: V0. V2 must pass before the replica is seeded.
  - Tasks, widest rework first:
    1. Identity federated with AD and least-privilege roles; network segmentation and private endpoints; keys managed by the hospital; run V2.
    2. Start the second diverse circuit and VPN backup (lead time from week 1); V5 test design.
    3. Database compatibility assessment, then the managed-vs-VM decision (§3).
    4. Seed the cloud copy and start replication on-premises → cloud (read-only); start V3's 14-day clock.
    5. Create stable DNS names for the database and app listener now, so the cutover is a DNS change, not a reconfiguration of every interface.
    6. Size the cloud app tier at 2× BASELINE peak; run V1.
    7. Draft cloud DR to the BC/DR RTO/RPO once supplied.
  - Rollback: tear down the copy and replication. The on-premises system of record is untouched.
  - Exit check: V2 and V1 pass; V3 running.

- **Phase 2: App tier serves real users in groups (database still on-premises)**
  - Unlocks: the cloud app path proven on every user group before the database moves.
  - Depends on: V1, V2.
  - Tasks:
    1. Pin interface-sending and batch jobs to one on-premises node; check daily for duplicate messages.
    2. Route user groups by AD group, smallest first: IT and scheduling super-users → one low-volume outpatient clinic → 10% of call-centre seats → 50% → all.
    3. Each wave lasts at least one week including a Monday peak, and advances only while latency stays within V1's threshold and errors are no higher than baseline.
  - Rollback: shift load-balancer weight back to the on-premises app tier (seconds). Health checks fail cloud nodes over automatically if the link drops.
  - Exit check: all groups on the cloud app tier for 2 weeks within budget; zero duplicate interface messages or reminders.

- **Phase 3: Database cutover (one event, E1)**
  - Unlocks: the cloud becomes the system of record.
  - Depends on: V3, V4 (two rehearsals plus signed go/no-go), V5, the CAB slot.
  - Tasks:
    1. Freeze schema and config changes.
    2. Switch replication to synchronous; confirm zero lag.
    3. Planned failover in a low-volume window (scheduling never fully stops in a hospital).
    4. In the same runbook: start reverse replication cloud → on-premises; move the single-instance jobs and interface listeners via the DNS names from Phase 1.
    5. Smoke-test every inventoried interface; run reconciliation within 1 h.
  - Rollback: fail back to on-premises through reverse replication (rehearsed in V4). Point of no return is Phase 5, not this phase.
  - Exit check: the V4 thresholds hold in production; the reconciliation (counts and checksums) is clean at T+1 h and T+24 h.

- **Phase 4: Stabilize in the cloud**
  - Unlocks: the evidence needed for decommissioning.
  - Depends on: Phase 3.
  - Tasks:
    1. Drain the on-premises app tier to zero but keep it warm; on-premises database stays as a reverse-replication standby.
    2. Cloud DR test: zone failover plus a point-in-time restore against the BC/DR RTO/RPO.
    3. Run V7 over 30 days; rightsize.
  - Rollback: failback is still available.
  - Exit check: 30 days without failback; DR test within RTO/RPO; V7 evaluated.

- **Phase 5: Decommission on-premises (point of no return)**
  - Depends on: V6, V7.
  - Tasks:
    1. Stop reverse replication.
    2. Take a final full backup exported in the engine's native format and restore-test it.
    3. Archive under the retention policy.
    4. Wipe storage media to NIST 800-88 with certificates.
    5. Remove firewall rules and service accounts.
  - Rollback: none after reverse replication stops; V6 guards this step.
  - Exit check: V6 evidence filed; no remaining consumers of on-premises endpoints.

## 10. Deferred
- **Re-architecture** (containers, services, a managed database the app isn't built for). Pulled forward when Phase 5 is done, the system has been stable for 90 days and a modernization case is approved.
- **Disaster recovery across regions.** Pulled forward if the BC/DR RTO/RPO (UNKNOWN) needs recovery beyond one region's zones.
- **Moving the interface engine to the cloud.** Pulled forward when its other consumers plan their own migration.
- **New features** such as patient self-scheduling. Pulled forward after Phase 5; a feature freeze applies until then.
- **Autoscaling.** Pulled forward if V7 fails on idle capacity.
- **A read replica for reporting.** Pulled forward if reporting load threatens the latency budget.
