# BUILD PLAN: Real-time collaborative document editor

## 1. Classification and constraints
- **What:** A browser-based rich-text editor where several people edit the same document at once. Each person's edits show up for the others live and are saved on the server. Documents are shared within workspaces and through per-document grants.
- **Type:** Software. Greenfield. Not a small build: it has outside users, customer documents (personal data) and several R3 decisions.
- **Dominant constraint:** Correctness. Every copy of a document must end up the same, and no edit the server has confirmed may be lost.
- **Worst failure:** A document silently diverges or loses edits. A user sees "saved", but collaborators' copies, or the copy on the server, differ or are missing confirmed edits. Nobody notices until the content is gone. Guarded by V1, V3 and the convergence checksum in production (Phase 1).

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Remote edit latency (keystroke on A shows on B, same region) | p95 < 200 ms | ASSUMPTION: below roughly 250 ms, collaborators read edits as live. Confirm with product owner | V0 floor; V4 |
| Local input latency (keystroke to screen) | p95 < 16 ms on a 100-page doc | ASSUMPTION: one 60 Hz frame | V1 |
| Doc open time | p95 < 1.5 s for a 100-page doc with 30 days of heavy edit history | ASSUMPTION: a typical web-app load expectation | V1 |
| Throughput per doc | ≤ 50 concurrent editors | ASSUMPTION: team documents. Large broadcast audiences are deferred (§10) | V4 |
| Throughput, whole system | — | UNKNOWN: needs projected peak concurrent editors and open docs. Product owner supplies it in Phase 1; V4 needs it in Phase 3 | V4 |
| RPO | 0 for edits the server has confirmed (acked) | ASSUMPTION: "saved" must mean saved. Confirm with product owner | V3 |
| RTO (losing one collab server) | Clients reconnected and synced, p95 < 30 s | ASSUMPTION: a reconnect a user tolerates without losing work | V3 |
| RTO (losing a region) | — | UNKNOWN: product owner supplies it with the SLA, before Phase 5 | Phase 5 restore drill |
| Availability / SLO | — | UNKNOWN: needs the SLA the business commits to (product/sales), before Phase 5 | Phase 5 SLOs and burn-rate alerts |
| Storage | Raw edit history ≤ 10× the doc's compacted snapshot after 30 days of heavy editing | ASSUMPTION: estimated from the CRDT format's overhead, to confirm | V1 |
| Operational complexity | Two deployables, managed Postgres, Redis only if V4 flips; ≤ 2 pages/week | ASSUMPTION: a team of 6 or fewer engineers | Phase 3 exit check |

**Missing inputs** (the order rests on these assumptions):
1. **No end-to-end encryption.** I assume the server may read document content so it can check edits and save snapshots. If E2EE is required, the trust boundary changes completely and the plan restarts from Step 1.
2. **Offline editing.** I assume disconnections last minutes, not days. If offline-first is required, client-side storage moves into Phase 1, and the CRDT choice becomes a requirement instead of a default.
3. **Business-team (B2B) workspaces in one region.** I assume no data-residency rule. If one applies, the region becomes a Phase 1 data-model decision, not something to add later.
4. **Scale, SLA and team size.** These change thresholds, not the order.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| How concurrent edits merge: CRDT vs OT vs locking | R3: it fixes the stored format and the client protocol; real docs cannot be safely re-encoded | **Yjs CRDT** bound to ProseMirror (Tiptap + y-prosemirror) | Yjs converges for our schema; its leftover deleted-content markers ("tombstones") stay within the storage and load budgets | V1 | V1 fails, or a need appears for a single server-ordered edit history (audit) → OT (prosemirror-collab, server-assigned versions) |
| Consistency vs availability | R3: users rely on "saved" | Every copy converges to the same state. Local edits apply at once, even while offline. The server acks only **after a durable Postgres commit**; the UI shows "unsaved" until then | The cost of committing each update fits the latency budget | V3 (durability), V4 (latency) | V4 shows per-update commits break latency → group commits in windows of ≤ 50 ms, still acking only after they are durable |
| Storage model and identifiers | R3: fixed once real docs exist | Postgres append-only edit log plus snapshots. UUIDv7 doc IDs. `tenant_id` and `schema_version` on every row. Raw edits kept (archived, never deleted) | One Postgres primary handles the peak write rate | V4 | V4 shows one primary cannot keep up → split the edit log across databases by `doc_id` |
| Tenancy and isolation | R3: a cross-tenant leak cannot be undone | Shared schema, `tenant_id` on every row, Postgres row-level security (RLS) | B2B workspaces with no dedicated-isolation contracts | V2 | A contract requires dedicated isolation → a separate (siloed) tier for that customer |
| Trust boundary | R3: what the server enforces is a security commitment | The server decides all permissions. It checks the role when a client joins a document and **on every update**. It applies each update to its own copy and rejects any that breaks the schema or is too large. Clients are never trusted | Checking updates on the server fits the latency budget | V2, V4 | V4 shows the check is too costly → check asynchronously and reverse or quarantine the offending client's updates |
| Data-privacy boundary | R3: exposure cannot be undone | Document content and titles exist only in the browser, collab-server memory, Postgres and encrypted backups. Never in logs, traces, metrics, the error tracker or analytics. Telemetry uses hashed doc IDs. No E2EE. Single region | No customer needs E2EE or data residency | V5 | A customer or regulator requires E2EE → re-plan from Step 1. Residency required → one deployment per region |
| Build vs buy | R3 if hosted (customer documents end up held by the vendor); R2 if self-hosted | **Self-host** open-source Yjs and the Hocuspocus sync server. Buy the identity provider (OIDC: WorkOS, Auth0 or Cognito) and managed Postgres | The team can run a stateful WebSocket tier | V3; Phase 3 exit check (on-call load) | On-call load goes over budget → evaluate hosted sync (Tiptap Cloud or Liveblocks) with a tested export path, as a new R3 decision reviewed under V5 |
| Routing of editing sessions | R2: an internal topology | **One owning server per open doc** (consistent hash on `doc_id`). The owner saves edits and sends them to every editor | One doc's editors fit on one server (≤ 50) | V4 | V4 fails, or a single doc needs more than one server → several servers per doc, fanned out through Redis pub/sub |
| Monolith vs services | R2 | One repo, two deployables: a stateless HTTP API and a stateful collab WebSocket server | The two tiers scale and deploy differently | Phase 3 exit check | Ops load too high → merge into one deployable. Separate teams need separate release cycles → split further |
| Sync vs async | R2 | Edits are pushed asynchronously with an ack. Side effects (search, notifications, thumbnails) go through a transactional outbox, never in the edit path. Permission changes are synchronous | Side effects can lag by seconds | Phase 4 exit check | A side effect needs to see its own write immediately → make it synchronous |
| Editor document schema | R2: a breaking change means migrating every doc | Minimal Tiptap schema (paragraphs, headings, lists, marks, links, images by reference), versioned, with migrate-on-load | — | Phase 4 migration test on a synthetic set of docs | A needed node type can't be added without breaking old docs → write an explicit migration with a backfill |

**R1 defaults:** TypeScript throughout; React + Vite; GitHub Actions; Terraform; OpenTelemetry → Grafana stack; OpenFeature flags; presence (live cursors) via Yjs awareness, which is temporary and not saved; images in S3 behind signed URLs.

**N/A:** AI rows (no AI component); brownfield rows (greenfield).

## 4. Walking skeleton (Phase 0)
- **The one real request:** An internal user signs in, creates a document and types a line. A second browser session, signed in as another internal user with an editor grant, sees the line appear. A reload shows the line was saved.
- **Tiers it crosses:** Browser (React + Tiptap + Yjs) → CDN (static assets) → HTTP API (OIDC login, create doc, ACL check, issue a short-lived WebSocket token) → collab server (Hocuspocus; checks the token; applies, saves and acks the update) → Postgres (edit log row) → sent out to the second client.
- **Day zero:**
  - **Deployed:** CI builds container images pinned by digest and deploys them with Terraform into the production account.
  - **Logged:** Structured logs, with document content excluded by construction (an allow-list of fields).
  - **Traced:** One OpenTelemetry trace runs from the browser span through the API, the collab server and the Postgres commit.
  - **Monitored:** Alerts on WebSocket error rate, ack latency, and failed saves.
  - **Rolled back:** The pipeline redeploys the previous image once.
- **Who can reach it:** Internal staff on an allow-list, behind a feature flag. Skeleton docs are tagged `disposable` and are deleted if V1 flips. They run on the unvalidated Yjs default.

**Exit check (V0):**
- The request above succeeds with one trace across every tier.
- A deploy and a rollback succeed through the pipeline.
- Killing the collab process fires an alert.
- Remote-edit latency, ack latency and doc-open time are recorded as near-zero-load baselines.

## 5. Phases

- **Phase 1: Merge core and data model** (biggest rework if wrong)
  - Unlocks: A settled storage format, so permissions, durability and features can be specified.
  - Depends on: V0.
  - Tasks:
    1. Run V1 (fuzz testing and size benchmark).
    2. Finalize the edit-log and snapshot tables (`tenant_id`, UUIDv7, `schema_version`, `client_id`, `seq`), with expand/contract migrations.
    3. Turn on Postgres row-level security.
    4. Build the ACL schema: workspace roles (owner, editor, commenter, viewer) plus per-document grants.
    5. Build the convergence checksum: clients periodically report a hash of their copy, and the server compares it with its own.
    6. Get the projected peak from the product owner, which V4 needs.
  - Rollback: Expand/contract migrations. If V1 fails, delete the disposable docs and switch to OT before any real doc exists.
  - Exit check: V1 passes. A divergence alert fires when a mismatch is injected on purpose.

- **Phase 2: Trust boundary and durability**
  - Unlocks: Internal staff using it for real work (the first exposure to real data).
  - Depends on: Phase 1, V1.
  - Tasks:
    1. Check permissions on HTTP calls, on WebSocket join and on every update.
    2. Close live sessions within 5 s when access is revoked.
    3. Check every update against the schema and size limits on the server.
    4. Sanitize pasted HTML.
    5. Ack only after a durable commit.
    6. Keep unacked updates in the browser (IndexedDB) and resend them after a reload.
    7. Resync on reconnect.
    8. Drain a server cleanly during deploys.
    9. Run V2 and V3.
    10. Open dogfooding to internal staff, behind the flag.
  - Rollback: Redeploy the previous image. Never roll back to weaker permission checks; turn the flag off instead.
  - Exit check: V2 and V3 pass. Dogfooding has run for one week with no divergence alerts.

- **Phase 3: Scale and cost**
  - Unlocks: The routing and scaling design can be hardened; GA infrastructure cost can be committed.
  - Depends on: Phase 2, V3, and the product owner's peak figure.
  - Tasks:
    1. Route each doc to its owning server (consistent hash), behind a flag.
    2. Unload idle docs from server memory.
    3. Hand docs over to another server during a drain.
    4. Compact the edit history into snapshots without deleting the raw edits, which are archived to S3.
    5. Add backpressure and per-tenant connection quotas.
    6. Run V4.
  - Rollback: Turn the routing flag off to fall back to the Phase 2 topology. Compaction can be reversed because the raw edits are kept.
  - Exit check: V4 passes. Over two weeks of dogfooding, on-call load stays within the ops budget in §1.

- **Phase 4: Collaboration features** (leaf work)
  - Unlocks: A product worth piloting.
  - Depends on: Phase 3, V1 (format), V2 (roles).
  - Tasks:
    1. Comments anchored to text positions that survive concurrent edits (Yjs relative positions); enforce the commenter role.
    2. Version history and restore, built on snapshots.
    3. Sharing UI and link sharing (expiring, scoped by role).
    4. Export (sanitized).
    5. Outbox consumers (notifications, thumbnails).
    6. Presence and cursors. This is the flashiest feature and depends on everything else.
    7. Schema-migration tests on a synthetic set of docs.
  - Rollback: A flag per feature. Comment and outbox tables only add to the schema, so removing a feature never touches existing data.
  - Exit check: Every feature's V2 permission tests pass. Migrations pass on the synthetic doc set. Outbox lag p95 < 10 s.

- **Phase 5: Exposure in widening waves**
  - Unlocks: General availability.
  - Depends on: Phase 4, V2, V3, V5; the SLA committed; the pen test done.
  - Tasks:
    1. One design-partner customer.
    2. Pen test findings fixed.
    3. Define SLOs and burn-rate alerts.
    4. 10% of new signups.
    5. GA.
    6. Rehearse restoring from backup against the region RTO.
  - Rollback: Each wave is gated by flag: turn it off and offer that customer an export.
  - **Point of no return:** Once outside customers have real documents, the stored format is permanent (it was guarded by V1 and V3 before this phase).
  - Exit check: Each wave runs 2 weeks with zero divergence alerts and zero acked edits lost before the next wave starts.

## 10. Deliberately deferred
- **Offline-first editing (days offline):** pulled forward when product requires it. Yjs keeps this option open.
- **End-to-end encryption:** pulled forward when a customer or regulator requires it. That means re-planning from Step 1.
- **Multiple regions or data residency:** pulled forward when V5 or a contract requires residency, or the SLA needs more than one region.
- **Deleting raw edit history:** pulled forward when storage cost goes over budget and a check confirms that snapshots match the full replayed history. It is gated as an irreversible operation.
- **Several servers per doc (Redis fan-out):** pulled forward when V4 fails or a doc needs more than 50 editors.
- **Suggestion mode / tracked changes:** pulled forward when design-partner feedback in Phase 5 asks for it.
- **Full-text search:** pulled forward when users report they can't find documents; it is fed by the outbox.
- **Public API and webhooks:** pulled forward when customers ask for them. They become R3 once anyone outside uses them.
- **Native mobile apps:** pulled forward when mobile web usage data or customer demand justifies them.
- **.docx import:** pulled forward when it becomes an onboarding blocker for the design partner.
