# Plan: Multi-Tenant SaaS Billing System

> **Interpretation (stated, not assumed):** This is a billing platform where each tenant is a business with its own catalog, customers and invoices (like Chargebee or Stripe Billing). If you only mean billing for *one* SaaS product's subscribers, the build-vs-buy gate flips. Buy Stripe Billing, and most of this plan collapses into an integration.

---

## 1. Classification
- **What:** A multi-tenant platform. Tenants define products and prices, subscribe their customers, meter usage, issue invoices, collect payments and reconcile.
- **Type:** Software, with infra concerns (payment-service provider, or PSP, integration; queues; data isolation). No AI.
- **Dominant constraint:** **Correctness**, followed closely by **compliance** (PCI DSS scope, tax, audit trail, SOC 2).
- **Worst failure:** A customer is charged the wrong amount or charged twice, and no immutable record exists to prove what happened or fix it. A cross-tenant data leak is the next worst, and it is closed off in Phase 1.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| Consistency vs availability | **Strong consistency (CP) for money.** The ledger, invoices and subscription state live in a single-primary Postgres, and ledger postings use SERIALIZABLE transactions. **Availability first (AP) for usage ingestion:** accept events, dedupe later. | Never flip the ledger to AP. If one primary can't keep up with ledger writes (sustained >~3k postings/s or primary CPU >70% at peak), shard **by tenant** and keep each tenant strongly consistent. |
| Monolith vs services | **Modular monolith** with enforced module boundaries (ledger, catalog, subscriptions, invoicing, payments, usage). Modules talk only through interfaces and the outbox, and an import linter enforces this in CI. | Pull usage ingestion out into its own service when it needs different scaling (>5k events/s), or when its deploy cadence regularly blocks ledger releases. |
| Sync vs async | **Sync** for API writes that change state (create subscription, finalize invoice, request refund). They return only after the database commit. **Async** (transactional outbox, then a queue) for PSP calls, invoice batch runs, dunning, tax calls in batch, and outbound webhooks. | If tenants need a synchronous "charge now and confirm" call at checkout, add a sync PSP path with a strict timeout. The async path stays the source of truth. |
| Build vs buy | **Buy:** payment processing and card tokenization (Stripe or Adyen, which keeps us in PCI SAQ-A scope because no card numbers touch us), tax calculation (Stripe Tax or Avalara), email delivery, and auth for dashboard users (an OIDC provider). **Build:** ledger, rating, subscriptions and invoicing. That is the product. | If this is internal billing for a single SaaS (see interpretation above), buy the whole engine. If one PSP's coverage or fees block >10% of tenant revenue, add a second PSP behind a payments interface. |
| Tenant isolation | **Shared database and shared schema**, with `tenant_id` on every row and **Postgres row-level security (RLS)**. The app's database role has no BYPASSRLS. | An enterprise contract requires a dedicated database or data residency → move that tenant to a dedicated cell. The schema is identical, so only routing changes. |
| Money representation (irreversible) | Store amounts as **integer minor units** (`bigint`) with an ISO 4217 currency code on every amount. Usage unit prices use `numeric(38,12)`. Rounding is **half-even at the line-item level** and is recorded on the line. Ledger accounts are single-currency. | None. This cannot be changed later without restating history. |
| Ledger model (irreversible) | **Double-entry, append-only and immutable.** Corrections are reversing entries and credit notes, never UPDATEs. | None. |
| Region / data residency | Single region (e.g., us-east-1). Point-in-time recovery (PITR) and cross-region backups from day zero. | First EU tenant with a GDPR residency clause → add an EU cell. |
| (AI) prompt+RAG vs fine-tune | N/A: there is no AI component. | Only if an AI feature is added (see Deferred). |
| (AI) hosted API vs self-host | N/A: there is no AI component. | Same as above. |

## 3. First end-to-end slice (Phase 0)

**The one real request:** An internal "house" tenant calls `POST /v1/invoices` with its API key and an `Idempotency-Key`. The invoice is one $1.00 one-off line for a real customer whose card is stored as a PSP token.
**The real response:** `201` with the invoice ID. The invoice then moves `open → paid` within seconds, and `GET /v1/invoices/{id}` returns `status: paid` with the PSP charge ID.

**Tiers crossed:**
1. Edge: load balancer with TLS and a WAF.
2. API: authenticates the hashed API key and resolves `tenant_id` from it.
3. Postgres, in one transaction: insert the invoice, write a 2-line double-entry posting (debit accounts receivable, credit revenue), write an outbox row.
4. Worker: reads the outbox and calls the PSP to create a PaymentIntent. The PSP idempotency key is `invoice_id:attempt_1`.
5. PSP webhook: signature verified, then written durably.
6. Postgres: mark the invoice paid and post cash against accounts receivable.
7. `GET` returns the paid invoice.

**Deliberately hardcoded:** one tenant, one currency, no catalog, no subscriptions, no tax.

**Deployed:**
- CI builds an immutable container image, pinned by digest.
- Terraform provisions everything: ECS or Kubernetes, RDS Postgres with PITR on, SQS, Secrets Manager.
- Migrations are versioned and run as a deploy step.

**Logged:** Structured JSON logs with `request_id`, `tenant_id`, `idempotency_key`, `invoice_id` and `trace_id`.

**Monitored:**
- OpenTelemetry trace across API → DB → outbox → worker → PSP → webhook.
- Request rate, error rate and duration metrics on the API.
- `invoice_paid_total`, `outbox_lag_seconds` and `webhook_failures_total`.
- Alerts on 5xx rate, outbox lag >60s, and any webhook signature failure.

**Exit check:** One **live-mode** $1.00 charge and its refund complete in prod. A single trace covers every tier, and paid and refunded invoices both show on the dashboard. A PITR restore into a scratch instance has been done once.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

**Phase 1: Tenancy, identity and money substrate**
- **Unlocks:** Every later module can safely store tenant-scoped money.
- **Depends on:** Phase 0 deploy, trace and outbox path proven in prod.
- **Tasks:**
  1. Tenant model and RLS policies on every table. `tenant_id` comes only from the auth context, never from the request body.
  2. Auth model: per-tenant API keys, hashed, with scopes (`read`, `write`, `ingest-only`, `refunds`), plus key rotation.
  3. Money type and currency invariants in code and as DB CHECK constraints.
  4. Real double-entry ledger schema: accounts, transactions, postings. A DB-level constraint keeps each transaction's postings summing to zero.
  5. Idempotency-key store: request hash plus stored response, with a 24h replay window.
  6. Append-only audit log (UPDATE and DELETE revoked).
  7. Generalize the outbox: at-least-once delivery, with dedupe by event ID on the consumer side.
- **Exit check:**
  - A property test (fast-check or Hypothesis, fixed seeds, 100k cases) shows every transaction balances.
  - A cross-tenant suite shows tenant A's key cannot read or write tenant B's data through any endpoint, or through raw SQL as the app role.
  - Replaying a request with the same idempotency key 1,000 times concurrently produces exactly one posting.

**Phase 2: Catalog, customers and API contract**
- **Unlocks:** Subscriptions and invoices can reference stable, versioned prices.
- **Depends on:** Phase 1 tenancy, money type and ledger.
- **Tasks:**
  1. Public API shape: OpenAPI is the source of truth, with date-based version headers, cursor pagination and a standard error envelope. This has the widest impact because tenants code against it.
  2. Products and **immutable price versions**. A price is frozen once any invoice uses it, and changes create a new version.
  3. Customers, with PII fields classified.
  4. Payment methods stored only as PSP tokens.
  5. Generate SDKs from the spec.
- **Exit check:** Contract tests pass against the spec. Any attempt to mutate a used price version is rejected. An SDK smoke test runs in CI.

**Phase 3: Subscriptions and the billing clock**
- **Unlocks:** Recurring revenue and the invoices it produces.
- **Depends on:** Phase 2 price versions and customers.
- **Tasks:**
  1. Subscription state machine: `trialing → active → past_due → canceled/paused`. It is an explicit transition table, and no other transitions exist.
  2. Injectable clock and per-tenant **test clocks** for time travel.
  3. Billing-period calculation, including anchors, month-end and leap years.
  4. Proration rules for upgrades, downgrades and mid-cycle changes.
  5. Scheduler that emits exactly one "period closed" event per (subscription, period), enforced by a unique constraint.
- **Exit check:** A seeded simulation of 10k subscriptions over 24 simulated months, with random plan changes, matches the expected invoice schedule exactly. Every transition not in the table is rejected.

**Phase 4: Invoicing and rating**
- **Unlocks:** Billable documents that customers can be charged for.
- **Depends on:** Phase 3 period events and Phase 1 ledger.
- **Tasks:**
  1. Invoice lifecycle: `draft → finalized → paid / void / uncollectible`. Finalized invoices are immutable (DB trigger).
  2. Gapless invoice numbering per tenant, for compliance.
  3. Rating of line items, with rounding recorded on each line.
  4. Tax-provider integration. The response is snapshotted onto the invoice.
  5. Credit notes. These are the only way to correct a finalized invoice, and they post reversing ledger entries.
  6. Invoice snapshot: price versions, tax response and calculation version, so the invoice can be regenerated deterministically.
  7. PDF and email rendering. This is the leaf task and comes last.
- **Exit check:**
  - A golden-file suite of 200 invoice scenarios passes.
  - A nightly job confirms open invoice totals equal the accounts-receivable balance in the ledger, to the cent, for every tenant.
  - A regenerated PDF matches its stored snapshot.

**Phase 5: Payments, collection and reconciliation**
- **Unlocks:** Real cash collection for every tenant.
- **Depends on:** Phase 4 finalized invoices and Phase 0's proven PSP path.
- **Tasks:**
  1. Payments interface plus the PSP adapter. The idempotency key is `invoice_id:attempt_n`. On a timeout, query the PSP for the payment's state before any retry; never retry blindly.
  2. Inbound webhook processor: signature verified, deduped, and tolerant of out-of-order delivery because the state machine guards every update.
  3. Daily reconciliation of the ledger against PSP balance and payout reports, with a queue of differences.
  4. Dunning: versioned retry schedules, then `past_due` and cancel.
  5. Refunds and disputes as ledger postings.
  6. Customer emails for failed payments.
- **Exit check:**
  - Seven consecutive days of zero unexplained reconciliation differences in prod.
  - Fault injection (PSP timeout after the charge succeeded, duplicate webhooks, reversed webhook order) causes zero double charges in 10k runs.

**Phase 6: Usage-based metering**
- **Unlocks:** Usage and hybrid pricing.
- **Depends on:** Phase 4 rating and Phase 5 collection. Usage only matters once it can be invoiced and paid.
- **Tasks:**
  1. Ingestion API contract: tenant-supplied event ID, dedupe window, timestamp rules, late-arrival policy. This has the widest impact because tenants instrument their code against it.
  2. Async ingestion. Events are buffered in SQS or Kinesis, and raw events are stored immutably in S3.
  3. Deterministic aggregation (sum, max, unique count) per meter and period.
  4. Feed aggregated usage into rating.
  5. Late events arriving after finalization become adjustments on the next invoice, never edits to a finalized one.
  6. A usage preview endpoint.
- **Exit check:**
  - Replaying the raw S3 events reproduces the aggregates byte-for-byte.
  - Sending each event 3 times at a 5k events/s load test produces no double counting.
  - Ingestion lag p99 stays under 60s.

**Phase 7: Tenant-facing surfaces**
- **Unlocks:** Tenants can self-serve and integrate.
- **Depends on:** Phases 1–6 with stable APIs and events.
- **Tasks:**
  1. Outbound webhooks to tenants: a versioned event schema that tenants build integrations on, so it has the widest impact.
  2. Tenant dashboard: OIDC SSO, role-based access (owner, finance, read-only), and dual approval for manual ledger adjustments above a threshold.
  3. Hosted customer portal: update payment method, view invoices, cancel.
  4. Reports and exports: MRR, AR aging, a revenue-recognition export.
- **Exit check:**
  - At least 99.9% of webhooks are delivered within 5 minutes, and replay from the dead-letter queue works.
  - Five pilot tenants complete onboarding without help from engineering.
  - Report totals tie out to the ledger.

**Phase 8: Harden what has proven load-bearing**
This phase hardens what is proven (principle 2). It is not where security or observability first appear.
- **Unlocks:** Enterprise scale and audit readiness.
- **Depends on:** Production load data from Phases 5–7.
- **Tasks:**
  1. Partition the ledger and postings tables by time.
  2. Read replicas for reporting.
  3. Formal service-level objectives with error budgets.
  4. Automate SOC 2 Type II evidence collection.
  5. Exercise the extraction or sharding revisit triggers from Section 2 if they have triggered.
- **Exit check:** Load test at 10× current peak stays within the objectives. The disaster-recovery rebuild meets a recovery time under 4h and data loss under 5 min. The SOC 2 audit window opens.

## 6. AI layer
**N/A.** There is no AI or agentic component. The system is deterministic by design, since it handles money and must be reproducible. Any future AI feature, such as churn prediction or dunning-message drafting, would sit outside the ledger's write path (see Deferred).

## 7. Deferred
- **Multi-currency FX conversion and settlement.** Pull forward when a tenant needs to invoice in one currency and settle in another. Single-currency accounts and a currency code on every amount make this addable later.
- **Dedicated database or region cells.** Pull forward on the first enterprise or residency contract. The shared schema is already compatible.
- **Splitting into microservices.** Pull forward when the revisit triggers in the monolith-vs-services gate trigger.
- **A second PSP and payment routing.** Pull forward when PSP coverage or fees block more than 10% of tenant revenue, or a PSP outage costs over an hour of collections.
- **Full revenue-recognition engine (ASC 606 schedules).** Ships as an export only for now. Pull forward when tenants above a set ARR band need it, or our own audit does.
- **Entitlements and feature-gating service.** Pull forward when more than 3 tenants ask to check access through our API instead of webhooks.
- **Quotes, CPQ and contract negotiation.** Pull forward when sales-led tenants become the majority of new revenue.
- **Marketplace and split payouts.** Pull forward when a tenant platform needs to pay sub-merchants. It needs a PSP Connect product and changes compliance scope.
- **Custom invoice template editor and GraphQL API.** Pull forward when it shows up in the top-3 tenant requests for two quarters running.
- **AI features (anomaly detection on usage, churn scoring).** Pull forward after Phase 6 data has been stable for 6 months. They would be read-only and outside the ledger's write path.
