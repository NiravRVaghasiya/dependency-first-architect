# Architecture and Build Plan: `photo-rename`, a CLI that renames photos by EXIF capture date

## 1. Summary

- **What:** A command-line tool for one person on their own machine. It renames every photo in a folder to its EXIF capture date, for example `IMG_4031.JPG` becomes `2024-07-14_18-03-22.JPG`.
- **Shape:** One Python package with a pipeline of small modules: **Scanner → MetadataReader → Planner → Executor (+ Journal) → Reporter**. The Planner is a pure function and holds all the decision logic. Only the Executor changes the filesystem, and all it does is rename. It never writes into a photo.
- **Key decisions:**
  1. **Dry run is the default.** `--apply` is required to change anything, and it asks for confirmation.
  2. **Existing files are never overwritten.** Name clashes get deterministic suffixes (`_1`, `_2`), and an existing file's name always counts as taken.
  3. **Every applied run writes a journal.** `photo-rename undo` reverses it exactly, even after a crash partway through.
  4. **Metadata is read through an interface.** v1 uses the pure-Python `exifread` library, and a spike checks it against real files before we rely on it.
  5. **Files with no usable date are skipped and reported.** The tool never guesses a date silently.
- **Milestone 1 (about 3–5 developer-days):** Dry run, apply and undo for JPEGs from start to finish, with CI passing on Windows, macOS and Linux. It also includes two spikes: whether the metadata library covers the formats you actually have, and how renaming behaves on each filesystem.
- **Top risks:** The library might misread or miss dates in HEIC and RAW files. Edge cases like case-only renames, exFAT SD cards and network shares could cause collisions or partial runs. Burst shots with the same timestamp could be ordered unpredictably.

## 2. Context and Goals

- **Problem:** Camera and phone file names (`IMG_4031`, `DSC00012`) don't sort by time, repeat across devices, and say nothing about when the photo was taken. Renaming by hand doesn't scale, and generic batch renamers don't read EXIF safely.
- **Goals:** Rename a folder of up to about 10,000 photos so that sorting by name puts them in capture order. It must never lose or damage a file, and every run must be reversible.
- **Non-goals (v1):** Moving files into date folders. Recursing into subfolders (deferred). Videos such as MOV and MP4, since they have no EXIF and use different metadata (deferred). Changing EXIF data or correcting camera clocks. A GUI. Removing duplicates.
- **Success measures:** No lost or overwritten files and no changed file contents in any test or real run. At least 99.5% of files with a valid date renamed correctly on the reference test set. Running the tool again on a folder it already renamed changes nothing.

## 3. Drivers, Requirements, and Constraints

**Ranked quality attributes** (all targets are assumptions until confirmed):

| # | Attribute | Measurable target | Why it matters |
|---|---|---|---|
| 1 | Data safety | No overwrites. File contents unchanged (SHA-256 checked before and after in tests). 100% of applied runs can be undone, including interrupted ones | Photos can't be replaced. One overwritten file outweighs every other benefit |
| 2 | Date correctness | ≥99.5% correct names on the reference set. 0% silently guessed dates | A wrong name is worse than no rename because it misleads |
| 3 | Predictability | `--apply` does exactly what the dry run showed. A second run does nothing. The same input always gives the same suffix order | Users must be able to trust the preview |
| 4 | Portability | Passes CI on Windows, macOS and Linux, on NTFS, APFS, ext4 and exFAT (SD cards) | Photos live on all of these |
| 5 | Performance | Dry run of 10,000 JPEGs on a local SSD in under 60 s | Fine for a batch job. Not a structural driver |

**Key functional requirements:**
- Get the capture time from `DateTimeOriginal`, fall back to `DateTimeDigitized`, and never use `DateTime`, because editing software overwrites that field.
- Use `SubSecTimeOriginal` to order burst shots.
- Show a preview, apply the plan, and undo it.
- Report skipped files with a reason.

**Constraints:**
- The workspace is empty, so this is a new build.
- The developer appears to be on Windows, judging by the paths.
- Assumed: one developer who knows Python. No budget, no hosting, no compliance rules.

**Hard parts:**
1. **Renaming safely.** POSIX `rename` silently replaces an existing target. Case-only renames behave differently across filesystems. A crash partway through leaves a folder half renamed.
2. **Reading metadata across formats.** JPEG is easy. HEIC and RAW formats (CR3 especially) differ between libraries. Sentinel values such as `0000:00:00 00:00:00` and malformed dates are common.
3. **Collisions and stable naming.** Burst shots share a timestamp, folders may already contain names in the target format, and re-runs must change nothing.

## 6. Architecture Overview

```mermaid
flowchart LR
  U[User terminal] --> CLI
  subgraph photo_rename package
    CLI --> Scanner --> Reader[MetadataReader<br/>ExifreadReader]
    Reader --> Planner[Planner - pure]
    Planner --> Reporter
    Planner -->|--apply| Executor --> Journal
    CLI -->|undo| Undo --> Journal
  end
  Scanner -. list .-> FS[(Photo folder)]
  Reader -. read headers only .-> FS
  Executor -. rename only .-> FS
  Journal -. .photo-rename-*.jsonl .-> FS
```

The trust boundary is the photo files, which are untrusted input. Only parsed integers from them ever reach a file name. Everything runs in one process with no network access.

| Component | Responsibility | Owns data | Interface | Tech | Depends on |
|---|---|---|---|---|---|
| CLI (`cli.py`) | Parse arguments, confirm, set exit codes | none | `photo-rename <dir> [--apply] [--yes]`, `photo-rename undo <dir>` | argparse | all |
| Scanner (`scanner.py`) | List candidate files and group them by base name | `SourceFile` list | `scan(dir) -> list[SourceFile]` | stdlib `os.scandir` | FS |
| MetadataReader (`metadata.py`) | Return the capture time or a reason it's missing | `CaptureTime` | `read(path) -> CaptureTime \| Missing` | `exifread` | FS |
| Planner (`planner.py`) | Work out target names, collisions and skips | `Plan` | `plan(files, times, existing_names) -> Plan` | pure Python | model only |
| Executor (`executor.py`) | Apply the Plan safely and record each step | — | `apply(plan, journal)` | stdlib | Journal, FS |
| Journal / Undo (`journal.py`) | Keep a durable record of completed renames and reverse it | journal file | JSON Lines, schema `v:1` | stdlib | FS |
| Reporter (`report.py`) | Print the plan table and summary | — | text to stdout | stdlib | — |

## 7. Component Details

- **MetadataReader.**
  - Uses `DateTimeOriginal`, then `DateTimeDigitized`. Also reads `SubSecTimeOriginal`.
  - Rejects empty values, all-zero values, and anything that won't parse as a date.
  - Catches every parser exception per file and returns `Missing(reason)`, so one corrupt file can't stop the run.
  - Reads headers only and never opens files for writing.
  - Defined as a `Protocol`, so an `ExifToolReader` (using `exiftool -json` in batch mode) can replace it without touching anything else.
- **Planner.** This is where the hard logic lives.
  - It works on `(file, capture_time)` pairs plus the set of all names already in the folder, compared case-insensitively.
  - **Stable names:** if a file's current name is already `base` or `base_N` for its own timestamp, it is left alone. This is what makes re-runs do nothing.
  - **Occupied names:** a candidate name is taken if any file currently in the folder has it, even a file that is about to be renamed. This rules out rename chains and cycles, at the cost of sometimes adding a suffix that wasn't strictly needed.
  - **Suffix order:** suffixes go in order of (sub-second, original file name). This is deterministic.
  - It does no I/O. It doesn't see the folder itself. It only receives the set of existing names from the Scanner.
- **Executor.**
  - Before each rename, it checks that the source still exists and that the target is free (case-insensitively), then calls `os.rename`.
  - On Windows, `os.rename` itself refuses to overwrite. On POSIX the remaining check-then-rename race is accepted, because we assume nothing else writes to the folder.
  - Case-only renames go through a temporary name if Spike B shows they're needed.
  - **On any OS error it stops.** The journal is left complete up to that point. The user can then re-run, which picks up where it stopped because re-runs skip finished files, or run `undo`.
- **Journal.**
  - Before the first rename it writes a header with the tool version, start time and folder.
  - After each successful rename it appends `{"from","to"}`, then flushes and `fsync`s.
  - The file sits in the photo folder as `.photo-rename-YYYYMMDD-HHMMSS.jsonl`, and the Scanner excludes it.
  - **Undo** reverses the recorded steps from last to first. It refuses to restore a name that is now taken, and finally appends `{"undone": true}`.
- Scaling isn't a driver. Everything is one pass and in memory.

## 8. Data Design

- **Entities** (frozen dataclasses in `model.py`):
  - `SourceFile` (path, name, ext, group stem)
  - `CaptureTime` (naive datetime, subsec, source tag)
  - `RenameOp` (src, dst)
  - `Skip` (file, reason: `NO_DATE`, `UNREADABLE`, `ALREADY_NAMED`, `UNSUPPORTED`)
  - `Plan` (ops, skips)
- **System of record:** the filesystem for names and the journal for history. The Executor is the only component that writes to either. There is no database.
- **Consistency:** each rename is atomic. A run as a whole is not, so the journal plus undo, together with re-runs being safe, provide recovery.
- **Retention:** journals stay until the user deletes them. Deleting a journal means that run can no longer be undone, and the README says so.
- **Sensitivity:** EXIF can contain GPS coordinates and serial numbers. The tool never logs or stores them. Journals contain only file names.
- **Schema evolution:** journal lines carry `"v":1`, and later versions must still read v1.

## 9. Key Flows

1. **Dry run (default):** `photo-rename D:\Photos\Trip`
   1. Scan the folder.
   2. Read each file's capture time.
   3. Build the Plan.
   4. Print the table and a summary, for example "812 to rename, 14 already named, 3 skipped (no date)".
   5. Exit with code 0. Nothing changes on disk.
2. **Apply:** `--apply`
   1. Build the same Plan as the dry run (it's deterministic).
   2. Show the summary and ask `Rename 812 files? [y/N]`, unless `--yes` was given.
   3. Write the journal header.
   4. For each operation: check preconditions, rename, append to the journal and fsync.
   5. Print the summary and exit with code 0.
3. **Failure path: interrupted run.** The disk is pulled out at operation 400 of 812.
   1. The rename for operation 401 raises `OSError`.
   2. The Executor stops, prints "400 of 812 renamed; journal at …; run again to continue or `photo-rename undo`", and exits with code 3.
   3. Running again finds 400 files already correctly named, skips them, and plans 412.
   4. Running `undo` instead restores the 400 renamed files to their original names, last to first.
4. **Failure path: corrupt or date-less file.** The reader returns `Missing(UNREADABLE)` or `Missing(NO_DATE)`. The file appears under "Skipped", stays untouched, and the run continues.

## 11. Cross-Cutting Concerns

- **Security** (M1):
  - Photos are untrusted input. New names are built only from parsed integers, so EXIF text can't reach a path (no path traversal or name injection).
  - Symlinks and non-regular files are skipped.
  - Parser exceptions are caught per file.
  - CI runs `pip-audit` (M3).
- **Reliability** (M1): no-overwrite checks, fsync'd journal, undo, safe re-runs, and stop-on-error. These are covered under Executor in Section 7.
- **Observability** (M1, M2):
  - The summary always prints counts plus skip reasons.
  - `--verbose` logs each file's chosen tag and value.
  - `--json` output for scripting is deferred.
- **Performance** (M2): reads headers only, in one pass. A 10,000-file benchmark runs in CI as an informational job.
- **Cost:** none.
- **Operations:** the user runs it themselves. Support means the README, the `--verbose` output and the journal file. Releases are tagged on PyPI (M3).
- **AI-specific:** not applicable. There are no model components.

## 14. Testing and Validation Strategy

- **Unit and property tests** (planner, reader) cover correctness and predictability. Hypothesis checks the invariants listed in T6.
- **Fault-injection tests** (executor, undo) cover safety. They also assert that file hashes are unchanged.
- **E2E tests in `tmp_path`** run on the 3-OS CI matrix and cover portability.
- **Test data:**
  - Synthetic JPEGs generated with `piexif`, committed as generator code.
  - A small reference set of real HEIC and RAW files from the user. These are private, so keep them out of the repo and run them locally or from a private store.
- **Release blockers:** all CI jobs green, and ≥99.5% correct on the reference set. The 10k benchmark is informational only.

## 15. Rollout, Migration, and Rollback

- **Rollout:** no data migration and no existing system. Users roll out by trying the dry run, then applying to a copied folder, then to real folders. The README recommends this order.
- **Rollback for users:** `photo-rename undo` works for as long as the journal file exists. Deleting it removes the ability to undo.
- **Rollback for the tool:** pin the previous version with pipx. Journal schema `v1` stays readable by later versions.
