# Plan — Multi-Tenant SaaS Billing System

## 1. Classification
- **What:** A billing platform that is itself multi-tenant SaaS. Each tenant (a business) defines its own catalog and bills its own customers for subscriptions and metered usage. The platform produces invoices, collects payments, handles dunning and reconciles against the payment processor. The hierarchy is `Platform → Tenant → Customer account → Subscription → Charges → Invoice → Payment`.
- **Type:** Software (with some infra). No AI.
- **Dominant constraint:** **Correctness**, with compliance close behind (PCI scope, tax, invoice numbering rules, audit trail).
- **Worst failure:** Money moves wrong and nobody notices: a double charge, a charge to the wrong tenant's customer, or one tenant seeing another tenant's data. Every major decision below is ranked by how well it prevents this or makes it detectable and reversible.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| **Consistency vs availability** | **Split.** The ledger, invoices and payments favour consistency: a single-writer Postgres (RDS/Aurora) with ACID transactions and `SERIALIZABLE` isolation on ledger postings. Usage ingestion favours availability: accept, store durably, acknowledge, and rate later. | Ledger: no flip to eventual consistency. If multi-region writes become necessary (latency or data residency), shard by region with each tenant pinned to one home region. Ingestion: none needed, it is already the available side. |
| **Monolith vs services** | **Modular monolith**, one deployable, with enforced module boundaries (`tenancy`, `ledger`, `catalog`, `subscriptions`, `invoicing`, `payments`, `usage`, `notifications`). Modules talk only through internal interfaces and outbox events, with no reads across module tables. Lint rule plus ArchUnit-style tests. | Extract `usage` first if it sustains more than ~5k events/s or needs its own scaling or deploy cadence. Extract any other module only when a separate team owns it. |
| **Sync vs async** | **Sync** for commands that change money state (create subscription, finalize invoice, post to ledger). **Async** via a transactional outbox → SQS for anything that calls outside systems (payment processor, tax, email, tenant webhooks) and for batch work (billing runs, dunning, rating). | If p99 of a synchronous command goes over 500 ms because of an internal dependency, move that dependency behind the outbox. Never make ledger posting async. |
| **Build vs buy** | **Buy:** payment processing and card storage (Stripe/Adyen via tokenization, which keeps us at PCI SAQ-A), tax calculation (Stripe Tax/Avalara), email delivery (SES/Postmark). **Build:** ledger, catalog, subscription engine, rating, invoicing, dunning and reconciliation. These are the product. | If the real requirement is internal billing with only flat or per-seat pricing and no usage, buy Stripe Billing, Chargebee or Orb and drop this plan. If a second processor is needed (regional coverage, lower fees), add a `PaymentProvider` adapter. The interface is defined in Phase 0. |
| **Tenant isolation model** | **Pooled.** Shared database and schema, `tenant_id` on every row, Postgres row-level security enforced by a non-`BYPASSRLS` app role, and the tenant context set per transaction (`SET LOCAL app.tenant_id`). | An enterprise contract requires a dedicated database or data residency: add a "silo" tier that runs the same code against a per-tenant database, chosen through a tenant→connection routing table that exists from Phase 1. |
| **Money representation** | Integer minor units (`BIGINT`) plus an ISO-4217 currency on every amount. Unit prices use `NUMERIC(38,12)` so sub-cent usage prices work. Rounding happens once, at the invoice line, using a documented mode (banker's rounding). Floats are banned by a lint rule. | None. This cannot be reversed cheaply once real invoices exist. |
| **Ledger model** | Double-entry, append-only and immutable. Corrections are reversing entries, never `UPDATE`. Invariant: every journal entry nets to zero per currency. | None. |
| **Currency scope** | One currency per customer account at launch. The schema carries currency everywhere from day zero. | A tenant needs mixed-currency accounts or FX conversion. Add FX rate snapshots per invoice; the schema already allows it. |
| **Time model** | Store everything in UTC. Billing-period boundaries are computed in the tenant's or customer's timezone. Everything reads time from an **injectable billing clock**, never `now()`. | None. The clock is what makes billing deterministic and testable. |
| **Region / data residency** | One region (`us-east-1`), with a `home_region` column on tenants. | First EU or other contract that requires residency: stand up a second regional cell and route by `home_region`. |
| (AI) prompt+RAG vs fine-tune | N/A: there is no AI component. | Not applicable. |
| (AI) hosted API vs self-host | N/A: there is no AI component. | Not applicable. |

## 3. First end-to-end slice (Phase 0)
**The one real request:** An internal dogfood tenant calls `POST /v1/invoices` with an `Idempotency-Key` header for one customer on one hard-coded flat price ($1.00 USD). The response is `201` with invoice JSON (`id`, `number`, `total: 100`, `currency: usd`, `status: open`). The payment then runs async through Stripe, and `GET /v1/invoices/{id}` returns `status: paid` after the webhook arrives. In production the first run uses Stripe test-mode keys. Once that passes, run one live $1 charge on an internal card and refund it.

**Tiers crossed:**
1. **Edge:** ALB with TLS. API-key auth; keys are stored hashed and resolve to `tenant_id`.
2. **App:** the monolith (Go on ECS Fargate). It sets the tenant context, enforces idempotency, and in **one transaction** writes the invoice row, a two-line journal entry (debit `accounts_receivable`, credit `revenue`) and an outbox row.
3. **Data:** Postgres with RLS on from the first table.
4. **Async:** an outbox relay sends to SQS. A worker calls the Stripe PaymentIntent API through a `PaymentProvider` interface.
5. **Inbound:** the Stripe webhook endpoint verifies the signature, then posts the payment journal entry (debit `cash_clearing`, credit `accounts_receivable`) and marks the invoice paid.

**Day-zero deploy, logs and monitoring:**
- **Deploy:** Terraform for all infrastructure. GitHub Actions builds the image, runs migrations, does a blue/green deploy, and smoke-tests the skeleton request after each deploy.
- **Logs and traces:** OpenTelemetry traces span HTTP → DB → outbox → SQS → worker → Stripe → webhook, all under one trace ID. Structured JSON logs carry `trace_id`, `tenant_id`, `idempotency_key` and `invoice_id`.
- **Metrics:** RED metrics on the API; `invoices_created_total`; `payments_succeeded/failed_total`; outbox lag.
- **The billing alarm:** a `ledger_imbalance` gauge, computed every minute as the sum of debits minus credits per currency. It must be 0; anything else pages someone.

**Exit check:** In production, the request returns a real invoice. Its trace shows every tier including the webhook. `invoices_created_total` increments on the dashboard. `ledger_imbalance = 0`. Replaying the same `Idempotency-Key` returns the same invoice and creates no second charge.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

**Phase 0 — First end-to-end slice** (above)
- Unlocks: a deployable, observable spine with money flowing end to end.
- Depends on: nothing.

**Phase 1 — Tenancy, identity and the money substrate**
- Unlocks: every later module can safely store tenant-scoped financial data.
- Depends on: the Phase 0 spine being proven in production.
- Tasks, widest impact first:
  1. **Tenant isolation model.** `tenant_id` and RLS policies on every table, plus the tenant→connection routing table (needed later for silo tenants). Every future table inherits this.
  2. **Ledger schema and posting API.** Accounts chart per tenant, journal entries and lines, the balance invariant enforced by a DB constraint/trigger and by the posting API. Immutable.
  3. **Money and currency types.** A shared library with the lint rule against floats.
  4. **Idempotency and outbox framework.** The generic `idempotency_keys` table, which stores the request hash and response. A versioned outbox event envelope (`event_id`, `tenant_id`, `type`, `schema_version`, `occurred_at`, `payload`). Tenants will see this envelope later as their webhook format.
  5. **Authentication and authorization.** API keys with scopes (`full`, `read`, `ingest-only`). Dashboard users via OIDC. RBAC roles (owner, admin, finance, read-only).
  6. **Audit log.** Append-only record of who did what to which object, before and after.
  7. **Tenant onboarding API.** Leaf work.
- Exit check:
  - A cross-tenant isolation test suite runs in CI and finds zero leaks. It fuzzes every endpoint with tenant B credentials against tenant A objects, and also runs queries with RLS forced on.
  - Ledger property tests pass, with fixed seeds and 10k random postings: entries always balance and nothing can be updated or deleted.
  - Restoring the database from a backup succeeds.

**Phase 2 — Catalog and subscriptions (the contract layer)**
- Unlocks: knowing what each customer owes and for which period.
- Depends on: tenancy and ledger, proven by the Phase 1 exit checks.
- Tasks, widest impact first:
  1. **Price versioning.** Products and prices become **immutable once referenced**; changes create a new version. Past invoices stay reproducible forever.
  2. **The `Charge` contract.** The generic output of anything billable: `source`, `price_version`, `quantity` as a decimal, `period`, `amount`. Invoicing and usage both depend on it. Before freezing it, validate it with a spike that uses synthetic tiered and sub-cent usage charges.
  3. **Subscription state machine.** `trialing → active → past_due → canceled / paused`. Transitions are explicit and each one emits an event.
  4. **Billing clock and period engine.** Anchors, calendar vs anniversary billing, timezones, month-end edge cases (Jan 31 → Feb 28).
  5. **Proration rules.** Upgrade, downgrade, mid-cycle quantity changes.
  6. **Plan-change and cancel APIs.**
- Exit check: A test-clock simulation of 1,000 subscriptions over 24 simulated months, with random plan changes, produces charges that match committed golden files exactly. Running it twice gives byte-identical results.

**Phase 3 — Invoicing and tax**
- Unlocks: legally valid invoices that the payments phase can collect on.
- Depends on: the `Charge` contract and the period engine, proven in Phase 2.
- Tasks, widest impact first:
  1. **Invoice lifecycle.** `draft → finalized (immutable) → paid / void / uncollectible`. Finalizing posts to the ledger.
  2. **Invoice numbering.** Per tenant, gap-free and sequential, allocated at finalization in the same transaction. EU rules require this.
  3. **Scheduled billing runs.** Resumable and checkpointed per subscription, sharded per tenant.
  4. **Tax integration.** Quote at draft, commit at finalize. The tax quote is stored as a snapshot.
  5. **Credit notes.** Corrections are reversing entries, never edits.
  6. **Rendering.** Deterministic PDF/HTML from stored invoice inputs.
  7. **Invoice emails.** Leaf work.
- Exit check:
  - A completeness check passes: the number of invoices generated equals the number of subscriptions due, per run.
  - Re-rendering any finalized invoice from stored inputs reproduces the same document.
  - A sample of invoices reconciles exactly with the tax provider's transaction log.

**Phase 4 — Payments, collections and reconciliation**
- Unlocks: cash collected, and cash proven to match the books.
- Depends on: finalized invoices and ledger postings, proven in Phase 3.
- Tasks, widest impact first:
  1. **Payment state machine and provider idempotency.** A provider timeout means the outcome is *unknown*: query the PaymentIntent status before retrying, and never retry a charge blind.
  2. **Webhook ingestion.** Verify the signature and store the raw payload, then process idempotently and in order per object.
  3. **Daily reconciliation.** Match ledger `cash_clearing` against provider balance transactions and payouts. Any mismatch goes to an exceptions queue.
  4. **Refunds and disputes.** Each posts reversing ledger entries.
  5. **Dunning.** A configurable retry schedule per tenant, and on exhaustion the subscription moves to `past_due` and then `canceled`.
  6. **Payment-method management.** Tokenized only, through Stripe Elements or Checkout.
  7. **Receipt and failure emails.** Leaf work.
- Exit check:
  - 7 consecutive days of reconciliation with zero unexplained differences.
  - A chaos test passes: inject a provider timeout, a duplicate webhook and an out-of-order webhook, with 0 double charges and an unchanged ledger balance.

**Phase 5 — Usage metering and rating**
- Unlocks: usage-based and hybrid pricing.
- Depends on: the `Charge` contract and subscriptions (Phase 2), and invoicing, proven in Phase 3.
- Tasks, widest impact first:
  1. **Event schema and dedupe contract.** The tenant supplies `event_id`; the guarantee is at-least-once in, exactly-once rated.
  2. **Durable ingestion path.** `POST /v1/usage` writes to SQS and then to a partitioned Postgres raw-event table, and acknowledges only after the durable write.
  3. **Late-event policy.** Events arriving before period close are rated normally; events arriving after it become adjustment charges on the next invoice.
  4. **Aggregation per meter and period.** Sum, max, unique count, last value.
  5. **Rating engine.** Per-unit, tiered, volume and package pricing; the output is a `Charge`.
  6. **Usage-preview API.** Leaf work.
- Exit check:
  - Injecting 1% duplicate events gives rated totals exactly equal to an independent recompute from the raw events.
  - Ingestion p99 lag stays under 60 s at 3× the projected peak load.
  - Re-rating a closed period from raw events produces identical charges.

**Phase 6 — Tenant-facing surfaces**
- Unlocks: tenants can self-serve, and their customers get a portal.
- Depends on: every domain module above, proven by their exit checks. The UI only sits on top of APIs that already work.
- Tasks, widest impact first:
  1. **Outbound webhooks to tenants.** Public, versioned event contracts using the Phase 1 envelope.
  2. **Public API docs and SDKs**, generated from OpenAPI.
  3. **Tenant dashboard.** Catalog, customers, invoices, reconciliation exceptions.
  4. **Hosted invoice page and customer portal.** Signed, expiring URLs.
  5. **Reporting.** MRR, churn, AR aging, all read from ledger projections.
  6. **Branding and theming.** Leaf work.
- Exit check:
  - A pilot tenant onboards, configures a plan, bills a real customer and receives webhooks with no help from us.
  - Webhook delivery success is at least 99.9% over 7 days.

## 6. AI layer
**N/A.** This system has no AI or agentic component. Possible later AI features, such as churn prediction or anomaly detection on invoices, are listed under deferred work and would need their own AI-layer pass before being built.

## 7. Deferred
| Not building yet | Pull it forward when |
|---|---|
| **Silo tenancy** (dedicated DB per tenant) | An enterprise deal requires it contractually. The routing table already exists from Phase 1. |
| **Multi-region / EU cell** | The first contract that requires data residency. |
| **Extracting usage into a separate service; Kafka + ClickHouse** | More than ~5k events/s sustained, more than ~1B events per month, or Postgres partitions hurt query p99. |
| **Multi-currency accounts and FX** | A tenant needs mixed-currency customers. |
| **Full revenue recognition (ASC 606 schedules)** | A tenant's auditor requires it, or we sell to public-company finance teams. The ledger already has deferred-revenue accounts. |
| **Exports to accounting systems** (NetSuite, QuickBooks, Xero) | 3 or more pilot tenants ask for the same integration. |
| **Second payment processor / routing** | A region the current processor doesn't cover, or fees above an agreed threshold. The `PaymentProvider` interface already exists. |
| **Quotes, contracts and CPQ** | Tenants selling sales-led enterprise deals need negotiated pricing. |
| **Entitlements and feature gating** | Tenants ask to gate product features on plan state. Subscription events already carry what's needed. |
| **AI features** (churn prediction, invoice anomaly detection) | Enough history exists to train on, and there is a clear user. Requires a full AI-layer pass first. |
| **SOC 2 Type II audit** | The first enterprise security review asks for it. The controls are already in place from Phase 0 onward. |
