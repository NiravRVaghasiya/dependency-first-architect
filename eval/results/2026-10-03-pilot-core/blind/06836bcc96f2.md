# Plan: Autonomous GitHub Issue Triage and Resolution Agent

## 1. Goals and scope

**Goals**
- Give every new issue a useful first response within minutes: labels, a duplicate check, requests for missing info, and routing to the right owner.
- Resolve issues that are well-scoped and low-risk by opening a tested pull request (PR) that a human reviews.
- Lower maintainer workload without letting the agent make changes nobody approved.

**Out of scope (at first)**
- Merging PRs, releases, or deploys.
- Closing issues where people disagree.
- Making design decisions.
- Handling security disclosures publicly.

## 2. High-level architecture

```
GitHub (webhooks) ──► Event Ingest ──► Queue ──► Orchestrator
                                                  │
              ┌───────────────────────────────────┼─────────────────────┐
              ▼                                   ▼                     ▼
        Triage Agent                     Resolution Agent        Follow-up Agent
   (classify, dedupe, route)         (reproduce, fix, open PR)  (CI failures, review
              │                                   │               comments, stale)
              ▼                                   ▼
        GitHub API (scoped)             Sandbox Runner (ephemeral container)
              │                                   │
              └──────────► State Store + Audit Log ◄──────────┘
                         Vector Index (issues, code, docs)
```

**Components**
| Component | Responsibility |
|---|---|
| **GitHub App** | Least-privilege identity: write access to issues and PRs, write access to contents only on `agent/*` branches, no admin. |
| **Event ingest** | Receives `issues.opened/edited`, `issue_comment`, `labeled`, `pull_request_review`, and `check_suite` events. Checks webhook signatures and drops duplicate deliveries. |
| **Queue** | Per-repo ordering, retries, backpressure, dead-letter queue. |
| **Orchestrator** | Runs the issue state machine. Picks which agent to run and enforces budgets (steps, tokens, wall-clock time, $ per issue). |
| **State store** | Issue state, attempt history, and decisions with rationale (Postgres). Labels mirror the state so humans can see it. |
| **Vector index** | Embeddings of past issues, PRs, docs, and code, used for dedupe and to find relevant code. |
| **Sandbox runner** | Throwaway container per attempt: repo clone, dependencies, test runner. Network access only to an allowlist, no secrets. |
| **Policy engine** | Config-driven rules for which repos, labels, and paths are eligible and which actions need human approval. |

## 3. Issue state machine

```
NEW → TRIAGED → (NEEDS_INFO ⇄ TRIAGED) → ELIGIBLE → IN_PROGRESS → PR_OPEN → DONE
                     │                       │             │            │
                     ▼                       ▼             ▼            ▼
                  DUPLICATE             HUMAN_OWNED     ABANDONED   REVISING
```
Each transition is logged with the inputs, the model output, the confidence score, and the action taken.

## 4. Triage pipeline (runs on every issue)

1. **Sanitize and parse:** Strip or flag possible prompt injection. Extract stack traces, versions, OS, and repro steps.
2. **Security screen:** Look for vulnerability reports, leaked secrets, or personal data. If found, hide or escalate to the security team, apply a private label, and post no public analysis.
3. **Spam and abuse filter.**
4. **Duplicate detection:** Search the vector index for similar issues, then have an LLM confirm the match. If it's confident (for example >0.9), comment with a link and label `possible-duplicate`. Never auto-close without a human, at least at first.
5. **Classification:** Type (bug, feature, question, docs, chore), area/component, severity, and confidence. Use structured output against a label set loaded from the repo.
6. **Completeness check:** If repro steps, version, or logs are missing, post a templated, specific request for them → `NEEDS_INFO`. After N days with no reply, nudge, then hand to a human.
7. **Routing:** Assign owners from CODEOWNERS plus history of who touched the relevant files. Answer questions with links to docs.
8. **Resolution eligibility score**, based on:
   - Clear repro or acceptance criteria
   - Likely small diff
   - Touches paths that aren't sensitive (not auth, crypto, billing, migrations)
   - Test suite exists
   - Repo has opted in
   
   Issues above the threshold → `ELIGIBLE`, or wait for a maintainer to add an `agent:fix` label (the recommended default).

## 5. Resolution pipeline (eligible issues only)

1. **Set up the sandbox:** Clone at the default branch HEAD, install dependencies from cache, and run the baseline tests to learn which tests were already failing.
2. **Find the relevant code:** Use stack traces, symbol search, embedding search, and `git blame`/history to collect candidate files.
3. **Reproduce:** Write a failing test (or script) that captures the bug. If it can't reproduce the bug, stop. Comment with what it found and hand off to a human. This step is the main protection against "fixes" that fix nothing.
4. **Plan:** Write a short plan of the root cause and the intended change, kept for the PR description and the audit log.
5. **Implement:** Make small edits through file-edit tools. Follow repo conventions (lint config, style examples).
6. **Verify:**
   - The new test passes.
   - The full or affected test suite passes, with no new failures compared to the baseline.
   - Lint, type checks, and build pass.
   - Diff-size and allowed-path policy checks pass.
7. **Self-review:** A separate critic pass checks the diff against the issue, looks for unrelated changes, unhandled edge cases, and missing tests, and confirms nothing was hard-coded to make the test pass.
8. **Open a draft PR** on an `agent/issue-<n>` branch with:
   - A link to the issue and a root-cause explanation
   - What changed and how it was tested
   - A confidence score and known limitations
   
   Request reviewers from routing.
9. **Retry limits:** At most K attempts (for example 3), each starting from a fresh sandbox. If they all fail, post a summary of findings to the issue. A partial diagnosis is still useful.

## 6. Follow-up agent

- **CI fails:** Read the logs and push fixes, up to M times.
- **Review comments:** Address the requested changes, reply to each thread, and re-request review. Only respond to users with write access.
- **Staleness:** Rebase when there are conflicts. If a PR is idle for X days, ping the reviewers, then close and leave a note.
- **After merge:** Confirm the issue was closed through the PR link, and record the outcome for evaluation.

## 7. Agent tools (all logged)
- `github.*`: read issues and PRs, comment, label, assign, open PRs. No merge, no deleting branches other than its own.
- `search_code`, `search_issues` (vector + lexical), `read_file`, `git_log/blame`
- `edit_file`, `run_command` (sandbox only, with timeouts), `run_tests`
- `ask_human`: posts a question to the issue and pauses the state machine

## 8. Safety and guardrails
- **Prompt injection:** Treat issue and comment text as untrusted data, never as instructions. Keep the system policy separate from user content. Commands from comments are honored only from users with write access, and only through fixed keywords (`/agent fix`, `/agent stop`).
- **Least privilege:**
  - Short-lived tokens; branch protection prevents the agent from pushing to protected branches.
  - Workflows on agent PRs need maintainer approval to run with secrets.
- **Sandbox isolation:** No credentials, egress limited to package registries, CPU/memory/time limits, destroyed after each run.
- **Path deny-list:** Never edit CI workflows, `CODEOWNERS`, security-sensitive modules, or lockfiles unless the change is explicitly allowed.
- **Rate limits:** Caps on comments and PRs per repo per day, and a global kill switch (a `agent:paused` label on the repo or a config flag).
- **Transparency:** Every comment and PR is clearly marked as from the agent and links to its reasoning trace.
- **Cost controls:** Per-issue and per-repo budgets, with cheaper models for classification and stronger ones for resolution.

## 9. Evaluation

**Offline (before launch):** Replay historical closed issues. Check triage labels against the labels maintainers actually applied. For resolution, use a SWE-bench-style setup: check out the commit before the fix and run the hidden tests from the real fix PR.

**Online metrics**
| Area | Metric |
|---|---|
| Triage | Label precision/recall, how often maintainers relabel, duplicate precision, time to first response |
| Resolution | PR merge rate, reviewer rounds per PR, revert or regression rate within 30 days, share of issues reproduced |
| Experience | Maintainer satisfaction (thumbs up/down on agent comments), reporter reply rate on info requests |
| Ops | Cost per issue, latency, failure and timeout rates |

## 10. Rollout phases
1. **Shadow (2–4 wks):** Triage runs silently and decisions are only logged. Compare them against what humans did.
2. **Suggest:** Post triage suggestions as comments. A human applies the labels.
3. **Auto-triage:** Apply labels, dedupe links, and info requests automatically. Still no closing.
4. **Opt-in fixes:** Resolution runs only on issues labeled `agent:fix` and opens draft PRs.
5. **Auto-eligible:** The agent picks eligible issues itself in opted-in repos, once the merge rate passes a target (for example >50%) and the revert rate stays below a threshold.

## 11. Main risks and mitigations
| Risk | Mitigation |
|---|---|
| Plausible but wrong fixes | Require a failing test before the fix, a critic pass, mandatory human review, and track reverts |
| Noise annoys maintainers | Comment rate limits, high confidence thresholds, and opt-in per repo |
| Prompt injection or supply-chain attack | Untrusted-input handling, sandbox without secrets, no workflow edits, CI that needs approval |
| Flaky tests mislead the agent | Baseline run plus re-running failing tests to detect flakiness |
| Cost overruns | Budgets per issue, model tiering, early exit when it can't reproduce |
