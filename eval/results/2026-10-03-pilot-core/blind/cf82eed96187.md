# Plan: Autonomous GitHub Issue Triage and Resolution Agent

## 1. Classification and constraints
- **What:** A GitHub App agent. It triages new issues (labels, duplicate detection, requests for a reproduction). When a maintainer asks it to, it tries a fix in a sandbox and opens a **draft PR from its own fork** for a human to review.
- **Type:** AI-agentic plus software. The agent is new, but it acts inside existing repos, CI, and maintainer workflows, so it is brownfield at the boundary. This is not a small build: it acts on the world, takes input from outside users, and spends money.
- **Dominant constraint:** Correctness and security. The system's own uptime matters much less.
- **Worst failure:** A prompt-injected issue makes the agent leak secrets, either the GitHub token or CI secrets through code it wrote, or get malicious code into a repo's supply chain. Close behind: a comment the agent posts sets off an existing ChatOps or label-triggered workflow.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Webhook ack | < 10 s, then hand off to a queue | REQUIREMENT: GitHub webhook delivery timeout | V0 |
| Triage latency | p95 ≤ 5 min from issue opened to a triage proposal | ASSUMPTION: maintainers triage within hours today; confirm with pilot maintainers | V0 floor; Phase 2 exit |
| Resolution attempt | ≤ 45 min wall clock, hard kill at 60 min | ASSUMPTION: bounds sandbox cost; similar to CI length | Phase 3 exit |
| Throughput (issue volume) | Measured from the pilot repo's issue history via API | BASELINE (Phase 0); per repo in each Phase 5 wave | V0, Phase 5 |
| Availability | No SLO. At-least-once processing; a reconciliation sweep catches missed webhooks within 1 h | ASSUMPTION: an async helper, not on anyone's critical path | Phase 1 exit |
| AI cost: triage | ≤ $0.05 per issue typical, $0.25 hard cap | ASSUMPTION: small model, a few thousand tokens | V0 baseline; Phase 2 exit |
| AI cost: resolution | Hard cap of $5 and 40 tool iterations per attempt | ASSUMPTION: stops runaway loops; re-set from the Phase 3 baseline | Phase 1 exit (cap fires); V7 |
| AI cost: daily org cap / cost per merged PR | — | UNKNOWN: needs the spend ceiling and loaded maintainer hourly cost from the budget owner / engineering manager, before Phase 4 | V7 |
| Maintainer review time per agent PR | — | UNKNOWN: no baseline exists; measured on the canary | V7 |
| Resource use | 1 sandbox per attempt (4 vCPU / 8 GB), concurrency cap 5 | ASSUMPTION: pilot volume; re-set from the Phase 0 baseline | Phase 3 exit |
| Storage | Traces kept 30 days, then counts only; traces carry the source repo's classification | ASSUMPTION: enough for debugging and eval mining | Phase 2 exit |

**Missing inputs.** The phase order rests on these assumptions:
1. **Autonomy ceiling.** Assumed: the agent never merges, closes issues, or touches workflow files, and a human merges every PR. If autonomous merge is required, a new gate goes before Phase 5 and branch-protection design moves into Phase 1.
2. **Repo scope.** Assumed: the pilot is one public repo the org owns, so code and issues are already public. If the pilot has to be private, V1 blocks Phase 0 instead of Phase 4.
3. **Hosted model for source code.** Assumed acceptable under zero-retention and no-training terms (pending V1). If refused, private repos need a self-hosted model and model access gets re-planned.
4. **People.** An org admin to install the App and set rulesets (blocks Phase 0). Pilot maintainers to label about 300 historical issues and review agent PRs (starts in Phase 0, needed by Phase 2). A security lead for V2 and V3. A budget owner for V7's inputs.
5. **Repo CI shape.** Whether tests run without secrets or live services. If they don't, resolution can't verify itself on that repo (V5).

**Inherited constraints** (not changed by this plan):
- GitHub stays the system of record for issues and PRs.
- Each repo's CI, CODEOWNERS, and branch protection stay as they are.
- GitHub API rate limits per installation apply.
- Changing any of these means a change request per repo.

**minor defaults:**
- Consistency vs availability → at-least-once delivery plus an idempotent executor (key = event ID + action hash).
- Sync vs async → ack the webhook, then queue (SQS).
- Monolith vs services → one deployable (receiver + worker processes) plus sandbox tasks.
- Orchestration → a single agent loop with tools, not multi-agent.
- Code retrieval → agentic ripgrep / tree-sitter symbol search, no vector index.
- State store → Postgres (jobs, approvals, audit log).
- Approval UI → Slack interactive message bound to the action hash.

**N/A:** Migration strategy, cutover, and decommissioning don't apply; nothing is being replaced. Existing repos and CI are inherited constraints (§2).

## 4. First end-to-end slice (Phase 0)
- **Request → response:**
  - An allow-listed internal author opens a real issue on the public pilot repo.
  - The agent posts **one triage comment**: a summary, suggested labels from a fixed list, and the result of a default-branch test run.
  - Only one label is applied: `triage/agent-seen`.
- **Tiers:**
  - GitHub webhook → receiver (HMAC check, ack < 10 s) → SQS → worker.
  - Model gateway (hard caps: 8k tokens, $0.25, 1 call). Issue text sits in a delimited untrusted-data block.
  - Sandbox: an ephemeral Fargate task in a no-egress subnet. It clones the repo read-only at HEAD and runs the test command.
  - Executor (holds the token; filters out URLs, images, `/commands`, and secrets) → GitHub comment → Postgres audit row.
  - **The PR tier runs in dry-run mode:** the diff is stored as an artifact and never pushed, until V3 passes.
- **Deploy:** GitHub Actions builds a signed image pinned by digest, and Terraform deploys to ECS Fargate, RDS Postgres, and SQS. Prompt, model ID, and tool schemas are versioned in git and stamped on every trace.
- **Logging/monitoring:**
  - One OpenTelemetry trace per issue across all tiers.
  - Token and $ metrics per call.
  - Alerts on worker error rate, dead-letter queue depth, and cap hits.
  - Traces are stored with the pilot repo's classification.
- **Rollback:**
  - Redeploy the previous image digest.
  - Global kill switch `agent.enabled`, checked by the executor before every write.
  - Last resort: uninstall the App.
- **Phase 0 also does:**
  - Inventory the pilot repo's workflows and bots (§2).
  - Pull the issue-volume baseline.
  - Start the organizational lead-time items: maintainer labeling, the V1 review, the budget-owner inputs.
- **Who can reach it:** Only issues from an author allow-list on one pilot repo, behind a flag. Every other issue is ignored and logged.

**Exit check V0:**
- A real issue gets its comment with one trace across every tier.
- A deploy and a rollback both succeed through the pipeline.
- An injected failure (gateway 500, sandbox timeout) fires an alert.
- The kill switch blocks a write.
- Baselines are recorded: time to triage, $ per triage, sandbox test runtime, pilot issue volume.

## 5. Phases

- **Phase 1: Defenses and trust boundary**
  - Unlocks: the agent may process issues from any author and push code (once V3 passes).
  - Depends on: V0.
  - Tasks (widest rework first):
    1. App permission set and rulesets (bot can't approve, has no `workflows` scope, can't push to the target repo).
    2. Bot fork and fork-PR workflow approval.
    3. Sandbox egress: deny all except the model gateway and a read-only package-registry mirror; block the cloud metadata endpoint.
    4. Executor policy-as-code: a typed action schema, tool allow-list, argument validation, and a label allow-list that excludes every label wired to a workflow.
    5. Output filter: no external URLs or images, no ChatOps commands, gitleaks on all outbound text and diffs, block changes to `.github/` and binary files.
    6. Caps: per call, per attempt, per author per hour, per repo per day, plus a spend auto-pause.
    7. Approval service: Slack approval bound to the action hash and enforced by the executor.
    8. Injection suite in CI.
  - Rollback: policies and caps are git-reverted config. No point of no return.
  - Exit check: V2 and V3 pass. A synthetic runaway loop is cut off at the cap and emits a metric. The reconciliation sweep replays a dropped webhook.

- **Phase 2: Triage (retrieval + model access)**
  - Unlocks: triage on all pilot-repo issues; autonomous labels after V4.
  - Depends on: Phase 1, V2.
  - Tasks:
    1. Duplicate index: embeddings of issue titles and bodies, partitioned by repo, embedding model pinned in the index version.
    2. Context retrieval: CONTRIBUTING, label definitions, code search tools.
    3. Gateway hardening: structured-output validation, retries, a fallback model, static model choice per task.
    4. Build-vs-buy bake-off.
    5. Two weeks of shadow mode, then V4.
    6. Then: allow-listed labels go autonomous. Comments stay approval-only.
  - Rollback: flag back to approval mode. Agent labels live under `triage/*` and a script removes them.
  - Exit check: V4 passes. Triage p95 latency and $ per issue are within budget at the baseline volume.

- **Phase 3: Resolution (memory + orchestration)**
  - Unlocks: draft PRs on the pilot repo, triggered by `agent:fix`.
  - Depends on: Phase 2, V3; V5 and V6 inside this phase.
  - Tasks:
    1. Per-repo sandbox image and V5.
    2. Agent loop: read, search, edit, test, iterate, with every step traced.
    3. Memory: per-issue attempt state in Postgres. Long-term repo notes live only in a maintainer-reviewed `.github/agent.md`; the agent can't write long-term memory itself.
    4. Diff gate: secrets, `.github/`, binaries, and dependency changes are flagged.
    5. V6 offline replay.
    6. Live: push to fork, open a draft PR with linked issue and test log. The agent closes its own PRs after 14 days idle.
  - Rollback: flag off; close agent PRs; delete fork branches.
  - Exit check: V5 and V6 pass. Attempts stay within the time and $ caps. Every failed attempt surfaces as an approval-gated "couldn't fix" note rather than disappearing.

- **Phase 4: Canary and economics**
  - Unlocks: the scale-out decision.
  - Depends on: Phase 3, V6. Also V1 if the second repo is private.
  - Tasks:
    1. Add one second repo, preferably one with outside contributors. Run V3 and V5 on it.
    2. Four weeks of metering: $ per attempt, merge rate, review time.
    3. V7.
    4. Per-repo kill switch.
  - Rollback: uninstall the App from the canary repo.
  - Exit check: V7 passes. No abuse-driven cap breaches go unalerted. On-call load fits the ops budget.

- **Phase 5: Waves and feedback**
  - Unlocks: org-wide use.
  - Depends on: V7, and V1 for private repos.
  - Tasks:
    1. Per-repo onboarding: maintainer opt-in, workflow/bot inventory, V3 and V5 rerun.
    2. Waves of 3, then 10, then the rest.
    3. Feedback: merge/reject outcomes and label corrections go through a review queue into the eval set and prompts. Nothing trains automatically.
    4. Eval regression runs on every change to prompt, model, or tools.
  - Rollback: per-wave uninstall or flag.
  - Exit check: per-wave triage precision and merge rate stay within the V4/V6 bars. Reviewed feedback improves the eval with no regressions elsewhere.

## 9. Exceptions
None. Running the PR tier as a dry run in Phase 0 follows Step 4's read-only rule, so it isn't an exception.

## 10. Deferred
- **Autonomous merge.** Pull forward when maintainers ask for it on a narrow class (e.g., dependency bumps) and a new gate passes: zero reverted agent merges over a set window, plus security sign-off.
- **Autonomous comments to outside authors.** Pull forward when V7 passes and the approval reject rate stays under a maintainer-set bar for 4 weeks.
- **Closing duplicate or stale issues.** Pull forward when duplicate precision passes a stricter version of V4.
- **Iterating on PR review comments.** Pull forward once V6 passes and reviewers ask. Only comments from maintainers would be accepted as input.
- **Vector code index.** Pull forward when traces show retrieval misses on large monorepos.
- **Dynamic model routing.** Pull forward if V7 fails on cost while quality has headroom.
- **Multi-agent orchestration.** Pull forward if the single loop fails a task class that matters.
- **Fine-tuning.** Pull forward if the eval plateaus after retrieval work and legal clears the data.
- **Self-hosted model.** Pull forward if V1 is refused, or V7 fails on vendor cost.
- **Duplicate detection across repos.** Pull forward when two repos with the same visibility both opt in. Never across visibility levels.
- **Availability SLO / multi-region.** Pull forward when a team's process depends on triage latency.
- **GitHub Enterprise Server / multiple orgs.** Pull forward when a second org requests it.
