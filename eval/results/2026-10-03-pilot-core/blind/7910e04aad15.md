# BUILD PLAN: Real-time card-transaction fraud detection

**Assumptions this plan depends on.** I'm stating these up front because each one changes the phase order, not just a threshold:
- **A1. Issuer-side system.** You are an issuer or issuer-processor, and you already run an authorization switch.
- **A2. In-path scoring is the goal.** Scoring eventually sits inside the authorization path and can approve, step up (send an extra identity check such as a one-time code or 3DS) or decline. It starts out shadow-only.
- **A3. A fallback already exists.** Basic rules and the card networks' own scores (Visa Advanced Authorization, Mastercard Decision Intelligence) already exist, and they stay as the fallback.

If any of these is false, the plan changes:
- **Not in-path (post-authorization alerting only):** V2 and V3 shrink to exit checks, and Phase 5 becomes "alert routing".
- **Acquirer or merchant side:** the entity keys and label sources change, so V1 and the labels part of E1 change.
- **No switch exists yet:** this becomes a different, greenfield plan.

## 1. Classification and constraints
- **What:** A streaming pipeline that scores each card authorization within the switch's time budget. It combines rules and a machine-learning model, applies a decision policy (approve / step-up / decline / review), and logs every decision for disputes and retraining.
- **Type:** Software, infrastructure and predictive ML (no LLM). Brownfield: it plugs into the existing authorization switch, disputes and chargeback systems. Not a small build: it handles real money and cardholder data under PCI DSS, and it has R3 decisions.
- **Dominant constraint:** Latency and correctness in the authorization path, under PCI DSS compliance.
- **Worst failure:** The in-path scorer causes mass false declines or authorization timeouts across the whole portfolio. Every cardholder's card fails at once. The control that guards this is gate V3.

**Budgets**

**Missing inputs, in order of impact:**
1. A1–A3 above.
2. Fraud-performance targets (fraud risk owner).
3. The actual latency budget left in the switch (auth-platform owner).
4. Data residency and retention (legal/compliance).
5. Whether GDPR or a similar regime applies. That decides whether an automated decline needs legal review (V6).
6. Which step-up channel exists today (SMS one-time code, app push or 3DS).

## 3. Tradeoff gates (resolved up front)

|---|---|---|---|---|---|
| Sync vs async | R2 (changing it is a coordinated change with the switch team) | Synchronous gRPC score call from the switch with an 80 ms hard timeout. | Failure mode on scorer error or timeout | R3 (minutes of wrong behavior cause harm at portfolio scale) | Fail open: fall back to existing rules plus network score. | Consistency vs availability (online features) | R2 (feature semantics are baked into training data) | Availability: per-card counters do an atomic increment-and-read in the store. If the store is down, score with a flag saying features are missing | Bursts are caught by per-card counters, not by global consistency | V2 (burst replay) | Card-testing replay escapes because counters are stale: add read-your-writes per card |

**R1 defaults:**
- Monolith vs services: one scorer service (rules, model and policy in-process), one Flink job, one batch label job.
- Model family: gradient-boosted trees (LightGBM), compiled with Treelite.
- Score and policy are separate: thresholds are config.
- Infrastructure: Terraform plus ArgoCD.
- Online store: Redis Enterprise or Aerospike.
- Offline store and decision log: Iceberg on S3.

**N/A:**
- Prompt+RAG vs fine-tune, and hosted vs self-hosted LLM: no LLM in this system.
- Tenancy: single issuer.

## 4. Walking skeleton (Phase 0)
- **Before anything is built:**
  - CAB approval for the switch change.
  - A PCI-segmented Kubernetes namespace.
  - A tokenizing adapter inside the switch, using the existing vault/HSM.
- **The request:** A real authorization from an allow-listed internal test or employee card at a real merchant. The switch adapter tokenizes it and calls `Score` over gRPC with mTLS. The scorer applies one trivial rule, increments a per-card counter in the online store, and returns `{score, decision=APPROVE, reason_codes, model_version}`. The switch **logs the response and ignores it**: the existing path still decides.
- **Tiers crossed:**
  1. Switch adapter
  2. Scorer
  3. Online feature store
  4. Kafka (transaction plus decision event)
  5. Flink (updates one aggregate)
  6. Decision log in Iceberg
  7. A Grafana dashboard
- **Day-zero operations:**
  - **Deploy:** CI builds a signed image, ArgoCD deploys it, and a switch feature flag turns the call on per card token.
  - **Logs and traces:** OpenTelemetry, with one trace ID from the switch call through the decision-log row. All logs hold tokens only.
  - **Monitoring:** Prometheus alerts on scorer p99, timeout rate and Flink lag.
  - **Rollback:** flip the switch flag off, plus an ArgoCD rollback to the previous image.
- **Who can reach it:** Only allow-listed card tokens behind the switch flag. Responses are not acted on.

**Exit check (V0):**
- One real authorization produces one trace across all 7 tiers.
- A deploy and a rollback both go through the pipeline.
- Injecting 200 ms of scorer latency makes the switch time out, fail open and fire the alert.
- Baselines recorded: scorer p50/p99 at near-zero load, auth p99 and peak TPS from switch logs, and the auth SLO.

## 5. Phases

- **Phase 1: Data contract, full shadow mirror, labels**
  - Unlocks: specifying features, rules and the model; measured baselines for fraud and false declines.
  - Depends on: Phase 0 and V0; data-access approval.
  - Tasks:
    1. Freeze the V1 schema in the registry, with compatibility mode BACKWARD.
    2. Run the V1 replay and DLP scan.
    3. Mirror **all** auth traffic asynchronously to Kafka, out of the auth path.
    4. Start label ingestion (E1): fraud-coded chargebacks, cardholder fraud claims, Visa TC40 / Mastercard SAFE reports. Join them to the decision log by transaction ID.
    5. Backfill 13 or more months of history (tokenized) from the warehouse.
    6. Get fraud-performance targets from the risk owner, and retention and residency from legal.
    7. Start V6.
  - Rollback: turn the mirror off. Nothing is in the path. The schema evolves only through registry versions.
  - Exit check: V1 passes; baseline fraud basis points and false-decline rate are published; risk-owner targets are recorded with their labels.

- **Phase 2: Defenses and budgets in the path**
  - Unlocks: synchronous shadow scoring on all traffic.
  - Depends on: Phase 1 and V1.
  - Tasks:
    1. Circuit breaker and timeout in the switch adapter; fail open to the existing decision.
    2. Decline-rate and step-up-rate kill switch: compare the 1-minute rate to baseline and auto-revert to the fallback.
    3. Input validation. Out-of-range or malformed fields get a "degraded" flag and are never used for a hard decline.
    4. Four-eyes approval and audit for every rule or threshold change.
    5. V2 load test with burst replay.
    6. Widen synchronous shadow scoring from the allow-list to 1%, then 10%, then 100%, with decisions still ignored.
    7. Online-store recovery drill (RTO).
  - Rollback: switch flag per traffic slice.
  - Exit check: V2 passes. V3 runs on shadow traffic, and its kill-switch trip is rehearsed. Auth p99 is within baseline + 5 ms at 100% shadow (an ASSUMPTION; confirm with the switch owner).

- **Phase 3: Features and rules (shadow)**
  - Unlocks: rules-based decisions ready for advisory; training data for the model.
  - Depends on: Phase 2 and V2.
  - Tasks:
    1. One shared feature-definition library used by Flink and the offline backfill: velocity (per card, merchant, device, BIN), geo-distance, merchant category risk, card-present vs card-not-present, network scores.
    2. Run V4.
    3. Port existing rules into the scorer's rules engine, run them in shadow, and compare against the existing engine's decisions.
    4. Stream advisory reason codes to the analyst case queue.
  - Rollback: features are versioned. A feature-set flag pins the previous version.
  - Exit check: V4 passes. Shadow rules agree with existing-engine decisions ≥ 99.5% (ASSUMPTION), with differences explained.

- **Phase 4: Model**
  - Unlocks: model-driven scores.
  - Depends on: Phase 3 and V4; V6; labels at least 90 days mature (E1).
  - Tasks:
    1. Train LightGBM on out-of-time splits. Register it in MLflow with data snapshot, feature version and code hash.
    2. Derive reason codes (SHAP top-k).
    3. Run V5.
    4. Serve it in-process in shadow and confirm V2 latency still holds with the model loaded.
  - Rollback: the model registry pins the previous version, and the model can be swapped by config.
  - Exit check: V5 and V6 pass, and the V2 re-run with the model loaded passes.

- **Phase 5: Enforcement rollout (exposure smallest first)**
  - Unlocks: real fraud prevention.
  - Depends on: Phase 4, V3, V5, V6; analysts staffed.
  - Tasks:
    1. Advisory: decisions go to analysts only.
    2. Enforce **step-up** on a 1% BIN-range canary for 14 days and run V7.
    3. Then enforce **decline** at the top score band on the same canary.
    4. Widen 1% → 10% → 50% → 100%, re-running V7 at each step.
    5. Cardholder notification and an analyst override path.
  - Rollback: flip a slice back to advisory through the policy config, in seconds. No point of no return: the existing rules are never removed (see §10).
  - Exit check: V7 passes at each widening; 100% of traffic is enforced.

- **Phase 6: Champion/challenger and retraining loop**
  - Unlocks: sustained performance under drift.
  - Depends on: Phase 5 and V7.
  - Tasks:
    1. Challenger model in shadow on 100% of traffic.
    2. Drift monitors (population stability index on features and scores).
    3. Scheduled retraining on matured labels. Analyst labels go through review, never straight into training.
    4. Promote a challenger only through a V5 re-run plus a canary.
  - Rollback: the previous champion is pinned.
  - Exit check: one full retrain → V5 → canary → promotion cycle completes, traced and audited.

## 10. Deliberately deferred
- **Decommissioning the existing rules engine.** Pull forward when: two quarters at 100% enforcement pass V7. It then needs its own gate with a rehearsal and a named approver.
- **Graph or deep-learning features (merchant/device networks).** Pull forward when: the V5 uplift plateaus or a fraud-ring pattern beats the current features.
- **Multi-region active-active scoring.** Pull forward when: residency rules or the switch's own region setup require it, or scorer SLO misses push fail-open losses past the risk limit.
- **Other payment channels (ACH, P2P, wallets).** Pull forward when: the business asks and the schema has a V1-style review.
- **Consortium or external data enrichment.** Pull forward when: V5 shows a feature gap that only outside data can fill, and legal signs off.
- **Automated retraining without review.** Pull forward when: never without reviewed labels. Revisit after 3 reviewed retraining cycles with no regression.
- **LLM assistant for analysts.** Pull forward when: review-queue workload becomes the bottleneck. It would bring in the full LLM defense layer.
