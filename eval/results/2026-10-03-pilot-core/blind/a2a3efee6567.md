# BUILD PLAN: Autonomous GitHub Issue Triage and Resolution Agent

## 1. Classification and constraints
- **What:** An agent that reacts to new GitHub issues by labelling them, finding duplicates and asking reporters for missing details. When a maintainer asks it to, it attempts a code fix and opens it as a draft pull request (PR) for human review.
- **Type:** An AI agent plus a software control plane. The service is new, but it works inside existing repos, so their branch protection, CI, label automations and human triage are constraints it inherits. Human triage stays as the fallback the whole time. This is not a small build: anyone can file an issue (outside users), the agent spends money on model calls, and it acts on code.
- **Dominant constraint:** Getting actions right. An attacker steering the agent costs more than any delay. Cost comes second.
- **Worst failure:** Someone writes instructions into an issue, comment or repo file, and the agent follows them. It then leaks a credential or private code, or gets malicious code merged. That would be a supply-chain compromise across every repo the GitHub App is installed on.

**Missing inputs and the assumptions the plan rests on:**
1. **What "resolve" means.** I assume draft PRs that humans review and merge; the agent never merges or closes an issue on its own. If you need auto-merge, a new gated phase goes after Phase 5 (see §10). That changes the phase order, so please confirm.
2. **Who can file issues.** I assume a mix that includes public repos, so every issue author, comment and repo file is treated as untrusted. If all repos are internal, the order stays the same; V1 still applies because pasted logs and dependencies carry outside text.
3. **Sending private code to a hosted model vendor.** Not yet approved. If it is refused, the hosted-vs-self-host decision flips and Phase 2 gains model-serving infrastructure (V6).
4. **Target repos.** Their count, languages and whether their CI can run in a sandbox drive the sandbox images built in Phase 3.
5. **GitHub hosting.** GitHub.com versus GitHub Enterprise Server changes networking and how the App is installed.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Autonomy and trust boundary | R3: a merged backdoor or leaked secret cannot be undone | **Autonomous:** read; apply allowed labels; comment with a missing-info request or duplicate candidate. **Needs bound human approval:** close, assign, start a fix attempt. **Never:** merge, push upstream, edit `.github/` or secrets | No filter stops every injection, so containment must be built into the structure | V1 | V1 fails → suggestions go only to a maintainer dashboard, with no public writes |
| Credentials and push model | R3: a trust boundary | A GitHub App. The tool executor holds short-lived installation tokens; the model never sees them. Upstream permissions: `issues:write`, `pull_requests:write`, `contents:read` only. Code goes to a fork the agent owns, and PRs come from that fork | GitHub's merge API and pushes need `contents:write`, and workflow files need `workflows`, so the App structurally cannot merge. Fork PRs under `pull_request` get no repo secrets | V1 (cited basis plus test) | V1 fails; or a repo's required checks need secrets on PRs → that repo stays triage-only |
| Where code runs | R3 by the cost of being wrong: the agent runs code steered by untrusted text | A fresh gVisor/Firecracker sandbox for each attempt: no credentials, outbound traffic only to a package mirror, destroyed by a time-to-live reaper | Ephemeral isolation holds against test-suite and agent-written code | V2 | V2 fails → the agent only edits code and relies on fork CI, which has no secrets |
| Data-privacy boundary | R3: data sent to a vendor cannot be recalled | Hosted API under zero-retention, no-training terms. Secrets and personal data are redacted before the model and before logs. Public repos come first. Retrieval is limited to the issue's own repo, so nothing is more visible in output than it was in input | The vendor terms cover private code and personal data in issues | V6 | V6 refused → self-host for private repos |
| Consistency and system of record | R2: changes the ledger schema | GitHub is the system of record for issues, labels and PRs. Postgres holds runs, approvals and the action ledger, with idempotency keys. It is strongly consistent; if it is down, the agent pauses and humans carry on | Event volume is far below what one Postgres primary handles | Phase 0 volume baseline (peak events/s against a single-primary benchmark) | The baseline exceeds 10% of benchmark capacity, or the ledger allows a double action |
| Build vs buy | R2: the integration is rework, but policies and evals carry over | Build the control plane (policy executor, approvals, budgets, audit, sandbox orchestration). Plug in an open-source coding loop (e.g., OpenHands or SWE-agent) behind an interface whose only tools are our executor's | Hosted coding agents may hold their own credentials outside our executor (to verify) | V4 compares the candidate loops, including one hosted agent | A hosted agent passes V4 within rows 1–2 → buy it for resolution and keep our control plane |
| Prompt+RAG vs fine-tune | R2; training on reporters' text would be R3 | Prompts plus retrieval (issue index, code search, CODEOWNERS); no training on issue data | Retrieval gets enough context in | V3, V4 | V3 or V4 plateaus below its threshold after retrieval and prompt tuning |
| Hosted API vs self-host | R2 behind the model interface | Hosted: a small model for triage, a frontier model for resolution | Terms and price are acceptable | V6, V5 | V6 refused, or V5 cost fails |

**R1 defaults:** sync vs async → async queue (GitHub's 10 s webhook timeout forces this). Monolith vs services → one deployable for the receiver and workers; the sandbox pool is separate for isolation, not scale. Queue → managed (SQS or Pub/Sub). Approval UX → GitHub comment commands and labels. Orchestration → one loop with fixed stages. Telemetry → OpenTelemetry into the existing backend.
**N/A:** migration strategy, cutover and decommissioning. Nothing is migrated; human triage stays as the parallel fallback.

## 4. Walking skeleton (Phase 0)
- **The real request:** a team member opens an issue on `org/agent-sandbox`, a real repo in the production org. The agent applies exactly one label from `{bug, feature, question}`, and the run ID is recorded.
- **Tiers it crosses:**
  1. GitHub webhook
  2. Receiver: checks the HMAC signature and acknowledges in under 10 s
  3. Managed queue
  4. Worker
  5. Model interface: issue text goes in a delimited untrusted-data block, with an 8k-token hard cap, a per-call cost cap and a structured output schema
  6. Policy executor: one allowed tool, `add_label`, with an allowed value set
  7. GitHub API, using an installation token held only by the executor
  8. Postgres action ledger
- **Deployed, logged, monitored, rolled back:** the container goes out through the CI pipeline (IaC, pinned image digest) to a managed runtime. One OpenTelemetry trace spans every tier, and run, error, token, cost and latency metrics are recorded. Alerts fire on dead-letter queue (DLQ) depth > 0 and on error rate. One rollback is done by redeploying the previous image digest. A global write kill-switch flag exists from day zero.
- **Who can reach it:** the App's write installation covers only the sandbox repo, and the worker drops events from authors not on the allow-list. Separately, a read-only installation on the candidate canary repos collects baselines:
  - 90-day issue volume
  - human time to first label
  - PR review time
  - the label-automation and `pull_request_target` audit from §2
- **Exit check (V0):** see §6.

## 5. Phases

**Phase 1: Defenses and budgets (shadow mode, read-only on real repos)**
- **Unlocks:** public writes in Phase 2.
- **Depends on:** V0. V6 for private repos.
- **Tasks:**
  1. Policy executor: tool allow-list, argument validation, per-repo policy as code. The allowed labels exclude the automation-triggering labels found in Phase 0.
  2. Approval binding: a hash of the exact action, an approver whose write permission is checked through the API (not read from comment text), single use, with expiry.
  3. Secret and personal-data redaction on every input and on logs. Agent output is stripped of external URLs and images, which closes exfiltration through rendered markdown.
  4. Budgets: per-run caps, a per-author daily cap (guards against spam issues running up cost), a per-repo concurrency limit, and a monthly circuit breaker.
  5. A reconciliation sweep that re-lists issues since the last checkpoint, to catch missed webhooks.
  6. Injection suite plus honeytokens in CI; then the red-team exercise (V1).
  7. Shadow triage on the canary repos, with output going only to an internal dashboard.
  8. Build the eval sets for V3 and V4. Measure how often two maintainers agree on labels (BASELINE, 100 double-labelled issues).
- **Rollback:** a flag; there are no outside writes yet.
- **Exit check:** V1 passes. A forced runaway loop is cut off at its cap and emits a cost metric. A simulated 2 h outage recovers within the §1 budget.

**Phase 2: Triage capability (retrieval → model access → memory), canary**
- **Unlocks:** autonomous triage on the canary repos, and the inputs Phase 3 needs.
- **Depends on:** Phase 1, V1, V3 (exposure), and the spend ceiling.
- **Tasks:**
  1. Duplicate search over an index of the same repo's issues; area mapping from CODEOWNERS.
  2. Harden the model interface: fallback model by config, retries, schema validation.
  3. Per-issue conversation state, so the agent re-triages when the reporter answers its info request. Agent config is read only from the default branch.
  4. Eval in CI on every prompt, model or index change.
  5. Run V3.
  6. Expose to 1 opted-in public repo, then 3. Closing duplicates still needs maintainer approval.
- **Rollback:** a per-repo flag, plus a ledger-driven script that removes the agent's labels and deletes its comments. Comments may already have been read; that is accepted because they contain only redacted, same-repo content.
- **Exit check:** V3 passes. API use stays within budget. The rate of maintainer corrections is visible per repo.

**Phase 3: Resolution substrate (sandbox → coding loop, offline)**
- **Unlocks:** live fix PRs in Phase 4.
- **Depends on:** V1, Phase 2 (repo retrieval), V2 before any repo code runs.
- **Tasks:**
  1. Sandbox images per repo language, pinned by digest. The executor clones the repo and hands the sandbox a copy without credentials.
  2. Sandbox escape suite (V2).
  3. Coding loop behind the interface (build-vs-buy candidates).
  4. A diff guard that flags deleted, skipped or weakened tests and any change to `.github/`.
  5. Replay harness at each pre-fix commit (V4).
  6. Get the human cost per fix and the review-time BASELINE for V5.
- **Rollback:** offline; nothing external.
- **Exit check:** V2 and V4 pass, and the build-vs-buy row is decided.

**Phase 4: Resolution canary (orchestration, live)**
- **Unlocks:** the V5 evidence.
- **Depends on:** V2, V4, a V1 re-run with the push and open-PR tools in scope, and the `pull_request_target` audit for each canary repo.
- **Tasks:**
  1. An attempt starts only on a maintainer trigger bound to the issue and commit.
  2. Push to the agent's fork and open a draft PR whose description links the run trace.
  3. Merging stays behind branch protection and a human CODEOWNERS review. The App also has no `contents:write`.
  4. Enforce the cap on open PRs per repo.
  5. Roll out to 1 repo, then 2.
- **Rollback:** flag off, close the agent's draft PRs, delete fork branches. A merged PR is a human decision and is reverted through the repo's normal process.
- **Exit check:** V1 (re-run) and V5 pass.

**Phase 5: Widening and feedback (routing and feedback)**
- **Unlocks:** general use across the org.
- **Depends on:** V5.
- **Tasks:**
  1. Repo waves of 5, then 20, then everything opted in. Each wave first gets the label and workflow audit.
  2. Maintainer corrections and PR review outcomes go through human review before they reach the eval sets or prompts.
  3. A quality circuit breaker per repo: auto-pause when the correction rate rises above that repo's Phase 2 level.
  4. Refresh the red-team suite every quarter.
- **Rollback:** uninstall the App from a wave.
- **Exit check:** each wave holds its V3 and V5 levels for 2 weeks before the next wave starts.

## 10. Deliberately deferred
- **Auto-merge of agent PRs.** Pulled forward if, for one narrow change class, V5's merged-with-minor-edits rate stays high over ≥ 100 PRs and maintainers ask for it. It would get its own gate on revert rate.
- **Closing issues without approval** (duplicates, stale). Pulled forward if live duplicate precision holds V3's bar for 3 months and the repo's maintainers opt in.
- **Agent revising its PR in response to review comments.** Pulled forward once V5 passes and maintainers ask; it needs a V1 re-run with review comments as an injection surface.
- **Retrieval across repos.** Pulled forward if monorepo or multi-repo duplicates make up a measured share of misses. It needs a check that retrieved content is never more visible than the issue it answers.
- **Fine-tuning.** Pulled forward if V3 or V4 plateau after retrieval and prompt tuning and ≥ several thousand reviewed examples exist. Personal-data review first.
- **Self-hosted model.** Pulled forward if V6 is refused or V5 fails on hosted pricing.
- **Dynamic routing.** Pulled forward if V5 cost misses its target while a cheaper model passes V4 on a subset.
- **Long-term repo memory or notes.** Pulled forward if traces show repeated rediscovery of the same repo facts costing > 20% of tokens.
- **Multi-agent orchestration.** Pulled forward if one issue class fails V4 and splitting the task fixes it in eval.
- **A dedicated approval UI.** Pulled forward if the volume of approvals makes comment commands unworkable.
- **A second org or GitHub Enterprise Server.** Pulled forward when a named org asks.
