# Build plan: moving the hospital's patient scheduling system to the cloud with no downtime

## 1. Classification and constraints
- **What:** Move the hospital's on-premises patient scheduling application and its database to a cloud account the hospital owns. Users, interfaces and outside vendors must keep working throughout.
- **Type:** Infrastructure plus software. It replaces an existing system (brownfield). It's a large build: protected health information (PHI), clinical users, several teams and vendors, and some decisions that are hard to undo.
- **Dominant constraint:** Correctness of bookings during the move, then availability, then compliance.
- **Worst failure:** Two databases accepting writes at once (split-brain), or a cutover or rollback that silently loses or duplicates appointments. Patients miss care or get double-booked, and nobody notices for days. The controls against it are V4, V5, V6 and fencing (only one database can ever accept writes), described in Phase 3.

**Planning assumptions** (if any is false, the plan changes as noted):
- The hospital runs the system itself on one relational database. The vendor supports running it on cloud servers. Users reach it through hostnames the hospital controls. **If false:** if the vendor's own hosted offering is the target, this becomes a vendor-led move and Phases 1–3 are re-planned around their tools. If desktop clients connect straight to the database, a database-name step is added to Phase 2.
- **HIPAA applies (US).** If not, V1 is re-scoped to the local rules (for example GDPR or NHS DSPT) and the data-location row in §3 changes.
- **The scheduling database is not shared with other applications** (for example registration). If it is, the move covers every application on it and Phase 2 grows.

**Missing inputs, most important first:**
1. Which product this is, and the vendor's written support and licensing terms for the cloud.
2. Client type: web, or desktop clients connecting directly to the database.
3. Database engine, version, size and peak volumes.
4. Cloud provider, and whether a business associate agreement (BAA, the HIPAA contract with the provider) is already signed.
5. Clinical operations' definition of "no downtime".
6. Whether the database is shared with other applications.

**Things this plan will not change (each with its cost to change):**
- Application version: an upgrade means re-testing clinical workflows, which is weeks of work.
- Database engine: changing it means rewriting the schema and stored code, which is months.
- HL7 interfaces stay on the on-premises interface engine: re-pointing them affects every partner system.
- Login stays on Active Directory (AD): changing the login model changes the security boundary.

**Not applicable:**
- Monolith vs services: no re-architecture during a move.
- Sync vs async: inherited (HL7 stays asynchronous through the interface engine).
- AI rows: no AI component.

## 4. Walking skeleton (Phase 0)
The skeleton is the thinnest real path through the new cloud setup, used by IT staff only, with the current system untouched as the fallback.

- **The real request:**
  1. An IT analyst on the allow-list books, then cancels, a slot for the hospital's designated test patient in a designated test clinic.
  2. The booking is done through one cloud app server.
  3. The booking is then read back from the cloud database copy.
- **Path it takes:**
  1. Hospital workstation → internal DNS and proxy, on a separate hostname.
  2. Site-to-site VPN → private-only cloud load balancer → one cloud app server, running the same build as production.
  3. On-premises live database (still the official record) → interface engine → EHR scheduling message for the test patient.
  4. Native replication → cloud database copy → a check query confirms the booking arrived.
- **Deploy, log, monitor, roll back:**
  - The landing zone and the app server image deploy through the pipeline from Terraform.
  - Logs and traces go to the SIEM, classified as PHI.
  - Alerts go to the existing on-call: app health and replication delay.
  - Rollback: take the server off the hostname, revert the infrastructure code, stop replication through the CAB plan, and destroy the cloud copy's encryption key so the copy can never be read again.
- **Who can reach it:** only allow-listed IT workstations, on a separate internal hostname. Clinical users keep using the on-premises system unchanged. No outside access. No PHI goes into the cloud until V1 passes.
- **Exit check (V0):**
  - The test booking traces end to end through every tier.
  - One deploy and one rollback run through the pipeline.
  - A deliberately killed replication stream fires an alert.
  - First baselines are recorded: speed of key actions, replication delay, and the extra delay of the app calling the database across the VPN. These are a floor at near-zero load, not capacity.

## 5. Phases

**Phase 0 — Prerequisites, baselines and the skeleton**
- **Unlocks:** Phase 1.
- **Depends on:** nothing earlier.
- **Tasks:**
  1. Start the long-lead-time items: CAB approval, BAA, cloud account, order both circuits, ask the vendor for its support and licensing statement, get clinical operations' definition of "no downtime" and the CMIO's confirmation on booking loss.
  2. Measure today's live system through its own change process: automated test transactions for the key actions, the busiest hours, availability.
  3. Start dependency discovery: network flow logs plus a database connection audit, covering at least 35 days including a month-end (V2).
  4. Build the landing zone with Terraform: private-only network, hospital-managed keys, SIEM logging, sign-in with multi-factor authentication.
  5. Pass V1.
  6. Set up the VPN, seed the cloud database copy, deploy the app server.
  7. Run V0.
- **Rollback:** as described in §4. The live system's only change is replication being turned on, which can be turned off under the CAB plan.
- **Exit check:** V1 and V0 pass; baselines recorded; discovery running.

**Phase 1 — Production-scale data tier and proof the copy is identical**
- **Unlocks:** Phase 2.
- **Depends on:** V0, V1, both circuits installed.
- **Tasks:**
  1. Compatibility check: vendor statement plus database features in use.
  2. Size the cloud database and app tier across availability zones.
  3. Move replication onto the circuits.
  4. Start continuous reconciliation between the two databases (V4). It compares row counts and checksums only, never records.
  5. Stand up in the cloud the runtime services discovery found: AD domain controllers, DNS, print servers, email relay.
  6. Replay production load against the cloud stack (V3).
  7. Test-restore a cloud backup.
- **Rollback:** tear down the cloud tier. On-premises is still the official record and still serving everyone.
- **Exit check:** V3 passes; V4 reconciliation running with alerts; cost estimate checked against Finance's budget.

**Phase 2 — Re-point consumers, cut over read-only consumers first, rehearse**
- **Unlocks:** Phase 3.
- **Depends on:** V2, V3, V4 running.
- **Tasks** (smallest exposure first):
  1. Move every consumer V2 found onto stable hostnames behind the hospital proxy, one consumer group at a time, still pointing at on-premises. Each move is undone with a DNS change.
  2. Move read-only consumers (data warehouse loads, reports) onto the cloud copy.
  3. Optional, only if V3 shows the cloud app calling the on-premises database across the link stays within budget: put one low-volume clinic's schedulers on cloud app servers for 1 week.
  4. Script the cutover runbook.
  5. Run V5 rehearsals.
  6. Pre-stage outside vendors' allow-list changes.
  7. Refresh paper downtime procedures and the printed 48-hour schedules.
- **Rollback:** re-point each group or read-only consumer back by DNS or proxy.
- **Exit check:**
  - V2 and V5 pass.
  - No traffic on the old addresses for 7 days.
- **Note on exposure:** the write path can't be trialled with a small group without two databases accepting writes, which §3 rules out. Exposure is narrowed by sequence instead: IT staff, then read-only consumers, then one clinic, then the full switch.

**Phase 3 — Production cutover and soak**
- **Unlocks:** Phase 4.
- **Depends on:** V4 (14 days, plus the last 72 h clean), V5, V6.
- **Tasks**, in the quietest window from the baseline (never just before a release of new booking slots):
  1. The interface engine holds incoming HL7 messages.
  2. Pause saving.
  3. Wait until replication delay is zero.
  4. Fence: demote the on-premises database to read-only and turn off the old app servers' database logins.
  5. Promote the cloud database.
  6. Switch the proxy and drain sessions.
  7. Release the held HL7 messages.
  8. Start reverse replication, cloud → on-premises.
  9. Run booking integrity checks every 5 minutes.
  10. Soak for 30 days including a month-end.
- **Rollback:** the same script run in reverse back to on-premises, within the RTO, while reverse replication runs.
- **Exit check:**
  - V6 post-cutover criteria held for the whole soak.
  - Availability at or above BASELINE.

**Phase 4 — Steady state and decommissioning**
- **Unlocks:** the end of running two environments.
- **Depends on:** Phase 3 soak; V7.
- **Tasks:**
  1. Build a second-region DR copy and test a restore.
  2. Make a final archive export and test that it restores.
  3. Pass V7.
  4. Stop reverse replication.
  5. Decommission: wipe media to NIST 800-88, revoke credentials, remove firewall rules.
- **Point of no return:** stopping reverse replication. V7 guards it.
- **Exit check:** V7 passes; nothing still depends on the on-premises hosts.

## 10. Deliberately deferred
- **Upgrading the app or database version:** after V7, unless the vendor's end of support forces it sooner.
- **Re-architecture, or a move to the vendor's own hosted product:** pulled forward after one quarter at steady state, or if the vendor's terms require it.
- **Moving the interface engine to the cloud:** pulled forward if V3 shows HL7 delay across the link breaks its budget.
- **Long-term cloud pricing commitments (reserved capacity):** after 60 days of steady usage and against Finance's budget.
- **Automatic scaling:** pulled forward if the busiest hour gets within 70% of the fixed capacity.
- **Active-active DR across two regions:** pulled forward if the committed availability or RTO target can't be met by restoring from DR.
- **Moving the data warehouse and reporting platform:** a separate project once read-only consumers are stable on the cloud copy.
