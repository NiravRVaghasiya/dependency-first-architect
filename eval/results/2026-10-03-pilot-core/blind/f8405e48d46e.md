# BUILD PLAN: Real-time card-transaction fraud detection

## 1. Classification
- **What:** A system that scores every card authorization in real time and returns approve, decline, review or step-up before the authorization deadline. It learns from chargebacks and analyst decisions.
- **Assumption (stated, not silent):** We are the issuer or processor, sitting inside the ISO 8583 authorization flow. If we are an acquirer or payment provider scoring before authorization, the gates hold, but the response contract and label sources change.
- **Type:** Software and infrastructure, plus classical machine learning (ML). It is **not LLM-based or agentic**: no language model sits in the decision path.
- **Dominant constraint:** **Latency**, under compliance limits (PCI DSS, card-scheme rules, model governance). Correctness is measured afterwards, against labels that arrive 30 to 120 days late.
- **Worst failure:** The fraud scorer slows down or fails and **blocks or declines good transactions at scale**. A total outage of card acceptance is worse than missing fraud for an hour. A close second is a model that silently degrades and goes unnoticed for months.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| Consistency vs availability: when the scorer fails | **Availability.** If the scorer times out, the payment switch falls back to a local backup ruleset with tighter limits. It never hangs. Features may be up to 1 s stale (p99). Ordering is guaranteed per card by partitioning on the card token. | Fraud losses during fallback windows exceed tolerance (e.g. more than 2× normal fraud bps), or a scheme or regulator requires fail-closed for a segment. Hard credit limits stay in the core ledger, never here. |
| Monolith vs services | **Modular monolith scoring service.** Feature lookup, rules and model inference run in one process, so no internal network hops eat the latency budget. One separate streaming job computes features. | Separate teams need to deploy independently, or inference needs different hardware (GPU) or its own scaling. |
| Sync vs async | **Only the decision is synchronous.** A feature may sit in the synchronous path only if it is a single key lookup of 5 ms or less. Anything computed (windows, aggregates) is precomputed asynchronously in the stream. Cases, labels and training are all asynchronous. | A feature with proven large lift needs the current transaction (e.g. distance from the last transaction's location). It may be computed in-request only if a load test shows it fits the budget. |
| Build vs buy | **Buy infrastructure:** managed Kafka with schema registry, managed Aerospike or Redis, managed Flink. **Buy signals:** card-network risk scores (Visa Advanced Authorization, Mastercard Decision Intelligence) used as features. **Build** the decision engine, labels and model; our own data is the advantage. | Fewer than about 3 fraud/ML engineers, or go-live required within 6 months. Then buy a vendor platform (Feedzai, Featurespace) and build only the integration, the label pipeline and monitoring. |
| What counts as fraud (the label) | Confirmed-fraud reports (TC40/SAFE), chargebacks with fraud reason codes, and analyst-confirmed fraud. A label is final after 90 days. "Friendly fraud" disputes are excluded. | Late labels make the model adapt too slowly to new attacks. Then add customer-confirmed early labels as a separate, weighted label. The target definition itself stays versioned. |
| (AI) prompt+RAG vs fine-tune → *reframed:* rules vs ML, and which model | **Rules first. Then gradient-boosted trees (LightGBM)**, which give per-decision reason codes. **No LLM in the authorization path.** | The tree model's gains plateau, and a sequence model catches more fraud offline at the same decline rate within the latency budget. |
| (AI) hosted API vs self-host | **Self-host, in-process inference.** No third-party API call in the authorization path, for latency and PCI scope. | A vendor platform is chosen under the build-vs-buy gate. |
| Data-privacy boundary | **The full card number (PAN) never enters this system.** The payment switch tokenizes it (HMAC, key held in an HSM). Personal data such as name or address is not used as raw features. The scorer is kept outside the PCI cardholder-data environment where possible. GDPR Art. 22 is handled with reason codes and a review path. | A feature needs raw data. It is then computed inside the cardholder-data environment and only the derived value is exported. |

## 3. Walking skeleton (Phase 0)
- **The real request:** One real production authorization (0100/0200 message), mirrored to the scorer in **shadow mode**. The switch logs our decision but does not act on it.
- **The real response:** `{decision, score, reason_codes[], ruleset_version, model_version: null, trace_id}`. In Phase 0 the decision comes from one rule: `amount > X AND txn_count_card_24h > N → review`.
- **Tiers crossed:**
  1. Payment switch, which tokenizes the PAN.
  2. Scoring service over gRPC, running on Kubernetes across 2 availability zones.
  3. Online store (Aerospike or Redis), looked up by card token for the single feature `txn_count_card_24h`.
  4. The one rule, written as a CEL expression.
  5. Response back to the switch.
  6. Transaction event plus decision record published to Kafka.
  7. A plain Kafka consumer that updates the counter (no Flink yet; it isn't needed).
  8. A sink into a raw Iceberg zone.
- **Deployed:** Terraform for infrastructure, Argo CD for deploys, pinned image digests, CI with unit tests plus a contract test against the switch's message format.
- **Logged and monitored:**
  - OpenTelemetry trace from switch to scorer to store.
  - Prometheus metrics: scoring latency histogram, timeout rate, decisions by type, consumer lag, counter freshness.
  - A Grafana dashboard.
  - Alerts at scoring p99 > 50 ms and timeout rate > 0.1%.
- **Fail-open from commit one:** The switch has an 80 ms hard timeout and carries on with its existing logic. A kill switch stops the mirroring.

**Exit check:** A real production authorization produces a decision record in Iceberg that joins to a single trace ID. The latency metric and counter-freshness metric are visible on the dashboard. Killing the scorer pod causes zero failed authorizations.

## 4. Phases

**Phase 1: Event and data-contract foundation**
- **Unlocks:** Every feature, label, replay, audit and backtest.
- **Depends on:** The Phase 0 skeleton running in production shadow.
- **Tasks (widest impact first):**
  1. **Canonical transaction event schema.** Protobuf in the schema registry, BACKWARD_TRANSITIVE compatibility. A stable `txn_id` links the whole lifecycle: authorization, incremental authorization, reversal, clearing and later chargeback.
  2. **Decision record contract.** Stores the decision, score, reason codes, a **snapshot of the feature values used**, and the ruleset and model versions. This is the audit trail and the training join key.
  3. **Tokenization enforced in code.** The schema has no PAN field. CI rejects fields that match a card-number pattern. A data-loss-prevention scan runs on the topics.
  4. Deduplication on `txn_id + message type`; ordering per card through token partitioning.
  5. Retention of at least 13 months (Kafka tiered storage plus Iceberg), covering chargeback windows and a full year of seasonality.
  6. **Replay harness:** re-run a historical day through the scorer offline.
  7. Daily reconciliation of our counts against the switch.
- **Exit check:**
  - 100% of production authorizations are mirrored.
  - Reconciliation drift is under 0.01%.
  - Replaying a day with pinned versions reproduces the decision records exactly.

**Phase 2: Ground truth and features (two parallel tracks)**
- **Unlocks:** Measuring any rule or model, and serving features without training/serving mismatch.
- **Depends on:** Phase 1 IDs, retention and replay.
- **Tasks:**
  1. **Label pipeline.** Ingest fraud reports, chargebacks with fraud reasons, disputes and analyst decisions. Join them to `txn_id`. Apply the 90-day maturity policy. Keep **versioned label snapshots**. This is the widest task: it defines every metric.
  2. **Single feature-definition framework.** One definition compiles to both a Flink streaming job (online) and a point-in-time backfill on Iceberg (offline), with an automated test that the two match.
  3. **Entity state store and write policy.** State per card, merchant, device and merchant ID. An explicit rule for which events change state: declines count toward velocity, reversals decrement amount sums.
  4. About 20 starter features:
     - card velocity (count and amount) over 1 min, 1 h and 24 h
     - first-time merchant category for this card
     - country mismatch
     - card-not-present flag
     - time since last transaction
     - network risk score
  5. A freshness target per feature, plus **default-on-miss**: a missing feature gets a default value and a flag, never an error.
- **Exit check:**
  - Online and offline values agree for at least 99.9% of sampled transactions.
  - Feature freshness p99 is under 1 s.
  - A backfilled month's labels reconcile to within 5% of the fraud losses Finance reports.

**Phase 3: Decision engine v1 (rules, enforcement, analyst loop)**
- **Unlocks:** Real fraud prevention, and a baseline any model must beat.
- **Depends on:** Phase 2 features and labels, which make backtesting possible.
- **Tasks:**
  1. **Action contract with the switch.** Actions are approve, decline, or review (approve and queue for an analyst), mapped to response codes. Decline codes stay generic ("do not honor") so fraudsters can't probe the logic. Each action can be enforced independently. Widest task: it changes what customers experience.
  2. **Rules as code.** CEL expressions in git, two-person approval, and a required backtest (replay plus labels) reporting fraud caught and false-positive ratio before any merge.
  3. **Backup ruleset deployed into the switch**, so fail-open has real teeth.
  4. **Analyst case management (the human review loop).** A review queue whose decisions feed the label pipeline. Buy or build a thin tool.
  5. **Card-testing / BIN-attack rules:** bursts of small card-not-present authorizations per merchant or per card range.
  6. **Gradual enforcement:** shadow → review-only → declines on 1% of traffic → 100%.
- **Exit check:**
  - Rules are enforced on 100% of traffic.
  - p99 stays within budget under a load test at 2× peak.
  - Baseline dashboards show fraud bps and false-positive ratio.
  - Every decline traces to a ruleset version.

**Phase 4: ML model (shadow, then champion/challenger)**
- **Unlocks:** Catching more fraud at the same decline rate.
- **Depends on:** At least 6 months of matured labels, features proven consistent between training and serving, and the decision engine enforcing.
- **Tasks:**
  1. **Cost policy and thresholds.** A cost matrix weighing fraud losses against the cost of falsely declining good customers (including churn), signed off by Fraud Ops and Finance. It defines what "better" means.
  2. **Training pipeline.** Point-in-time joined data, time-based splits, LightGBM with pinned seeds, and the data hash recorded in MLflow.
  3. **Model serving interface.** The model runs in-process (Treelite or ONNX), is loaded by version from the registry, and is swapped through config.
  4. **Reason codes.** The top SHAP features are mapped to reason codes for analysts and regulators.
  5. **How decisions combine:** hard rules override → model score → calibrated threshold → action.
  6. Shadow for 2 to 4 weeks, then a canary at 5% → 50% → 100%.
- **Exit check:**
  - At the same decline rate, the model catches at least X% more fraud dollars than rules alone, on both the matured holdout and in production shadow.
  - p99 stays within budget.
  - Rolling back with one config change has been tested in production.

**Phase 5: Risk-tiered routing and step-up**
- **Depends on:** Calibrated model scores in production.
- **Tasks:**
  1. **Routing policy:** low risk takes a fast path that skips optional features; medium risk gets step-up (a 3DS/SCA challenge or an OTP for card-not-present); high risk is declined. PSD2 transaction-risk-analysis exemptions apply if we operate in the EU.
  2. Integration with the 3DS server.
  3. A "Was this you?" push or SMS, which also produces fast labels.
- **Exit check:**
  - Step-up conversion and fraud rate are measured per tier.
  - The fast path's p99 is measurably lower.

**Phase 6: Feedback and adaptation (automate only loops already proven)**
- **Depends on:** At least 2 manual retrain cycles completed successfully in Phase 4.
- **Tasks:**
  1. Drift monitoring: PSI per feature, plus the score distribution.
  2. Scheduled retraining with automated evaluation gates.
  3. Weighting for fast labels.
  4. Attack-response playbooks.
  5. Model-risk documentation in the style of the US model-risk guidance SR 11-7.
- **Exit check:**
  - An automated retrain produces a challenger that passes the gates and is promoted with no code change.
  - An injected drift in staging triggers the alert.

## 5. Cross-cutting concerns

| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|
| 0 | mTLS from switch to scorer; PAN tokenized at the switch; least-privilege IAM | Trace from switch to store; latency, timeout and lag metrics; alerts | Terraform, pinned image digests, CI contract test | 80 ms timeout with fail-open, 2 availability zones, kill switch |
| 1 | CI blocks PAN-like fields; data-loss scan on topics; encryption at rest | Schema-violation and reconciliation-drift metrics | Schema registry compatibility rules, immutable log, replay harness | Deduplication by `txn_id`, dead-letter queue, consumer-lag alerts |
| 2 | Personal data excluded from features; access to label data restricted | Freshness per feature, online/offline mismatch rate, label match rate | Versioned feature definitions and label snapshots | Default-on-miss, backfill handles late labels |
| 3 | Two-person rule changes, immutable audit log, generic decline codes, rule logic access-restricted | Decline and review rates per rule, analyst queue size and age | Rule versions in git, a backtest artifact for each change | Backup ruleset in the switch, a kill switch per rule, 2× load test |
| 4 | Model artifacts signed; registry access controlled; probing detection (repeated near-threshold attempts) | Score distribution, shadow-vs-champion comparison, inference latency | MLflow lineage (data hash, seed, code commit) | One-change rollback; on model failure, fall back to rules |
| 5 | 3DS/OTP integration over mTLS; OTP rate limits | Conversion and fraud per tier, step-up abandonment rate | Routing policy versioned in each decision record | Step-up provider outage → fall back to the rules tier |
| 6 | Poisoning checks on fast labels (watch for coordinated "it was me" confirmations) | Drift (PSI) alerts, retrain evaluation reports | Retrains reproducible from snapshot IDs | Automatic promotion blocked if gates fail; last good model pinned |

## 6. AI layer (adapted for an ML system with no LLM)
The skill's AI layer is written for LLM agents. Below it is mapped onto ML equivalents, with defenses and budgets first:

1. **Guardrail defense:** Here the threat is hostile input, not prompt injection: card testing, probing the threshold, and poisoning labels through false disputes or confirmations. Built in Phases 1, 3 and 6. *Exit check:* a replayed card-testing burst is caught within N transactions.
2. **Latency budget:** Scoring p99 ≤ 50 ms with an 80 ms hard timeout, plus the 5 ms rule for synchronous features. In place from **Phase 0**. *Exit check:* an injected slowdown triggers fail-open, and the metric shows it.
3. **Human review gating:** The review queue, two-person rule and threshold changes, and the cost policy sign-off. Phases 3 and 4. *Exit check:* every threshold change has an approver on record.
4. **Retrieval:** Online feature lookup from the store. Phase 2.
5. **Model access:** The in-process serving interface, swappable through config. Phase 4.
6. **Memory:** Per-entity state and its write policy. **Deliberate deviation:** this is built in Phase 2, *before* model access, because both rules and the model need these features to score at all. Learned behavioral profiles are deferred.
7. **Orchestration:** Rules override, then model, then thresholds. Phase 4.
8. **Routing:** Risk tiers and the fast path. Phase 5.
9. **Feedback:** Labels, analyst decisions, fast labels and retraining. Phases 2, 3 and 6. *Exit check:* a corrected label changes the next challenger's evaluation metrics.

## 7. Deliberately deferred
- **Graph features for fraud rings** (shared devices, merchant collusion). Pull forward when ring or bust-out fraud exceeds about 15% of losses.
- **Deep sequence models.** Pull forward under the model gate's flip condition.
- **Learned per-customer behavioral profiles or embeddings.** Pull forward when the tree model plateaus and holdout analysis shows lift from per-customer baselines.
- **Online or continuous learning.** Pull forward only after Phase 6 automated retraining has been stable for at least 3 cycles and attacks adapt faster than the retrain cadence.
- **Multi-region active-active.** Pull forward when the scheme or regulator demands it, or the downtime cost exceeds the cost of running it.
- **Splitting the scorer into microservices.** Pull forward under the monolith gate's flip condition.
- **LLM-written case summaries for analysts** (strictly outside the authorization path). Pull forward when analyst handling time is the bottleneck. It would need its own guardrail design.
- **Separate models per merchant or segment.** Pull forward when the global model under-performs on a segment worth more than X% of volume.
- **Account-takeover and application fraud.** Pull forward as a separate program; they have different data and labels.
