# Plan: CI/CD platform for 50 microservices

## 1. Classification and constraints
- **What:** A shared build, test, sign and deploy platform. All 50 microservices move onto it and their current pipelines are retired.
- **Type:** Infra plus software. Brownfield (assumed; see Missing inputs). Not a small build: many teams, R3 trust-boundary decisions, and it deploys to production.
- **Dominant constraint:** Correctness and security of the delivery path. One shared platform means one mistake reaches every service at once.
- **Worst failure:** Someone with a pull request, a stolen CI token or a tampered template ships code to production for many services. Second worst: the platform goes down and no service can ship an emergency fix.

**Missing inputs.** Each is followed by what changes if the assumption is false:
1. **Brownfield, with mixed existing pipelines** (assumed). If greenfield: Phase 0 uses the first new service, the waves become onboarding as services are created, and Phase 5 and V7 are dropped.
2. **Deploy target is Kubernetes** (managed clusters, one cloud, existing clusters per environment). If it is mostly VMs or serverless: the deploy-model row in §3 flips to push deploys with short-lived per-service OIDC roles. Admission control becomes signature checks at deploy time. Phase order stays the same.
3. **One Git host (GitHub or GitLab) across all 50 repos, and separate repos per service** (assumed). With a monorepo, Phase 1 adds build-graph and affected-target detection, and V3 is re-scoped.
4. **Compliance regime** (SOC 2, SOX, PCI or none). If regulated: Phase 2 adds separation of duties and evidence for change approvals, and retention gets a REQUIREMENT. This adds organizational dependencies but does not change the order.
5. **Service owners, criticality tiers, platform team size and budget.** Wave composition and V4 depend on these.

## 3. Key decisions (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Deploy model: push vs pull (sync vs async) | R3: this is where the production trust boundary sits | **Pull (GitOps).** CI builds, signs and pushes an image to the registry by digest, then opens a PR that bumps the digest in an environment config repo. Argo CD in each cluster pulls and applies it. CI never holds prod cluster credentials. | Deploy targets are Kubernetes | V2 | V2 fails, or the inventory shows most targets are not Kubernetes → push deploys with short-lived OIDC roles scoped per service and environment |
| Admission when signing or policy checks are unavailable (consistency vs availability) | R3: failing open bypasses the trust boundary, and that harm can't be undone | **Fail closed**, with an audited break-glass path | Break-glass works within the 30 min hotfix target | V2 (fail closed holds), V6 (break-glass works) | V6 fails → make admission highly available before more services are enforced. Never fail open |
| Data-privacy boundary | R3: a leaked secret or personal data in logs can't be taken back | No production data and no long-lived secrets in CI. Tests use synthetic fixtures. Logs are masked and kept 30 days. Services get runtime secrets from the existing secret manager. | No service's tests need production data | V2 (its test cases include secret leaks) | A service needs prod-like test data → build a separate masked-data pipeline with its own gate |
| Pipeline contract (how a service declares build, test and deploy) | R2: 50 repos consume it, so changing it means coordinated change across teams | Versioned reusable templates (GitHub reusable workflows or GitLab includes), one per archetype, pinned by semver tag. Each repo has a `service.yaml` with only declared parameters, plus one declared custom-step slot. Renovate opens the PRs that bump template versions. | A few archetypes cover the fleet | V1 | V1 fails → more archetypes or a wider escape hatch, and wave sizes are re-planned |
| Artifact identity and provenance | R2: changing it later means re-signing artifacts and rewriting admission policy everywhere | Immutable OCI digests. Signed with cosign using a cloud KMS key (not keyless, so repo names stay out of public transparency logs). SLSA provenance and an SBOM (syft) attached to each image. | Admission can verify all three fast enough | Phase 1 pilot: sign and verify on every archetype | Offline or air-gapped verification needed → bundle keys and attestations with the artifact |
| Build vs buy: CI engine | R2 | Buy: use the CI built into the existing Git host | One Git host is standard across all repos | Phase 1 pilot | Mandated on-prem or air-gapped CI → self-hosted engine, and re-plan |
| Runner hosting | R2 | Vendor-hosted runners. Fork and PR builds run isolated with no secrets. | Hosted capacity and cost hold up | V3, V4 | V3 or V4 fails → self-hosted, autoscaled runners (Actions Runner Controller on Kubernetes) for the heavy archetypes |
| Platform shape (monolith vs services) | R2 | Assemble managed and OSS parts with thin glue. No custom platform services and no portal in v1. | Small platform team | Phase 3 exit: platform toil per week stays within team capacity | Repeated manual onboarding work swamps the team → build a self-service layer (see §10) |
| (Brownfield) Migration strategy, coexistence, system of record, rollback | R2 | **Replatform the pipelines, not the services.** Before cutover, the new path deploys a separate internal-only deployment and Argo CD does not manage the user-facing one. **minor defaults:** Kyverno for admission (`verifyImages`); Argo Rollouts for canaries; syft for SBOMs; build cache in the vendor's cache; notifications to the owning team's chat channel; existing linters and test runners kept per language.
**N/A:** prompt+RAG vs fine-tune and hosted vs self-hosted model (no AI component); tenancy model (one organization; team access is handled in V2's RBAC).
**Kept as they are (cost to change):** Git host and repo layout (months, every repo); existing clusters and environment set (weeks per environment); observability stack and secret manager (weeks, cross-team). The plan uses these and does not redesign them.

## 4. First end-to-end slice (Phase 0)
- **The real request:** a real commit to `main` of one low-risk, stateless service with a willing owner. The response is that exact commit running in the production cluster, answering a real HTTP request, and visible on one trace.
- **Tiers crossed:**
  1. Git host (protected `main`)
  2. CI job on a hosted runner using template v0
  3. Unit tests
  4. Image build
  5. Signing, SBOM and provenance
  6. Registry push by digest, authenticated with OIDC (no static keys)
  7. Auto-PR to the environment config repo
  8. Argo CD syncs staging, then a manually approved sync to prod
  9. Kyverno checks the image in **audit mode**
  10. Prod cluster and the service pod
  11. Telemetry
- **Deployed:** by the pipeline itself. The platform's own pieces (Argo CD, Kyverno, OIDC roles, registry) are Terraform/Helm in a platform repo.
- **Logged:** CI and Argo CD logs go to the central log store, tagged with commit SHA and image digest.
- **Monitored:**
  - CI run, deploy event and service request share one trace (OpenTelemetry exporter for CI, deploy annotations on dashboards).
  - Alerts fire on a failed `main` build, an Argo CD sync that fails or degrades, and service health.
- **Rolled back:** `git revert` in the environment repo, then Argo CD syncs the previous digest.
- **Who can reach it:** the new path deploys `<svc>-next`, a separate deployment in the prod namespace. It is routed only for requests carrying an internal header from the corporate network. User traffic stays on the deployment built by the old pipeline, which remains the source of truth and the fallback. Only the platform team and the service owner can change templates and the environment repo.
- **Alongside:**
  - Inventory all 50 services: language, build tool, deploy target, database migrations, secrets, owner, criticality, and what depends on the old pipeline (each marked CONFIRMED or ASSUMED).
  - Export baselines from current CI history: builds per day, peak concurrency, durations, spend.
  - Start the organizational items in §2.

**Exit check (V0):**
- A real commit reaches prod `<svc>-next` with one trace across every tier.
- One deploy and one rollback succeed through the pipeline.
- A build with a deliberately failing readiness probe fires the sync-degraded alert.
- First values are recorded as baselines: commit-to-prod time, queue time, cost per run.

## 5. Phases

- **Phase 1: Pipeline contract and artifact identity** (the change that would cause the most rework if wrong)
  - **Unlocks:** contract v1 and the wave plan.
  - **Depends on:** V0 and the Phase 0 inventory.
  - **Tasks:**
    1. Cluster the inventory into archetypes.
    2. Write the `service.yaml` schema and template v1 per archetype, with semver tags and Renovate bump PRs.
    3. Fix the artifact identity scheme (digest, tags, KMS signing, SBOM, provenance) and the environment repo layout (an app-of-apps per environment).
    4. Pilot one service per archetype (about 4–6) through staging, plus an internal-only prod `-next` deployment.
    5. Set registry lifecycle rules (30-day non-release retention, release artifacts kept).
    6. Run V1.
  - **Rollback:** pilots return to template v0 or their old pipeline; no user traffic is affected.
  - **Exit check:** V1 passes; contract v1.0 is tagged; each pilot builds with a cold cache.

- **Phase 2: Trust boundary and production admission** (controls the worst failure)
  - **Unlocks:** user traffic on the new path.
  - **Depends on:** Phase 1 and the security lead's review slot.
  - **Tasks:**
    1. Scope OIDC trust per repo, branch and environment. CI's only cloud permission is registry push from protected branches.
    2. Remove static credentials from the new path.
    3. Add CODEOWNERS and required reviews on the templates and environment repos.
    4. Give fork PRs no secrets.
    5. Turn on secret scanning and push protection, and log masking.
    6. Write Kyverno policies as code, with tests: signed by the platform key, approved registry only, digest-pinned.
    7. Enforce them on the pilot `-next` namespaces only.
    8. Run Kyverno with 2+ replicas and document its failure policy.
    9. Build the break-glass procedure (time-boxed role, page on use, after-the-fact review).
    10. Run V2, then V6.
  - **Rollback:** admission back to audit mode per namespace. User traffic is still on the old pipelines.
  - **Exit check:** V2 and V6 pass; deploy and break-glass audit logs reach the SIEM.

- **Phase 3: Safe delivery, capacity, and wave 1** (the pilots take user traffic)
  - **Unlocks:** waves at scale.
  - **Depends on:** V2, V6, and the deploy SLO input.
  - **Tasks:**
    1. Add Argo Rollouts canaries with automated analysis on the service's SLO metrics (steps 5% → 25% → 100%).
    2. Add a pre-deploy database migration job (expand/contract, least-privilege database role).
    3. Cut over the pilots (Argo CD adopts the user-facing deployment; old deploy step switched off). Promotion to prod still needs manual approval.
    4. Enforce admission on the pilots' namespaces.
    5. Run V5 on the pilots; when it passes, enable auto-promotion.
    6. Run V3 as a synthetic load test.
    7. Start metering cost per run for V4.
    8. Publish DORA metrics dashboards.
  - **Rollback:** per service, flip the source-of-truth flag back, pause Argo CD auto-sync, switch the old deploy step back on.
  - **Exit check:** V5 and V3 pass; pilots deploy to users only through the new path; platform toil per week is within the complexity budget.

- **Phase 4: Migration waves** (exposure grows from smallest to largest)
  - **Unlocks:** the whole fleet on the platform.
  - **Depends on:** V3 (before wave 2); V4 and any procurement (before wave 3).
  - **Tasks:**
    1. Wave 2: about 10 low-criticality stateless services.
    2. Wave 3: about 20 services.
    3. Wave 4: the remaining 14 or so, including tier-1, stateful and odd-case services.
    4. Each wave: a generated onboarding PR, owner review, a week on the internal `-next` deployment, cutover, then admission enforced on that namespace.
    5. Re-point what depended on the old pipelines (package publishing, change tickets, release notes) as each service moves.
    6. A wave halts if change-failure rate or queue time goes past its baseline or its V3 bar.
  - **Rollback:** per-service flag, as in Phase 3.
  - **Exit check:** all 50 services deploy only through the platform; the lead-time target is set and tracked.

- **Phase 5: Retire the old pipelines and enforce everywhere**
  - **Unlocks:** a single delivery path; old credentials gone.
  - **Depends on:** V7 per service, the retention requirement, and V6 re-run at full fleet.
  - **Tasks:**
    1. Export and archive each old pipeline's config.
    2. Revoke its prod credentials and delete its static secrets.
    3. Enforce admission on the whole cluster (deny anything not admitted through Argo CD).
    4. Turn on drift detection.
    5. Rehearse rebuilding the platform from Git (V6 re-run).
  - **Point of no return:** revoking a service's old credentials, guarded by V7. The archived config allows reconstruction, but only after new credentials are issued (days).
  - **Exit check:** zero deploys outside Argo CD over 30 days; old credentials are reported revoked.

## 10. Deferred
- **Developer portal or self-service scaffolding (e.g. Backstage):** pull forward when onboarding toil goes past platform team capacity, or the fleet grows well beyond 50.
- **Self-hosted runner fleet:** pull forward if V3 or V4 fails.
- **Preview environment per PR:** pull forward when teams ask for it and V4 shows cost headroom.
- **Hermetic builds and higher SLSA levels:** pull forward on a compliance or customer requirement (Missing input 4).
- **Monorepo build-graph tooling (e.g. Bazel):** pull forward if the repo layout turns out to be a monorepo, or feedback p90 misses V3 on large repos.
- **Multi-region or multi-cluster rollout orchestration:** pull forward when a service needs active-active deploys.
- **Per-team cost chargeback:** pull forward when the V4 projection comes within 20% of budget.
- **Test-data masking pipeline:** pull forward when a service's tests need prod-like data (§3 privacy row).
