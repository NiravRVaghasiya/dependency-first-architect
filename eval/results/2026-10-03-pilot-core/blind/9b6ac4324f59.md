# Plan: Moving the Patient Scheduling System to the Cloud Without Downtime

I don't know your vendor, database, cloud provider or integrations, so this plan is written to work across most setups. The questions at the end are what you'd need to answer to make it specific.

**The core idea:** never let two systems accept bookings at the same time. Copy data to the cloud continuously while the on-prem system stays in charge. Then switch which system takes new bookings in one quick, rehearsed step that you can undo. Users should see at most a few seconds of slowness, not an outage.

---

## Phase 0: Governance and compliance (weeks 1–4)

- **Business Associate Agreement (BAA)** signed with the cloud provider (HIPAA in the US; GDPR or local health-data laws elsewhere). Use only services the BAA covers.
- **Security review:** encryption in transit and at rest, customer-managed keys, audit logging, access controls, network separation, and keeping data in the required region. Update your HIPAA risk analysis.
- **Clinical sponsor:** someone like the CMIO or nursing informatics lead who signs off on go/no-go and patient-safety risk.
- **Change governance:** the plan goes through the change advisory board (CAB), with a change freeze around cutover.
- **Vendor check:** if the scheduling software is commercial, confirm the vendor supports your target cloud setup and licensing. Many won't support self-hosting it in the cloud, or only on certain configurations.

## Phase 1: Discovery and dependency mapping (weeks 2–6)

Integrations are where scheduling migrations usually fail. List every connection:

| Category | Typical examples |
|---|---|
| Inbound feeds | ADT (patient admit/transfer feeds), provider/resource master files, orders that trigger scheduling |
| Outbound feeds | HL7 SIU messages (appointment updates) to the EHR, billing/eligibility, lab, radiology |
| Interface engine | Mirth, Rhapsody, Cloverleaf, Ensemble: routes, IP allowlists, certificates |
| Patient-facing | Portal, online booking, SMS/email/phone reminders, kiosks |
| Internal | Call center/phone system, reporting/data warehouse, single sign-on |
| Hidden | Scheduled jobs, file drops, hard-coded IPs/hostnames, ODBC report users, printers |

Also capture:
- **Baselines:** peak load (often Monday mornings and call-center opening), message volumes, response times, database size, and how fast data changes.
- **Targets:** maximum acceptable data loss and recovery time (RPO/RTO) for the new environment. Aim for at least as good as today.

## Phase 2: Target architecture (weeks 4–8)

- **Hybrid network:** a dedicated private link to the cloud (AWS Direct Connect, Azure ExpressRoute or GCP Interconnect) with a site-to-site VPN as backup. Plan for the possibility that the hospital's internet link fails while the cloud is fine, and decide how users reach the app if it does.
- **Spread across availability zones:** application and database spread over at least two zones. Add another region for disaster recovery if your recovery-time target needs it.
- **Keep the app and its database together.** Don't run the app in the cloud against an on-prem database (or the reverse) for long. Scheduling apps make many small database calls, and the network delay between sites hurts performance.
- **One switch point:** put a load balancer or proxy in front of the app, and a stable DNS name or connection endpoint in front of the database, so cutover is a configuration change, not a reinstall.
- **Interface engine:** decide whether it moves first, moves with the scheduling system, or stays on-prem. Moving it first, or putting it in a hybrid setup, makes cutover simpler.
- **Infrastructure as code** (Terraform, Bicep, etc.) so environments are identical and can be rebuilt.

## Phase 3: Build and continuous replication (weeks 8–14)

1. Build the cloud environment and harden it to your security baseline.
2. Do a first full copy of the data, then **keep it in sync continuously**, using the database's own replication (SQL Server Always On/distributed availability groups, Oracle Data Guard or GoldenGate, PostgreSQL logical replication) or a migration service (AWS DMS, Azure DMS).
3. Track replication lag all the time. It must sit near zero at peak load before you're allowed to cut over.
4. **Daily reconciliation:** compare row counts and checksums by date, provider and location. Also check that the next 90 days of appointments match exactly.

## Phase 4: Testing (weeks 12–18)

- **Shadow traffic:** replay real read and search traffic against the cloud copy and compare results and response times.
- **Load test** at 1.5–2× your measured peak.
- **Integration testing:** end-to-end with test environments for the EHR, portal, reminders and billing, including SIU message order and acknowledgments.
- **Clinical user acceptance testing:** schedulers, call center and clinic front desks run real workflows (booking, rescheduling, overbooking, recurring appointments, multi-resource bookings).
- **Failure tests:** take down an availability zone, cut the network link, and fail the database over.
- **Rehearse cutover and rollback at least twice** in a production-like environment, and time every step.

## Phase 5: Cutover (one rehearsed window)

**Timing:** lowest-volume period, such as early Sunday morning. Avoid holidays, month-end billing and EHR upgrade windows. It's zero-downtime, but you still want the smallest possible impact if something goes wrong.

**Before you start:**
- Downtime procedures are ready: printed or exported schedules for the next 72 hours at every clinic, plus paper booking forms. This is a safety net, not the plan.
- A command center is staffed: IT, DBA, interface team, vendor, clinical liaison and help desk.
- Go/no-go criteria are met: replication lag under a few seconds, reconciliation clean, rehearsals passed.

**Sequence (the switch itself takes seconds to a few minutes):**
1. Pause the interface engine's outbound queues. Messages build up safely instead of being lost.
2. Put the on-prem app into read-only mode, or hold new connections at the proxy. Users see a brief spinner, not an error.
3. Confirm replication has fully caught up and the final checksums match.
4. Promote the cloud database to primary and set up **reverse replication back to on-prem** so you can roll back.
5. Point the load balancer, DNS and interface endpoints at the cloud.
6. Release the held connections and resume the interface queues.
7. **Smoke tests:** book, reschedule and cancel a test patient. Check the EHR received the SIU message, and check a portal booking and a reminder.

**Rollback trigger:** if a predefined condition is hit (errors above a set rate, interfaces failing, data mismatch), reverse the steps. On-prem is current because of reverse replication.

**Phased alternative:** if your system can separate data by location, cut over one clinic or department at a time. This lowers risk but adds complexity, because every location needs one clear system of record at any given moment.

## Phase 6: Stabilization (weeks 1–4 after cutover)

- Hypercare: help desk staff on site with users, daily check-ins, and close watching of performance, interface errors and replication.
- Keep on-prem warm with reverse replication for 2–4 weeks as a rollback option.
- Run a disaster recovery failover test in the new environment.
- Then decommission on-prem: final archive, data retention per policy, certified media destruction, and updated runbooks, network diagrams and BAA records.

## Key risks

| Risk | Mitigation |
|---|---|
| Double bookings from two active systems | Only one system accepts bookings at any moment; never write to both |
| A missed integration | Discovery plus a network traffic capture on the old servers before decommissioning |
| Messages lost during the switch | Pause and queue at the interface engine, then reconcile message counts |
| Hospital internet link failure | Backup links; decide how users reach the app if the link is down |
| Vendor won't support the setup | Confirm in writing during Phase 0 |
| Users affected | Low-volume window, communication plan, staff on site, downtime procedures ready |

## Rough timeline

About 4–6 months to cutover plus 1 month of stabilization, depending on the number of integrations and vendor involvement.
