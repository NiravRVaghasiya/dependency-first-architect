# BUILD PLAN — Customer-Support RAG Chatbot over Help-Center Docs

## 1. Classification
- **What:** A customer-facing chat assistant that answers support questions from your help-center articles, cites its sources, and hands off to a human when it can't answer.
- **Type:** Mostly AI. Underneath it is ordinary software: a chat API, an ingestion pipeline and a widget.
- **Dominant constraint:** Correctness. Every answer must come from the docs and cite them. Latency and cost come second.
- **Worst failure:** The bot states a policy, refund or commitment that isn't in the docs, and the customer treats it as binding. A close second is exposing internal-only content.
- **Assumptions (please confirm):** Docs live in a hosted help center (Zendesk Guide, Intercom or similar) with an API or webhooks. Customers aren't logged in for v1. Postgres is already in your stack. English only at launch.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| Consistency vs availability | **Availability, with the index allowed to lag.** The index can trail the help center by ≤15 min. If the LLM is down, show top article links instead of failing. | Docs gain time-critical content (outage status, live pricing) → switch to webhook-driven reindex with a freshness SLA. A stale answer causes a real incident → tighten the lag. |
| Monolith vs services | **One chat service** (API + retrieval + orchestration) **plus a separate ingestion job**. | Ingestion load interferes with chat latency, or separate teams own retrieval and chat. |
| Sync vs async | **Sync with streaming** for chat. **Async** for ingestion and evals. | p95 total latency stays above budget after routing → move slow steps (groundedness check) async or speculative. |
| Build vs buy (whole product) | **Build a thin custom path and buy the parts** (LLM API, managed Postgres, tracing). Week 1: run your helpdesk vendor's native AI bot on the same eval set as a bake-off. | Vendor bot scores within ~5 pts of ours on groundedness and deflection at acceptable cost → **buy it** and stop at Phase 1. |
| Vector store | **pgvector on existing Postgres**, hybrid with full-text search. | More than ~5M chunks, or p95 retrieval above 150 ms after indexing → dedicated vector DB. |
| (AI) prompt+RAG vs fine-tune | **Prompt+RAG.** It's reversible and the docs change. | Retrieval recall is good (≥0.9) but tone or format still fails evals after prompt iteration, **and** there are ≥1k labeled examples → fine-tune for style only, never for facts. |
| (AI) hosted API vs self-host | **Hosted API** with a DPA and zero data retention. Model ID pinned. | A data-residency or regulatory requirement, or cost at volume exceeding about 2× the self-host total cost. |
| (AI) Data-privacy boundary | **Index only public articles. No customer account data. PII redacted before logging and before the LLM.** Every chunk carries an `audience` field from day one, even though v1 only uses `public`. | Product wants account-specific answers → needs customer auth plus per-user ACL filtering at retrieval. Making that cheap is why `audience` is in the schema now. |
| Actions vs answers | **Answer-only. The bot never executes actions** (refunds, account changes). | Deflection plateaus and the top unresolved intents are actions → add allow-listed tools behind human approval (Phase 2 rules). |

## 3. Walking skeleton (Phase 0)
- **Request → response:** A staff member asks "How do I reset my password?" in the prod widget. It returns a streamed answer citing the correct article URL.
- **Tiers crossed:**
  1. Widget on the help-center page, behind a feature flag (staff only)
  2. API gateway with rate limiting
  3. Chat service (single container, e.g. FastAPI)
  4. Retrieval: pgvector over ~20 top articles, embedded by a committed script
  5. Hosted LLM
  6. Response with a citation, back to the widget
- **Deployed:** Through your existing CI/CD to your container platform, infrastructure as code (Terraform), flag-gated.
- **Logged and monitored on day zero:**
  - OpenTelemetry traces across every tier, plus LLM spans (prompt version, model ID, tokens, retrieved chunk IDs) in Langfuse or similar.
  - Metrics: requests, p50/p95 latency, tokens, cost per request, top retrieval score, status (answered / fallback / error).
  - A dashboard, plus alerts on 5xx rate and p95 latency.
  - PII redaction on logs from the first commit.
- **Exit check:** That real request returns a cited answer in prod. One trace shows all tiers and the cost metric is on the dashboard. Killing the LLM key produces the "here are articles that may help" fallback, not an error.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 1: Contracts and eval harness (the base everything else is measured on)**
- Unlocks: Every later change is scored, not judged by feel. The buy-vs-build bake-off becomes possible.
- Depends on: The Phase 0 skeleton running in prod.
- Tasks:
  1. Freeze the **document/chunk schema**: `doc_id, version, content_hash, url, title, section_path, audience, locale, updated_at`. Every later phase reads it.
  2. Freeze the **answer contract**: `{status: answered|abstained|handoff, answer, citations[{doc_id, chunk_id, url}]}`.
  3. Build a **golden eval set**:
     - ~200 questions from real resolved tickets, each with its expected source article
     - ~30 out-of-scope questions (should abstain)
     - ~20 adversarial questions (injection, asking for policy exceptions)
  4. Add an **eval runner in CI** measuring recall@5, groundedness (LLM-judge plus 10% human spot-check), correct abstention, latency and cost.
  5. Run the vendor bake-off.
- Exit check: CI posts baseline eval numbers for the skeleton on every PR, and the bake-off result is recorded. If the vendor bot meets the flip condition, stop here and buy it.

**Phase 2: Defenses, budgets, human-in-the-loop (AI layer steps 1–3)**
- Unlocks: Exposure to untrusted input and real traffic.
- Depends on: The answer contract (to enforce `abstained` and `handoff`) and the eval set (to prove the defenses work).
- Tasks:
  1. **Trust separation:** system prompt and policy are trusted; retrieved chunks and user text are wrapped as data.
  2. **Never-commit policy:** refunds, billing disputes, legal, security and account changes always go to `handoff`.
  3. **Budgets:** token cap per request, turn cap per session, timeout.
  4. **Human handoff:** create a helpdesk ticket with the redacted transcript.
  5. **Filters:** input PII redaction; output check that blocks uncited claims and policy commitments.
- Exit check: An injection string planted in a test article doesn't change behavior. "Can I get a refund outside 30 days?" produces a handoff, not a promise. A runaway prompt is cut off at the cap and emits a metric. Every handoff is audit-logged.

**Phase 3: Retrieval at full corpus**
- Unlocks: Answers across the whole help center.
- Depends on: The frozen chunk schema and the eval harness.
- Tasks:
  1. **Ingestion pipeline:** help-center API full sync plus webhooks, idempotent on `content_hash`, deletions handled. A stale or deleted doc is the widest-impact retrieval bug.
  2. **Chunking** by heading structure.
  3. **Hybrid search** (pgvector + Postgres full-text).
  4. **Reranker.**
  5. **Relevance threshold** that triggers `abstained`.
  6. **Shadow mode:** run the bot on incoming tickets and have agents rate the drafts. Customers don't see them.
- Exit check: recall@5 ≥ 0.9 on the golden set. A deleted article leaves the index within 15 min. Shadow-mode agent rating reaches ≥80% "usable".

**Phase 4: Model access hardening**
- Unlocks: Swapping models, and staying up through provider outages.
- Depends on: Retrieval proven, so model comparisons measure the model and not retrieval noise.
- Tasks:
  1. Provider abstraction with config-driven model ID.
  2. Validate structured output against the answer contract, with one retry.
  3. Retries with backoff, plus a fallback model.
  4. Prompt registry (versioned files).
- Exit check: The model is swapped via config with no code change and evals rerun. A forced primary outage serves from the fallback.

**Phase 5: Conversation (memory, then orchestration)**
- Unlocks: Multi-turn support ("what about on mobile?").
- Depends on: Stable model access.
- Tasks:
  1. **Session memory:** last N turns, server-side, TTL 24h, redacted, nothing stored across sessions.
  2. **Orchestration chain:** query rewrite from history → retrieve → answer → groundedness check → contract validation.
  3. **Ramp to 5%** of logged-out visitors.
- Exit check: The multi-turn eval subset passes, each chain step appears as its own span, and the 5% cohort meets the groundedness target (≥95%).

**Phase 6: Routing**
- Unlocks: Lower cost and latency without losing quality.
- Depends on: The orchestration chain and its per-step cost data.
- Tasks:
  1. Intent/difficulty classifier.
  2. Single-article FAQ questions go to the cheap model. Multi-doc or ambiguous questions go to the strong model. Sensitive intents or frustrated users go straight to a human.
- Exit check: Cost per conversation drops without the eval score dropping, and every routing decision is logged.

**Phase 7: Feedback loop and full rollout**
- Unlocks: Continuous improvement and 100% traffic.
- Depends on: Routing and the full eval pipeline.
- Tasks:
  1. Thumbs up/down, plus "did this resolve your issue?"
  2. Handoff reasons and agent corrections feed the eval set.
  3. Weekly **doc-gap report** for the docs team (questions that were abstained or answered badly).
  4. Ramp 5% → 25% → 100%, gated by eval metrics and deflection.
- Exit check: A captured correction becomes an eval case, and a later fix measurably moves that metric. 100% rollout holds the targets for 2 weeks.

*All numeric targets above are starting points. Calibrate them against the Phase 1 baseline.*

## 6. AI layer

| # | Sublayer | In this system | Exit check |
|---|---|---|---|
| 1 | Injection / guardrails | Retrieved docs and user text treated as data. Output must be cited. No policy commitments. | A planted injection doesn't change behavior. |
| 2 | Cost + latency budget | Starting targets: ≤4k input tokens per call, ≤10 turns per session, p95 first token <2s and total <6s, ~$0.05 per conversation. Calibrate in Phase 1. | A runaway session is cut off and the metric fires. |
| 3 | Human-in-the-loop | No actions in v1. Sensitive intents and low-confidence answers hand off to a ticket. Shadow mode before customers see anything. | Handoffs are created and audit-logged. Shadow ratings are recorded. |
| 4 | Retrieval | Heading-aware chunks, hybrid search, reranker, abstain threshold, `audience` filter. | recall@5 ≥ 0.9 on the golden set. |
| 5 | Model access | Thin provider interface, schema-validated output, fallback model. | Swap via config. Outage served by fallback. |
| 6 | Memory | Session-only, last N turns, 24h TTL, redacted. No long-term memory. | Follow-ups resolve correctly. Nothing persists past the TTL. |
| 7 | Orchestration | A single linear chain: rewrite → retrieve → answer → verify. No agents. | Each step is traced. The multi-turn subset passes. |
| 8 | Routing | Cheap model for FAQs, strong model for complex questions, humans for sensitive ones. | Cost drops at equal eval score. Routes are logged. |
| 9 | Feedback | Thumbs, resolution signal and agent corrections feed evals and the doc-gap report. | A correction moves a later metric. |

## 7. Deliberately deferred
- **Account-aware answers** (order status, plan details). Pull forward when customer auth is in the widget and per-user ACL retrieval is designed. The `audience` field already prepares for it.
- **Actions/tools** (refunds, password resets). Pull forward when the top unresolved intents are actions; each then needs allow-listing and human approval.
- **Agent-assist copilot for human agents.** Pull forward if the Phase 3 shadow results are strong but customer-facing risk tolerance is low. It reuses the same backend.
- **Multilingual.** Pull forward when non-English traffic passes ~10% or localized docs exist (`locale` is already in the schema).
- **Fine-tuning.** Only when the prompt+RAG gate's flip condition is met.
- **Long-term cross-session memory.** Pull forward when repeat-contact data shows users re-explaining context, and only after a privacy review.
- **Dedicated vector DB or self-hosted models.** Only when their gate flip conditions are met.
- **Multi-agent orchestration.** Not until a single chain clearly fails a measured task class.
- **Voice/phone channel.** When chat deflection is proven and the latency budget allows it.
