# BUILD PLAN: Real-time collaborative document editor

The request gives no scale, content model, offline requirement or compliance context, so I planned on these assumptions:

- **A1.** Hosted service (SaaS) for outside users, built from scratch.
- **A2.** Rich text: headings, lists, marks, links and images.
- **A3.** Works online first, and can survive short offline gaps.
- **A4.** One cloud region, and no regulated data beyond ordinary personal data under GDPR.
- **A5.** No AI features.

If A1 is false (customers run it themselves, or on air-gapped sites), Phase 0 needs an exception. If A3 is false (users work offline for days), the default merge choice stays, but Phase 2 grows. If A4 is false (data must stay in a given country, or end-to-end encryption is needed), §3 rows 3, 6 and 7 change before Phase 1 is specified.

## 1. Classification and constraints
- **What:** A browser editor where many users edit the same rich-text document at once and see each other's changes live. It also needs sharing, permissions and stored history.
- **Type:** Software, built from scratch. Not a small build: it has outside users, their personal data and several hard-to-reverse (R3) decisions.
- **Dominant constraint:** Correctness: every user's copy must end up identical and no edit may be lost. Latency comes second.
- **Worst failure:** An edit the server already confirmed is silently lost, or users' copies drift apart, and nobody notices. Gates V1 and V2 guard against this, and the divergence detector (Phase 1) watches for it in production. The next worst is a user seeing a document they have no right to see, which V4 guards.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Local keystroke apply | ≤16 ms p99 | ASSUMPTION (one 60 Hz frame) | V1 |
| Keystroke shown on another user's screen (same region) | p95 ≤200 ms, p99 ≤500 ms | ASSUMPTION (usual feel of collab editors; product to confirm) | V5 |
| Editors per document | 50 at the latency budget | ASSUMPTION | V5 |
| Peak concurrent sessions (total) | UNKNOWN: product supplies the expected peak; needed before V5 (Phase 4) | UNKNOWN | V5 |
| Large-document load | ~1 MB text with 100k edits of history loads ≤1 s, ≤50 MB memory | ASSUMPTION (upper end of normal documents) | V1 |

**Missing inputs:**
- A1–A5 above.
- Peak concurrency and the cost ceiling.
- Whether data must stay in a given region.
- Who the security reviewer is.

## 3. Tradeoff gates (resolved up front)

| # | Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|---|
| 1 | How concurrent edits merge (the consistency model) | R3: the stored format and the sync protocol are locked once real documents exist | CRDT (Yjs + y-prosemirror). Every copy ends up identical without the server deciding order. The server relays, checks and stores edits | Yjs merges correctly on our content schema and is fast enough at our document sizes | V1 | V1 fails → server decides edit order with operational transforms (ShareDB), and Phase 1 is re-planned |
| 2 | Consistency vs availability | R3: users see these semantics directly | Editing keeps working during network splits (edits apply locally and merge later). Permissions stay strictly consistent: the server is the authority and checks every incoming edit | Users accept merge-later behavior for text | V1 (edits), V4 (revocation) | A requirement for locked or serial editing → add section locks that stay strictly consistent |
| 3 | Document data model and identifiers | R3: real data | Postgres tables: `documents` (random 128-bit IDs), append-only `updates` (doc_id, seq, bytes, user, client, ts), `snapshots`. Content schema v1 carries a version number; clients below the minimum schema version are rejected at connect | Old clients can be forced to upgrade | V3, V2 | V3 fails → migrate each document's schema version on the server, with the min-version gate kept |
| 4 | When the server confirms an edit | R3: getting it wrong loses edits for good | Confirm only after the Postgres commit, using a managed HA database with synchronous replication | The commit stays within the latency budget | V2 | V2 fails, or commit p99 breaks the budget → commit in batches, with the client keeping edits until a checkpoint confirms them |
| 5 | Trust boundary and permission model | R3: rework touches every entry point and leaks are customer-visible | Managed OIDC login. Per-document roles (owner, editor, commenter, viewer) checked on the server: on WebSocket connect, on every incoming edit and on every REST, history or export call. Share links are random, revocable tokens | No org-level policy or SSO needed for beta | V4 | An enterprise deal needs SSO, SCIM or org policies → add an organization layer before Phase 5 |
| 6 | How customers are separated (tenancy) | R3: isolation | Shared Postgres, `workspace_id` on every row, enforced by Postgres row-level security | No contract requires dedicated isolation | V4 (cross-workspace tests) | A contract requires a dedicated database or a specific region |
| 7 | Privacy boundary | R3: leaked content cannot be recalled, and the region choice is hard to move | Document content is treated as customer-confidential. It never goes into logs, traces, error reports, analytics or session replay; telemetry records only IDs and sizes. Encrypted at rest, one region | A4 | V4 (planted-string scan) | A data-residency requirement → deploy per region (§10) |
| 8 | Build vs buy for the collaboration backend | R2 now (swapping a library). Would be R3 if hosted (documents would live at the vendor) | Self-host open-source Yjs, Hocuspocus and TipTap. Buy login, Postgres and Redis as managed services | The team can staff on-call for a WebSocket service | V5 (cost and operations) | The team cannot staff on-call, or V5's cost check fails → evaluate a hosted collab backend (Liveblocks or Tiptap Cloud) with a DPA, before beta data exists |
| 9 | One service vs several | R2: splitting the sync tier takes weeks | One TypeScript service. The REST and WebSocket sync roles share an image; a background-worker role runs from the same image with another entry point | The sync and API roles scale together | V5 | V5 shows the sync tier needs to scale on its own → split it out |
| 10 | Sync vs async work | R2 | Live sync over WebSocket. Storing an edit happens inline, before it is confirmed. Compaction, export and notifications run async on a Postgres-backed queue (pg-boss) | Queue lag stays within minutes | Phase 2 exit check | Queue lag stays over 5 min → move to a dedicated queue |
| 11 | Spreading edits across server replicas | R2 | Redis pub/sub between replicas | Redis handles the message load at peak | V5 | V5 shows Redis CPU over 60% or p95 over budget → route each document to one server (consistent hashing) |

**R1 defaults:**
- TypeScript throughout.
- TipTap on ProseMirror for the editor.
- y-indexeddb for the client cache and the offline queue.
- GitHub Actions for CI, Terraform for infrastructure, containers on managed ECS.
- OpenTelemetry plus Grafana for monitoring.
- Sentry for errors, with content scrubbing.
- Unleash for feature flags.

**N/A:** The AI rows (A5: no AI component). The migration and cutover rows (built from scratch).

## 4. Walking skeleton (Phase 0)
- **Request:** An internal user types one character into a document in browser A. It shows up in browser B, used by a second internal user connected to the *other* server replica. A reload in either browser still shows it.
- **Tiers:**
  - Browser: TipTap + Yjs.
  - CDN serving the static app.
  - Load balancer (WebSocket upgrade).
  - Sync service (Hocuspocus, 2 replicas). It checks the login token on connect.
  - Postgres: the edit is appended to `updates` before it is confirmed.
  - Redis pub/sub carries the edit to replica 2, then to browser B.
  - There is also one REST call: create the document.
- **Deploy, logging, monitoring, rollback:**
  - **Deploy:** GitHub Actions builds an image pinned by digest, then deploys to staging and then production, all set up with Terraform.
  - **Logs:** Structured, with trace ID, document ID, edit size and user ID. No document content.
  - **Monitoring:** One OpenTelemetry trace from client send → store → fan-out → apply on the other client (the client reports its timings). Metrics: open connections, store latency, fan-out latency, errors. Alerts fire on store failures, Redis disconnects and missing heartbeats.
  - **Rollback:** Redeploy the previous image through the pipeline. Database migrations only add things during this phase.
- **Who can reach it:** Internal staff on an IdP allow-list group, behind a feature flag. Internal test documents only, which may be thrown away. Everything runs on defaults no gate has checked yet, and nothing is hardened.
- **Exit check (V0):**
  - The request above succeeds with one trace across every tier.
  - A deploy and a rollback both succeed through the pipeline.
  - Killing Redis fires an alert.
  - First values for local-apply time, cross-screen time and store time are recorded as a near-zero-load floor (baselines, not targets).

## 5. Phases

- **Phase 1: Document contracts** (the stored format, sync protocol and permission model have the widest rework if wrong)
  - **Unlocks:** Specifying and hardening everything that reads or writes documents.
  - **Depends on:** V0. V1 must pass before the format is specified (V1 starts in Phase 0).
  - **Tasks:**
    1. Finish V1.
    2. Freeze the storage tables (§3 row 3) and the document-ID scheme.
    3. Freeze content schema v1 and the sync protocol, both versioned, with the min-version handshake.
    4. Server-side validation: apply each incoming edit to the server's copy, check it against the ProseMirror schema, and reject edits that are malformed or too large (max 1 MB per edit, max 10 MB per document).
    5. Permission tables (documents, roles, share tokens, workspace_id) designed and stubbed.
    6. Divergence detector: clients send a hash of their document state every 30 s; the server compares and alerts on any mismatch.
    7. Run V3.
  - **Rollback:** Only internal documents exist, so tables can be dropped and recreated.
  - **Exit check:** V1 and V3 pass. The divergence detector fires on a mismatch planted in staging.

- **Phase 2: Durability and recovery**
  - **Unlocks:** Trusting the system with documents that matter.
  - **Depends on:** Phase 1.
  - **Tasks:**
    1. Confirm edits only after the commit (row 4).
    2. Managed Postgres with HA and synchronous replication. Point-in-time recovery with encrypted backups.
    3. Client offline queue in IndexedDB that resends unconfirmed edits; reconnect with exponential backoff and jitter.
    4. Drain connections during deploys.
    5. Snapshot compaction job (async, safe to re-run). It writes a snapshot, checks it matches a full replay of the log, and keeps the raw log 30 days before deleting.
    6. Run V2, including a scripted restore drill.
  - **Rollback:** Code goes back through the pipeline. The point of no return is deleting log rows; V2 guards it, and the 30-day window keeps it recoverable until then.
  - **Exit check:** V2 passes. Queue lag stays under 5 min during the chaos run.

- **Phase 3: Access control and beta-critical editing**
  - **Unlocks:** People outside the company can be let in.
  - **Depends on:** Phases 1 and 2.
  - **Tasks:**
    1. Enforce permissions on every route (row 5), including rejecting edits from viewers.
    2. Revocation ends live sessions.
    3. Share-link tokens.
    4. Audit log of sharing changes.
    5. Rate limits per connection and per user.
    6. Make links safe to render (block `javascript:` URLs, sanitize pasted HTML).
    7. Presence and cursors (Yjs awareness; temporary, never stored).
    8. Per-user undo and redo (Yjs UndoManager).
    9. Run V4 and the security review.
    10. Get the peak-concurrency and cost-ceiling inputs.
  - **Rollback:** Feature flags per capability, plus pipeline rollback.
  - **Exit check:** V4 passes. Both missing inputs are in hand.

- **Phase 4: Private beta** (reach the fewest users first)
  - **Unlocks:** Real usage data. Running V5 on real-shaped load.
  - **Depends on:** V2, V3 and V4. Legal documents and DPAs signed, on-call staffed (§2).
  - **Tasks:**
    1. Kill switch that puts every document into read-only mode.
    2. SLO dashboard and error budget.
    3. A manual runbook for GDPR access and erasure requests.
    4. Canary deploys: 1 replica first, rolled out further after 30 min clean.
    5. Open the cohort in stages:
       - one design-partner workspace (≤20 users)
       - then ≤10 workspaces
       - then ≤500 users
       Widen each stage only after 7 days with no divergence alert, no lost confirmed edit and the SLO met.
    6. Run V5 in a production-sized staging environment.
  - **Rollback:** The flag sends the cohort to read-only and their documents can be exported. Code rolls back through the pipeline. Point of no return: the first outside user's document. From then on the stored format can only be migrated forward, never rolled back. V2, V3 and V4 guard it.
  - **Exit check:** V5 passes. The final stage meets the SLO for 14 days.

- **Phase 5: Opening to everyone**
  - **Unlocks:** Self-serve sign-up.
  - **Depends on:** V5 (and its flips, if any fired).
  - **Tasks:**
    1. Apply V5's outcome (route each document to one server, or split the sync tier, if V5 says so).
    2. Autoscaling and load shedding.
    3. Sign-up abuse controls (CAPTCHA, limits on new accounts).
    4. Automated GDPR export and erasure that purges logs, snapshots and backups within their retention.
    5. Version-history UI built on the snapshots.
    6. Async export to Markdown, DOCX and PDF.
    7. Status page.
    8. Open sign-up by flag: 1% → 10% → 50% → 100%, each step after 7 days within the SLO and the cost ceiling.
  - **Rollback:** Turn the ramp flag down.
  - **Exit check:** 99.9% over 30 days at 100%. Cost per session stays under the ceiling.

## 10. Deliberately deferred
- **Long offline sessions (days):** Pull forward if product confirms the need (A3).
- **Comments and suggestion mode:** Pull forward if a design partner needs it, or beta feedback ranks it first.
- **End-to-end encryption:** Pull forward if a regulated or enterprise customer needs it. It is R3 and stops the server validating edits, so decide before Phase 5 if it looks likely.
- **Multi-region and data residency:** Pull forward when a contract or law requires it.
- **Splitting the sync service, or routing each document to one server:** Pull forward when V5 fails.
- **Enterprise SSO, SCIM and an org admin console:** Pull forward with the first enterprise deal.
- **Public API and webhooks:** A public contract (R3). Pull forward when a partner integration is committed.
- **Full-text search, and import from DOCX or Google Docs:** Pull forward when beta feedback asks for them, or a typical user has more than about 50 documents.
- **Native mobile apps:** Pull forward on demand measured in Phase 5.
- **AI features:** Pull forward when product commits to them. They would add prompt-injection defense, cost limits and human-review gating before any capability, with document text treated as untrusted input.
