# Plan: Multi-tenant SaaS billing platform

> **Assumptions this plan rests on** (stated because the request doesn't settle them, and two of them change the phase order):
> **(a)** This is a billing *platform*: each tenant (a SaaS company) uses it to bill its own end customers for subscriptions and usage. It is not the billing module of a single SaaS product that bills its own tenants. If it is the module, buy Stripe Billing or Chargebee, and Phase 5 plus most of §3 drops out.
> **(b)** Tenants are the merchant of record, charging through their own connected payment-provider accounts. We never hold funds. If we become the merchant of record, the plan goes back to Step 1, because licensing and tax registration then come first.
> **(c)** It is greenfield, and usage-based pricing is needed at launch. If it isn't, Phase 4 moves to §10.

## 1. Classification and constraints
- **What:** A multi-tenant billing platform. Tenants set up a catalog and subscriptions and report usage. The platform rates usage, issues invoices, collects payment through a payment provider (PSP), runs dunning (retrying failed payments), and keeps a double-entry ledger.
- **Type:** Software on managed cloud infra. Greenfield. Not a small build: outside tenants, money, and end-customer personal data.
- **Dominant constraint:** Correctness, meaning money and tenant isolation.
- **Worst failure:** Money moves wrongly and nobody notices before settlement: an end customer is charged twice, charged the wrong amount, or charged under the wrong tenant.

## 3. Key decisions (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Tenancy and isolation | R3: rework of every row and query; a leak can't be undone | Pooled: one Postgres schema. `tenant_id` leads every primary key and index. Postgres Row-Level Security reads `app.tenant_id`, which is set per transaction from the authenticated context. Tenants are routed through a cell field so they can move to dedicated cells later | No tenant contractually needs physical isolation; volume fits one primary | V2, V3 | V2 fails, V3 fails, or a contract requires a dedicated database or region → that tenant moves to a silo cell |
| Auth model and trust boundary | R3: trust boundary | Each request resolves to exactly one tenant at the edge: hashed, scoped API key, or OIDC session plus RBAC role. `tenant_id` is never read from the request body. Support staff get tenant-scoped, audited impersonation only | A single-tenant principal covers all use cases (no cross-tenant users at launch) | V2 | Agencies or resellers need multi-tenant principals → add an explicit membership model |
| Ledger and data model | R3: identifiers and financial records once real data exists | Append-only double-entry ledger is the system of record for balances. Money is `bigint` minor units plus ISO 4217 currency. IDs are prefixed UUIDv7 (`inv_`, `cus_`). Prices are versioned and immutable. A finalized invoice never changes; corrections go through credit notes. Invoice numbers are gapless per tenant series, assigned at finalization | Postgres holds the ledger at projected volume | V1, V3 | V1 fails → redesign before dependents. | Consistency vs availability | R3: consistency model | Strong (serializable or row-locked transactions on one primary) for ledger, invoice finalization and payment attempts. | Monolith vs services | R2: internal boundary | Modular monolith (billing core) plus a separate usage-ingest service, because ingest has a different scale and uptime profile | One team owns the core | Phase 4 exit check | A module's scale or team ownership diverges |
| Sync vs async | R2 | Synchronous commands with required idempotency keys. | Usage pipeline | R2: data migration | Ingest writes to day-partitioned Postgres tables, unique on (`tenant_id`, `event_id`), then aggregates | Sustained peak stays under ~5k events/s (design parameter) | V3 | V3 projects above it → Kinesis/MSK plus ClickHouse behind the same ingest API |
| Build vs buy | R3 for the PSP (stored payment methods live at the vendor); R2 for tax | Build the billing core (it is the product). | Data-privacy boundary | R3: personal data | Card data never touches our systems (PSP-hosted fields). | Funds flow / merchant of record | R3: legal | Tenant is merchant of record through connected accounts; we never hold funds; our fee is an application fee | No money-transmitter or payment-institution licence is needed in the launch markets | V6 | V6 fails → the PSP's managed-platform model, or re-plan |

## 4. First end-to-end slice (Phase 0)
- **Request:** Internal tenant 0 (our own company, with an internal test customer) calls `POST /v1/subscriptions` with an idempotency key for a flat $1/month price. The call returns a subscription. A test clock advances the period; the invoice is finalized and charged. `GET /v1/invoices/{id}` then returns `paid`, and tenant 0's webhook endpoint receives `invoice.paid`.
- **Tiers crossed:**
  1. Edge: ALB plus WAF
  2. API-key auth, which resolves the tenant
  3. Billing core: subscription, invoice and ledger modules
  4. Aurora Postgres, RLS on from the start
  5. Outbox and job worker
  6. PSP in **test mode**
  7. Inbound webhook receiver
  8. Ledger settlement
  9. Outbound webhook dispatcher
- **Day zero:**
  - Deployed by GitHub Actions to ECS: images pinned by digest, Terraform-managed, migrations run in the pipeline.
  - One OpenTelemetry trace runs from the API through the database, outbox, worker and PSP call to the webhook.
  - Structured logs carry IDs only.
  - Alerts on outbox lag, worker error rate, and failed webhook signatures.
  - Rollback is redeploying the previous image. Migrations only add things.
- **Who can reach it:** Only allow-listed tenant-0 API keys, behind a flag. No external tenants. The PSP runs in test mode, so no real money moves until V5 and V4 pass.
- **Organizational tasks that start now:**
  - PSP platform application and contract
  - V5 and V6 reviews
  - Volume projection (input 3)
  - Name the finance lead and security reviewer
  - Recruit two design partners

Exit check V0: §6.

## 5. Phases

- **Phase 1: Tenancy, identity, ledger and contracts** (widest rework first)
  - Unlocks: Specifying everything that sits on the data model.
  - Depends on: V0.
  - Tasks:
    1. Tenant, user, role and API-key model; OIDC dashboard login.
    2. RLS policies on every table; a connection with no tenant context sees nothing.
    3. ID scheme and money type.
    4. Ledger accounts, transactions and entries, with a database-enforced balance invariant.
    5. Invoice state machine (draft → finalized → paid / void / uncollectible).
    6. Credit-note model.
    7. Outbox and inbox tables; versioned event schemas.
    8. Append-only audit log.
    9. Per-tenant data keys for personal data.
    10. Automated cross-tenant test suite (V2, part 1).
    11. Ledger property tests (V1).
  - Rollback: Only tenant-0 data exists, so the schema can still be rebuilt. From the end of this phase, migrations must be expand-then-contract and ledger corrections must be compensating entries.
  - Exit check: V1 passes. V2 part 1 is green in CI. Killing the worker between commit and outbox dispatch produces neither a lost nor a duplicated event.

- **Phase 2: Catalog, subscriptions and invoicing**
  - Unlocks: Correct invoices for flat, per-seat and tiered prices.
  - Depends on: Phase 1, V1, volume input 3.
  - Tasks:
    1. Products and immutable price versions.
    2. Subscription lifecycle: create, upgrade or downgrade with proration, pause, cancel.
    3. Billing clock and scheduler, with test clocks.
    4. Invoice run: idempotent per (subscription, period), resumable, failures isolated per tenant.
    5. Gapless numbering at finalization.
    6. Tax-engine adapter in sandbox.
    7. PDFs in a private bucket with short-lived signed URLs; email sending to an allow-list only.
    8. V3 load test of the ledger and the invoice run.
    9. Point-in-time restore drill.
  - Rollback: A flag per pricing model. A finalized invoice can't be undone except by credit note, which is why only tenant 0 gets invoices.
  - Exit check: V3 (ledger and run part) passes. The restore drill meets RPO/RTO. Expected vs generated invoices per period reconcile to 0 missing.

- **Phase 3: Payments and collections**
  - Unlocks: Collecting money.
  - Depends on: Phase 2, V1; V5 before the first live charge.
  - Tasks:
    1. `PaymentProvider` adapter.
    2. Connected-account onboarding.
    3. Payment-method capture through PSP-hosted fields only.
    4. Payment attempts whose PSP idempotency key is derived from `payment_attempt_id`.
    5. Inbound webhook verification and inbox dedup.
    6. Dunning schedule; refunds; disputes.
    7. Daily reconciliation: every PSP balance transaction ↔ a ledger entry.
    8. Duplicate-charge detector.
    9. Kill switches for charging, one global and one per tenant.
    10. V4 fault-injection suite in test mode, then live mode for tenant 0 only (employee cards, small amounts) for 2 cycles.
  - Rollback: Kill switch plus PSP refunds. A captured live charge is a point of no return, guarded by V5 and V4.
  - Exit check: V5 and V4 pass.

- **Phase 4: Usage metering and rating**
  - Unlocks: Usage-based and hybrid pricing.
  - Depends on: Phase 2 (invoice lines), V1, V3 projection.
  - Tasks:
    1. Separate ingest service with tenant-scoped keys, per-tenant rate limits and quotas, and size limits.
    2. Dedup on (`tenant_id`, `event_id`).
    3. Late-event policy: events accepted until invoice finalization, then credited to the next period.
    4. Aggregation, and a rating engine whose version is recorded on each invoice line.
    5. Accepted-vs-rated reconciliation per tenant.
    6. Dead-letter queue.
    7. V3 ingest part, including node-kill tests.
  - Rollback: Ingest flag per tenant. Unfinalized usage can be re-rated, because raw events are immutable and rating is deterministic.
  - Exit check: V3 (ingest part) passes. A billing-core outage doesn't drop accepted events. If ingest and core don't separate cleanly, revisit the monolith-vs-services row.

- **Phase 5: Tenant surface and first external tenant** (smallest exposure first)
  - Unlocks: Real outside tenants.
  - Depends on: Phases 3–4, V2 (pentest), V4, V6.
  - Tasks:
    1. Public API v1 release candidate.
    2. Per-tenant sandbox (test mode) on the production version.
    3. Tenant dashboard with SSO/MFA.
    4. Hosted invoice and customer-portal pages.
    5. Webhook delivery log, retries, and secret rotation.
    6. External pentest (V2, part 2).
    7. DPA signed.
    8. Design partners integrate in sandbox (V7).
    9. Design partner 1 goes live in **shadow**: invoices computed but not sent, their legacy billing stays the system of record. Compare for one cycle (V8).
    10. Cut over design partner 1, then partner 2.
  - Rollback: Until V8 passes, the tenant's legacy billing remains the system of record and we stay in shadow. After cutover, the tenant gets a full export (JSON/CSV). Their payment methods already sit in their own PSP account.
  - Exit check: V2, V6, V8 pass for both partners. V7 is under way.

- **Phase 6: General availability (GA) in waves**
  - Unlocks: General onboarding.
  - Depends on: Phase 5, V7, V8 per tenant, SLA and unit-cost inputs.
  - Tasks:
    1. Freeze API v1.
    2. Waves of 1 → 5 → 25 → open, each pausable.
    3. SLOs with burn-rate alerts, on-call and runbooks.
    4. DR drill to RTO.
    5. Retention and deletion jobs, once the legal period is known.
    6. Access reviews.
    7. Unit-cost dashboard against the target take rate.
  - Rollback: Pause a wave or a tenant. Each tenant's decommissioning of legacy billing is a point of no return, guarded by V8 and that tenant's sign-off.
  - Exit check: SLO attainment over the first 30 days. Unit cost is under the target. Operational complexity is within the budget.
