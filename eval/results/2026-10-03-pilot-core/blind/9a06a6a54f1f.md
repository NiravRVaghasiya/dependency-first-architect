# Plan: Zero-downtime cloud migration of the hospital patient scheduling system

## 1. Classification
- **What:** Moving a live, in-house (or customizable) patient scheduling application and its relational database from on-prem to a HIPAA-eligible cloud. The system has HL7 links to the EHR, ADT feeds, reminder vendors, and reporting, and it must never visibly go down.
- **Type:** Infra plus software. This is a data-migration and traffic-routing problem. It is not a rewrite.
- **Dominant constraint:** Correctness, meaning no lost or double-booked appointments. Compliance (HIPAA) is a close second, and availability is the third requirement.
- **Worst failure:** Split-brain writes. On-prem and cloud both accept bookings during cutover, which causes double-booked OR or clinic slots, or appointments that silently disappear. A close second is outbound feeds firing twice, which sends duplicate SMS reminders to patients and duplicate SIU messages to the EHR.
- **Assumptions to confirm before Phase 0:**
  - **Vendor product?** If the system is a vendor product such as Epic Cadence or Oracle Health scheduling, the vendor's hosting program decides the migration path, and most of this plan becomes vendor-managed.
  - **What "without downtime" means here:** no user-visible outage. The single write cutover still pauses writes for a few seconds (target under 30 s): they are held and then replayed, not rejected. The existing paper downtime procedures stay staffed as a safety net.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| **Consistency vs availability** | **CP, one writer.** Exactly one database is authoritative at any moment. No dual-writes, no multi-master. The cloud copy is read-only until the cutover. | **Never flip to multi-master for this system.** If availability drills fail RTO, add a cross-region warm standby. It stays single-writer. |
| **Cutover granularity** | **One atomic write-authority switch for the whole system**, with writes held at the proxy. Shared resources (radiology rooms, surgeons, interpreters) cross department lines, so splitting writes by department would need bidirectional replication. | Flip to per-site cutover only if the Phase 1 inventory proves that a site's resources share nothing with the others. |
| **Migration style (rehost / replatform / re-architect)** | **Replatform.** Same app code on cloud VMs or containers, with a managed DB on the **same engine** (e.g. SQL Server on-prem → Azure SQL MI or RDS SQL Server). No refactoring during the move. | Flip to rehost (lift-and-shift VMs) if licensing or OS dependencies block managed services. Re-architecting is deferred (§7). |
| **DB engine change** | **Keep the same engine.** Same-engine CDC is far more reliable, and an engine change on top of a migration compounds risk. | Revisit after migration only if licensing cost is over budget. That becomes its own project. |
| **Monolith vs services** | **Keep the monolith as-is.** | Extract a service (e.g. reminders) only after migration, if it limits scaling or release speed. |
| **Sync vs async** | **Synchronous** booking writes, so the user sees a confirmed slot. **Async** CDC replication and interface fan-out over durable queues. | If replication lag p99 goes above 5 s, reads that need fresh data stay on the primary and are not served from the replica. |
| **Build vs buy** | **Buy:** managed CDC (AWS DMS / Azure DMS / Qlik / GoldenGate), managed DB, and the existing integration engine (Rhapsody / Mirth / Cloverleaf) rehosted. **Build:** only the reconciliation checks and the cutover runbook. | Build trigger-based capture only if the CDC tool can't handle specific types (LOBs, computed columns) or the change volume. |
| **Cloud / compliance boundary** | A provider with a **signed BAA**, an in-country region, multi-AZ, private connectivity only, and customer-managed keys. | A data-residency or state-law requirement forces the region choice. A provider refusing a BAA disqualifies it. |
| **Identity** | **Federate to the existing hospital AD** (Entra ID / SAML). No new user store. | None. A second identity store for clinical staff is not acceptable. |
| **Rollback model** | **On-prem stays a hot standby** after cutover, fed by reverse CDC (cloud → on-prem), for 30–90 days. | Retire it early only after the cloud cross-region DR has passed a failover test. |
| AI gates (RAG vs fine-tune, hosted vs self-host) | N/A. The migration has no AI component. | Becomes relevant if AI features such as no-show prediction are proposed later (§7). |

## 3. First end-to-end slice (Phase 0)
**The one real request:** a scheduler looks up *"provider availability for Clinic X tomorrow."* It is served end-to-end from the cloud using real production data. Writes are not possible on this path.

**Tiers crossed:**
1. Scheduler workstation (existing client, SSO via hospital AD)
2. On-prem reverse proxy / load balancer (F5 or NGINX). This becomes **the routing control point** for the whole migration.
3. Redundant private link: ExpressRoute or Direct Connect, plus a backup IPsec VPN
4. Cloud private load balancer and WAF
5. Cloud app instance in **read-only mode**, enforced by a database login that only has `SELECT` grants
6. Cloud managed DB replica, fed by CDC from the on-prem primary. To start, only the tables needed for this one query are replicated.

The response goes back along the same path.

**Who gets real responses:**
- 100% of matching requests are mirrored in shadow mode, and the cloud response is diffed against the on-prem response.
- A pilot group of 3–5 IT or scheduling super-users gets the cloud response for real, using a feature flag at the proxy.
- If the cloud path is slower than 2 s or errors, the proxy falls back to on-prem.

**Day zero deploy, logging, monitoring:**
- Infra and app deploy from Terraform/Bicep through a CI pipeline. Nothing is set up by hand.
- A correlation ID is attached at the proxy and logged on both sides. Logs are structured and PHI-scrubbed, and sent to a SIEM covered by the BAA.
- The dashboard shows p95 latency, error rate, CDC lag, shadow-diff rate, and proxy fallback count. Alerts go to on-call.
- **Started now because it needs a long lead time:** passive network-flow and DB-connection capture on the on-prem DB server, so monthly and quarterly jobs show up in the Phase 1 inventory.

**Exit check:**
- A pilot user's availability lookup returns from the cloud in production.
- The trace shows every tier, and the lag and diff metrics are visible on the dashboard.
- The shadow-diff rate is 0 over 72 h, apart from known differences that are explained.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

**Phase 0: First end-to-end slice** (above)
- Tasks, in order:
  1. BAA signed
  2. Landing zone with policy guardrails
  3. Private connectivity
  4. SSO federation
  5. Proxy routing control point
  6. Partial CDC
  7. Read-only app instance
  8. Dashboard

**Phase 1: Prove the data substrate and find every dependency**
- Unlocks: everything else. Nothing gets routed to the cloud until the data is provably identical and every consumer is known.
- Depends on: the Phase 0 CDC path and private link working in production.
- Tasks:
  1. **Dependency inventory.** Combine flow capture, DB login audit, interface-engine routes, and cron/SQL Agent jobs to list every reader and writer: ADT inbound, SIU outbound, reminder/IVR vendor, billing, reporting/BI, and ODBC links from Access or Excel. A missed consumer is the most likely silent failure after cutover.
  2. **Put indirection in front of every consumer.** Every client, interface, and report must reach the system through the proxy or a DB listener/DNS alias. The cutover then becomes a routing change instead of reconfiguring 40 clients. Remove hardcoded IPs.
  3. **Full-database CDC** with schema parity checks. Schema changes are frozen, or applied to both sides through versioned migrations.
  4. **Continuous reconciliation:** hourly row counts plus per-table checksums, and a nightly full-hash comparison of the appointment and slot tables.
  5. Restore a cloud backup to a scratch instance to prove point-in-time recovery (PITR) works.
- Exit check:
  - 14 consecutive days of full replication with lag p99 under 5 s and zero unexplained reconciliation diffs.
  - The inventory is signed off by the interface team and department leads.
  - 100% of consumers go through switchable indirection.

**Phase 2: Rebuild integrations in the cloud, in dry-run**
- Unlocks: moving traffic without breaking feeds to the EHR, billing, and patients.
- Depends on: the Phase 1 inventory, plus replicated data that is proven identical.
- Tasks:
  1. **Write-authority flag and singleton guard.** A single flag says which side is authoritative. Every outbound interface and batch job (reminders, SIU, nightly exports) checks it before acting, so the cloud **cannot** send to patients or to the EHR while on-prem is authoritative.
  2. Run cloud outbound interfaces in **capture-only mode**. Generated HL7 SIU and reminder payloads are compared message-by-message with what on-prem actually sent.
  3. Pre-provision the inbound ADT path to the cloud, but leave it inactive. On-prem still receives ADT, and the changes reach the cloud through CDC.
  4. Re-point reports and BI to the cloud replica, since they only read.
- Exit check:
  - 7 days of outbound dry-run with a 100% match against on-prem messages.
  - The singleton guard is verified by trying to fire a cloud job while on-prem is authoritative. It must refuse.
  - Reports run from the cloud without a regression.

**Phase 3: Move read traffic gradually**
- Unlocks: proven cloud capacity and latency under real load before writes depend on it.
- Depends on: Phase 2 interfaces running in parallel, and the Phase 1 reconciliation staying green.
- Tasks:
  1. **Handle read-your-writes.** After a user writes, route that session's reads to the primary for 30 s. Also, if CDC lag goes over the threshold, the proxy sends all reads to on-prem automatically.
  2. Load-test the cloud at 2× the observed peak, for example the Monday 08:00 booking surge.
  3. Ramp read routing through the proxy: 5% → 25% → 50% → 100%, department by department, with automated canary analysis at each step.
  4. Move portal "view my appointments" to the cloud last, because it is patient-facing.
- Exit check:
  - 100% of reads served from the cloud for 14 days with SLOs met (p95 under 800 ms, errors under 0.1%).
  - The stale-read counter stays at 0 complaints and 0 detected cases.

**Phase 4: Rehearse the write cutover and the rollback**
- Unlocks: a cutover whose risk has been measured, not guessed.
- Depends on: Phase 3 proving the cloud can carry production load.
- Tasks:
  1. **Reverse CDC** (cloud → on-prem), built and verified in staging. This is the rollback mechanism.
  2. **Cutover runbook as code:** the scripted sequence with go/no-go checks at every step.
  3. **At least 3 full rehearsals and at least 1 full rollback rehearsal** on a staging environment built from IaC, using a masked clone of production data at production size. Time each one.
  4. Define rollback triggers. Examples: booking error rate above 0.5% for 5 min, any double-booking detected, interface ACK failures, or CDC reverse lag above 60 s.
  5. Get clinical operations sign-off. Choose a low-volume window (e.g. Sunday 02:00, avoiding month-end and holidays). Put downtime procedures and print-ready schedules on standby.
- Exit check:
  - The rehearsed write-hold is under 30 s, three times in a row.
  - The rollback rehearsal restores on-prem authority in under 15 min with zero data loss.
  - The CAB and the CMIO sign off.

**Phase 5: Switch write authority**
- Unlocks: the cloud becomes the system of record.
- Depends on: a Phase 4 rehearsal passing at the current production versions.
- Tasks, executed from the rehearsed script:
  1. The proxy holds writes, with a bounded queue.
  2. Confirm CDC lag is 0 and checksums match.
  3. Set the on-prem DB to read-only.
  4. Flip the write-authority flag.
  5. Start reverse CDC.
  6. Activate cloud ADT inbound, outbound interfaces, and batch jobs. The singleton guard turns on-prem's copies off.
  7. Release the held writes to the cloud.
  8. Run synthetic book/cancel transactions against a test patient.
  9. Hold a **4-hour war-room watch**, then a 72 h heightened watch.
- Exit check:
  - 72 h with zero double-bookings, zero lost appointments (reconciled against reverse CDC), all interface ACKs green, and SLOs met.

**Phase 6: Bake, prove DR, decommission**
- Unlocks: retiring on-prem without losing the safety net it currently provides.
- Depends on: a stable Phase 5 cloud primary.
- Tasks:
  1. **Cross-region DR replica plus a real failover test.** On-prem is the only DR until this passes, so it comes first.
  2. Keep the on-prem hot standby for 30–90 days.
  3. Make on-prem a read-only archive and apply record-retention rules.
  4. Decommission with NIST 800-88 media sanitization certificates.
  5. Close out on-prem accounts, firewall rules, and circuits.
- Exit check:
  - The DR failover test meets RTO ≤ 1 h and RPO ≤ 5 min (targets to confirm with clinical ops).
  - The decommission certificates are filed.

## 6. AI layer
N/A. This plan has no AI or agentic component. If AI features such as no-show prediction or smart slot suggestions are added later, they get their own plan, with PHI guardrails and a human approval step built first (§7).

## 7. Deferred
- **Re-architecting to services, or a UI rewrite.** Pull forward only if the monolith can't meet post-migration SLOs, or release speed blocks clinical requests. Never during the migration.
- **DB engine change (e.g. SQL Server/Oracle → PostgreSQL).** Pull forward if licensing cost passes the agreed threshold, and run it as a separate project after Phase 6.
- **Active-active multi-region.** Pull forward only if the hospital network's availability target can't be met by warm cross-region DR. Single-writer stays the rule.
- **Cloud-native autoscaling and serverless reminders.** Pull forward if Phase 3 load tests or post-cutover peaks show sustained capacity pressure.
- **New patient self-scheduling or FHIR APIs.** Pull forward after Phase 6, once the cloud has been the stable system of record for at least 90 days.
- **Migrating adjacent systems (EHR, integration engine as a whole, billing).** Pull forward per system, each with its own the plan plan, after this migration is decommissioned.
- **AI features (no-show prediction, overbooking optimization).** Pull forward when a clinical sponsor and a data-governance approval exist.
