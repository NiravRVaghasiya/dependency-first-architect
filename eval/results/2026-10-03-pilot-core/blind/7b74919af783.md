# BUILD PLAN: Multi-Tenant SaaS Billing System

> **Assumption:** this plan treats the system as a **billing platform that is itself multi-tenant SaaS**. Each tenant uses it to bill its own customers, as with Chargebee or Orb. If you actually mean *internal billing for your own SaaS product*, the build-vs-buy gate below changes the answer to "buy" (see Gate 4).

---

## 1. Classification
- **What:** A multi-tenant platform where tenants set up a product catalog, run subscriptions and usage-based pricing, issue invoices, collect payment through a payment processor, and chase failed payments.
- **Type:** Software, with a meaningful infra component (tenant isolation, scheduled billing runs, usage ingestion).
- **Dominant constraint:** **Correctness**, then compliance (PCI scope, tax, invoice immutability, audit trail). Latency and scale come after both.
- **Worst failure:** **Money that is wrong and nobody notices.** That covers double-charging, lost charges, or one tenant's data or charges reaching another tenant, found weeks later by a customer or an auditor. Any design choice that could let this happen silently loses.

## 2. Tradeoff gates (resolved up front)

| # | Decision | Default (chosen now) | Flip condition |
|---|---|---|---|
| 1 | **Consistency vs availability** | **Consistency first for money.** Ledger entries, invoices and subscription changes are committed in single Postgres transactions. If the system can't confirm a write, it refuses it (fails closed). **Availability first only for usage ingestion:** accept events, deliver at least once, dedupe by event ID later. | Never flips for the ledger. Read-only views (dashboards, reports) can become eventually consistent on read replicas once read load is >30% of primary CPU. |
| 2 | **Monolith vs services** | **Modular monolith:** one deployable, one Postgres. The modules are `tenancy`, `ledger`, `catalog`, `subscriptions`, `invoicing`, `payments`, `metering` and `notifications`. Boundaries are enforced in CI by an import linter (e.g. go-arch-lint). | Split **metering** out first, when ingestion is >~5k events/s sustained or >1B events/month, or when it threatens the database's write latency. Split anything else only when >3 teams keep blocking each other's deploys. |
| 3 | **Sync vs async** | **Sync** for state changes inside our own database. **Async through a transactional outbox** (the outbox row commits in the same transaction as the change) for everything that leaves the system: payment charges, emails, tenant webhooks, PDF rendering. Tax calculation is sync at finalization, with a timeout; on failure the invoice stays in draft and is retried. | Swap the Postgres outbox for Kafka or SQS when outbox lag p99 is >60s under normal load, or when the outbox is >15% of database writes. |
| 4 | **Build vs buy** | **Buy:** payment processing (Stripe with Connect), tax calculation (Stripe Tax or Avalara), email (Postmark/SES), identity provider for dashboard users (Auth0/WorkOS). **Build:** ledger, catalog, subscriptions, rating, invoicing, dunning. Those are the product. | If billing is *not* the product (internal billing only), buy Stripe Billing or Orb outright and build only the integration plus a reconciliation job. If tax becomes the main source of tenant complaints, consider a merchant-of-record provider (Paddle). |
| 5 | **Tenant isolation model** | **Shared database and schema, `tenant_id` on every row, Postgres row-level security (RLS) enforced.** A tenant→cell routing step exists from day one but points everything at one cell. | Move a tenant to its own database or cell when it is >20% of load, or when an enterprise contract requires physical isolation or data residency. The routing step makes this a data migration, not a rewrite. |
| 6 | **Merchant of record / funds flow** | **The tenant is the merchant of record**, through Stripe Connect accounts. We never hold funds, and card data never touches our servers (PCI SAQ-A). | Becoming merchant of record (we collect, remit tax and pay out) is a regulatory and licensing project. Do it only when the business decides to, not because of a technical reason. |
| 7 | **Ledger model** | **Double-entry, append-only journal.** Corrections are reversing entries; rows are never updated or deleted. Balances are derived or snapshotted, never mutated in place. | None. Choosing a mutable balance table instead is the decision that causes the worst failure. |
| 8 | **Money representation** | Stored amounts are **int64 minor units plus an ISO 4217 currency code**. Unit prices and rates are fixed-scale decimals (`numeric(38,12)`). Rounding happens once, at the line item, half-up, and is documented. No floats anywhere. No currency conversion inside the ledger. | Add a currency-conversion module when the first tenant needs invoices in a currency other than its settlement currency. |
| 9 | **Data residency** | One region (e.g. AWS `eu-central-1` or `us-east-1`). Every tenant records a region from day one. | First tenant with a residency clause triggers a second cell in that region. |
| 10 | **Payment processor coupling** | One processor (Stripe) behind a narrow internal `PaymentGateway` interface. | Add a second processor when a tenant needs one (e.g. Adyen) or there's a geographic coverage gap. |
| — | (AI) prompt+RAG vs fine-tune | **N/A:** no model in the request path. | Applies if an AI feature is added (see §6). |
| — | (AI) hosted API vs self-host | **N/A:** same reason. | Same. |

## 3. Walking skeleton (Phase 0)

**The one real request:** a tenant's API key calls `POST /v1/invoices` with one customer and one $10.00 line item. A payment is collected in Stripe test mode, and `GET /v1/invoices/{id}` returns `status: paid` with balanced ledger entries.

**Tiers crossed:**
1. **Edge:** AWS ALB with TLS, then the API service (Go) on ECS Fargate, two tasks spread over two availability zones.
2. **Auth:** a tenant API key, stored as a hash, sets `app.tenant_id` on the database session.
3. **Domain:** in one transaction, `invoicing` writes the invoice, `ledger` writes debit A/R $10 and credit Revenue $10, and an outbox row is written.
4. **Data:** RDS Postgres 16 (Multi-AZ), with RLS enabled on all three tables.
5. **Async:** an outbox worker creates a Stripe PaymentIntent (test mode) using an idempotency key.
6. **External callback:** Stripe calls `POST /webhooks/stripe`. We verify the signature, dedupe on event ID, and post a ledger entry (debit Cash, credit A/R).
7. **Response:** the GET reflects `paid`.

**Deployed:** Terraform defines the infrastructure. GitHub Actions builds the image (pinned by digest), runs database migrations, and deploys to staging, then prod. Prod uses Stripe test keys until Phase 6.

**Logged:** structured JSON logs. Every line carries `tenant_id`, `trace_id` and `request_id`, and personal data is redacted.

**Monitored on day zero:**
- OpenTelemetry traces cover API → database → outbox → Stripe → webhook as one linked trace.
- Request rate, error rate and latency per endpoint.
- Outbox lag gauge.
- Webhook failure counter.
- A **ledger invariant check** runs every 5 minutes. If total debits ≠ total credits for any tenant and currency, it pages someone.

**Exit check:** a real request in prod returns `paid`. A single trace covers every tier. The invariant check shows 0 imbalance. An alert fires when an imbalance is deliberately injected in staging.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

**Phase 1: Tenancy, identity and API contract**
- **Unlocks:** every later module can assume the tenant scope and API conventions are correct.
- **Depends on:** Phase 0 (deploy pipeline, database, tracing).
- **Tasks:**
  1. Tenant model and RLS on every table. A CI migration check rejects any table that has no `tenant_id` or no RLS policy.
  2. Auth model: scoped, hashed API keys (`secret`, `publishable`, `usage-write-only`), OIDC with MFA for dashboard users, RBAC roles (owner, admin, finance, read-only).
  3. API contract: `/v1` versioning, a required `Idempotency-Key` header on every write (with a stored-response table), cursor pagination, a standard error format, and money as `{amount_minor, currency}`.
  4. Append-only audit log of who did what to which tenant.
  5. Tenant→cell routing step (one cell for now).
- **Exit check:** a cross-tenant test suite (every endpoint called with tenant B's key against tenant A's IDs) returns 404 everywhere. A repeated request with the same idempotency key returns the original response and creates no duplicate rows.

**Phase 2: Ledger and money core**
- **Unlocks:** anything that moves money can post to a trusted ledger.
- **Depends on:** Phase 1 (tenant scope, idempotency).
- **Tasks:**
  1. Journal schema: transactions and entries, accounts per tenant and currency (A/R, Revenue, Deferred Revenue, Cash, Customer Credit, Refunds).
  2. Database-enforced immutability: the app role gets INSERT only on journal tables, plus a trigger that rejects UPDATE and DELETE.
  3. A `Money` type and rounding library, with property-based tests.
  4. Balance snapshots and point-in-time balance queries.
  5. Manual adjustment flow that needs two-person approval.
- **Exit check:** property tests (fixed seeds, 10⁶ cases) show every transaction balances. Replaying the full journal reproduces the snapshots exactly. A restore drill from backup passes the invariant check.

**Phase 3: Catalog and customers**
- **Unlocks:** subscriptions have something stable to reference.
- **Depends on:** Phase 2 (amounts are `Money`, and price changes never mutate history).
- **Tasks:**
  1. **Immutable price versions.** A product has many prices, a price has many versions, and editing a price creates a new version. This is the widest-reaching task because every invoice ever issued points at a version.
  2. **Line-item contract:** `{source_type: subscription|proration|usage|one_off|credit, price_version_id, quantity:decimal, unit_amount:decimal, amount_minor:int64, currency, period_start, period_end, tax_code}`. The `usage` type is reserved now and filled in Phase 7.
  3. Customers, with personal data classified and encrypted at field level where needed.
  4. Payment methods stored only as Stripe tokens or IDs.
  5. Pricing models: flat, per-seat, tiered and volume. Usage pricing uses the same rate-table shape.
- **Exit check:** an invoice from fixture data can be recomputed from a historical price version after that price has been edited. A spike rates a fake usage line through the contract without changing its schema.

**Phase 4: Subscriptions and billing clock**
- **Unlocks:** recurring charges.
- **Depends on:** Phase 3 (price versions, line-item contract).
- **Tasks:**
  1. Subscription state machine: `trialing → active → past_due → canceled/paused`, with transitions only through explicit commands.
  2. **Injectable clock and test clocks.** All billing logic reads time from the clock, never directly from the system, and all times are UTC. Each tenant has a configured anchor timezone for period boundaries.
  3. Billing run scheduler: idempotent on `(subscription_id, period_start)`, resumable, and isolated per tenant.
  4. Proration for upgrades, downgrades and seat changes, emitting `proration` line items.
  5. Trials, coupons and discounts.
- **Exit check:** a test-clock simulation runs 24 months of lifecycle across 50 fixture subscriptions. Its output matches a stored snapshot file exactly. Killing the billing run halfway and restarting it produces no duplicates and no gaps.

**Phase 5: Invoicing and tax**
- **Unlocks:** legally valid, collectable invoices.
- **Depends on:** Phase 4 (line items from billing runs) and Phase 2 (ledger posting).
- **Tasks:**
  1. Invoice state machine: `draft → finalized → paid|void|uncollectible`. **Finalized invoices are immutable**; corrections are only through credit notes, which post reversing ledger entries.
  2. Gapless invoice numbering per tenant: a sequence allocated at finalization, inside the transaction.
  3. Tax integration at finalization. The tax provider's response is stored with the invoice so the invoice can be reproduced exactly.
  4. Ledger postings on finalization: A/R against Revenue, or Deferred Revenue for prepaid periods.
  5. PDF rendering (async, versioned template) and invoice email. This is the narrowest task.
- **Exit check:** every finalized invoice total equals its ledger postings (nightly reconciliation, 0 diffs). During a simulated tax outage, invoices stay in draft and finalize automatically once the provider recovers.

**Phase 6: Payments, dunning and reconciliation**
- **Unlocks:** cash collection on real tenants' Stripe accounts. Live keys are switched on here.
- **Depends on:** Phase 5 (finalized invoices) and Phase 0 (the proven Stripe and webhook path).
- **Tasks:**
  1. Stripe Connect onboarding and per-tenant connected accounts.
  2. Payment attempt state machine, including an `unknown` state. A timeout leads to a status query, never a blind retry; every attempt carries an idempotency key.
  3. Webhook processing hardening: store the raw payload, dedupe, process out of order, and pull from Stripe periodically to catch missed events.
  4. Dunning: a retry schedule configurable per tenant, `past_due` handling, and a cancel-or-pause policy.
  5. Refunds and disputes, both with ledger postings.
  6. Daily reconciliation of our ledger cash against Stripe balance transactions and payouts.
- **Exit check:** daily reconciliation shows 0 unexplained differences for 14 consecutive days in prod. A chaos test that drops 10% of webhooks still converges to correct state within 1 hour.

**Phase 7: Usage metering and rating**
- **Unlocks:** usage-based and hybrid pricing.
- **Depends on:** Phase 3 (the reserved `usage` line type), Phase 4 (billing periods), Phase 5 (invoicing).
- **Tasks:**
  1. Ingestion API using a usage-write-only key. Delivery is at least once, with dedupe on `(tenant_id, event_id)`.
  2. Raw events stored as an immutable, append-only table partitioned by time. They are the source of truth for re-rating.
  3. Late-event policy: events up to N hours after period close are accepted into the open invoice; later ones become a next-period adjustment.
  4. Aggregation per meter and period.
  5. Rating engine as a **pure function** of `(price_version, aggregated_usage) → line_items`, with versioned rules.
  6. Usage previews and threshold alerts.
- **Exit check:** raw event count equals aggregated count per period (0 drift). Re-rating a closed period from raw events reproduces the invoiced amount to the cent. A load test at 2× expected peak ingestion holds database write p99 under target.

**Phase 8: Tenant-facing surfaces and reporting**
These are the most visible features, so they come last.
- **Unlocks:** self-serve tenants and their customers.
- **Depends on:** everything above; this phase only reads or orchestrates proven modules.
- **Tasks:**
  1. Outbound webhooks to tenants: HMAC-signed, retried, replayable. The widest task here, because tenants build integrations against it.
  2. Tenant dashboard.
  3. Hosted customer portal: update card, download invoices, change plan.
  4. Reports (MRR, A/R aging, payments) built from the ledger only, served from read replicas.
- **Exit check:** dashboard and report numbers match ledger queries exactly. Tenant webhook delivery succeeds ≥99.9% within 24h, with a replay endpoint working.

## 6. AI layer
**N/A.** This system has no model in its request path, so prompt-injection defense, cost and latency budgets, human approval steps, retrieval, model access, memory, orchestration, routing and feedback do not apply. **Pull-forward condition:** if an AI feature is added, such as anomaly detection on charges or a natural-language billing assistant, run the full AI layer for that feature. It must be read-only against the ledger, and any action that moves money needs human approval.

## 7. Deliberately deferred
- **Splitting into microservices.** Pull forward when the Gate 2 thresholds are hit; metering goes first.
- **Kafka/ClickHouse for usage.** Pull forward at >5k events/s sustained or >1B events/month, or when Postgres partitions slow down aggregation past the period-close SLA.
- **Database-per-tenant or multi-region cells.** Pull forward on the first residency or isolation contract, or a tenant >20% of load. The routing step already exists.
- **Currency conversion and multi-currency settlement.** Pull forward on the first tenant that invoices in a non-settlement currency.
- **Revenue recognition reports (ASC 606 / IFRS 15).** Pull forward when a tenant's auditor asks. Deferred Revenue accounts exist from Phase 2, so this is reporting work, not a schema change.
- **Second payment processor.** Pull forward on a tenant requirement or a coverage gap (Gate 10).
- **Quotes, contract pricing and sales approval workflows.** Pull forward when sales-led enterprise tenants make up more than ~20% of the pipeline.
- **Custom invoice templates and branding beyond logo and colours.** Pull forward when it shows up as a top-3 churn or sales objection.
- **SOC 2 Type II audit.** The controls are built in from Phase 0; the formal audit waits for the first enterprise deal that requires it.
- **Becoming merchant of record.** Pull forward only on an explicit business decision (Gate 6).
- **Smarter dunning (choosing retry timing from data).** Pull forward after ≥6 months of payment-attempt data and a plateau in recovery rate.
