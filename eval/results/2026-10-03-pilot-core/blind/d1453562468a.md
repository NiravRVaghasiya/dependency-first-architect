# BUILD PLAN: `exifrename`, a CLI that renames a folder of photos by EXIF capture date

## 1. Classification
- **What:** A local command-line tool. It reads each photo's EXIF capture timestamp and renames the file to a sortable date-based name, in place.
- **Type:** Software. A single-process local CLI. There is no service tier and no AI.
- **Dominant constraint:** Correctness. Speed barely matters, and every file it touches belongs to the user and may be the only copy.
- **Worst failure:** Lost or clobbered photos. Two files map to the same name and one silently overwrites the other, or the run dies halfway and leaves a library that can't be put back. A close second: confidently renaming files to the *wrong* date, which is silent and permanent.

*Adaptation note:* this skill's template assumes a server. For a CLI, I read "prod" as a published, installed release run on a real folder. I read "monitored" as structured logs, defined exit codes, a run journal and a CI smoke run. Nothing is sent home (see Security).

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **Consistency vs availability** (read as: all-or-nothing batch vs best-effort) | **Plan, then execute.** Build the full rename plan, check it for collisions, then apply. Stop at the first *execution* error and offer rollback. Files whose metadata can't be read are skipped and reported. They never stop the run. | Users with libraries of 50k+ files ask to push past I/O errors. Then add `--continue-on-error`. The journal stays mandatory. |
| **Monolith vs services** | **Monolith.** One Python package with one entry point. | N/A in practice. Revisit only if a GUI or watch-folder daemon needs the core as a library. If so, split out `core/` as an importable package. That is not a separate service. |
| **Sync vs async** | **Synchronous and sequential.** Read, plan, then rename one file at a time. | EXIF reads on large network shares run over about 2 minutes per 10k files. Then parallelize **reads only** with a thread pool. Renames stay serial and journaled. |
| **Build vs buy: EXIF parsing** | **Buy:** `exifread` (pure Python, installs with pip, covers JPEG/TIFF/HEIC and common RAW). It sits behind a `DateExtractor` interface. | Any file in the Phase 1 fixture corpus is read wrongly or unreadably (likely CR3, some HEIC variants, or video). Then add an `exiftool` subprocess backend (`-json -n`, batch mode) behind the same interface. |
| **Language / distribution** | **Python 3.11+, installed with `pipx`.** Pinned `uv.lock`. Only standard-library `argparse` besides `exifread`. | Non-technical users need zero-install. Then ship PyInstaller or Nuitka single binaries. If startup time or binary size is unacceptable, rewrite the core in Go. That is expensive, so it needs evidence first. |
| **Filename contract** (irreversible once users' libraries carry it) | `YYYY-MM-DD_HH-MM-SS<ext>`. Same-second collisions get `_01`, `_02` and so on. The original extension is **kept exactly as is**. No colons, because they are illegal on Windows. | Repeated user requests for other layouts. Then add a `--format` template. The default never changes after 1.0. |
| **Which timestamp counts as "capture date"** | Use `DateTimeOriginal`, then `CreateDate`/`DateTimeDigitized`, then **missing**. `ModifyDate` is never used by default, because edits change it. | Specific camera models are shown to write only `DateTime`. Then allow `--allow-modify-date` as an opt-in. |
| **Timezone** | Use the **wall-clock time as recorded**, with no conversion. `OffsetTimeOriginal` is logged but ignored. | Multi-timezone trip users need one consistent order. Then add `--to-utc` or `--tz`, which needs `OffsetTime*` or a user-supplied offset. |
| **Missing EXIF fallback** | **Skip and report.** File mtime is never silently used. It is unreliable after copying. | Explicit demand. Then add `--fallback=mtime`, opt-in, with every such file flagged in the output. |
| **Default mode** | **Dry run by default.** Changing files needs `--apply`. | None planned. This is a safety invariant. |
| **In-place vs copy** | **In-place rename**, which is what was asked, made reversible by a journal. | Users on unreliable media (SD cards, flaky NAS) report failed runs. Then add `--copy-to DIR`. |
| (AI) prompt+RAG vs fine-tune | N/A: no model in the system. | — |
| (AI) hosted API vs self-host | N/A: no model. **Privacy boundary still applies:** photo metadata (GPS, device serial numbers) never leaves the machine. | — |

## 3. Walking skeleton (Phase 0)
**The one real request:** `exifrename ./fixtures/one --apply` on a folder with **one real JPEG** that has `DateTimeOriginal`.
**The real response:** `IMG_0412.JPG` becomes `2024-06-01_14-32-05.JPG`. One JSON log line, a summary line (`renamed=1 skipped=0 failed=0`), and exit code `0`.

**Tiers crossed (each the thinnest version that works):**
1. **CLI:** `argparse` reads `DIR` and `--apply`.
2. **Scan:** non-recursive `os.scandir`, regular files only, symlinks not followed.
3. **Extract:** `exifread` reads `DateTimeOriginal`. Missing means skip.
4. **Plan:** compute the target name. If the target exists and is not the source, skip it with reason `collision`. No suffixing yet.
5. **Journal:** before renaming, append `{src, dst, state}` to `.exifrename-journal-<ts>.jsonl` in the folder.
6. **Apply:** a no-overwrite rename. On POSIX that is `os.link` + `os.unlink` where hard links work; otherwise an exists-check + `os.rename`. On Windows `os.rename` already refuses to overwrite.
7. **Report:** log line, summary and exit code.

**Deployed:** a GitHub Actions matrix (ubuntu, macos, windows) builds the wheel from `uv.lock`, installs it with `pipx`, and runs the command above on the committed fixture. It then asserts the new filename exists and the old one is gone. A tag push publishes to PyPI via trusted publishing.
**Logged:** `--log-json` writes one structured line per file to stderr (`src`, `dst`, `tag_used`, `action`, `reason`). The human summary goes to stdout.
**Monitored:** exit codes are a contract from day zero: `0` OK, `1` some files skipped, `2` usage error, `3` run aborted. The CI smoke run on every commit is the canary. There is no telemetry.

**Exit check:** the released wheel, installed fresh on all three OSes, renames the real fixture JPEG. The JSON log line and the summary counts appear, and the exit code is `0`.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

### Phase 0: Walking skeleton
- **Unlocks:** every later phase. There is now a real end-to-end path to harden.
- **Depends on:** nothing.
- **Tasks:** (1) repo, `pyproject.toml`, `uv.lock`, CI matrix → (2) the exit-code and log-line contract → (3) the skeleton path above → (4) publish 0.0.1.
- **Exit check:** as in §3.

### Phase 1: Date-extraction substrate (proving the thing every rename rests on)
- **Unlocks:** trusting any computed name. Nothing about naming or collisions gets specified until this is proven.
- **Depends on:** Phase 0's extractor slot, CLI and CI.
- **Tasks (widest first):**
  1. **A typed extraction result:** `Found(dt, subsec, tag, offset) | Missing | Invalid(reason)`. Every later layer consumes this, so it gets fixed first.
  2. **A golden fixture corpus.** EXIF is written deterministically by a script (`piexif` for JPEG), plus a few small real camera files. It covers: JPEG, HEIC, DNG/CR2/NEF, PNG with no EXIF, the zero date `0000:00:00 00:00:00`, a malformed or truncated EXIF block, only `CreateDate` present, `SubSecTimeOriginal`, and `OffsetTimeOriginal`.
  3. **Tag precedence and date validation:** reject impossible dates and years before 1990 or in the future, flagged as `Invalid`, not renamed.
  4. **Hostile-input limits:** cap bytes read per file, set a per-file timeout, and catch every parser exception so one bad file can't crash the run.
  5. **`--explain FILE`:** prints the tags found and which one won.
- **Exit check:** 100% of fixtures match their expected results on all three OSes. **This is where the build-vs-buy gate is decided:** any wrong or unreadable fixture triggers the `exiftool` backend before Phase 2 begins.

### Phase 2: Rename plan and safety engine (the name contract, collisions, reversibility)
- **Unlocks:** safe `--apply` on real libraries.
- **Depends on:** Phase 1's proven extraction result.
- **Tasks (widest first):**
  1. **Freeze the data contracts.** Filename format v1, the plan record (`src, dst, status, reason`), and the journal schema with a `schema_version`. Undo has to read journals written by older versions, so this has the widest blast radius in the tool.
  2. **A deterministic plan builder.** Sort by `(datetime, subsec, original name)` so the same input always gives the same output. Same-second bursts get `_01`, `_02` in capture order.
  3. **Collision resolution against three sets:** files already on disk, other targets in the same batch, and sources not yet renamed (chain and swap cases). On Windows and macOS, comparisons ignore case.
  4. **Idempotency.** A file already named correctly is a no-op, so a second run reports `renamed=0`.
  5. **`exifrename undo <journal>`** reverses completed entries in reverse order and refuses to overwrite anything.
  6. **Dry-run output:** a readable `old → new` table, the default when `--apply` is absent.
- **Exit check:** property tests (`hypothesis`) over random sets of names and dates show that applying the plan never loses or overwrites a file (file count and content hashes unchanged), and that `apply` then `undo` restores the original names exactly. A real folder of 1,000 or more photos runs end to end with no collisions lost.

### Phase 3: Failure-safe execution (interrupts and I/O errors)
- **Unlocks:** running on large or slow media without fear.
- **Depends on:** Phase 2's journal schema and undo.
- **Tasks (widest first):**
  1. **Write-ahead journaling.** Write and fsync `pending`, then rename, then write `done`. Undo resolves `pending` entries by checking which name actually exists.
  2. **A SIGINT/SIGTERM handler.** Finish the current rename, flush the journal, exit `3` and print the undo command.
  3. **Classified I/O errors:** permission denied, read-only media, Windows file locks, disk full and long paths. Each aborts cleanly with a reason code.
  4. **A FAT/exFAT path.** These systems have no hard links (common on SD cards). Detect them and use the exists-check + rename fallback, with the single-user race documented.
- **Exit check:** a fault-injection suite makes the rename fail at a random Nth file, and SIGINT is sent mid-run. In every case, `undo` on the journal restores the exact original set.

### Phase 4: Coverage and UX leaves
- **Unlocks:** real-world libraries and daily use.
- **Depends on:** Phase 3's safe executor.
- **Tasks (widest first):**
  1. **Companion files.** `.xmp`, `.aae` and Live Photo `.MOV` files with the same stem are renamed **as a group** with their photo, and the whole group rolls back if one rename fails. Getting this wrong breaks Lightroom and Apple Photos links.
  2. **`--recursive`:** stays inside the root and never follows symlinks.
  3. **Opt-in flags:** `--fallback=mtime` and `--allow-modify-date`, with every affected file flagged.
  4. **Polish:** a progress bar (on a TTY only), a per-category summary, coloured dry-run output, and the README.
- **Exit check:** a Lightroom- or Apple-style fixture folder keeps every photo-companion pair linked after rename and after undo. 1.0.0 is published.

## 6. AI layer
**N/A.** No model, retrieval or agent is involved. The only part of it that carries over is the data-privacy boundary, which is enforced in the gates and the Security column: metadata never leaves the machine.

## 7. Deliberately deferred
- **`--format` naming templates:** pulled forward by repeated user requests. The v1 format stays the default.
- **Timezone conversion (`--to-utc`):** pulled forward by multi-timezone users reporting wrong order.
- **Video files (MP4/MOV as primary files):** pulled forward by user demand. QuickTime `CreateDate` is usually **UTC**, unlike EXIF's local time, so this needs its own extraction rules and fixtures.
- **`exiftool` backend:** pulled forward automatically if any Phase 1 fixture fails with `exifread`.
- **Parallel EXIF reads:** pulled forward if the sync gate's throughput threshold is breached.
- **Sorting into date folders (`YYYY/MM/`):** pulled forward by demand. Moves across directories need different collision and undo handling.
- **Duplicate detection by content hash:** pulled forward if collision reports show many true duplicates.
- **Standalone binaries:** pulled forward if users can't use `pipx`.
- **Telemetry or crash reporting:** not planned. If ever added, it would be opt-in, send no metadata, and would need its own privacy review.
- **GUI or watch-folder mode:** pulled forward only after 1.0 is stable. It would reuse `core/` as a library, per the monolith gate.
