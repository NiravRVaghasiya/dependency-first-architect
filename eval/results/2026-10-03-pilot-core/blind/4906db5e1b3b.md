# Plan for building a CI/CD platform for 50 microservices

**Assumptions** (tell me if any are wrong and I'll adjust the plan): services are or can be containerized, they deploy to Kubernetes or something similar, you have a small platform team (2–5 engineers), and today each team runs its own mix of pipelines.

**Main idea:** First get one service all the way from commit to production. Then turn that path into reusable templates, and only then move services onto it in waves. Teams usually get this wrong by building every CI feature first, moving all 50 services, and leaving deployment and rollback for last.

---

## Phase 0: Discovery and contracts (weeks 1–2)
**Goal:** Know what you're working with and set the rules every service must follow.
- List all 50 services: language, build tool, how it deploys now, what it depends on, who owns it, and how critical it is.
- Group them into archetypes, for example "Java REST API", "Node worker" or "Python batch job". You'll usually find 4–6.
- Write down the **service contract**: a standard Dockerfile, health and readiness endpoints, config through environment variables or a config service, structured logs, a semantic version or commit SHA as the artifact ID, and one build command per repo.
- Choose the tools: CI engine, artifact registry, CD approach (GitOps with Argo CD or Flux, or a push-based tool), secrets manager.

**Done when:** the archetypes are mapped, the contract is published and the tools are chosen.

## Phase 1: Foundations (weeks 2–5)
**Goal:** Build the shared infrastructure everything else needs. Most of the work on the critical path is here.
- CI runners that scale automatically, with build caching.
- An artifact and container registry with retention and immutability policies.
- Identity and secrets: short-lived credentials (OIDC from CI to the cloud and registry), with no long-lived keys stored in pipelines.
- Environment setup: dev, staging and prod clusters or namespaces, defined in infrastructure-as-code.
- A GitOps config repo layout, or an equivalent deployment target model.

**Done when:** a "hello world" container builds, is signed, is pushed to the registry and deploys to dev automatically.

## Phase 2: Walking skeleton with 2–3 pilot services (weeks 4–8)
**Goal:** Take real services all the way to production in a basic way.
- Pick pilots that differ from each other: one simple, one with a database migration, one with downstream dependencies. Avoid the most critical service.
- Build the full path: commit → build → unit tests → image → dev → staging → manual promotion to prod → **tested rollback**.
- Add basic deployment notifications and links to dashboards.

**Done when:** each pilot deploys to prod and rolls back through the platform, and the owning teams have signed off.

## Phase 3: Golden-path templates (weeks 7–11)
**Goal:** Turn what worked in the pilots into reusable building blocks.
- Write versioned, reusable pipeline templates, one per archetype. Services include a template rather than copying it.
- Keep each service's pipeline to about 10–20 lines of config.
- Add service scaffolding (a cookiecutter or Backstage template) so new services start out compliant.
- Document how to override the template, and limit how much teams can override.

**Done when:** a new service goes from zero to deployed in dev in under a day without help from the platform team.

## Phase 4: Migration Wave 1, about 10 services (weeks 10–14)
- Pick low-to-medium-criticality services that cover every archetype.
- Have platform engineers pair with service teams, and keep a list of friction points.
- **Fix the templates, not the individual services.** If something is hard to migrate, treat that as a platform bug.
- Run the old and new pipelines in parallel for a short time, then shut the old one off.

**Done when:** 10+ services are on the platform, the most common friction points are fixed, and the migration runbook is written.

## Phase 5: Quality and security gates (weeks 12–18, overlapping Wave 2)
Add these **after** the basic path works, so gates don't hold up adoption:
- Static analysis, dependency and container scanning, and an SBOM for every build.
- Image signing and admission policy (for example cosign with Kyverno or Gatekeeper).
- Contract or integration tests in staging.
- Start every new gate in **warn-only mode**, then switch to blocking once false positives are under control.

## Phase 6: Migration Wave 2, about 25 services (weeks 14–20)
- Service teams migrate themselves using the runbook, and the platform team supports them.
- Hold office hours and set up a migration dashboard showing each service's status.

## Phase 7: Progressive delivery and the critical services (weeks 18–24)
- Add canary or blue-green deployments with automated analysis based on SLO metrics, plus automatic rollback.
- Add feature-flag integration and deploy windows or freeze controls if needed.
- **Wave 3:** move the remaining ~15 services, including the most critical ones, *after* safe rollout features are in place.

## Phase 8: Operate and improve (ongoing)
- Track the DORA metrics: deployment frequency, lead time, change failure rate and time to restore.
- Track pipeline speed against a budget, for example a CI run under 10 minutes, and keep tuning caching.
- Manage template versions with a deprecation policy and automated upgrade PRs (Renovate-style).
- Add self-service through a developer portal, cost visibility for runners, and preview environments.

---

## Dependencies and parallel work

```
Phase 0 → Phase 1 → Phase 2 → Phase 3 → Wave 1 → Wave 2 → Wave 3
                         ↘ Phase 5 (gates, warn-only) ↗      ↑
                                     Phase 7 (progressive delivery)
```

- **Critical path:** identity and secrets → registry → deployment model → pilot to prod with rollback.
- **Can run in parallel:** security gates, observability hooks and scaffolding can be built while migration waves are underway.
- **Hard rule:** don't move critical services until rollback is tested and progressive delivery exists.

## Common mistakes
1. **Building CI only and leaving CD for later.** The deployment model shapes everything, so settle it in Phase 2.
2. **Copy-pasted pipelines.** With 50 copies, every fix means 50 PRs. Use versioned templates from the start.
3. **Blocking gates too early.** Teams will avoid the platform. Start in warn mode.
4. **Too much flexibility.** If every override is allowed, you end up with 50 one-off pipelines. Make the golden path the easiest choice.
5. **Shared databases and coupled releases.** Find these in Phase 0. They may need expand-and-contract migrations, or have to be migrated together.

**Rough timeline:** about 6 months to have all 50 services on the platform with progressive delivery, given a team of 3–5. A smaller team or a more varied tech stack would push it toward 9 months.
