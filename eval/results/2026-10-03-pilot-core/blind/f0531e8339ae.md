# BUILD PLAN: CI/CD platform for 50 microservices

**Assumptions this plan's order depends on** (your request didn't say; if any is wrong, tell me and I'll re-sequence):
- **A1. The services already exist and already ship through some current CI.** If this is a new build instead, Phase 4's migration waves become onboarding waves, and V6 and Phase 5 go away.
- **A2. All 50 services deploy to Kubernetes.** If some don't, those targets need their own deploy step, built and gated before the wave that includes them.
- **A3. Code lives on GitHub, one repo per service.**
- **A4. No strict change-control rules apply** (for example SOX or PCI). If they do, approval and separation-of-duties steps go into the shared pipeline templates in Phase 2, and the change board must approve before Phase 0.

---

## 1. Classification and constraints
- **What:** one shared build, test and deploy platform that 50 existing services move onto, with each service's current pipeline kept as a fallback until it moves.
- **Type:** infrastructure plus platform software; existing system (A1); not a small build (many teams, and it holds production deploy access for every service).
- **Dominant constraint:** security and correctness of the path to production. One platform will hold deploy authority for all 50 services.
- **Worst failure:** someone gets into the pipeline, or a bad shared template ships, and an unverified artifact reaches production for many services at once. A long-lived production credential leaking from CI is the same failure.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Developer feedback time (PR checks start to finish) | p90 ≤ 10 min | ASSUMPTION: a common developer-productivity target; confirm with engineering leadership. Current value measured in Phase 0 | V2 |
| Runner queue time | p95 ≤ 2 min at 2× peak load | ASSUMPTION: queue time should be a small share of feedback time | V2 |

## 3. Tradeoff gates (decided up front)

**Inherited constraints** (kept as they are; cost to change):
- GitHub as the code host: re-permissioning every repo.
- Kubernetes as the runtime: re-platforming every service.
- One repo per service.
- The existing observability stack: re-pointing every alert and dashboard.

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Push vs pull deploys (the trust boundary) | R3: it decides where production credentials for 50 services live | **Pull (GitOps).** One Argo CD per environment cluster. CI only writes image-version bumps to a `deploy-config` repo and holds no cluster credentials. Cloud access uses short-lived OIDC tokens scoped per repo and environment. Each team gets an Argo AppProject that restricts it to its own namespaces | A2 | V3 | V3 fails on the GitOps path, or the inventory finds non-Kubernetes targets. Then: push with scoped OIDC, for those targets only |
| What may run in production | R3: it is the admission trust boundary | Build each image once and promote the same version through every environment. Every image is signed (cosign with a cloud KMS key) and carries an SBOM and build provenance. Kyverno checks signatures: audit-only first, then enforced one namespace at a time | Signature checking can be made highly available enough to sit in the pod-creation path | V3, V4 | V4 fails. Then: stay audit-only, alert on unsigned images, and scan continuously |
| Data-privacy boundary | R3: personal data that reaches build logs cannot be un-exposed | No production data in CI or test environments. Tests use synthetic fixtures. Runners have no network route to production data stores. Logs are masked, secret-scanned, and kept 90 days | No service's tests need copies of production data | V3 (network reachability test) | A service needs production-like data. If the platform is down, deploys stop; running services are unaffected. | Build vs buy | R2: rewriting 50 pipelines | **Buy and adopt:** GitHub Actions, ARC runners, Argo CD and Rollouts, Kyverno, a managed registry. | Pipeline definition (shared templates vs per-service YAML) | R2: the template inputs are a contract used by 50 repos | Reusable workflows, versioned with semver; each service pins a major version. | Runner model | R2 | Self-hosted, throwaway runners (one job per pod) in an isolated CI account with no route to production | Meets queue-time targets at an acceptable cost | V2 | V2 fails. Then: GitHub-hosted large runners using OIDC to reach the registry |
| Layout of the `deploy-config` repo | R2: moving 50 apps' config later is costly | One repo with a directory per team, service and environment, protected by CODEOWNERS. A required check rejects any bot commit outside the service's own folder | Path ownership can be enforced by CI checks plus branch protection | V3 (cross-team write attempt) | V3 shows a team can write to another team's folder. The record of what runs in production moves from the old CI to `deploy-config` at cutover | Old CI deploy jobs can be switched off per service | V5 (per wave) | V5 fails for a stack. Then: pause that stack and roll its services back to the old CI |
| Rollback and point of no return | R3 at decommissioning | Old deploy jobs are disabled, not deleted, until V6 passes. Argo Applications are set so that deleting one never deletes production resources | — | V6 | V6 finds something still depending on the old CI |

**R1 defaults:**
- Deploy feedback: Argo notifications write deploy status back to the GitHub commit.
- Signing: a cloud KMS key, not public Rekor, which would publish private repo names.
- Rollout style: Argo Rollouts canary for tier-1 services, rolling updates for the rest.
- Infrastructure as code: Terraform plus Helm with pinned versions.
- Telemetry: OpenTelemetry into the existing stack.
- Registry: managed (ECR or GAR) with immutable tags.

**N/A:**
- Monolith vs services, and data consistency, for the 50 services themselves: their architecture is out of scope.
- The AI rows: there is no AI component.

## 4. Walking skeleton (Phase 0)

**Before building:**
- Start the lead-time items: the CI account, GitHub App approval, deploy-path change approval, the security lead booking for V3, and the budget request.
- Take an inventory of everything that depends on the current CI, marking each CONFIRMED or ASSUMED: deploy jobs, cron and batch jobs run as pipelines, secrets stored in CI, release tooling, compliance evidence exports, and webhook consumers.
- Export 90 days of job history to get today's lead time, failure rate, and peak concurrency.

**The real request:** a real commit merged to `main` on **pilot-svc**. Pick an internal, stateless, low-traffic service whose team volunteers.

**The real response:**
- The commit status reads "deployed to prod @ <image version>".
- pilot-svc's `/version` endpoint returns the new commit hash.

**Tiers it crosses:**
1. GitHub
2. A draft reusable workflow in GitHub Actions
3. A throwaway ARC runner in the CI account
4. Build and unit tests
5. Push to the registry by image version, using OIDC
6. cosign signing plus an SBOM
7. A bot commit to `deploy-config/pilot-svc/prod`
8. Argo CD in the production cluster
9. Kyverno, audit-only
10. Pod rollout and health check
11. Status written back to the commit

**Deployed, logged, monitored, rolled back:**
- **Deployed:** all platform pieces are installed from Terraform and Helm in a `platform` repo.
- **Logged and traced:** pipeline runs are emitted as OpenTelemetry spans. Each deploy carries an ID (commit hash plus run ID) that links the CI run, the image version, the Argo sync, and a deploy marker on pilot-svc's dashboard.
- **Alerts:** a pipeline fails on `main`; an Argo app stays Degraded or out of sync for more than 10 min; runner queue exceeds 5 min.
- **Rollback:** `git revert` of the version bump. The fallback is pilot-svc's old pipeline, used after pausing Argo auto-sync.

**Who can reach it:**
- Argo CD and Grafana sit behind SSO, open only to the platform team and the pilot-svc team.
- Argo manages only pilot-svc's namespace.
- CI holds no cluster credentials from the first day.
- pilot-svc's users reach it exactly as they did before.

**Exit check (V0):**
- One real commit reaches production with a single trace across every tier.
- A deploy and a revert both succeed through the pipeline.
- An injected failure fires its alert. Use an image that fails its readiness check, and separately kill the ARC controller.
- The first lead-time, rollback-time and queue-time values are recorded. These are near-zero-load floors, not capacity.

## 5. Phases

- **Phase 1 — The trust boundary and supply chain**
  - Unlocks: Phase 2 (more services getting deploy authority); signature enforcement.
  - Depends on: V0.
  - Tasks (widest rework first):
    1. OIDC trust policies per repo and environment; a least-privilege GitHub App; removal of all static CI secrets; SSO and role-based access in Argo.
    2. The `deploy-config` repo layout, CODEOWNERS, the path-ownership check, and one AppProject per team.
    3. Artifact identity: deploy by image version only, immutable registry, SBOM, provenance, signing.
    4. Kyverno audit-only across the cluster, set up for high availability. Run V4, then enforce for pilot-svc's namespace only.
    5. Network isolation and outbound allow-list for runners.
    6. Log masking and secret scanning in the draft templates.
    7. Get the CI budget and the compliance answer (A4).
    8. Run V3.
  - Rollback: each control is a Helm or Terraform revert. Enforcement goes back to audit-only with one policy flag.
  - Exit check: V3 and V4 pass; a scan finds zero static production credentials in CI.

- **Phase 2 — Shared templates v1 and a pilot of 5 services**
  - Unlocks: freezing the template contract; Phase 4.
  - Depends on: V3, V4. Also A4 for any approval steps.
  - Tasks:
    1. Define the template input contract. This is the widest-rework item: all 50 repos will consume it.
    2. Build template families for the tech stacks found in the inventory.
    3. Add a staging environment and promotion of the same image version.
    4. Add a database migration step: expand/contract migrations, run as an Argo pre-sync job.
    5. Add Argo Rollouts canary with automated analysis for the one tier-1 pilot.
    6. Add test caching.
    7. Set up the template release process: semver, canary services first.
    8. Add a dashboard per service for lead time, deploy frequency, change failure rate and time to restore.
    9. Move pilot-svc plus 4 more services through the sequence: shadow runs, cutover, enforcement turned on in each namespace.
    10. Run V1.
  - Rollback: per service, pause Argo auto-sync and re-enable the old deploy job.
  - Exit check: V1 passes.

- **Phase 3 — Scale and operate the platform** (may overlap Phase 2 once Phase 2's first task, the contract, exists)
  - Unlocks: committing runner capacity for 50 services.
  - Depends on: Phase 2's first task; the CI budget from Phase 1.
  - Tasks:
    1. Runner autoscaling, a warm pool, and build caches.
    2. Registry replication and deletion protection.
    3. Platform service-level targets with burn-rate alerts.
    4. A platform on-call rotation and runbooks, including break-glass.
    5. Disaster-recovery drill: rebuild Argo CD and the runner fleet from infrastructure-as-code in a fresh cluster.
    6. Run V2.
  - Rollback: a revert of the fleet's infrastructure code. Capacity changes are additive.
  - Exit check: V2 passes; the recovery drill meets the data-loss targets in §1; ≤ 2 platform pages per week over 2 weeks.

- **Phase 4 — Migration waves** (exposure smallest first)
  - Unlocks: Phase 5.
  - Depends on: V1, V2, V3.
  - Tasks:
    - **Wave 1:** 10 low-risk services. **Wave 2:** 15. **Wave 3:** the remaining 20, including critical tier-1 services, which use canary rollouts.
    - Per service:
      1. Rebuild its pipeline on the templates.
      2. Run the new CI in shadow on PRs for one week.
      3. Switch deploy authority to the new path; disable (don't delete) the old deploy job.
      4. Do one production rollback drill.
      5. Turn on signature enforcement for its namespace.
    - V5 must pass before each next wave.
  - Rollback: per service, pause Argo and re-enable the old job.
  - Exit check: all 50 services deploy only through the platform; V5 passes for wave 3.

- **Phase 5 — Retire the old CI and finish enforcement**
  - Unlocks: running a single platform.
  - Depends on: Phase 4; the audit retention period (UNKNOWN, from compliance).
  - Tasks:
    1. Turn on signature enforcement across the cluster.
    2. Move the vulnerability gate from warn to block for critical CVEs, one team at a time.
    3. **Rehearsal:** disable the old CI's production credentials and scheduled jobs for 30 days.
    4. Export the old CI's audit history.
    5. Run V6.
    6. Revoke the credentials and delete the old pipelines.
  - **Point of no return:** step 6, guarded by V6. Until then, rollback means re-enabling the old credentials.
  - Exit check: V6 passes.

## 10. Deliberately deferred
Each item, with what would bring it forward:
- **Per-PR preview environments:** teams ask for them repeatedly, or staging contention becomes the main source of lead time.
- **Self-service portal (e.g. Backstage):** onboarding becomes the platform team's biggest source of work.
- **Hermetic, fully reproducible builds (SLSA level 3):** a customer or regulator requires them, or V3 finds a build-tampering path.
- **Canary analysis for every service** (not just tier-1): failures that a canary would have caught push V5's failure rate above today's value.
- **Merge queue and flaky-test quarantine:** feedback p90 goes over 10 min because of retries.
- **Multi-region or multi-cloud deploys:** a service gets a cross-region availability requirement.
- **Per-team cost showback:** CI spend goes over the V2 budget.
- **Non-Kubernetes deploy targets:** the Phase 0 inventory finds any (A2).
