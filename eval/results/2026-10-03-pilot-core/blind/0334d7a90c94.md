# Multi-Tenant SaaS Billing System: Architecture

**Assumption:** This design is for billing the customer organizations ("tenants") of a multi-tenant SaaS product. If you're building a billing platform that other SaaS companies use (like Stripe Billing), add a `merchant` level above tenants. The rest of the design stays mostly the same.

---

## 1. Requirements

**Functional**
- Pricing models: flat, per-seat, tiered/volume, usage-based, hybrid, prepaid credits, minimum commitments, and custom enterprise contracts.
- Subscription lifecycle: trials, upgrades and downgrades with proration, pause, cancel, scheduled changes, and keeping existing customers on old prices.
- Usage metering at high volume, with idempotent ingestion.
- Invoicing, tax, payments, dunning (retrying failed payments), credit notes and refunds.
- Multiple currencies, multiple selling legal entities, and parent/child accounts with consolidated billing.
- Entitlements: which features and limits each tenant gets.
- Exports for revenue recognition (ASC 606/IFRS 15) and the general ledger.

**Non-functional**
- **Correctness beats availability for money.** No double charges and no lost usage. Every amount must be auditable and reproducible.
- Strict tenant data isolation.
- Usage ingestion must keep accepting events when downstream services fail.
- Finalized invoices never change. Corrections go through credit notes.
- Compliance: PCI DSS (keep scope to SAQ-A by never touching card data), SOC 2, GDPR, and invoice-numbering laws in some jurisdictions.

Two different kinds of workload get two different stores:
- **Billing Core** has low volume but needs strong consistency, so it runs on **Postgres** with ACID transactions.
- **Usage** has high volume and only needs to be eventually aggregated, so it runs on **Kafka and ClickHouse**, with raw events archived to S3 for replay.

## 3. Core Domain Model

```sql
-- Every tenant-owned table has tenant_id as the first column of its PK/index.
tenants            (id, parent_tenant_id, seller_entity_id, currency, timezone,
                    tax_ids, billing_address, status)
billing_accounts   (id, tenant_id, payment_terms, default_payment_method_id, invoice_settings)

products           (id, name, ...)
prices             (id, product_id, version, currency, model,      -- flat|per_unit|tiered|volume|package
                    tiers jsonb, interval, meter_id, active_from, active_to)   -- never mutate; add new versions
meters             (id, event_name, aggregation,                   -- sum|max|count|unique_count|last
                    value_property, filters jsonb)

subscriptions      (id, tenant_id, account_id, status, billing_anchor,
                    current_period_start, current_period_end, trial_end,
                    cancel_at, contract_id, version)               -- version = optimistic locking
subscription_items (id, subscription_id, price_id, quantity, effective_from, effective_to)
subscription_schedules (id, subscription_id, phases jsonb)         -- future-dated changes
contracts          (id, tenant_id, commit_amount, overrides jsonb, start, end)  -- enterprise deals

usage_events       [ClickHouse] (tenant_id, meter, idempotency_key, value, ts, properties, received_at)
usage_aggregates   (tenant_id, subscription_item_id, period_start, period_end, value, computed_at)

invoices           (id, tenant_id, account_id, number, status, currency, subtotal,
                    discount, tax, total, amount_due, period_start, period_end,
                    finalized_at, due_at, pdf_url)
invoice_lines      (id, invoice_id, type, price_id, quantity, unit_amount_decimal,
                    amount, period_start, period_end, proration bool, metadata)
credit_notes       (id, invoice_id, reason, amount, lines ...)

payment_methods    (id, tenant_id, psp, psp_token, brand, last4, exp)   -- tokens only, never PANs
payments           (id, tenant_id, invoice_id, amount, status, psp_ref, idempotency_key)
payment_attempts   (id, payment_id, attempt_no, outcome, decline_code, next_retry_at)

credit_grants      (id, tenant_id, amount, remaining, priority, expires_at, source)
ledger_entries     (id, tenant_id, txn_id, account, direction, amount, currency,
                    ref_type, ref_id, created_at)                  -- append-only, double-entry

entitlements       (tenant_id, feature_key, limit, source_subscription_id, valid_until)
outbox             (id, aggregate_id, event_type, payload, created_at, published_at)
audit_log          (id, tenant_id, actor, action, before, after, at)
```

**Money rules**
- Store amounts as integers in minor units, such as cents, with an explicit currency.
- Allow `unit_amount_decimal` with higher precision for fractional usage prices, such as $0.00012 per API call.
- Round once per invoice line using a documented rule (banker's or half-up, decided per currency). Never round per event.

## 4. Multi-Tenancy Design

| Concern | Approach |
|---|---|
| **Data isolation** | `tenant_id` on every row, plus Postgres **row-level security** keyed on a session variable set by middleware. This protects data even if application code has a bug. |
| **Scale-out** | Shard Postgres by `tenant_id` (Citus, or app-level shard map) once one database isn't enough. Billing data per tenant is small, so this can wait. |
| **Noisy neighbors (usage)** | Per-tenant ingestion rate limits and quotas. Partition Kafka by `tenant_id`; split very hot tenants by `hash(tenant_id, key)` into sub-partitions. Isolated consumer pools for the largest tenants. |
| **Noisy neighbors (billing runs)** | Each tenant's billing anchor is its signup date by default, which spreads load across the month. If everyone is billed on the 1st, queue the billing run with per-shard concurrency limits. |
| **Hierarchies** | `parent_tenant_id` allows enterprises with many workspaces. Choose either a consolidated invoice at the parent or separate invoices per child. Usage can roll up to the parent's commitment. |
| **Custom deals** | `contracts` override catalog prices per tenant. The catalog stays clean and exceptions are explicit and auditable. |
| **Multiple entities and currencies** | Each tenant maps to a seller legal entity, which sets invoice numbering, tax registration and PSP account. Prices exist per currency; don't use live FX conversion in billing. |
| **Encryption** | Optionally use per-tenant keys (envelope encryption) for PII if enterprise customers require it. |

## 5. Key Flows

### 5.1 Subscription state machine
```
           ┌──────────┐ trial ends + pay ok ┌────────┐
 create ──►│ trialing │────────────────────►│ active │◄──────── payment recovered
           └────┬─────┘                     └─┬──┬───┘                 │
                │ no payment method           │  │ payment fails  ┌────┴─────┐
                ▼                             │  └───────────────►│ past_due │
           ┌──────────┐      cancel           │                   └────┬─────┘
           │ canceled │◄──────────────────────┘   dunning exhausted    │
           └──────────┘◄───────────────────────────────────────────────┘
                (paused is a side state: no invoicing, entitlements per policy)
```
- Every transition is a command (`ChangePlan`, `Cancel`, `Pause`) handled in one transaction that:
  1. updates the subscription (with an optimistic-lock version check),
  2. writes the outbox event,
  3. writes the audit log entry.
- **Proration:** on a mid-cycle change, credit the unused time on the old item and charge the remaining time on the new item. Measure time to the second and make the policy configurable: prorate now, at the next invoice, or not at all.
  - Upgrades usually invoice immediately.
  - Downgrades usually take effect at the period end via `subscription_schedules`.

### 5.2 Usage ingestion → rated line items
1. **Ingest:** `POST /usage` accepts batched events with a client-supplied `idempotency_key`. The service validates the schema and the tenant, writes to Kafka, and returns `202`. Its only dependency is Kafka, so it stays available when other services are down.
2. **Archive:** all raw events go to S3 so any period can be replayed and re-aggregated.
3. **Dedupe:** use a keyed state store of `(tenant_id, idempotency_key)` with a TTL longer than the maximum late-arrival window. As a second safety net, use a ClickHouse `ReplacingMergeTree`.
4. **Aggregate:** keep running per-meter totals by subscription item and period. These feed real-time spend alerts, usage caps and customer dashboards.
5. **Rate at invoice time:** apply the price (tiers, packages, contract overrides) to the final aggregate for the period. Rating is a pure function of `(aggregate, price version, contract)`, so it is deterministic and can be re-run.
6. **Late events:** set a grace window, such as 24 hours after period close. Events arriving after the invoice is finalized go on the next invoice as a "prior-period adjustment" line, or are dropped, depending on policy. Never edit a finalized invoice.

### 5.3 Billing run (invoice generation)
```
Scheduler (every minute):
  SELECT subscriptions WHERE current_period_end <= now() AND status IN (active, past_due)
  → enqueue job with key = (subscription_id, period_end)   -- idempotent; reruns are no-ops

Job:
  1. Roll period forward (in txn) → current_period_* = next period
  2. Create DRAFT invoice:
       recurring lines (in advance) for new period
     + usage lines (in arrears) for closed period, after grace window
     + proration lines accumulated
     − discounts / coupons
  3. Apply credit grants (by priority, then expiry)
  4. Tax calculation (external; cache by address+product tax code; fallback queue on outage)
  5. Draft window (e.g. 1h, or longer for enterprise review) → allows manual adjustments
  6. FINALIZE: assign invoice number (gapless sequence per seller entity, allocated in txn),
     write ledger entries (DR Accounts Receivable / CR Deferred Revenue + Tax Payable),
     render PDF, emit invoice.finalized
  7. Collect: auto-charge, or send invoice with net-30 terms
```

**Invoice states:** `draft → open (finalized) → paid | void | uncollectible`. Once an invoice is `open`, it can only be corrected with credit notes.

### 5.4 Payments and dunning
- A **PSP adapter** interface (`charge`, `refund`, `createSetupIntent`) wraps Stripe or Adyen. Each seller entity can route to a different PSP account.
- Card collection uses PSP-hosted elements, so card numbers never reach our systems (PCI SAQ-A). We store only tokens.
- Every charge carries an idempotency key, `payment:{invoice_id}:{attempt_no}`, so retries after timeouts can't double-charge.
- **Webhooks are the source of truth** for final payment status. Verify signatures, store the raw event, process idempotently by PSP event ID, and handle out-of-order delivery.
- **Dunning** follows a configurable schedule (for example day 0, 3, 5, 7) with smart retry timing based on decline codes. It sends emails at each step, and SCA/3DS challenge links when needed.
  - When dunning starts, the subscription becomes `past_due`, but entitlements stay in a grace period.
  - When dunning is exhausted, the subscription is canceled or downgraded per policy.
- **Reconciliation job (nightly):** match PSP balance transactions against `payments` and ledger entries. Alert on any mismatch.

### 5.5 Entitlements (keeping billing off the product's hot path)
- Billing emits `subscription.updated` and `invoice.paid` events. The entitlement service turns them into `(tenant, feature, limit)` records.
- Product services read entitlements from a local cache or Redis with roughly 1 ms latency. **Product requests never call billing synchronously.**
- If billing goes down, customers can still use the product; they just can't change plans until it's back.

## 6. Ledger and Financial Integrity
- **Double-entry and append-only.** Every financial event (invoice finalized, payment received, refund, credit applied, write-off) writes balanced debit and credit entries in one transaction. Balances are derived from entries, never stored as editable fields.
- **Invariant checks:** within each transaction, the sum of debits equals the sum of credits. Each tenant's AR balance must equal open invoices minus unapplied payments. Run these checks continuously and alert on any violation.
- **Revenue recognition:** spread deferred revenue ratably over each line's service period. Export to the ERP (NetSuite) or a rev-rec tool daily.
- **Reproducibility:** each invoice line stores the price version, aggregate value and contract version used, so any invoice can be recomputed and explained.

## 7. Reliability Patterns
| Pattern | Where |
|---|---|
| Idempotency keys (stored with the response, 24h+ TTL) | All mutating APIs, usage ingestion, PSP calls |
| Transactional outbox → event bus | Every state change in Billing Core. No dual writes. |
| Deterministic job keys | Billing runs, dunning steps, tax retries |
| Optimistic locking (`version`) | Subscriptions, invoices in draft |
| Sagas with compensation | Plan change → invoice → charge → (on failure) revert or leave past_due |
| Test clocks | Per-tenant simulated time, so trials, renewals and dunning can be tested end to end |
| Shadow billing | When migrating or changing pricing, compute invoices in parallel and compare before cutover |

## 8. Scaling Profile (rough)
- **Billing Core:** about 10⁵–10⁶ subscriptions is easy on one Postgres primary with replicas. Shard by tenant when you go beyond that.
- **Usage:** 10⁴–10⁶ events per second. Scale out ingestion pods and Kafka partitions. ClickHouse handles billions of rows per day, and pre-aggregated materialized views keep queries cheap.
- **Billing runs:** they parallelize by subscription. 1M invoices on the 1st of the month comes to about 12 per second spread over a day. That's manageable, but the tax API and PSP rate limits are usually the real bottleneck, so throttle per provider.

## 9. Security and Compliance
- PCI: tokenize cards and use only PSP-hosted payment fields.
- RBAC for internal tools. Manual credits, refunds and write-offs above a threshold need two-person approval, and all of them are logged.
- GDPR: keep PII (name, address, email) separate from the financial records you're legally required to retain. On an erasure request, anonymize the PII and keep invoices for the statutory 7–10 years.
- Invoice compliance: gapless numbering per entity, required legal fields, and e-invoicing (PEPPOL, Mexico's CFDI, India's GST e-invoice) added as region-specific renderers or submitters.

## 10. Build vs. Buy
Billing has a lot of hidden complexity (tax, proration edge cases, dunning, invoice compliance). A common pragmatic split:

| Buy | Build |
|---|---|
| PSP (Stripe/Adyen), tax engine (Avalara/Stripe Tax) | Entitlements (tightly coupled to your product) |
| Optionally the whole subscription/invoice engine (Stripe Billing, Chargebee, Orb, Metronome; Lago if you want open source) | Usage ingestion pipeline, if volume or latency outgrows vendors |
| Rev-rec (or ERP module) | The thin "billing domain" layer that maps product concepts to the vendor, so you can switch vendors later |

Build the full core yourself if pricing is a competitive differentiator, you need complex enterprise contracts, or vendor fees (often 0.5–0.8% of revenue) become significant at scale.

## 11. Phased Rollout
1. **MVP:** catalog, flat and per-seat subscriptions, Stripe payments, invoices, basic dunning, entitlements, outbox and ledger from day one. A ledger is very painful to retrofit.
2. **Usage:** metering pipeline, tiered and usage pricing, real-time usage dashboards and alerts.
3. **Enterprise:** contracts and commitments, parent/child accounts, invoice terms and purchase orders, prepaid credits.
4. **Global:** multiple currencies and entities, e-invoicing, regional PSPs, rev-rec automation.
