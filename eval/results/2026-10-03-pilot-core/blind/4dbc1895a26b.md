# Plan: CI/CD platform for 50 microservices

## 1. Classification and constraints
- **What:** a shared build, test, sign, publish and deploy platform that 50 existing microservices move onto. It replaces their mixed legacy pipelines.
- **Type:** infrastructure and platform software. Brownfield (the services and their current deploy paths already exist). Not a small build: about 50 owning teams, production credentials, and a trust boundary between CI and production.
- **Dominant constraint:** correctness of what gets deployed. What runs in production must be exactly what was reviewed, built and tested. A close second is the platform's own availability, because once it is the only path, an outage blocks every team's hotfixes.
- **Worst failure:** a compromised pull request, CI runner or token pushes an unreviewed or malicious artifact into production across all 50 services. This is a supply-chain breach, and its impact is the whole estate. Gate V1 guards it.

**Missing inputs** (the plan states its assumption for each):
1. **Deploy targets.** Assumed: most services are containerized on Kubernetes. If a large share run on VMs or serverless, a target-normalization phase or a push-deploy path is added before Phase 3. That changes the phase order, so confirm this first.
2. **Legacy CI and everything else it runs** (cron jobs, backups, release notes, compliance exports). The Phase 0 inventory finds these.
3. **Source-control platform and repo layout.** Assumed: GitHub, one repo per service. If it's GitLab, swap in GitLab CI; the order doesn't change.
4. **Compliance regime.** Assumed: SOC 2-style change control. SOX or PCI would add separation-of-duties approvals in Phase 1 and Phase 4.
5. **Organization:** the CI budget, platform team size, the named security reviewer for V1, and the owner and criticality tier of each service.

If the services are actually greenfield, Phases 3–4 become onboarding waves and Phase 6 disappears. The rest of the order holds.

| Build vs buy | R2: the pipeline language gets written into 50 repos | Buy and compose: source-control-native CI (GitHub Actions) with self-hosted ephemeral runners on Kubernetes (ARC), Argo CD, the existing registry, Kyverno | Native CI meets throughput and cost | V2 | V2 fails on cost → hosted runners or spot capacity. - Versioning: SemVer tags plus commit-SHA labels; the digest is the deploy identity.
- Secrets: cloud secret manager through External Secrets Operator.
- Environments: dev, staging, prod.
- Dashboards: the existing observability stack.

## 4. First end-to-end slice (Phase 0)
- **Inventory first.** Record all 50 services: language, deploy target, current CI, DB migrations, owner, criticality tier. Record everything else the legacy CI runs (each item CONFIRMED or ASSUMED). Baseline lead time, change-failure rate, build time and peak concurrent jobs from legacy logs. Start the organizational items: budget, security reviewer, admin rights, compliance regime.
- **The one real request:** a merged commit to one real service from the 50 that is low-criticality, stateless and internal (`svc-pilot`).
- **The real response:** that service's `/version` endpoint in production returns the new commit SHA, and the deploy status is posted back on the commit.
- **Tiers it crosses:**
  1. GitHub.
  2. Actions job on an ephemeral ARC runner: build and unit tests.
  3. Registry: push by digest, using OIDC.
  4. Environment-config repo: digest bump.
  5. Argo CD syncs staging and runs a smoke test.
  6. Promotion PR.
  7. Argo CD syncs production.
  8. The service.
  9. Observability.
- **Deployed:** platform infrastructure through Terraform, with Argo CD bootstrapped by Helm. After that the platform manages itself through an app-of-apps.
- **Logged:** CI and Argo logs go to the existing log store with secret masking.
- **Monitored:** pipeline events are correlated end to end by commit SHA through an OpenTelemetry CI exporter. Alerts fire on pipeline failure, Argo sync failure or degraded state, and runner queue depth.
- **Rolled back:** revert the digest commit in the environment repo, and Argo restores the previous image. Platform components roll back by Git revert. For `svc-pilot`, the legacy prod job is disabled, not deleted, and re-enabling it is the fallback.
- **Who can reach it:** only the platform team can merge to `svc-pilot` and the environment repo. Branch protection is on, CI holds no cluster credentials, and no other service uses the path. Signing and admission enforcement aren't in place yet (Phase 1).

Exit check (V0): see §6.

## 5. Phases

- **Phase 1 — Supply-chain trust boundary and pipeline contract**
  - Unlocks: other services can be exposed on the new path.
  - Depends on: V0, the inventory, the security reviewer.
  - Tasks, widest rework first:
    1. Pipeline contract v0: stages, artifact naming, required checks, hooks.
    2. OIDC federation for all cloud access; remove static secrets; secrets through External Secrets Operator.
    3. Runner isolation: ephemeral pods, an untrusted-PR pool with no secrets, an egress NetworkPolicy.
    4. Signing, provenance and SBOM added to the template.
    5. Kyverno `verifyImages`: audit mode in production first, then enforce for namespaces the platform manages.
    6. CODEOWNERS and a production-promotion review rule on the environment repo (two-person if compliance requires it).
    7. Secret scanning and log masking.
    8. Run V1.
  - Rollback: every policy lives in Git and can be reverted. Admission stays fail-closed (see §3); bypass goes only through break-glass.
  - Exit check: V1 passes.

- **Phase 2 — Golden path on a pilot group, plus capacity**
  - Unlocks: template v1 frozen; waves at scale.
  - Depends on: V1.
  - Tasks:
    1. Promotion model: same digest dev → staging → prod.
    2. Onboard 4 more pilot services of different kinds, so 5 with `svc-pilot`: different languages, and one with a DB whose migration stays manual for now.
    3. Version the templates, and roll template changes out to the pilot services first.
    4. Runner autoscaling across availability zones; build caching.
    5. Run V2 and V4.
    6. Retention policies; DORA dashboards.
  - Rollback: re-enable a service's legacy job.
  - Exit check: V2 and V4 pass; template v1 is tagged.

- **Phase 3 — Stateless waves, exposure smallest first**
  - Unlocks: most services on the platform.
  - Depends on: V2, V4.
  - Tasks:
    1. Move hidden legacy jobs to Kubernetes CronJobs before the jobs they live on are frozen.
    2. Wave A: about 10 internal, low-tier services.
    3. Wave B: about 15 customer-facing services that aren't tier-1.
    4. Per service:
       - Run shadow builds for one week and compare test results with the legacy pipeline.
       - Cut over deploy authority.
       - Run a rollback drill in staging.
       - Disable the legacy prod credentials.
  - Rollback: per service, re-enable the legacy job (kept until V6).
  - Exit check, per wave before the next one widens:
    - Change-failure rate ≤ BASELINE.
    - Rollback ≤ 10 min (ASSUMPTION).
    - No severe incident attributable to the platform.

- **Phase 4 — Stateful and tier-1 services**
  - Depends on: Phase 3, V3, V5.
  - Tasks:
    1. V3 rehearsal; the migration becomes its own gated step.
    2. V5 game day.
    3. Stateful waves.
    4. Tier-1: one service first, then the rest; production approval rules applied.
  - Rollback: per service, the legacy job.
  - Exit check: V3 and V5 pass; wave checks as in Phase 3; all 50 services cut over.

- **Phase 5 — Progressive delivery and platform SLOs**
  - Depends on: Phase 4; per-service SLO metrics.
  - Tasks:
    1. Platform SLO (99.5%, ASSUMPTION) with error-budget alerts.
    2. Argo Rollouts canaries: manual promotion for tier-1; automated analysis only where SLO metrics exist.
    3. Critical-CVE policy moves from warn to block.
    4. Cross-region registry replication.
  - Rollback: rollout specs are reverted in Git.
  - Exit check: SLO dashboard live for 30 days; one canary auto-abort demonstrated.

- **Phase 6 — Decommission the legacy CI**
  - Depends on: all 50 services cut over; V6.
  - Tasks:
    1. Set the legacy CI read-only for 30 days.
    2. Export the audit and build history, and test a restore.
    3. Revoke all legacy credentials and service accounts.
    4. Delete.
  - **Point of no return:** deletion, guarded by V6.
  - Exit check: V6 go/no-go is signed and the deletion is recorded.

## 10. Deferred
- **Internal developer portal (Backstage):** when onboarding goes over 1 engineer-day, or the service count passes about 100.
- **Automated canary analysis for every service:** per service, once it emits SLO metrics.
- **Ephemeral preview environments:** when integration defects found in staging become a top cause of change failure.
- **SLSA L3 / hermetic builds:** when a compliance or customer contract requires it.
- **Monorepo build tooling (Bazel, remote execution):** when build p95 still misses 15 min after caching.
- **Multi-region active platform:** when the availability or RTO requirement goes beyond what V5's break-glass covers.
- **CI cost chargeback per team:** when V2's cost projection lands within 20% of the budget.
- **Push-deploy path for targets other than Kubernetes:** when the inventory finds them (see the trust-boundary flip row).
