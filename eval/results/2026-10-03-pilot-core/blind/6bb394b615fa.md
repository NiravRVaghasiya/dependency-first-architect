# Plan: Real-time fraud detection for card transactions

## 1. Classification and constraints
- **What:** A service that scores every card authorization inline, using streamed per-card features and an ML model on top of rules. It starts by watching only, then advises analysts, then decides for a small cohort, then widens.
- **Type:** Software, data streaming, and an ML scoring model. There is no LLM or agent. It is brownfield: it plugs into an existing authorization path and works next to the existing fraud rules. This is not a small build: it handles money and regulated cardholder data, it involves several teams, and it has R3 decisions.
- **Dominant constraint:** Correctness under a hard latency limit. The decision has to fit inside the auth path's time slice, and it has to be right.
- **Worst failure:** The scorer causes legitimate customers to be declined in bulk, through a bad model, a bad threshold push, or a timeout that the auth path turns into declines. A wrong decline cannot be taken back. The second worst is card numbers (PANs) leaking out of the PCI cardholder-data environment (CDE) into features, logs or training data. Those are guarded by V5 and V4.

**Starting assumptions (the plan's shape depends on them):** We are a card issuer, or an issuer-processor. There is an existing auth platform, an existing rules engine that also serves as the fallback, a token vault or HSM, case management, and Kafka. If we are actually an acquirer, PSP or merchant, the integration point becomes a pre-auth API and the labels come from chargebacks through the acquirer. The phase order stays the same. If we are a processor serving many issuers, tenant isolation becomes an extra R3 row and a gate before Phase 3.

**minor defaults:**

- Stream processor: Flink.
- Online store: Aerospike or Redis, behind an interface; it can be rebuilt from the event log.

- Infrastructure as code: Terraform.

## 4. First end-to-end slice (Phase 0)
- **The request:** A real authorization on an internal test card at a real merchant (a small card-not-present purchase). The scorer returns a stub score and a reason code. The auth platform logs that response and ignores it. The existing rules make the actual decision.
- **Tiers crossed:**
  1. Card network
  2. Auth platform hook (tokenizes the card number, checks the flag and allow-list)
  3. Scorer over mTLS (schema validation, increments one velocity counter in the online store, stub rules and model)
  4. Response back to the auth platform
  5. Decision event to Kafka
  6. Decision log store
  7. Dashboard
- **Day zero:**
  - Deployed through CI/CD from IaC with pinned images.
  - Traces use the auth correlation ID and the token, never the PAN. Telemetry is classified as cardholder-adjacent and access to it is restricted.
  - Alerts fire on scorer errors and latency, and on a change in auth latency.
  - One rollback is rehearsed: redeploy the previous version, then switch the flag off.
- **Discovery and baselines, also in Phase 0:** Find everything that consumes the existing rules' output. Through the auth platform's own change process, baseline auth p99, peak TPS, the existing rules' decline rate, fraud losses in basis points, and the false-positive rate.
- **Lead-time items started in Phase 0:** QSA engagement, model-risk validator time, data-access approval, and the efficacy targets from fraud risk.
- **Who can reach it:** Only allow-listed internal test-card tokens, behind a flag. The response cannot change any decision; it is a dry run.

**Exit check (V0):**
- The test authorization succeeds with one trace across every tier.
- A deploy and a rollback succeed through the pipeline.
- Killing the scorer fires an alert, and the auth path's outcome and latency do not change.
- Auth latency with and without the hook, and scorer p99 at near-zero load, are recorded as baselines.

## 5. Phases
- **Phase 1: Contracts and safety rails**
  - Unlocks: real data leaving the CDE; any later use of a score.
  - Depends on: V0.
  - Tasks:
    1. Canonical event schema in the registry, with contract tests on real auth message samples.
    2. Tokenization hardened at the hook, plus PAN scanners on every topic, log and store (V4 continues).
    3. Fail-safe path, tested against a stub that declines everything, on test cards (V5):
       - hard timeout falling back to the existing rules
       - kill switch
       - circuit breaker on decline rate, comparing treatment with control
       - malformed-response handling
    4. Get the efficacy and cost inputs (UNKNOWN in §1) from the head of fraud risk and from finance.
    5. Record the confirmed latency slice in V2.
  - Rollback: schema changes are expand/contract only; the hook can be switched off with a flag.
  - Exit check: V5 passes; contract tests pass in CI; the UNKNOWN inputs have numbers.

- **Phase 2: History, labels, offline model**
  - Unlocks: the build-vs-buy decision and the design of the streaming platform.
  - Depends on: Phase 1, V4, data-access approval.
  - Tasks:
    1. Backfill at least 13 months of tokenized auth history into the offline lake, under the retention policy.
    2. Label pipeline joining claims and chargebacks to transactions, plus the 200-sample label audit.
    3. Measure the label-maturity curve.
    4. Score the existing rules on the same history to get their baseline.
    5. Train a gradient-boosted model using only features that can be computed online within the latency slice (V1).
    6. Start model documentation for V6.
  - Rollback: everything is offline; derived datasets are deleted under the retention policy.
  - Exit check: V1 passes; the label audit passes.

- **Phase 3: Streaming features and full-traffic shadow**
  - Unlocks: trustworthy online scores.
  - Depends on: V1, V4.
  - Tasks:
    1. Single feature definitions that compile to both the Flink job and the offline batch.
    2. Online store keyed by token, with inline velocity counters.
    3. The model served in-process from a signed registry artifact.
    4. Every authorization mirrored async to the scorer. Shadow only; the auth path does not wait for it.
    5. Load test (V2) and parity check (V3).
    6. Rebuild-the-store drill and DR drill.
  - Rollback: stop the mirror; the online store is disposable and rebuilt from the log.
  - Exit check: V2 and V3 pass; the store rebuild meets the RTO.

- **Phase 4: Analyst advisory**
  - Unlocks: the first human use of scores, and labels within days instead of the 90-day maturity window.
  - Depends on: V3, V5, V6.
  - Tasks:
    1. Switch to the inline call (hard timeout) for all traffic, with the score logged but not used to decide.
    2. Send high scores to the case-management queue; analysts decide.
    3. Log reason codes.
  - Rollback: switch off the queue feed; the existing rules' alerts carry on.
  - Exit check: the precision of score-driven alerts, as judged by analysts, is no worse than the existing rules' alerts over 2 weeks; no regression in auth latency.

- **Phase 5: Decision canary, then widen**
  - Unlocks: model-driven declines for everyone.
  - Depends on: V5, V6, plus the EU legal review if it applies.
  - Tasks:
    1. Hashed card cohorts at 1%, then 5%, 25% and 100%, each with a matched control on the existing rules only.
    2. Threshold changes are versioned config shipped through the pipeline, approved by two people.
    3. V7 must pass at each step before widening.
  - Rollback: the per-cohort kill switch puts that cohort on rules only (tested in V5). There is no point of no return because the existing rules are kept. Wrong declines cannot be undone, which is why V5 and V7 come before each step.
  - Exit check: V7 passes at 100%; the breaker has not tripped for 30 days.

- **Phase 6: Feedback and model lifecycle**
  - Unlocks: sustained performance as fraud patterns shift.
  - Depends on: Phase 5.
  - Tasks:
    1. Monthly retraining on matured labels.
    2. Champion/challenger: the challenger runs in shadow before promotion.
    3. Drift alerts on feature distributions (PSI).
    4. Label corrections reviewed by fraud ops; first-party claims excluded.
    5. Each promotion goes through model-risk review as in V6.
  - Rollback: roll the registry back to the previous champion.
  - Exit check: a challenger beats the champion out-of-time and in shadow before it is promoted, with no segment getting worse.

## 8. AI layer
This is an ML scoring model, not an LLM. The sublayers are read for fraud scoring here.

| Sublayer | In this system | Built in | Exit check or V-ID |
|---|---|---|---|
| 1. Guardrail defense | Fraudsters control the inputs and probe for thresholds. Defenses: schema and range validation, hard rules the model cannot override, the decline-rate breaker, no score shown to outsiders. | Phase 0 (validation), 1 (breaker) | V5 |

## 10. Deferred
- **Active-active multi-region scoring:** pulled forward if the DR drill shows fallback-mode losses that fraud risk will not accept.
- **Async graph or ring detection** (mule networks, compromised merchants): pulled forward when fraud ops reports patterns that per-card features miss.
- **Separate models per segment** (card-present vs card-not-present) with routing: pulled forward when one segment trails the overall model by more than the agreed margin.
- **3DS step-up as a softer action than decline:** pulled forward when the issuer's 3DS access control server can be integrated.
- **Exploration traffic** (approving a small sample of flagged transactions to get unbiased labels): only with explicit approval from fraud risk, and once selection bias is measured to distort retraining.
- **Sequence or deep-learning models:** pulled forward when the gradient-boosted model plateaus across two retraining cycles.
- **Decommissioning the existing rules:** not in this plan; they are the fallback. Pulled forward only if their run cost becomes significant. It would then need its own gate: a named approver, a rehearsed fallback replacement, and 6 months at 100% with no breaker trips.
