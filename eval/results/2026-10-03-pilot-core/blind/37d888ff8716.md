# Plan: Moving patient scheduling to the cloud without downtime

## The core rules

1. **Only one system takes bookings at any moment.** Scheduling has one rule that can't be broken: no double-booked slots. Avoid having both systems write at once (dual-write) and avoid two-way sync while both are live. Copy data one way to the cloud, then move "write authority" over in a single controlled switch.
2. **What "no downtime" realistically means:** users never see an outage. At the moment of the switch there is usually a write pause of a few seconds to under a minute, hidden by automatic retries. If you need literally zero pause, the app needs extra work (queued writes), so decide this early.
3. **Every step must be reversible** until the on-premises system is shut down.

---

## Phase 0: Discovery and compliance (weeks 1–4)

- **List everything connected to scheduling:** the database, app servers, and every integration. That usually means:
  - the EHR, plus HL7 messages for patient admissions (ADT) and appointments (SIU)
  - the interface engine (e.g., Mirth or Rhapsody)
  - registration, billing and eligibility checks
  - reminders (SMS, phone, IVR)
  - the patient portal and kiosks
  - reporting and data-warehouse feeds
  - printers and label makers
- **Measure the workload:** peak bookings per minute, busiest hours, and database size and change rate.
- **Set targets:** how much data you can afford to lose (RPO, which should be about zero) and how fast you must recover (RTO).
- **Compliance:** sign a BAA (Business Associate Agreement) with the cloud provider, use only HIPAA-eligible services, update the HIPAA risk analysis, and confirm data-residency rules. I'm assuming you're in the US; use GDPR or local equivalents otherwise.
- **Pick a strategy:** I'd usually recommend replatforming: the same app on cloud VMs or containers, plus a managed database.
- **If this is a vendor product** (e.g., Epic Cadence), the vendor's hosting and migration path will drive most of this plan. Check that first.

## Phase 1: Cloud foundation (weeks 3–8)

- Redundant private network links between the hospital and the cloud (e.g., Direct Connect or ExpressRoute), with VPN backup.
- Single sign-on tied to your existing directory (AD/Entra), using least-privilege access.
- Encryption of stored data with keys you manage, and TLS for data in transit.
- Network segmentation, plus central audit logging kept as long as policy requires.
- Everything defined as code (infrastructure-as-code), with backups and a multi-zone setup for high availability.

## Phase 2: Build the cloud copy alongside the old one (weeks 6–12)

- Deploy the app in the cloud. Make the app tier stateless if possible.
- Put a **routing layer** (proxy, load balancer or DNS with a short TTL) in front of both systems. The final switch then becomes a configuration change, not a reinstall.
- Make integration endpoints configurable, so the interface engine can be repointed without code changes.

## Phase 3: Data replication (weeks 10–14)

- Do an initial bulk copy, then continuous one-way change data capture (CDC), on-premises → cloud. Tools include AWS DMS, Azure DMS, Debezium, or native database replication.
- **Validate continuously.** Check row counts and checksums, and also business checks such as "appointments per provider per day match" and "no orphaned slots."
- Track replication lag. Your cutover depends on it staying near zero at peak load.

## Phase 4: Shadow running and testing (weeks 12–18)

- Run the cloud app **read-only** against the copied data. Replay or mirror real read traffic and compare responses.
- Move low-risk read traffic to the cloud first, such as reporting and schedule lookups.
- Load-test at 2–3× your peak volume.
- **Integration rule:** only the active system may send outbound HL7 appointment (SIU) messages, so the EHR never gets duplicates. Keep the cloud system's outbound messages switched off until cutover.
- Run **at least two full dress rehearsals** of the cutover and the rollback, using production-sized data, and time each step.

## Phase 5: Cutover (one planned night, about 1–2 hours including checks)

Pick the lowest-volume window, typically early on a Sunday morning. Clinical leadership signs off, and the change freeze is in effect.

1. **Go/no-go check:** replication lag under ~1 second, validation passing, rollback tested, on-call staff confirmed, and paper downtime procedures ready just in case.
2. Pause queued outbound jobs (reminders, batch exports).
3. Set the on-premises database to read-only. The write pause starts here, and the app retries bookings automatically.
4. Wait for replication lag to reach zero, then run a quick validation.
5. Make the cloud database the primary and allow writes.
6. Switch the routing layer to the cloud app. The write pause ends here, and the target is under 60 seconds.
7. **Start reverse replication** (cloud → on-premises) so the old system stays current for rollback.
8. Point the interface engine's inbound and outbound feeds at the cloud, then turn on the cloud's outbound messages.
9. Run smoke tests: book, reschedule and cancel a test patient from start to finish, and confirm the EHR received the messages.
10. Resume the queued jobs.

**Roll back if any of these happen:** error rate or response times exceed agreed limits, data mismatches appear, integration messages fail, or clinicians escalate problems. To roll back, reverse steps 5–8. The on-premises system already has every change through reverse replication.

## Phase 6: Hypercare and shutdown (30–90 days)

- Watch the system closely with on-site support in the first week, and survey scheduling staff.
- Keep the on-premises system warm with reverse replication for 30–90 days.
- Then shut it down: take a final archive, wipe the data to NIST 800-88 standards, and update disaster-recovery and downtime runbooks for the cloud setup.

## Main risks and how to reduce them

| Risk | How to reduce it |
|---|---|
| Double bookings or lost bookings | One system writes at a time; never dual-write; business-level checks |
| Duplicate or missing HL7 messages | Only the active system sends; message IDs that can safely be resent; reconcile counts |
| Network link to the cloud fails | Redundant links; keep on-premises devices like printers and kiosks working locally |
| Slowness for on-site users | Pick a nearby cloud region; test response times from hospital workstations |
| Compliance gaps | BAA, updated risk analysis, audit logging checked before go-live |
| Staff confusion | Communicate ahead; nothing visibly changes; paper downtime procedures on standby |
