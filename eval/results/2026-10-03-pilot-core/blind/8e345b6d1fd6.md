# Plan: Real-time collaborative document editor

## 1. Classification and constraints
- **What:** A browser-based rich-text editor. Several users edit the same document at once, see each other's changes live, and every document is saved permanently.
- **Type:** Software, greenfield, not a small build. It has outside users, user content that may include personal data, and several R3 decisions (merge model, saved format, who-can-access-what).
- **Dominant constraint:** Correctness. Every copy of a document must end up identical, and no edit the user was told is saved may be lost.
- **Worst failure:** An edit shown as "Saved" disappears, or copies silently drift apart and corrupt the document. A close second is a user opening a document they are not allowed to see. V3 and V5 guard these two.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Remote edit delay (a keystroke on A appears on B, same region) | p95 < 200 ms, p99 < 500 ms | ASSUMPTION: a commonly cited point where edits feel live; product owner to confirm | V0 records the floor; V4 |
| Local typing delay | p95 < 16 ms from key press to screen, on a 1 MB document | ASSUMPTION: one frame at 60 Hz | V1 |
| Document open time | p95 < 1.5 s for a 1 MB, ~200-page document with a year of edit history | ASSUMPTION: a large but realistic document | V1 |
| Simultaneous editors per document | 50 | ASSUMPTION: similar products cap live editors at around 100; product owner to confirm | V4 |
| Total simultaneous connections | — | UNKNOWN: needs the launch user forecast from the product owner before Phase 4 sizing | V4 sizing, Phase 5 |
| RPO for saved edits | 0 confirmed edits lost | ASSUMPTION: users treat "Saved" as a promise; product owner to confirm | V3 |
| RTO | Collaboration server back in < 1 min (clients keep editing locally meanwhile); full database restore < 1 h | ASSUMPTION: starting values to confirm | V3 |
| Availability / SLO | — | UNKNOWN: needs the uptime the business will commit to, from the product owner, before Phase 5 opens to everyone | V7 |
| Storage | Bytes stored per document ≤ 3× its latest snapshot, after compaction | ASSUMPTION: keeps the edit log from growing without limit | Phase 2 exit |
| Operational complexity | 2 deployable services + Postgres (Redis only after V4); one on-call rotation | ASSUMPTION: one team of 4–8 people | Phase 4 exit |

**Missing inputs.** The phase order rests on four assumptions:
- **We run it as a hosted service in the browser.** If it ships for customers to install themselves, Phase 0 becomes an installable release, and upgrade and version-compatibility gates move up.
- **It is a rich-text editor.** If it is plain text or code, V2 shrinks a lot.
- **Offline-first editing is not required.** If it is, browser-side storage and long-offline merge tests move into Phase 1 and V1, and content stored on devices joins V6.
- **No regulated content (health, payments).** If there is, those obligations become dependencies that block real content in Phase 2.

Numbers still needed: the scale forecast, the SLO, any data-residency requirement, and team size.

## 3. Key decisions (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| How concurrent edits merge (consistency vs availability) | R3: the saved format and sync protocol depend on it; once real documents exist, switching means converting every document | Merge-by-design shared data type (CRDT: Yjs + y-prosemirror). Every client edits locally and all copies converge. The server relays and saves edits but does not decide between them | Yjs converges for this schema and is fast enough at the target document size | V1 | V1 fails, or the product needs the server to reject individual edits → server-ordered edits instead (OT: ShareDB + prosemirror-collab) |
| When "Saved" is shown | R3: a lost confirmed edit cannot be undone | The server writes the edit to the Postgres edit log before confirming it. Peers receive the edit right away. The client keeps and resends anything not yet confirmed | One commit per edit batch fits the remote-delay budget | V3 (no loss), V4 (delay) | Confirmation delay p95 over budget → batch commits in 50 ms windows. Never confirm before the write |
| Document schema and saved format | R3: every stored document is in this shape | Minimal ProseMirror schema v1 (paragraphs, headings, lists, bold/italic/link). Every snapshot is stamped with its schema and format version. Storage is an append-only edit log plus snapshots | New schema versions can roll out while older app versions are still open | V2, V3 | V2 fails → a schema change forces old app versions to reload before they can connect |
| IDs and tenancy | R3: IDs and isolation are permanent once real data exists | Time-ordered unique IDs (UUIDv7). Every row carries a workspace ID from day one (the seam that keeps a later split possible). One shared database. IDs are not secrets; access control is the protection | Shared-database isolation is enough for early customers | V5 (cross-workspace cases) | A contract requires dedicated isolation → per-tenant database or deployment |
| Access-control model (trust boundary) | R3: it shapes the database schema and the protocol, and a mistake exposes documents | Per-document permissions (owner/editor/commenter/viewer) plus workspace membership. Link sharing off by default. Checked on the server when a connection opens **and on every edit** (viewers' edits rejected). Revoking access disconnects live sessions | Per-document permissions cover the first customers | V5 | V5 fails, or customers need folder-level permission inheritance → permissions inherited down a folder tree |
| Data-privacy boundary | R3: content that leaks or sits in the wrong region cannot be pulled back | Content stays in one region, encrypted at rest, and never appears in logs or telemetry. Few outside vendors. Deleted content is purged within 30 days, backups included (ASSUMPTION). The server can read content | No residency requirement and no demand for end-to-end encryption at launch | V6 | Legal or a customer requires a specific region → per-region deployments. End-to-end encryption required → re-plan, because server-side features break |
| Monolith vs services | R2: splitting an internal service boundary takes weeks | One codebase, two deployables (HTTP API and WebSocket collaboration server), one Postgres | One team | Phase 4 exit review | Collaboration server deploys disrupt the API, or the two need to scale separately |
| Sync vs async | R2 | Saving before confirmation is synchronous. Peer broadcast is immediate. Derived data (search, thumbnails) is updated asynchronously through an outbox table | — | V3, V4 | Confirmation delay over budget (see the "Saved" row) |
| Running on more than one collaboration server | R2: changes routing, no data migration | One server plus a hot standby until V4. Then several servers sharing edits through Redis (Hocuspocus Redis extension) | Redis adds little delay | V4 | V4 shows Redis over the delay budget → route each document to one server by its ID |
| Build vs buy | R2: the format stays Yjs, so a later move is possible. A hosted collaboration vendor would make it R3 because our documents would live there | Buy login (managed OIDC). Use open-source Yjs/Tiptap/Hocuspocus and run it ourselves. Do not build our own merge engine, and do not use a hosted collaboration vendor | The team can run a WebSocket service around the clock | Phase 4 exit review of on-call load | On-call load exceeds team capacity → a hosted Yjs-compatible backend, with a tested export first |
| Offline editing | R2: storing content on devices adds client-side data and privacy work | Survive short disconnects only (unsent edits buffered in memory, resync on reconnect) | Not required at launch | Missing input (§1) | Product requires offline → pull in browser storage (y-indexeddb) and extend V1 and V6 |

**minor defaults:** React + Tiptap (on top of the ProseMirror schema) for the UI; GitHub Actions for CI; Terraform for infrastructure; managed Postgres (RDS or Cloud SQL); OpenTelemetry → Grafana for monitoring; a feature-flag service behind the OpenFeature API; Playwright for end-to-end tests.
**N/A:** Fine-tuning vs retrieval and hosted vs self-hosted model: no AI component. Migration, coexistence and cutover: greenfield. Payments: no money flows.

## 4. First end-to-end slice (Phase 0)
- **Request:** An allow-listed staff member signs in, creates a document, and types "hello". A second browser session sees it. Reloading shows it was saved.
- **Tiers it crosses:** Browser (React + Tiptap + Yjs) → static hosting/CDN → HTTP API (login check via OIDC, document created in Postgres, short-lived signed token for the collaboration connection) → Hocuspocus WebSocket server (checks the token: owner-only for now) → edit appended to the Postgres edit log → confirmation to the author and broadcast to the other session.
- **Deployed:** CI builds container images, referenced by exact digest, and Terraform applies to the production account.
- **Logged:** Structured logs and one OpenTelemetry trace from the browser through the API, the collaboration server and the database. Logs record document IDs, sizes and timings, never content.
- **Monitored:** Dashboards for open connections, save delay, errors and remote edit delay. An alert fires on save failures. A synthetic check every 5 minutes opens a test document in two clients, types, and confirms the edit arrives.
- **Rolled back:** Redeploy the previous image through the pipeline. Database migrations only add, never remove. Clients reconnect with backoff.
- **Who can reach it:** Only staff in a login-provider group, behind a feature flag. Documents are **disposable test data**: a banner says so, and wiping is allowed until V3 passes, because the saved format is not yet validated.
- **Exit check (V0):** One traced request succeeds across every tier. A deploy and a rollback both succeed through the pipeline. Killing the database connection fires the save-failure alert. The first values for remote delay, save delay and document open time are recorded as baselines.

## 5. Phases

- **Phase 1: Convergence, document model, identity**
  - **Unlocks:** Committing to the saved format and the schema-evolution path.
  - **Depends on:** Phase 0, V0.
  - **Tasks:**
    1. Run the V1 test harness and benchmark.
    2. Settle the IDs and workspace-ID columns.
    3. Write the permission tables and the connection-time check as a decided contract (owner/editor only for now).
    4. Freeze schema v1 and its version stamp.
    5. Set limits on edit message size and rate per connection.
    6. Add a client-version check at connect.
    7. Run V2.
    8. Book the external security test vendor.
  - **Rollback:** Data is still disposable. Revert and wipe.
  - **Exit check:** V1 and V2 pass. The drift detector (below) is live in the skeleton.

- **Phase 2: Durability and sync protocol**
  - **Unlocks:** Staff use the editor for real content (internal use is the first exposure, the smallest group).
  - **Depends on:** V1, V2.
  - **Tasks:**
    1. Save before confirming, and have clients resend unconfirmed edits.
    2. On reconnect, sync only what each side is missing (Yjs state vectors).
    3. Turn on point-in-time recovery and encrypted backups.
    4. Script a restore drill.
    5. Compact the edit log into snapshots: decode each snapshot and compare it with a replay of the log before deleting log entries, then keep the log for 30 more days.
    6. Run V3.
  - **Point of no return:** Ending the wipe policy, and the first deletion of compacted log entries. Both are guarded by V3.
  - **Exit check:** V3 passes. The storage-per-document ratio stays within budget on documents in internal use.

- **Phase 3: Access control, sharing, privacy**
  - **Unlocks:** Being ready for outside users.
  - **Depends on:** Phase 2. The privacy review and vendor agreements started in Phase 0.
  - **Tasks:**
    1. Full roles, checked on every edit.
    2. Workspace membership.
    3. Revocation that disconnects live sessions.
    4. Link sharing (off by default).
    5. Audit log of permission changes.
    6. Sanitize pasted HTML (the schema strips unknown markup; block `javascript:` links); strict content-security policy.
    7. Run V5 (automated test matrix, then the external test) and V6.
  - **Rollback:** Feature flags per capability. A permission-schema change is reversed with the add-then-remove migration pattern.
  - **Exit check:** V5 and V6 pass.

- **Phase 4: Collaboration-server scale and editor features**
  - **Unlocks:** Beta limits and sizing; editor features.
  - **Depends on:** V2 (for features), V3, and the scale forecast (for sizing).
  - **Tasks:**
    1. Run V4.
    2. Add Redis multi-server sharing, or route each document to one server if V4 calls for it.
    3. Drain connections smoothly on deploy.
    4. Cap editors per document and slow down senders who flood it.
    5. Then the lower-risk features, each one schema-evolved through the V2 suite:
       - live cursors and presence (temporary, never saved)
       - tables
       - images: upload through pre-signed links, check file type and size, serve from a separate sandboxed domain
       - version-history view built from the snapshots
  - **Rollback:** Every feature behind a flag. Multi-server mode can fall back to a single server.
  - **Exit check:** V4 passes. The on-call load review is done. Hosting cost per 1,000 connections is recorded.

- **Phase 5: Outside exposure, smallest first**
  - **Unlocks:** Opening to everyone (general availability).
  - **Depends on:** V5, V6, V4. The SLO input and a staffed on-call rotation.
  - **Tasks:**
    1. One allow-listed outside workspace, capped at the V4 editor limit.
    2. Widen to 5, then 25 workspaces, then open signup. Each step waits for 7 days of SLO data with no lost-edit or drift alerts.
    3. Run V7.
  - **Rollback:** Turn off the cohort flag. Existing documents stay readable and exportable.
  - **Exit check:** V7 passes.

## 10. Deferred
- **Offline-first editing (browser storage):** pull forward if product requires it, or if telemetry shows many sessions offline for more than 5 minutes. It then extends V1 and V6.
- **Comments and suggestion mode:** pull forward when product prioritizes it. Each goes through the V2 suite.
- **Full-text search (fed from the outbox):** pull forward when workspaces reach more documents than browsing can handle, by product signal.
- **Import and export (.docx, PDF):** pull forward on customer demand. An open-format export (JSON/Markdown) comes first if the build-vs-buy decision flips.
- **End-to-end encryption:** pull forward on enterprise demand. That means re-planning from Step 1, since server-side features break.
- **Per-region or per-tenant deployments:** pull forward when a residency or isolation contract arrives (see the privacy and tenancy rows).
- **Multi-region active-active:** pull forward when the SLO from V7 or the RTO cannot be met from one region.
- **Native mobile apps:** pull forward when mobile web usage justifies them. They require the minimum-version rules from V2.
- **AI writing features:** pull forward when product prioritizes them. Re-plan the AI layer then, with guardrails and cost limits first.
