# BUILD PLAN: Multi-tenant SaaS billing platform

**Main assumption (it changes the phase order).** I read the request as: the billing platform is the product. Tenant businesses use it to bill their own end customers. That covers plans, subscriptions, usage metering, invoicing, tax and collection. Each tenant is the merchant of record and charges through its **own** payment provider account, so we never hold funds.

**If it's actually internal billing for one SaaS product of yours:** build vs buy flips to buy (Stripe Billing or Chargebee). The plan then shrinks to integration, entitlements and reconciliation. Phases 2, 5 and 6 mostly go away.

**If you want to be the merchant of record (like Paddle):** re-plan from Step 1. That mode needs licensing, carries tax liability, and changes how money flows.

---

## 1. Classification and constraints
- **What:** A multi-tenant billing platform. It covers the product catalog, subscriptions, usage metering, invoicing, tax, payment collection through each tenant's payment provider, dunning, a ledger and reporting. It is exposed to tenants through a public API, a dashboard and an end-customer portal.
- **Type:** Software, greenfield. Not a small build: it moves money, serves outside users and holds personal data.
- **Dominant constraint:** Correctness of money. Tenant isolation is a close second.
- **Worst failure:** An end customer is charged the wrong amount, or charged twice, and nobody notices until they complain. Close behind: one tenant's customer or invoice data is visible to another tenant. The first is guarded by V1 and V7, the second by V2.

## 4. Walking skeleton (Phase 0)
- **Real request:** An internal "house" tenant calls the API to create a customer, a flat $10/month price and a subscription, then triggers an invoice. The invoice is finalized with ledger entries and a gapless number. The outbox enqueues a payment attempt. The worker charges a test card in **Stripe test mode**, through a connected test account. The signed Stripe webhook arrives, the payment is recorded, and the ledger balances. `GET /invoices/{id}` returns `status=paid`.
- **Tiers:** ALB/WAF + TLS → API-key authentication (hashed, mode-scoped) → core monolith (stub catalog, subscription, invoice, ledger and payment modules) → RDS Postgres (RLS on from the first migration) → outbox → SQS → payment worker → Stripe test mode → webhook receiver (signature verified) → Postgres.
- **Deploy, log, monitor, roll back:** Terraform for the infrastructure. GitHub Actions builds a signed image and deploys blue/green to ECS. Migrations are expand-only. Structured JSON logs carry `tenant_id`, `request_id` and `trace_id`, never personal data or tokens. Logs are classified as tenant-confidential and access is restricted. One OpenTelemetry trace spans API → queue → worker → webhook. Alerts fire on 5xx rate, outbox lag, webhook signature failures and a ledger-balance check that runs hourly. Rollback means flipping back to the previous blue/green target.
- **Who can reach it:** Only the house tenant, from allow-listed IPs, behind a `platform_enabled` flag. There is no live-mode Stripe key, so no real money moves (no live key exists until V7).

**Exit check (V0):** The request above succeeds with one trace across every tier. One deploy and one rollback both succeed through the pipeline. Killing the worker mid-payment fires the outbox-lag alert. Baselines are recorded at near-zero load: API p99, finalize-to-paid latency and outbox lag.

## 5. Phases

- **Phase 1 — Data foundation: tenancy, money, ledger, identifiers** (widest rework first)
  - Unlocks: specifying everything else that is tenant-scoped or touches money.
  - Depends on: V0.
  - Tasks:
    1. Tenant directory with `home_cell` and `mode`.
    2. RLS policies, plus a CI lint that fails any table without `tenant_id`, `mode` and RLS.
    3. Money type and the documented rounding rules.
    4. Double-entry ledger with an immutability trigger.
    5. Invoice state machine (draft → open → paid/void/uncollectible) and credit notes.
    6. Per-tenant gapless numbering.
    7. Prefixed ID scheme, idempotency-key store and append-only audit log.
    8. Per-tenant KMS data keys for personal-data columns.
    9. Start V5 and V4 paperwork (lead time).
  - Rollback: before any real data, the schema is dropped and recreated freely. After the Phase 1 exit, changes are expand/contract only.
  - Exit check: V1 and V2 pass; module boundary lint is green.

- **Phase 2 — Auth model and public API contract**
  - Unlocks: tenant integrations and the dashboard.
  - Depends on: Phase 1, V2.
  - Tasks:
    1. Dashboard users on OIDC SSO with tenant-scoped role-based access (owner, admin, finance, read-only).
    2. Secret and restricted API keys per mode, with rotation.
    3. API v1 surface (OpenAPI spec first) with date-based versioning and required idempotency.
    4. Outbound tenant webhooks: signed, with exponential-backoff retries, a dead-letter queue and a replay endpoint.
    5. Per-tenant rate limits.
    6. SDK generation and contract tests.
  - Rollback: per-route feature flags; the API is unfrozen until V6.
  - Exit check: V2 re-run in CI covers every new route; V6 review has started with 2 design partners.

- **Phase 3 — Catalog, subscriptions, billing engine, metering**
  - Unlocks: correct draft invoices for every launch pricing model.
  - Depends on: V1, V2; the ingest-volume input (before V3 can pass).
  - Tasks:
    1. Products and prices (flat, seat, tiered, usage).
    2. Subscription lifecycle with upgrades, downgrades and proration.
    3. Billing-calendar scheduler and invoice-run workers, partitioned by tenant.
    4. Ingest service: `POST /usage` → durable log → dedupe → hourly aggregates in partitioned Postgres tables.
    5. Usage invoice lines that link to their aggregates.
    6. Add golden proration cases to V1.
  - Rollback: invoice runs are idempotent per (subscription, period); drafts can be discarded; each pricing feature is flagged.
  - Exit check: V3 passes; V1 golden suite still green; deployables still within the complexity budget.

- **Phase 4 — Tax and legal invoice documents**
  - Unlocks: invoices that are lawful to send to real end customers.
  - Depends on: Phase 3; tax-vendor contract; launch jurisdictions and retention (inputs); V8.
  - Tasks:
    1. `TaxProvider` integration, with each calculation snapshotted on its invoice line.
    2. Tax-ID capture and validation (VIES for EU).
    3. Jurisdiction-specific invoice fields and PDFs.
    4. Credit-note documents.
    5. Retention policy enforcement.
    6. Data-subject requests: export, plus erasure by crypto-shredding.
  - Rollback: per-jurisdiction flag; disabling tax holds finalization rather than issuing untaxed invoices.
  - Exit check: V8 passes.

- **Phase 5 — Payments and collections**
  - Unlocks: real money, house tenant first.
  - Depends on: V5 (before design), V4 and Stripe live platform approval (before live mode), Phase 4.
  - Tasks:
    1. Connect Standard OAuth onboarding for tenants.
    2. Hosted payment fields and Stripe-hosted payment-method updates.
    3. Payment attempts with an idempotency key derived from (invoice, attempt number), and a state machine that tolerates "charge status unknown".
    4. Webhook ingestion with dedupe and out-of-order handling.
    5. Dunning schedules, refunds and disputes.
    6. Daily reconciliation of the ledger against Stripe balance transactions, alerting on any difference.
    7. Live-mode canary on the house tenant only.
  - Rollback: kill switch for live mode per tenant; held payment attempts resume idempotently. **Point of no return:** a real charge, guarded by V7.
  - Exit check: V4 and V7 pass.

- **Phase 6 — Tenant surfaces and private beta**
  - Unlocks: external tenants, smallest exposure first.
  - Depends on: V2, V6, V7, V8, V10, V11; SLA input; signed design-partner agreements.
  - Tasks:
    1. Tenant dashboard.
    2. Hosted invoice page and end-customer portal.
    3. CSV/Parquet exports and ledger-based revenue reports.
    4. SLOs and burn-rate alerts set from the SLA.
    5. Freeze API v1.
    6. Onboard 1 design-partner tenant in live mode, then 5, then the waitlist. Widen only after 14 days of zero-difference reconciliation and no Sev-1 at each step.
  - Rollback: per-tenant live-mode kill switch; a tenant can fall back to manual invoicing from its exports.
  - Exit check: V10 and V11 pass before the first external tenant; load test meets the latency budgets at 2× beta load.

- **Phase 7 — GA and scale**
  - Unlocks: general availability and price commitments.
  - Depends on: Phase 6 widening complete; V9.
  - Tasks:
    1. Noisy-neighbor controls: per-tenant invoice-run quotas, and moving a large tenant to its own cell.
    2. Tenant data export in open formats.
    3. Collect SOC 2 control evidence (controls have run since Phase 0).
    4. DR drill repeated quarterly.
  - Rollback: GA is a flag on onboarding; cell moves are reversible through the directory.
  - Exit check: V9 passes; one DR drill done in this phase.

## 9. Methodology exceptions
None. Phase 0 uses Stripe test mode because a live charge before V7 would put real money at risk. That is how the skeleton handles a tier it can't yet run for real, not an exception.

## 10. Deliberately deferred
- **Merchant-of-record mode:** pulled forward if the product chooses it (full re-plan from Step 1).
- **Second region or residency cells** (the `home_cell` seam exists from Phase 1): pulled forward when a signed tenant requires another region.
- **Dedicated silo per tenant:** pulled forward when a contract requires it or noisy-neighbor limits are breached.
- **Revenue-recognition engine (ASC 606 / IFRS 15):** pulled forward if launch tenants require it (missing input 5).
- **E-invoicing networks (Peppol, Italy's SDI, India's GST e-invoicing):** pulled forward when a launch jurisdiction mandates it.
- **Payment providers beyond Stripe (Adyen etc.):** pulled forward when a signed tenant requires one, or for regional coverage.
- **Columnar usage store:** pulled forward if V3 fails or volume reaches 50% of V3's tested peak.
- **SOC 2 Type II audit** (controls run from Phase 0): pulled forward when the first enterprise deal requires it.
- **Quotes/CPQ, marketplace billing and smart dunning:** pulled forward on design-partner demand after GA.

**To finish the plan, I need from you:** the product interpretation, launch jurisdictions, usage volume and the SLA. Several thresholds (V3, V8, V9 and the availability target) are marked UNKNOWN and can't be met until those inputs arrive.
