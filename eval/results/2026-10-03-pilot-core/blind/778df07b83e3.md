# How to sequence a CI/CD platform for 50 microservices

I'm assuming a typical setup: containerized services, Kubernetes or similar, a small platform team (3–5 engineers), and services owned by several product teams. Tell me your actual stack and I can make this more specific.

## The rule behind the order
Get one service all the way from commit to production first. Turn that into a reusable template. Then move the other services over in waves. Don't build every feature before anyone uses it, and don't let each of the 50 services end up with its own custom pipeline.

---

## Phase 0: Discovery and baseline (1–2 weeks)
- **List all 50 services:** language, build tool, how and where each deploys, owner, current pipeline, database or stateful dependencies, how often it ships.
- **Group them into archetypes,** for example: "Java + Postgres", "Node stateless", "Python worker", "the weird ones". Most groups will turn out to be about 4–6 archetypes.
- **Record today's numbers:** deploy frequency, lead time, change failure rate and time to recover (the four DORA metrics). You'll need these later to show the platform helped.
- **Pick 3 pilot services:** one simple, one typical, and one hard (database migrations, many dependencies).
- **Make the core decisions:** which CI engine, push-based deploys or GitOps (e.g. Argo CD), artifact registry, environment layout (dev, staging, prod), and branching model (trunk-based is strongly recommended).

**Done when:** archetypes are mapped, pilots are chosen, and the tooling decisions are written down.

## Phase 1: Foundations (2–4 weeks)
These are what everything else depends on, so they come first:
- The platform's own infrastructure defined as code, so it can be rebuilt
- Ephemeral CI runners that scale automatically
- Artifact and container registry, with retention policies
- Secrets management (Vault or a cloud secrets manager) and passwordless OIDC login from CI to the cloud
- Target environments created and isolated
- A basic deploy registry and audit log (which version is running where)

**Done when:** a "hello world" container can build, push and deploy to dev without anyone touching it.

## Phase 2: Walking skeleton (2–3 weeks)
Take the **simple pilot** all the way through:
- Build → unit tests → image → push → deploy to dev → promote to staging → manual approval → prod
- Rollback works and has been tested on purpose
- Deploys show up as events in your observability tool

**Done when:** the pilot ships to production through the new path, and rolling it back takes minutes.

## Phase 3: Golden path templates (3–4 weeks)
- Pull the pipeline out into **versioned shared libraries or templates**, one per archetype
- Create base Helm or Kustomize charts with sensible defaults (probes, resource limits, autoscaling)
- Move the **typical and hard pilots** onto the templates. The hard pilot will expose what's missing, such as database migration steps and config handling.
- Write a service scaffold or onboarding command plus documentation

**Done when:** all 3 pilots run on shared templates with no copy-pasted pipeline code, and a new service can be onboarded in under a day.

## Phase 4: Quality and security gates (in parallel with Phase 5)
- Code scanning, dependency scanning, image scanning, and a software bill of materials (SBOM)
- Image signing (cosign) and admission policies in the cluster (Kyverno or OPA)
- Contract tests between services, plus integration tests in short-lived preview environments

**Order:** turn every gate on in **warn-only mode first**, let teams fix findings during the migration waves, then enforce. Blocking deploys on day one causes revolt.

## Phase 5: Migration waves (8–14 weeks)
| Wave | Services | Which ones |
|---|---|---|
| 1 | ~5 | Willing teams, common archetypes, low risk |
| 2 | ~10 | The rest of the main archetypes |
| 3 | ~15 | Business-critical or core services, now that the templates are proven |
| 4 | ~17 | The long tail: oddballs, legacy, low-change services |

- **Within each wave:** go archetype by archetype, so fixes to a template help everyone at once.
- **Track progress** with a scorecard per service: on the platform, gates passing, rollback tested, old pipeline removed.
- **Switching over:** run old and new pipelines side by side for about a week per service, then delete the old one. Old pipelines left running quietly become permanent.

## Phase 6: Progressive delivery (after Wave 2)
- Canary or blue-green releases (Argo Rollouts or Flagger), with automatic rollback driven by SLO metrics
- Feature flag integration so deploying code and releasing features are separate steps
- DORA dashboards per team

This comes late on purpose. Canary analysis needs metrics you can trust and a standardized deploy path, and neither exists until the earlier phases are done.

## Phase 7: Run and optimize (ongoing)
- Build caching, test sharding, quarantining flaky tests
- SLOs for the platform itself (pipeline success rate, queue time, p95 build time)
- Cost controls on runners and preview environments
- A deprecation policy for template versions

---

## Critical path
```
Discovery → Foundations → Walking skeleton → Templates → Waves 1–4
                                                 ↘ Gates (warn → enforce)
                                                 ↘ Progressive delivery (after Wave 2)
```

**Rough timeline:** 6–9 months to have all 50 services on the platform.

## Common ways this goes wrong
1. **Building the platform with nobody using it.** Get a real service to production by around week 6.
2. **Too many options.** Every template parameter you add is something you'll have to maintain. Push hard against customization for each service.
3. **Database migrations left for later.** That's why one pilot is the hard case: it surfaces these problems early.
4. **No owners on the product teams.** Each wave needs a named contact on every team being migrated.
5. **Enforcing gates before the backlog is fixed.** Warn first, enforce second.

To make this concrete, it would help to know: what are you running on now (Kubernetes? which cloud?), how many CI systems are in use today, and how big is the platform team? Those answers change which tools to pick and how big the waves should be.
