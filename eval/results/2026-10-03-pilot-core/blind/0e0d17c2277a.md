# Plan: `photo-rename`, a CLI that renames photos by their EXIF capture date

## 1. Classification and constraints
- **What:** A local command-line tool. You point it at a folder of photos and it renames each photo (plus its sidecar files) to a pattern built from its EXIF capture date. It shows the plan before applying it, and every applied run can be undone.
- **Type:** Software only, with no AI component. Greenfield. Small build: one developer, no outside service, no money, no regulated data. The photos are personal data, though, because EXIF holds GPS position and timestamps.
- **Dominant constraint:** Correctness. No photo may be lost, overwritten or given the wrong date.
- **Worst failure:** A filename collision makes one photo silently overwrite another. On POSIX, `os.rename` replaces an existing target, so this can happen. The photo is gone for good. The case-insensitive filesystems used on Windows and macOS make collisions more likely, and so do burst shots taken in the same second.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Data safety | 0 files lost or overwritten. File count and SHA-256 content hashes are identical before and after apply and undo | ASSUMPTION (implied by "rename"; confirm with requester) | V2, V3 |
| Date accuracy | 100% agreement with an `exiftool -DateTimeOriginal` oracle on files that have a date. Files without a date are skipped, never given a wrong date | ASSUMPTION (any wrong date breaks the tool's purpose) | V1 |
| Throughput | ≥ 100 files/s on a local SSD | ASSUMPTION (only headers are read, about 64 KB per file). Baseline measured at V0 | Phase 2 exit |
| Resource use | ≤ 200 MB RSS for a 50k-file folder | ASSUMPTION (each plan entry is under 1 KB) | Phase 2 exit |
| Operational complexity | No services. Python plus one metadata library | ASSUMPTION | Phase 0 |

**Missing inputs** (most important first):
1. **One-off or repeated use?** If this is a one-time cleanup, ExifTool's built-in `exiftool '-FileName<DateTimeOriginal' -d %Y-%m-%d_%H-%M-%S%%-c.%%e DIR` already does the job, and nothing needs building. *Assumed: repeated use, where dry-run, undo and sidecar pairing are worth having.* If that's wrong, stop here and use ExifTool.
2. **Formats.** *Assumed:* JPEG, HEIC and common RAW (CR2, CR3, NEF, ARW, DNG). Video is out. If video is in scope, the reader choice changes (see V1).
3. **Platforms and filesystems.** *Assumed:* Windows, macOS and Linux, including SD cards formatted exFAT. This sets the V2 test matrix.
4. **In place or copy to a new folder.** *Assumed:* in place. The phase order is the same either way. Copy mode would only make V2 easier.
5. **Real sample photos** from the requester's cameras and phones. V1 needs them (§2).

## 3. Key decisions

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Plan unit and journal contract | R2: planner, journal and undo all build on it, and changing it breaks old journals | The unit is a **file group** sharing one stem: photo, `.xmp`, `.aae`, RAW+JPEG pair, Live Photo `.MOV`. The journal is JSONL with `schema_version` and, per group, the original path, new path and SHA-256 | Real folders contain sidecars that must stay paired | Cheap check, Phase 1: the corpus includes each sidecar type and every group pairs correctly | Real files share a stem but are different shots: switch to a per-file unit with explicit sidecar matching |
| Collision policy and rename primitive | R3: one overwrite destroys a photo for good, even if it's noticed seconds later | Never overwrite. Collisions get deterministic `_1`, `_2` suffixes, ordered by `SubSecTimeOriginal` and then by original name. Renames use each OS's no-replace call: `renameat2(RENAME_NOREPLACE)` on Linux, `renamex_np(RENAME_EXCL)` on macOS, `MoveFileExW` without `REPLACE_EXISTING` on Windows. Collisions are compared case-folded | These calls hold on ext4, APFS, NTFS and exFAT | V2 | V2 fails on any filesystem: use copy mode there (write renamed copies to a new folder and leave originals untouched) |
| Privacy boundary (EXIF GPS, file paths) | R3: leaked location data can't be recalled | Fully offline: no network code, no telemetry, no update check. Logs stay on the machine and record only paths, the capture date and reason codes, never GPS or other EXIF fields | Nothing needs the network | Cited basis: no dependency can open a network connection, enforced by CI tests that block sockets (`pytest-socket`) | Someone proposes a network feature (crash reports, updates): it must be opt-in and get its own review |

**minor defaults:**
- **Build vs buy:** build a thin tool, but keep ExifTool as the test oracle. Building is worth it only for dry-run, undo, sidecar groups and the no-overwrite guarantee. See Missing inputs 1.
- **Language:** Python 3.12, using `uv` for locked dependencies.
- **Reader:** `ExifRead` behind a `DateSource` interface. If V1 fails, switch to an `exiftool -json` subprocess.
- **Date source:** `DateTimeOriginal`, with `SubSecTimeOriginal` used only to order photos taken in the same second. Local time is used as recorded, with no timezone conversion.
- **Missing date:** skip the file and report why. There's no fallback to file modification time by default.
- **Name pattern:** `YYYY-MM-DD_HH-MM-SS[_n].<original ext>`. `--format` accepts strftime patterns but rejects characters Windows doesn't allow.
- **Execution:** sequential, one process.
- **Distribution:** PyPI wheel, installed with `pipx`.

**N/A:**
- Consistency vs availability: one local process. Safety after a crash is handled by the journal in Phase 2.
- Monolith vs services: a single CLI.
- Brownfield and AI rows: neither applies.

## 4. First end-to-end slice (Phase 0)
- **Real request:** `photo-rename plan ~/Pictures/some-real-folder`. It reads EXIF from real photos, prints each proposed `old → new` name, writes `plan.jsonl`, and exits with a non-zero code if any file failed.
- **Tiers:** argument parsing → folder walk → EXIF reader → name planner (with simple collision suffixes) → plan writer and summary. The rename step runs **dry-run only**, printing "would rename". Nothing gets renamed until V2 passes.
- **Deployed:** GitHub Actions builds the wheel from a tag and publishes a pre-release to TestPyPI with trusted publishing. CI then installs it with `pipx` on Windows, macOS and Linux runners and runs it on a synthetic fixture folder.
- **Logged:** Each run gets a run ID. JSONL logs go to the per-user state folder. The run ends with a summary (`planned / skipped:no_exif / errors`).
- **Monitored:** The person running it sees the exit code and the summary. A failed CI smoke run sends a GitHub notification.
- **Rolled back:** Yank the pre-release, then reinstall the previous version with `pipx install photo-rename==<prev>`.
- **Who can reach it:** Only the developer. It's a TestPyPI pre-release, unannounced, and it can't modify files.
- **Exit check:** V0.

## 5. Phases

**Phase 1: Plan contract and date correctness**
- **Unlocks:** A trustworthy dry-run plan, and a frozen journal schema for Phase 2 to build on.
- **Depends on:** Phase 0 / V0, plus the corpus (§2).
- **Tasks:**
  1. Freeze the journal and plan schema (§3 row 1).
  2. Build file grouping for every sidecar type.
  3. Make the plan deterministic: inputs sorted, ties broken by stable rules.
  4. Make it idempotent: a file already named correctly is skipped.
  5. Add reason codes per file: `no_exif`, `unparseable_date`, `zero_date` (`0000:00:00`), `collision_suffixed`.
  6. Fuzz the EXIF parsing with malformed files.
  7. Run V1 against the oracle.
- **Rollback:** Nothing on disk changes in this phase. Revert the commit or yank the pre-release.
- **Exit check:** V1 passes. The sidecar cheap check passes. Running `plan` twice on the same folder produces byte-identical output.

**Phase 2: Safe apply, undo, release**
- **Unlocks:** Real renames, then a public release.
- **Depends on:** Phase 1, V1.
- **Tasks:**
  1. Build the no-replace rename primitive for each OS.
  2. Write each journal entry and flush it to disk (`fsync`) *before* each rename, so an interrupted run can always be undone.
  3. Add `apply plan.jsonl`. It refuses to run if any file's size or modification time changed since the plan was made.
  4. Add a per-folder lock file so two runs can't overlap.
  5. Refuse to follow symlinks out of the target folder.
  6. Add `undo journal.jsonl`.
  7. Run V2 and V3.
  8. Widen exposure in steps, each only after the previous one passes:
     - synthetic fixtures
     - copies of the corpus on each filesystem image
     - the developer's own backed-up real folder
     - an `rc` release to named testers
     - stable release on PyPI
- **Rollback:**
  - For renames: `undo` with the journal.
  - For releases: yank the version.
  - **Point of no return:** published PyPI versions can be yanked but never deleted. The stable release is guarded by V3.
- **Exit check:**
  - V2 and V3 pass.
  - Throughput and memory budgets hold on a 10k-file corpus.
  - Testers report no undo failures during the `rc` period.

## 9. Exceptions
None. Phase 0 runs dry-run because it touches real data before V2 has passed. The method calls for that; it isn't an exception.

## 10. Deferred
- **Video files** (`CreateDate` in MP4/MOV): pull forward if the requester's folders contain video. This would likely bring the ExifTool backend forward too (V1 flip).
- **Timezone normalization** (`OffsetTimeOriginal`, GPS time): pull forward when users mix devices set to different timezones and the sort order comes out wrong.
- **Fallback to modification time or filename:** pull forward as an opt-in flag if the V1 corpus shows that more than 5% of files have no EXIF date (ASSUMPTION).
- **Recursive walk and date-folder layout** (`YYYY/MM/`): pull forward when requested. It adds a move step that has to be added to the V2 tests.
- **Camera clock correction** (`--shift +1h`): pull forward when a user reports a camera with its clock set wrong.
- **Parallel EXIF reading:** pull forward if the measured throughput misses the §1 budget on the requester's real folder sizes.
- **Standalone binary** (PyInstaller): pull forward when a target user can't install Python or pipx.
- **GUI:** pull forward when there's demand from people who don't use a command line.
