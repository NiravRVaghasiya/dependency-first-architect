# Plan: Real-Time Collaborative Document Editor

## 1. Classification
- **What:** A browser-based editor where many people edit the same rich-text document at once. It shows live cursors and presence, keeps working offline, and has version history, comments and sharing.
- **Type:** Software. There is no AI layer.
- **Dominant constraint:** **Correctness**, meaning every replica ends up with the same document. Latency comes second: a remote edit should be visible in under about 200 ms.
- **Worst failure:** **Silent divergence or a lost acknowledged edit.** Two users end up looking at different documents, or an edit the user saw as "saved" disappears. Nobody notices until the damage can't be undone, and users stop trusting the product.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| **Concurrency algorithm** (most irreversible: it fixes the stored data format) | **CRDT using Yjs.** Merges are commutative and idempotent, offline editing comes for free, and the library is mature. The server still relays, stores and authorizes. | Switch to OT (ShareDB-style, server-ordered) if CRDT tombstone or memory overhead goes over budget (for example, more than 50 MB in memory for a large doc after compaction), or if a customer needs strictly server-ordered edit semantics. |
| **Consistency vs availability** | **Split by data type.** Document content is AP with strong eventual consistency: local edits are always accepted and the CRDT converges. Metadata (ACLs, ownership, workspaces) is CP in Postgres. | Add server-sequenced linearizable ordering for specific docs if a legal or regulated workflow needs it (for example, contract locking). |
| **Ack semantics (sync vs async)** | **The server acks only after a durable write.** Each update is appended to the Postgres update log before the ack. Everything after that is async through a queue: fan-out, compaction, search indexing, notifications, export. | Use group commit (batch appends within a window of about 10–20 ms) if append p99 goes over 50 ms. Never ack before the write is durable. |
| **Doc-to-node routing** | **One process owns each doc**, assigned by consistent hash on doc ID. The doc lives in memory on one node, with no cross-node fan-out. | Add Redis or NATS pub/sub fan-out across nodes if one doc regularly has more than about 200 concurrent editors or saturates one node. |
| **Monolith vs services** | **Modular monolith: one repo, one codebase, two process types.** The `api` process is stateless HTTP. The `collab` process holds long-lived WebSockets. They are split because they scale differently, not for organizational reasons. | Extract a service (search, export, notifications) when separate teams own it or its scaling or failure profile hurts the collab process. |
| **Transport** | **WebSocket through the server**, which is needed for authz, durability and validation. | Use WebRTC peer-to-peer for presence only, if server egress cost for presence dominates. Edits always go through the server. |
| **Storage** | **Postgres for everything:** an append-only `doc_updates` log partitioned by doc, plus a `doc_snapshots` table. | Move snapshots to S3 when the snapshot table grows past about 500 GB or p99 snapshot size passes 5 MB. |
| **Document schema** (a data contract) | **A versioned ProseMirror/TipTap schema, add-only:** node and mark types are never removed or renamed. | None. This rule is permanent. Breaking changes go through an explicit migration plus client version gating. |
| **Authorization granularity** | **Per-document ACL** with roles owner, editor, commenter and viewer, enforced when the WebSocket connects and on every message. | Do a redesign if block-level permissions or suggestion mode becomes a hard requirement, because both change the schema and authz model. |
| **Build vs buy** | **Buy or adopt:** Yjs, y-protocols, TipTap/ProseMirror, an OIDC provider (WorkOS, Auth0 or similar), managed Postgres. **Build:** a thin collab server around y-protocols, so we own ack, persistence and authz semantics. | Use a fully hosted collab backend (Liveblocks, Tiptap Cloud) if time-to-market dominates and data-residency rules allow it. |
| **Region topology** | **Single region.** | Go multi-region if more than 20% of sessions have RTT over 150 ms to the primary region, or a data-residency contract is signed. |
| (AI) prompt+RAG vs fine-tune | N/A: there is no AI capability in scope. | N/A |
| (AI) hosted API vs self-host | N/A: there is no AI capability in scope. | N/A |

## 3. First end-to-end slice (Phase 0)
The skeleton deliberately starts very simple: **plain text in a `<textarea>` bound to a `Y.Text`**, with no rich text, cursors or styling. Rich text depends on proven sync, so it waits.

- **The one real request:** A logged-in user opens `/d/:docId` and types "hello". A second browser, signed in as a different user, sees "hello" appear. Reloading either tab rebuilds "hello" from Postgres.
- **Tiers crossed:**
  1. The browser SPA, served as static files from a CDN.
  2. The edge load balancer, which handles TLS and the WebSocket upgrade.
  3. The `api` process (OIDC login callback, `POST /docs`, short-lived JWT).
  4. The `collab` process (WebSocket; checks the JWT on upgrade; appends the update to `doc_updates`; acks; broadcasts to other sockets on the doc).
  5. Postgres.
- **Deploy:** A CI pipeline builds one container image. It deploys to staging, then the *same image* is promoted to prod. Terraform defines both environments, and DB migrations are versioned.
- **Logged:** Structured JSON logs containing only IDs (`doc_id`, `client_id`, `update_seq`), never document content.
- **Monitored:** The OpenTelemetry trace covers client send → collab receive → Postgres append → ack → broadcast. Metrics are active connections, append p99 and end-to-end ack RTT. There is one dashboard and one alert, on append error rate above 0.1%.

**Exit check:** In prod, two browsers converge on the same text, a reload restores it, and both the full trace and the ack-RTT metric are visible on the dashboard.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

**Phase 1: Convergence and durability (the correctness core)**
- Unlocks: Every later feature can trust that edits converge and are never lost.
- Depends on: The Phase 0 skeleton running in prod.
- Tasks:
  1. **Freeze the stored data format.** Define the `doc_updates` table (doc_id, seq, update bytes, client_id, schema_version, created_at) and the `doc_snapshots` table, with a format version byte. This is the widest-impact task because every document ever written depends on it.
  2. **Durable-before-ack protocol.** The client keeps unacked updates in IndexedDB and resends them on reconnect. Resending is safe because Yjs updates are idempotent.
  3. **Reconnect sync.** Run y-protocols sync steps 1 and 2 (state-vector diff) on every reconnect.
  4. **Per-doc ownership routing plus graceful drain.** On deploy, a node flushes its docs and hands them off before shutting down.
  5. **Async snapshot and compaction job.** Merge updates every N updates or M minutes. Never delete log entries until the snapshot is verified.
  6. **Convergence fuzz harness.** N simulated clients make random concurrent edits under partition, reordering and duplication. The test asserts that all replicas are identical *and* that a reload from Postgres matches them. It runs in CI.
- Exit check: 10k fuzz sessions with zero divergence. A `kill -9` on the collab node mid-edit loses zero acked updates. A client offline for 10 minutes merges cleanly.

**Phase 2: Identity, tenancy and access control**
- Unlocks: Real users and real content (internal dogfooding, then beta).
- Depends on: Phase 1. ACLs protect content, so content must already be durable.
- Tasks:
  1. **Workspace and ACL schema** in Postgres, with authz policy living in one module. This touches every request path.
  2. **Enforcement:** the JWT and role are checked when the WebSocket connects, *and on every message*. Viewers' update messages are rejected; their awareness messages are allowed.
  3. **Live revocation:** when an ACL changes, the server closes or downgrades active sockets within 5 seconds.
  4. Share links using scoped tokens that expire.
  5. Audit log of permission changes.
- Exit check: A CI test matrix covering every role and action passes. In prod, a revoked user's socket closes within 5 seconds.
- *Judgment call:* This phase comes before rich text because the authz model has the wider impact. Real data shouldn't enter the system before access control exists.

**Phase 3: Rich-text document model**
- Unlocks: A real editor experience.
- Depends on: Phase 1 sync and the fuzz harness. Rich text adds new ways for replicas to diverge, and the harness needs to catch them.
- Tasks:
  1. **A versioned schema package** shared by the client and a headless server-side validator. The server rejects updates that produce invalid structure. Unknown node types from newer clients are kept and shown as placeholders, never dropped.
  2. **y-prosemirror binding**, with the fuzz harness extended to rich-text operations such as concurrent split-and-format and list nesting.
  3. **Per-user undo** with `Y.UndoManager`, tracking local edits only.
  4. **Paste sanitization**, converting pasted HTML into the schema.
  5. Toolbar and keyboard shortcuts (the leaf work).
- Exit check: The rich-text fuzz run shows zero divergence. A schema v1→v2 migration passes against an anonymized copy of the snapshot corpus. A paste XSS test corpus is fully blocked.

**Phase 4: Presence and awareness**
- Unlocks: Live cursors, selections and a "who's here" list.
- Depends on: Phase 3. Cursors are Yjs relative positions inside the rich-text structure.
- Tasks:
  1. Awareness channel on the same socket. It is ephemeral (never persisted), throttled to about 50 ms, and capped in size.
  2. Remote cursors and selections via relative positions.
  3. Avatar list. Display names come from the server-verified identity.
  4. Typing indicators (the leaf work).
- Exit check: With 20 concurrent editors, p95 remote-cursor latency is under 150 ms, and no awareness data reaches `doc_updates`.

**Phase 5: Offline-first and version history**
- Unlocks: Long offline sessions and point-in-time restore.
- Depends on: Phase 1 (log and snapshots) and Phase 3 (schema versioning).
- Tasks:
  1. **History model.** Versions are snapshots derived from the log. A restore is applied as a *new forward update*; the log is never rewritten.
  2. **Offline client.** Use y-indexeddb plus a service worker for the app shell, and show online, offline and unsynced states in the UI.
  3. **Revoked-while-offline policy.** If a user lost access while offline, their rejected edits are saved as a private copy, never dropped silently.
  4. History diff view (the leaf work).
- Exit check: Two devices that each edit offline for 24 hours merge correctly. Restoring version N produces exactly snapshot N, and the restore itself can be undone.

**Phase 6: Comments, mentions and notifications**
- Unlocks: Async collaboration.
- Depends on: Phase 2 (the commenter role), Phase 3 and Phase 4 (relative-position anchoring).
- Tasks:
  1. **Comment anchor model.** Comments live in Postgres and anchor to text via Yjs relative positions. A comment whose text was deleted is marked "detached", never lost.
  2. Threads and resolve.
  3. Notifications through a transactional outbox, then a queue, then email or in-app delivery.
  4. Reactions (the leaf work).
- Exit check: Anchors survive the fuzz harness. Notifications are delivered exactly once from the user's point of view, even when a consumer crashes.

**Phase 7: Capacity, then secondary read paths**
- Unlocks: Growth, search and export.
- Depends on: A stable snapshot format (Phase 1) and the ACL model (Phase 2).
- Tasks:
  1. **Capacity model and SLOs:** ack p99 under 200 ms and 99.9% availability, with load tests on hot docs and large docs.
  2. **Search index** fed asynchronously from snapshot events, with ACL filtering at query time.
  3. Export to PDF and DOCX (the leaf work).
- Exit check: SLOs hold at 3× projected peak load, and the search index can be rebuilt from scratch out of snapshots alone.

## 6. AI layer
**N/A.** The system has no AI or agentic capability, so prompt-injection defense, model budgets, retrieval and the rest don't apply. If AI writing assistance is added later, it gets its own plan with the full AI layer (see Deferred).

## 7. Deferred
- **Multi-region active-active editing.** Pull forward when more than 20% of sessions have RTT over 150 ms, or a data-residency contract is signed.
- **Cross-node fan-out for hot docs (Redis or NATS).** Pull forward when one doc regularly has more than about 200 editors or saturates one node's CPU.
- **Tables, images and embeds.** Images need a blob upload pipeline, and tables are a known source of divergence in CRDTs. Pull forward once the rich-text fuzz run has been clean for 4 weeks and users ask for them.
- **Suggestion mode and block-level permissions.** These change both the schema and authz. Pull forward on a committed customer requirement, and schedule them through the schema-versioning gate.
- **End-to-end encryption.** It conflicts with server-side validation, search and export. Pull forward only for a regulated customer, and re-open the validation and search gates first.
- **Splitting into microservices.** Pull forward per the monolith-vs-services revisit trigger.
- **Snapshots in S3.** Pull forward per the storage revisit trigger.
- **Native mobile apps.** Pull forward once web offline (Phase 5) has been stable in prod for a quarter.
- **AI writing assistant.** Needs a separate plan. Pull forward when the product roadmap commits to it.
