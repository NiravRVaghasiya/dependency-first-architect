# BUILD PLAN: Customer-support RAG chatbot over help-center docs

Your request didn't say what the help-center platform is, whether the bot can see customer accounts, or whether every doc is public. This plan assumes: **anonymous customers, public published articles only, answers only, and a handoff to a human as the bot's single action.** §1 lists what changes if any of that is false. Please confirm those first.

## 1. Classification and constraints
- **What:** a chat widget on the help center. It answers customer questions only from published help-center articles, cites its sources, and hands off to a human agent when the docs don't cover the question.
- **Type:** AI (RAG) plus software. A new service that reads from the existing help center and writes to the existing ticketing system. **Not a small build:** outside users can reach it, and customers type personal data into chats.
- **Dominant constraint:** correctness (answers must match the docs).
- **Worst failure:** the bot confidently tells customers something the docs don't say, such as a refund, price, security or legal claim, and the company is held to it (cf. *Moffatt v. Air Canada*, 2024 BCCRT 149). If this happens at scale, nobody notices until the damage is done. V4 guards it, and V2 guards the version caused by injected instructions. The runner-up failure is customer personal data leaking through logs or the model provider, guarded by V5.

**Missing inputs, and the order changes they would force:**
1. **Account-aware answers or actions** (order status, refunds). If yes, you need authentication, per-user authorization and human approval on writes before Phase 2. That is a different plan.
2. **Permissioned docs** (internal, plan-tier or customer-specific). If yes, access must be enforced at retrieval time, and that becomes a risk gate inside V3.
3. **Platforms:** which help center and ticketing system (Zendesk, Intercom, Salesforce…). This decides the connector and whether the vendor's own bot is a real "buy" option.
4. **Languages, and EU or regulated users.** These add eval sets per language, data residency, a DPIA, and possibly AI-disclosure duties. Legal confirms which apply; the plan builds the disclosure regardless.
5. **Baselines from support ops:** ticket volume, cost per ticket, CSAT. V6 cannot pass without them.

**R1 defaults:**
- **Services:** monolith, meaning one chat service plus one ingestion job.
- **Sync vs async:** chat is synchronous and streamed; ingestion is asynchronous.
- **Consistency vs availability:** the index is eventually consistent within the freshness budget. If the LLM is down, the bot falls back to search results.
- **Prompt+RAG vs fine-tune:** prompt+RAG, because the docs change and citations are required. Fine-tuning is in §10.
- **Search store:** Postgres with pgvector plus full-text search, used as hybrid search.
- **Embedding model:** pinned to each index version. Swapping it means building a new index and switching an alias (blue/green); re-embedding takes minutes at this size.
- **Chunking:** by article heading.
- **Conversation state:** kept server-side, last 6 turns, 30-minute TTL.

**N/A:**
- **Migration, cutover and system of record:** nothing is replaced. The existing contact path stays as the permanent fallback.
- **Tenancy:** one public corpus.

## 4. Walking skeleton (Phase 0)
- **Request:** an employee on the allow-list asks "How do I reset my password?" in the widget on the production help center and gets a streamed answer that links to the password-reset article.
- **Tiers it crosses:**
  - The widget, behind a feature flag (e.g. LaunchDarkly or Unleash).
  - The chat service, with conversation state in memory.
  - Retrieval over a real index of the real public articles, built by the ingestion job: naive chunks, a pinned embedding model, `index_v1`.
  - The hosted LLM, through a thin model client. System instructions are kept separate, and user text and retrieved text go in delimited data blocks. Hard caps from §1 apply, plus a 20 s timeout.
  - The answer streams back to the widget, with citation links checked against the URLs that were actually retrieved.
- **Day-zero operations:**
  - **Deploy:** a container through the existing CI/CD pipeline, with infrastructure as code.
  - **Logging:** one OpenTelemetry trace from widget to LLM. Tokens and cost are recorded as a metric on every request. Logs are classified as customer personal data from day one, so they are redacted and access-controlled.
  - **Monitoring:** alerts on error rate and on spend.
  - **Rollback:** redeploy the previous image or turn the flag off; for the index, point the alias back to the previous version.
- **Who can reach it:** staff on the SSO allow-list only, using synthetic questions only (no real customer data). Customers see nothing.
- **Exit check V0:** a real request succeeds with one trace across every tier. A deploy and a rollback both succeed through the pipeline. An injected failure (provider key revoked) fires an alert, and the user gets the degraded "search results + contact us" reply. Starting values for latency, tokens/cost per turn and ingestion time are recorded, measured at near-zero load.

## 5. Phases

- **Phase 0 tasks (alongside §4):**
  - Get the cost-per-ticket, volume and CSAT baselines from support ops.
  - Agree with support ops on what "resolved" means. Proposed: no handoff, and no ticket from the same session or email within 72 h.
  - Start V5 legal and privacy review (it has lead time).
  - Start the V1 ticket sampling.

- **Phase 1: Defenses and budgets**
  - **Unlocks:** safe to add capability and, later, to expose customers.
  - **Depends on:** V0.
  - **Tasks:**
    1. Output renderer: only allow-listed help-center links, no images, no raw HTML. This closes the exfiltration path.
    2. Tool executor allow-list containing only `create_handoff`. It runs only after a user confirmation tied to that specific handoff, and is enforced in code, not by the model.
    3. Citation-required output guard, plus the refusal template.
    4. Input and output filters: jailbreak patterns, abuse, the topic deny-list from legal. PII redaction before anything reaches logs.
    5. Rate limits per session and per IP, the daily spend cap, and an auto kill switch.
    6. AI disclosure and disclaimer text, sent to legal.
    7. Injection suite in CI.
  - **Rollback:** guard config is versioned; revert it or turn the flag off.
  - **Exit check:** V2. A runaway loop gets cut off at the cap and emits a metric.

- **Phase 2: Retrieval and eval harness**
  - **Unlocks:** answer generation can be specified.
  - **Depends on:** Phase 1, V1.
  - **Tasks:**
    1. Ingestion allow-list: only articles that are public and published. Drafts and internal articles are excluded at the source.
    2. Metadata on every chunk: article ID, URL, locale, `updated_at`, product.
    3. Chunking by heading.
    4. Hybrid search (BM25 + vector), plus a reranker only if V3 needs one.
    5. Incremental sync (webhook or 5-minute poll) with deletes propagated, plus a nightly full rebuild into a new index version.
    6. Versioned eval set built from the V1 sample and search logs, including unanswerable questions.
    7. Eval runner in CI (e.g. promptfoo or an in-house harness).
    8. The build-vs-buy comparison from §3.
  - **Rollback:** switch the index alias back to the previous version.
  - **Exit check:** V3. A full re-index finishes within the RTO.

- **Phase 3: Model access, generation, memory, orchestration, handoff**
  - **Unlocks:** ready for the canary.
  - **Depends on:** V3. The handoff contract signed off.
  - **Tasks:**
    1. Provider abstraction with retries and backoff, a circuit breaker, a fallback model, and structured output (`answer`, `cited_chunk_ids`, `answerable`).
    2. Single-chain orchestration: rewrite the query using history, retrieve, generate or refuse, offer a handoff.
    3. Conversation state per §3 (R1 line). Nothing persists past the TTL.
    4. Integration with the ticketing sandbox, then production with internal test tickets.
    5. A "release bundle" ID (prompt + model + index + guard versions) on every trace.
    6. Load test against the latency budget.
  - **Rollback:** revert to the previous release bundle. Turning handoff off falls back to a static contact link.
  - **Exit check:** V4 passes on both the primary and fallback models. Support ops signs off on the handoffs.

- **Phase 4: Customer canary and widening**
  - **Unlocks:** production value; the scaling decision.
  - **Depends on:** V2, V4, V5; the throughput input.
  - **Tasks:** steps of 1% → 5% → 25% of help-center visitors, holding at least 3 days per step. At each step, check:
    - error rate and p95 latency;
    - a daily SME audit of 50 sampled conversations for unsupported claims;
    - thumbs-down rate, handoff rate and spend against the cap.

    Measure V6 at 5–25%, then go to 50% → 100%. Breaching the spend cap or the error SLO triggers automatic rollback to the previous step.
  - **Rollback:** turn the flag down. The old contact path is always live, so there is no point of no return. Sending customer data to the provider is the irreversible part, and V5 guards it.
  - **Exit check:** V6 passes before going past 25%. An unsupported claim in the audit stays at or below V4's rate.

- **Phase 5: Feedback loop**
  - **Unlocks:** continuous improvement without poisoning the system.
  - **Depends on:** Phase 4 at ≥ 25%; content owners named.
  - **Tasks:**
    1. Thumbs and comments go into an SME review queue.
    2. Accepted items become eval cases or doc-fix tickets for content owners. Raw feedback never changes prompts or the index directly.
    3. Weekly report clustering unanswered intents.
  - **Rollback:** the eval set and prompts are versioned; revert.
  - **Exit check:** each change merges only if the next eval run improves its target metric with no V4 regression.

## 10. Deliberately deferred
1. **Logged-in, account-aware answers and actions** (order status, refunds): needs authentication, per-user authorization and human approval on writes. Pull forward if V1 fails, or if account-specific intents are more than 40% of handoffs in Phase 4.
2. **Memory across sessions:** pull forward if repeat-contact analysis shows customers re-explaining. It needs its own privacy review.
3. **Routing to a cheaper model, or a semantic cache:** pull forward if V6 fails or passes only narrowly.
4. **Other languages:** pull forward when non-English sessions pass about 10% (ASSUMPTION) or a market requires it. Each language needs its own eval set and V3/V4 runs.
5. **Fine-tuning:** pull forward only if V4 still fails after retrieval and prompt fixes. Training on transcripts is R3 and would need a new privacy gate.
6. **More sources** (community forum, macros, internal knowledge base): pull forward when Phase 5 traces gaps to content that exists only there. Forum content is untrusted, so V2 has to be re-run with it planted.
7. **An agent-assist copilot for support staff** on the same retrieval: after Phase 4 reaches 100%.
8. **Other channels** (email, in-app, voice): after Phase 4 has held stable for 30 days.

The quickest way to tighten this plan is to answer the five missing inputs in §1. The two that would most change the order are #1 (account-aware answers) and #2 (permissioned docs).
