# BUILD PLAN: CI/CD platform for 50 microservices

## 1. Classification
- **What:** A shared CI/CD platform. Each of the 50 services gets this path: commit → build → test → signed artifact → promotion through environments → production rollout. Rollback is automated.
- **Type:** Infrastructure, with a thin software layer on top (pipeline templates, service manifest, onboarding tooling). **Not AI.**
- **Dominant constraint:** Deploy correctness and supply-chain integrity at scale. With 50 services, one shared component is a fleet-wide single point of failure.
- **Worst failure:** The platform ships a bad or compromised artifact to many production services at once. That could come from a broken shared template or from stolen CI credentials. CI is usually the most privileged system in the company, so every gate below limits what it can do.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **Consistency vs availability** | **Consistent** for promotion state: Git (the GitOps repo) is the single record of which artifact version runs in each environment. **Available** for builds: they are stateless, retried and spread across a pool. | A platform outage blocks a P1 hotfix for more than 30 minutes in a quarter → add an audited break-glass direct-deploy path (still digest-pinned and signed) |
| **Monolith vs services** (repo and pipeline model) | Keep the existing polyrepo. One central set of versioned, reusable pipeline templates. No per-team custom pipelines. | More than 30% of changes touch 2+ services, or breakage from version skew between services keeps recurring → evaluate a monorepo with Bazel or Nx |
| **Sync vs async** (deploy coupling) | **Async pull-based GitOps.** CI writes a digest bump to the environment repo, and Argo CD pulls and applies it. **CI never holds cluster credentials.** | A deploy target can't run a pull agent (serverless, legacy VMs) → push deploys for those targets only, using short-lived OIDC credentials |
| **Build vs buy** | **Buy/OSS the engines:** GitHub Actions control plane, self-hosted ephemeral runners on Kubernetes (Actions Runner Controller), BuildKit, ECR or Harbor, Argo CD + Argo Rollouts, Sigstore/cosign, Kyverno. **Build only the glue:** templates, service manifest schema, onboarding generator, promotion policy. | CI minutes cost more than budget, queue p95 stays above 5 minutes, or data residency forbids SaaS → GitHub Enterprise Server or a self-hosted control plane |
| **Artifact model** | **Build once, promote the same digest.** Images are immutable and referenced by digest (sha256), never by mutable tag. Environment differences live only in config overlays. | A regulator requires separate per-environment builds (rare) → per-environment builds with provenance linking them to the same commit |
| **Runner trust model** | Ephemeral runners, one job each, then destroyed. Separate runner pools for untrusted work (fork PRs) and trusted work (main or release). | Cold-cache build time hurts lead time (p95 > 15 min even with remote cache) → warm persistent runners, *for the trusted pool only* |
| **Rollout strategy** | Rolling deploy gated on health checks, with automatic rollback, for all services. Canary analysis (Argo Rollouts) for **tier-1 only**. | Change-failure rate above 15% in tier-2, or a tier-1 incident caused by a deploy that canary would have caught → expand canary |
| **Deploy target** *(stated, not assumed)* | Kubernetes (EKS/GKE/AKS), one staging cluster and one prod cluster to start. | Non-Kubernetes targets exist → add a target adapter in Phase 4 (see the push-deploy flip above) |
| **Signing keys** | Keyless cosign through OIDC (Fulcio/Rekor). | Air-gapped or sovereignty requirements → keys held in a KMS |
| (AI) prompt+RAG vs fine-tune | **N/A.** The system has no model component. | — |
| (AI) hosted API vs self-host | **N/A.** The system has no model component. | — |

## 3. Walking skeleton (Phase 0)

**The one real request:** a `git push` of commit `abc123` to `main` of **one real, low-risk, stateless service**. A real service is used, not a toy.
**The real response:** `GET https://<svc>.prod/version` returns `abc123`, and the deploy appears as an event on a dashboard.

**Tiers crossed:**
1. GitHub: branch protection and a required review on `main`.
2. GitHub Actions control plane.
3. An ephemeral ARC runner pod on the platform Kubernetes cluster.
4. BuildKit build from a base image pinned by digest. The push to the registry returns a digest.
5. CI opens a pull request in the GitOps environment repo that bumps the staging digest. The PR auto-merges once checks pass.
6. Argo CD syncs to the **staging** cluster. A smoke test hits `/version`.
7. A promotion PR to the **prod** overlay needs one human approval. Argo CD then syncs prod.
8. A synthetic probe checks prod `/version`.

**Deployed:** The platform's own infrastructure (runner cluster, registry, Argo CD, OIDC trust) is in Terraform with remote, locked state from the first commit. The service pipeline is a **plain inline workflow file**, deliberately not a template yet (see principle 2).

**Logged:** Runner logs and Argo CD events go to central logging. Pipeline runs are exported as OpenTelemetry traces with spans for checkout, build, push, PR, sync and probe. Every span carries the commit SHA, the image digest and the run ID.

**Monitored on day zero:**
- Pipeline success/failure and duration metrics.
- An alert on pipeline failure on `main`.
- An alert if prod `/version` doesn't match the GitOps prod digest for more than 15 minutes (drift or a stuck sync).

**Exit check:**
- A real commit reaches prod, with one trace and one deploy metric visible.
- A `git revert` of the digest bump rolls prod back, and that rollback is observed in the same dashboards.
- An audit confirms there are no static cloud or cluster secrets in CI.

## 4. Phases (ordered by dependency; within each phase, widest blast radius first)

**Phase 0: Walking skeleton.** Described in §3. It proves the substrate everything else uses: identity, runner, registry, GitOps, cluster and telemetry.

---

**Phase 1: Contracts and trust boundaries** (proven with 3 deliberately different pilot services)
- **Unlocks:** Templates can be written against stable contracts. Onboarding becomes mechanical.
- **Depends on:** The Phase 0 path running in prod.
- **Tasks (widest → narrowest):**
  1. **Identity and authorization model.** Covers who can merge, who can promote to prod (CODEOWNERS on environment directories), and per-service OIDC cloud roles. If this is wrong, every service and every pipeline gets reworked.
  2. **Artifact contract v0.** Image naming, digest-only references, required OCI labels (`git.sha`, `pipeline.run`, `owner`, `tier`), SBOM format (SPDX via syft), and registry layout and retention.
  3. **GitOps repo layout v0.** App-of-apps, per-environment overlays (kustomize or Helm values) and how promotion PRs are shaped.
  4. **Service manifest schema v0** (`service.yaml`): owner, tier, language, ports, health endpoints, deploy strategy, migrations yes/no. Validated by JSON Schema in CI. Versioned, with **additive changes only**.
  5. **Runtime secrets path.** External Secrets Operator backed by Vault or a cloud secrets manager. Runtime secrets never pass through CI.
  6. **Runner fleet.** Separate trusted and untrusted pools, autoscaling, minimum warm capacity.
  7. **Onboard pilots #2 and #3, picked to stress the contracts.** For example, a JVM service with DB migrations and a Go or Node service with two images.
- **Exit check:**
  - All 3 pilots, on different stacks, deploy to prod under the same contracts.
  - Every running prod image can be traced to its commit and pipeline run from labels alone.
  - The schema validator rejects a malformed `service.yaml`.

---

**Phase 2: Shared pipeline templates v1** (extracted from the pilots, not designed up front)
- **Unlocks:** One change improves 50 pipelines, which also means one bad change can break 50. That is why template rollout rings come first in this phase.
- **Depends on:** Contracts proven by the 3 pilots.
- **Tasks:**
  1. **Template versioning and rollout rings.** Templates are pinned by tag or SHA. Each release goes pilot ring → 20% → all. A ring halts automatically if its failure rate rises. This comes first because a template bug is the widest-blast-radius failure the platform has.
  2. **Stage contract.** Fixed stage order: lint → unit test → build → SBOM + scan → sign → push → environment PR. Teams may override only through declared hooks.
  3. **Build cache.** BuildKit registry cache plus a remote dependency cache keyed by lockfile hash.
  4. **Signing.** Keyless cosign signature and SLSA provenance attestation on every image.
  5. **Dependency hygiene.** Renovate keeps action SHAs, base image digests and lockfiles current.
  6. **Language-specific steps** (Maven, Gradle, Go, Node, Python). These are leaf work.
- **Exit check:**
  - All 3 pilots run on template v1.
  - A deliberately broken template release is caught and halted in the pilot ring before reaching ring 2.
  - Commit → prod-ready artifact p95 is under 15 minutes. Queue wait p95 is under 2 minutes.

---

**Phase 3: Deploy safety and progressive delivery**
- **Unlocks:** Production cutover for real fleets, including stateful and tier-1 services.
- **Depends on:** Templates producing signed, attested artifacts (needed before admission control can enforce anything).
- **Tasks:**
  1. **Admission policy.** Kyverno `verifyImages` or the Sigstore policy-controller. Only signed images from our registry, with provenance, are admitted. Starts in audit mode and switches to enforce mode once audit shows zero violations for a week.
  2. **DB migration pattern.** Expand/contract migrations run as a pre-sync job. Every deploy must be rollback-safe. This is wide-impact because it constrains how every stateful service ships.
  3. **Automatic rollback on health and SLO signals** for all services.
  4. **Argo Rollouts canary for tier-1**, with Prometheus analysis templates (error rate and p99 latency compared against the stable version).
  5. **Vulnerability gate.** Critical CVEs block promotion. Exceptions go through a time-boxed workflow and expire after 30 days.
  6. **Break-glass path and freeze windows.**
- **Exit check:**
  - An injected bad release (a pilot returning 5xx) rolls back automatically in under 10 minutes without a human.
  - An unsigned image is rejected in prod.
  - A migration followed by a rollback is rehearsed on a prod-snapshot schema.

---

**Phase 4: Fleet onboarding in waves**
- **Unlocks:** Platform value at scale. Legacy pipelines can be retired.
- **Depends on:** The safety rails from Phase 3. Nothing goes to prod at scale without automated rollback.
- **Tasks (widest → narrowest):**
  1. **Wave A: one representative of each remaining service archetype** (about 5 services), onboarded to staging. If an archetype breaks a contract, everything gets reworked, so this goes first.
  2. **Onboarding generator.** A command that reads `service.yaml` and produces the workflow, environment overlays and OIDC role as one PR, with no hand edits.
  3. **Wave B: bulk tier-2 and tier-3 services** (about 30). Each runs in shadow mode first (the new pipeline builds alongside the legacy one), then cuts over.
  4. **Wave C: tier-1 services** (about 10), with canary rollout. These carry the highest production risk, so their *prod cutover* comes last. Their archetypes were already proven in staging in Wave A.
  5. **Decommission each legacy pipeline** after 2 clean weeks, and revoke its credentials.
- **Exit check:**
  - 50 of 50 services deploy through the platform.
  - Zero legacy pipeline credentials are left.
  - Per-service DORA metrics are no worse than the legacy baseline.

---

**Phase 5: Self-service and insight** (the visible layer, built last)
- **Unlocks:** New services can launch without platform-team tickets. Leadership can see delivery health.
- **Depends on:** All 50 services on the platform, so the metrics are complete and trustworthy.
- **Tasks:**
  1. **Platform SLOs and on-call.** CI availability at least 99.5%, queue p95, Argo sync lag.
  2. **New-service scaffolder** with security and observability defaults built in.
  3. **DORA dashboard per team** (deploy frequency, lead time, change-failure rate, MTTR).
  4. A basic service catalog view (the Backstage catalog, or just the indexed `service.yaml` files).
- **Exit check:**
  - A new service goes from scaffold to prod in under 1 day with zero platform tickets.
  - A daily test scaffolds and deploys a throwaway service and passes.

---

**Phase 6: Harden what has proven load-bearing**
- **Depends on:** At least 3 months of fleet telemetry showing which parts are stable and heavily used.
- **Tasks:**
  1. Disaster recovery drill: rebuild Argo CD and the registry from Terraform and Git.
  2. Chaos tests against the platform itself (runners, registry, Argo CD, a GitHub outage).
  3. SLSA Level 3 (hardened builders, provenance verified at admission).
  4. Flaky-test quarantine.
  5. Cost per build-minute controls.
- **Exit check:**
  - DR restore takes under 4 hours.
  - Each degraded mode is documented and rehearsed.
  - Platform SLOs are met for a full quarter.

## 5. Cross-cutting concerns (per phase, from the first commit)

| Phase | Security | Observability | Reproducibility | Resilience |
|---|---|---|---|---|
| **0** | GitHub→cloud OIDC with zero static secrets; branch protection; CI has no cluster credentials (pull GitOps) | OTel pipeline traces (SHA/digest/run ID); success and duration metrics; prod `/version` drift alert | Platform in Terraform with locked state; actions pinned by SHA; base image pinned by digest | Argo CD self-heal; rollback via `git revert` tested once; runner jobs retried |
| **1** | CODEOWNERS on environment directories; least-privilege per-service OIDC roles; External Secrets; trusted/untrusted runner split; SBOM and scan in report-only mode | Required OCI labels give commit→digest→deploy traceability; per-service pipeline metrics tagged by owner and tier | Build once, promote the digest; immutable registry tags; schema-validated `service.yaml` | Argo CD in HA mode; registry replication or pull-through cache; minimum warm runners |
| **2** | Protected template repo; cosign signing and provenance on every image; gitleaks and SAST in templates; Renovate for pins | Template version as a metric dimension (which service runs which version); cache hit rate; queue-time metric | Containerized build steps; caches keyed by lockfile hash; same-SHA rebuild gives same digest for selected services | Template rollout rings with automatic halt; cache failure falls back to a cold build instead of failing |
| **3** | Admission control enforces signature and provenance; critical-CVE gate with expiring exceptions; audited break-glass | SLO-based canary analysis; deploy markers on every service dashboard; change-failure rate measured | Environment parity: same manifests, only overlay values differ; migrations versioned and tested on a prod-snapshot schema | Automatic rollback on SLO burn; expand/contract keeps rollbacks safe; freeze windows |
| **4** | OIDC roles generated from `service.yaml`; legacy credentials revoked at cutover (tracked to zero) | Onboarding dashboard (on-platform yes/no, template version, DORA); shadow-mode duration comparison between legacy and new | Onboarding only through generated PRs; one template lineage for all 50 services | Shadow runs before cutover; legacy pipeline kept 2 weeks as fallback; wave halt criteria |
| **5** | Scaffolder ships secure defaults; portal behind SSO with RBAC | Team DORA dashboards; platform SLOs with alerting; cost per service | Versioned scaffolder templates; daily golden-path test | Platform on-call rotation and runbooks; error budgets for the platform |
| **6** | SLSA L3; provenance verified at admission | Flaky-test detection; cost-per-minute telemetry | Hermetic builds for tier-1 | DR rebuild from code; chaos tests against runners, registry, Argo CD and a GitHub outage |

## 7. Deliberately deferred

| Not building yet | Pulled forward when |
|---|---|
| Monorepo / Bazel migration | More than 30% of changes span 2+ services, or version-skew incidents recur |
| Per-PR preview environments | Waiting on shared staging costs teams more than about 10 hours a week |
| Canary for tier-2 and tier-3 | Tier-2 change-failure rate goes above 15% |
| Multi-region / multi-cluster deploy orchestration | A second prod region or cluster is approved |
| Full Backstage developer portal (plugins, TechDocs) | More than 10 teams, or onboarding surveys flag discoverability problems |
| Test-impact analysis and test sharding | Commit→artifact p95 goes above 15 minutes after caching is in place |
| Feature-flag platform (buy, e.g. LaunchDarkly or Unleash) | Product needs releases decoupled from deploys, or dark launches |
| Self-hosted CI control plane | Data-residency mandate, or SaaS cost or limits are breached (see the build-vs-buy gate) |
| Hermetic builds for every service | A supply-chain incident, or a compliance requirement (SLSA L3+ fleet-wide) |
| Cost chargeback per team | Platform spend grows more than 25% quarter over quarter with no clear owner |
| Custom CI orchestration engine | Effectively never. Only if GitHub Actions hits hard limits that no vendor solves |
