# Build order for a real-time collaborative document editor

I read "order the build" as "put the build steps in sequence." Each phase below depends on the ones before it, so you always have something working end to end. If you meant something else, like a work order or a tech spec, tell me and I'll rewrite it.

---

## Phase 0: Decisions to make first
These are hard to change later, so settle them before writing code.
1. **How edits get merged.** Use a **CRDT** (Yjs or Automerge) rather than Operational Transformation (OT). CRDTs work offline, can sync peer-to-peer and are easier to get right. OT needs a central server and is hard to implement correctly.
2. **Editor framework.** ProseMirror or TipTap (with `y-prosemirror`), Lexical, or Slate. Pick one that already has a binding to your CRDT.
3. **Transport.** WebSockets as the main channel. Server-Sent Events (SSE) or long polling as a fallback is optional.
4. **Document schema.** Decide which content types you support (paragraphs, headings, lists, tables, images, etc.) and fix that list early.

## Phase 1: Single-user editor
5. Set up the editor using your schema.
6. Add basic formatting, a toolbar, keyboard shortcuts and copy/paste cleanup.
7. Save and load locally (IndexedDB).
**Done when:** one person can write a rich document and reload it without losing anything.

## Phase 2: CRDT document model
8. Store the document in a CRDT (e.g., `Y.Doc`) and bind it to the editor.
9. Check that edits round-trip correctly between the editor and the CRDT.
**Done when:** two editors running in the same browser tab stay in sync.

## Phase 3: Sync server
10. Build a WebSocket server (`y-websocket`, Hocuspocus, or your own) that sends updates to everyone in a document "room."
11. Add the sync handshake: when a client connects, it exchanges state vectors with the server and receives only the changes it's missing.
12. Reconnect automatically with backoff, and queue edits made while disconnected.
**Done when:** two browsers on different machines edit the same document live.

## Phase 4: Persistence
13. Save CRDT updates on the server (Postgres, S3 or Redis). Periodically merge them into a single snapshot.
14. Load a document from its latest snapshot plus any updates saved after it.
15. Store document metadata (title, owner, created and updated dates) in a relational database.
**Done when:** a document survives a server restart.

## Phase 5: Identity and access
16. Add authentication (OAuth or magic link) and verify a token when each WebSocket connects.
17. Add permissions per document (owner, editor, commenter, viewer). Enforce them on the server so viewers can't send edits.
18. Add sharing links and invites.
**Done when:** people only see and edit documents they have access to.

## Phase 6: Presence and awareness
19. Show other users' cursors and selections with names and colors.
20. Show who is currently in the document (avatar list) and their online/away status.
**Done when:** it feels like working together in real time.

## Phase 7: Collaboration features
21. Comments and threads attached to specific text, so they stay in place as the text around them changes.
22. Suggestions or tracked changes (optional, and complex).
23. Version history: named snapshots, a diff view and restoring an older version.
24. Mentions and notifications.

## Phase 8: Offline and resilience
25. Full offline editing: a service worker plus IndexedDB, so edits made offline merge cleanly when the user reconnects.
26. Test conflicts: merging edits made in parallel, editing on a bad network, one very large document.

## Phase 9: Scaling
27. Run more than one sync server. Use Redis pub/sub, or keep each document's connections on the same server.
28. Limit how fast clients can send updates, cap update sizes and set backpressure limits.
29. Lazy-load large documents and garbage-collect old CRDT history (deleted content the CRDT still keeps).

## Phase 10: Production hardening
30. Monitoring: sync latency, connection counts, update sizes, error rates.
31. Security review: validate updates on the server, prevent cross-site scripting (XSS) in pasted content, add audit logs.
32. Backups and disaster recovery for document storage.
33. Accessibility (screen readers, keyboard navigation) and mobile layouts.
34. Export and import (Markdown, PDF, DOCX).

---

### Key points
- **Critical path:** 1 → 8 → 10–11 → 13 → 16–17. That gives you a minimum viable product (MVP) of a secure, multi-user editor that saves its documents.
- **Hardest parts:** sync correctness (handled for you if you use a mature CRDT), keeping comments attached to the right text, and scaling servers that hold live connections.
- **Fastest route:** TipTap, Yjs and Hocuspocus together cover Phases 1–3 and most of 6 almost ready-made.
