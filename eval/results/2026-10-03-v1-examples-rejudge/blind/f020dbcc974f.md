# Plan: Autonomous GitHub issue triage and resolution agent

## 1. Classification
- **What:** A GitHub App agent that triages every new issue: type, area, duplicates, missing info, owner, and whether it looks like a security report. When a maintainer asks, it reproduces the bug in a sandbox, writes a fix, verifies it with tests, and opens a draft PR. It covers repos we own, starting with one, and handles issues only.
- **Type:** Mostly AI-agentic. It also includes software (the webhook service and an action ledger) and infra (a sandbox that runs code).
- **Dominant constraint:** **Correctness.** Every write must be right *and* safe. Cost comes second, because agent loops have no natural limit. Latency matters little, since issues are asynchronous.
- **Worst failure:** Text written by an attacker inside an issue hijacks the agent (prompt injection). On a public repo anyone can file an issue. The agent then leaks a secret or lands malicious code under the project's name, which is a supply-chain compromise. *(The most likely failure is different: PRs that look plausible but are wrong and waste maintainers' trust. Evals and human approval target that.)*

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| Consistency vs availability | **Consistency for the action ledger** (the database record of every action the agent takes). One Postgres primary with a managed standby. Every GitHub write carries an idempotency key so retries can't repeat it. Only one run per issue at a time. If we're down, issues just wait. GitHub doesn't retry failed webhook deliveries, so a reconciler re-requests them through the deliveries API and backfills with `issues?since=`. | Dashboards and retrieval caches may become eventually consistent, but only if failover time breaks the triage target (95% of issues answered within 5 min). The ledger never flips. |
| Monolith vs services | **Modular monolith.** One repo and one image with two roles: `web` receives webhooks, `worker` runs jobs. One exception from day one: code runs in a separate isolated sandbox. That split is for **security**, not scale. | Split out a module only when it needs to scale independently (e.g. the sandbox fleet) or gets a separate owner. |
| Sync vs async | **Async.** The webhook handler verifies the signature, saves the event, queues it, and returns 202, well inside GitHub's 10 s delivery timeout. Runs are Postgres queue jobs (`FOR UPDATE SKIP LOCKED`), checkpointed after each step. | Move runs to Temporal (a durable workflow engine) when runs waiting days for human approval become the main cause of stuck runs, or when more than ~200 runs are waiting at once. The webhook path never becomes sync. |
| Build vs buy | **Buy the commodity parts:** hosted model, managed Postgres, OpenTelemetry (OTel) tracing backend, Octokit, gVisor, gitleaks. **Build the core that's specific to us:** policy engine, action ledger, guardrails, eval harness, triage logic. Whether we build the fix-writing loop is decided by a Phase 6 bake-off against off-the-shelf tools such as GitHub Copilot coding agent and OpenHands. | Adopt a bought resolver if it matches our baseline on the repo benchmark and fits our permission and data limits. Build our own only if none qualifies. |
| (AI) prompt+RAG vs fine-tune | **Prompts plus retrieval (RAG)** everywhere. A model fine-tuned on one repo goes stale with every commit and is harder to change. | Fine-tune a *small triage classifier only*, once there are ≥5k labels confirmed by maintainers and prompt accuracy has stalled below target, or once triage costs more than 30% of spend. Fixing stays prompt-based. |
| (AI) hosted API vs self-host | **Hosted frontier model**, because fix quality depends on the model. Use zero-data-retention, no-training terms and pin an exact model snapshot. | Self-host an open-weight model if a repo's contract forbids third-party processing, or if spend exceeds the cost of running GPUs at our volume *and* an open model scores within 5 points on our benchmark. |
| (AI) data-privacy boundary | **Sent to the provider:** issue text, retrieved code and test output, after removing secrets, emails, and tokens that reporters paste into logs. **Never sent:** credentials (the agent's context and the sandbox hold none), repos tagged `restricted`, or other installations' data. Traces are kept 30 days. | A repo tagged `restricted` is excluded or sent to a self-hosted model. A deletion request removes the reporter's data from memory and traces. |
| Autonomy ceiling | **The agent proposes; humans merge.** It may add labels, comment, and open draft PRs. It never merges, never pushes to protected branches, and never closes an issue without approval. It also lacks the GitHub `workflows` permission, so GitHub itself rejects any edit to CI workflow files. That limit comes from GitHub permissions, not from the prompt. | Allow auto-merge for one class of change (e.g. docs typos) after ≥50 PRs with ≥95% merged unedited, no reverts in 30 days, and maintainer sign-off. Remove it automatically on the first revert. |
| GitHub identity & write path | **GitHub App, never a personal access token.** Its tokens expire after 1 h. Permissions grow phase by phase, and the repo owner must re-approve each increase. It can only read the main repo and pushes only to a **fork owned by the bot**. PRs from a fork get no repo secrets in CI, and CI waits for a maintainer to approve the run. | If forks aren't allowed (common for private repos): use `agent/**` branches in the same repo. Keep the App off every ruleset bypass list. Alert on any push outside `agent/**`. Move CI secrets into GitHub Environments that require a reviewer. |
| Execution sandbox | **Short-lived gVisor containers** (e.g. GKE Sandbox) on an isolated pool. They hold no credentials, can't reach the cloud metadata endpoint, and have no network except a proxy to package registries. CPU, memory, and time are capped, and each container is destroyed after its run. | Switch to Firecracker microVMs (or a managed microVM sandbox under a data processing agreement) if we run third-party repos at scale, need fast snapshot starts, or hit a gVisor limitation that breaks a test suite. |

Only the parts that are expensive to reverse are fixed from day one: the ledger schema, the action contract, the sandbox boundary, and the App permissions. Everything else stays simple until evals show it is load-bearing. All numeric thresholds are starting guesses, to be recalibrated from what Phases 1–2 measure.

## 3. First end-to-end slice (Phase 0)

**The request:** A maintainer adds the label `agent:triage` to a real issue in the target repo, and GitHub sends an `issues.labeled` webhook.
**The response:** Within 2 minutes the App posts one comment, e.g. *"Triage suggestion (v0): type `bug` · area `parser` · confidence 0.72 · [trace]"*. The comment comes from a fixed template. The model only fills in fields whose values must come from the repo's existing labels (enforced by a JSON schema). No free text from the model reaches GitHub yet.

**Tiers crossed:**
1. **GitHub App:** installed on the target repo with only `issues: write` and `metadata: read`.
2. **Ingress (`web`):**
   - verifies the `X-Hub-Signature-256` signature
   - drops duplicate deliveries by `X-GitHub-Delivery` ID
   - saves the raw event, queues it, and returns 202
3. **Postgres:** `events`, `runs` and `actions` tables, plus the job queue.
4. **Worker:**
   - confirms via the API that the sender has triage permission or higher
   - ignores events the agent caused itself
   - takes the per-issue lock and creates a 1-hour App token
5. **Model adapter:**
   - one hosted-model call
   - the issue text goes inside a separate block marked as untrusted data
   - output has a hard `max_tokens` limit and must match a JSON schema
6. **Action executor:**
   - allows exactly one action
   - writes a ledger row with an idempotency key, then posts the comment
   - the comment carries a hidden `<!-- agent-action:{key} -->` marker, and the comment ID is recorded
7. **Telemetry:** OTel spans across every step.

**Deployed:**
- A managed container platform (Cloud Run or ECS Fargate) plus managed Postgres, all set up with OpenTofu.
- One signed, digest-pinned image, built in CI from lockfiles.
- The App's private key, the webhook secret, and the model key live in the cloud secret manager.
- An `AGENT_WRITES_ENABLED` kill switch.

**Logged:** JSON logs keyed by delivery ID, run ID and trace ID. Every model call records the prompt-template hash, model snapshot ID, tokens in and out, dollar cost, and latency.

**Monitored:**
- Alerts on non-2xx webhook responses, any event waiting more than 5 min, run failure rate, and daily spend.
- An hourly synthetic canary opens and labels an issue in a separate canary repo, and pages if no comment appears within 5 min.
- A 25-issue golden set (historical issues with known labels) is scored on every deploy.

The skeleton already contains a minimal version of each AI defense:
- **Human approval:** only a maintainer's label triggers it.
- **Budget:** a hard token limit.
- **Injection defense:** an untrusted-data block, fixed-choice output, and a one-action allow-list.

So no unguarded model call ever runs in production.

**Exit check:**
1. A real label in production gets the comment within 2 min.
2. One trace covers webhook → queue → model → GitHub write, and the run's tokens and cost appear on the dashboard.
3. Redelivering the webhook from GitHub's UI does not post a second comment.
4. The kill switch stops writes within 60 s.
5. The canary stays green for 72 h.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

```
P0 --> P1 --+--> P2 --> P3 --> P4 --+--> P6 --> P7 --> P8
            |                       |
            +--> P5 (parallel) -----+
```
*P5 needs only P1, so it runs alongside P2–P4. P6 needs both branches.*

**Phase 0: First end-to-end slice** (see §3)
- Unlocks: Everything; it's the spine.
- Depends on: One cloud account and one target repo.
- Tasks:
  1. Ledger schema (`events`, `runs`, `actions`) with idempotency keys and trace IDs. Every later phase writes through it.
  2. OpenTofu infrastructure, plus a CI pipeline that builds a signed, digest-pinned image.
  3. The App and the signed-webhook endpoint.
  4. The worker and a one-function model adapter.
  5. The one-action executor and the kill switch.
  6. Alerts, the canary, and the golden-set eval.
  7. The comment template (leaf).
- Exit check: As in §3.

**Phase 1: Defenses, budgets, human approval, eval data**
- Unlocks: Reading untrusted text at volume and proposing write actions safely. Every later capability can now be measured.
- Depends on: Phase 0 exit (ledger, idempotent write and tracing proven in production).
- Tasks:
  1. **Action contract.** Every side effect becomes a typed `ProposedAction{type, target, args, tier, idempotency_key}`, judged by policy code with risk tiers T0–T3 (§6.3). Widest impact: every capability goes through it.
  2. **Trust boundary.** Untrusted content goes in labeled data blocks that record where it came from. Tools come from an allow-list, and their arguments are checked against a JSON schema. The model only *proposes* actions.
  3. **Approval flow.** A user with triage permission or higher (checked) approves with `/agent approve`. The approval is tied to a hash of the exact action, expires after 7 days, and goes into an append-only audit log.
  4. **Budgets** (§6.2): per-run limits, per-issue and per-author limits, a daily spending breaker, and a cap on maintainer attention.
  5. **Eval data**, frozen and hashed:
     - ≥300 closed issues with the labels maintainers gave them, plus known duplicate pairs
     - a localization set: each issue mapped to the files its fix PR changed
     - a red-team suite of ≥30 injection attempts, placed in issue bodies, comments, code comments, test output and past issues
  6. **Output filters:**
     - gitleaks rules for secrets
     - personal-data removal
     - stripping @-mentions
     - disabling links and images to domains not on an allow-list (GitHub's image proxy fetches whatever URL an image points to, so an image can carry data out)
- Exit check:
  - The red-team suite triggers no out-of-policy actions and leaks no secrets or links.
  - A runaway loop is stopped at its limit and emits a `budget_exhausted` metric.
  - A T2 action pauses: a non-collaborator's approval is rejected and logged, a maintainer's approval executes, and the audit row records the approver and the action hash.

**Phase 2: Retrieval + shadow triage**
- Unlocks: Triage decisions based on real context, scored against what maintainers actually do, with no write risk.
- Depends on: Phase 1 exit (the trust boundary wraps retrieved content and the eval sets are frozen).
- Tasks:
  1. **Context contract.** Every retrieved item records `{source, repo, commit SHA or issue #, author, trust}`. Prompts, memory, and evals all rely on it.
  2. **Code search at a fixed commit:**
     - ripgrep text search, a tree-sitter symbol map, and extraction of `file:line` from stack traces
     - the App gains `contents: read`
     - repos are cloned with git hooks, submodules, and LFS turned off
  3. **Issue-history index.** Keyword (BM25) plus embedding search over title, body, and labels, updated from webhooks.
  4. **Docs.** Label descriptions, CONTRIBUTING, CODEOWNERS.
  5. **Shadow triage on every new issue.** Type, area, duplicates, completeness, owner, and a possible-vulnerability flag are logged, never posted.
- Exit check:
  - For known duplicate pairs, the true duplicate is in the top 5 results ≥80% of the time.
  - The files the real fix changed appear in the top 10 for ≥70% of the localization set.
  - Two weeks of shadow decisions are scored per label class against maintainer actions.

**Phase 3: Model access hardening + live triage**
- Unlocks: Automatic labels and duplicate suggestions on every new issue. This is the first value users see.
- Depends on: Phase 2 exit. We know shadow precision for each class. The shape of the retrieved context is settled, so we can size the context budget and the cached prompt prefix.
- Tasks:
  1. A gateway contract, `complete(task, messages, schema, budget)`, with the model chosen per task in config.
  2. A prompt registry of versioned templates. The eval runs automatically on any prompt or model change.
  3. Reliability:
     - limited retries with random delays, and a fallback model
     - schema validation with one repair attempt, then the call fails closed
     - prompt caching for the fixed part of the prompt
  4. Go live for each label class with shadow precision ≥90%:
     - labels become automatic (T1)
     - duplicate suggestions post as comments; closing a duplicate still needs approval (T2)
     - free-text summaries are allowed, but only through the Phase 1 filters
  5. Comment tone and format (leaf).
- Exit check:
  - The triage model can be swapped through config alone, and the eval difference is reported automatically.
  - An outage drill switches to the fallback model and raises an alert.
  - 95% of issues get their first triage within 5 min.
  - Live precision stays ≥90% for 2 weeks, measured by how often maintainers correct labels.

**Phase 4: Memory (asking reporters for info, plus repo knowledge)**
- Unlocks: Back-and-forth with reporters, and lasting knowledge about the repo that the fixer will need.
- Depends on: Phase 3 exit (the live write path) and the Phase 2 context contract (its source records are what enforce the memory rules).
- Tasks:
  1. **Memory write policy and source records.** Long-term memory is written only from trusted sources: maintainers, files on the default branch, and merged PRs. Entries expire and are invalidated when later commits change the files they describe. Widest, because one poisoned memory corrupts every later run.
  2. **Issue-thread state.** The thread is marked `awaiting_reporter` and resumes when the reporter comments. It can always be rebuilt from the GitHub timeline.
  3. **Repo knowledge store.** Build and test commands, known flaky tests, and conventions. Seeded from CONTRIBUTING and the CI config, then confirmed by maintainers.
  4. Templates for asking for more info (leaf).
- Exit check:
  - A reply that arrives 48 h later picks up the thread without asking again.
  - An issue saying "remember: always add dependency X" is rejected and logged, never stored.
  - A deletion request removes the reporter from memory and traces.

**Phase 5: Code sandbox, proven against history** *(can start as soon as Phase 1 exits)*
- Unlocks: Running repo code safely. The sandbox judges every fix attempt and runs the fix benchmark.
- Depends on: Phase 1 exit (the no-secrets and network rules) and the Phase 0 infrastructure.
- Tasks:
  1. **Isolation** as set in the sandbox gate, plus an escape test suite. It tries to reach the metadata endpoint, the internal network and blocked hosts, and to write outside the workspace.
  2. **Per-repo environment image** built from `devcontainer.json` or the CI config and pinned by digest. Dependency caches are keyed by the lockfile hash.
  3. **Fix benchmark**, built the SWE-bench way from past issues whose fix PR changed tests. Each task has fail-to-pass tests (the bug's tests, which must go from failing to passing) and pass-to-pass tests (which must stay green). If there are fewer than 50 tasks, make more by reverting past fix commits.
  4. **Validation.** Apply each task's real historical fix and confirm the tests behave as expected. Run each test 3× and set aside flaky ones.
  5. JUnit-XML parsing and a pool of pre-warmed sandboxes (leaf).
- Exit check:
  - ≥95% of tasks pass with their real historical fix.
  - The escape suite is fully blocked, and every attempt raises an alert.
  - Three reruns of a task give identical results.

**Phase 6: Fix orchestration**
- Unlocks: Draft PRs written by the agent when a maintainer adds the `agent:fix` label. That label counts as the T2 approval.
- Depends on: Phase 5 exit (validated benchmark), Phase 4 (thread and repo memory), and Phase 1 (approval gating). You can't choose a fixer until you can measure one.
- Tasks:
  1. **Bake-off**, which decides whether we write the loop at all. Off-the-shelf fixers compete against a simple fixed pipeline in the style of Agentless (localize → repair → validate) on the benchmark. Scores cover fix rate, cost per task, and fit with our policies.
  2. **Write path** as set in the identity gate:
     - the App gets `contents: write` on the bot's fork only, plus `pull_requests: write` on the main repo
     - no `workflows` permission
     - CI runs on fork PRs require maintainer approval
     - audit the repo for `pull_request_target` workflows that check out PR code, since those would hand agent code the secrets
  3. **Stage machine** with checkpoints: reproduce → localize → patch → verify → propose. Inside each stage the model runs a tool loop with a hard limit.
  4. **Reproduce first.** A failing test or repro script is required before any patch.
  5. **Verify.** The bug's fail-to-pass tests, the full existing test suite, and linters all run in the sandbox. Only all-green results go forward.
  6. **Diff policy.** Patches that add dependencies or touch sensitive paths stay draft and get `needs-human-review`. Sensitive paths are CI, build scripts, manifests and lockfiles, CODEOWNERS, and auth or crypto code. gitleaks scans every diff.
  7. **Draft PR** with the repro, test evidence, cost and trace link. If the agent gives up, it posts its findings instead (leaf: PR template).
- Exit check:
  - On held-out tasks (3 trials each), the fix rate is at least the bake-off baseline.
  - No sensitive-path patch leaves draft without a human.
  - Killing a worker mid-stage resumes from the last checkpoint.
  - A canary fork PR whose test dumps the CI environment finds no secrets.

**Phase 7: Routing**
- Unlocks: The agent offering to fix suitable issues on its own initiative, and lower average cost.
- Depends on: Phase 6 exit (the fix path is proven and we have cost data per stage) and Phase 3 (live triage signals).
- Tasks:
  1. **Fixability score.** It decides which issues ever enter the $5 path. Inputs: a repro, a stack trace, how confident localization is, overlap with sensitive paths, and issue type. Claims in the issue text such as "easy fix!" are never inputs.
  2. **Path routing:**
     - questions get a docs answer
     - docs and typo fixes take the cheap path, verified by a docs build and link check
     - feature requests get a label only
     - possible vulnerabilities go privately to maintainers
     - high-scoring bugs get "I can attempt this (est. $X)", approved with one command
     - low-scoring issues go to a human
  3. **Model tiers per stage.** A small model classifies and summarizes; the frontier model localizes and patches. Escalate once if verification fails. Decline when the estimated cost exceeds the remaining budget.
  4. Threshold tuning (leaf).
- Exit check:
  - The cheap path matches the frontier model on its class of issues.
  - Average cost per fixed issue drops ≥30%, losing no more than 2 points of fix rate.
  - Every routing decision is logged with its inputs and cost.

**Phase 8: Feedback and earned autonomy**
- Unlocks: The agent improves from what maintainers do, and each action class earns or loses autonomy.
- Depends on: Phase 7 exit plus ≥4 weeks of live outcomes.
- Tasks:
  1. **Outcome capture**, counting collaborators only, each signal attributed:
     - label corrections within 7 days, and reversed duplicate calls
     - PR outcomes: merged as-is, merged with edits (and how big the edits were), closed, or reverted within 30 days
     - review comments and `/agent wrong` reports
  2. **Failures become eval cases**, reviewed by a human before entering the frozen set.
  3. **Updates ship as PRs.** Changes to prompts, examples, and retrieval go to the agent's config repo, and an eval must pass before merge.
  4. **Autonomy ladder.** Dashboards per action class. Promotion follows the autonomy gate plus sign-off; demotion is automatic when a threshold is breached.
  5. A weekly digest for maintainers (leaf).
- Exit check:
  - A batch of corrections raises held-out triage accuracy by ≥3 points without regressing on the golden set.
  - A simulated spike in reverts demotes that class automatically within one cycle.

## 6. AI layer (AI/agentic systems only)

Defenses and budgets are stubbed in Phase 0 and completed in Phase 1, before any capability. The capabilities then follow in order.

1. **Prompt-injection and guardrail defense** (stub in P0, full in P1)
   - *In this system:* Anything a non-maintainer can write is untrusted: issue and comment text, code and code comments, commit messages, test output, and past issues pulled in by retrieval. Three structural moves:
     - The model *proposes* typed actions; fixed policy code decides.
     - The three risky ingredients never meet: the part that reads untrusted text has no secrets and no open network access, and can only write through the policy engine.
     - Outbound text is filtered for secrets, links, images and mentions.

     Issues that look like vulnerability reports get no public analysis.
   - *Exit:*
     - The red-team suite triggers no out-of-policy actions and no leaks.
     - Triage decisions match the clean control in ≥95% of injection attempts.

2. **Cost and latency budget** (stub in P0, full in P1)
   - *In this system:*
     - **Triage:** ≤$0.10 per issue; 95% of first responses within 5 min.
     - **Fixing:** ≤$5, ≤50 tool calls and ≤30 min per attempt; at most 2 attempts per issue.
     - **Abuse limits:** ≤5 runs per author per day, so nobody can run up our bill; ≤10 writes per issue per hour, which stops loops between bots; a $100 daily breaker per repo.
     - **Maintainer attention, the scarcest budget:** ≤3 open agent PRs and ≤10 pending approvals per repo.

     Limits are reset to 1.5× the measured 95th percentile.
   - *Exit:*
     - A test that never passes is stopped at the limit, emits `budget_exhausted{cost,iterations}`, and posts a status comment.
     - A load test trips the breaker and pages on-call.

3. **Human approval gating** (trigger in P0, full in P1)
   - *In this system:*
     - **T0 (reads)** and **T1 (reversible writes:** labels, templated comments, requests for info) run on their own once shadow precision qualifies.
     - **T2 needs approval:** closing as a duplicate, assigning people, starting a fix, anything on a `security` issue, and taking a sensitive-path patch out of draft.
     - **T3 is forbidden *by permissions*:** merging, pushing to protected branches, editing workflows, changing settings, deleting.
   - *Exit:*
     - A T2 action pauses.
     - A non-collaborator's approval is ignored; a maintainer's executes.
     - An audit row tied to the action's hash is written.

4. **Retrieval** (P2)
   - *In this system:*
     - **Code at a fixed commit:** text search, a symbol map and stack-trace parsing. Embedding search for code is deferred.
     - **Past issues:** keyword plus embedding search, to find duplicates.
     - **Docs:** to pick labels and owners.
   - *Exit:*
     - The true duplicate is in the top 5 ≥80% of the time.
     - The real fix's files are in the top 10 for ≥70% of tasks.

5. **Model access** (one-function adapter in P0, full gateway in P3)
   - *In this system:* A single `complete(task, messages, schema, budget)` call. The model is chosen per task in config. It includes retries, a fallback model, schema validation and repair, and caching of the system prompt and repo map.
   - *Exit:*
     - Swapping the model is a config change only; the eval re-runs automatically and reports the difference.
     - An outage drill switches to the fallback.

6. **Memory** (P4)
   - *In this system:*
     - Working state for each run, checkpointed in the ledger.
     - Issue-thread state, which can be rebuilt from the timeline.
     - Long-term repo knowledge, written only from trusted sources, with its source recorded, an expiry, and invalidation by commits. This is the defense against poisoned memory.
   - *Exit:*
     - A reply 48 h later resumes cleanly.
     - An injected "remember…" is never stored.

7. **Orchestration** (P6)
   - *In this system:* One agent, not a team of agents. A fixed sequence of stages runs a limited tool loop in each stage. No repro means no patch, and only fully green verification produces a PR. The simple Agentless-style pipeline is the baseline any freer loop must beat.
   - *Exit:*
     - A benchmark task runs end to end, with each stage traced with tokens and cost.
     - A worker killed mid-stage resumes from its checkpoint.

8. **Routing** (P7)
   - *In this system:*
     - **By issue:** question, docs, feature, vulnerability, fix, or human, based on the fixability score.
     - **By model:** small for classifying, frontier for patching, escalating once if verification fails.
   - *Exit:*
     - Cheap issues take the cheap path with no loss in fix rate, hard ones escalate, and both are logged.
     - Average cost per fixed issue drops ≥30%.

9. **Feedback** (P8)
   - *In this system:* Maintainer corrections, PR outcomes, reverts and `/agent wrong` reports feed four things:
     - new eval cases
     - prompt and example changes, shipped as PRs that must pass evals
     - confirmed duplicates as positive examples for retrieval
     - promoting or demoting action classes
   - *Exit:* A batch of corrections raises held-out triage accuracy by ≥3 points with no regression on the golden set.

## 7. Deferred

- **Auto-merge for any class.** Pulled forward only by the autonomy-ceiling flip: ≥50 PRs, ≥95% merged unedited, no reverts in 30 days, maintainer sign-off.
- **Alternatives held behind a gate:** Temporal, a fine-tuned triage classifier, a self-hosted model, Firecracker, the same-repo write path, multi-region. Each is pulled forward only by its revisit trigger in §2.
- **Multiple agents (planner, coder, reviewer).** When the single stage machine stops improving on the benchmark for two releases *and* a test shows a reviewer pass adds ≥3 points.
- **Embedding search for code.** When text and symbol search miss the real fix's files in more than 30% of localization tasks.
- **Updating its own PRs from review comments.** When merge-with-edits data shows most reviewer requests are small and mechanical.
- **Issue classes with no automatic check** (UI or visual bugs, performance, flaky tests, environment-specific bugs). These go to humans until a check exists for that class, e.g. a performance benchmark in CI.
- **Reviewing PRs written by humans.** Out of scope. Pull forward only if maintainers ask, and only once the agent's own PRs merge ≥80% of the time.
- **Rollout to a whole org, many repos, or as a hosted product.** Only after one repo holds its fix-rate and trust numbers for a quarter, and after a review of how installations are isolated from each other.
- **Dependency-upgrade PRs.** Not built; use Dependabot or Renovate.
- **Slack or chat interface.** GitHub is the only interface. Pull forward if the median approval wait exceeds 24 h because maintainers aren't seeing requests.
