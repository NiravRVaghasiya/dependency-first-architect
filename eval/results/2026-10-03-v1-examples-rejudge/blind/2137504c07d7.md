# Plan: CI/CD platform for 50 microservices

## 1. Classification
- **What:** A shared platform that takes each of 50 microservices from a merged commit to a built, tested, signed artifact. It then promotes that artifact through dev → staging → prod, checks it, and can roll it back fast.
- **Type:** Infra (platform engineering) with a thin software layer: the pipeline template, the deploy chart and the promotion scripts. There is no AI component. **Assumption:** the 50 services already ship some other way today. They will move over in waves, and each keeps its old pipeline switched off but ready as a fallback.
- **Dominant constraint:** **Correctness.** Prod must run exactly the artifact that was reviewed and tested, and every change must be reversible. Scale makes this harder: with 50 services × 3 environments, any platform mistake is copied 50 times.
- **Worst failure:** A bad or malicious artifact reaches prod in many services at once and can't be rolled back fast. It could get there through a change to the shared template or a stolen CI credential. A CI/CD platform is the most privileged system in the company.

## 2. Key decisions (resolved up front)

| Decision | Default (chosen now) | Revisit trigger |
|---|---|---|
| Consistency vs availability | **Integrity first.** Git is the single source of truth for each environment, and Argo CD reverts any drift. Prod accepts only verified artifacts: checked at promotion from Phase 2, and at cluster admission from Phase 4. Emergencies use a break-glass path: two-person approval, time-limited, already-built digests only, written back to Git within 24 h. | The integrity checks (Git host, registry, verifier) cause a missed incident-recovery target more than once a quarter → add a pre-approved **hotfix lane** that lets the deploy through and verifies afterwards. The normal prod path never flips. |
| Monolith vs services | **One shared platform.** One standard pipeline template (versioned, each service pins a version) and one Argo CD per trust tier (prod and non-prod). Not 50 custom pipelines. | More than 10 services need to bypass core stages → split into 2–4 templates by service type. Reconcile p95 > 3 min, or a regulated group of services needs isolation → split Argo CD into shards. |
| Sync vs async | **Async, pull-based.** CI's job ends when the artifact is published and a PR is opened on the env repo. Argo CD then applies it, and each promotion step is a PR. So **CI never holds cluster credentials.** PR checks stay synchronous and blocking (≤ 10 min p95). | More than 5% of releases need services deployed in a fixed order → add a synchronous release orchestrator (Kargo / Argo Workflows) for those releases only, and treat that coupling as a defect to remove. |
| Build vs buy | **Use off-the-shelf tools for standard layers; build only the glue.** GitHub Actions (hosted runners first), Argo CD + Argo Rollouts, ECR/GAR, Sigstore cosign, Kyverno, External Secrets, and the existing Prometheus/Grafana/Loki. Built in-house: the template, the base chart, the promotion workflows. (If you're on GitLab, use GitLab CI; the order doesn't change.) | Compliance forbids a hosted CI control plane, or vendor outages block shipping > 4 h a quarter by our own measurement → self-host the CI engine behind the same template. |
| Artifact model | **Build once, promote the same digest** through dev → staging → prod. Environments differ only in config and secrets. Manifests never use mutable tags. | A target needs a different binary (FIPS, another CPU architecture) → build a separate artifact that is tested and attested on its own. Never rebuild per environment. |
| Rollback & schema changes | **Rollback = deploy the previous digest** (`git revert`). This only works if every DB migration is backward-compatible with the previous version (expand/contract), run as a pre-deploy Job. | A release can't stay compatible with the previous version → mark it `forward-only`: take a snapshot first, require human prod approval, no auto-promotion. |
| Deploy target | **Kubernetes only.** Dev, staging and prod clusters already exist or are provided by the runtime team, with one namespace per service. | 5 or more services can't move to K8s during the program → add a push-style deployer for their target, with OIDC-scoped access and the same digest and signature checks. |
| Repo topology | **One repo per service**, plus one central env repo (`platform-deploy`) where CODEOWNERS controls who owns which paths. Onboarding needs no repo migration. | The services already share one repo, or > 10% of changes span several repos → build only the affected services (Bazel/Nx); only the Phase 2 template changes. Promotion PRs keep conflicting → split the env repo per team. |
| (AI) prompt+RAG vs fine-tune | N/A: no model anywhere in the system | — |
| (AI) hosted API vs self-host | N/A: no model anywhere in the system | — |

## 3. First end-to-end slice (Phase 0)
- **The one real request and response:** a developer merges a real, trivial change to `main` of **service #1**. Pick a stateless, low-traffic internal API whose team volunteers. **Response:** in prod, `GET /version` returns the new commit SHA, and the commit shows a green `deployed: prod` status.
- **Every tier it crosses:**
  1. Git host (protected `main`).
  2. GitHub Actions on a hosted runner: unit tests, then `docker buildx build`.
  3. OIDC login to a short-lived cloud role that can push to only **one** registry repo.
  4. Registry: tags can't be overwritten, and the image is recorded by digest.
  5. Env repo: CI opens a PR that sets `envs/prod/service-1` to the new digest, and the service owner merges it.
  6. Argo CD in the prod cluster pulls the change and syncs.
  7. Kubernetes rolling update, which only sends traffic to pods that pass the readiness check.
  8. A post-deploy smoke Job checks `/healthz` and that `/version` equals the SHA.
  9. An Argo CD notification posts the deploy status back to the commit.
- **Deployed:** Platform infra lives in Terraform: the registry, the OIDC trust, the IAM role, and the GitHub App that opens PRs. Argo CD is installed with Helm and then manages its own config from `platform-deploy`. Nothing is set up by hand in a console.
- **Logged:** CI logs, Argo CD controller logs, K8s events and service logs all go to the existing log backend.
- **Monitored:**
  - Each pipeline run is exported as an OpenTelemetry trace (one span per step), tagged with the commit SHA and digest.
  - Argo CD metrics (`argocd_app_sync_total`) go to Prometheus.
  - Grafana shows deploy markers on service #1's dashboard, plus lead time (commit to prod sync).
  - Two alerts: a prod app is `Degraded` or `OutOfSync` for more than 10 min, and the pipeline fails on `main`.
- **Build order (widest impact first):**
  1. Trust boundary: OIDC, no cluster credentials in CI, Argo CD pulls changes.
  2. First version of the desired-state format: `envs/<env>/<svc>` layout, references by digest only, and OCI `source`/`revision` labels on images.
  3. Platform infrastructure as code.
  4. The observability pieces, live *before* the first pipeline run.
  5. Service #1's plain workflow file (no template).
  6. The rollback drill.
- **Deliberately absent:** template, staging, signing, canaries, portal.

**Exit check:**
- A real merged commit reaches prod with one human approval (the env-repo PR) and no other manual step.
- In prod, `/version` returns the new SHA.
- The pipeline trace and the lead-time metric are visible in Grafana.
- `git revert` restores the previous digest in prod in under 5 min.
- An IAM audit confirms CI never held cluster credentials.

## 4. Phases (ordered by dependency; within a phase, widest impact first)

**Phase 0: First end-to-end slice** (§3). Everything below depends on it.

**Phase 1: Environments, promotion and the rollback contract (3 pilot services)**
- **Unlocks:** Safe delivery across dev, staging and prod. A desired-state layout that all 150 service × environment apps will follow. A rehearsed rollback for services that own a database schema.
- **Depends on:** Phase 0's proven path (digest → env repo → Argo CD) and its rollback drill.
- **Tasks:**
  1. **Promotion model.** Layout `envs/{dev,staging,prod}/<svc>`. The same digest moves one PR per step:
     - dev merges automatically;
     - staging is promoted automatically once the dev smoke test passes;
     - prod needs owner approval (manual until Phase 3).

     *Widest impact: it sets the layout of every future app.*
  2. **Trust tiers.** A non-prod Argo CD for dev and staging, separate from the prod one. Argo CD AppProjects (per-team permission scopes) limit each team to its own namespaces. CODEOWNERS on `envs/prod/**`. *This is the access model.*
  3. **Schema-change rules.** Migrations run as a pre-deploy Job using the same digest. A migration linter in CI (squawk or Atlas) enforces expand/contract. *Getting this wrong costs data, not just rework.*
  4. **Config and secrets.** Per-environment config lives in Git. Secrets come only from the cloud secret manager through External Secrets, and each service has its own workload identity.
  5. **Smoke tests after each deploy**, in every environment. A failure blocks promotion.
  6. **Pilots #2 and #3**, picked to stress these rules: one uses a different build toolchain, and #3 owns a Postgres schema. They run copies of the pipeline. *No template yet: extract it only after three working pipelines exist.*
- **Exit check:**
  - For all 3 pilots, an automated check confirms the prod digest equals the staging digest.
  - A manual edit in prod is reverted automatically by Argo CD.
  - Pilot #3 ships an expand migration, then rolls back to the previous version with zero errors (in staging, then in one planned prod drill).
  - gitleaks finds no secrets in any repo.
  - The only secret CI holds is the GitHub App key, and it can only open PRs on the env repo.

**Phase 2: Standard pipeline template, base chart and signed artifacts (13 services)**
- **Unlocks:** One change improves every service. Every artifact carries signed build provenance. A tested way to roll changes out to all services, which the rest of the program relies on.
- **Depends on:** Three working pipelines from Phase 1, and the promotion path that the template hands off to.
- **Tasks:**
  1. **Template interface and release process.** A reusable workflow in `platform-pipelines`.
     - Core stages can't be removed: test → build → scan → sign/attest → publish → open dev deploy PR. Services can only add steps at declared hook points.
     - Releases are versioned (semver) and services pin a version.
     - Every release must pass a test suite of sample repos, one hello-world repo per service type.
     - Renovate sends a new release to a canary group of services immediately, and to everyone else after 3 days (`minimumReleaseAge`).

     *Widest impact: this is how the worst failure would spread.*
  2. **Base deploy chart.** The shared runtime rules:
     - required health probes, CPU/memory requests and limits, and a PodDisruptionBudget;
     - non-root with a read-only root filesystem, plus standard labels;
     - OpenTelemetry auto-instrumentation with `service.version` set to the commit SHA.

     *It shapes how every service behaves in prod.*
  3. **Signing and attestations.** Each image gets a keyless cosign signature, an SBOM (Syft) and SLSA build provenance, signed under the reusable workflow's identity. *Signing waits until now because that identity only becomes stable once the template exists.* Promotion rejects digests that fail verification. Kyverno `verifyImages` runs in **Audit** mode (report only) in all clusters.
  4. **Dependency proxy.** A pull-through cache for base images and packages (ECR pull-through + CodeArtifact, or Artifactory). Lockfiles are mandatory.
  5. **Wave 1:** about 10 services across service types, each keeping its old pipeline as a fallback.
  6. *Narrowest:* per-service hooks, such as custom test commands and cache tuning.
- **Exit check:**
  - 13 services run on template v1.x, and none has forked a core stage.
  - A deliberately broken template pre-release is stopped by the sample-repo suite, and a release that passes reaches the canary group first.
  - The Kyverno audit shows 13/13 prod images with a valid signature and provenance from the platform workflow.
  - Request rate, error rate and latency by `service.version` are visible for 13/13 services.
  - Builds still pass with Docker Hub blocked at the network.

**Phase 3: Gradual rollout and automated checks**
- **Unlocks:** Routine prod deploys with no human in the loop. Each deploy's damage is capped at the share of traffic on the canary.
- **Depends on:** The per-version request, error and latency metrics proven in Phase 2. The canary checks can't be written until those queries return real data.
- **Tasks:**
  1. **Rollout rules.** The base chart gains an Argo Rollouts `Rollout`: canary at 10 → 25 → 50 → 100% with pauses in between. It is opt-in first, then on by default. Traffic is split through the existing ingress or Gateway API, or by replica count where that isn't available. *It changes every service's manifest, so it lands while 13 services use the chart, not 50.*
  2. **Shared canary checks** (ClusterAnalysisTemplates). Compare the canary's error rate and p95 latency with the stable version, using per-service thresholds. A failed check rolls back automatically.
  3. **Auto-promotion rule.** After 5 clean, checked rollouts, a service's prod promotions can be merged by a bot. `forward-only` releases still need a human.
  4. *Narrowest:* per-service threshold tuning and alert routing.
- **Exit check:**
  - In a planned test, a deliberately bad build (injected 5xx errors) on a pilot is stopped and rolled back in prod with no human action, within 10 min and with at most 10% of traffic exposed.
  - Good builds for eligible services reach 100% unattended.
  - Fewer than 5% of rollouts are wrongly aborted over 2 weeks.

**Phase 4: All 50 services, enforcement on, old pipelines off**
- **Unlocks:** Every service is on the platform, the old CI and its prod credentials are gone, and prod clusters reject unverified images.
- **Depends on:** The full standard path (Phases 1–3) proven on 13 services, so the remaining 37 move once, straight to the final setup.
- **Tasks:**
  1. **Harden the platform before all services depend on it.**
     - Platform SLOs with error budgets: pipeline availability, queue time p95, lead time p95.
     - Argo CD in high-availability mode.
     - A break-glass drill, and a disaster-recovery rebuild from Git.

     *Widest impact: from here on, a platform failure hits all 50 services.*
  2. **Waves 2–4**, about 12 services each, lowest risk first. Kyverno is switched to **Enforce** in each service's namespace as that service moves over.
  3. **Retire the old pipelines.** For each service, after 10 clean deploys on the platform, delete the old pipeline and revoke its prod credentials. Then switch the cluster-wide default to Enforce. Every namespace is already enforced by then, so this last switch changes little.
  4. **Vulnerability gate.** Critical CVEs with an available fix block promotion. It runs warn-only for 2 weeks first and has an exception process.
  5. *Narrowest:* runbooks and cost tuning.
- **Exit check:**
  - 50/50 services deploy only through the platform.
  - An IAM audit finds no old-pipeline credentials with prod access.
  - No unsigned images run in prod under cluster-wide Enforce.
  - Platform SLOs hold for 30 days.
  - A disaster-recovery drill rebuilds the platform in a sandbox account in under 2 h.

**Phase 5: Self-service and developer experience (the visible part, built last)**
- **Unlocks:** New services reach prod without help from the platform team, and every team can see its own delivery metrics.
- **Depends on:** Rules that stayed stable across all 50 services in Phase 4. Automating onboarding any earlier would copy every later rule change into each new repo.
- **Tasks:**
  1. **New-service generator** (a Backstage Software Template). It creates a repo already set up with the pinned template, the base chart, env-repo entries, Argo CD apps and repo protections. *Widest impact of the developer-experience items: every future service inherits what it generates.*
  2. **Service catalog**, filled from existing sources (CODEOWNERS, image labels, Argo CD). No new metadata that someone has to maintain by hand.
  3. **Per-team DORA dashboards** (deploy frequency, lead time, change failure rate, recovery time), built from the deploy events recorded since Phase 0.
  4. *Narrowest:* chat commands, badges, notification preferences.
- **Exit check:**
  - A new service goes from generated repo to prod in under a day with no platform-team ticket.
  - Catalog ownership matches CODEOWNERS for 50/50 services.
  - Every team has a live DORA dashboard.

## 6. AI layer (AI/agentic systems only)
**N/A.** There is no model, retrieval or agent anywhere in this system. If an AI feature is added later (for example, LLM triage of failed builds), plan it as its own AI layer, starting with guardrails and cost limits.

## 7. Deferred
- **Self-hosted runners (short-lived, via Actions Runner Controller):** bring forward when builds need private-network access, queue time p95 passes 5 min, or hosted-runner spend exceeds the cost of running our own.
- **Service mesh:** bring forward when replica-based canaries are too coarse (services with fewer than 5 replicas) or encrypted, authenticated service-to-service traffic (mTLS) becomes a requirement.
- **Preview environment per PR:** bring forward when waiting for shared staging takes more than about 20% of lead time.
- **Cross-service test gates:** Pact contract tests (`can-i-deploy`) plus a small suite for critical user journeys. Never a full end-to-end gate across the fleet, which would tie 50 release schedules back together. Bring forward when at least 20% of rollbacks, or 2 or more Sev-2 incidents a quarter, come from breaks between services that canaries missed.
- **Promotion orchestrator (Kargo):** bring forward when promotion needs more than PRs that bump a digest, such as bundles of services or multi-step approvals.
- **Multi-region promotion and registry replication:** bring forward when the first service runs in prod in more than one region or cluster.
- **Hermetic, bit-for-bit reproducible builds:** bring forward if an audit or customer requires proof by rebuild.
- **Onboarding more than 13 services before Phase 3 is done:** bring forward if the old CI hits an end-of-life or licence deadline, or is causing incidents. Those services would use the Phase 2 setup and switch on gradual rollouts later with one chart value.
