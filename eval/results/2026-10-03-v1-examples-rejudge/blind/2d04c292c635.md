# BUILD PLAN: Real-time collaborative document editor

**Build order:** get one keystroke working end-to-end in prod → freeze and test the document format → access control → storage lifecycle → multiple servers → content features → history/search/export → live cursors last.

## 1. Classification
- **What:** A rich-text editor in the browser. Many users edit one document at the same time, see each other's changes live, and keep every confirmed edit, with history.
- **Type:** Software + infra: a real-time distributed system that holds live state on the server. **Not AI or agent-based.** The AI layer doesn't apply, so §6 is left out, as the template says.
- **Dominant constraint:** **Correctness.** Every copy of a document must end up identical, and no confirmed edit may be lost. Latency comes a close second: 95% of keystrokes should reach other screens within 250 ms in the same region.
- **Worst failure:** **Copies drifting apart, or edits vanishing, with no error.** Two people see different documents, or work marked "Saved" disappears. This is worse than an outage because nobody notices. Every phase below adds a guard or a detector for it.

## 2. Tradeoff gates (resolved up front)

| Decision | Default (chosen now) | Flip condition |
|---|---|---|
| **CRDT vs OT** *(the decision everything else depends on: data model, wire format, storage, offline)* | CRDT: **Yjs**, pinned to an exact version, same build on client and server (Node/TS), with the y-prosemirror editor binding. Edits merge in any order, so reconnect, multiple servers and offline stay possible without a rewrite. | We need the server to reject individual edits (e.g., locked sections), or CRDT overhead blows the budgets after compaction (95th-percentile snapshot > 10 MB, or 95th-percentile load > 2 s on real docs). Then switch to server-ordered OT (ShareDB) or prosemirror-collab. |
| Consistency vs availability | **Content favors availability.** Typing never waits on the network, and all copies converge once they've received the same updates. **"Saved" only appears after the edit is committed in Postgres.** **Permissions, sharing and document create/delete favor consistency**: one Postgres primary decides. | We need strict ordering in content (locks, approvals, "claim this item"). Then add a server-ordered side channel for those fields only. Content stays CRDT. |
| Monolith vs services | One codebase and one container image. Phase 0 runs a single process. Phase 4 runs two roles from that image (stateless `api`, stateful `collab`) that deploy independently. | Separate teams own the two roles, or they need separate release schedules. Then split into two services with a versioned internal contract. |
| Sync vs async | The edit path is synchronous: apply → send to other users → batched database write (≤ 50 ms window) → confirm to the sender. Everything derived (search, export, notifications, previews) runs async on a Postgres-backed job queue. | Confirmations get slow because of the database (95th percentile > 250 ms). Then confirm once the edit is in a replicated log (Kafka/Redpanda, acks=all) that drains into Postgres; a confirmation still means the edit is stored. If job-queue lag passes 60 s (95th percentile), move to a dedicated message broker. |
| Build vs buy | **Buy** commodity parts: OIDC login provider, RDS Postgres, S3 + CloudFront, an OpenTelemetry-compatible monitoring backend. **Use open source** for the hard parts: Yjs, y-protocols, ProseMirror/TipTap. **Build** only a thin collaboration server (auth hook, confirm-after-save storage, document ownership, metrics), because that's where the worst failure lives. Never build our own CRDT or editor core. | Shipping fast matters more than control, and no customer needs data kept in a specific region. Then use a hosted Yjs backend (Tiptap Cloud, Liveblocks, y-sweet). Documents stay in Yjs format, so switching either way stays cheap. |
| Source of truth & storage format | An append-only `doc_updates` table of Yjs updates, plus snapshots that are just merged Yjs updates (one format). Yjs garbage collection stays on; history comes from stored snapshots, not from GC-disabled docs that grow forever. Everything else (HTML, text, search index, previews) is derived and can be rebuilt. | The update table bloats the database (vacuum lag, or > 50 GB). Then move log segments and snapshots to S3, with Postgres keeping pointers. |
| Document schema & changes to it | ProseMirror schema v1 with a minimal set of node types, and a `schema_version` per doc. Changes only add things, never remove or rename. Rollout order: every client can display a new node type before anyone can create one. | The product is markdown- or code-first: use CodeMirror 6 + Y.Text instead. A remove/rename change is unavoidable: migrate docs one at a time offline, with editing frozen and a rollback snapshot kept. |
| Topology & document ownership | Clients talk to a server over secure WebSockets (no peer-to-peer). **Each open document has exactly one owner server**: it holds the doc in memory and is the only one writing it to storage. One server until Phase 4. | One document draws more users than a server can handle (~1,000+ concurrent connections). Then add read-only copies fed by the owner. |
| Permission granularity | Roles per document (owner/editor/commenter/viewer), checked when the connection opens by one shared policy function. The server drops edits from users who can't write. Anything needing different permissions than the document body is stored outside it, because you can't check permissions edit by edit inside a CRDT. | Customers need permissions per section. Then make sections separate sub-documents with their own permissions. If that's not acceptable, revisit CRDT vs OT. |
| Can the server read content? | Yes. TLS in transit, KMS encryption at rest (database, S3, backups). That makes server-side compaction, search and export possible. | A target customer segment requires end-to-end encryption. Then offer a separate E2EE workspace mode where the server only relays and stores encrypted data, and compaction, search and export run in the client. Decide before selling to that segment. |
| Tenancy & region | One shared database for all customers. `tenant_id` is on every row, token and log line from the first migration. Single region, multiple availability zones. | A customer contract requires data to stay in a region. Then run separate regional stacks, each tenant pinned to one. This is cheap only because `tenant_id` exists from day 0. |
| (AI) prompt+RAG vs fine-tune | N/A: there's no AI model in the product. | If an AI assistant is pulled forward (§7), settle this and decide what document content may leave our infrastructure first. |
| (AI) hosted API vs self-host | N/A: there's no AI model in the product. | Same as above. |

## 3. Walking skeleton (Phase 0)
- **The one request and response:** Signed-in user A types "hello" into document D. Signed-in user B, on another machine in the same workspace, sees it appear. The edit is stored in Postgres and is still there after a page reload or a server crash.
- **Tiers crossed:**
  1. **Browser:** TipTap (built on ProseMirror) + y-prosemirror + a WebSocket client. The app itself is served from S3/CloudFront.
  2. **Load balancer:** AWS ALB handles TLS and WebSockets. The app pings every 25 s so the ALB's 60 s idle timeout never closes connections.
  3. **App (one Node/TypeScript container):**
     - HTTP: login callback (OIDC), sessions, `POST /docs`, and `POST /docs/:id/ws-token`, which issues a 5-minute token.
     - WebSocket: the token is sent as the first message, never in the URL. The server checks the Origin header and workspace membership, then loads D by replaying `doc_updates`.
     - For each edit it applies the change, **writes it to the database, then sends it to other users**. This order is the simplest correct one; Phase 1 replaces it.
  4. **Postgres (RDS, multiple availability zones, point-in-time recovery on):** tables `tenants`, `users`, `memberships`, `documents`, `doc_updates`.
- **Deployed:**
  - GitHub Actions pipeline: tests → container image tagged with the git commit → migrations → staging → two-browser Playwright smoke test.
  - The **same image** goes to prod on ECS Fargate as a single task. One server is deliberate until Phase 4.
  - All infrastructure is defined in Terraform.
- **Logged:** JSON log lines with tenant, document, connection, hashed user ID, trace ID, message type and size. **Never document content or titles.**
- **Monitored:**
  - **Traces and metrics:** OpenTelemetry traces from the browser through apply, save and send. Metrics: open connections, documents in memory, save time, send time, errors, reconnects. Browser errors are reported too.
  - **Canary:** a synthetic test runs every minute (Checkly with Playwright). Two clients open a test document, A types a random string and B must see it; the time it takes is recorded. Both copies must hash the same, and a reload must still show the string.
  - **Alerting:** if the canary fails, on-call gets paged.
- **Build order inside Phase 0 (widest impact first):** tenant/user/document ID model → `doc_updates` table → login and token handshake → WebSocket edit path → editor UI.

**Exit check:** In prod, two real users on different networks edit D together, and the edit survives a forced crash of the server task. Connections without a valid login, or from another workspace, are refused. The edit's trace and the canary's latency metric show on the dashboard, and one rollback to the previous build has been done.

## 4. Phases (ordered by dependency; within a phase, widest blast radius first)

- **Phase 1: Lock and prove the document format**
  - **Unlocks:** every content feature (they all store into this format), multiple servers (needs proven convergence and safe retries), offline (needs proven resync).
  - **Depends on:** the Phase 0 edit path running in prod.
  - **Tasks:**
    1. **Freeze the storage format (lock it down).** The server saves what the Yjs document reports as new, so re-sent or duplicate updates never create extra rows. The fencing column for multiple servers is *not* added yet; it's a cheap migration in Phase 4.
    2. **Schema v1 and the add-only rule (lock it down).** A CI check fails any schema change that isn't purely additive. The client reports its schema version on connect, and the server tells outdated clients to reload.
    3. **Wire protocol v1 (lock it down).**
       - Message types: the standard Yjs sync messages plus our own `ack`, `auth_refresh` and `reload_required`.
       - The cursor/presence channel and its budget (≤ 10 messages/s per client) are reserved now but built in Phase 7.
       - Versioning: the protocol version is sent on connect, and the current and previous versions are both supported.
       - Hard limits on message size, update size and message rate.
    4. **Confirm only after saving.** New order: apply → send to others → batched write → confirm. The client's Saving… / Saved / Offline indicator reflects real confirmations.
    5. **Prove tasks 1–4.**
       - **Simulation harness:** many simulated clients and a server in one deterministic test, with random but reproducible network faults (delays, reordering, duplicates, drops, partitions, server restarts). It asserts that every copy **and the stored data** end up identical. It goes in alongside task 1 and gates every later change.
       - **Crash tests:** kill the server abruptly and fail over the database while under load. Every confirmed edit must survive.
    6. **Reconnect and local copy.** Reconnect with randomized backoff, then resync by exchanging what each side already has. Keep a copy in the browser's IndexedDB so a crashed tab keeps unconfirmed edits. Refresh the login token over the open connection.
    7. **Per-user undo/redo (small, last).** Undo only reverts your own edits, never a collaborator's.
  - **Exit check:**
    - Simulation: 100k sessions a night with zero divergence, 7 nights in a row.
    - Crashes: 500 random kills and 3 database failovers lose 0 confirmed edits.
    - Latency: 95% of confirmations within 250 ms in prod.
    - Detection: the divergence detector (§5) has run silent for 7 days.

- **Phase 2: Access control & sharing**
  - **Unlocks:** sharing individual documents, outside collaborators, and the commenter/viewer roles that comments, search and presence depend on.
  - **Depends on:** Phase 0 identity and tenancy; the Phase 1 handshake, which carries the role and the close codes.
  - **Tasks:**
    1. **One permission function (lock it down).** `can(user, action, resource)` is shared by HTTP and WebSocket paths. Deny by default; document roles sit on top of workspace membership.
    2. **Enforce on live connections.** The role is fixed per connection. Edits from users without write access are dropped and counted, and their editor switches to read-only.
    3. **Revocation.** A sharing change is written through a transactional outbox and broadcast via Postgres NOTIFY. The server owning the document re-checks open connections and closes or downgrades them within 5 s. If a notification is missed, the 5-minute token expiry catches it.
    4. **Append-only audit log** of every grant and revocation.
    5. **Sharing UI (small, last).** Email invites. Link sharing is off by default and uses long random links that can be revoked.
  - **Exit check:**
    - CI: a generated test matrix (every role × action × HTTP/WebSocket × same/other tenant) passes.
    - Pen test: an external test of the WebSocket path (forged or expired tokens, other tenants' document IDs, cross-site WebSocket hijacking) finds no high-severity issues.
    - Prod: 99% of revocations take effect within 5 s.

- **Phase 3: Storage lifecycle & background jobs**
  - **Unlocks:** fast loading of large or old documents, plus everything derived: history, search, export, notifications.
  - **Depends on:** the frozen Phase 1 format; the Phase 2 permission function (derived data and deletion must respect tenants and permissions).
  - **Tasks:**
    1. **Snapshots and compaction (lock it down).** The owner server writes a full snapshot every 500 updates and when the document closes. It writes the new snapshot first and only then moves the pointer to it. Loading = latest snapshot + later updates. **Keep every snapshot and the full log for now.** The pruning policy is set in Phase 6, once history defines what it needs; lost history can't be recovered and storage is cheap.
    2. **Job queue (simple for now).** graphile-worker on Postgres. Jobs are safe to retry, back off on failure, and land in a dead-letter table if they keep failing. Jobs carry IDs, never content.
    3. **Derived data.** Plain text and JSON per document, rebuildable from the source with one command.
    4. **Deletion that actually deletes.** Soft delete, then hard delete after 30 days, covering updates, snapshots, derived data, files and indexes. Every store added later must plug into this.
    5. **Replay check.** Nightly, rebuild sample documents from the full log and compare them to the latest snapshot.
    6. **Restore drill.** A scripted point-in-time restore to a scratch database that verifies document hashes.
    7. **Size cap.** A document over 25 MB becomes read-only with a banner and an alert, instead of crashing the server.
  - **Exit check:**
    - Load time: 95% of cold loads within 1 s, even for the largest 1% of documents.
    - Replay check: 0 mismatches for 14 days.
    - Restore drill: at most 5 minutes of data lost, back up within 1 hour.
    - Deletion: the test leaves nothing behind.

- **Phase 4: Multiple servers & operations**
  - **Unlocks:** no single point of failure for live documents, deploys without downtime, and known capacity. Features will multiply traffic on the write path, so this is proven before they arrive.
  - **Depends on:** Phase 1 (moving a document to a new server is just a reconnect + resync, already proven); Phase 2 (reconnects re-check permissions); Phase 3 (snapshots make moves fast).
  - **Tasks:**
    1. **Lease plus fencing (lock it down).** Each document has a lease with an `epoch` number that only goes up. Writes check the epoch in the same transaction, so a server that lost ownership can't write.
    2. **Routing.** Envoy routes each document ID to a fixed server (ring hash). That server takes over the lease when it expires or is handed over, and the epoch bump blocks the previous owner.
    3. **Split the `api` and `collab` roles.** Same image, different scaling: CPU for `api`, connections and memory for `collab`.
    4. **Safe deploys.** On shutdown a server stops taking documents, flushes pending writes, snapshots, releases its leases and tells clients to reconnect.
    5. **Database outage.**
       - Stop confirming edits; clients show "Saving…".
       - Keep relaying edits between users in memory for up to 5 minutes or 10 MB per document.
       - After that, switch clients to local-only, with edits kept in IndexedDB.
       - Never show "Saved" falsely.
    6. **Overload protection.** Connection caps per document; rate limits per user, tenant and IP. Disconnect clients that fall more than 4 MB behind (they resync). Cursor traffic is dropped before edits.
    7. **Load test and SLOs.** A Node load generator runs real Yjs clients, sending edits plus cursor traffic at the Phase 1 budget. Use 3 servers, not 30, and keep autoscaling simple until the data says otherwise.
  - **Exit check:**
    - Chaos tests in staging at 2× expected peak: kill an owner server, cut a server off from the database, cut off the router.
    - Under those tests: documents move to a new server within 15 s (95%), with 0 confirmed edits lost, 0 writes accepted from a stale owner, and every document converged.
    - Deploys: 10 prod deploys in a row where users notice nothing but a reconnect of up to 3 s.

- **Phase 5: Content features**
  - **Unlocks:** a usable product: comments, images, tables, mentions.
  - **Depends on:** the Phase 1 schema rule, the Phase 2 commenter role, the Phase 3 queue, the Phase 4 capacity model.
  - **Tasks:**
    1. **Comments (widest impact: new stored data and a new permission boundary).**
       - **Where they live:** ordinary Postgres rows controlled by the server, not CRDT. "Only the author can edit or delete their comment" can't be enforced inside a shared Yjs document.
       - **Anchors:** Yjs relative positions, so they follow the text through concurrent edits. If the anchored text is deleted, the comment shows in the sidebar.
       - **Updates** go out over the existing connection.
    2. **Images and attachments.** Direct-to-S3 uploads using presigned URLs limited to that document and user, with type and size limits and an async malware scan. Documents store asset IDs, not URLs.
    3. **New node types** (tables, code blocks, task lists), each rolled out display-first behind a feature flag.
    4. **Mentions → notifications (small, last).** A background job with duplicate protection.
  - **Exit check:**
    - The simulation harness and the reference file set cover every new node type.
    - Comment anchors survive concurrent edits in simulation.
    - The permission matrix shows commenters can't edit the body or delete others' comments.
    - No file can be fetched without read access to its document.

- **Phase 6: History, search, import & export**
  - **Unlocks:** version history and restore, search, import, export.
  - **Depends on:** Phase 3 snapshots, derived text and queue; the Phase 2 permission function; Phase 5 files (exports embed images) and comment anchors (restore must keep them).
  - **Tasks:**
    1. **Version history and restore (widest impact: writes into live documents).**
       - **Retention, set now:** every snapshot for 24 hours, hourly for 30 days, daily after that; named versions are kept.
       - **Restore is a new edit:** the smallest set of ProseMirror changes, so untouched text and its comments survive.
       - It's credited to whoever restored, can be undone, and never rewrites the log.
    2. **Search** on Postgres full-text search (simple for now). Results are filtered by tenant and permissions at query time, and snippets are generated only after that check.
    3. **Import** (Markdown/HTML/DOCX) runs in an isolated worker with no network and CPU/memory limits. Content goes through the schema, and anything unknown is dropped.
    4. **Export** (Markdown/PDF/DOCX) from a fixed snapshot, delivered through short-lived download links. Smallest impact, since exports can always be regenerated.
  - **Exit check:**
    - Restore: going back to version N produces exactly version N's content, can be undone, and keeps concurrent editors in sync.
    - Search: the permission matrix finds 0 unauthorized results, and 95% of edits are searchable within 60 s.
    - Export: output matches the reference files.

- **Phase 7: Live presence (the flashiest part, so last: nothing is stored and nothing depends on it)**
  - **Unlocks:** live cursors and selections, avatars, "who's here", follow mode.
  - **Depends on:** the Phase 1 reserved channel and budget, Phase 2 identity and roles, the Phase 4 capacity model (cursor traffic was already load-tested), the Phase 5 content model (cursors inside tables).
  - **Tasks:**
    1. **Presence rules.** The server fills in the user's identity from their token. Each message is capped at 1 KB and limited to 10 per second, enforced on the server. Stale entries expire after 30 s.
    2. **Remote cursors and selections** via the y-prosemirror cursor plugin, with a fixed color per user.
    3. **Presence list, avatars, follow mode (small, last).**
  - **Exit check:**
    - Load: 50 people editing one document with cursors on stays within the latency target, and cursor traffic is at most 30% of bandwidth.
    - Security: no faked identities get through.
    - Isolation: turning presence off leaves editing untouched.

## 7. Deliberately deferred
- **Full offline mode** (long offline sessions, creating documents offline, offline login). *Bring forward* when over 5% of editing sessions include a disconnect longer than 2 minutes, or when a field-work customer segment signs. The groundwork already exists: the local copy and resync from Phase 1, local-only mode from Phase 4.
- **Suggestion mode / track changes.** *Bring forward* when it's a top-3 customer request, or when targeting legal or regulated customers.
- **AI writing assistant.** *Bring forward* when the product commits to it, then work through the gates and AI layer first. Document text is **untrusted input**: any collaborator can plant a prompt injection in a shared doc. AI edits should arrive as suggestions a person accepts, which depends on suggestion mode above. It also needs cost and latency budgets per tenant, and a clear limit on what content may leave our infrastructure.
- **End-to-end encrypted workspaces.** *Bring forward* when a signed customer requires the server not to read content (see the gate in §2).
- **Regional stacks / multi-region.** *Bring forward* with the first contract requiring data to stay in a region, or when distance pushes a region's latency past the target.
- **Read-only copies for very large audiences.** *Bring forward* when any document passes ~1,000 concurrent connections.
- **Permissions per section.** *Bring forward* when customer demand is confirmed (see the gate in §2).
- **Native mobile apps** using Yrs (the Rust port of Yjs, which reads and writes the same format). *Bring forward* when mobile web passes 20% of sessions.
- **Rewriting the collaboration server in Rust (Yrs).** *Bring forward* when server event-loop lag passes 50 ms (99th percentile) at target load and adding servers costs more than porting. The reference set of saved documents must load identically before switching.
- **A dedicated message broker instead of the Postgres queue, and OpenSearch instead of Postgres search.** *Bring forward* when queue lag passes 60 s, or search passes 300 ms (both at the 95th percentile).
- **Public API, webhooks, integrations.** *Bring forward* when partners ask; it needs OAuth scopes added to the Phase 2 permission function.
