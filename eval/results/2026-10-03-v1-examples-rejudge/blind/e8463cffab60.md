# Plan: an autonomous agent that triages and fixes GitHub issues

The workspace is empty, so this plan starts from scratch. I've stated my assumptions, and the questions at the end are the ones most likely to change the design.

**Core idea:** Two agents do the work. A cheap, read-only **triager** sorts issues, and a **resolver** writes fixes inside a sandbox. Neither can act on GitHub directly; they can only propose specific, predefined actions. Plain code (a rules check and one component that holds the GitHub credentials) decides what actually happens. Each kind of action earns more freedom as its accuracy is proven, and loses it automatically if accuracy drops. A human approves every merge.

## 1. Scope

**Goals**
- Triage every new issue within minutes: classify it, label it, find duplicates, ask for missing info, route it to owners and catch security reports.
- Resolve a well-scoped subset: answer usage questions, and for bugs and docs, open PRs that pass tests and are ready for review.

**Out of scope for v1:** merging or approving PRs, closing issues on its own, handling security reports in public, and making product decisions on feature requests.

**Assumptions:** GitHub.com, one org with one to a few dozen repos, tests that can run in a container, and a hosted frontier LLM.

## 2. Design principles
1. **Issue text is untrusted input.** Anyone can file an issue, so safety has to come from limiting what the agent can do, not from careful prompt wording.
2. **The LLM proposes; plain code decides.** Agents emit predefined actions with supporting evidence. A policy engine checks them, and only one component (the actuator) holds GitHub credentials.
3. **Freedom is earned per action type.** Each action moves from shadow (logged only) to suggest to act based on measured accuracy, and moves back down automatically when accuracy drops.
4. **Humans always win.** If a human reverts something the agent did, the agent never redoes it. `/agent stop` halts work on an issue. If a human is assigned or opens a linked PR, the agent steps back.
5. **Safe to retry, bounded, no loops.** Every run can be retried without side effects, has budgets (tokens, time, iterations) and ignores events it caused itself.
6. **Fail usefully.** A failed fix attempt still leaves notes on where the bug is and, when it has one, a test that reproduces it.

## 3. Architecture

```
                                Reconciler (sweeps for missed events)
                                  v
GitHub --webhook--> Ingress --> Queue --> Orchestrator --+--> Triage agent
  ^                                                      +--> Resolver agent
  |                                                                |
  |                                                   proposed actions + evidence
  |                                                                v
  +--------- Actuator (sole holder of GitHub token) <------- Policy engine
```
Shared services: Postgres for state and the audit log, pgvector for the issue index, per-repo config, an LLM gateway and tracing.

| Component | Responsibilities |
|---|---|
| Ingress | Verify `X-Hub-Signature-256`, drop repeats using `X-GitHub-Delivery`, ignore the bot's own events, return 2xx right away (GitHub times out after 10 s) and enqueue the event |
| Reconciler | GitHub doesn't retry failed webhook deliveries, so every ~10 min it checks for issues updated since the last check |
| Orchestrator | Durable workflows (Temporal, or a Postgres queue at small scale). One active run per issue. Waits ~2 min after an issue is opened, because authors often edit right after filing. Cancels runs on close or `/agent stop`. Enforces budgets |
| Triage agent | Fast model with read-only tools (issue search, code search, docs, label list); returns a structured decision |
| Resolver agent | Strongest coding model, running in a sandbox; returns a patch plus evidence and never pushes |
| Policy engine | Per-repo autonomy levels, allowed labels, confidence thresholds, protected paths, rate limits, respect for human reversals |
| Actuator | The only component with the GitHub App token. Safe to retry. Edits its own comments instead of posting new ones, using hidden markers (`<!-- issue-agent:triage -->`). Respects GitHub rate limits |
| LLM gateway | Hands out a token per run and enforces that run's budget, so real API keys never enter a sandbox |

**GitHub App permissions:** Issues (read/write), Pull requests (read/write), Contents (read/write), Checks and Actions (read), Metadata (read), plus Projects (read/write) if routing uses Projects. The App deliberately gets **no Workflows or Administration permission**, so it cannot change `.github/workflows/` or branch rules.

**Webhook events:** `issues`, `issue_comment`, `pull_request`, `pull_request_review`, `pull_request_review_comment`, `check_suite` or `workflow_run`, and `installation_repositories`.

## 4. Issue lifecycle

```
opened    -(debounce ~2 min)-> TRIAGING -> TRIAGED
TRIAGED   -> NEEDS_INFO -(author replies)-> TRIAGING
TRIAGED   -> ANSWERED | DUPLICATE_SUGGESTED -(human/author confirms)-> closed
TRIAGED   -> FIX_CANDIDATE -(trigger)-> RESOLVING
RESOLVING -> PR_OPEN <-> ITERATING -> MERGED | REJECTED
RESOLVING -> ATTEMPT_FAILED (notes posted if useful)
any       -> HALTED  on: /agent stop | issue closed | human assignee or linked human PR
```

## 5. Triage pipeline

Plain-code steps run first; the LLM runs second.
1. **Filter:** Skip PRs (both `issue_comment` events and the REST Issues API include them; check the `pull_request` field). Also skip bot authors, locked issues and anything labeled `agent:ignore`.
2. **Parse:** Pull issue-form fields (version, OS, reproduction steps) out directly, without the LLM.
3. **Safety screen:**
   - Spam goes to maintainers for review.
   - Suspected vulnerabilities trigger a private alert to the security owners. Optionally post a template comment pointing to private vulnerability reporting. Never discuss details or attempt a public fix.
4. **Gather context:**
   - Find similar issues using vector search, keyword search and exact matches on error messages or stack traces.
   - Map stack-trace lines to files in the repo, then look up CODEOWNERS for those paths.
   - Note recent related PRs, and use reaction counts as a measure of demand.
5. **Decide:** The LLM returns output in a fixed schema:
   - `type` and `areas` (areas come from a fixed list in config)
   - `priority`, plus which rubric criteria it matched
   - `duplicate_candidates`, each checked one-to-one against the new issue
   - `missing_info`, `summary` and `security_sensitive`
   - `resolvability` (how likely the agent can fix it) with reasons
   - a quote from the issue as evidence for each decision
6. **Confidence:** Don't trust the model's own confidence score. Run the decision 3 times and measure agreement, with thresholds tuned on the evaluation set. When the runs disagree, pass the decision to a stronger model or a human.
7. **Act (every action goes through the policy engine):**
   - **Labels:** only from the configured list.
   - **Duplicates:** comment with links to the candidates and add `possible-duplicate`. No auto-closing in v1.
   - **Incomplete reports:** post one *specific* request (for example, "Which version? Can you paste the full traceback?") and add `needs-info`. Triage again when the author replies.
   - **Routing:** set a Project field, assign someone, or mention area owners (with a cap on mentions).
   - **Questions:** draft an answer based on the docs and code, with links pinned to a specific commit. Start in suggest mode.
   - **Fix candidates:** mark issues that look fixable (`agent:candidate`) so a maintainer can start a fix with one action.
   - **Stale issues:** optionally nudge `needs-info` issues after 14 days. Auto-closing is off by default, because stale bots annoy communities.

**Comment hygiene:**
- At most one triage comment per issue, edited in place.
- Say clearly that the comment is automated.
- Don't comment when labels alone are enough.
- Filter everything the bot posts: length limit, approved link domains only, a cap on mentions, and a scan for secrets.

## 6. Resolution pipeline

**Trigger (v1):** Someone with write access adds `agent:fix` or comments `/agent fix`. Check their actual repo permission through the API; the `author_association` field isn't precise enough. The issue is eligible only if all of these hold:
- It's a bug, a docs change, or a small, well-specified enhancement.
- It isn't security-sensitive and doesn't touch protected paths.
- Nobody is assigned and there's no open PR that references it.
- Budget is available and the repo hasn't hit its cap on open agent PRs.

Automatic triggering comes in a later phase.

**Sandbox:**
- A throwaway container or microVM, built from the repo's devcontainer or Dockerfile and cached by lockfile hash.
- It contains a checkout of the default branch.
- There's no GitHub token and no secrets in it. It reaches the model only through a gateway token issued for that run.
- Network access is off, or limited to an approved package proxy. For private repos the code itself is the sensitive data, so the default is no network.

**Agent loop** (phases adapted from the Agentless and SWE-agent research projects; each step has a limit):
1. **Baseline:** Build the environment and run the tests, noting any that already fail. If the environment won't build, log it as an infrastructure failure, not an agent failure.
2. **Reproduce (bugs):** Restate the issue as acceptance criteria and write a test that fails on the current code. If it can't reproduce the bug, it reports what it tried and adds `needs-info`.
3. **Localize:** Narrow down from stack traces and code search to files, then to functions.
4. **Patch:** Make the smallest change that fits the repo's conventions. Optionally generate 2–3 candidate patches.
5. **Self-check:** The reproduction test passes, the test suite is no worse than baseline, and lint, formatting and type checks pass.
6. **Review:** A separate reviewer agent with a clean context checks for a root-cause fix rather than a symptom patch, edge cases, compatibility and weakened tests.
7. **Return:** A structured result with a status (`fixed | cannot_reproduce | needs_info | gave_up`), the patch, the reproduction test, PR text, a verification log and risks.

**Independent verification (the agent can't influence this step):**
- Apply the patch in a *fresh* sandbox.
- The reproduction test must fail before the patch and pass after it. Tests that passed before must still pass.
- Then run rule checks:
  - protected paths
  - a cap on diff size
  - no new dependencies
  - a secret scan
  - a flag on deleted or skipped tests, or edited assertions in existing tests (the usual ways agents "make tests pass")

**PR:**
- The actuator rebases onto the latest base branch, verifies again, and pushes `agent/issue-123-slug`.
- It opens a **draft** PR containing "Fixes #123", the root cause, the change, the verification commands and results, and the risks.
- It requests review from CODEOWNERS.
- If the repo requires signed commits, create the commits through the GitHub API so they show as verified.

**Iterate:**
- On a CI failure, feed the failing job's logs back to the resolver (up to 3 rounds).
- Respond to review comments only from users with write access (up to 5 rounds). On public repos anyone can comment, so all other comments are treated as information, not instructions.
- Mark the PR ready for review when CI passes. Stop if the PR is closed, someone says `/agent stop`, or the budget runs out.

**On failure:** No PR. If the agent found where the bug lives or wrote a working reproduction test, it posts short notes with the test and adds `agent:attempted`. Otherwise it only logs the attempt.

## 7. Security model

**Threats:**
- Prompt injection hidden in issues and comments
- Malicious reproduction steps (`curl … | bash`)
- Code in a PR that steals CI secrets when its tests run
- Spam issues meant to burn the budget
- Attempts to trick the bot into closing or relabeling legitimate issues
- Private information leaking into public comments

**Controls** (none of them rely on the model behaving well):
- **Separated capabilities:**
  - The triager has no write tools.
  - The resolver can only write inside a sandbox that holds nothing worth stealing.
  - Only the actuator holds credentials, and it only runs actions the policy engine has approved.

  No single part combines private data, untrusted input and an unchecked way to send data out (Simon Willison's "lethal trifecta").
- **Branch protection:** Rules on the default and release branches require a PR and human approval. Turn on "dismiss stale approvals" or "require approval of the most recent push", so anything the agent pushes after approval gets reviewed again. The actuator only ever pushes `agent/*` branches.
- **CI secrets:** Agent PRs come from branches in the same repo, and actions taken with a GitHub App token do trigger workflows. That means **CI runs with your secrets**. Treat agent PRs like PRs from forks: keep secrets out of PR test jobs, or put those jobs behind an environment that needs approval.
- **Who can give instructions:** Only users with write access. Config is read only from the default branch.
- **Separated knowledge:** Runs on public repos can't search private issues or internal docs.
- **Limits:** Rate limits per author and per repo, plus kill switches at the global, repo and issue level.
- **Data handling:** For private repos, check the model provider's data-retention terms.

## 8. Per-repo configuration

```yaml
# .github/issue-agent.yml  (read from default branch only)
autonomy:              # shadow | suggest | act
  labels: act
  duplicates: suggest
  needs_info: act
  answers: suggest
  resolver: on_request # off | on_request | auto
taxonomy:
  type: [bug, feature, question, docs]
  areas:
    area/parser: { paths: ["src/parser/**"], owners: ["@acme/parser"] }
    area/cli:    { paths: ["src/cli/**"],    owners: ["@acme/cli"] }
priority_rubric: .github/triage-rubric.md
resolver:
  setup: pip install -e ".[dev]"
  test: pytest -q
  lint: ruff check .
  protected_paths: [".github/**", "src/auth/**", "migrations/**"]
  max_diff_lines: 300
  max_open_agent_prs: 3
  budget: { minutes: 45, usd: 5, ci_rounds: 3, review_rounds: 5 }
```

- **`AGENT.md`:** A file maintainers own (architecture notes, conventions, gotchas). The resolver reads it on every run and can propose changes only through a PR.
- **Onboarding:** When the App is installed on a repo, it opens a PR with a draft config based on the repo's existing labels, CODEOWNERS and CI files.
- **Maintainer controls:** `/agent fix`, `/agent retriage`, `/agent stop`, and the labels `agent:fix` and `agent:ignore`.

## 9. Evaluation

**Offline (every prompt or model change must pass this first):**
- **Triage test set:**
  - About 12 months of past issues, with labels humans applied as the answer key (labels added by bots excluded).
  - Duplicates taken from issues closed as duplicates (by label, close reason, or a "Duplicate of #N" comment).
  - Plus ~200 issues labeled by hand, because historical labels are sparse and noisy.
- **Fix test set (in the style of the SWE-bench benchmark):**
  - Closed issues that were fixed by merged PRs which added tests.
  - Check out the commit just before the fix. Success means the PR's new tests pass and nothing else breaks.
  - Prefer issues filed after the model's training cutoff, since public fixes may be in its training data. Have a human grade a sample.
- **Shadow runs:** New versions process live events without acting, and their decisions are compared to the current version.

**Online:**
- **Triage:**
  - Accuracy: how often humans remove or change the agent's labels within 7 days.
  - Coverage: labels humans add later that the agent missed.
  - Duplicate acceptance, response rate to `needs-info`, and time to first response.
- **Fixes:**
  - Merge rate, and the share merged without changes.
  - Review rounds, and reverts or follow-up fixes within 30 days.
  - Reviewer minutes per PR, and **cost per merged PR** (not per attempt).

**Promotions and automatic shutoffs (example thresholds; tune per repo):** Move an action to `act` at ≥95% accuracy over ≥200 decisions. Drop back to shadow mode and alert if any of these rolling numbers crosses its threshold: human reversals, comment volume, cost, or CI failure rate on agent PRs.

## 10. Roadmap

| Phase | Build | Done when |
|---|---|---|
| 0. Foundations | App, ingress, queue, reconciler, state store, actuator, audit log and tracing, kill switches, event replay, test sets | A week of live events handled with nothing missed or processed twice (shadow mode only) |
| 1. Triage in shadow, then suggest (one pilot repo) | Classification, areas, duplicates, missing info, security screen, decision dashboard | Offline accuracy targets met; pilot maintainers find the suggestions useful |
| 2. Triage acts | Automatic labels, needs-info and duplicate comments, routing, respect for human reversals, automatic shutoffs | Under 5% of decisions reversed for 2 weeks, with no incidents |
| 3. Fixes on request | Sandbox images, agent loop, independent verification, draft PRs, CI-fix rounds; docs and small bugs first | Offline fix rate and pilot merge rate meet the agreed targets |
| 4. Expand | Responding to reviews, automatic triggers, question answering, a backlog sweep ("does this still reproduce on main?"), more repos, using past accepted decisions as examples | Metrics hold as volume grows |

Auto-merge, even for docs typos, stays off unless phase-4 data makes an overwhelming case for it.

## 11. Stack, and build vs. buy
- **Service:** TypeScript with Octokit, or Python with githubkit or PyGithub.
- **Orchestration:** Temporal; its durable timers suit the post-filing wait and the nudges.
- **Resolver runtime:** Claude Agent SDK (built-in file and shell tools, `PreToolUse` hooks to enforce rules on every tool call, subagents for the reviewer), or OpenHands or SWE-agent.
- **Sandbox:** Docker with gVisor, Firecracker, or a hosted sandbox (E2B, Modal, Daytona).
- **LLM gateway:** LiteLLM proxy (keys with per-key budgets) or an in-house service.
- **Data and observability:** Postgres with pgvector; OpenTelemetry plus an LLM tracing tool.
- **Models:** A small, fast model for triage that escalates when unsure, and the strongest coding model for fixes. Pin versions, and change them only after the offline tests pass.

**Build vs. buy:** Copilot's coding agent, the Claude Code GitHub Action and OpenHands' resolver already turn an issue into a PR when a human triggers them. A practical path is to try fixes with one of them on your repos first. Then build what they don't provide: org-wide triage, the policy engine, the test harness and the metrics.

## 12. Biggest risks
- **Low-quality PRs eating reviewer time** is the most likely way this fails. Mitigations: fixes only on request, verification gates, draft PRs, caps on open PRs, and automatic slowdown when the merge rate falls.
- **Bot noise putting off contributors.** Mitigations: start in shadow mode, use one comment edited in place, never redo what a human reverted, and offer an opt-out label.
- **Environment setup** is the hardest engineering problem. Use devcontainers and cached images, and set aside time for it explicitly.
- **Prompt injection.** Rely on the separated capabilities in §7, not on prompt hardening.

## Open questions
1. How many repos, and how many issues per week?
2. Are the repos public, private or both? This affects exposure to injection, how far the offline tests can be trusted, and how much bot activity the community will tolerate.
3. What languages and test setups do the repos use, and do they have containerized dev environments?
4. What's the ceiling: draft PRs only, or auto-merge one day for narrow cases?
5. Should it be a standalone service, or start on GitHub Actions?
6. Are there limits on which model provider you can use, or on budget?
