# BUILD PLAN — Real-Time Collaborative Document Editor

## 1. Classification and constraints

**What:** A web-based real-time collaborative document editor enabling multiple users to author, edit, and see changes instantly with conflict-free editing.

**Type:** Software (greenfield); small build (typically one team, no external R3 commitment, eventual restricted launch).

**Dominant constraint:** Correctness (conflict-free merge of concurrent edits) and latency (subsecond update propagation). Availability and scale secondary (assume 10–100 users per document, peak 50 concurrent documents).

**Worst failure:** A user loses unsaved changes or sees corrupted text after a merge, breaking trust in the data.

**Budgets:**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Update latency (edit → broadcast → visible) | p99 < 500 ms | ASSUMPTION: typical for collaborative editing; acceptable to users | V1 (synthetic test), V2 (real canary) |
| Throughput (edits/s per document) | 10 edits/s per document (multiple users) | ASSUMPTION: typical concurrent user activity | Phase 1 exit check (load test) |
| Availability / SLO | — | UNKNOWN: business SLO (product owner, before Phase 3); draft: 99.5% (single data center) | SLIs and alerts in Phase 2 |
| RPO / RTO | RPO = 0 (every edit is durable immediately); RTO = 5 min | ASSUMPTION: document recovery on server restart; 5 min acceptable downtime | V3 (durability + failover test) |
| Storage cost | — | UNKNOWN: cost per GB retained (depends on retention policy); baseline after Phase 1 | Phase 3 exit check |
| Operational complexity | One backend service, one database, one WebSocket broker; no cluster | ASSUMPTION: two-person team, hosted on managed platform (AWS, GCP, Heroku, or similar) | Phase 2 exit check |

**Missing inputs and assumptions:**
- **Data retention policy** (how long to keep historical edits and deleted documents): needed by end of Phase 1 to finalize storage budgets; assume 90 days until confirmed.
- **User account model** (authentication, multi-tenancy, document sharing rules): assumed simple (email login, document shared by URL token or list of collaborator emails) until product clarifies.
- **Offline editing** (whether clients edit while disconnected and sync when online): assumed NOT in scope (always-connected model); a change in this would reorder phases 2 and 3.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |

| **CRDT vs OT (conflict-free merge)** | R3: data model and recovery code depend on it; switching after real documents exist breaks history | CRDT (Yjs or Automerge); simpler to reason about, no central authority needed for merge | CRDTs are fast enough for subsecond latency at 10 edits/s per doc | V1 (synthetic merge test: 1000 concurrent edits, p99 < 100 ms) | V1 fails: switch to an OT library (e.g., OT.js) or custom OT logic, re-test; if both fail, re-scope to turn-taking locking |
| **Operation log storage (transactional log vs snapshot + incremental)** | R2/R3: affects recovery time and storage cost; a change mid-use requires backfill | Log-only for Phase 0–1; snapshot + log in Phase 3 if storage grows; snapshots are idempotent recomputes, so reversible if schema stays fixed | Assume documents stay < 1 MB and < 10k operations in Phase 0–1 | V3 (durability test: write 5000 edits, crash, restart, all edits present and correct) | Snapshot query latency degrades or storage cost exceeds budget: add snapshots; log replay time on recovery > 30 s, add snapshots |
| **Sync vs async persistence** | R1/R2: affects latency and throughput but is inside the service | Async: write to memory buffer, broadcast to clients, persist to log within 100 ms (not after client ACK) | Eventual durability is acceptable; crash between ACK and persistence is rare and recoverable from client memory | V2 (latency canary: confirm async write is fast enough) | Async latency exceeds budget (> 500 ms p99) or data loss observed: switch to sync-on-ACK before scaling |
| **Sharing model (URL token vs invite list vs public)** | R3: user expectations and access-control logic; a change breaks existing documents | URL token (one unique token per document, shared via link; no invite list, no login required initially); password-optional for read/write separation | Simplifies Phase 0 (no user identity needed yet); can add login + invite lists in Phase 2 without breaking existing documents if token stays | No gate needed; gate only if rule changes | Users expect accounts + fine-grained permissions: add in Phase 2 as an upgrade; old token links still work |

## 4. Walking skeleton (Phase 0)

**Real request and response:**
- A user (behind a flag, internal only initially) opens a new document.
- Server assigns a unique URL token.
- Client opens a WebSocket to the server.
- User types a character; edit is sent as a JSON message: `{type: "edit", version: 1, change: {pos: 0, text: "A"}}`.
- Server receives, applies to CRDT, broadcasts to all clients (including the sender, for ACK).
- Client receives the same edit back (confirmed), updates the local CRDT, and re-renders.
- A second user's change (in the same document) is merged and broadcast; both see the combined text.
- Connection drops; user types offline (in a browser tab without backend awareness, to avoid blocking the UI). Connection resumes; client sends catch-up request; server replies with missing edits; client merges them in, resolves conflicts, and re-renders.
- User closes the editor; server persists the final document state (edits + CRDT snapshot) to a PostgreSQL table `documents(id, token, content_crdt, version, updated_at)`.
- Server restarts; user reopens the same token; server loads the CRDT from the database and reconstructs the same text.

**Every tier it crosses:**
1. **Client (React app, in-browser CRDT state)** → sends edit message.
2. **Network (WebSocket)** → message delivery.
3. **Server (Node.js / Python, WebSocket handler)** → receives, validates, applies to CRDT.
4. **In-memory CRDT state** → all clients' shared document state.
5. **Database (PostgreSQL, one table)** → durability checkpoint every N edits or after idle timeout.
6. **Logging (structured JSON to stdout)** → each step traced.
7. **Monitoring (metrics only, no alerting yet)** → message count, latency histogram, active connections.

**Deployment, logging, monitoring, and rollback:**
- **Deploy:** One container image (backend + WebSocket server) pushed to a managed platform (AWS ECS, GCP Cloud Run, or Heroku). Database is a managed instance (RDS, Cloud SQL). Client is static HTML+JS served by the backend or a CDN (no build step needed for Phase 0; inline React via JSX or use a pre-built UMD bundle).
- **Logging:** Structured JSON (timestamp, user token, action, duration, error) to stdout; platform captures it. No log aggregation needed yet.
- **Monitoring:** Prometheus-compatible metrics (edits/s, merge time p99, active WebSocket connections) emitted by the server; visualized in a dashboard (free tier of Grafana, or the platform's built-in metrics). **Alert only on catastrophic failure:** if the service is down for > 2 minutes (manual restart, no auto-heal yet).
- **Rollback:** Kill the service, restart the old container image. The database stays unchanged; no schema migration needed, so re-starting the old code re-reads the last persisted state.
- **Who can reach it:** Only internal traffic (e.g., via a VPN or localhost if deployed locally) or with a hard-coded allow-list of 3–5 email addresses. A feature flag in the code determines whether the editor is visible (defaults to off in Phase 0).

**Exit check (V0):**
1. A real edit is typed, broadcast to a second client, and both see the same text.
2. A crash and restart occurs; the document is reconstructed from the database; text matches.
3. A second user's edit is merged with a first user's concurrent edit; text is consistent across both clients and survives a restart.
4. A WebSocket connection is dropped and resumed; client catch-up works and no edits are lost.
5. Logs show a trace (edit timestamp, merge time, broadcast time, render time) for each edit; p99 end-to-end latency is recorded (baseline, not a hard threshold yet).
6. A deploy succeeds through the pipeline and a rollback restores the old code within 1 minute.
7. An injected failure (e.g., database offline) is logged and a manual alert is visible (no auto-response yet).

## 5. Phases (Phase 1 onward; dependency order)

### Phase 1 — Core collaborative editing layer
**Unlocks:** Document sharing with multiple users, conflict-free editing on real documents, and the first tests of latency and merge correctness.

**Depends on:** V0 passes (skeleton runs and is observable).

**Tasks:**
1. **Implement CRDT layer** (Yjs or Automerge): each edit operation, each client integration point, unit tests for merge determinism on synthetic conflict scenarios (100+ concurrent edits).
2. **Version vector / causality tracking** (to detect causal relationships and enable efficient catchup): schema for operation log (document_id, version, client_id, operation, timestamp).
3. **WebSocket message protocol** finalization (what fields, JSON schema validation, error responses).
4. **Server-side operation log** (append-only table in PostgreSQL; writes are synchronous for V0, async-batched later if latency is an issue).
5. **Client catchup logic** (when a client reconnects, request missing edits from version N to current; apply locally; re-render).
6. **Full-document snapshot on idle** (after 5 minutes of inactivity, serialize the CRDT state to a snapshot column to speed up future load).
7. **Document purge on expiration** (if data retention is set to 90 days, add a background job that marks documents as deleted after 90 days; soft-delete only, no hard row removal yet).
8. **Load test** (spawn 100 simulated users on 10 documents, each editing at 1 edit/s, measure latency and throughput; confirm V1 threshold is met or adjust the default).

**Rollback:** None needed within Phase 1; if a task fails, fix or re-plan. Once the phase exits, the database schema and operation log format are considered load-bearing (see V1).

**Exit check:**
- V1 passes (merge correctness on 1000 synthetic concurrent edits, all correctly ordered and deterministic).
- Load test shows p99 latency < 500 ms and throughput >= 10 edits/s per document.
- Operational log entries are traced end-to-end and contain sufficient detail to reconstruct an edit.
- Database schema is documented (columns, types, indices).

---

### Phase 2 — Multi-user and observability hardening
**Unlocks:** Sharing documents with named collaborators, production monitoring, and the first step toward scaling to real users.

**Depends on:** Phase 1, V1 (merge correctness), V2 (latency on real canary traffic).

**Tasks:**
1. **Authentication layer** (simple: email login via a third-party provider like Auth0 or AWS Cognito; or passkey-based, with no server-side password storage). Add a `users` table (id, email_or_identifier, created_at).
2. **Document sharing model** (expand from token-only to an invite list): add a `document_collaborators` table (document_id, user_id, permission); URL token still works for anonymous read-only (backward compatible).
3. **User identity in operation log** (add user_id to each edit operation; enables "undo this user's changes" and audit trails). No backward-compat break: NULL for Phase 1 documents.
4. **Production SLIs** (Service-Level Indicators): measure edit latency, merge time, database query latency, WebSocket connection time, and track success rate (% of edits that are broadcast within 500 ms without error).
5. **Observability hardening**: structured logs (correlation IDs for each edit, user token), metrics dashboards (Grafana or platform-provided: latency histogram, throughput over time, error rate), and distributed tracing (optional; skip if a small team can debug from logs alone).
6. **Error tracking and alerting** (send alerts only on real failures: database connection lost > 30 s, service unhealthy for > 1 min, error rate > 1% for > 5 min). Use a free or cheap tier (e.g., Sentry, or a simple Slack webhook from platform logs).
7. **First (**
 canary rollout** (enable the editor for 10% of internal users; measure real-world latency, error rate, and data correctness for 1 week; compare to baseline). Gate the next phase on this canary's success.
8. **Conflict scenario tests** (add e2e tests: two users edit the same paragraph concurrently, confirm final text is correct and matches both clients' last-known state).

**Rollback:** Database schema is now load-bearing; a rollback requires careful schema migration. In Phase 2, the new columns are nullable and optional, so rolling back the code (not the database) is safe. A schema rollback is deferred to the flip condition of V2 (if latency budget fails).

**Exit check:**
- V2 passes (latency canary at 10% traffic for 1 week shows p99 < 500 ms, no data loss, SLI > 99%).
- SLIs are being reported to a dashboard; alerting is in place (no alert storms; thresholds are reasonable).
- Conflict scenario e2e tests pass.

### Phase 3 — Scale and resilience
**Unlocks:** Public beta (real external users with feedback), performance optimization, and automated failover.

**Depends on:** Phase 2, V2 (10% canary passed), V3 (RPO/RTO test: durability and failover).

**Tasks:**
1. **Snapshot and recovery optimization** (if phase 1 load test showed snapshot query latency is acceptable, snapshot every N edits and on idle; if replay time on restart > 30 s, this is not deferred further).
2. **Read-replica for backups** (add a standby database in the same availability zone; replicate via PostgreSQL streaming replication). Configure automatic failover if primary goes down (managed by the database service or via a custom script; SLO goal: failover within 5 min, no data loss).
3. **Distributed tracing** (if Phase 2 revealed that logs alone are insufficient, add lightweight tracing; sample 10% of requests to trace end-to-end latency across tiers).
4. **Rate limiting and DoS protection** (each token/user can send max 20 edits/s; clients that exceed it are rate-limited for 60 s; monitor for abuse). Gate this behind a flag until Phase 4.
5. **Automated performance regression testing** (add a CI/CD step: before merging, run the load test again; if latency or throughput degrades by > 10%, block the merge and alert the team).
6. **Data export and recovery testing** (document the backup recovery procedure; test a full restore from backup once). Add a recovery runbook.
7. **Expand canary to 50%** of internal users for 1 week; measure again (SLI, error rate, feedback). If all pass, proceed to Phase 4. If latency degrades, identify the cause (e.g., higher user count, data size) and fix before expanding further.
8. **Security review** (code review against OWASP top 10, WebSocket security, CRDT state serialization for injection points, SQL injection in queries). Fix critical issues before Phase 4.

**Rollback:** Failover and rollback are rehearsed before Phase 4; once real users are active, a rollback requires coordinating with users to understand which documents are in flight. Schema changes in Phase 3 are made via expand/contract migrations: old and new code run in parallel, then old code is removed in a later phase.

**Exit check:**
- V3 passes (RPO/RTO test: kill the primary database, confirm failover to the replica occurs within 5 min, no data loss, service is available again).
- Load test at 50% canary shows SLI >= 99%, latency p99 < 500 ms, no new errors.
- Performance regression test passes on the candidate build.
- Security review is complete; all critical and high issues are fixed.
- Recovery runbook is documented and tested (simulated restore from backup succeeds).

### Phase 4 — General availability and optimization
**Unlocks:** Public launch, real revenue (if monetized), and ongoing scaling.

**Depends on:** Phase 3, V3 (RPO/RTO test passed), 50% canary SLI passed, security review passed.

**Tasks:**
1. **Full canary rollout** (100% of internal users for 1 week; measure SLI and collect feedback).
2. **Public launch announcement** (feature flag removed or switched on for all new signups; old users can opt in).
3. **Monitoring and on-call**: SLIs displayed publicly (internal team); on-call rotation for incidents (one person, page on critical alerts).
4. **Feedback loop**: collect user reports of bugs, feature requests, and latency complaints; prioritize the next sprint.
5. **Optional optimizations** (based on Phase 3 data):
   - Compression of operation log (if storage grows > $X/month, compress old entries or archive to cold storage).
   - Client-side CRDT caching (persist local state to IndexedDB to avoid re-downloading on browser refresh).
   - Geographic replication (if users are spread across regions, add a secondary database in another region and replicate; route reads locally for latency).
6. **Monetization** (if applicable): per-document limits, storage quotas, or subscription tiers. Gate this behind a separate feature flag; no charge until explicitly enabled.

**Rollback:** Once real users are live, breaking changes require coordinated communication and a migration plan. New versions must be backward-compatible with in-flight documents. A rollback of the service is possible but requires users to re-authenticate if the session is lost.

**Exit check:**
- 100% canary for 1 week: SLI >= 99%, p99 latency < 500 ms, error rate < 0.1%.
- On-call page was not triggered (no incidents, or incidents were handled gracefully).
- Public launch announcement was sent; adoption and feedback are being tracked.

## 10. Deliberately deferred

- **Offline editing** (client edits while disconnected, syncs when reconnected): pulled forward if product feedback shows users need it. Adds client-side IndexedDB persistence and a more complex reconciliation logic (detect edits made offline vs edits from other users during disconnection); estimated 2–3 weeks of work.
- **Rich-text formatting** (bold, italic, bullet lists, headings): deferred until Phase 4. Phase 0–3 support plain text only. Pulled forward if user testing shows plain text is too limiting; requires extending the CRDT to handle format metadata and client-side editor to support formatting UI.
- **Real-time voice/video chat** in the editor: not in scope (out-of-band, use third-party Zoom/Jitsi link). Pulled forward if product defines a collaboration requirement that includes embedded voice chat; adds a WebRTC broker and licensing costs.
- **Geographic replication** (documents replicated across continents for low-latency reads): deferred to Phase 4 (Phase 3 has a local read replica only). Pulled forward if adoption metrics show users in multiple time zones with latency complaints; requires cross-region replication, conflict resolution on updates, and monitoring of replication lag.
- **GDPR data deletion and export** (right to be forgotten, data portability): deferred until a user with personal data is in the system. Pulled forward by product/legal if personal data (e.g., email, document names) is required earlier; adds a data-subject-request workflow and a secure deletion procedure.
- **Monetization** (subscriptions, per-document limits, storage quotas): deferred to Phase 4 post-launch. Pulled forward if business model requires a trial or freemium tier before launch; adds billing integration and quota enforcement.
