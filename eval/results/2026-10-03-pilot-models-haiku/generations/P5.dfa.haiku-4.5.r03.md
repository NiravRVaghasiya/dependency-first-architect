# BUILD PLAN — Real-Time Collaborative Document Editor

## 1. Classification and constraints

**What:** A multi-user real-time document editor where changes propagate instantly across all clients, including concurrent edits, presence indicators, and version history.

**Type:** Software (frontend, backend, infrastructure); greenfield; medium build (2–3 small teams, coordinated components, external availability requirement).

**Dominant constraint:** Correctness (conflict-free merge under concurrent edits; no data loss); availability (users expect synchronous feedback); latency (edit propagation < 500 ms to feel real-time).

**Worst failure:** Concurrent edits producing corrupted document state (lost content, merged incorrectly, irreconcilable divergence), not recoverable from history.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| **Conflict-free algorithm: OT vs CRDT** | R3 (months rework; integration, undo, compaction differ; affects all downstream code & client logic) | CRDT (Yjs or Automerge) | OT (Operational Transform) easier to understand but undo/redo and offline-first are simpler with CRDT; Yjs has proven single-room scaling | V1 (spike on real conflict scenarios with each; measure latency, code complexity, test undo/redo) | V1 fails on latency > 200 ms, or undo unreliable after 3+ concurrent edits, → try OT; or implementation cost > 4 weeks → reconsider; or single-user workload only → simplify |
| **Sync model: operational log vs snapshot + delta** | R2 (weeks of data migration; reshapes persistence & join logic) | Snapshot + operation delta (initial state as full doc, then apply operations; compact by rewriting snapshot when log grows past threshold) | Operational log (replay all ops on join) simpler architecture but join latency grows with doc age; snapshots trade complexity for join speed | V2 (load test with doc > 10k ops: join latency, memory per client, snapshot read + apply time) | V2 fails threshold (join > 2 s) → full snapshot on every join; or memory cost > budget → smaller snapshots more often |
| **Presence (cursors, awareness) in merge log or separate channel?** | R2 (affects client subscription, merge handling, compaction strategy) | Separate ephemeral channel (WebSocket message, not logged) | Presence in the operation log means undo/redo affects presence (confusing); ephemeral simpler but requires explicit re-broadcast on join and no history | (Design review + spike: 1 week code, test 20 concurrent users with presence) | Presence becomes a requirement for undo/redo → merge into ops log and redesign; or operational log grows too large → move presence out |
| **Persistence: single-writer (append-only) vs optimistic lock-then-merge** | R3 (changes audit trail structure, affects conflict resolution on server, RPO model) | Single-writer pattern (one thread/process serializes all incoming edits, appends to log, broadcasts) | Locking introduces latency spikes and deadlock risk; single-writer proven simpler for CRDT, no merge-on-persist | (Spike: implement both, compare p99 latency and queueing behavior under 50 concurrent clients; operational log confirms no dropped edits) | Latency > 300 ms or log replay reveals missed edits → switch to async merge + reconciliation check (V3) |
| **State sharing: in-memory index vs replay from log on each join** | R2 (affects startup time, memory cost, recovery design) | In-memory index (keep a "live" merged state server-side; on join, send snapshot + log tail; on edit, update index + append log) | Replay-from-log (stateless) avoids index divergence but join time grows; index divergence is the risk, mitigated by V3 checkpoint test | V3 (checkpoint + crash recovery test: after 1,000 ops, crash server, verify replay matches index state) | Index and replay diverge by > 1 op → rebuild index from log periodically; or join latency unacceptable → caching layer |
| **Broadcasting: fanout (server to each client) vs hub (server is bottleneck) vs tree** | R1 (latency tuning; reversible in days) | Hub (server queues edits, broadcasts to all clients; simple, single point of order) | Fanout (each client broadcasts to peers, server acks) is lower latency but harder to order and audit; tree topology (server delegates to client relays) is premature optimization | (Load test Phase 1: 50 clients, 10 edits/sec/client, measure p99 server queue depth and broadcast latency; if hub bottleneck rises above 100 ms, fanout spike) | Hub queue depth > 1 s at projected load → fanout or add broker tier; or fanout loses edits under network split → hub + broker |
| **Broker technology: Redis Pub/Sub vs Kafka vs RabbitMQ** | R1 (replaceable in days; use interface) | Redis Pub/Sub (simple, in-memory, low latency for single-room; no durability) | Kafka (ordered, persistent, scales to many docs) complex for single room; RabbitMQ middle ground | (Phase 1 spike: latency under 50 concurrent, replay from log test; if durability needed, swap to Kafka / RabbitMQ) | Phase 2 load test shows > 200 ms latency → persist in broker; or room > 10k concurrent → multi-topic sharding |

**R1 defaults:** Monolith backend (frontend + API + websocket in one service) → services only if backend hits single-point scaling limits in Phase 4; IndexedDB for offline state → switch to Dexie or Wasm SQLite if queries become complex; TypeScript frontend (Svelte or React) → framework picked after Phase 0 skeleton.

**N/A:**
- Build vs buy: a collaborative platform is complex; build required for custom UX and data residency control.
- Tenancy/multi-user model: single document, single organization initially; multi-tenant added in deferred work.
- Consistency model (strong vs eventual): editorial document is read-repair safe but requires conflict-free merge (CRDT/OT, a main R3 decision, above).

## 4. Walking skeleton (Phase 0)

**The real request and response:**
1. **Client 1 types "Hello" at position 0** in a shared document; WebSocket sends `{ op: "insert", pos: 0, text: "Hello", id: "user1", clock: 1 }`.
2. **Server receives, appends to log**, broadcasts to all connected clients.
3. **Client 2 (joined earlier) receives and applies** the operation to its local state; display updates.
4. **Client 1 receives ACK** (operation confirmed written); cursor shows "saved" state.
5. **Both clients' document text matches** after the operation (conflict-free).

**Every tier it crosses:**
- **Client 1 (browser):** local CRDT state (Yjs doc), WebSocket connection, IndexedDB for offline cache.
- **Network:** TLS WebSocket tunnel.
- **Backend (Node.js):** HTTP API (join/leave), WebSocket handler, CRDT state machine (Yjs server), operation log (in-memory for now).
- **Message broker (Redis Pub/Sub):** fanout operation to all subscribers on the room channel.
- **Persistence:** in-memory operation log (no database yet); no durability.
- **Client 2 (browser):** receives operation, applies to Yjs doc, re-renders.

**Deployment, logging, monitoring, rollback on day zero:**
- **Deploy:** Single backend container (Node.js + Redis) and client bundle via CDN or static server; managed with Docker Compose locally, helm chart stub for production-ready runbook.
- **Who can reach:** Internal users only; feature flag `editor.enabled = false` (off by default); allow-listed email domains (engineering team).
- **Logging:** console + structured JSON logs to stdout (backend); client-side errors sent to backend `/logs` endpoint (in-memory buffer, printed on exit); no external log aggregation yet.
- **Monitoring:** Grafana with Prometheus scrape (backend exports `edits_received`, `clients_connected`, `broadcast_latency_ms`); alert if `clients_connected == 0` (service down).
- **Rollback:** Kill backend container; clients reconnect to fallback (no-op, document read-only); manual restart of server restores state from in-memory log (no persistence yet, so state lost; acceptable for internal spike).

**Exit check (V0):** 
- Two internal users open the skeleton in browsers, both edit the same document, and both see the other's edit within 500 ms.
- One edit is ACK'd, written to the in-memory log, and visible on a third browser after reload (verifies single-writer and fanout).
- Server logs show one complete trace per request (client ID, operation, timestamp, broadcast latency).
- Prometheus metrics show `edits_received=2`, `clients_connected=2`; injected failure (kill backend) triggers alert and metrics drop.
- Rollback: stop server, restart, clients rejoin; state reset (expected).

### Phase 2 — Real database persistence & multi-room isolation

**Unlocks:** Production-ready durability; audit trail; ability to scale to many documents in parallel; read access to history.

**Depends on:** Phase 1 (V1, V2 pass); no new validation gates to pass before hardening, but operational design must handle transaction failures (see cross-cutting).

**Tasks:**
1. **Implement database layer:** Use PostgreSQL (ACID transactions, JSON columns for operations, proven at scale). Schema: `documents (id, name, created_at)`, `operations (id, doc_id, vector_clock, user_id, text, position, created_at)`, `snapshots (id, doc_id, version, state (JSONB), created_at)`. Each document is a separate stream; multi-room isolation by partition key.
   - **Evidence:** Schema definition, migration scripts, indexes (doc_id, created_at for range queries).
2. **Refactor persistence:** Operations are durably written to the database before ACK to client (satisfies RPO < 1 op). On server restart, load latest snapshot + operation tail from DB. Measure join latency for doc with 100k ops; target < 2 s (V2 tested at 50k; Phase 2 validates at 100k).
   - **Evidence:** Load test at 100k ops, join latency histogram.
3. **Implement optimistic locking on snapshot writes:** Multiple servers may compact simultaneously; use `version` column + CAS (compare-and-swap) to avoid double-writes. If CAS fails, retry load latest snapshot + recompute tail; verify no ops lost (transaction test).
   - **Evidence:** Concurrent snapshot test (5 servers, 10 simultaneous snapshot triggers → no duplicates, no missing ops).
4. **Add read path (API):** `GET /rooms/{room_id}/operations?from_clock=0` returns operation batch (paginated, 1000 ops per page). Used by offline clients to rebuild state. Audit trail accessible via `GET /rooms/{room_id}/history`.
   - **Evidence:** API tests, latency under load (p95 < 500 ms for 10k op query).
5. **Implement database connection pooling & resilience:** PgBouncer or application-level pool (connection limit per server, retry on transient errors, circuit breaker if DB unavailable). If DB goes down, clients can still read from in-memory index (eventual consistency mode); writes queue locally until DB comes back (no data loss if write buffer persisted locally).
   - **Evidence:** Resilience test (kill DB connection, verify writes queue; restart DB, verify flush and no reorders).
6. **Update audit log to database:** Audit entries written to PostgreSQL `audit_log` table (separate to allow TTL-based cleanup). Include result hash for each operation; audit dashboard queries this table to show change history.
   - **Evidence:** Audit table schema, TTL cleanup script, dashboard queries.

**Rollback:** Revert to Phase 1 (in-memory persistence); existing rooms stay active on old server; new joins redirect to fallback (document read-only). Phase 2 DB schema is separate from business DB (TBD in later phases); no production data at risk.

**Exit check:**
- Load test: 50 concurrent clients, 20 edits/sec total, for 1 minute. All edits durable in DB; no duplicates, no loss; replay from DB matches in-memory state.
- Failover test: kill DB, verify write queue; restart DB, verify recovery and no reorders.
- Audit table populated correctly; no sensitive data (user email OK, document content NOT in audit if classified).

### Phase 3 — Offline-first client & conflict resolution UX

**Unlocks:** Users can edit offline; changes sync when reconnected; conflicts shown and resolvable via UI; no lost work.

**Depends on:** Phase 2 (V2 database validation passes); no new validation gates; but UX design must be user-tested (see deferred work: formal UX testing deferred to Phase 4 or post-launch).

**Tasks:**
1. **Implement offline-first client state (IndexedDB):** Yjs client syncs with server over WebSocket. When offline (network unavailable detected via `navigator.onoffline` or socket timeout), local edits are applied to local CRDT copy and stored in IndexedDB. When back online, Yjs performs automatic CRDR merge; server receives all pending operations, applies them, and broadcasts result.
   - **Evidence:** IndexedDB schema, offline detection + reconnection test (5 offline clients, 10 edits each, reconnect, verify all 50 ops merged and visible on all clients).
2. **Add conflict visualization (optional for V1):** When two users edit the same position concurrently, the CRDT merge is conflict-free (no choice needed), but the UX can highlight "concurrent edits here" with different colors per user. Implement as client-side annotation layer; no server involvement.
   - **Evidence:** Spike demo (concurrent editing side-by-side, color annotation visible).
3. **Implement local undo/redo on offline state:** Client-side undo affects only local CRDT; redo restores it. When synced, the server's undo/redo is separate (gated by Phase 3 exit check).
   - **Evidence:** Offline undo test (edit, go offline, undo, verify local state; back online, verify sync doesn't re-apply undone edit).
4. **Update observability for offline:** Client logs `offline_duration_sec`, `pending_ops_count`, `merge_time_ms` on reconnect. Backend logs `sync_batch_size`, `merge_time_ms` for batches from offline clients.
   - **Evidence:** Grafana dashboard for offline metrics.
5. **Test at scale:** Spawn 20 simulated clients, 5 go offline for 30 sec, edit 10 times each offline, reconnect. Verify all 50 ops merged, no duplicates, no loss, merge time < 500 ms. Latency from any client < 2 s after sync completes.
   - **Evidence:** Load test report (offline reconnection latency histogram, merge correctness).

**Rollback:** Disable IndexedDB persistence (feature flag `offline.enabled = false`); users see "offline" message, document read-only. Phase 3 code does not affect on-line path; no rollback required.

**Exit check:**
- V3 checkpoint test: 1,000 operations in a document, crash server mid-operation, restart, verify from-disk recovery matches in-memory state before crash (no ops lost, no corruption).
- Offline merge test: 20 clients offline, 10 edits each, reconnect, all 200 ops applied, visible on all clients, no duplicates or loss, merge time < 500 ms.

### Phase 4 — Scaling, observability, and hardening

**Unlocks:** Multi-document sharding; per-user quotas; production-grade SLOs; chaos testing.

**Depends on:** Phase 3 (V3 passes); Phase 2 (database persistence validated); throughput target UNKNOWN (must be provided by product owner before this phase, or use ASSUMPTION 1,000 edits/s).

**Tasks:**
1. **Implement multi-document sharding:** Backend scales horizontally: use consistent hashing (or Redis cluster) to shard rooms by document ID. Update observability: track operations per shard, load distribution, rebalancing.
   - **Evidence:** Sharding design doc, load distribution test (200 concurrent documents, 5 operations/sec each, verify even distribution and < 500 ms latency per doc).

   - **Evidence:** Quota enforcement tests (exceed limits, verify rejections and alerts).
3. **Run load test (V2 revisited for multi-doc):** Scale to 1,000 edits/sec across 200 documents, 50 concurrent users. Measure: p99 latency (target < 500 ms), availability (target 99.5%), resource use (RAM, CPU per shard). If availability < 99.5%, implement circuit breaker and request queuing. If latency > 500 ms, implement adaptive sharding (smaller shards or more replicas).
   - **Evidence:** Load test report, SLI dashboard screenshots, scaling analysis.
4. **Implement SLI tracking & alerting:** Measure latency (p50, p95, p99 of operation round-trip), availability (% of requests succeeding), error rate. Define error budget: if SLO = 99.5%, allow 0.5% * 30 days = 216 minutes of downtime per month. Alerts: latency > 1 s, error rate > 1%, availability < 99.5%.
   - **Evidence:** Alert rules (Prometheus), dashboard, SLI definition doc.
5. **Run chaos test:** Randomly kill backend instances, fail database, lose messages in broker. Verify: client reconnects within 10 s, no edit is lost, server recovers within 5 min. Test rollback: kill new version, old version serves requests.
   - **Evidence:** Chaos test report (scenario, outcome, recovery time), video recording if possible.
6. **Security: add rate limiting per IP:** Prevent brute-force or spam attacks on WebSocket connections. Rate limit: 100 connections per IP per minute.
   - **Evidence:** Rate-limiting test (exceed limit, verify rejections).
7. **Compliance audit:** If user data contains email, names, or regulated content, verify GDPR/data residency compliance (organizational dependency, likely Phase 4 or deferred pending data classification).

**Rollback:** Disable sharding (feature flag `sharding.enabled = false`); route all rooms to primary shard (single-shard mode). Scale down to Phase 3 capacity (50 concurrent users per document). No production data at risk; rollback takes < 5 min.

**Exit check:**
- Load test (V2): 1,000 edits/sec across 200 documents, p99 latency < 500 ms, availability 99.5%, no data loss.
- Chaos test: all failure scenarios recover within threshold (client rejoin < 10 s, server recovery < 5 min, no edits lost).
- SLI dashboard live; alerts configured and tested.
- Security: rate limiting deployed and tested.

## 10. Deliberately deferred

- **Multi-user authentication and authorization:** Phase 0–4 assume internal allow-listed users. Add OAuth2 (or OpenID Connect) integration, role-based access control (RBAC: owner, editor, commenter, viewer), and team isolation in Phase 5 (pull condition: when a second organization requests access).
- **Document-level permissions (fine-grained):** Currently, all users on a document can read and edit. Add per-user role (read-only, suggest, full edit) in Phase 5 (pull: when product requests view-only collaboration).
- **AI-powered suggestions:** Spell-check, grammar suggestions, or auto-complete using a language model. Not started; pull condition: product prioritizes this feature and provides model budget.
- **Multi-language support (i18n):** UI currently English only. Add i18n framework and translate in Phase 5 or post-launch (pull: when non-English users onboard).
- **Compliance audit for regulated data:** If user documents contain PII, health records, or other regulated content, a formal compliance review (HIPAA, GDPR, SOC 2) is needed. Deferred pending data classification (see Missing inputs, §1); pull condition: data classification provided and classified as regulated.
- **Undo/redo server-side history:** Currently, undo/redo is client-side only. Add a server-side undo stack (per user, per document) in Phase 4 if UX testing shows users want to undo edits after reconnection (phase 4 UX testing deferred to post-launch spike).
- **Version branching (edit branches):** Allow a user to branch a document and merge changes later. Complex CRDT merge; deferred to Phase 5+ (pull: product defines merge semantics and UX).
- **Comments and annotations:** Add a comment thread layer (separate from edits, but references text ranges). Deferred to Phase 5 (pull: product prioritizes collaborative review).
- **Real-time presence (beyond cursors):** Show which user is typing where, last active time. Cursors in Phase 0–1; full presence (activity heatmap) in Phase 5 if product requests.
