Walking skeleton (Phase 0)\n\n**Real request:** A human files a GitHub issue in a test repo: *\"Login button broken on iOS Safari, v2.1.\"*\n\n**Real response:** Within 30 s, the agent posts a triage suggestion comment: *\"🤖 Suggested labels: `bug`, `mobile`, `ios-safari`. Severity: high (blocks login flow). Tentative assignment: [@ios-team](https://github.com/ios-team). Related: #42, #51.\"* The suggestion is read-only; no labels are set. Trace through every tier:\n\n1. **GitHub API (webhook ingress):** Issue created webhook fires → HMAC-verified → event queued to serverless function.\n2. **Serverless function (entrypoint):** Validates webhook, enqueues job, returns 200 within 1 s.\n3. **Prompt-injection / guardrail defense (inline):** Issue title and body extracted; treated as untrusted data. Injection suite (planted jailbreak strings, SQL, shell escapes, tool-call escapes) runs on the text in CI; no malicious string reaches the model.\n4. **Embedding & retrieval (vectorstore):** Past 10 issues chunked, embedded (local embeddings, not on user input yet), stored; for this request, retrieval fetches top-3 similar issues (no retrieval on user input in Phase 0, only schema verified). Retrieval latency < 500 ms.\n5. **Model API call (inference):** Prompt sent to hosted Claude API with token cap (2,000 tokens in, hard stop at 4,000 out), tool-call cap (max 5 calls), timeout 20 s. Response: structured JSON (labels array, severity, owner suggestion, related-issue IDs). Cost metered.\n6. **Tool allowlist (write guard):** Response parsed; all tool calls validated against allowlist: \\[`retrieve_issue`, `retrieve_pr`, `post_comment`\\]. Tool call to `post_comment` with suggested labels and assignment (no label-set mutation, comment only). Arguments sanitized: no inline code, no HTML, no markdown that GitHub will render as code execution.\n7. **GitHub API (response egress):** Comment posted: *\"🤖 Suggested…\"* with no edits to issue state (no label set, no assignee mutated). Timestamp and cost logged.\n8. **Observability (logging & trace):** Every step traced: webhook arrival, validation pass/fail, retrieval hits, model call (tokens in/out, cost), tool call (name, arguments, result, auth check result), final comment ID. Trace ID = webhook delivery ID.\n9. **Monitoring:** Latency: 2.3 s end-to-end (webhook ingress + retrieval + model + post). Cost: $0.008 (156 input tokens + 87 output tokens). Injected failure: seed jailbreak in issue title → injection suite fires in CI (pass); model call returns no tool calls (blocked by injection logic, not filtering); no state mutation (pass).\n10. **Rollback:** Function can be reverted to a no-op (deleted, or feature flag off); webhook deliveries can be manually replayed or skipped. Prior triage suggestion comments can be deleted if the function is reverted before another issue lands.\n\n**Who can reach it:** Internal repo with allow-listed GitHub org members only (GitHub actions token scoped to this repo). No real user data. Suggestion is read-only (no mutations except the comment itself).\n\n**Exit check V0:** \n- ✓ Real issue created, webhook fired, agent suggests triage in < 30 s, comment posted.\n- ✓ Trace (webhook ID → function call ID → model call ID → comment ID) complete in logs.\n- ✓ Deploy (push code → action runs → function deployed) succeeds; rollback (revert + redeploy or delete route) succeeds.\n- ✓ Injected failure (jailbreak string in issue title) fires test alert in CI (injection not reached model).\n- ✓ Baseline recorded: latency < 3 s, cost < $0.01, no tool-call violations.\n\n---\n\n### 5. Phases (Phase 1 onward; dependency order)\n\n**Phase 1 — Retrieval & triage suggestions (read-only expansion)**\n\n- **Unlocks:** Cost validation (V1); canary triage on real repo; multi-repo skeleton.\n- **Depends on:** Phase 0 (V0 passes); V1 cost threshold to be checked at Phase 2.\n- **Tasks:**\n  1. Embed repository context: README, issue templates, past 100 issues (chunked by function/file/author), PR history (commit messages, review patterns).\n  2. Finalize retrieval index: Supabase pgvector or Pinecone; embedding model (e.g., text-embedding-3-small); chunk size (500–1000 tokens); metadata schema (repo, issue ID, date, author).\n  3. Expand model prompt: few-shot examples of good triage (labels, severity, assignment, related links). Inject current labels and prior-issue context into each model call.\n  4. Triage suggestion rules (non-generative fallback): If issue title matches regex (e.g., \"crash\", \"hang\", \"memory leak\"), force `severity: critical`; if no repo context retrieved, suggest `needs-info`.\n  5. Webhook routing: Scale to multiple repos (same function, repo ID in payload). Retrieve context per repo.\n  6. Cost metering: Log tokens-in, tokens-out, API cost per request; aggregate cost-per-issue.\n\n- **Rollback:** Revert retrieval index + re-seed old schema; disable webhook on new repos.\n- **Exit check:**\n  - Retrieval hits the target repo context (top-5 results include relevant past issues) on ≥ 90% of 50 test queries (V2 acceptance threshold).\n  - Cost baseline: mean $0.006/issue (ASSUMPTION), measured on 200 issues from test repo.\n  - No unauthorized mutations; all 200 test issues show comment-only suggestion, no label/assignee change.\n  - Latency: p95 < 12 s (includes webhook delay + function cold start).\n\n**Phase 2 — Human-in-the-loop fix suggestions & approval gating**\n\n- **Unlocks:** Confidence to allow auto-label & auto-assign (Phase 3); cost budget validated (V1 passes); feedback loop (Phase 4).\n- **Depends on:** Phase 1 exit check + V1 (cost per issue < budget); V3 (injection containment confirmed); Phase 0 exit check (rollback tested).\n- **Tasks:**\n  1. Extend model prompt: given issue description, repo context, and related code snippets, suggest a fix (in code, not prose). Response: structured JSON (file path, change rationale, code block, test or manual repro steps).\n  2. Schema for fix suggestions: store in GitHub as draft-PR comment (no merge, no commit yet) or as a separate Markdown document in a gist. Draft PR stays local to the function; final PR is human-triggered.\n  3. Approval workflow: two models—(a) auto-label & auto-assign low-confidence issues (< 50% confidence of severity) requires no human review; (b) code fix suggestions are comment-only (human reviews, optionally uses `/approve-fix` command in comment to trigger a draft PR).\n  4. Sensitive repo rules: skip triage for private repos with `security-sensitive` label; skip code-fix suggestions for issues tagged `security`.\n  5. Test on canary: deploy to 1–2 real (internal) repos; run Phase 1 exit check again on each; measure cost-per-issue, time-to-first-fix-suggestion, human approval rate.\n  6. Feedback schema: humans can thumb-up/down a suggestion or post `/reject <reason>` comment; log feedback in a separate table (repo, issue ID, suggestion ID, feedback, timestamp).\n\n- **Rollback:** Disable fix-suggestion prompt; revert to Phase 1 (triage-only).\n- **Point of no return:** Once real PRs are drafted or merged (Phase 3), reverting this phase requires a PR undo. Gate this with V3 passing (no tool-call violations, no injections succeed) + Phase 2 exit check (human approval workflow tested).\n- **Exit check:**\n  - V3 passes: injection suite run in CI on 100 planted jailbreak strings in issue bodies; none escape the tool allowlist or reach unapproved write operations.\n  - Cost per issue + cost per fix suggestion on canary: < $0.15 / issue (ASSUMPTION, includes failed fix attempts).\n  - Human approval rate: on 50 auto-suggested fixes, ≥ 80% are reviewed within 24 h (cadence check, not correctness yet).\n  - No unauthorized writes: audit 100 issues; all changes are comments, labels, assignments, or draft-PR creation (no merges, no force-pushes, no deletes).\n\n**Phase 3 — Auto-label, auto-assign, & feedback iteration**\n\n- **Unlocks:** Confidence to enable auto-merge on safe changes (Phase 4, optional); multi-repo rollout strategy.\n- **Depends on:** Phase 2 exit check + V1 (cost validated); Phase 0 exit check (rollback practiced).\n- **Tasks:**\n  1. Enable auto-label and auto-assign: for issues where model confidence > 70% and labels are in the allow-list (e.g., `bug`, `feature`, `docs`, `stale`), set labels immediately. For assignment, suggest only; do not auto-assign.\n  2. Draft-PR creation: when human approves a fix suggestion (via comment or GitHub API), draft a PR (opened, not merged; reviewers set to code owners).\n  3. Feedback loop: aggregate human feedback (thumbs, `/reject` comments) into a structured table. Weekly: recompute triage accuracy (precision, recall per label). Use feedback to adjust model prompt or retriever weights.\n  4. Cost optimization: evaluate faster/cheaper models (e.g., GPT-3.5, Llama) for low-risk triage; route only high-risk issues to more expensive model. Measure cost reduction and quality regression.\n  5. Multi-repo rollout: enable on 3–5 internal repos; measure cost, latency, and approval rate on each. Use metrics to size infrastructure (function concurrency, vectorstore read replicas).\n  6. Performance dashboard: plot triage accuracy, cost-per-issue, auto-assign rate, and PR draft rate over time; alert on regressions.\n\n- **Rollback:** Disable auto-label and auto-assign; revert to Phase 2 (suggestion-only).\n- **Exit check:**\n  - Triage accuracy on feedback set: precision ≥ 0.85, recall ≥ 0.80 per label (measured on 500 issues from canary repos).\n  - Cost per issue < budget ($0.15 per issue, including failed fix attempts); cost per resolved issue (issue closed + fix merged or manual action) < $1.00 (UNKNOWN baseline until Phase 3 exit).\n  - Auto-label correctness: human reviews 100 auto-labeled issues; none are mislabeled (accept all or none; if rejects > 5, revisit prompt).\n  - PR draft quality: on 50 drafted PRs, human review finds ≥ 80% are buildable and logically sound (no compile errors, no obvious logic bugs).\n\n**Phase 4 — Auto-merge (safe changes only) & external rollout**\n\n- **Unlocks:** GitHub Actions automation for simple fixes (e.g., lint, format, dependency updates); candidate for public beta (Phase 5).\n- **Depends on:** Phase 3 exit check + V4 (cost per resolved issue < human cost); repository has CI/CD (tests must pass before merge).\n- **Tasks:**\n  1. Auto-merge policy: draft PR is auto-merged only if (a) PR checks pass (CI/CD green), (b) code review by a code owner is added via a GitHub Action bot, and (c) the change is low-risk (e.g., dependency update, lint fix, documentation—no logic change to production code).\n  2. Audit log: every auto-merge is logged (PR URL, change summary, cost, model version, approver bot version). Rollback (revert commit) can be triggered by any maintainer within 24 h.\n  3. Safety rails: block auto-merge if the PR touches (a) authentication/auth layer, (b) payment/billing code, (c) data-deletion code, or (d) any file with a manual `no-auto-merge` tag.\n  4. Cost per resolved issue: meter the cost of issues that are fully resolved (closed with a merged fix, not just labeled or commented). Validate V4 on canary.\n  5. External repo pilot: select 2–3 open-source or internal projects; enable read-only triage + fix suggestions; measure adoption (% issues receiving suggestions, % humans engaging with suggestions).\n  6. Human escalation: if a fix suggestion requires context the agent cannot access (e.g., \"ask the team lead\"), post a comment asking for context; if not provided in 48 h, close the suggestion.\n\n- **Rollback:** Disable auto-merge; all PRs remain drafts and require manual merge.\n- **Point of no return:** Once merges start, a rollback cannot undo commits. Gate with V4 passing (cost per resolved < human cost) + Phase 4 exit check (100 auto-merges audited, 0 regressions or security issues).\n- **Exit check:**\n  - V4 passes: cost per resolved issue < human-support baseline (UNKNOWN; needs support-team data, Phase 3).\n  - Merge safety: on 100 auto-merges, no regressions in CI/CD; 0 security issues reported within 7 days.\n  - Adoption on pilot repos: ≥ 30% of issues receive suggestions; ≥ 50% of suggestions are engaged (human action within 48 h).\n\n**Phase 5 — Multi-repo, feedback learning, & optimization**\n\n- **Unlocks:** General availability; optional: train a domain-specific fine-tuned model (Phase 6, deferred).\n- **Depends on:** Phase 4 exit check + V4 passes.\n- **Tasks:**\n  1. Roll out to 10+ internal repos; measure cost per issue and approval rate; identify repos where cost is high (poor retrieval, expensive fixes) vs. low (simple triage only).\n  2. Feedback-driven tuning: retrain embedding weights or re-chunk repo context for high-cost repos; recompute model prompt based on aggregated feedback.\n  3. Cost optimization via routing: use a cheaper model (GPT-3.5) for triage only; route code-fix requests to a more expensive model (GPT-4) only if the issue is labeled high-priority or has ≥ 3 upvotes.\n  4. Performance SLO: latency p95 < 15 s; cost per issue < $0.10 (optimized baseline); availability > 99.5% (no triage service blocks issue filing).\n  5. Operational monitoring: set up burn-rate alerts for cost; dashboard for latency, cost, and approval rate per repo.\n\n- **Rollback:** Disable new-repo onboarding; stay on Phase 4 rollout set.\n- **Exit check:** cost per issue < $0.10; latency p95 < 15 s; user feedback sentiment positive (> 60% thumbs-up on suggestions).\n\n---\n\n### 6.
