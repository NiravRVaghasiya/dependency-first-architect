Walking skeleton (Phase 0)\n\n**Request:** One real microservice (canary service) from the 50, with a realistic code change, passes through the new platform from commit to production within the latency targets, with a rollback verified.\n\n**The path:**\n1. Developer pushes a feature branch to GitHub (or equivalent).\n2. Platform detects push, triggers build pipeline: syntax check → unit tests → integration tests → container image build → push to registry → approval gate.\n3. Merge to main → automated canary deployment (0% traffic initially, then 10% for 1 minute, then 100% if no errors).\n4. Monitor platform's own logs, metrics, and the service's observable (status code, latency, errors) for 2 minutes.\n5. If healthy, mark deployment live; if unhealthy, automated rollback to previous image.\n6. Trigger manual rollback verification: revert the image, confirm service recovers.\n\n**Tiers crossed:**\n- **Source control** (GitHub or GitLab): webhook → builder\n- **Job orchestration** (CI/CD platform's control plane: Buildkite, GitHub Actions, or GitLab Runner manager): queues the build\n- **Builder runner** (ephemeral container): checkout, test, build image\n- **Artifact storage** (container registry: Docker Hub, ECR, or private registry): push image\n- **Secrets backend** (Vault, Sealed Secrets, or cloud secret manager): retrieve registry credentials and deploy-time credentials\n- **Deployment orchestrator** (kubectl, cloud API, or Nomad): apply deployment manifest with promotion gates\n- **Target environment** (Kubernetes cluster, ECS, or Lambda): run the container, serve traffic\n- **Observability backend** (logs: CloudWatch, Datadog, or ELK; metrics: Prometheus or cloud metrics): ingest traces, metrics, and logs from the service\n\n**Deployment, logging, monitoring, and rollback (day zero):**\n- **Deploy:** Service manifest includes: image digest (immutable), resource requests, health checks, deployment strategy (canary: 10% for 60 s, then 100%), revision history (keep 2).\n- **Logging:** All platform and service logs routed to central log aggregator; platform logs tagged with service name, build ID, deploy ID; searchable within 2 s.\n- **Monitoring:** Dashboard shows: platform build queue depth, runner utilization, deploy duration per service, service error rate during deploy. Alert fires if error rate > baseline + 2 σ during deployment.\n- **Rollback:** Automated: if service error rate > 5% or latency p95 > 1.5× baseline during canary, kill canary traffic and revert to previous image. Manual: click \"Rollback\" button, confirm in Slack, deploy reverts to previous safe revision.\n\n**Access:** Only internal engineers and the platform team can trigger builds and deployments. Webhook from GitHub is allowed only to the platform's Build API endpoint; all other requests blocked.\n\n**Defaults, not hardened:**\n- Single-region, single zone (no HA yet).\n- No rate limiting or quota enforcement (Phase 1).\n- No per-service RBAC (Phase 1); single \"can deploy\" role for all service teams.\n- Secrets injected as environment variables (not mounted files; Phase 1 hardens this).\n\n**Exit check (V0):** \n- A real commit to the canary service's feature branch triggers a build that passes all stages within < 5 min.\n- Merge to main triggers a deployment that reaches 10% canary within < 2 min and promotes to 100% within < 4 min if no alerts fire.\n- Injected-failure test: manually trigger an error in the service (e.g., kill a pod); platform alert fires within 10 s; manual rollback succeeds within 2 min.\n- All three flow events produce searchable logs and traces in the aggregator; platform operator can correlate build → deploy → service behavior in < 30 s.\n- First baseline values recorded: build latency, deploy latency, runner utilization at one concurrent service build, control-plane memory and CPU.\n\n---\n\n## 5.
