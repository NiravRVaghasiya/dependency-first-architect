Walking skeleton (Phase 0)\n\n**Real request:** A test tenant creates a usage event (e.g., \"10 API calls logged\"). The system records the event in the ledger, applies a pricing formula (USD 0.05/call = $0.50), generates an invoice entry, and returns the posted ledger balance to the tenant's API client. A second request reconciles the processor's webhook (simulated payment of $0.50), which updates the invoice state to \"paid.\"\n\n**Every tier:**\n1. **API Gateway** (bare endpoint, no auth yet): POST /v1/tenants/{tenant_id}/events → validates tenant_id exists\n2. **Ledger Service** (monolith): accepts the event, applies posting rule, writes to ledger table via Postgres transaction\n3. **Database** (Postgres, single primary): persists event, ledger posting, and invoice entry with `tenant_id` and `created_at` index\n4. **Invoice Generator** (batch job, in-process): query and aggregate ledger postings for the test tenant, write to `invoices` table\n5. **Payment processor simulation** (mock): in V0, a local test sends a webhook to the event queue\n6. **Event Queue** (RabbitMQ, shared by all tenants; access controlled by tenant_id): webhook handler consumes, updates invoice state to \"paid,\" triggers reconciliation alert\n7. **Observability** (logs, metrics, trace): every API call, ledger posting, invoice state transition, and error logged with tenant_id; metrics: API latency p99, ledger writes/s, invoice generation time\n8. **Rollback** (git + database snapshot): redeploy previous commit; restore database from pre-test snapshot via automated backup\n\n**Who can reach it:** Internal IP only (no public route); test tenant flagged in code; no real payment processor or customer data.\n\n**Exit check (V0):** \n- ✓ One POST /v1/tenants/{test_tenant}/events succeeds with 200 and a trace across ledger, database, and invoice generator.\n- ✓ Deploy to staging via CI pipeline (git push → container build → database migration → helm install).\n- ✓ Rollback succeeds (redeploy previous commit, database reverts to backup).\n- ✓ Injected failure (e.g., database connection failure) fires a metric alert in 5 s.\n- ✓ Baselines recorded: API latency p99 = 45 ms (floor, 1 concurrent call), ledger write = 8 ms, invoice generation = 120 ms for 1 tenant (near-zero load).\n\n---\n\n## 5. Phases (Phase 1 onward)\n\n### Phase 1 — Ledger schema and tenancy model hardening\n\n**Unlocks:** Multi-tenant invoice schema, real tenant provisioning, per-tenant tests.\n\n**Depends on:** V0 passes; tenancy model decision (§3) fixed.\n\n**Tasks:**\n1. Design and migrate schema:\n   - Ledger table: `(id, tenant_id, account_id, debit_amount, credit_amount, posting_date, created_at)` with PK on (tenant_id, id); indexes on (tenant_id, posting_date), (account_id, posting_date).\n   - Invoice table: `(id, tenant_id, invoice_number, start_date, end_date, total_amount, state, created_at)` with state ∈ {draft, posted, paid, refunded}.\n   - Add Postgres RLS policy: tenants can only read/write their own tenant_id rows.\n   - Test: no row leaks across tenant_id in queries; RLS blocks query for tenant A on tenant B's data.\n\n2. Implement tenant provisioning:\n   - Tenant registry table: `(tenant_id, name, plan, region, created_by, created_at)`.\n   - Provisioning API: POST /v1/admin/tenants (internal only) → creates tenant, initializes ledger account, stores in registry.\n   - Test: two test tenants can co-exist; ledger rows are isolated by RLS.\n\n3. Data residency routing:\n   - Add `region` to tenant registry and Connection Pool selector: tenant in US-East → connect to US-East Postgres.\n   - For MVP (US-only), single region; placeholder for Phase 5 (multi-region).\n   - Test: tenant row successfully queried via correct region.\n\n4. Build versioned ledger posting rules engine:\n   - Struct: `PostingRule { plan_id, event_type, debit_account, credit_account, formula(usage_quantity) }`.\n   - Example: plan \"starter\" + event \"api_call\" → debit \"revenue\", credit \"accounts_receivable\", formula = quantity × $0.05.\n   - Test: posting rule applied correctly; ledger balance equals cumulative postings.\n\n**Rollback:** redeploy Phase 0 schema; RLS policies remain but are not enforced (tenants self-isolated by code); no data loss (schema is additive).\n\n**Exit check:**\n- ✓ Two co-resident test tenants post events; ledger rows are isolated by RLS and verification query.\n- ✓ Tenant provisioning API creates and initializes a tenant in < 100 ms.\n- ✓ Posting rule engine applies rules correctly for 5 plan/event combinations.\n- ✓ V1 passes (see §6).\n\n---\n\n### Phase 2 — Backup, recovery, audit trail, and reconciliation state machine\n\n**Unlocks:** Phase 3 (real payment processor integration); multi-week runaway ledger will be checkpointed and reconciled.\n\n**Depends on:** Phase 1; V1 passes; data residency approval from legal (organizational, in-hand before Phase 3).\n\n**Tasks:**\n1. Implement backup and recovery:\n   - Daily snapshot of Postgres (WAL archiving to S3, full backup once per week) at 02:00 UTC.\n   - RTO test: restore from 1-week-old backup, re-run recent transactions, compare ledger balance to source of truth (processor API for payments; billing rules for events).\n   - Retention policy: backups kept for 90 days; older backups moved to Glacier.\n   - Test: recovery to 1 day ago successfully restores all ledgers, with no tenant data loss.\n\n2. Build audit trail (read-only ledger snapshot + append-only event log):\n   - Create `ledger_audit_log` table: `(id, tenant_id, action, old_value, new_value, actor, timestamp)`.\n   - On every ledger update: insert one row into `ledger_audit_log` (INSERT is append-only; UPDATE/DELETE on ledger itself is forbidden for posted rows).\n   - Policy: invoice state transitions are audited; ledger entries are immutable once posted.\n   - Test: audit trail shows every state change; no ledger row is modified in-place.\n\n3. Payment state machine and reconciliation:\n   - Invoice states: draft → posted → (pending_payment | paid | refunded).\n   - Payment event states: (pending_capture | captured | failed | disputed).\n   - Reconciliation job (runs after batch invoicing): compare invoice state to processor's payment status; detect mismatches (e.g., invoice marked paid but processor shows failed); emit alert.\n   - Test: invoices and payments reconcile; mismatches are detected and logged.\n\n4. Event schema (payment processor webhooks):\n   - Event table: `(id, tenant_id, processor_event_id, event_type, payload, processed_at, status)` (status ∈ {pending, processed, failed}).\n   - Idempotency: (tenant_id, processor_event_id) is unique; duplicate webhook is no-op.\n   - Test: webhook processed once, even if sent twice.\n\n**Rollback:** Phase 1 state; audit table is new and can be dropped; no ledger re-writes.\n\n**Exit check:**\n- ✓ V1 passes (see §6).\n- ✓ Backup and restore RTO test succeeds.\n- ✓ Audit trail immutability verified (audit table is append-only; ledger rows are not updated).\n- ✓ Reconciliation job runs on test invoices and detects a mismatch.\n\n---\n\n### Phase 3 — Payment processor integration, real-tenant onboarding, and batch billing at scale\n\n**Unlocks:** Phase 4 (production cutover); real customers can be billed.\n\n**Depends on:** Phase 2; V2 passes (batch throughput); V3 passes (PCI compliance); payment processor contract in hand; Stripe API keys configured.\n\n**Tasks:**\n1. Stripe integration:\n   - Implement webhook handler: POST /webhooks/stripe → parses `charge.captured`, `charge.failed`, `invoice.payment_succeeded` events.\n   - On `charge.captured`: update payment event state to \"captured\"; trigger reconciliation check.\n   - Implement payment capture API: POST /v1/tenants/{tenant_id}/payments → calls Stripe API (hosted form only; no card data in our system).\n   - PCI scope check: card entry only via Stripe hosted fields; no card numbers in logs, database, or API requests.
