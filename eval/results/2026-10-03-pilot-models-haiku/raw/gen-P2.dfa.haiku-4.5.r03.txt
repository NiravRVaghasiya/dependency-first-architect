Walking skeleton (Phase 0)\n\n**The one real request and response:**\n\n*Request:* A fully authenticated internal operator (internal user, API token, behind a VPN allow-list) creates a metered billing event for a test tenant (sandbox tenant, no real payment processing yet): `POST /internal/billing/events` with `{ tenant_id: \"test-001\", subscription_id: \"sub-123\", event_type: \"api_call\", count: 10, timestamp: <now> }`.\n\n*Response:* HTTP 201; event is persisted in the database; a trace with request ID appears in structured logs within 100 ms; the event is idempotent (same payload, same timestamp → same result, no duplicate).\n\n**Every tier it crosses:**\n\n1. **API Gateway** (auth + rate limit): Verify API token, check allow-list, rate limit.\n2. **Billing service** (in-process): Validate tenant_id (must be a known test tenant), validate subscription_id (must exist), check idempotency key (cache for 24 hours), store event.\n3. **Event store** (Postgres): Write to `billing_events` table (columns: tenant_id, subscription_id, event_type, count, timestamp, idempotency_key, created_at); enforce tenant_id + idempotency_key unique constraint.\n4. **Observability** (structured logs + metrics): Log the event with request ID, tenant ID, latency; emit a counter `billing_events_received`.\n5. **Rollback**: Delete the event row, re-increment the cache TTL.\n\n**Who can reach it:** Internal operators and CI/CD only, behind a VPN allow-list, using named service accounts; no external or customer access; behind a feature flag `SKELETON_BILLING_ENABLED` defaulting to off in prod (on in dev/staging).\n\n**Exit check V0:**\n- A real event is written and appears in logs within 100 ms; idempotency works (replay shows no duplicate in the DB).\n- A deploy succeeds through CI/CD (code pushed, tests pass, artifact built and pushed to registry, image deployed to staging, smoke test POST /internal/billing/events succeeds, rollback removes the pod and redeploys the prior image, smoke test passes again).\n- An injected failure (e.g., rate limit hit, tenant not found) fires an alert in Slack (PagerDuty integration).\n- First budget values are recorded: latency baseline (p50, p95, p99 at near-zero load), throughput baseline (1–2 events/s during the test), storage baseline (event row size ~500 bytes).\n\n---\n\n## 5. Phases\n\n### Phase 1 — Metering and event foundation\n\n**Unlocks:** Precision metering across pricing models; foundation for invoicing and usage validation.\n\n**Depends on:** V0 (skeleton runs), V1 (event throughput at 100 events/s for one hour shows no data loss or duplication).\n\n**Tasks (in dependency order):**\n1. Finalize metering schema and pricing model rules (flat fee, per-unit overage, tiered usage). *Depends on:* product input (missing input #1 from Step 1) → unblock this first in Phase 0 closure.\n2. Event ingestion hardening: Kafka topic for events (dead-letter queue for failures), idempotent writer to event store, schema validation (Avro or Protobuf).\n3. Usage aggregation: Time-bucket aggregation (5-min windows during billing period close) with SUM, MAX, and percentile functions; store aggregates in a separate table (`usage_aggregates`).\n4. Tenant isolation validation: Ensure every query in the metering layer includes `tenant_id` in the WHERE clause; add code review checklist + static analysis rule.\n5. Audit log for all metering changes: Store who (which service account) posted what event, when, for which tenant; immutable log.\n6. Tax rules loader: Read tax rules per jurisdiction from a config file (YAML) and cache; no external dependency yet, rules are hand-curated.\n\n**Rollback:** Disable Kafka topic, drain in-flight events to file, revert to Phase 0 skeleton (events-only, no invoicing yet).\n\n**Exit check V1:**\n- V1 gate passes: 100 raw events/s for 1 hour show zero data loss, zero duplication, and p99 latency < 50 ms.\n- Aggregation job runs successfully: For a 1-day usage window across 10 test tenants, aggregates match hand-rolled sums.\n- Tenant isolation test passes: Penetration test (internal) attempts to read one tenant's events via another tenant's API key; request is rejected.\n- Audit log is complete for all metering changes; no row is written without a corresponding audit entry.\n\n---\n\n### Phase 2 — Invoicing and revenue recognition\n\n**Unlocks:** Live invoice generation; revenue recognition; payment readiness; first internal testing of end-to-end billing.\n\n**Depends on:** Phase 1, V1, V4 (revenue recognition rules validated by finance against ASC 606 sample contracts).\n\n**Tasks (in dependency order):**\n1. Finalize revenue recognition rules and deferral logic with finance + legal (missing input #7). Deliver rule engine (deterministic: invoice → revenue line items with dates and amounts).\n2. Invoice schema: `invoices` table with tenant_id, subscription_id, period_start, period_end, total_amount, tax_amount, status (draft → finalized → paid), created_at, finalized_at, paid_at, external_invoice_id (for payment system sync).\n3. Invoice generation job (monthly, per-tenant cohort): Aggregate usage for the period, apply pricing rules, calculate tax (using Phase 1 tax rules), calculate deferred revenue, create invoice rows; atomically insert all data in a single transaction.\n4. Invoice retrieval API: `GET /tenants/:tenant_id/invoices`, `GET /tenants/:tenant_id/invoices/:invoice_id`; paged, with filtering by date range and status.\n5. Invoice preview endpoint (for UX): `POST /tenants/:tenant_id/invoices/preview?period_start=...&period_end=...` (read-only, no side effects; shows what the invoice will be without generating it).\n6. Verify V3 passed: PCI compliance review complete; SAQ A confirmed with acquirer (Stripe, etc.); no card data stored by us.\n2. Payment processor integration (Stripe or equivalent):\n   - Set up hosted card fields (Stripe Elements or Adyen Web) — card data never touches our systems.\n   - Implement payment intent flow: Create payment intent, return to client for card capture, webhook post on success/failure.\n   - Store payment intent ID (not card data) in `payments` table (tenant_id, subscription_id, invoice_id, stripe_payment_intent_id, amount, status, created_at, paid_at).\n3. Payment webhook handler: Receive `charge.succeeded` webhook, verify signature, idempotently update payment status, trigger revenue posting (mark invoice as paid, journal entry finalized).\n4.
