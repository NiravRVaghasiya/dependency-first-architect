Walking skeleton (Phase 0)\n\n**The one real request:**\nDeveloper pushes a commit to a service's repo (e.g., `services/auth-svc` branch). The platform detects the push via webhook, starts a build, runs tests in a container, tags and pushes an image to the registry, updates a deployment manifest in a GitOps repo, observes the rollout in the dev environment, records the result, and rolls back (one injected failure: image pull failure) to prove the rollback succeeds.\n\n**Every tier it crosses:**\n1. **SCM webhook (GitHub/GitLab)** → Platform controller\n2. **Platform controller** (build orchestrator; runs on a single VM, no HA yet)\n3. **Runner** (Kubernetes Pod or VM; pulls code, runs tests, builds and pushes image to a registry)\n4. **Docker registry** (local or managed; artifact storage)\n5. **GitOps tool** (Flux or ArgoCD; syncs deployment manifests to the dev cluster)\n6. **Kubernetes dev cluster** (deploys the image, health-checks it, serves traffic)\n7. **Observability pipeline** (logs → centralized store, traces → agent, metrics → Prometheus)\n8. **Rollback orchestrator** (reverts the deployment manifest, triggers rollback in GitOps)\n\n**Deployment and rollback on day zero:**\n- Controller and runner stateless (configs in Git, secrets in Vault).\n- Entire setup stands up from code (IaC: Terraform or Helm) on day zero; no manual steps after the first apply.\n- Rollback: a Git revert of the deployment manifest triggers GitOps rollback; confirmed by reading the cluster state and comparing with Git.\n- Failure injection: kill the image pull on rollback; alert fires; operator manually rolls back or deploys the previous manifest.\n\n**Who can reach it:**\nInternal networks and allow-listed developer machines only (no external traffic) until Phase 2. Platform runs behind a firewall; webhooks from SCM use a static secret or IP whitelist.\n\n**Observability (day zero):**\n- Logs: every step (push detected, build started, test run, image pushed, deployment applied, rollback triggered) goes to stdout (JSON-structured).\n- Traces: one W3C trace ID follows the commit from webhook to cluster state.\n- Metrics: build duration, test pass rate, deployment success/failure, rollback latency.\n- Baseline: record all measurable budgets at zero load (sub-second latency within internal network; no failures).\n\n**Exit check (V0):**\n- A real commit triggers the full pipeline: push → build → test → artifact → deploy → health check → verify running → rollback → verify reverted.\n- Deploy and rollback succeed.\n- One failure (image pull) is injected mid-rollback; alert fires and is visible in the log store.\n- All three measurable budgets are recorded as baselines: latency (build + deploy time), rollback latency, and uptime (no errors).\n- All tasks complete in a single namespace and cluster; no multi-region or HA setup yet.\n\n## 5.
