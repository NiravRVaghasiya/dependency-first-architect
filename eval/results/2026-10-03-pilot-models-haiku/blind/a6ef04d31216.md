# Plan — Multi-Tenant SaaS Billing System

## 1. Classification and constraints

**What:** A multi-tenant SaaS billing system handling recurring subscriptions, metered usage, invoicing, payment processing, and revenue recognition across customer organizations with subscription and usage-based pricing models.

**Type:** Software, greenfield, not a small build (multi-tenant touches auth, data isolation, tenancy, payment compliance, and revenue integrity; real financial data and money flow).

**Dominant constraint:** Correctness (revenue must be accurate and auditable; billing errors compound over time and are costly to reverse). Secondary: compliance (PCI DSS for card data; revenue recognition rules per jurisdiction) and availability (payment processing outages directly harm revenue).

**Worst failure:** Data isolation break or concurrency bug causing one tenant's charges, credits, or invoice data to leak into or overwrite another tenant's records, eroding trust, creating audit violations, and enabling fraudulent billing.

**Budgets:**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency (invoice generation + payment post) | p99 ≤ 2 s (invoice query + PDF gen); payment webhook delivery ≤ 5 s | ASSUMPTION: typical for SaaS; confirm with product owner | V0 records floor; Phase 2 exit check at scale |
| Throughput | 500 invoices/s during monthly close; 100 metered events/s steady-state | REQUIREMENT: stated for multi-tenant at product scale | Phase 2 load test (invoicing); Phase 1 exit check (event ingestion) |
| Availability / SLO | 99.95% for payment processing; 99.9% for invoice queries (revenue-driving path is critical, read-only paths can degrade) | REQUIREMENT: SaaS buyer standard | Phase 4; SLI + burn-rate alerts |
| RPO / RTO | RPO ≤ 1 hour (last successful sync to payment provider); RTO ≤ 30 min for payment processing outage | REQUIREMENT: revenue continuity | Phase 3 exit check (backup/recovery) |

## 3. Key decisions (resolved up front)

## 4. First end-to-end slice (Phase 0)

**The one real request and response:**

*Request:* A fully authenticated internal operator (internal user, API token, behind a VPN allow-list) creates a metered billing event for a test tenant (sandbox tenant, no real payment processing yet): `POST /internal/billing/events` with `{ tenant_id: "test-001", subscription_id: "sub-123", event_type: "api_call", count: 10, timestamp: <now> }`.

*Response:* HTTP 201; event is persisted in the database; a trace with request ID appears in structured logs within 100 ms; the event is idempotent (same payload, same timestamp → same result, no duplicate).

**Every tier it crosses:**

1. **API Gateway** (auth + rate limit): Verify API token, check allow-list, rate limit.
2. **Billing service** (in-process): Validate tenant_id (must be a known test tenant), validate subscription_id (must exist), check idempotency key (cache for 24 hours), store event.
3. **Event store** (Postgres): Write to `billing_events` table (columns: tenant_id, subscription_id, event_type, count, timestamp, idempotency_key, created_at); enforce tenant_id + idempotency_key unique constraint.
4. **Observability** (structured logs + metrics): Log the event with request ID, tenant ID, latency; emit a counter `billing_events_received`.
5. **Rollback**: Delete the event row, re-increment the cache TTL.

**Who can reach it:** Internal operators and CI/CD only, behind a VPN allow-list, using named service accounts; no external or customer access; behind a feature flag `SKELETON_BILLING_ENABLED` defaulting to off in prod (on in dev/staging).

**Exit check V0:**
- A real event is written and appears in logs within 100 ms; idempotency works (replay shows no duplicate in the DB).
- A deploy succeeds through CI/CD (code pushed, tests pass, artifact built and pushed to registry, image deployed to staging, smoke test POST /internal/billing/events succeeds, rollback removes the pod and redeploys the prior image, smoke test passes again).
- An injected failure (e.g., rate limit hit, tenant not found) fires an alert in Slack (PagerDuty integration).
- First budget values are recorded: latency baseline (p50, p95, p99 at near-zero load), throughput baseline (1–2 events/s during the test), storage baseline (event row size ~500 bytes).

## 5. Phases

### Phase 1 — Metering and event foundation

**Unlocks:** Precision metering across pricing models; foundation for invoicing and usage validation.

**Depends on:** V0 (skeleton runs), V1 (event throughput at 100 events/s for one hour shows no data loss or duplication).

**Tasks (in dependency order):**
1. Finalize metering schema and pricing model rules (flat fee, per-unit overage, tiered usage). *Depends on:* product input (missing input #1 from Step 1) → unblock this first in Phase 0 closure.
2. Event ingestion hardening: Kafka topic for events (dead-letter queue for failures), idempotent writer to event store, schema validation (Avro or Protobuf).
3. Usage aggregation: Time-bucket aggregation (5-min windows during billing period close) with SUM, MAX, and percentile functions; store aggregates in a separate table (`usage_aggregates`).
4. Tenant isolation validation: Ensure every query in the metering layer includes `tenant_id` in the WHERE clause; add code review checklist + static analysis rule.
5. Audit log for all metering changes: Store who (which service account) posted what event, when, for which tenant; immutable log.
6. Tax rules loader: Read tax rules per jurisdiction from a config file (YAML) and cache; no external dependency yet, rules are hand-curated.

**Rollback:** Disable Kafka topic, drain in-flight events to file, revert to Phase 0 skeleton (events-only, no invoicing yet).

**Exit check V1:**
- V1 gate passes: 100 raw events/s for 1 hour show zero data loss, zero duplication, and p99 latency < 50 ms.
- Aggregation job runs successfully: For a 1-day usage window across 10 test tenants, aggregates match hand-rolled sums.
- Tenant isolation test passes: Penetration test (internal) attempts to read one tenant's events via another tenant's API key; request is rejected.
- Audit log is complete for all metering changes; no row is written without a corresponding audit entry.

### Phase 2 — Invoicing and revenue recognition

**Unlocks:** Live invoice generation; revenue recognition; payment readiness; first internal testing of end-to-end billing.

**Depends on:** Phase 1, V1, V4 (revenue recognition rules validated by finance against ASC 606 sample contracts).

**Tasks (in dependency order):**
1. Finalize revenue recognition rules and deferral logic with finance + legal (missing input #7). Deliver rule engine (deterministic: invoice → revenue line items with dates and amounts).
2. Invoice schema: `invoices` table with tenant_id, subscription_id, period_start, period_end, total_amount, tax_amount, status (draft → finalized → paid), created_at, finalized_at, paid_at, external_invoice_id (for payment system sync).
3. Invoice generation job (monthly, per-tenant cohort): Aggregate usage for the period, apply pricing rules, calculate tax (using Phase 1 tax rules), calculate deferred revenue, create invoice rows; atomically insert all data in a single transaction.
4. Invoice retrieval API: `GET /tenants/:tenant_id/invoices`, `GET /tenants/:tenant_id/invoices/:invoice_id`; paged, with filtering by date range and status.
5. Invoice preview endpoint (for UX): `POST /tenants/:tenant_id/invoices/preview?period_start=...&period_end=...` (read-only, no side effects; shows what the invoice will be without generating it).
6. Revenue journal entry generation: Emit journal entries (invoice date, account code, amount, GL account) for external accounting system to consume (not persisted in billing system, only generated on demand or during reconciliation).
7. Reconciliation job (monthly, post-close): Compare generated revenue lines to external accounting system's journal entries; alert if drift > 0.1%.

**Rollback:** Delete generated invoices and revenue journal entries (safe because not yet exposed to payment processing); revert invoice schema; redeploy Phase 1 code.

**Exit check V2:**
- V2 gate passes: For 50 test invoices with a mix of pricing models (flat, overage, tiered, multi-currency), hand-rolled expected revenue matches system-generated revenue to the cent.
- Invoice generation at scale: 500 invoices/s during month-end close (measured via load test with synthetic data); p99 latency < 2 s; no invoice skipped or duplicated.
- Revenue reconciliation: Reconciliation job runs successfully; drift < 0.1%; audit log shows all calculations traceable to source usage events.
- Tax calculation validated: Finance team reviews sample invoices for 5 jurisdictions; tax amounts match external tax calculator (spike comparison).
- Invoice API latency: `GET /invoices` for one year of history (365 rows): p99 < 500 ms.

### Phase 3 — Payment processing and PCI compliance

**Unlocks:** Live payment processing; real money flow; production revenue generation.

**Depends on:** Phase 2, V2, V3 (PCI compliance review + acquirer sign-off for SAQ A), V5 (webhook idempotency and reconciliation check passed).

**Tasks (in dependency order):**
1. Verify V3 passed: PCI compliance review complete; SAQ A confirmed with acquirer (Stripe, etc.); no card data stored by us.
2. Payment processor integration (Stripe or equivalent):
   - Set up hosted card fields (Stripe Elements or Adyen Web) — card data never touches our systems.
   - Implement payment intent flow: Create payment intent, return to client for card capture, webhook post on success/failure.
   - Store payment intent ID (not card data) in `payments` table (tenant_id, subscription_id, invoice_id, stripe_payment_intent_id, amount, status, created_at, paid_at).
3. Payment webhook handler: Receive `charge.succeeded` webhook, verify signature, idempotently update payment status, trigger revenue posting (mark invoice as paid, journal entry finalized).
4. Webhook idempotency: Store webhook event ID in `webhook_events` table with a unique constraint (tenant_id, external_event_id); if same event arrives twice, second is silently ignored.
5. Refund and chargeback handler: `POST /payments/:payment_id/refund`; validate authorization (only tenant admins or support staff with audit reason), create refund record (amount, reason, approved_by, created_at), trigger negative journal entry.
6. Payment reconciliation: Daily job comparing our `payments` table to Stripe reconciliation API; alert if variance.
7. Backup and recovery: Daily backup of all billing + payment data to S3 (encrypted, versioned); test restore procedure (restore to staging, verify data integrity).
8. RTO testing: Simulate a payment service outage; confirm failover to manual reconciliation (interim script) meets RTO ≤ 30 min.

**Rollback (point of no return: first live payment):** Before the first real payment is posted, rollback to Phase 2 is safe (no real money). After that, payment records are immutable; corrections only via refunds (tracked in audit log).

**Exit check V3:**
- V3 gate passes: PCI compliance review complete; SAQ A signed off; penetration test finds no card data in logs, caches, or backups.
- V5 gate passes: 10 test payments through Stripe; webhook redelivery (simulate 2× delivery) shows idempotent handling (only one charge recorded).
- Reconciliation: Daily reconciliation job compares system to Stripe for 7 days; variance ≤ $0.01 (rounding).
- RTO test: Simulate payment service outage; manual reconciliation runs, no invoices lost, failover completes ≤ 30 min.
- Backup + restore: Restore from 1-day-old backup to staging, verify 100% of records present.
