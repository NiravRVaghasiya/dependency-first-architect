# BUILD PLAN: Real-Time Collaborative Document Editor

## 1. Classification and constraints

**What:** A real-time collaborative document editor with simultaneous multi-user editing, live cursor positions, and operational-transform or CRDT-based conflict resolution.

**Type:** Software (greenfield); small build (single team).

**Dominant constraint:** Correctness (document integrity under concurrent writes) and latency (real-time visibility of changes, <500ms propagation).

**Worst failure:** Concurrent writes cause data corruption, data loss, or fork the document state across clients (unreconcilable divergence).

**Budgets:**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency (change propagation) | p95 < 500 ms from keystroke to peer visibility | ASSUMPTION: acceptable for collaborative editing | V0 baseline; V2 under load |
| Throughput | 10 concurrent editors, 100 ops/s aggregate | ASSUMPTION: typical small-team document | V2 stress test |
| Availability / SLO | 99.5% (brief outages acceptable; editing resumes on reconnect) | ASSUMPTION: internal or beta users | Phase 3 exit check |
| Storage cost | ≤ $50/month for 10 GB active documents | ASSUMPTION: one-team scale | — |
| Operational complexity | One backend service, one managed database, WebSocket broker | ASSUMPTION: two-person team | Phase 4 exit check |

**Missing inputs:**
- Persistence model: durability guarantee required (eventual consistency vs. strong consistency)? Supplied by: product owner, needed before Phase 1.
- Scale expansion plan: when do we plan to support >10 concurrent editors or >1 million documents? Affects sharding, event log retention; deferred until Scale phase.

**Assumption:** The dominant architecture risk is whether CRDT (Conflict-free Replicated Data Type) or Operational Transform (OT) scales to our latency and concurrency targets without data corruption. This drives Phase 1 validation gate (V1).

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| CRDT vs. Operational Transform | R3 (both assume different network ordering; switching mid-development breaks clients) | CRDT (Yjs library: simpler eventual-consistency, no OT tombstones, works offline-first) | Yjs ecosystem is mature; OT is tightly coupled to server ordering | V1: conflict-free merge on ≥100 concurrent ops, no corruption | Benchmark shows latency > 1s or ops/s < 50 at Phase 1 load; then switch to OT with server authority |
| Consistency model | R3 (affects schema, client code, conflict semantics) | Eventual consistency with CRDT (each client applies ops locally, syncs via server) | Accept temporary divergence; rare conflicts auto-resolved by CRDT merge | V1 passes; latency and simplicity favored | V1 fails or product requires strong linearization; switch to OT + server-ordered log |
| Real-time channel (WebSocket vs. polling) | R2 (backend change, client library swap) | WebSocket (lower latency, two-way push, standard for collab tools) | WebSocket is proven; polling adds 1–5s latency unacceptable here | Phase 0 proof of concept works on WebSocket | Throughput test shows WebSocket server cannot sustain 100 ops/s; add polling fallback |
| Offline support | R2 (client-side queue, server merge logic) | Yes: queue local ops offline, sync on reconnect via delta (CRDT advantage) | Offline access is a core feature for mobile and network churn | Phase 0 functional test; V2 stress test includes reconnection | V2 shows >1 min recon time or conflicting deltas fail to merge; defer offline to Phase 3 |
| Document storage (database choice) | R2 (swap database, schema adjust, client queries unchanged if using CDC/event log) | PostgreSQL + event log table (durability, ACID for log, manageable for one team) | Single primary sufficient at 10 concurrent editors; PostgreSQL proven for append-only logs | Phase 2 capacity check (V3); no need for sharding yet | Throughput test shows single primary saturates; migrate to Postgres with logical replication or NATS JetStream |
| Tenancy and authorization | R3 (baked into document schema, access checks, API surface) | Workspace-based: one document per workspace; read/write ACLs per user | One-team beta; expand to multi-tenant only if adoption requires | Phase 1 scoping (not gated, but documented); Phase 3 access-control test | Real users require tenant isolation; refactor schema before Phase 4 exposure |

**R1 defaults:** UI framework → React + TipTap (proven rich-text + CRDT integration); error handling strategy → local optimistic updates, server-reconciled on sync.

**N/A:** Build vs. buy — evaluated as not viable for greenfield (no hosted CRDT service with our SLA needs); Data privacy boundary — no PII stored in first phase (internal users only).

## 4. Walking skeleton (Phase 0)

**Request:** One user opens a document, types three characters, a second user on the same document sees those characters appear with <500 ms latency, both users' cursor positions are visible, then User 1 closes and reconnects (simulating disconnect); the edits are resync'd without conflict.

**Tiers:**
1. Client 1: Rich-text editor (TipTap + Yjs), in-memory CRDT state, WebSocket client.
2. Client 2: Same.
3. Backend (Node.js + Express): WebSocket server (ws library), routes messages between peers, persists ops to a log.
4. Database: PostgreSQL table `ops_log` (id, doc_id, user_id, op, timestamp, applied_at).

**Deployment:**
- Local development: both clients localhost:3000 and localhost:3001, backend localhost:8080 via nodemon.
- Docker Compose: brings up Postgres, backend, and serves both clients via a simple nginx proxy.
- Pipeline: GitHub Actions → (npm run test, npm run lint) → Docker build → push to local registry → docker-compose pull + up.

**Logging & monitoring:**
- Backend logs every WebSocket message (op, user, doc, timestamp) to stdout; structured JSON.
- Client logs local ops and remote merges to browser console (DEBUG flag).
- Postgres logs slow queries (>100 ms) to stderr.

**Rollback:**
- kill docker-compose, git revert, rebuild, up again.
- No persistence state beyond Postgres; stopping the service loses in-memory client state (acceptable for local run).

**Who can reach it:** Internal developers and QA only (runs on localhost, no network exposure).

**Exit check (V0):**
- ✓ User 1 types 3 characters; User 2 sees them within 500 ms (measured via WebSocket callback timestamp).
- ✓ Both clients' cursor positions update on remote keystroke; no visual lag.
- ✓ User 1 closes browser tab; User 2 continues editing.
- ✓ User 1 reopens; edits resync in <1 second without conflicts.
- ✓ Ops log contains exactly 3 entries from User 1, all applied once (no duplicates).
- ✓ Backend restart: all clients reconnect and resume with state intact (Yjs re-syncs from server).
- ✓ Inject a test: kill Postgres; backend alerts (connection error logged) and stops accepting ops; clients show "offline" state.
- ✓ Baseline latency recorded: 50 ms (local, no network delay); ops/s recorded: 50 (single user typing); storage used: <1 MB for 100 ops.

## 5. Phases (Phase 1 onward)

**Phase 1 — CRDT conflict resolution & algorithm validation**
- **Unlocks:** Confidence to specify UI and server-sync protocol; Phase 2 begins.
- **Depends on:** Phase 0 (V0 passes).
- **Tasks:**
  1. Implement Yjs `Y.Doc` and Y.Text for shared document (replaces ad-hoc CRDT).
  2. Write conflict-resolution test suite: 100 concurrent ops from 5 simulated clients, random order, verify no data loss or corruption.
  3. Benchmark: measure time to apply remote op (should be <5 ms in-process), merge latency (should be <10 ms).
  4. Protocol hardening: define WebSocket message format (op, clock, user_id, timestamp); add message ID to detect duplicates; add version vector for causal ordering.
  5. Offline queue: implement client-side queue; apply ops optimistically; on reconnect, send queued ops and resolve conflicts.
- **Rollback:** Revert to Phase 0 and re-scope consistency model (trigger a flip to OT + server-ordered log if V1 fails).
- **Exit check:** V1 passes (see gates). Conflict-resolution test passes all 100 op sequences with zero corruption. Protocol spec finalized. Client reconnection resync succeeds in 5 test runs with random disconnects.

**Phase 2 — Persistence, concurrency, and stress test**
- **Unlocks:** Proof that the system scales to our latency and throughput targets; Phase 3 begins.
- **Depends on:** Phase 1 (V1 passes).
- **Tasks:**
  1. Persistence layer: ops_log table; write all ops to Postgres with commit timestamp (event sourcing).
  2. Snapshot optimization: periodically write `doc_snapshots` table (doc_id, version, state_blob); on client join, send snapshot + ops since.
  3. Capacity test: spawn 10 concurrent clients, each typing 10 ops/s for 60 s; measure:
     - Server CPU, memory, Postgres query latency.
     - Latency p95, p99 for op propagation.
     - Detect any data divergence or missing ops.
  4. Failover test: kill backend, restart; clients reconnect and re-sync; verify no ops lost and no duplicates.
  5. Garbage collection: implement periodic cleanup of old ops (keep last 7 days; snapshot every 1 day to enable recovery).
- **Rollback:** Stop the load test, revert persistence schema, restart backend in-memory-only; no data loss (log entries were temporary). If latency target is missed, increase snapshot frequency (Phase 3).
- **Exit check:** V2 passes. Ops/s sustained at 100; p95 latency <500 ms. Postgres query latency p95 <50 ms. No data divergence. Failover recovers in <5 s.

**Phase 3 — Authorization, multi-document, and production readiness**
- **Unlocks:** First internal user rollout (beta); Phase 4 begins.
- **Depends on:** Phase 2 (V2 passes).
- **Tasks:**
  1. Authorization model: implement document ACLs (owner, editors, viewers); embed user_id in JWT; backend validates write permission before accepting op.
  2. Multi-document routing: extend protocol; client sends doc_id with every op; backend routes to correct Yjs instance; implement per-doc subscriptions.
  3. Observability hardening: structured logs (user_id, doc_id, op_count, latency, error); deploy to ELK or similar; set SLIs (availability, error rate, latency p95).
  4. Error handling: implement retry logic (exponential backoff, max 10 retries) for failed ops; surface errors to UI (e.g., "Sync failed—edit queued for retry").
  5. UI polish: add presence indicators (who is online), conflict-resolution UX (show merged edits with attribution), offline banner.
- **Rollback:** Feature flag for auth checks (default off); disable multi-doc routing; revert to single-doc-per-backend setup; restart.
- **Exit check:** V3 passes (access-control test). Multi-doc test: 5 concurrent documents with 2 users each; all edits correctly routed and persisted. Observability dashboards show latency and error rates. SLI alert fires on 5% error rate.

**Phase 4 — Beta user rollout and cost/performance confirmation**
- **Unlocks:** General availability (Phase 5).
- **Depends on:** Phase 3 (V3 passes); organizational (product owner sign-off on features and rollout plan).
- **Tasks:**
  1. Canary: deploy to 1 internal user; monitor for 1 week; check latency, error rate, storage growth.
  2. Expand: 10 users; run for 1 week; measure storage cost ($ per user/month), support burden.
  3. Expand: 50 users; run for 1 week; measure operational overhead (is one backend sufficient? Postgres query latency still <100 ms p95?).
  4. Incident simulation: kill backend mid-sync, verify graceful failover and data integrity (V4 flip condition).
- **Rollback:** Disable beta flag; users revert to "sync in progress, please wait" state; data is safe on Postgres.
- **Point of no return:** Once 50 users have been writing to the production database for 1 week, data loss becomes visible (users have edited documents). Gate: V4 (incident simulation) must pass; operational sign-off required.
- **Exit check:** V4 passes. Latency p95 still <500 ms (measured on live traffic). Error rate <1%. Storage cost confirmed within budget ($50/month for 50 users' 500 GB aggregate). On-call load acceptable (≤1 page/week). Go/no-go for GA.

**Phase 5 — General availability and scale**
- **Unlocks:** Public marketing; feature development backlog (offline-first client, mobile app, real-time search indexing).
- **Depends on:** Phase 4 (V4 passes); organizational (launch approval).
- **Tasks:**
  1. Remove beta flag; launch publicly or to broader cohort.
  2. Scale plan: if user base >500, plan sharding by workspace ID; re-run load test (Phase 2 equivalent) at 5× scale.
  3. Long-term: monitor for new failure modes (storage growth, Postgres connection limits, snapshot size).
  4. Feedback loop: track user-reported conflicts, lag, or data loss incidents; triage and prioritize fixes.

## 10. Deliberately deferred

- **Multi-workspace tenancy:** Deferred until Phase 5. Requires refactoring authorization model and ops_log schema to include workspace_id. Triggered when: user base requests multi-workspace support or security audit mandates strict tenant isolation.
- **Full-text search on documents:** Deferred until Phase 4 beta expands to 50+ users. Requires indexing ops_log snapshots (or Elasticsearch sidecar). Triggered when: users request search feature or support load reveals search as common request.
- **Mobile native app (iOS/Android):** Deferred until Phase 5 GA. Requires Yjs binding for mobile frameworks (e.g., React Native). Triggered when: web version is stable and user base requests mobile support.
- **Offline-first client (sync on background):** Deferred until Phase 4. Requires persistence layer (e.g., IndexedDB client-side, iCloud/Google Drive backup). Triggered when: beta users report WiFi/connectivity issues affecting editing experience.
- **Encryption at rest for Postgres:** Deferred until real user data reaches compliance threshold. Triggered when: Phase 4 beta includes users with sensitive data or compliance audit mandates encryption.
- **Sharding and multi-region failover:** Deferred until Phase 5 scale phase or user base exceeds 5,000. Triggered when: load test (Phase 2 equivalent at 5× scale) shows single-instance limits exceeded, or geographic distribution of users makes regional latency unacceptable.
