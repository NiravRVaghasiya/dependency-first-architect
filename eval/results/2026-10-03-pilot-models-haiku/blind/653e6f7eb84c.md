# BUILD PLAN
## Autonomous GitHub Issue Triage and Resolution Agent

### 1. Classification and constraints

**What:** An autonomous agent that reads incoming GitHub issues, triages them (labels, priority, assignment), and attempts resolution (reproduce, propose fixes, open PRs, merge when allowed).

**Type:** AI-agentic system; greenfield; small build (one team, internal cohort behind a flag initially, no regulated data, money flow scoped to API cost).

**Dominant constraint:** Correctness (must not corrupt issue state or make unauthorized changes); Cost (models/API are the main variable cost; must meter closely); Availability (cannot block issue operations; shadow mode first).

**Worst failure:** The agent reads a sensitive issue and, through prompt injection or a tool-call bug, either (a) leaks private details in a public comment, or (b) auto-merges a PR that breaks the build because injection tricked it into approving untrusted code.

**Budgets:**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency (time to suggest triage) | < 10 s p95 | ASSUMPTION: GitHub issue webhook timeout is 30 s; target leaves headroom | Phase 0 baseline; Phase 2 under load |
| Latency (time to suggest code fix) | < 60 s p95 per request | ASSUMPTION: model reasoning on issue text + repo fragment | Phase 3 eval |
| Throughput (issues ingested/hour) | UNKNOWN: depends on repo activity; assume 10–100/hour for a mid-size repo | ASSUMPTION | Phase 1 webhook setup |
| Availability / SLO | No blocking gate on GitHub; degrades to read-only if model unavailable | ASSUMPTION: user can still file and close issues | Phase 1 exit check |
| AI inference cost | UNKNOWN: needs decision on model (GPT-4, Claude, Llama); estimate $0.05–0.20 per issue triaged, $0.50–2.00 per fix suggested | ASSUMPTION | V1 (cost-per-issue on canary before scale) |
| Operational complexity | One serverless function (Lambda, Cloud Run) + one vector DB (managed embedding store, e.g., Supabase, Pinecone) | ASSUMPTION: no on-prem | Phase 2 exit check |

**Missing inputs:**

- **Scope of write access:** which actions does the agent propose vs. execute? (Opens issues → yes; approves merges → no. Confirm in Phase 0.)
- **Sensitive repo handling:** rules for private repos, security issues, PII. *Assumption: the skeleton runs on a public or internal repo only; private & security repos deferred to Phase 2.*
- **Fix quality threshold:** error rate acceptable before human review? *Assumption: all changes proposed, none auto-merged until Phase 3.*
- **Supported languages:** start with which repo languages? *Assumption: Python + JavaScript; others Phase 2.*

### 4. Walking skeleton (Phase 0)

**Real request:** A human files a GitHub issue in a test repo: *"Login button broken on iOS Safari, v2.1."*

**Real response:** Within 30 s, the agent posts a triage suggestion comment: *"🤖 Suggested labels: `bug`, `mobile`, `ios-safari`. Severity: high (blocks login flow). Tentative assignment: [@ios-team](https://github.com/ios-team). Related: #42, #51."* The suggestion is read-only; no labels are set. Trace through every tier:

1. **GitHub API (webhook ingress):** Issue created webhook fires → HMAC-verified → event queued to serverless function.
2. **Serverless function (entrypoint):** Validates webhook, enqueues job, returns 200 within 1 s.
3. **Prompt-injection / guardrail defense (inline):** Issue title and body extracted; treated as untrusted data. Injection suite (planted jailbreak strings, SQL, shell escapes, tool-call escapes) runs on the text in CI; no malicious string reaches the model.
4. **Embedding & retrieval (vectorstore):** Past 10 issues chunked, embedded (local embeddings, not on user input yet), stored; for this request, retrieval fetches top-3 similar issues (no retrieval on user input in Phase 0, only schema verified). Retrieval latency < 500 ms.
5. **Model API call (inference):** Prompt sent to hosted Claude API with token cap (2,000 tokens in, hard stop at 4,000 out), tool-call cap (max 5 calls), timeout 20 s. Response: structured JSON (labels array, severity, owner suggestion, related-issue IDs). Cost metered.
6. **Tool allowlist (write guard):** Response parsed; all tool calls validated against allowlist: \[`retrieve_issue`, `retrieve_pr`, `post_comment`\]. Tool call to `post_comment` with suggested labels and assignment (no label-set mutation, comment only). Arguments sanitized: no inline code, no HTML, no markdown that GitHub will render as code execution.
7. **GitHub API (response egress):** Comment posted: *"🤖 Suggested…"* with no edits to issue state (no label set, no assignee mutated). Timestamp and cost logged.
8. **Observability (logging & trace):** Every step traced: webhook arrival, validation pass/fail, retrieval hits, model call (tokens in/out, cost), tool call (name, arguments, result, auth check result), final comment ID. Trace ID = webhook delivery ID.
9. **Monitoring:** Latency: 2.3 s end-to-end (webhook ingress + retrieval + model + post). Cost: $0.008 (156 input tokens + 87 output tokens). Injected failure: seed jailbreak in issue title → injection suite fires in CI (pass); model call returns no tool calls (blocked by injection logic, not filtering); no state mutation (pass).
10. **Rollback:** Function can be reverted to a no-op (deleted, or feature flag off); webhook deliveries can be manually replayed or skipped. Prior triage suggestion comments can be deleted if the function is reverted before another issue lands.

**Who can reach it:** Internal repo with allow-listed GitHub org members only (GitHub actions token scoped to this repo). No real user data. Suggestion is read-only (no mutations except the comment itself).

**Exit check V0:** 
- ✓ Real issue created, webhook fired, agent suggests triage in < 30 s, comment posted.
- ✓ Trace (webhook ID → function call ID → model call ID → comment ID) complete in logs.
- ✓ Deploy (push code → action runs → function deployed) succeeds; rollback (revert + redeploy or delete route) succeeds.
- ✓ Injected failure (jailbreak string in issue title) fires test alert in CI (injection not reached model).
- ✓ Baseline recorded: latency < 3 s, cost < $0.01, no tool-call violations.

### 5. Phases (Phase 1 onward; dependency order)

**Phase 1 — Retrieval & triage suggestions (read-only expansion)**

- **Unlocks:** Cost validation (V1); canary triage on real repo; multi-repo skeleton.
- **Depends on:** Phase 0 (V0 passes); V1 cost threshold to be checked at Phase 2.
- **Tasks:**
  1. Embed repository context: README, issue templates, past 100 issues (chunked by function/file/author), PR history (commit messages, review patterns).
  2. Finalize retrieval index: Supabase pgvector or Pinecone; embedding model (e.g., text-embedding-3-small); chunk size (500–1000 tokens); metadata schema (repo, issue ID, date, author).
  3. Expand model prompt: few-shot examples of good triage (labels, severity, assignment, related links). Inject current labels and prior-issue context into each model call.
  4. Triage suggestion rules (non-generative fallback): If issue title matches regex (e.g., "crash", "hang", "memory leak"), force `severity: critical`; if no repo context retrieved, suggest `needs-info`.
  5. Webhook routing: Scale to multiple repos (same function, repo ID in payload). Retrieve context per repo.
  6. Cost metering: Log tokens-in, tokens-out, API cost per request; aggregate cost-per-issue.

- **Rollback:** Revert retrieval index + re-seed old schema; disable webhook on new repos.
- **Exit check:**
  - Retrieval hits the target repo context (top-5 results include relevant past issues) on ≥ 90% of 50 test queries (V2 acceptance threshold).
  - Cost baseline: mean $0.006/issue (ASSUMPTION), measured on 200 issues from test repo.
  - No unauthorized mutations; all 200 test issues show comment-only suggestion, no label/assignee change.
  - Latency: p95 < 12 s (includes webhook delay + function cold start).

**Phase 2 — Human-in-the-loop fix suggestions & approval gating**

- **Unlocks:** Confidence to allow auto-label & auto-assign (Phase 3); cost budget validated (V1 passes); feedback loop (Phase 4).
- **Depends on:** Phase 1 exit check + V1 (cost per issue < budget); V3 (injection containment confirmed); Phase 0 exit check (rollback tested).
- **Tasks:**
  1. Extend model prompt: given issue description, repo context, and related code snippets, suggest a fix (in code, not prose). Response: structured JSON (file path, change rationale, code block, test or manual repro steps).
  2. Schema for fix suggestions: store in GitHub as draft-PR comment (no merge, no commit yet) or as a separate Markdown document in a gist. Draft PR stays local to the function; final PR is human-triggered.
  3. Approval workflow: two models—(a) auto-label & auto-assign low-confidence issues (< 50% confidence of severity) requires no human review; (b) code fix suggestions are comment-only (human reviews, optionally uses `/approve-fix` command in comment to trigger a draft PR).
  4. Sensitive repo rules: skip triage for private repos with `security-sensitive` label; skip code-fix suggestions for issues tagged `security`.
  5. Test on canary: deploy to 1–2 real (internal) repos; run Phase 1 exit check again on each; measure cost-per-issue, time-to-first-fix-suggestion, human approval rate.
  6. Feedback schema: humans can thumb-up/down a suggestion or post `/reject <reason>` comment; log feedback in a separate table (repo, issue ID, suggestion ID, feedback, timestamp).

- **Rollback:** Disable fix-suggestion prompt; revert to Phase 1 (triage-only).
- **Point of no return:** Once real PRs are drafted or merged (Phase 3), reverting this phase requires a PR undo. Gate this with V3 passing (no tool-call violations, no injections succeed) + Phase 2 exit check (human approval workflow tested).
- **Exit check:**
  - V3 passes: injection suite run in CI on 100 planted jailbreak strings in issue bodies; none escape the tool allowlist or reach unapproved write operations.
  - Cost per issue + cost per fix suggestion on canary: < $0.15 / issue (ASSUMPTION, includes failed fix attempts).
  - Human approval rate: on 50 auto-suggested fixes, ≥ 80% are reviewed within 24 h (cadence check, not correctness yet).
  - No unauthorized writes: audit 100 issues; all changes are comments, labels, assignments, or draft-PR creation (no merges, no force-pushes, no deletes).

**Phase 3 — Auto-label, auto-assign, & feedback iteration**

- **Unlocks:** Confidence to enable auto-merge on safe changes (Phase 4, optional); multi-repo rollout strategy.
- **Depends on:** Phase 2 exit check + V1 (cost validated); Phase 0 exit check (rollback practiced).
- **Tasks:**
  1. Enable auto-label and auto-assign: for issues where model confidence > 70% and labels are in the allow-list (e.g., `bug`, `feature`, `docs`, `stale`), set labels immediately. For assignment, suggest only; do not auto-assign.
  2. Draft-PR creation: when human approves a fix suggestion (via comment or GitHub API), draft a PR (opened, not merged; reviewers set to code owners).
  3. Feedback loop: aggregate human feedback (thumbs, `/reject` comments) into a structured table. Weekly: recompute triage accuracy (precision, recall per label). Use feedback to adjust model prompt or retriever weights.
  4. Cost optimization: evaluate faster/cheaper models (e.g., GPT-3.5, Llama) for low-risk triage; route only high-risk issues to more expensive model. Measure cost reduction and quality regression.
  5. Multi-repo rollout: enable on 3–5 internal repos; measure cost, latency, and approval rate on each. Use metrics to size infrastructure (function concurrency, vectorstore read replicas).
  6. Performance dashboard: plot triage accuracy, cost-per-issue, auto-assign rate, and PR draft rate over time; alert on regressions.

- **Rollback:** Disable auto-label and auto-assign; revert to Phase 2 (suggestion-only).
- **Exit check:**
  - Triage accuracy on feedback set: precision ≥ 0.85, recall ≥ 0.80 per label (measured on 500 issues from canary repos).
  - Cost per issue < budget ($0.15 per issue, including failed fix attempts); cost per resolved issue (issue closed + fix merged or manual action) < $1.00 (UNKNOWN baseline until Phase 3 exit).
  - Auto-label correctness: human reviews 100 auto-labeled issues; none are mislabeled (accept all or none; if rejects > 5, revisit prompt).
  - PR draft quality: on 50 drafted PRs, human review finds ≥ 80% are buildable and logically sound (no compile errors, no obvious logic bugs).

**Phase 4 — Auto-merge (safe changes only) & external rollout**

- **Unlocks:** GitHub Actions automation for simple fixes (e.g., lint, format, dependency updates); candidate for public beta (Phase 5).
- **Depends on:** Phase 3 exit check + V4 (cost per resolved issue < human cost); repository has CI/CD (tests must pass before merge).
- **Tasks:**
  1. Auto-merge policy: draft PR is auto-merged only if (a) PR checks pass (CI/CD green), (b) code review by a code owner is added via a GitHub Action bot, and (c) the change is low-risk (e.g., dependency update, lint fix, documentation—no logic change to production code).
  2. Audit log: every auto-merge is logged (PR URL, change summary, cost, model version, approver bot version). Rollback (revert commit) can be triggered by any maintainer within 24 h.
  3. Safety rails: block auto-merge if the PR touches (a) authentication/auth layer, (b) payment/billing code, (c) data-deletion code, or (d) any file with a manual `no-auto-merge` tag.
  4. Cost per resolved issue: meter the cost of issues that are fully resolved (closed with a merged fix, not just labeled or commented). Validate V4 on canary.
  5. External repo pilot: select 2–3 open-source or internal projects; enable read-only triage + fix suggestions; measure adoption (% issues receiving suggestions, % humans engaging with suggestions).
  6. Human escalation: if a fix suggestion requires context the agent cannot access (e.g., "ask the team lead"), post a comment asking for context; if not provided in 48 h, close the suggestion.

- **Rollback:** Disable auto-merge; all PRs remain drafts and require manual merge.
- **Point of no return:** Once merges start, a rollback cannot undo commits. Gate with V4 passing (cost per resolved < human cost) + Phase 4 exit check (100 auto-merges audited, 0 regressions or security issues).
- **Exit check:**
  - V4 passes: cost per resolved issue < human-support baseline (UNKNOWN; needs support-team data, Phase 3).
  - Merge safety: on 100 auto-merges, no regressions in CI/CD; 0 security issues reported within 7 days.
  - Adoption on pilot repos: ≥ 30% of issues receive suggestions; ≥ 50% of suggestions are engaged (human action within 48 h).

**Phase 5 — Multi-repo, feedback learning, & optimization**

- **Unlocks:** General availability; optional: train a domain-specific fine-tuned model (Phase 6, deferred).
- **Depends on:** Phase 4 exit check + V4 passes.
- **Tasks:**
  1. Roll out to 10+ internal repos; measure cost per issue and approval rate; identify repos where cost is high (poor retrieval, expensive fixes) vs. low (simple triage only).
  2. Feedback-driven tuning: retrain embedding weights or re-chunk repo context for high-cost repos; recompute model prompt based on aggregated feedback.
  3. Cost optimization via routing: use a cheaper model (GPT-3.5) for triage only; route code-fix requests to a more expensive model (GPT-4) only if the issue is labeled high-priority or has ≥ 3 upvotes.
  4. Performance SLO: latency p95 < 15 s; cost per issue < $0.10 (optimized baseline); availability > 99.5% (no triage service blocks issue filing).
  5. Operational monitoring: set up burn-rate alerts for cost; dashboard for latency, cost, and approval rate per repo.

- **Rollback:** Disable new-repo onboarding; stay on Phase 4 rollout set.
- **Exit check:** cost per issue < $0.10; latency p95 < 15 s; user feedback sentiment positive (> 60% thumbs-up on suggestions).

The plan follows the canonical order: Phase 0 (skeleton, read-only, instrumented); V0 passes (production deployment, rollback tested); Phase 1–2 (expand scope, add human gates); V1–V3 pass (cost, retrieval, security); Phase 3–4 (automation, auto-merge); V4 passes (cost per resolved < human cost); Phase 5 (scale).

Alternatives considered but not adopted:
- **Feasibility spike before Phase 0:** Not needed; triage is a straightforward classification task. Retrieval + prompt design is low-risk enough to validate in Phase 1.
- **Air-gapped or production-unreachable skeleton:** Not applicable; GitHub API is the only external dependency, and it is widely available.

### 10. Deliberately deferred

1. **Auto-merge for all code changes** — Deferred to Phase 4, conditional on V4 (cost per resolved < human cost). Blocks: no safe cost data until Phase 3 canary runs.
2. **Fine-tuned model** — Deferred to Phase 6. Blocks: must first validate that prompt + RAG achieves acceptable triage accuracy (V2 pass); fine-tuning is R2 (weeks of data and eval work) and should only be pursued if cost-per-token improves or accuracy gap is > 10%.
3. **Multi-turn fix suggestions (follow-up questions to clarify issue)** — Deferred to Phase 3. Blocks: requires robust feedback & memory layer; Phase 2 establishes single-turn workflow first.
4. **Private repo support** — Deferred to Phase 2. Blocks: Phase 0–1 runs on internal/public repos only; private repos require scoped GitHub token & repo-level access control (organizational dependency: GitHub team access policy).
5. **Security issue handling (auto-remediation)** — Deferred to Phase 4. Blocks: security issues require human approval before any fix is merged; no auto-merge for security fixes until Phase 4 audit passes and a security team sign-off is added.
6. **Feedback-driven fine-tuning** — Deferred to Phase 6. Blocks: must first accumulate 1,000+ issues with consistent feedback (Phase 3–5 accumulation); fine-tuning requires retraining, not just prompt tweaks.
7. **Dashboard & alerting system** — Built iteratively: Phase 0 (basic logs), Phase 1 (cost dashboard), Phase 2 (feedback dashboard), Phase 3 (multi-repo dashboard), Phase 5 (full ops SLO dashboard).
8. **Rollback automation** — Deferred to Phase 4. Blocks: after auto-merge is enabled, a rollback script (revert commit, post comment) must be tested; Phase 0–3 rely on manual rollback or GitHub UI.
