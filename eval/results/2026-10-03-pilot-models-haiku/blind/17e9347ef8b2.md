# BUILD PLAN — CI/CD Platform for 50 Microservices

## 1. Classification and constraints

**What:** A CI/CD platform to unify build, test, and deployment pipelines for 50 microservices currently running heterogeneous tooling (various CI runners, manual deployments, inconsistent artifact storage).

**Type:** Software / infra hybrid; brownfield (services exist; tooling does not). Medium build (multiple teams, regulated data exposure possible, customer-facing traffic affected by deployment failures).

**Dominant constraint:** Availability and correctness of deployments; latency for feedback to developers is secondary; cost is bounded by current spend.

**Worst failure:** A broken pipeline that blocks all 50 teams from deploying—cascading developer productivity loss and inability to roll back critical hotfixes in production.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Pipeline latency (commit to feedback) | p95 < 5 min | ASSUMPTION: developer velocity at 5–10 min feedback is standard | V0 baseline; Phase 2 spike test |
| Deployment throughput (services/hour in production) | ≥ 10 services/hour steady-state | ASSUMPTION: peak is 30/hour (hotfix cascades) | Phase 3 load test |
| Platform availability / SLO | 99.5% (pipeline + artifact store) | ASSUMPTION: tooling downtime ≤ 7.2 hrs/month acceptable | Phase 2 exit check; SLIs active by Phase 3 |
| Rollback / RTO for a single service | ≤ 3 min from decision | REQUIREMENT: stated by ops team | V0 exit check; Phase 1 validation gate |
| Operational complexity | ≤ 2 FTE for day-to-day platform ops | ASSUMPTION: 50 services, mature teams | Phase 4 staffing review |
| Storage cost (artifacts, logs) | ≤ $500/month | ASSUMPTION: based on 6-month retention | Phase 2 design review |

**Missing inputs that would change the plan:**

- Who owns the platform after launch? (Assumed: a dedicated 2-person platform team; if split across services, organizational dependencies emerge.)

## 4. Walking skeleton (Phase 0)

**The one real request:**
Developer pushes a commit to a service's repo (e.g., `services/auth-svc` branch). The platform detects the push via webhook, starts a build, runs tests in a container, tags and pushes an image to the registry, updates a deployment manifest in a GitOps repo, observes the rollout in the dev environment, records the result, and rolls back (one injected failure: image pull failure) to prove the rollback succeeds.

**Every tier it crosses:**
1. **SCM webhook (GitHub/GitLab)** → Platform controller
2. **Platform controller** (build orchestrator; runs on a single VM, no HA yet)
3. **Runner** (Kubernetes Pod or VM; pulls code, runs tests, builds and pushes image to a registry)
4. **Docker registry** (local or managed; artifact storage)
5. **GitOps tool** (Flux or ArgoCD; syncs deployment manifests to the dev cluster)
6. **Kubernetes dev cluster** (deploys the image, health-checks it, serves traffic)
7. **Observability pipeline** (logs → centralized store, traces → agent, metrics → Prometheus)
8. **Rollback orchestrator** (reverts the deployment manifest, triggers rollback in GitOps)

**Deployment and rollback on day zero:**
- Controller and runner stateless (configs in Git, secrets in Vault).
- Entire setup stands up from code (IaC: Terraform or Helm) on day zero; no manual steps after the first apply.
- Rollback: a Git revert of the deployment manifest triggers GitOps rollback; confirmed by reading the cluster state and comparing with Git.
- Failure injection: kill the image pull on rollback; alert fires; operator manually rolls back or deploys the previous manifest.

**Who can reach it:**
Internal networks and allow-listed developer machines only (no external traffic) until Phase 2. Platform runs behind a firewall; webhooks from SCM use a static secret or IP whitelist.

**Observability (day zero):**
- Logs: every step (push detected, build started, test run, image pushed, deployment applied, rollback triggered) goes to stdout (JSON-structured).
- Traces: one W3C trace ID follows the commit from webhook to cluster state.
- Metrics: build duration, test pass rate, deployment success/failure, rollback latency.
- Baseline: record all measurable budgets at zero load (sub-second latency within internal network; no failures).

**Exit check (V0):**
- A real commit triggers the full pipeline: push → build → test → artifact → deploy → health check → verify running → rollback → verify reverted.
- Deploy and rollback succeed.
- One failure (image pull) is injected mid-rollback; alert fires and is visible in the log store.
- All three measurable budgets are recorded as baselines: latency (build + deploy time), rollback latency, and uptime (no errors).
- All tasks complete in a single namespace and cluster; no multi-region or HA setup yet.

## 5. Phases (dependency order; rework widest first, exposure smallest first)

### Phase 1 — Vault + core pipeline for 1 service
**Unlocks:** Secret injection for all downstream services; a pattern for the remaining 49.

**Depends on:** V0 (Phase 0 complete). Phase 0 proves the end-to-end path exists.

**Tasks:**
1. Deploy HashiCorp Vault in the dev cluster (static auth, no dynamic credentials yet). V1 gate: Vault is up and the runner injects a test secret into a build.
2. Define the config schema (YAML) for a service pipeline: build commands, test suite, deployment target, rollout strategy (immediate vs canary).
3. Add the 1st real service (`auth-svc`) to the platform using the schema: fork its build steps from the legacy CI, add Vault secrets, run the full pipeline on its next commit.
4. Validate deployment health checks (the new manifest includes readiness probes; they pass before GitOps considers the rollout complete).
5. Capture audit logs: every secret read, every deployment, every rollback is logged with timestamp and operator (if manual).

**Rollback:** Phase 1 reverts the Vault deployment and service config; all 49 services remain on the old system.

**Exit check:** V1 passes; `auth-svc` is built, deployed, and rolled back twice with no data loss. Secrets are redacted from logs and audit events.

### Phase 2 — Scale to 10 services + staging environment
**Unlocks:** Confidence that the platform scales horizontally; Staging matches production topology.

**Depends on:** V0, Phase 1, V1 (Vault + 1 service).

**Tasks:**
1. Build a staging environment (mirror of dev; services run on dedicated cluster or namespace).
2. Add 9 more services (sampled across tech stacks: Node, Go, Python, Java) to uncover config schema gaps and runner bottlenecks.
3. V2 gate: The schema accommodates all 9 without modification; if not, revise and re-test on the 9.
4. Load test the platform: run pipelines for all 10 services in parallel (simulates peak: commits from all 10 simultaneously). Measure pipeline latency (build + deploy) at p95; confirm it stays <5 min and throughput is ≥ 10/hour.
5. Set up SLIs and burn-rate alerts: measure platform availability and pipeline success rate; set burn-rate thresholds at 5% per day.
6. Spin up artifact garbage collection: delete images > 6 months old; verify retention policy is enforced.

**Rollback:** Phase 2 shuts down staging; services 2–10 revert to the old pipeline; auth-svc stays on the new platform.

**Exit check:** V2 passes (schema accommodates all 9); load test shows p95 latency < 5 min and throughput ≥ 10/hour on 10 services. SLI dashboards are live and no critical alerts fire in a 4-hour steady run.

### Phase 3 — Production readiness: secrets, rollback, and canary for 50 services
**Unlocks:** All 50 services can be onboarded. Production deployments can use the platform.

**Depends on:** V0, Phase 1, Phase 2, V1, V2. Rework is widest here: every service must adopt the config schema and pass the rollout check.

**Tasks:**
1. **Production Vault:** Deploy Vault in production with HA (3 nodes, replicated across zones; backed by managed DB). V3 gate: Vault is up, unsealed, and all dev + prod services can authenticate.
2. **Canary rollout:** Implement traffic-split (via load balancer or service mesh) to deploy a new service version to 5% of traffic, measure error rates and latency, expand to 25% then 100% or rollback.
3. **Bulk onboarding:** Ramp 40 services in waves of 5–10 (two per week, blitzing on Friday); each wave runs its pipeline on the new platform before the old pipeline is disabled.
4. **Health checks:** Every service must define readiness and liveness probes in its deployment manifest; the platform does not mark the rollout complete until probes pass for 10 seconds.
5. **Rollback validation:** Test rollback on each wave (inject a bad image or kill the health check; verify rollback succeeds and traffic re-routes to the stable version) before disabling the old pipeline.
6. **Cross-service config validation:** A service's pipeline can reference secrets, resources, and deployments scoped to that service; a config cannot reference another service's resources or secrets. V4 gate: all 50 services' configs pass isolation checks; if any fail, reject the config and require a fix before onboarding.
7. **Cutover gate (V5):** All 50 services are on the new platform for 2 weeks without fallback; error rate and latency are within baselines (V0 recorded); no manual interventions needed. If any metric exceeds baseline, the flip condition triggers a rollback plan for that service.

**Rollback:** If V5 fails (one or more services exceed error-rate baseline), those services revert to the old pipeline; the platform remains in place for the passing services.

**Exit check:** V3, V4, V5 pass. All 50 services are on the new platform. Error rate, latency, and deployment throughput are stable and match baselines. The old CI system is kept as a standby for 2 weeks; then decommissioning begins (Phase 4).

### Phase 4 — Operationalization and handoff
**Unlocks:** The platform becomes the single source of truth for CI/CD; the platform team can shrink to 1 FTE (if adoption is high).

**Depends on:** V0, Phase 1, Phase 2, Phase 3, V1, V2, V3, V4, V5.

**Tasks:**
1. Decommission the old CI system: no more webhooks to legacy runners; old artifact storage is archived.
2. Runbook automation: on-call playbooks for common alerts (queue depth, Vault seal, artifact store full). V6 gate: a runbook is tested end-to-end; an on-call engineer can follow it and resolve the issue in < 15 min without platform team help.
3. Cost accounting: tag all resources by service; bill back to service teams (optional, depends on organizational policy).
4. Feedback loop: survey the 50 teams on pain points; prioritize improvements.

**Rollback:** The old system is archived; rollback is a restore-from-archive and manual re-enablement of old runners (weeks of work; only in case of critical platform flaw).

**Exit check:** V6 passes. The old system is decommissioned. The platform team can document day-to-day operations and hand off to a single engineer on rotation.

## 9. Methodology exceptions

**E1 — Feasibility spike before skeleton**

- **Rule bypassed:** Walking skeleton first (principle 6).
- **Why it does not apply:** The main risk is whether the config schema can represent the heterogeneous build and deploy steps across 50 services (Node/npm, Go/make, Python/poetry, Java/Maven, custom bash scripts). Running a skeleton on just one service hides this risk until Phase 1 or Phase 2, when rework is expensive.
- **Replacement validation:** Two-week spike (parallel to Phase 0): define the config schema on paper, code the validator, and test it against the actual build configs of 6 sampled services (mix of tech stacks). The spike validates the schema, not the deployment.
- **Evidence required:** Schema spec (markdown), validator source code, and test results (6 services: pass/fail per config). Stored in Git.
- **Resumes when:** The spike passes (all 6 configs are valid) and Phase 0 builds the skeleton on auth-svc (also runs through the validator). If the spike fails, the schema is revised and the 6 services are re-tested before Phase 0 starts (delays Phase 0 by ~1 week).

## 10. Deliberately deferred

- **Multi-region deployment (replica clusters in EU, APAC):** Pull forward when customers are in multiple regions and latency from the primary region becomes a blocking complaint; likely Phase 5 or later.
- **Dynamic service-to-service secrets (e.g., Vault service identity for pod-to-pod auth):** Deferred until microservice mesh (Istio / Linkerd) is in place; likely Phase 4 or later.
- **AI-driven anomaly detection for SLI thresholds:** Deferred until the platform operates for ≥ 3 months with stable baselines; Phase 5+.
- **Billing and chargeback (cost per service per month):** Deferred until Phase 4; added only if organizational policy mandates it.
- **Self-service UI for config creation (drag-and-drop pipeline builder):** Deferred until adoption of YAML configs stabilizes; Phase 4 exit survey will inform the decision.
- **Custom metrics and webhooks for third-party notifications (PagerDuty, Datadog, custom webhooks):** Deferred until Phase 4; available as a plugin model in Phase 5.
