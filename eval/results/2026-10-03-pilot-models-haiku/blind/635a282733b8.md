# Plan — Multi-Tenant SaaS Billing System

## 1. Classification and constraints

**What:** A multi-tenant subscription and usage-based billing platform that calculates charges, generates invoices, collects payments, and reconciles ledger entries across isolated customer accounts.

**Type:** Software; greenfield; not small (multi-tenancy model, financial data, regulatory exposure, complex domain logic).

**Dominant constraint:** Correctness (billing errors compound; a $1 error per customer per month compounds to liability and churn); compliance (PCI DSS for card handling, revenue recognition rules, tax jurisdiction rules, data residency for some customers). Availability is secondary (a 4-hour window to resolve a billing run is acceptable; real-time payment processing is outsourced to a payment processor).

**Worst failure:** Silent billing error (double charge, skipped charge, or wrong amount per tenant) that goes undetected for weeks: financial loss for customers, legal liability, churn, and reputational harm.

**Budgets:**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency (billing run) | Monthly invoice generation < 1 hour for all tenants | ASSUMPTION: 100K active customers, ~200K line items/month; a 1-hour window is acceptable per product owner | V2 (batch throughput) |
| Latency (payment capture) | < 5 s (blocking) | REQUIREMENT: payment UX; real-time feedback to customer | V0 (skeleton), Phase 3 (at scale) |
| Throughput (API: read queries) | 1,000 requests/s at peak (dashboards, ledger lookups) | ASSUMPTION: based on typical SaaS usage; confirm with product owner | Phase 3 load test |
| Throughput (batch: monthly invoicing) | 100K customers billed in parallel within 1 hour | ASSUMPTION: tenant count and data size; if 200K+, re-evaluate job topology | V2 |
| Availability / SLO | 99.5% (scheduled maintenance window 2 h/month; payment outages routed to processor's status) | ASSUMPTION: internal commitment; no customer-facing SLA stated | Phase 4 SLI target |
| RPO / RTO | RPO = 1 hour (last billing checkpoint); RTO = 4 hours (restore from backup and re-run recent transactions) | ASSUMPTION: financial audit trail requires daily snapshots | Phase 2 (backup design gate V1) |
| Data residency | EU customer data in EU region; US / APAC in AWS US-East / AP-Southeast | REQUIREMENT: GDPR + local law; non-negotiable per legal | Phase 1 (tenant onboarding) |
| PCI DSS scope | SAQ A-EP: card entry only via processor's hosted fields; no storage of card numbers | REQUIREMENT: risk reduction; reduces certification cost | V3 (risk/security) before Phase 3 |
| Operational complexity | ≤ 2 teams; no self-hosted cluster; managed database and message queue | ASSUMPTION: team size | Phase 3 exit check |

**Missing inputs:**

- Payment processor selection (Stripe, Adyen, etc.): blocks Phase 3 (API integration). Assumed Stripe for planning.
- Customer data residency tiers and count per region: blocks tenant isolation design if multi-region is required. Assumed US-only for MVP; EU expansion deferred.
- Tax jurisdiction rules scope (sales tax, VAT, GST): planning assumes US only; if multi-jurisdiction, Phase 2 expands and V4 (tax engine) gates Phase 4.
- Invoice retention policy and audit-log compliance: blocks data-lifecycle design in Phase 2. Assumed 7-year retention (US IRS + SOX equivalent).

## 4. First end-to-end slice (Phase 0)

**Real request:** A test tenant creates a usage event (e.g., "10 API calls logged"). The system records the event in the ledger, applies a pricing formula (USD 0.05/call = $0.50), generates an invoice entry, and returns the posted ledger balance to the tenant's API client. A second request reconciles the processor's webhook (simulated payment of $0.50), which updates the invoice state to "paid."

**Every tier:**
1. **API Gateway** (bare endpoint, no auth yet): POST /v1/tenants/{tenant_id}/events → validates tenant_id exists
2. **Ledger Service** (monolith): accepts the event, applies posting rule, writes to ledger table via Postgres transaction
3. **Database** (Postgres, single primary): persists event, ledger posting, and invoice entry with `tenant_id` and `created_at` index
4. **Invoice Generator** (batch job, in-process): query and aggregate ledger postings for the test tenant, write to `invoices` table
5. **Payment processor simulation** (mock): in V0, a local test sends a webhook to the event queue
6. **Event Queue** (RabbitMQ, shared by all tenants; access controlled by tenant_id): webhook handler consumes, updates invoice state to "paid," triggers reconciliation alert
7. **Observability** (logs, metrics, trace): every API call, ledger posting, invoice state transition, and error logged with tenant_id; metrics: API latency p99, ledger writes/s, invoice generation time
8. **Rollback** (git + database snapshot): redeploy previous commit; restore database from pre-test snapshot via automated backup

**Who can reach it:** Internal IP only (no public route); test tenant flagged in code; no real payment processor or customer data.

**Exit check (V0):** 
- ✓ One POST /v1/tenants/{test_tenant}/events succeeds with 200 and a trace across ledger, database, and invoice generator.
- ✓ Deploy to staging via CI pipeline (git push → container build → database migration → helm install).
- ✓ Rollback succeeds (redeploy previous commit, database reverts to backup).
- ✓ Injected failure (e.g., database connection failure) fires a metric alert in 5 s.
- ✓ Baselines recorded: API latency p99 = 45 ms (floor, 1 concurrent call), ledger write = 8 ms, invoice generation = 120 ms for 1 tenant (near-zero load).

## 5. Phases (Phase 1 onward)

### Phase 1 — Ledger schema and tenancy model hardening

**Unlocks:** Multi-tenant invoice schema, real tenant provisioning, per-tenant tests.

**Depends on:** V0 passes; tenancy model decision (§3) fixed.

**Tasks:**
1. Design and migrate schema:
   - Ledger table: `(id, tenant_id, account_id, debit_amount, credit_amount, posting_date, created_at)` with PK on (tenant_id, id); indexes on (tenant_id, posting_date), (account_id, posting_date).
   - Invoice table: `(id, tenant_id, invoice_number, start_date, end_date, total_amount, state, created_at)` with state ∈ {draft, posted, paid, refunded}.
   - Add Postgres RLS policy: tenants can only read/write their own tenant_id rows.
   - Test: no row leaks across tenant_id in queries; RLS blocks query for tenant A on tenant B's data.

2. Implement tenant provisioning:
   - Tenant registry table: `(tenant_id, name, plan, region, created_by, created_at)`.
   - Provisioning API: POST /v1/admin/tenants (internal only) → creates tenant, initializes ledger account, stores in registry.
   - Test: two test tenants can co-exist; ledger rows are isolated by RLS.

3. Data residency routing:
   - Add `region` to tenant registry and Connection Pool selector: tenant in US-East → connect to US-East Postgres.
   - For MVP (US-only), single region; placeholder for Phase 5 (multi-region).
   - Test: tenant row successfully queried via correct region.

4. Build versioned ledger posting rules engine:
   - Struct: `PostingRule { plan_id, event_type, debit_account, credit_account, formula(usage_quantity) }`.
   - Example: plan "starter" + event "api_call" → debit "revenue", credit "accounts_receivable", formula = quantity × $0.05.
   - Test: posting rule applied correctly; ledger balance equals cumulative postings.

**Rollback:** redeploy Phase 0 schema; RLS policies remain but are not enforced (tenants self-isolated by code); no data loss (schema is additive).

**Exit check:**
- ✓ Two co-resident test tenants post events; ledger rows are isolated by RLS and verification query.
- ✓ Tenant provisioning API creates and initializes a tenant in < 100 ms.
- ✓ Posting rule engine applies rules correctly for 5 plan/event combinations.
- ✓ V1 passes (see §6).

### Phase 2 — Backup, recovery, audit trail, and reconciliation state machine

**Unlocks:** Phase 3 (real payment processor integration); multi-week runaway ledger will be checkpointed and reconciled.

**Depends on:** Phase 1; V1 passes; data residency approval from legal (organizational, in-hand before Phase 3).

**Tasks:**
1. Implement backup and recovery:
   - Daily snapshot of Postgres (WAL archiving to S3, full backup once per week) at 02:00 UTC.
   - RTO test: restore from 1-week-old backup, re-run recent transactions, compare ledger balance to source of truth (processor API for payments; billing rules for events).
   - Retention policy: backups kept for 90 days; older backups moved to Glacier.
   - Test: recovery to 1 day ago successfully restores all ledgers, with no tenant data loss.

2. Build audit trail (read-only ledger snapshot + append-only event log):
   - Create `ledger_audit_log` table: `(id, tenant_id, action, old_value, new_value, actor, timestamp)`.
   - On every ledger update: insert one row into `ledger_audit_log` (INSERT is append-only; UPDATE/DELETE on ledger itself is forbidden for posted rows).
   - Policy: invoice state transitions are audited; ledger entries are immutable once posted.
   - Test: audit trail shows every state change; no ledger row is modified in-place.

3. Payment state machine and reconciliation:
   - Invoice states: draft → posted → (pending_payment | paid | refunded).
   - Payment event states: (pending_capture | captured | failed | disputed).
   - Reconciliation job (runs after batch invoicing): compare invoice state to processor's payment status; detect mismatches (e.g., invoice marked paid but processor shows failed); emit alert.
   - Test: invoices and payments reconcile; mismatches are detected and logged.

4. Event schema (payment processor webhooks):
   - Event table: `(id, tenant_id, processor_event_id, event_type, payload, processed_at, status)` (status ∈ {pending, processed, failed}).
   - Idempotency: (tenant_id, processor_event_id) is unique; duplicate webhook is no-op.
   - Test: webhook processed once, even if sent twice.

**Rollback:** Phase 1 state; audit table is new and can be dropped; no ledger re-writes.

**Exit check:**
- ✓ V1 passes (see §6).
- ✓ Backup and restore RTO test succeeds.
- ✓ Audit trail immutability verified (audit table is append-only; ledger rows are not updated).
- ✓ Reconciliation job runs on test invoices and detects a mismatch.

### Phase 3 — Payment processor integration, real-tenant onboarding, and batch billing at scale

**Unlocks:** Phase 4 (production cutover); real customers can be billed.

**Depends on:** Phase 2; V2 passes (batch throughput); V3 passes (PCI compliance); payment processor contract in hand; Stripe API keys configured.

**Tasks:**
1. Stripe integration:
   - Implement webhook handler: POST /webhooks/stripe → parses `charge.captured`, `charge.failed`, `invoice.payment_succeeded` events.
   - On `charge.captured`: update payment event state to "captured"; trigger reconciliation check.
   - Implement payment capture API: POST /v1/tenants/{tenant_id}/payments → calls Stripe API (hosted form only; no card data in our system).
   - PCI scope check: card entry only via Stripe hosted fields; no card numbers in logs, database, or API requests. Verify by scanning logs and database schema (V3).
   - Test: end-to-end payment flow (event posting → invoice creation → payment capture → reconciliation) succeeds on test tenant with test Stripe account.

2. Batch invoicing at scale:
   - Job: query ledger for all tenants, aggregate by tenant+period, generate invoices, emit for dispatch.
   - Parallelization: shard by tenant_id; 10 concurrent workers per region, each handling up to 10K tenants.
   - Run test: 100K test tenants with 200K ledger entries each → invoice generation completes in < 1 hour.
   - Idempotency: invoice generation is re-runnable; duplicate invoices are deduplicated by (tenant_id, period, hash).
   - Test: V2 passes (see §6).

3. Real tenant onboarding (internal):
   - Create onboarding checklist: (tenant name, plan, region, legal approval, PCI scope confirmation).
   - API: POST /v1/admin/tenants → validates checklist, provisions tenant, creates onboarding token.
   - Test: three test tenants onboarded; each can post events and generate invoices.

4. Load test at target scale:
   - Simulate 100K tenants, 10 events/tenant/day, 5 concurrent API requests → measure latency (p95, p99), database load, queue depth.
   - Pass threshold: p99 API latency < 500 ms, database CPU < 70%, queue depth recovers within 5 min.
   - Test: Phase 3 exit check includes load test results.

**Rollback:** disable Stripe integration flag in code; fall back to Phase 2 (test payments only); real payments are rejected with a maintenance message.

**Exit check:**
- ✓ V2 passes (batch throughput).
- ✓ V3 passes (PCI scope validation).
- ✓ End-to-end payment flow (post event → invoice → capture payment → reconcile) succeeds on real Stripe test account.
- ✓ Load test at 100K tenants, 10 events/tenant/day passes (p99 latency < 500 ms, database CPU < 70%).
- ✓ Real-tenant onboarding succeeds for three test customers.

### Phase 4 — Production launch and 24/7 operations

**Unlocks:** Paying customers; production monitoring and on-call rotations; planned Phase 5 work (multi-region, advanced features).

**Depends on:** Phase 3; V4 passes (tax engine, if multi-jurisdiction; else deferred); SLI targets confirmed; on-call runbook signed off; legal/security clearance.

**Tasks:**
1. Activate production database and Stripe account:
   - Migrate from test to production Postgres (same schema, new cluster, point-in-time backup of Phase 3 test data, then wiped).
   - Configure Stripe production API keys; webhooks point to production endpoint.
   - Enable alerting: PagerDuty integration for invoice failures, reconciliation mismatches, SLO breaches.
   - Test: canary tenant (first customer) successfully posts events and receives invoice.

2. Canary rollout (5% of paying customers):
   - Flag `use_new_billing` applies to 5% of customers; 95% route to legacy system or manual billing (Phase 5 cutover).
   - Monitoring dashboard: invoice accuracy (compare to legacy system), latency, error rate, reconciliation drift.
   - Threshold: if accuracy < 99.9% or reconciliation drift > 0.1%, halt and investigate.
   - Run for 1 week; if stable, expand to 25%, then 100%.

3. On-call handoff and runbooks:
   - Runbook: ledger reconciliation failure → manual reconciliation steps → re-run batch job.
   - Runbook: invoice not generated → query batch job logs → re-run for specific tenant.
   - Runbook: payment webhook not received → query Stripe API → manually trigger reconciliation.
   - On-call engineer trained and on rotation.

4. Production observability hardening:
   - Dashboard: invoice volume, error rate, reconciliation accuracy, SLO burn-down.
   - Alerts: invoice generation misses deadline (> 1 h), reconciliation drift > 0.1%, payment webhook latency > 10 s.
   - Test: injected failure (e.g., database unavailability) fires alert in < 5 s.

**Rollback:** Kill feature flag (set `use_new_billing` = false for all customers); all traffic routes to legacy system; no data loss (both systems write to same ledger during overlap).

**Exit check:**
- ✓ Canary tenant (internal) invoiced correctly and reconciled.
- ✓ Canary rollout to 5% of customers: run for 1 week with < 0.1% error rate and invoice accuracy ≥ 99.9%.
- ✓ SLI dashboard: latency p99 < 500 ms, availability ≥ 99.5%, reconciliation drift < 0.1%.
- ✓ On-call rotation active; runbooks tested.
