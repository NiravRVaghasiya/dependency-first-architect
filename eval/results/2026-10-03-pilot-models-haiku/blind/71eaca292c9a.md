# BUILD PLAN: CI/CD Platform for 50 Microservices

## 1. Classification and constraints

**What:** A unified CI/CD platform to orchestrate builds, tests, deployments, and rollbacks for 50 independently developed microservices across multiple deployment environments.

**Type:** Software infrastructure; greenfield platform, but brownfield for the 50 consuming services (they have existing pipelines or manual processes).

**Dominant constraint:** Availability (the platform becomes a critical path blocker; any extended outage halts all 50 services' deployments); secondarily, latency (feedback speed drives developer productivity and incident response).

**Worst failure:** A platform failure during a production incident that prevents rollback or emergency patching of a service, compounding customer impact and lengthening MTTR.

## 3. Tradeoff gates (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Consistency (CI config) vs availability (quick feedback) | R2 — impacts 50 services' feedback loop if changed | Optimize for availability first: fast feedback on commit (< 5 min); consistency enforced via contracts, not runtime validation | Services tolerate eventual consistency in test results (flaky tests addressed separately) | Phase 1 exit check: feedback latency meets target at peak load; Phase 2: flakiness rate < 1% | If p95 latency > 8 min, split fast and slow test tiers; if flakiness > 3%, add deterministic re-test stage |

| Secrets management — centralized vs distributed | R3 — coupling all 50 services' secrets to one service creates systemic risk if compromised | Centralized secrets backend (HashiCorp Vault, Sealed Secrets, or cloud-native secret manager) with auditable access and rotation; read by runners at deploy time, never stored in job artifacts | Centralized has one point of failure; mitigated by disaster-recovery and per-service temporary credentials | V0 walk-through: inject a secret into one job without leaking it into logs or artifacts; Phase 1 rotate a secret and verify no service breaks; Phase 2: audit log completeness check | If a service logs a secret by mistake, root-cause and add scrubbing; if Vault downtime > 15 min, trigger RTO drill |
| Deployment strategy per service — one strategy vs configurable | R2 — high operational burden if each service has a bespoke strategy | Offer a library of standard strategies (blue-green, canary, rolling) and a configuration DSL; services declare choice in their manifest, not by hand | 80% of services will fit one of the three; custom strategies deferred | Phase 2: test all three on pilot services; Phase 3: onboard long tail | If a service's failure rate under canary > 5%, trigger rollback and pause that service's further onboarding |

## 4. Walking skeleton (Phase 0)

**Request:** One real microservice (canary service) from the 50, with a realistic code change, passes through the new platform from commit to production within the latency targets, with a rollback verified.

**The path:**
1. Developer pushes a feature branch to GitHub (or equivalent).
2. Platform detects push, triggers build pipeline: syntax check → unit tests → integration tests → container image build → push to registry → approval gate.
3. Merge to main → automated canary deployment (0% traffic initially, then 10% for 1 minute, then 100% if no errors).
4. Monitor platform's own logs, metrics, and the service's observable (status code, latency, errors) for 2 minutes.
5. If healthy, mark deployment live; if unhealthy, automated rollback to previous image.
6. Trigger manual rollback verification: revert the image, confirm service recovers.

**Tiers crossed:**
- **Source control** (GitHub or GitLab): webhook → builder
- **Job orchestration** (CI/CD platform's control plane: Buildkite, GitHub Actions, or GitLab Runner manager): queues the build
- **Builder runner** (ephemeral container): checkout, test, build image
- **Artifact storage** (container registry: Docker Hub, ECR, or private registry): push image
- **Secrets backend** (Vault, Sealed Secrets, or cloud secret manager): retrieve registry credentials and deploy-time credentials
- **Deployment orchestrator** (kubectl, cloud API, or Nomad): apply deployment manifest with promotion gates
- **Target environment** (Kubernetes cluster, ECS, or Lambda): run the container, serve traffic
- **Observability backend** (logs: CloudWatch, Datadog, or ELK; metrics: Prometheus or cloud metrics): ingest traces, metrics, and logs from the service

**Deployment, logging, monitoring, and rollback (day zero):**
- **Deploy:** Service manifest includes: image digest (immutable), resource requests, health checks, deployment strategy (canary: 10% for 60 s, then 100%), revision history (keep 2).
- **Logging:** All platform and service logs routed to central log aggregator; platform logs tagged with service name, build ID, deploy ID; searchable within 2 s.
- **Monitoring:** Dashboard shows: platform build queue depth, runner utilization, deploy duration per service, service error rate during deploy. Alert fires if error rate > baseline + 2 σ during deployment.
- **Rollback:** Automated: if service error rate > 5% or latency p95 > 1.5× baseline during canary, kill canary traffic and revert to previous image. Manual: click "Rollback" button, confirm in Slack, deploy reverts to previous safe revision.

**Access:** Only internal engineers and the platform team can trigger builds and deployments. Webhook from GitHub is allowed only to the platform's Build API endpoint; all other requests blocked.

**Defaults, not hardened:**
- Single-region, single zone (no HA yet).
- No rate limiting or quota enforcement (Phase 1).
- No per-service RBAC (Phase 1); single "can deploy" role for all service teams.
- Secrets injected as environment variables (not mounted files; Phase 1 hardens this).

**Exit check (V0):** 
- A real commit to the canary service's feature branch triggers a build that passes all stages within < 5 min.
- Merge to main triggers a deployment that reaches 10% canary within < 2 min and promotes to 100% within < 4 min if no alerts fire.
- Injected-failure test: manually trigger an error in the service (e.g., kill a pod); platform alert fires within 10 s; manual rollback succeeds within 2 min.
- All three flow events produce searchable logs and traces in the aggregator; platform operator can correlate build → deploy → service behavior in < 30 s.
- First baseline values recorded: build latency, deploy latency, runner utilization at one concurrent service build, control-plane memory and CPU.

## 5. Phases (Phase 1 onward)

### Phase 1 — Build Infrastructure & Core Observability

**Unlocks:** Platform scales to concurrent builds; runbooks and alerting are in place.

**Depends on:** V0 passes (canary service through full deploy cycle and rollback works).

**Tasks (in order — rework widest first, exposure smallest first):**

1. **Orchestration platform baseline** (widest rework if wrong): Provision and baseline the control plane (Buildkite/GitHub Actions/GitLab CI on target infrastructure). Run V1 load test at 100% concurrent (50 services with simultaneous builds), measuring queue latency, runner startup time, and control-plane CPU/memory. Confirm throughput target (2 concurrent builds per service, 50 simultaneous) met.

2. **Runner fleet auto-scaling** (foundation for Phase 2 rollout): Configure runners to spawn on demand. Test: trigger 50 builds at once; measure time to first job start (target: < 30 s) and time to all jobs running (target: < 2 min). Confirm cost stays below budget at idle (< 30% CPU).

3. **Artifact storage durability and audit**: Immutable container image storage (content-addressable; digest is the truth). Test: push an image, kill the registry VM, provision a new one from backup, verify image is restorable and digest matches. Record the RTO and RPO (target: < 4 hours, < 1 hour). Add versioning and retention: keep last 10 per service, retain all production images indefinitely, evict others after 30 days.

4. **Secrets backend and lifecycle** (blocking exposure): Deploy centralized secrets manager (Vault, Sealed Secrets, or cloud). Implement secret injection into build and deploy jobs without leaking into logs. Test: Inject a secret into a job; grep logs and artifacts for the secret; confirm zero instances. Test rotation: change a secret in Vault; re-run an old job; confirm it uses the new secret. Add audit logging: every secret read/write is logged with user, timestamp, and reason.

5. **Observability: telemetry schema and aggregation**: Define structured logs: every platform event (build start, job enqueue, deploy apply, rollback) contains: timestamp, service name, build ID, deploy ID, user/automaton, action, duration, result (pass/fail), and error detail. Ingest into centralized log aggregator (ELK, DataDog, or equivalent). Set baseline: latency of log ingest-to-queryable < 2 s (measured in Phase 1 exit check).

6. **Observability: platform metrics and alerting**: Collect platform metrics: build queue depth, runner utilization, deploy duration per service, MTTR, rollback count per week. Export to metrics store (Prometheus or cloud metrics). Set alerts: build queue depth > 10, runner utilization > 80%, deploy duration > 15 min, error rate > 1% (measured per service). Alert delivery: PagerDuty or Slack for platform team.

7. **Runbook and incident response**: Document the top 5 failure modes (build queue stuck, registry unavailable, secrets backend down, runner OOM, control-plane unhealthy). For each: detection (the alert), diagnostics (log queries to run), mitigation (manual steps or automated remediation), escalation (who to page, when). Test one runbook (registry unavailable): simulate failure, confirm alert fires, run diagnostics steps, verify resolution. Time to mitigation: < 10 min.

8. **Service team on-ramp documentation**: Document how to add a service to the platform: commit a `.platform.yaml` file with build and deploy config, trigger an onboarding job, integrate with the platform dashboard. Test: new engineer (not on platform team) onboards a dummy service end-to-end without questions.

**Rollback for Phase 1:** Control-plane state is version-controlled (Kubernetes manifests in Git). Runners are stateless and ephemeral. If a control-plane change causes failures, revert the commit and re-apply; live builds are unaffected (they run on runners). Artifact storage and secrets backend are backed up nightly; full restore is < 4 hours. No point of no return; Phase 1 is fully reversible.

**Exit check (V1 — load test + baseline observability):**
- V1 passes: 50 concurrent builds start within 30 s, all running within 2 min, at < 30% idle CPU and < 5 min feedback latency p95.
- Artifact storage: image push and retrieval latency < 5 s; backup/restore RTO < 4 hours, RPO < 1 hour, verified in a test.
- Secrets: one secret injected and rotated without leaking or breaking a job; audit log complete.
- Observability: all platform events logged, aggregated, and queryable within 2 s; alerts for queue depth, utilization, duration firing correctly.
- Runbook test: registry unavailable scenario resolved within < 10 min following the runbook.

### Phase 2 — Deployment Safety & Service Onboarding (Wave 1)

**Unlocks:** 10–15 services migrate to the new platform; safe promotion through environments; secrets and RBAC per service.

**Depends on:** Phase 1 exit check and V1 pass; V2 (promotion strategy validated).

**Tasks:**

1. **Deployment promotion strategy** (widest rework; blocking Phase 2 rollout): Implement per-service promotion manifests: define dev → staging → production promotion gates (approval, time-of-day restrictions, canary percentage, success metrics). Test on the canary service: merge a change, watch it flow dev → staging (auto) → prod canary (10% for 60 s) → prod 100% (if canary healthy). Confirm: error rate stays < 0.1% above baseline during canary; rollback happens automatically if error rate > 1%.

2. **Per-service RBAC and secrets** (blocking exposure): Extend secrets backend: each service gets a namespace. Developers can reference "db password" in their deploy manifest; the platform injects the actual secret for their service only (read-only access). Implement service-level deploy approval: service lead can approve deploys for their service only. Test: developer from Service A tries to deploy Service B; platform denies. Developer from Service A deploys Service A; succeeds. Audit logs show both attempts.

3. **Test-suite integration and flakiness detection**: Each service's `.platform.yaml` lists its test suites (unit, integration, e2e) with timeouts and failure thresholds. Platform runs them in parallel. Implement flakiness detection: if a test fails then passes on the same commit (within the same build), flag as flaky and don't fail the build, but log for the service team to fix. Measure: flakiness rate per service at end of phase.

4. **Canary deployment validation** (V2 prerequisite): On the canary service, deploy 5 real changes and measure: error rate delta during canary (target: ≤ 0.1% above baseline), latency delta (target: ≤ 5% above baseline), time to detection if a bad change slips through canary (target: < 2 min). Use synthetic probes + real service metrics. Confirm automated rollback happens and succeeds. Acceptance threshold: all 5 changes meet targets; if not, adjust canary percentage, duration, or metrics before Phase 2 rollout.

5. **Dashboard and service team visibility**: Build a service team dashboard: recent deploys, their status, error rates before/after, rollback history. Allow service teams to view their own logs and metrics, not others'. Include a "request more compute" button tied to Phase 3 cost review.

6. **Wave 1 service onboarding (10–15 services)** (exposure smallest first; rolling onboarding):
   - Weeks 1–2: Onboard 3 lowest-risk services (internal-only, high test coverage, simple deployment). Measure: all 3 deploy via the platform daily for one week with zero unplanned rollbacks.
   - Weeks 3–4: Onboard 5 services (customer-facing, moderate risk). Measure: no incident caused by platform; MTTR same or better than before.
   - Week 5: Onboard 7 services (remaining low-risk). Measure: weekly burn-rate for the platform < 2% (99.8% uptime).
   - If any wave has > 1 incident caused by the platform, pause onboarding and re-plan.

7. **Rehearsed disaster recovery for Phase 2**: Simulate control-plane loss; restore from backup; verify all 10–15 services can deploy. Confirm RTO < 4 hours. Test rollback of a bad image: all services can revert to a previous working image. Confirm rollback succeeds for at least 2 services concurrently.

**Rollback:** Services onboarded in Phase 2 keep their old pipeline (the fallback) active during wave 1. If the new platform has an extended outage, service leads can manually trigger the old pipeline to deploy. Once a service has run successfully on the new platform for 1 week with zero unplanned incidents, the old pipeline is decommissioned for that service. (No phase-wide rollback; each service can flip back individually until its cutover gate passes.)

**Exit check (V2 + Phase 2 exit check):**
- V2 passes: 5 canary changes flow dev → staging → prod canary and promote correctly; error/latency deltas during canary ≤ targets; automated rollback fires and succeeds.
- 10–15 services onboarded, each deploying at least daily for 1 week via the platform, zero unplanned rollbacks, no platform-caused incidents.
- Disaster-recovery: control-plane loss → restore → all 10–15 services can deploy within < 4 hours.
- Service team dashboards deployed and in use; self-service log/metric access working.

### Phase 3 — Scale to All 50 Services & Cost / Operational Hardening

**Unlocks:** All 50 services on the platform; cost tracking and per-service chargeback; incident response proven.

**Depends on:** Phase 2 exit check and V2; V3 (operational load test at 50 concurrent services).

**Tasks:**

1. **Remaining 35 services onboarding (Waves 2–3)** (exposure smallest first; rolling):
   - Week 1: Onboard 12 services (Wave 2, low-to-medium risk).
   - Week 2: Onboard 12 services (Wave 2, continued).
   - Week 3: Onboard 11 services (Wave 3, including highest-risk).
   - Measure each wave: zero platform-caused incidents, MTTR ≤ previous system.
   - If any wave has > 1 incident, pause and troubleshoot before continuing.

2. **Operational load test at 50 services** (V3): All 50 services trigger builds and deploys simultaneously (simulated: e.g., a scheduled build + manual test deploy). Measure: build queue depth peak, runner utilization, control-plane CPU/memory peak, latency p95 for build and deploy, alert latency. Confirm all budgets hold. If any is exceeded, Phase 3 does not exit until it is addressed.

3. **Cost metering and forecasting** (economic validation): Instrument compute and storage per service: runner CPU-seconds, memory-seconds, storage used, image count, build time. Aggregate to an estimated monthly cost per service (compute: $X per service, storage: $Y, total). Publish a cost dashboard viewable by service teams. Measure: actual cost vs. forecast accuracy (target: ≤ 10% error). Flag services in the top 10% of cost for optimization review.

4. **Per-service cost chargeback (if applicable; Phase 3 or deferred)**: If the organization wants to charge services for platform usage, implement chargeback logic at the end of Phase 3 (after 1 month of data). If not applicable, remove this task.

5. **Incident response drill and runbook refinement**: Simulate a major failure: control-plane unavailable, runners unable to pull images, secrets backend down. Platform team runs incident response using runbooks. Measure: time to detect, diagnose, and mitigate (target: < 30 min per incident type). Update runbooks based on drill findings.

6. **Multi-region contingency (deferred or planned for Phase 4)** (E3 exception): Single-region model is tested; no multi-region yet. Document the outage scenario: single-region failure halts all 50 services for hours. Estimate cost of multi-region (double infrastructure + operational complexity). Propose multi-region for Phase 4 if: a) regulatory requirement, b) platform outage > 4 hours observed, or c) service teams demand it. Do not implement in Phase 3.

7. **Deployment strategy library expansion**: Beyond blue-green, canary, rolling: add service-mesh integration (Istio, Linkerd) for traffic management on services that adopt it. Test on 3 pilot services; measure: traffic shift accuracy, latency impact. Offer but do not require.

**Rollback:** By end of Phase 3, all 50 services are on the platform, and old pipelines are decommissioned. Phase 3 is not reversible as a whole (services cannot flip back). However, individual components (e.g., multi-region or new deployment strategies) are rolled out incrementally; if a component fails, it is disabled and re-planned (not a full phase rollback).

**Point of no return:** Decommissioning old pipelines for the last services in Wave 3. Gate: V3 passes, and Phase 3 exit check passes (all 50 services operational for 1 week, zero platform-caused incidents). After the gate passes, old pipelines are removed; if a critical platform issue arises, it is fixed forward (no rollback to old pipelines).

**Exit check (V3 + Phase 3 exit check):**
- V3 passes: 50 concurrent builds/deploys succeed with all budgets held (latency p95 < 15 min deploy, throughput 2+ per service, control-plane < 60% CPU).
- All 50 services onboarded, each deployed at least once via the new platform.
- Cost metering accurate (forecast ≤ 10% error); cost per service visible; top 10% flagged.
- Incident response drill: all failure scenarios mitigated within < 30 min.
- 1 week post-onboarding of the final services: zero platform-caused incidents, MTTR same or better than before.

### Phase 4 — Multi-Region (or Advanced Features) & Long-Tail Hardening

**Unlocks:** Platform is geographically resilient (or advanced features are available); operational burden continues to scale sub-linearly.

**Depends on:** Phase 3 exit check; decision on multi-region requirement (Phase 3 gate or deferred).

**Tasks (if multi-region flip condition is true; otherwise, deferred):**

1. **Multi-region architecture**: Replicate control plane to second region. Implement: per-service placement hints (primary region or read-only replica deployments). Test: primary region failure → services in secondary region can still deploy (with lower throughput); replication lag < 1 min.

2. **Cost for multi-region**: Double infrastructure footprint. Re-measure cost per service; forecast monthly cost with multi-region. Confirm budget headroom (Phase 3 cost review should have identified savings or overhead if this is in scope).

3. **Deployment coordination across regions**: Services with multi-region deployments coordinate promotion: primary deploys, then replica waits for confirmation before deploying. Test: deploy a service to primary, confirm healthy, deploy to secondary; rollback primary, confirm secondary rolls back.

4. **Incident response for multi-region**: Drill failure scenarios: primary region network partition, secondary region compute exhausted. Runbook for geo-failover. Measure: mitigation time. Update runbooks.

**Or, if multi-region is deferred:**

1. **Advanced deployment strategies**: Canary by feature flag (route 10% of traffic by user segment, not by deployment replica count). Test: deploy a risky feature behind a flag; 10% of users see it; measure user-reported errors; rollback feature flag if > 1%.

2. **Cost optimization**: Analyze top 10% services by cost; recommend parallelism tuning, cache strategies, or test-suite pruning. Implement top 3 recommendations; measure savings.

3. **Developer experience**: Obsidian dashboard + Slack slash commands for deploy, rollback, log access. Test: developer can deploy without leaving Slack.

4. **Service-mesh integration**: Roll out to all services that opted in; measure: latency impact, canary accuracy with mesh-driven traffic splitting.

**Exit check (Phase 4):**
- If multi-region: Geofailover tested and within SLO; cost per service adjusted; 1 week of production traffic in secondary region with zero incidents.
- If advanced features: Top 3 cost optimizations implemented and measured; canary-by-feature-flag working on 5 services; Slack integration in use by 30+ engineers; service-mesh adopted by 10+ services.

## 10. Deliberately deferred

- **Multi-region deployment:** Deferred to Phase 4. Condition: trigger if a) single-region outage > 4 hours observed, or b) service teams demand geo-distribution, or c) regulatory data-residency requirement. Estimated cost: 2× infrastructure footprint. Decision: Phase 3 cost review and Phase 4 scope includes decision on multi-region.

- **Advanced deployment strategies (canary-by-feature-flag, blue-green with traffic splitting via service mesh):** Deferred to Phase 4. Condition: trigger after all 50 services are stable on basic canary/blue-green; then iterate on advanced strategies based on service team feedback and operational maturity.

- **Per-service chargeback and cost allocation:** Deferred to Phase 4 (optional). Condition: trigger if the organization commits to chargeback model. Requires V4 (cost metering accuracy) to pass first. If deferred, Phase 3–4 proceed with fixed platform costs shared across the organization.

- **Service-mesh integration (Istio, Linkerd):** Deferred to Phase 4. Condition: trigger if services adopt a service mesh for observability and traffic management. Requires testing on 3 pilot services to measure latency impact and validate canary accuracy through mesh-driven traffic splitting.

- **Self-healing and auto-remediation beyond automated rollback:** Deferred to Phase 4. Condition: trigger after Phase 3 incident response drill confirms team is confident in manual runbooks. Then add: auto-restart of failed runners, auto-scale control plane if CPU > 70%, auto-rotate secrets if rotation fails twice.

- **Compliance and audit reporting (SOC 2, ISO 27001):** Deferred to Phase 4 or out-of-scope for platform team. Condition: if organization requires SOC 2 certification, engage compliance and security teams in Phase 3 to assess platform against controls; remediation (immutability of audit logs, encryption in transit, etc.) is scheduled into Phase 4.
