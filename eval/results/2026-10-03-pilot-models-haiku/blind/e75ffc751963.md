# Plan — Multi-Tenant SaaS Billing System

## 1. Classification and constraints

**What:** A multi-tenant SaaS billing platform that ingests usage events from customer applications, aggregates them into line items, calculates charges per tenant using flexible pricing models, and generates invoices and payment instruments monthly.

**Type:** Software (greenfield); not small—multi-tenant isolation is R3, payment data is PCI-regulated, scale grows from pilot (10 tenants, ~10K events/min) to production (10K tenants, ~1M events/min).

**Dominant constraint:** Correctness (double-charging or non-invoicing breaks the business; reconciliation is operationally expensive); then compliance (PCI DSS for card processing, SOC 2 for hosted data); then availability (billing runs monthly; a late run delays cash, but is not a real-time SLO).

**Worst failure:** An invoice issued for the wrong amount or to the wrong tenant, or payment processed twice, creating both financial loss and customer trust damage.

## 4. First end-to-end slice (Phase 0)

**One real request and response:** An event ingestion request from a pilot tenant (event = `{tenant_id, event_id, timestamp, usage_units, category}`) → stored in Postgres → logged via structured JSON → monitored by Datadog.

**Tiers crossed:**
1. **Ingestion API:** Go service, one /ingest endpoint, validate tenant_id exists, parse event, add received_at.
2. **Event log:** Postgres table `events(id, tenant_id, event_id, timestamp, usage_units, category, received_at, dedup_key)`, unique constraint on (tenant_id, event_id, timestamp).
3. **Observability:** Structured logs (timestamp, tenant_id, event_id, status, latency_ms) to stdout; Datadog agent reads it. Dashboard: events per second, error rate, p99 latency.
4. **Alert:** On error rate > 5%, fire a Slack alert.

**Deployment, logging, monitoring, rollback:**
- Deployed via GitHub Actions + Helm to a staging Kubernetes cluster (DigitalOcean/AWS managed K8s).
- Health check: /health returns 200 and `{status: "ok", timestamp, uptime_seconds}`.
- Rollback: previous Helm release (helm rollback), tested with a dry-run in CI.
- Initial budget baselines recorded: latency (p50, p95, p99), throughput (events/sec), Postgres query time (ms), error count.

**Who can reach it:** Internal only (staging cluster, no ingress from public internet); one pilot tenant given API credentials behind a feature flag (`PILOT_TENANT_ENABLED=true`).

**Exit check V0:** A real pilot tenant sends 10 events over 5 minutes → all 10 stored and logged with trace IDs → a forced error (invalid tenant_id) fires a Slack alert → helm rollback succeeds and the service serves 200 OK again; baseline latencies recorded in Datadog.

### **Phase 3 — Payment processing and webhooks**
**Unlocks:** Phase 4 (compliance audit and production hardening) and Phase 5 (general availability).

**Depends on:** Phase 2, V2 (data-flow audit), V3.

**Tasks:**
1. Payment instrumentation (Stripe / PayPal): `/charges` endpoint accepts an invoice_id, creates a charge object, returns a checkout URL or payment ID. Store charge record in `charges(id, invoice_id, tenant_id, amount_cents, processor_id, status, created_at)`.

**Rollback:** Revert payment code; mark charges as "cancelled"; issue refund placeholders (manual follow-up). Webhook handler can revert to a stub that logs and discards.

## 10. Deferred

- **ACH (automated clearing house) bank transfers:** Condition: pilot customer explicitly requests ACH and provides signed wire-transfer agreement. Build in Phase 4 (add ACH handler, webhook receiver, reconciliation for 3–5 day settlement).

- **PDF invoice generation (branded templates):** Condition: customers ask for PDF vs. JSON endpoint. Build in Phase 5 (add html2pdf library, template per customer brand).
- **Automated dispute / chargeback handling:** Condition: chargeback rate > 0.5% or regulatory requirement (e.g., GDPR right to dispute payment). Build in Phase 5 (webhook receiver for chargeback notifications, dispute workflow).
