Walking Skeleton (Phase 0)\n\n**Goal:** One real build-and-deploy request, end-to-end, through the full pipeline, on a test service, to a test cluster, logged, monitored, and rolled back.\n\n**The request:** Git push to branch `main` of a test service → build triggered → artifact tagged and pushed to registry → deploy manifests written to deployment repo → GitOps detects change → deployment to test K8s cluster → 3 smoke tests (pod ready, health check pass, HTTP 200 on /health) → monitor 5 min for errors → success logged → manual rollback triggered (old artifact deployed, verified).\n\n**Who can reach it:** Only internal (test cluster behind VPN or private subnet; no internet-facing endpoint). No real traffic, no real users, no real data.\n\n**Tiers crossed:**\n1. **Git** (GitHub, GitLab, or internal): push trigger\n2. **CI orchestrator** (e.g., Jenkins, GitLab CI, or GitHub Actions): build job\n3. **Build agent** (Docker daemon, or Kaniko for rootless): compile, test, build image\n4. **Artifact registry** (ECR, GCR, or Artifactory): push image, tag with git-sha\n5. **Secrets manager** (Vault): fetch registry credentials, service account token\n6. **GitOps controller** (ArgoCD or Flux): detect change in deployment repo, trigger sync\n7. **Kubernetes cluster** (test): deploy pod, run probes\n8. **Observability** (ELK, Prometheus, or equivalent): ingest logs, metrics, traces\n9. **Rollback step:** GitOps re-sync to previous commit, pod replaced\n\n**Infrastructure as code:**\n- Skeleton pipeline defined in YAML (Jenkinsfile, .gitlab-ci.yml, GitHub Actions, or Argo Workflows).\n- Deployment manifests in Git (Kustomize or Helm).\n- Cluster config (RBAC, namespaces, secrets) in IaC (Terraform or Helm).\n- All code in version control; skeleton repo is read-only until Phase 1 (no manual tweaks).\n\n**Observability in Phase 0:**\n- **Logs:** All pipeline steps emit structured logs (JSON with timestamp, step name, status, error if any) → ELK.\n- **Metrics:** Build time (s), artifact size (MB), deploy latency (s), pod startup time (s) → Prometheus or CloudWatch.\n- **Traces:** Skeleton pipeline instrumented with Jaeger or Datadog (optional but encouraged for 30 min review cycles).\n- **Alerts:** Any step failure → Slack / PagerDuty (test-only; no page-on-call yet).\n\n**Security in Phase 0:**\n- Secrets (registry auth, cluster token, Vault credentials) passed via environment variables from a secret store; never logged or committed.\n- Image signed with a test key (Notary or sigstore, simple self-signed for skeleton); deploy verifies signature (fail if unsigned or invalid).\n- Audit log entry for every artifact build, push, and deploy (who, what, when, where); immutable append-only log in S3 or managed service.\n- RBAC in place: test service account can only deploy to test namespace; no prod access.\n\n**Reproducibility in Phase 0:**\n- Build is deterministic (same input → same artifact hash). Dockerfile is pinned (base image digest, not \"latest\"); all deps frozen.\n- Rollback is idempotent (re-deploy old artifact, same config, same outcome).\n- Skeleton runs twice; both deploys succeed; both roll back.\n\n**Resilience in Phase 0:**\n- If build fails, pipeline stops; developer is notified.\n- If artifact push fails (registry down), pipeline retries 3 times with exponential backoff; fails after 3 attempts.\n- If deploy fails (K8s not reachable), GitOps sync retries every 30 sec for 5 min, then alerts.\n- If a probe fails, pod is restarted; if restart fails repeatedly, pod is evicted and alarm fires.\n\n**Exit check V0:**\n- A real commit (not a mock) to test service triggers a complete pipeline.\n- Artifact is built, signed, pushed, and retrievable by digest.\n- Deployment succeeds; all 3 probes pass; no errors in logs.\n- Rollback succeeds; old artifact is live again.\n- Observability: at least one trace/log entry visible in ELK for each step; baseline latency recorded (total time commit → live ≤ 30 min).\n- Repeating the skeleton 2 hours later: same build artifact hash (reproducibility passes).\n\n**What is NOT in Phase 0:**\n- No multi-region, no canary, no staged deploy, no approval gates.\n- No integration with production cluster (test cluster only).\n- No load test or performance validation.\n- No second service (parallel builds not yet tested).\n- No secrets rotation or compliance audit (hardening deferred).\n\n---\n\n## 5. Phases\n\n### Phase 1: Platform Foundation (Weeks 1–4)\n\n**What it unlocks:** Ability to add real microservices (Phase 2), safely deploy to prod with canary (Phase 2), and measure platform stability (Phase 3).\n\n**Depends on:** V0 passes (skeleton works). Organizational: infra team trained on pipeline engine, cluster, and secrets manager (Lead time: recruiting, onboarding; assume week 0). Git, K8s cluster, Vault, artifact registry exist and are stable.\n\n**Tasks:**\n\n#### Phase 1a: Schema, RBAC, and infrastructure hardening (Weeks 1–2)\n\n1. **Artifact naming and versioning contract** (Day 1–2)\n   - Define naming scheme: `{service-name}:{git-branch}-{git-sha}-{build-number}`. Example: `payment-api:main-abc123-42`.\n   - Tag also with semver if service publishes one: `payment-api:v1.2.3`.\n   - Document and commit to platform wiki.\n   - Validation: template enforced in build pipeline (Phase 1b).\n\n2. **Deployment manifest schema** (Day 1–2)\n   - Define what a deployment manifest must contain: service name, Docker image (with exact tag, no \"latest\"), resource requests (CPU, memory), liveness/readiness probes, RBAC ServiceAccount, namespace.\n   - Kustomize or Helm template for each service (teams customize, not invent).\n   - Validate manifests before GitOps sync (Phase 1b gate).\n\n3. **RBAC and service accounts** (Day 2–3)\n   - Create Kubernetes namespaces: one per service (or per team; decide based on team structure).\n   - Create ServiceAccount per namespace; bind to deployment role (can deploy/update deployments, cannot delete PVCs or secrets).\n   - Bind cluster role to infra-team (admin on test namespace, limited deploy on prod).\n   - Bind teams to their own namespace (RBAC tests in Phase 1b).\n   - Audit logging: all RBAC decisions logged (API server audit).\n\n4. **Secrets manager integration** (Day 3–4)\n   - Vault unsealed, policies written: service-specific policies (team A's builds can only read team A's secrets).\n   - Workload Identity or OIDC configured (if using AWS/GCP): no long-lived credentials in environment variables.\n   - Test: build job acquires token from Vault, uses it to fetch a secret, token expires after 1 hour.\n   - Audit every fetch: log token ID (not value), service, timestamp, success/fail.\n   - **Validation gate V1:** Secrets manager integration (below).\n\n5. **Artifact repository hardening** (Day 4–5)\n   - Registry configured with read-write access control (teams can push to their own repos, pull public images).\n   - Image signing: set up Notary or Cosign; build signs every image.\n   - Registry policy: reject unsigned images (for prod namespace later; test namespace allows unsigned for iteration).\n   - Test: push unsigned image → reject (dry-run first, log but do not block).\n   - Audit: every push/pull logged (image, tag, user, timestamp, success/fail).\n\n6. **Observability baseline** (Day 5–6)\n   - ELK cluster running; pipeline and infra logs flowing in.\n   - Prometheus targets scraping: CI orchestrator metrics (job duration, success rate), K8s metrics (pod startup, resource use).\n   - Baseline established: Phase 0 latency recorded, error rate at ~0%.\n   - Dashboards created: \"Platform Health\" (build success rate, deploy success rate, average latency), \"Security\" (secret fetches, unsigned images rejected, RBAC denials).\n   - Alert rules: build failure → Slack; deploy failure → PagerDuty (test-only).\n\n7. **Disaster recovery baseline** (Day 6–7)\n   - Artifact store backed up every 15 min (to S3 or equivalent).\n   - GitOps state (deployment manifests) backed up every 1 hour.\n   - Vault backed up daily (or per Vault best practices).\n   - Restore test: simulate artifact loss, restore from backup, verify integrity (Phase 2 dry-run).\n   - RTO documented: artifact restore < 5 min, GitOps re-sync < 2 min, total platform recovery < 15 min.\n\n#### Phase 1b: Multi-service pipeline and canary validation (Weeks 2–4)\n\n1. **Pipeline engine template** (Day 8–11)\n   - Declarative pipeline template in Git (one per service; teams copy and customize).\n   - Stages: Git trigger → lint (Shellcheck, Dockerfile linter) → build → security scan (Snyk, Trivy) → push → test deploy (canary to test cluster) → emit artifact metadata.\n   - Security scan gate: fail if critical CVE found; warn if high; pass otherwise (gate V2 in Phase 1b).\n   - Retry logic: transient errors (registry timeout, network blip) retry 3x with exponential backoff; fail-fast on logic errors.\n   - Template in repo `platform-templates/` (read-only; version-controlled).\n\n2. **Artifact build reproducibility validation** (Day 8–10)\n   - Build same commit twice, compare artifact digests; must match (V1 detailed: see Validation gates).\n   - Test on 3 sample services; measure success rate (target: 100%).\n   - Document: Dockerfile must be deterministic (pinned base image digest, no timestamps in build).\n   - Linter enforces: reject Dockerfile with \"latest\" tag or current date in RUN.\n\n3. **Secret scanning in artifacts and logs** (Day 9–11)\n   - Artifact scanning: scan built images for hardcoded secrets (regex for AWS keys, DB passwords, API keys; entropy check).\n   - Log scanning: all pipeline logs scanned for secrets before ingestion into ELK.\n   - Action: if secret found, build fails; artifact deleted; developer notified; audit logged.\n   - Test: inject fake secret into build, verify detection and rejection (V2 gate).\n\n4. **Canary deploy validation on test cluster** (Day 11–14)\n   - Deploy test service to test cluster using canary strategy: 5% traffic (or 1 pod of 10) → wait 5 min → 25% (3 pods) → wait 5 min → 100% (10 pods).\n   - Metrics collected: error rate (target: < 5%), latency P99 (target: < 2 sec baseline), memory/CPU use.\n   - Auto-rollback trigger: if error rate > 5% for 1 min, or latency P99 > baseline × 1.5, rollback to previous version.\n   - Measure rollback time (target: < 2 min from trigger to success).\n   - Repeat 5 times with different service versions (stable, new, unstable mock).\n   - **Validation gate V3:** Canary deploy test (below).\n\n5. **Deploy authorization RBAC test** (Day 12–13)\n   - Team A tries to deploy team B's service: deny (RBAC policy blocks).\n   - Team A deploys team A's service to test namespace: allow.\n   - Infra team deploys anything to prod: allow (or gated by separate approval; decide policy now).\n   - Log each attempt (success and failure); audit trail must show who, what, when, result.\n   - Test RBAC failures trigger alerts (detect privilege escalation attempts).\n   - **Validation gate V2:** RBAC and audit (below).\n\n6. **Multi-service parallel build test** (Day 13–14)\n   - Trigger builds for 10 test services simultaneously.\n   - Measure: build success rate (target: ≥ 99%), build time (target: ≤ 10 min per service), artifact conflicts (target: 0).\n   - If conflicts, add dependency DAG logic (Phase 1b extension or Phase 2 task).\n   - If success, confirm parallel build is safe for Phase 2.\n\n7. **Runbook and documentation** (Day 14)\n   - Write runbooks: \"How to deploy my service,\" \"How to check deployment status,\" \"How to rollback,\" \"How to read logs.\"\n   - Publish wiki (linked from team onboarding).\n   - Templates ready for service teams to copy and adapt.\n\n**Rollback:** If a validation gate fails (V1, V2, V3), the specific feature is not hardened; deployments continue on Phase 0 capabilities (manual deploy, no canary, no auto-rollback) until gate passes. No data loss or production impact; test cluster revert to previous pipeline version (easy, no state change).\n\n**Exit check for Phase 1:**\n- V1: Secrets manager integration works; token scope and audit logged.\n- V2: RBAC blocks unauthorized deploys; audit trail complete; secret scanning rejects hardcoded secrets.\n- V3: Canary deploy succeeds; rollback < 2 min; error detection works.\n- All 10 test services build in parallel, < 10 min per service, ≥ 99% success.\n- Observability baseline recorded; platform dashboard green.\n- Runbooks exist and pass review by 2 service teams (dry-run of deploy).\n\n---\n\n### Phase 2: Prod Rollout (Weeks 5–8)\n\n**What it unlocks:** All 50 microservices can be deployed to production with safety controls in place.\n\n**Depends on:** Phase 1 complete; all V1–V3 gates passed. Organizational: service teams onboarded; runbooks read; at least 1 team has done a trial deploy to test cluster.\n\n**Tasks:**\n\n#### Phase 2a: Prod RBAC and controls (Week 5)\n\n1. **Production namespace and RBAC** (Day 1–2)\n   - Create prod namespaces (one per service or team).\n   - Create ServiceAccounts with lower privileges than test (read-only secrets, deploy updates only to own deployment, cannot delete PVCs, cannot access other namespaces).\n   - Infra team RBAC: can deploy, cannot delete; audit all actions.\n   - Bind service teams to their prod namespaces (read-only except for their own deployments).\n\n2. **Prod deployment policy** (Day 2–3)\n   - Policy: all deploys to prod go through canary (no all-at-once).\n   - Canary percent: 5% → wait 5 min → 25% → wait 5 min → 100%.\n   - Auto-rollback triggers: error rate > 5% for 1 min, latency P99 > baseline × 1.5, or pod crash loop.\n   - Approval gates: team can trigger deploy; infra team is auto-paged if rollback fires (not blocking deploy; informing).\n   - Team can manually rollback without approval (deploy previous version, go through canary again).\n\n3. **Secrets rotation prod policy** (Day 3–4)\n   - Prod secrets (DB passwords, API keys, OAuth tokens) rotated every 30 days (or per compliance requirement).\n   - Rotation is zero-downtime: new secret in Vault, Workload Identity fetches new token on next build, old secret evicted after 1 hour.\n   - Audit every secret rotation (who, what, when, old value hash [not value itself], new value hash).\n   - Test: rotate a prod-like secret, verify no deploy interrupted.\n\n4. **Prod incident playbook** (Day 4–5)\n   - Scenarios: single service deploy fails → canary catches it → auto-rollback (or team manual rollback).\n   - Scenario: multiple services deploy at once, one fails → canary catches one, others proceed independently.\n   - Scenario: artifact registry down → deploys queued; when registry back, queued deploys proceed automatically.\n   - Scenario: Vault unsealed → all builds pause; Vault sealed by on-call; resumes after.\n   - Each scenario: who is notified, what is the response, what is measured, what is the rollback.\n   - Tested (dry-run) by infra team + 2 service teams.\n\n#### Phase 2b: First service prod deploy (Week 5–6)\n\n1. **Select a low-risk service for pilot** (Day 1)\n   - Criteria: no critical dependencies (internal-only, non-financial), low traffic (< 1 req/sec), team confident in their code.\n   - Example: internal logging service, non-critical dashboard.\n\n2. **Deploy pilot to prod with canary** (Day 2–4)\n   - Run full canary deploy: 5% → 5 min → 25% → 5 min → 100%.\n   - Infra team monitors; team on call during deploy (5–15 min total).\n   - Measure: error rate, latency, pod startup, resource use.\n   - Success: all metrics green, canary proceeds smoothly, team confident.\n   - Audit: deploy event logged; team, approval, artifact version, canary progress, final status.\n\n3. **Trial rollback** (Day 4–5)\n   - Manually trigger rollback (even though deploy is stable).\n   - Verify old version comes back.\n   - Measure time: < 2 min.\n   - Confirm logs show rollback event.\n   - Test: deploy again to re-enable new version (practice).\n\n#### Phase 2c: Rollout to all 50 services (Weeks 6–8)\n\n1. **Wave 1: 10 services (Week 6)**\n   - Select 10 non-critical services (internal tools, non-financial, low traffic).\n   - Stagger deploys: 2–3 per day, 1 hour apart.\n   - Same canary policy, same monitoring.\n   - Exit: all 10 green, 0 unplanned rollbacks, teams confident using runbooks.\n\n2. **Wave 2: 20 services (Week 7)**\n   - Mix: internal and customer-facing (but non-critical to customer experience).\n   - Stagger: 3–5 per day.\n   - If any rollback, pause wave; debug; retrace in Phase 2c extension (not a blocker, but learning).\n   - Exit: all 20 green.\n\n3. **Wave 3: 15 services (Week 7–8)**\n   - Mix: more critical services, higher traffic.\n   - Canary windows extended if traffic > 10 req/sec (wait 10 min instead of 5 min between stages).\n   - Exit: all 15 green, 0 unplanned rollbacks.\n\n4. **Wave 4: Final 5 critical services (Week 8)**\n   - Highest-risk: financial, customer-critical, 100+ req/sec traffic.\n   - Canary windows: 10 min each stage.\n   - Infra team + service team + on-call manager present.\n   - Exit: all 5 green, system stable for 24 hours at 100% new version.\n\n**Rollback:** If unplanned rollback at any wave, pause; debug; fix (usually pipeline bug or service bug, not platform bug); re-test on Wave 0 service (not in prod yet); resume wave.\n\n**Exit check for Phase 2:**\n- All 50 services deployed to prod via canary.\n- 0 critical incidents caused by deploy mechanism (service bugs ok, infra bugs not ok).\n- All teams have deployed once; at least 1 team manual rollback succeeded.\n- Audit trail shows all deploys and rollbacks; RBAC blocked unauthorized attempts.\n- Observability: \"Platform\" dashboard shows 50 active services, < 0.5% deploy failure rate, canary latency < 5 min end-to-end.\n\n---\n\n### Phase 3: Observability, Compliance, and Optimization (Weeks 9–12)\n\n**What it unlocks:** Production hardening, audit compliance, cost optimization, multi-region readiness.\n\n**Depends on:** Phase 2 complete; GitOps per cluster?\n   - No rollout yet (Phase 4); design and tests only.\n\n**Exit check for Phase 3:**\n- Compliance gaps identified and remediated.\n- SLO targets met (or exceptions documented).\n- Cost within budget (or tuning plan for Phase 4).\n- Multi-region design approved.\n\n---\n\n### Phase 4: Scale, Multi-Region, and Continuous Improvement (Quarter 2+)\n\n**What it unlocks:** Multi-region deployment, advanced features (blue-green, traffic splitting, gradual darkening), cost optimization at scale.\n\n**Depends on:** Phase 3 complete; platform stable and proven on single region with 50 services.\n\n**Tasks:**\n- Multi-region rollout (same pipeline, separate artifact caches per region).\n- Advanced deploy strategies (blue-green for zero-downtime, traffic splitting for A/B testing).\n- CI/CD platform as a product: offer to other teams, charge-back model for cost allocation.\n- Continuous improvement: automate runbook scenarios, add self-healing for common failures, reduce on-call load.\n\n---\n\n## 6. deploy verifies signature (fail if unsigned or invalid).\n- Audit log entry for every artifact build, push, and deploy (who, what, when, where); immutable append-only log in S3 or managed service.\n- RBAC in place: test service account can only deploy to test namespace; no prod access.\n\n**Reproducibility in Phase 0:**\n- Build is deterministic (same input → same artifact hash). Dockerfile is pinned (base image digest, not \"latest\"); all deps frozen.\n- Rollback is idempotent (re-deploy old artifact, same config, same outcome).\n- Skeleton runs twice; both deploys succeed; both roll back.\n\n**Resilience in Phase 0:**\n- If build fails, pipeline stops; developer is notified.\n- If artifact push fails (registry down), pipeline retries 3 times with exponential backoff; fails after 3 attempts.\n- If deploy fails (K8s not reachable), GitOps sync retries every 30 sec for 5 min, then alerts.\n- If a probe fails, pod is restarted; if restart fails repeatedly, pod is evicted and alarm fires.\n\n**Exit check V0:**\n- A real commit (not a mock) to test service triggers a complete pipeline.\n- Artifact is built, signed, pushed, and retrievable by digest.\n- Deployment succeeds; all 3 probes pass; no errors in logs.\n- Rollback succeeds; old artifact is live again.\n- Observability: at least one trace/log entry visible in ELK for each step; baseline latency recorded (total time commit → live ≤ 30 min).\n- Repeating the skeleton 2 hours later: same build artifact hash (reproducibility passes).\n\n**What is NOT in Phase 0:**\n- No multi-region, no canary, no staged deploy, no approval gates.\n- No integration with production cluster (test cluster only).\n- No load test or performance validation.\n- No second service (parallel builds not yet tested).\n- No secrets rotation or compliance audit (hardening deferred).\n\n---\n\n## 5. Phases\n\n### Phase 1: Platform Foundation (Weeks 1–4)\n\n**What it unlocks:** Ability to add real microservices (Phase 2), safely deploy to prod with canary (Phase 2), and measure platform stability (Phase 3).\n\n**Depends on:** V0 passes (skeleton works). Organizational: infra team trained on pipeline engine, cluster, and secrets manager (Lead time: recruiting, onboarding; assume week 0). Git, K8s cluster, Vault, artifact registry exist and are stable.\n\n**Tasks:**\n\n#### Phase 1a: Schema, RBAC, and infrastructure hardening (Weeks 1–2)\n\n1. **Artifact naming and versioning contract** (Day 1–2)\n   - Define naming scheme: `{service-name}:{git-branch}-{git-sha}-{build-number}`. Example: `payment-api:main-abc123-42`.\n   - Tag also with semver if service publishes one: `payment-api:v1.2.3`.\n   - Document and commit to platform wiki.\n   - Validation: template enforced in build pipeline (Phase 1b).\n\n2. **Deployment manifest schema** (Day 1–2)\n   - Define what a deployment manifest must contain: service name, Docker image (with exact tag, no \"latest\"), resource requests (CPU, memory), liveness/readiness probes, RBAC ServiceAccount, namespace.\n   - Kustomize or Helm template for each service (teams customize, not invent).\n   - Validate manifests before GitOps sync (Phase 1b gate).\n\n3. **RBAC and service accounts** (Day 2–3)\n   - Create Kubernetes namespaces: one per service (or per team; decide based on team structure).\n   - Create ServiceAccount per namespace; bind to deployment role (can deploy/update deployments, cannot delete PVCs or secrets).\n   - Bind cluster role to infra-team (admin on test namespace, limited deploy on prod).\n   - Bind teams to their own namespace (RBAC tests in Phase 1b).\n   - Audit logging: all RBAC decisions logged (API server audit).\n\n4. **Secrets manager integration** (Day 3–4)\n   - Vault unsealed, policies written: service-specific policies (team A's builds can only read team A's secrets).\n   - Workload Identity or OIDC configured (if using AWS/GCP): no long-lived credentials in environment variables.\n   - Test: build job acquires token from Vault, uses it to fetch a secret, token expires after 1 hour.\n   - Audit every fetch: log token ID (not value), service, timestamp, success/fail.\n   - **Validation gate V1:** Secrets manager integration (below).\n\n5. **Artifact repository hardening** (Day 4–5)\n   - Registry configured with read-write access control (teams can push to their own repos, pull public images).\n   - Image signing: set up Notary or Cosign; build signs every image.\n   - Registry policy: reject unsigned images (for prod namespace later; test namespace allows unsigned for iteration).\n   - Test: push unsigned image → reject (dry-run first, log but do not block).\n   - Audit: every push/pull logged (image, tag, user, timestamp, success/fail).\n\n6. **Observability baseline** (Day 5–6)\n   - ELK cluster running; pipeline and infra logs flowing in.\n   - Prometheus targets scraping: CI orchestrator metrics (job duration, success rate), K8s metrics (pod startup, resource use).\n   - Baseline established: Phase 0 latency recorded, error rate at ~0%.\n   - Dashboards created: \"Platform Health\" (build success rate, deploy success rate, average latency), \"Security\" (secret fetches, unsigned images rejected, RBAC denials).\n   - Alert rules: build failure → Slack; deploy failure → PagerDuty (test-only).\n\n7. **Disaster recovery baseline** (Day 6–7)\n   - Artifact store backed up every 15 min (to S3 or equivalent).\n   - GitOps state (deployment manifests) backed up every 1 hour.\n   - Vault backed up daily (or per Vault best practices).\n   - Restore test: simulate artifact loss, restore from backup, verify integrity (Phase 2 dry-run).\n   - RTO documented: artifact restore < 5 min, GitOps re-sync < 2 min, total platform recovery < 15 min.\n\n#### Phase 1b: Multi-service pipeline and canary validation (Weeks 2–4)\n\n1. **Pipeline engine template** (Day 8–11)\n   - Declarative pipeline template in Git (one per service; teams copy and customize).\n   - Stages: Git trigger → lint (Shellcheck, Dockerfile linter) → build → security scan (Snyk, Trivy) → push → test deploy (canary to test cluster) → emit artifact metadata.\n   - Security scan gate: fail if critical CVE found; warn if high; pass otherwise (gate V2 in Phase 1b).\n   - Retry logic: transient errors (registry timeout, network blip) retry 3x with exponential backoff; fail-fast on logic errors.\n   - Template in repo `platform-templates/` (read-only; version-controlled).\n\n2. **Artifact build reproducibility validation** (Day 8–10)\n   - Build same commit twice, compare artifact digests; must match (V1 detailed: see Validation gates).\n   - Test on 3 sample services; measure success rate (target: 100%).\n   - Document: Dockerfile must be deterministic (pinned base image digest, no timestamps in build).\n   - Linter enforces: reject Dockerfile with \"latest\" tag or current date in RUN.\n\n3. **Secret scanning in artifacts and logs** (Day 9–11)\n   - Artifact scanning: scan built images for hardcoded secrets (regex for AWS keys, DB passwords, API keys; entropy check).\n   - Log scanning: all pipeline logs scanned for secrets before ingestion into ELK.\n   - Action: if secret found, build fails; artifact deleted; developer notified; audit logged.\n   - Test: inject fake secret into build, verify detection and rejection (V2 gate).\n\n4. **Canary deploy validation on test cluster** (Day 11–14)\n   - Deploy test service to test cluster using canary strategy: 5% traffic (or 1 pod of 10) → wait 5 min → 25% (3 pods) → wait 5 min → 100% (10 pods).\n   - Metrics collected: error rate (target: < 5%), latency P99 (target: < 2 sec baseline), memory/CPU use.\n   - Auto-rollback trigger: if error rate > 5% for 1 min, or latency P99 > baseline × 1.5, rollback to previous version.\n   - Measure rollback time (target: < 2 min from trigger to success).\n   - Repeat 5 times with different service versions (stable, new, unstable mock).\n   - **Validation gate V3:** Canary deploy test (below).\n\n5. **Deploy authorization RBAC test** (Day 12–13)\n   - Team A tries to deploy team B's service: deny (RBAC policy blocks).\n   - Team A deploys team A's service to test namespace: allow.\n   - Infra team deploys anything to prod: allow (or gated by separate approval; decide policy now).\n   - Log each attempt (success and failure); audit trail must show who, what, when, result.\n   - Test RBAC failures trigger alerts (detect privilege escalation attempts).\n   - **Validation gate V2:** RBAC and audit (below).\n\n6. **Multi-service parallel build test** (Day 13–14)\n   - Trigger builds for 10 test services simultaneously.\n   - Measure: build success rate (target: ≥ 99%), build time (target: ≤ 10 min per service), artifact conflicts (target: 0).\n   - If conflicts, add dependency DAG logic (Phase 1b extension or Phase 2 task).\n   - If success, confirm parallel build is safe for Phase 2.\n\n7. **Runbook and documentation** (Day 14)\n   - Write runbooks: \"How to deploy my service,\" \"How to check deployment status,\" \"How to rollback,\" \"How to read logs.\"\n   - Publish wiki (linked from team onboarding).\n   - Templates ready for service teams to copy and adapt.\n\n**Rollback:** If a validation gate fails (V1, V2, V3), the specific feature is not hardened; deployments continue on Phase 0 capabilities (manual deploy, no canary, no auto-rollback) until gate passes. No data loss or production impact; test cluster revert to previous pipeline version (easy, no state change).\n\n**Exit check for Phase 1:**\n- V1: Secrets manager integration works; token scope and audit logged.\n- V2: RBAC blocks unauthorized deploys; audit trail complete; secret scanning rejects hardcoded secrets.\n- V3: Canary deploy succeeds; rollback < 2 min; error detection works.\n- All 10 test services build in parallel, < 10 min per service, ≥ 99% success.\n- Observability baseline recorded; platform dashboard green.\n- Runbooks exist and pass review by 2 service teams (dry-run of deploy).\n\n---\n\n### Phase 2: Prod Rollout (Weeks 5–8)\n\n**What it unlocks:** All 50 microservices can be deployed to production with safety controls in place.\n\n**Depends on:** Phase 1 complete; all V1–V3 gates passed. Organizational: service teams onboarded; runbooks read; at least 1 team has done a trial deploy to test cluster.\n\n**Tasks:**\n\n#### Phase 2a: Prod RBAC and controls (Week 5)\n\n1. **Production namespace and RBAC** (Day 1–2)\n   - Create prod namespaces (one per service or team).\n   - Create ServiceAccounts with lower privileges than test (read-only secrets, deploy updates only to own deployment, cannot delete PVCs, cannot access other namespaces).\n   - Infra team RBAC: can deploy, cannot delete; audit all actions.\n   - Bind service teams to their prod namespaces (read-only except for their own deployments).\n\n2. **Prod deployment policy** (Day 2–3)\n   - Policy: all deploys to prod go through canary (no all-at-once).\n   - Canary percent: 5% → wait 5 min → 25% → wait 5 min → 100%.\n   - Auto-rollback triggers: error rate > 5% for 1 min, latency P99 > baseline × 1.5, or pod crash loop.\n   - Approval gates: team can trigger deploy; infra team is auto-paged if rollback fires (not blocking deploy; informing).\n   - Team can manually rollback without approval (deploy previous version, go through canary again).\n\n3. **Secrets rotation prod policy** (Day 3–4)\n   - Prod secrets (DB passwords, API keys, OAuth tokens) rotated every 30 days (or per compliance requirement).\n   - Rotation is zero-downtime: new secret in Vault, Workload Identity fetches new token on next build, old secret evicted after 1 hour.\n   - Audit every secret rotation (who, what, when, old value hash [not value itself], new value hash).\n   - Test: rotate a prod-like secret, verify no deploy interrupted.\n\n4. **Prod incident playbook** (Day 4–5)\n   - Scenarios: single service deploy fails → canary catches it → auto-rollback (or team manual rollback).\n   - Scenario: multiple services deploy at once, one fails → canary catches one, others proceed independently.\n   - Scenario: artifact registry down → deploys queued; when registry back, queued deploys proceed automatically.\n   - Scenario: Vault unsealed → all builds pause; Vault sealed by on-call; resumes after.\n   - Each scenario: who is notified, what is the response, what is measured, what is the rollback.\n   - Tested (dry-run) by infra team + 2 service teams.\n\n#### Phase 2b: First service prod deploy (Week 5–6)\n\n1. **Select a low-risk service for pilot** (Day 1)\n   - Criteria: no critical dependencies (internal-only, non-financial), low traffic (< 1 req/sec), team confident in their code.\n   - Example: internal logging service, non-critical dashboard.\n\n2. **Deploy pilot to prod with canary** (Day 2–4)\n   - Run full canary deploy: 5% → 5 min → 25% → 5 min → 100%.\n   - Infra team monitors; team on call during deploy (5–15 min total).\n   - Measure: error rate, latency, pod startup, resource use.\n   - Success: all metrics green, canary proceeds smoothly, team confident.\n   - Audit: deploy event logged; team, approval, artifact version, canary progress, final status.\n\n3. **Trial rollback** (Day 4–5)\n   - Manually trigger rollback (even though deploy is stable).\n   - Verify old version comes back.\n   - Measure time: < 2 min.\n   - Confirm logs show rollback event.\n   - Test: deploy again to re-enable new version (practice).\n\n#### Phase 2c: Rollout to all 50 services (Weeks 6–8)\n\n1. **Wave 1: 10 services (Week 6)**\n   - Select 10 non-critical services (internal tools, non-financial, low traffic).\n   - Stagger deploys: 2–3 per day, 1 hour apart.\n   - Same canary policy, same monitoring.\n   - Exit: all 10 green, 0 unplanned rollbacks, teams confident using runbooks.\n\n2. **Wave 2: 20 services (Week 7)**\n   - Mix: internal and customer-facing (but non-critical to customer experience).\n   - Stagger: 3–5 per day.\n   - If any rollback, pause wave; debug; retrace in Phase 2c extension (not a blocker, but learning).\n   - Exit: all 20 green.\n\n3. **Wave 3: 15 services (Week 7–8)**\n   - Mix: more critical services, higher traffic.\n   - Canary windows extended if traffic > 10 req/sec (wait 10 min instead of 5 min between stages).\n   - Exit: all 15 green, 0 unplanned rollbacks.\n\n4. **Wave 4: Final 5 critical services (Week 8)**\n   - Highest-risk: financial, customer-critical, 100+ req/sec traffic.\n   - Canary windows: 10 min each stage.\n   - Infra team + service team + on-call manager present.\n   - Exit: all 5 green, system stable for 24 hours at 100% new version.\n\n**Rollback:** If unplanned rollback at any wave, pause; debug; fix (usually pipeline bug or service bug, not platform bug); re-test on Wave 0 service (not in prod yet); resume wave.\n\n**Exit check for Phase 2:**\n- All 50 services deployed to prod via canary.\n- 0 critical incidents caused by deploy mechanism (service bugs ok, infra bugs not ok).\n- All teams have deployed once; at least 1 team manual rollback succeeded.\n- Audit trail shows all deploys and rollbacks; RBAC blocked unauthorized attempts.\n- Observability: \"Platform\" dashboard shows 50 active services, < 0.5% deploy failure rate, canary latency < 5 min end-to-end.\n\n---\n\n### Phase 3: Observability, Compliance, and Optimization (Weeks 9–12)\n\n**What it unlocks:** Production hardening, audit compliance, cost optimization, multi-region readiness.\n\n**Depends on:** Phase 2 complete; platform stable on all 50 services for 2 weeks.\n\n**Tasks:**\n\n1. **Compliance audit and hardening** (Week 9)\n   - Audit trail: full retention (90 days hot, 1 year cold in S3).\n   - RBAC audit: all actions logged, compliance-readable.\n   - Secrets audit: all fetches logged (token ID, service, timestamp); rotation history.\n   - Check against compliance requirement (SOC2, HIPAA, PCI DSS, or internal policy); map controls.\n   - Remediation if gaps (e.g., if PCI DSS requires encryption at rest, enable EBS encryption, KMS).\n\n2. **Platform SLO measurement and alerting** (Weeks 9–10)\n   - Measure: uptime (availability of pipeline), error rate (failed deploys), latency (commit → deployed).\n   - Target SLO: 99.5% uptime, deploy error rate < 1%, latency P99 < 15 min.\n   - Alerting: trigger if any metric crosses SLO band (not just outage; also degradation).\n   - On-call rotation: infra team rotates; SLA for response < 15 min.\n\n3. **Cost optimization** (Weeks 10–11)\n   - Review artifact storage cost (target: < 200 USD/month for 50 services × 30 days retention).\n   - Review CI orchestrator cost (if managed: AWS CodePipeline, GitHub Actions, etc.; if self-hosted: K8s pods, storage).\n   - If cost > budget, implement compression, archival, or retention policy tuning.\n   - Re-baseline: new cost vs. assumed cost; adjust Phase 3b.\n\n4. **Multi-region readiness** (Weeks 11–12)\n   - Plan: how to deploy same 50 services to a second region (replication, artifact distribution, secrets sync).\n   - Design: artifact registry replicated? Separate clusters? GitOps per cluster?\n   - No rollout yet (Phase 4); design and tests only.\n\n**Exit check for Phase 3:**\n- Compliance gaps identified and remediated.\n- SLO targets met (or exceptions documented).\n- Cost within budget (or tuning plan for Phase 4).\n- Multi-region design approved.\n\n---\n\n### Phase 4: Scale, Multi-Region, and Continuous Improvement (Quarter 2+)\n\n**What it unlocks:** Multi-region deployment, advanced features (blue-green, traffic splitting, gradual darkening), cost optimization at scale.\n\n**Depends on:** Phase 3 complete; platform stable and proven on single region with 50 services.\n\n**Tasks:**\n- Multi-region rollout (same pipeline, separate artifact caches per region).\n- Advanced deploy strategies (blue-green for zero-downtime, traffic splitting for A/B testing).\n- CI/CD platform as a product: offer to other teams, charge-back model for cost allocation.\n- Continuous improvement: automate runbook scenarios, add self-healing for common failures, reduce on-call load.\n\n---\n\n## 6.
