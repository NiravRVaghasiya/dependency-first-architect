Walking Skeleton (Phase 0)**\n\n**Real request:** An authenticated API client (internal test service, behind allow-list IP gate) creates a tenant, posts a single usage event (charge $10 for 100 API calls), queries the charge status, and receives an invoice PDF.\n\n**Every tier it crosses:**\n\n1. **API Gateway** (Nginx/AWS ALB): route `/charges/create` → backend service.\n2. **Auth service** (stub): verify API key (hardcoded test key, no DB lookup yet).\n3. **Tenant isolation layer** (query filter stub): accept tenant_id from header, inject into all queries.\n4. **Charges service** (Rust/Go): receive event, validate schema, call payment processor (Stripe test mode).\n5. **Payments integration** (Stripe SDK): submit $10 charge to test API, receive charge_id.\n6. **Event store** (PostgreSQL): append event (tenant_id, amount, charge_id, timestamp) to `events` table (append-only log).\n7. **Invoice generator** (async job, runs on event sink): on charge confirmation, create invoice record, render PDF.\n8. **PDF storage** (S3 or GCS): store PDF under `${tenant_id}/${invoice_id}.pdf`.\n9. **Query service** (stub): retrieve charge + invoice via API call.\n10. **Logging & monitoring:** every hop logs (trace_id, tenant_id, amount, latency) to stdout (ECS/GKE captures); Datadog ingest tags with tenant_id.\n11. **Rollback:** API has feature flag `enable_skeleton_billing`; set to false, charges go to /dev/null; smoke test redeploys with flag off, verifies no side effects.\n\n**Who can reach it:** Only internal services (test suite runner) and allow-listed IPs (team members' office, CI/CD runner); behind HTTP Basic Auth (username=`test`, password=vault secret, logged). Stripe test mode (no real charges). Production payment processor URLs NOT used.\n\n**Not yet hardened:**\n- API keys stored in code (acceptable for skeleton; will move to vault in Phase 1).\n- No encryption at rest (test DB runs on unencrypted volume; acceptable for non-sensitive data; will encrypt in Phase 1).\n- No audit trail immutability (events logged to regular table; will add signing in Phase 1).\n- Tenant isolation filter is hard-coded in test (will be enforced by middleware in Phase 1).\n- No rate limiting (will add in Phase 2 when multi-tenant traffic is real).\n\n**Exit check V0:**\n1. A real charge request from test client succeeds: charge_id returned, invoice PDF generated, both visible in Datadog trace and S3 console (no error).\n2. Deploy succeeds via CI/CD pipeline (code → build → push to GKE).\n3. Rollback (feature flag off) succeeds: new charge request returns 200 but no event is recorded (verified by querying DB).\n4. Injected failure test: kill Stripe mock, charge request fails gracefully with 503 (error logged, alert fires in Datadog).\n5. Baseline metrics recorded in Datadog: charge API p50=50ms, p99=120ms, memory=200MB, DB query=5ms (unloaded, one tenant, one event).\n\n**Real request path (pseudocode):**\n```\nPOST /charges/create\n  Tenant: \"tenant_abc123\" (header)\n  Body: { \"amount\": 1000, \"description\": \"100 API calls\" }\n  \n  → API Gateway accepts, routes to Charges service\n  → Auth: verify API key (hardcoded)\n  → Tenant filter: WHERE tenant_id = 'tenant_abc123'\n  → Charges service: validate payload, call Stripe API\n  → Stripe test API: returns { charge_id: \"ch_test_123\", status: \"succeeded\" }\n  → Event store: INSERT INTO events (tenant_id, amount, charge_id, timestamp, trace_id) VALUES (...)\n  → Event sink: triggers Invoice Generator (async)\n  → Invoice Generator: INSERT INTO invoices (tenant_id, charge_id, pdf_url) VALUES (...)\n  → Response to client: { charge_id: \"ch_test_123\", invoice_url: \"s3://bucket/tenant_abc123/inv_456.pdf\" }\n  \nGET /invoices/inv_456?tenant=tenant_abc123\n  → Query service: SELECT * FROM invoices WHERE id='inv_456' AND tenant_id='tenant_abc123'\n  → Return: { invoice_id, amount, issued_at, pdf_url }\n```\n\n---\n\n## **5. Walking Skeleton (Phase 0)**\n\n**Real request:** An authenticated API client (internal test service, behind allow-list IP gate) creates a tenant, posts a single usage event (charge $10 for 100 API calls), queries the charge status, and receives an invoice PDF.\n\n**Every tier it crosses:**\n\n1. **API Gateway** (Nginx/AWS ALB): route `/charges/create` → backend service.\n2. **Auth service** (stub): verify API key (hardcoded test key, no DB lookup yet).\n3. **Tenant isolation layer** (query filter stub): accept tenant_id from header, inject into all queries.\n4. **Charges service** (Rust/Go): receive event, validate schema, call payment processor (Stripe test mode).\n5. **Payments integration** (Stripe SDK): submit $10 charge to test API, receive charge_id.\n6. **Event store** (PostgreSQL): append event (tenant_id, amount, charge_id, timestamp) to `events` table (append-only log).\n7. **Invoice generator** (async job, runs on event sink): on charge confirmation, create invoice record, render PDF.\n8. **PDF storage** (S3 or GCS): store PDF under `${tenant_id}/${invoice_id}.pdf`.\n9. **Query service** (stub): retrieve charge + invoice via API call.\n10. **Logging & monitoring:** every hop logs (trace_id, tenant_id, amount, latency) to stdout (ECS/GKE captures); Datadog ingest tags with tenant_id.\n11. **Rollback:** API has feature flag `enable_skeleton_billing`; set to false, charges go to /dev/null; smoke test redeploys with flag off, verifies no side effects.\n\n**Who can reach it:** Only internal services (test suite runner) and allow-listed IPs (team members' office, CI/CD runner); behind HTTP Basic Auth (username=`test`, password=vault secret, logged). Stripe test mode (no real charges). Production payment processor URLs NOT used.\n\n**Not yet hardened:**\n- API keys stored in code (acceptable for skeleton; will move to vault in Phase 1).\n- No encryption at rest (test DB runs on unencrypted volume; acceptable for non-sensitive data; will encrypt in Phase 1).\n- No audit trail immutability (events logged to regular table; will add signing in Phase 1).\n- Tenant isolation filter is hard-coded in test (will be enforced by middleware in Phase 1).\n- No rate limiting (will add in Phase 2 when multi-tenant traffic is real).\n\n**Exit check V0:**\n1. A real charge request from test client succeeds: charge_id returned, invoice PDF generated, both visible in Datadog trace and S3 console (no error).\n2. Deploy succeeds via CI/CD pipeline (code → build → push to GKE).\n3. Rollback (feature flag off) succeeds: new charge request returns 200 but no event is recorded (verified by querying DB).\n4. Injected failure test: kill Stripe mock, charge request fails gracefully with 503 (error logged, alert fires in Datadog).\n5. Baseline metrics recorded in Datadog: charge API p50=50ms, p99=120ms, memory=200MB, DB query=5ms (unloaded, one tenant, one event).\n\n**Real request path (pseudocode):**\n```\nPOST /charges/create\n  Tenant: \"tenant_abc123\" (header)\n  Body: { \"amount\": 1000, \"description\": \"100 API calls\" }\n  \n  → API Gateway accepts, routes to Charges service\n  → Auth: verify API key (hardcoded)\n  → Tenant filter: WHERE tenant_id = 'tenant_abc123'\n  → Charges service: validate payload, call Stripe API\n  → Stripe test API: returns { charge_id: \"ch_test_123\", status: \"succeeded\" }\n  → Event store: INSERT INTO events (tenant_id, amount, charge_id, timestamp, trace_id) VALUES (...)\n  → Event sink: triggers Invoice Generator (async)\n  → Invoice Generator: INSERT INTO invoices (tenant_id, charge_id, pdf_url) VALUES (...)\n  → Response to client: { charge_id: \"ch_test_123\", invoice_url: \"s3://bucket/tenant_abc123/inv_456.pdf\" }\n  \nGET /invoices/inv_456?tenant=tenant_abc123\n  → Query service: SELECT * FROM invoices WHERE id='inv_456' AND tenant_id='tenant_abc123'\n  → Return: { invoice_id, amount, issued_at, pdf_url }\n```\n\n---\n\n## **5.
