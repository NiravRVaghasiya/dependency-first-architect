Multi-tenancy strategy\n\n**Recommended: pooled by default, with a silo option for large tenants.**\n\n- **Pooled (default):** shared Postgres cluster with `tenant_id` on every table.\n  - Enforce it with **Row-Level Security**. The session sets `app.tenant_id`, and policies filter on it. A forgotten `WHERE` clause can't leak data.\n  - Make `tenant_id` the leading column of every primary key and index.\n  - Use composite foreign keys that include `tenant_id`, so cross-tenant references are impossible at the schema level.\n- **Shard by `tenant_id`** (hash or directory-based) across Postgres clusters. Keep a tenant-to-shard routing directory so you can move hot tenants.\n- **Silo tier:** a dedicated database or cluster for enterprise tenants with compliance or noisy-neighbor needs. The same code runs against a different connection, resolved by the tenant directory.\n- **Noisy-neighbor controls:**\n  - Per-tenant rate limits and quotas at the gateway.\n  - Kafka partitioning by `tenant_id + customer_id`, with per-tenant throttling in consumers.\n  - Fair-share scheduling for billing runs, so a large tenant's month-end run doesn't starve small ones.\n- **Encryption:** per-tenant data keys (envelope encryption with KMS). This enables crypto-shredding on offboarding and per-tenant key rotation.\n- **Tenant context** is resolved once at the gateway from the API key or JWT. It is propagated via request context and event headers and never trusted from the request body.\n\n## 6. Key flows\n\n### 7.1 Subscription creation and renewal\n1. The API call carries an idempotency key. It creates the subscription pinned to a `plan_version`, with a billing anchor.\n2. The scheduler finds subscriptions whose `current_period_end <= now()`. Work is partitioned by tenant, and each subscription is claimed with `SELECT … FOR UPDATE SKIP LOCKED`.\n3. The invoicing engine builds a draft:\n   - Advance-billed items (flat and seat fees) cover the next period.\n   - Arrears items (usage) cover the period just ended.\n   - Proration lines and pending credits are included.\n4. Tax is calculated and the invoice is finalized (immutable, numbered).\n5. The ledger posts: Dr Accounts Receivable, Cr Deferred Revenue, Cr Tax Payable.\n6. The payment attempt is created, or the invoice is sent for manual (net-30) collection.\n\n### 7.2 Usage pipeline\n1. `POST /usage` goes to Kafka, keyed by `tenant+customer`. The API acks after a durable write.\n2. A dedup stage uses `(tenant, idempotency_key)` in a Bloom filter plus a persistent store (Redis/RocksDB), with a window of 24 to 72 hours.\n3. Events land in ClickHouse. A streaming job keeps near-real-time rollups for dashboards and usage alerts.\n4. At period close, there is a **cutoff plus grace window** (for example 2 hours). Metering then writes a **finalized rollup snapshot**. Rating reads only finalized snapshots.\n5. Events that arrive after finalization go to the next invoice as an adjustment, or trigger a credit note or supplementary invoice, depending on tenant policy.\n\n### 7.3 Mid-cycle change (upgrade or downgrade)\n- Compute proration from exact seconds or days remaining, using the tenant's chosen mode (`create_prorations`, `none`, or `always_invoice`).\n- Produce a credit line for the unused old price and a charge line for the new price.\n- Downgrades usually take effect at period end, through a `subscription_schedule`.\n\n### 7.4 Payment and dunning\n- The payment attempt is created with an idempotency key derived from `invoice_id + attempt_no`.\n- PSP webhooks are verified, deduplicated, and applied through an inbox table.\n- On failure, dunning follows a configurable schedule (for example days 1, 3, 5, 7). It uses decline-code-aware retry logic and sends customer notifications. After exhaustion, the subscription moves to `past_due`, then `canceled` or `unpaid` per tenant policy.\n- A successful payment posts Dr Cash, Cr Accounts Receivable, and emits `invoice.paid`.\n\n### 7.5 Corrections\n- Finalized invoices are never edited. Use **credit notes**, **voids** (only if unpaid), or **re-invoicing**. Each produces its own ledger entries.\n\n## 8. Consistency and reliability patterns\n\n- **Transactional outbox** for every state change that emits events. This avoids dual-write bugs between the DB and Kafka.\n- **Inbox/dedup table** for consumers and PSP webhooks, giving effectively-once processing.\n- **Sagas** for cross-service operations (finalize → tax → ledger → charge), with explicit compensation steps.\n- **Optimistic concurrency** on subscriptions (`version` column) to prevent lost updates from concurrent API calls and the scheduler.\n- **Billing-run checkpoints.** Runs are resumable and idempotent per subscription per period, keyed by `(subscription_id, period_start)` with a unique constraint.\n- **Reconciliation jobs, run daily:**\n  - Ledger balances against the invoice and payment tables.\n  - PSP settlement reports against internal payments.\n  - Usage totals from the raw store against the rollups.\n  - Any drift raises an alert.\n- **Time:** store UTC, keep the tenant time zone for anchors, and test month-end and DST edge cases heavily (Jan 31 anchor, leap days).\n- **Backfills and dry-runs:** support a \"preview invoice\" API, which the rating engine's purity makes easy. It also makes price-change simulations possible.\n\n## 9. Security and compliance\n\n- **PCI:** never touch raw card data. Use PSP-hosted fields or tokenization, so you stay at SAQ-A.\n- **AuthN/Z:** OAuth2/OIDC for users, scoped API keys for tenants (with restricted keys), and RBAC/ABAC within a tenant (admin, finance, read-only).\n- **Audit log:** append-only, covering who changed what and when (price changes, refunds, manual adjustments). Require two-person approval above a threshold.\n- **Data protection:** TLS everywhere, encryption at rest, and field-level encryption for tax IDs and bank details. Support GDPR export and erasure. Financial records usually need legal-retention exemptions, so pseudonymize them instead.\n- **Tax and invoicing compliance:** EU VAT (OSS, reverse charge, VIES validation), US sales tax nexus, and e-invoicing mandates (Peppol, Italy SDI, India GST). Keep these behind country-specific adapters.\n- **SOC 2 and ISO 27001:** controls for change management, least-privilege access, and secrets management (Vault/KMS).\n- **Data residency:** region-pinned tenant cells (EU, US, APAC). Each cell is a full stack, with a global control plane holding only tenant routing.\n\n## 10. Scalability and operations\n\n- **Cell-based architecture.** Each region has one or more cells, and each cell has its own DB shards, Kafka, and workers. This limits the blast radius.\n- **Hot spots:** month-start and month-end billing spikes. Mitigate by:\n  - spreading billing anchors (jittering),\n  - autoscaling workers from queue depth,\n  - prioritizing by SLA tier.\n- **Usage storage:** ClickHouse (or Druid/Pinot) with monthly partitions. Keep raw events for 13+ months in cheap object storage (Parquet) for audit and recompute.\n- **Caching:** cache catalog and price versions (immutable, so they're safe to cache aggressively).\n- **Observability:**\n  - OpenTelemetry traces tagged with `tenant_id`.\n  - SLOs: invoice generation success rate, payment-processing latency, usage ingestion lag, webhook delivery success.\n  - Business alerts: a sudden revenue drop, an invoice total outlier versus history, or zero-amount invoice spikes.\n- **DR:** PITR for Postgres, with an RPO of a few minutes and an RTO under one hour. Run cross-region replicas for the ledger, and rehearse restores regularly.\n\n## 11. API design\n\n- REST with resource-oriented endpoints (`/v1/customers`, `/v1/subscriptions`, `/v1/invoices`, `/v1/usage`), or GraphQL for the portal.\n- Required `Idempotency-Key` header on all POSTs.\n- Cursor pagination, expandable objects, and API versioning by date header (Stripe-style).\n- Outbound webhooks: HMAC-signed, retried with exponential backoff for up to 3 days, with ordered-per-object delivery hints and a replay UI.\n- An OpenAPI spec is the source of truth, and SDKs are generated from it.\n\n## 12.
