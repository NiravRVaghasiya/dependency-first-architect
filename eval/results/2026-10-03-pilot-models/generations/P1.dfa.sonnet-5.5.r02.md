# BUILD PLAN: customer-support RAG chatbot over the help center

## 1. Classification and constraints
- **What:** A customer-facing chat widget that answers questions from published help-center articles. It cites its sources and hands off to a human when it is unsure or the topic is policy-sensitive.
- **Type:** AI-agentic mix (RAG, read-only, no tools), added to an existing help center and support desk, so brownfield. It is not a small build, because outside users and customer-typed personal data are involved.
- **Dominant constraint:** correctness (grounded answers), then cost per resolved conversation.
- **Worst failure:** The bot confidently states a wrong or invented policy (refund, cancellation, pricing, legal) as the company's commitment, and the customer relies on it. A close second is leaking non-public content or customer PII.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency | First token p95 < 3 s; full answer p95 < 10 s | ASSUMPTION: typical for hosted-LLM chat; product owner to confirm | V0 floor; Phase 4 load check |
| Throughput | — | UNKNOWN: needs peak concurrent chats (support ops, before Phase 4) | Phase 4 load test |
| Availability / SLO | — | UNKNOWN: needs the availability the business commits to (product owner, before Phase 4). Fallback is "contact support", so the help center stays usable. | Phase 4 SLIs and burn-rate alerts |
| AI inference cost | Target cost per resolved conversation: no number | UNKNOWN: needs human cost per ticket (support lead, before Phase 4) | V5 |
| Operational complexity | One service, one managed Postgres (pgvector), one hosted LLM API | ASSUMPTION: small team, no self-hosted cluster | Phase 4 exit |
| Baselines to capture | Current ticket volume by topic, CSAT, re-contact rate | BASELINE: measured by support ops in Phase 0 | V5 |

Design parameters chosen now, which need no label:
- Per-request token caps
- A per-session cap
- A daily spend cap with alert and hard stop
- One model call per turn

**Missing inputs** (I'm proceeding on assumptions; each says what changes if it is false):
- **Corpus access.** I assume every indexed article is public and published. If gated or internal articles are included, retrieval must enforce the caller's entitlement before any pilot, and V3 gets heavier.
- **Read-only.** I assume the bot takes no account actions. If it must, tool allow-lists and human approval move before exposure, and the plan is re-planned.
- **Handoff.** I assume a live-chat or ticket handoff exists (ASSUMED). If not, building it precedes Phase 4.
- **Regulated data.** I assume none (no PHI or card data by design). Customers may still paste PII, so I treat chat text as personal data.
- **Not yet known:**
  - the help-center platform (Zendesk, Intercom, Confluence, or custom), including whether it has a publish webhook
  - languages
  - transcript retention period (legal, before Phase 1)
  - whether the platform's native AI is already licensed

## 3. Tradeoff gates

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Data-privacy boundary | R3: personal data sent to a vendor cannot be unsent | Hosted LLM under DPA (no training, limited retention); PII redacted before the model and before logs; the transcript store is ours, classified as personal data | Vendor terms are obtainable; redaction catches common PII | V2 | V2 fails, or the vendor won't contract these terms → different vendor or self-host |
| Hosted API vs self-host | R2: the model sits behind one interface (built in Phase 0), so swapping is weeks | Hosted LLM API with a second-vendor fallback | Volume and privacy terms fit a hosted API | V2 and V5 | V2 fails, or V5 shows cost per conversation is dominated by inference and self-host would beat it |
| Prompt+RAG vs fine-tune | R2 (R3 if trained on customer chats, which we will not do) | Prompt+RAG, no training on customer data | Failures are fixable by retrieval and prompt | V3 then V4 | V4 fails while V3 passes and failures are generation-type → spike a fine-tune on help-center text only |
| Document and chunk schema (stable article ID + revision, locale, audience/published flag, index version with pinned embedding model) | R2: the index rebuilds from source, but ids leak into citations, logs, and evals | Deterministic rebuild from the help-center source; the embedding model is pinned in the index version | Help center exposes stable article IDs | Phase 2 exit: a from-scratch rebuild in CI reproduces the same chunk IDs | Source lacks stable IDs → derive from URL + a mapping table |

**R1 defaults:**
- **Build vs buy:** build a thin service on a hosted LLM. This decides whether to build at all. If the help-desk vendor's native AI scores ≥ ours on the V3/V4 eval set at lower cost, buy and drop the custom build.
- **Monolith vs services:** one service.
- **Sync vs async:** streaming responses; ingestion is async.
- **Consistency vs availability:** the index is eventually consistent (publish webhook plus a nightly reconcile), and availability wins. Unpublished articles are removed on the webhook, within 1 h (ASSUMPTION).
- **Vector store:** pgvector.
- **Retrieval shape:** hybrid BM25 + vector, if V3 needs it.

**N/A:** Migration and cutover rows. Nothing is being replaced, and the existing contact form and human support remain the fallback and system of record.

## 4. Walking skeleton (Phase 0)
- **Real request:** An internal tester asks a real question from the ticket history in the widget. The service retrieves top-k chunks from a small real slice of published articles (~20), calls the LLM behind the model interface, and streams back an answer with citation links. The full-corpus index and eval set come later.
- **Tiers crossed:** widget → API service → retrieval (pgvector) → LLM vendor → response. The ingestion job runs once on the slice.
- **Deployed:** Through the real CI/CD pipeline to production, behind a feature flag, with infrastructure as code and a pinned model, prompt, and index version.
- **Logged and monitored:**
  - one trace ID per request across every tier
  - logs with token counts, latency, retrieval IDs, and cost
  - PII redacted and data-classed, with traces and logs access-controlled as personal data
  - alerts on error rate, latency, and spend
- **Day-zero guards:**
  - Retrieved and user text are passed as delimited data, never as instructions.
  - Hard token caps and a daily spend hard stop are in place.
  - Only test and internal queries reach the vendor until V2 and Phase 1.
- **Rolled back:** Flag off, so the widget falls back to the existing contact form. A deploy rollback is exercised once.
- **Reach:** Allow-listed staff only.
- **Also in Phase 0:**
  - Confirm the ASSUMED dependencies (webhook, handoff, article IDs).
  - Start the baseline capture.
  - Start the DPA request.
  - Start the eval labeling.

**Exit check (V0):** a real request succeeds with one trace across every tier; a deploy and a rollback succeed through the pipeline; an injected failure (LLM timeout) fires an alert; first latency and cost-per-turn values are recorded as a floor at near-zero load, not capacity.

## 5. Phases

- **Phase 1: Defenses and budgets** (all before any customer exposure)
  - Unlocks: internal use with real-looking data; Phases 2–3 hardening.
  - Depends on: Phase 0, V0.
  - Tasks, in order:
    1. Guardrails:
       - Separate system and untrusted content at the API boundary.
       - Allow only links to the help-center domain, and render no images.
       - Keep the bot read-only with no tools.
    2. PII redaction before the model and logs, with a retention policy.
    3. Per-session and daily caps, timeouts, and a degraded "contact support" response.
    4. Handoff: an always-visible "talk to a human" control.
    5. An injection suite in CI, with cases planted in user input and in indexed docs.
    6. A kill switch.
  - Rollback: flag off.
  - Exit check: V1 and V2 pass; a runaway or over-long request is cut at the cap and emits a cost metric.
- **Phase 2: Retrieval**
  - Unlocks: answer work.
  - Depends on: Phase 1, V2 (full-corpus text may contain customer-relevant content only, but the vendor terms gate embeddings), labeled set from the organizational dependency.
  - Tasks, in order:
    1. Document and chunk schema, and the index version pinned to the embedding model.
    2. Ingestion with the published and public filter.
    3. Webhook plus nightly reconcile, with deletion propagation.
    4. Chunking by heading.
    5. Hybrid search if needed.
    6. Run the eval in CI per index version.
  - Rollback: previous index version, which is retained.
  - Exit check: V3.
- **Phase 3: Grounded answers and model access**
  - Unlocks: exposure.
  - Depends on: V3.
  - Tasks, in order:
    1. Answer prompt that cites sources.
    2. Abstain when retrieval confidence is low.
    3. Policy-topic handling (refunds, cancellations, legal, pricing disputes, safety): link to the article and offer a human, make no commitment.
    4. Fallback model via config.
    5. Structured output parsing.
    6. Session-only conversation state.
  - Rollback: prior prompt or model config version.
  - Exit check: V4; switching to the fallback model is a config change and passes the eval at V4's bar.
- **Phase 4: Staged exposure** (smallest first)
  - Unlocks: wide rollout.
  - Depends on: V1, V2, V4, the handoff path, support-lead sign-off, and the UNKNOWN budget inputs supplied.
  - Tasks, in order:
    1. Support agents dogfood it.
    2. Canary of ~5% of traffic on one help-center section or one locale for a week.
    3. Load test at the supplied peak.
    4. SLIs and burn-rate alerts.
    5. Widen in steps after each check: V5 plus the escalation and CSAT checks.
  - Rollback: flag off per cohort. It is reversible at every step, with no point of no return.
  - Exit check: V5 passes; the SLO is attained over 30 days (once the target is supplied).
- **Phase 5: Feedback**
  - Unlocks: continuous improvement.
  - Depends on: Phase 4.
  - Tasks, in order:
    1. Thumbs and resolution signals.
    2. A "no answer found" report to help-center authors.
    3. Reviewed misses added to the eval set.
  - Rollback: n/a (no customer-facing change).
  - Exit check: the next eval run improves the target metric with no regression elsewhere; nothing enters prompts or training unreviewed.

## 10. Deliberately deferred
- **Account-specific answers or actions** (order status, refunds): pulled forward when V5 passes and a tool allow-list, human approval bound to the exact action, and an extended V1 are in place.
- **Gated or internal articles in the index:** pulled forward if the business wants them. Entitlement enforcement at retrieval and a V3 extension come first.
- **Additional languages:** pulled forward when the support lead supplies the locale priority. Each locale needs its own eval set and V3/V4 pass.
- **Long-term memory:** pulled forward when a measured use case needs cross-session context and legal approves the privacy boundary.
- **Routing or multi-model and orchestration:** pulled forward when V5 shows cost pressure and an eval shows a cheaper path within a stated quality margin.
- **Fine-tuning:** pulled forward only by the V4-fail flip in §3, on help-center text only. Training on customer chats is not planned.
- **Other channels (email, voice) and agent-assist mode:** pulled forward after Phase 4 metrics are stable.
