# BUILD PLAN: Multi-Tenant SaaS Billing System

## 1. Classification and Constraints

**What:** A multi-tenant billing system handling invoicing, payment processing, metering, and financial reporting for a SaaS platform.

**Type:** Software (backend services + APIs); not AI-agentic; assume greenfield with brownfield integration points (payment provider APIs, tax compliance).

**Scale:** Small to mid-market SaaS platform (simplify to one team initially, complexity emerges with multi-region and enterprise compliance only if budgets demand it).

**Dominant constraint:** **Correctness and compliance** — billing data loss, inaccuracy, or cross-tenant leakage causes financial harm, customer disputes, audit failures, and churn. **Availability** (revenue-critical path, SLO needed). **Data isolation** (every tenant's data and queries must be hermetically sealed).

**One failure that would hurt most:** Tenant A's invoice or payment applied to Tenant B, or invoices lost in crash/race condition.

**Budgets that matter:**
- **Availability:** REQUIREMENT (99.99% or stated in contract); baseline measured on legacy system if migrating.
- **Latency:** ASSUMPTION (invoice generation <5s, query <500ms at 10K concurrent users); confirm at scale or adjust async.
- **Compliance:** REQUIREMENT (PCI-DSS Level 1 or 2 if storing card data; SOX if public company; GDPR if EU customers; tax nexus per jurisdiction).
- **Cost per transaction:** ASSUMPTION (payment fee ~2.9% + $0.30; cost to store & query one invoice <$0.001 including compute and storage).
- **Data residency:** ASSUMED (single region; escalate if GDPR/data sovereignty contract terms demand it).
- **Operational complexity:** BASELINE (number of on-call incidents and runbooks for legacy billing; target <10% increase post-launch).

**Missing inputs that would change the plan:**
- Is this greenfield (new SaaS platform) or brownfield (migrating existing, scaling, or replacing legacy)? → ASSUMED greenfield; if brownfield, phases 0–2 add dependency mapping and cutover gates.
- Payment processing: build custom PSP integration or use Stripe/Recurly/Zuora? → ASSUMED use hosted provider (Stripe/Recurly); build custom only if stated.
- Multi-currency and tax? → ASSUMED single currency initially, tax calculation deferred to Phase 3.
- Multi-tenancy model: row-level security in shared schema, or separate schemas/databases per tenant? → DEFERRED to R3 Tradeoff gate (T1).

## 3. Tradeoff Gates

| Decision | Reversibility | Default (chosen) | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| **T1: Tenancy model** | R3 (schema change, migration, cascade on queries) | Shared schema, row-level security per tenant via `tenant_id` column + SQL WHERE filters | Multi-schema costs maintenance (N schemas × N migrations); shared schema simplifies deployment and cost | V1 isolation gate: inject query for Tenant B's invoices into Tenant A session; must fail. Test isolation on schema, API, caching layers | If compliance audit or tenant size demands isolation (contractual SLA), flip to schema-per-tenant and run Phase 1 refactor (Phase 2.5 insertion) |
| **T2: Idempotency & order** | R2 (add idempotency keys, adapt reconciliation) | Every invoice, charge, and payment has unique `idempotency_key` (e.g., `{tenant_id}#{source_id}#{timestamp}`); upsert on duplicate → skip & return existing | API clients will retry on timeout; kernel must not create duplicates on retry | V2: send same `idempotency_key` twice; same result returned second time; ledger unchanged | If first deploy sees duplicate invoices, add idempotency retroactively (weeks; run reconciliation migration) |
| **T3: Consistency model** | R3 (commit in write path, affects latency & failover) | **Immediate consistency**: writes to ledger must ACK only after committed to primary DB and replicated to read replica | Async replication risks stale reads during query (customer sees unpaid invoice already paid); immediate consistency trades latency for correctness on revenue data | V3: crash-test at 1K write TPS; verify no read-after-write anomaly; measure p99 write latency | If latency SLO fails (>5s), flip to eventual consistency with message queue; accept 2s staleness window and document it |
| **T4: Build vs. buy metering** | R1 (stub now, swap provider later) | Build thin wrapper around usage events from application; cache in Redis; no metering API yet | App already emits usage events (user assumption); we consume, aggregate, archive | Spike in Phase 1: confirm app can emit hourly usage snapshots; measure volume (100 events/s target) | If app cannot emit on cadence, buy hosted metering (Amberflo, Maxio) in Phase 2; skeleton stays, wrapper becomes adapter |
| **T5: Ledger storage** | R2 (migrate ledger to new table, add index) | Single `ledger_entries` table (immutable append-only); no sharding | Ledger grows ~1M rows/year per 100 tenants; single table + index sufficient for 10 years | V4 (Phase 2): load test 100M row scan, invoice generation query <500ms p95 | If query degradation, shard by `tenant_id` & month (Phase 3 work); read replicas meet v0 SLO for now |
| **T6: Tax calculation** | R1 (not in skeleton) | Deferred to Phase 3; skeleton charges gross amount only (tax_rate = 0) | SaaS initially US-only or single tax zone | Removed when tax nexus expands (Phase 3 gate) | Phase 3 adds tax service integration (20% of Phase 3 work) |

**R1 decisions (one line):**
- Initial deployment is single region, US-only, one currency (USD); flip to multi-region/currency after Phase 2 SLO is met.

**N/A:**
- Redundancy model (active-active vs. active-passive): implicit in consistency model (T3); this system uses a primary DB with read replicas; failover manual initially, automated in Phase 2.
- Monolith vs. microservices: skeleton is one service (billing API); refactor to async jobs (Phase 2); further split only if Phase 3 demands it.

## 4. Walking Skeleton (Phase 0)

**Real request & response:**
```
POST /api/invoices/create
{
  "tenant_id": "acme-corp",
  "customer_id": "cust-42",
  "line_items": [
    {"description": "SaaS subscription Jan", "amount": 1000.00}
  ],
  "due_date": "2026-02-03"
}

← 201 Created
{
  "invoice_id": "inv-uuid",
  "tenant_id": "acme-corp",
  "amount": 1000.00,
  "status": "draft",
  "created_at": "2026-01-03T14:22:33Z"
}
```

**Every tier it crosses:**
1. **API Gateway** (auth, rate limit) → verify `Authorization: Bearer <token>` includes `tenant_id`; reject if tenant mismatch.
2. **Billing Service** (invoice creation, ledger append) → parse request; append `ledger_entry` (type: invoice, amount, +1000); return invoice.
3. **Database** (PostgreSQL, primary in us-east-1) → INSERT into `invoices` and `ledger_entries`; wait for sync replication to read replica.
4. **Read-back** (verify write) → query read replica; confirm invoice visible (tests replication).

**Deployment & rollback:**
- **Deploy:** Git commit → GitHub Actions pipeline → lint, build, unit test → Docker image → push to ECR → deploy to ECS (dev environment) → run smoke test.
- **Rollback:** Previous image tag available; rollback to prior version in <2 min (manual trigger, no traffic until verified).
- **Logging & monitoring:**
  - Every API call logged with `request_id`, `tenant_id`, `user_id`, `method`, `status` (no sensitive data in logs).
  - Trace headers (W3C) threaded through DB call.
  - CloudWatch metrics: invoice create latency (p50, p95, p99), ledger write latency, replication lag.
  - Alert if replication lag >10s or invoice create latency >5s (skeletal, no multi-threshold logic yet).

**Who can reach it:**
- Phase 0 is **internal only** (dev/staging environment); no real tenants, no real payment data. Requests via curl/Postman from dev machine; no external internet access.
- Auth is stubbed: `Authorization: Bearer skeleton-token-internal` accepted for any `tenant_id` in request (will be hardened in Phase 1).

**Unvalidated defaults:**
- Replication lag: ASSUMPTION <100ms; not yet load-tested.
- Invoice generation latency: ASSUMPTION <500ms; not yet under load.
- Ledger queries: ASSUMPTION single index on `tenant_id, created_at` sufficient; not yet benchmarked at scale.

**Exit check V0** (passes before Phase 1 tasks start):
- ✅ Real invoice POST succeeds, returns 201 with invoice_id.
- ✅ Ledger entry visible on read-after-write (confirm replication worked).
- ✅ Deploy pipeline completes (build, push, deploy) in <5 min.
- ✅ Rollback to prior version completes in <2 min.
- ✅ Injected failure (kill primary DB, trigger failover) → request fails gracefully (500 error logged, alert fires); no data corruption.
- ✅ Baseline metrics recorded: invoice create latency p99 ~50ms, replication lag ~5ms, DB connection pool 10/10 available (floor).

### Phase 1 (Core API & isolation validation — weeks 2–4)
**Unlocks:** Phase 2 (compliance & production prep), Phase 3 (async jobs, scaling).

**Depends on:** V0 passes; T1 (tenancy model) locked; T2 (idempotency) locked; Org approval for plan (Finance/Legal sign-off).

**Tasks:**
1. **Multi-endpoint API:**
   - `POST /invoices` (create draft invoice).
   - `POST /invoices/{id}/send` (mark sent, emit event).
   - `GET /invoices/{id}` (retrieve; auth checks `tenant_id`).
   - `GET /invoices` (list for tenant; filtered by `tenant_id` in WHERE clause and token).
   - `POST /charges` (charge payment for invoice).
   - `GET /charges/{id}` (retrieve charge; auth check).
   - `POST /refunds` (refund charge).

2. **Auth & row-level security (hardened):**
   - Bearer token decoding: extract `tenant_id` from JWT.
   - Every query filters `WHERE ledger_entries.tenant_id = $1` (parameterized); no concatenation.
   - API middleware rejects any request with mismatched `tenant_id` in URL vs. token.
   - Test: inject Tenant B's invoice_id into Tenant A's GET request → 403 Forbidden (no data leakage).

3. **Charge & refund with payment provider (Stripe stub):**
   - POST `/charges`: call Stripe API `charges.create()` with `idempotency_key` → store charge in DB, ledger entry for debit.
   - POST `/refunds`: call Stripe API `refunds.create()` → store refund, ledger entry for credit.
   - Stripe webhook `/webhooks/charge-paid` → confirm charge status; update DB; emit internal event (async).

4. **Events & audit trail:**
   - Every create, update, or delete on invoices/charges/refunds logs event to immutable `events` table.
   - Event schema: `{event_id, tenant_id, entity_type, entity_id, action, old_state, new_state, created_at, created_by}`.
   - Events published to SQS for downstream subscribers (Phase 2+).

5. **Ledger correctness & double-write test (V2):**
   - Ledger append (immutable) + invoice state table must stay consistent.
   - Test: create invoice, charge, refund in quick succession; verify ledger balance = sum of invoice + charges - refunds.
   - Test race: two concurrent refunds for same charge → second must fail or second refund = 0.

6. **Observability hardening:**
   - Add structured logs: JSON format with `tenant_id`, `request_id`, `action`, `duration_ms`.
   - Metrics: per-endpoint latency, error rate by endpoint and tenant, ledger query latency.
   - Traces: one sample per 100 requests (1%); debug sampler for test tenants.
   - Dashboards: invoice creation SLI (latency p95, error rate), charge success rate.

**Rollback:** Feature flag per endpoint (Phase 1 endpoints off by default; gradually roll on); old schema + code in parallel for read-back queries; no migration.

**Exit check:** V1 (isolation gate), V2 (ledger correctness), V3 (idempotency), metrics baseline for Phase 2 SLO.

### Phase 2 (Compliance & production readiness — weeks 5–8)
**Unlocks:** Phase 3 (async jobs, scaling, tax), Production canary rollout.

**Depends on:** V0, V1, V2, V3 gates pass; Finance/Legal sign-off on data flows; V4 (ledger query performance).

**Tasks:**
1. **PCI-DSS compliance (Level 1 if storing card data, Level 2 if tokenized):**
   - Remove credit card numbers from DB entirely (use Stripe tokens only).
   - Add data expiry: delete `charges` table rows >7 years after charge (batch job).
   - Enable encryption at rest (RDS encryption, KMS key managed by Ops).
   - Audit logging: who queried what, when (CloudTrail for API calls; app logs for DB queries via RDS audit).
   - VPC isolation: billing service in private subnet; only App → Billing allowed; no inbound from internet.
   - Penetration test spike (optional, risk-based): if compliance audit required, schedule external pen test in Phase 2 (adds 2 weeks).

2. **Reconciliation & financial controls:**
   - Daily batch job: sum all ledger entries; compare to Stripe API total charges & refunds; alert if mismatch >1%.
   - Monthly reconciliation report: invoice total = revenue recognized; send to Finance for sign-off.
   - Ledger query performance validated (V4 gate): 100M rows, invoice generation query <500ms p95 under 1K concurrent users (load test).

3. **Webhooks & idempotency hardening (Stripe webhook risk):**
   - Webhook endpoint `/webhooks/stripe` receives charge.paid, charge.failed, charge.refunded events.
   - Webhook signature verified (Stripe sends `Stripe-Signature` header; validate using Stripe signing secret).
   - Event deduplication: store `webhook_event_id` in DB; if already processed, return 200 (no-op).
   - Retry logic: app processes webhook within 30s; if fails, SQS DLQ captures; Ops reviews daily.

4. **Backup & disaster recovery:**
   - RDS automated backups (daily snapshots, 30-day retention).
   - Restore procedure documented & tested (one rehearsal: restore to staging, verify data integrity).
   - RTO: 1 hour (restore from snapshot); RPO: 1 day (daily backup).
   - After rehearsal, document in runbook; verify Ops team can execute.

5. **Production deployment pipeline (hardened):**
   - Manual approval gate before production deploy (on-call eng or manager).
   - Canary deploy: 10% of traffic to new version for 10 min; monitor error rate & latency; abort if either spikes >5%.
   - Blue-green staging: new version validated fully in staging before canary.
   - Rollback: revert traffic split (traffic back to old version) if canary fails; <30s.

**Rollback:** Feature flag + canary: if canary fails, traffic reverts; old version still running. Data-only changes (data expiry, reconciliation format) tested in staging first.

**Exit check:** V4 (ledger query performance), V5 (PCI compliance audit readiness), reconciliation test passes, DR rehearsal successful, canary deploy procedure verified.

### Phase 3 (Async scaling, advanced features — weeks 9–12+)
**Unlocks:** Enterprise features (tax, multi-currency, advanced reporting), Phase 4 (multi-region).

**Depends on:** Phase 2 complete; V4, V5 gates pass; Finance sign-off on tax logic (if added).

**Tasks:**
1. **Async invoice generation (Metering → Invoice):**
   - Metering data from app (usage snapshots per hour).
   - Scheduled job (nightly): aggregate usage for each tenant → generate invoice line items.
   - Job publishes `invoice.generated` event → SQS → downstream (e.g., send email).
   - Idempotency: if job runs twice (clock skew), same invoice; no duplicates.

2. **Tax calculation (if scope includes it; else N/A):**
   - Add `tax_rate` field to invoice, per jurisdiction.
   - Daily batch: for each tenant with address, look up tax rate (simple table or external API, e.g., TaxJar).
   - Recalculate invoice totals: `amount_gross = amount + (amount * tax_rate)`.
   - Finance approval on tax logic before go-live.

3. **Advanced reporting:**
   - Aggregation tables: `revenue_by_month`, `churn_rate`, `ltv`.
   - Nightly batch populates from ledger.
   - Read-only API: `/reports/mrr`, `/reports/cohort`, etc.

4. **Notification system:**
   - Event → SQS → Lambda → send email (via SendGrid or SES).
   - Events: invoice.sent, charge.succeeded, charge.failed, refund.processed.

**Rollback:** Async jobs run in isolation; if job fails, DLQ + manual replay in staging.

**Exit check:** Async job latency <1s (publish to SQS); email delivery <5 min; tax calculation validated against known test cases.

5. **Advanced revenue recognition** (GAAP ASC 606) — pulled forward if public company or major enterprise contract. Blocker: accounting policy; Finance sign-off on journal entry rules.
