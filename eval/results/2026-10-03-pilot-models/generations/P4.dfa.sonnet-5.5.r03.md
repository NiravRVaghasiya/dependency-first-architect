# BUILD PLAN: Autonomous GitHub issue triage and resolution agent

## 1. Classification and constraints
- **What:** A GitHub App and worker service. It triages new issues (labels, priority, duplicate suggestions, clarifying questions). When a maintainer opts in, it reproduces the issue, writes a fix in a sandbox, and opens a draft PR for human review.
- **Type:** AI-agentic. The agent is new (greenfield), but it runs inside an existing GitHub org, CI, and review process (brownfield host). It is not a small build: it has write access to code, runs model-generated code, and holds credentials.
- **Dominant constraint:** Security and correctness. The agent reads attacker-influenced text and can change code. Cost is second.
- **Worst failure:** Injected text in an issue, comment, or repo file makes the agent exfiltrate secrets or private code, or lands malicious code that reaches a protected branch or runs in CI with secrets. V2 guards this.
- **Fallback and system of record:** The fallback is today's manual triage. GitHub remains the system of record for issues, PRs, and labels. The agent's database holds run state only. Sync is GitHub → agent by webhook, and agent → GitHub by API writes.

**Missing inputs** (assumptions stated; the plan proceeds on them):
1. **Can private code and issue text go to a hosted model API?** Assumed not until V1 passes, so Phase 0 uses only a sandbox repo with synthetic and public issues. If the answer is no, the plan flips to a self-hosted or private-endpoint model (§3). This changes Phase 2, not the phase order.
2. **Who files issues and are the pilot repos public?** Assumed: internal/private pilot repos. All issue text is treated as untrusted regardless.
3. **Pilot repos' languages and test setup.** Resolution needs a reproducible build and tests. Assumed: 2–3 repos with CI that runs in a container (repo owners, Phase 0).
4. **Runtime and cloud.** Assumed: a container platform and a managed Postgres already exist.
5. **Named security reviewer** for V2 (security lead, needed before Phase 1 exit).

## 3. Tradeoff gates

**R1 defaults:** sync vs async → async (webhooks must ack in seconds); queue → Postgres `SKIP LOCKED` (one fewer dependency); monolith vs services → one worker service plus the sandbox runner; consistency → single Postgres, idempotency keyed on `X-GitHub-Delivery`; language/framework → the team's default.
**N/A:** Migration strategy, cutover, and tenancy are not applicable. Nothing is being replaced, and there is one org and one tenant.

## 4. Walking skeleton (Phase 0)
- **Request:** A real issue is opened in a **sandbox repo** (synthetic and public-OSS issues only; no private data to a model before V1). The GitHub webhook hits the receiver, which verifies the HMAC and dedupes on delivery ID, then enqueues the job. A worker fetches the issue, treats its text as data in a delimited untrusted block, and calls the model through a provider interface. It validates the structured output (label, priority, summary) against a schema. The App then applies the label and posts a comment on the sandbox issue. The bot ignores its own events, so it can't loop.
- **Tiers:** GitHub → webhook receiver → Postgres queue → worker → model API → worker → GitHub API.
- **Deploy and rollback:** The pipeline builds a pinned container image, with infrastructure as code. Rollback is redeploying the previous image. A global **kill switch** (config flag) and an App suspend are the emergency stop. A hard per-run token/cost cap and a wall-clock timeout are in from the start.
- **Logging and monitoring:** OpenTelemetry trace per issue across all tiers. Structured logs and token/cost metrics, with trace and log stores carrying the same access classification as the repo data they hold, short retention, and secret redaction. Alerts on dead-letter depth, error rate, and cost-cap hits.
- **Reach:** Only the sandbox repo, with the App installed nowhere else. The org-admin approval and V1 request start now (lead time).
- **Exit check (V0):** A real sandbox issue produces a label and comment with one trace across every tier. A deploy and a rollback succeed through the pipeline. An injected failure (model 500s, poison message) fires an alert. Baselines are recorded: triage latency floor, tokens and cost per triage, and the pilot repos' 90-day issue volume.

## 5. Phases

- **Phase 1: Containment and gating** (defenses before capability)
  - Unlocks: Any exposure to real repos.
  - Depends on: V0.
  - Tasks, in order:
    1. Freeze the action schema and the tool-executor contract. Every write goes through an executor that enforces an allow-list, validates arguments, and requires an approval token bound to the exact action for gated actions.
    2. Add the branch/path rulesets and the secretless-CI rule. CI on `agent/*` branches runs with no secrets and no deploy credentials, as for fork PRs, and the agent token can't approve.
    3. Build the sandbox runner.
    4. Close exfiltration paths: no model-driven URLs, images, or outbound tools.
    5. Enforce the cost/iteration/time caps and the kill switch.
    6. Add the injection suite to CI, with cases planted in issue bodies, comments, repo files, CI logs, and tool output.
  - Rollback: Kill switch, then App uninstall. No real repos are involved yet.
  - Exit check: V2 passes; a runaway loop is cut at the cap and emits a metric; a gated action can't run without a bound approval.
- **Phase 2: Retrieval, model access, and live triage**
  - Unlocks: Triage on real repos; the base for resolve.
  - Depends on: V1 and V2.
  - Tasks:
    1. Harden the model interface: retries, a configured fallback model, strict output parsing.
    2. Build the repo and issue-history index with the embedding model pinned to the index version. It stays within the installed repo's own access, with no cross-repo retrieval.
    3. Run triage in **shadow** on one pilot repo (log only), scored against maintainers' actual labels (V3).
    4. If V3 passes, enable live labels and comments on that repo. Duplicates are suggested in comments only. The agent never closes issues.
  - Rollback: Kill switch. Labels and comments are removed by a bulk script keyed on the bot's authorship.
  - Exit check: V3 passes; a query never returns a passage the caller can't read; fallback model switch is a config change and passes the V3 eval set.
- **Phase 3: Resolution on one canary repo**
  - Unlocks: Draft PRs from the agent.
  - Depends on: V2, V3.
  - Tasks:
    1. Orchestration: a fixed state machine (plan → reproduce → patch → run tests → self-review → open draft PR), not multi-agent. Each step is traced, and failures retry or surface a "could not resolve" comment.
    2. Per-issue run state in Postgres is the only memory. There is no cross-issue learning.
    3. Run the offline benchmark (V4), including the Copilot comparison.
    4. If V4 passes, open a one-repo canary with `agent:resolve` opt-in, draft PRs only, and measure (V5).
  - Rollback: Kill switch and close agent PRs/branches by script. Nothing merges without a human, so there is no point of no return.
  - Exit check: V4, then V5 measured over the canary window; every PR traces to its run; the sandbox leaves no residue.
- **Phase 4: Widen, then optimize**
  - Unlocks: More repos; cost control.
  - Depends on: V4, V5.
  - Tasks:
    1. Widen one repo at a time, each after its own CI/test-setup check.
    2. Add routing (cheap model for triage and easy issues, strong model for patches) only if V5 misses its bar.
    3. Add feedback: maintainer outcomes (merged, edited, rejected) enter the eval set through review, never directly into prompts.
  - Rollback: Per-repo uninstall; routing behind a flag.
  - Exit check: Each new repo's triage agreement and accept rate are not worse than the previous repo's by more than the V3/V5 margins; routing passes a quality-within-margin eval at lower cost.

## 10. Deliberately deferred
- **Auto-merge or auto-approve:** pulled forward only if a long record of accepted PRs on a low-risk class exists and security signs off. It needs a new gate and would restructure the authority row in §3.
- **Auto-closing duplicates or stale issues:** pulled forward when V3-style duplicate precision is measured on real data and maintainers want it. It needs a separate gate for the harm to reporters.
- **Multi-agent orchestration:** pulled forward only if the state machine fails V4 on multi-step issues.
- **Fine-tuning:** pulled forward when the §3 flip condition is met.
- **Cross-repo or org-wide retrieval and memory:** pulled forward when a per-repo access-control design passes a retrieval-permission check.
- **Public repos with outside issue authors:** pulled forward after V2 is re-run with the public-repo corpus and the triage-only mode is live internally.
- **Self-hosted model:** pulled forward if V1 fails or V5 shows hosted cost is non-viable.
