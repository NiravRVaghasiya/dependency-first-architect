# Plan: Autonomous GitHub Issue Triage & Resolution Agent

## 1. Goals and non-goals

**Goals**
- Triage new issues: classify them, deduplicate them, label them, prioritize them, and ask for missing info.
- Resolve a safe subset automatically by opening a tested PR that links to the issue.
- Escalate everything else to humans, with useful context attached.

**Non-goals (v1)**
- Merging PRs without human review.
- Touching security-sensitive issues, release or CI config, or secrets.
- Large architectural changes.

## 2. Architecture

```
GitHub webhook (issues.opened / edited / commented / labeled)
        │
        ▼
  Event queue (dedupe, rate-limit, idempotency keys)
        │
        ▼
  Orchestrator (state machine per issue)
        ├── Triage stage      (read-only, cheap model)
        ├── Repro stage       (sandbox)
        ├── Fix stage         (sandbox, stronger model)
        ├── Verify stage      (tests, lint, independent review)
        └── PR / Report stage (GitHub API)
        │
        ▼
  State store (issue → stage, attempts, artifacts, cost)
  Audit log + metrics
```

**Key design choices**
- **Sandboxed execution.** Each run gets an ephemeral container with a fresh clone, no network except an allowlist (package registries and the GitHub API), and no long-lived credentials.
- **Least-privilege GitHub App** instead of a PAT. Scopes: issues r/w, pull requests r/w, contents write to `agent/*` branches only, checks read. Branch protection stops it from pushing to main.
- **Separation of stages.** Triage has read-only tools. Only the Fix stage can edit files. Only the PR stage can write to GitHub.

## 3. Pipeline stages

### Stage A: Triage
1. **Sanitize input.** Treat issue text and comments as untrusted data, not instructions (see §6).
2. **Classify** into bug, feature, question, docs, support, security, spam, or duplicate.
3. **Deduplicate** with embedding search over open and closed issues plus a keyword check. If the match is confident, comment with the link and label `duplicate`. Don't auto-close in v1. Propose it.
4. **Completeness check.** For a bug, look for a version, repro steps, expected vs. actual behavior, and logs. If any are missing, post one templated, specific request and apply `needs-info`. Set a reminder for 7 days.
5. **Localize.** Identify likely files, modules, and owners using code search, CODEOWNERS, and `git blame`.
6. **Label and prioritize.** Set area labels, severity (P0–P3), and difficulty, with a confidence score for each.
7. **Route** with the decision table below.

| Condition | Action |
|---|---|
| Security-flavored, or confidence < threshold | Label `needs-human`, notify maintainers, stop |
| Question or support | Answer from docs or code with citations, or route |
| Feature request | Label it, summarize it, and route to maintainers (no auto-implementation in v1) |
| Bug, well-specified, small scope | Go to Repro |
| Bug, unclear | Ask for info |

### Stage B: Reproduction
- Write a failing test or script that demonstrates the bug.
- If it can't be reproduced after N attempts, comment with what was tried and label `cannot-reproduce`. Don't proceed to a fix.
- A failing test that is committed with the fix is the strongest evidence the fix is correct.

### Stage C: Fix
- Agent loop with tools: `read_file`, `search_code`, `edit_file`, `run_tests`, `run_linter`, `git_diff`.
- **Budgets:** a cap on steps, wall-clock time, tokens and dollars, and files changed (e.g. ≤ 5 files, ≤ 200 lines). Exceeding any of them escalates.
- **Rules:** make the minimal change, follow the repo's conventions (read CONTRIBUTING.md and existing style), don't edit tests to make them pass, and don't touch denylisted paths (`.github/workflows`, lockfiles, auth and crypto modules, migrations).

### Stage D: Verification
- Run the full relevant test suite, linter, type checker, and build.
- The new repro test must fail before the fix and pass after it.
- **Independent review pass.** A separate model call with fresh context reviews the diff against the issue. It looks for scope creep, missed edge cases, and suspicious changes such as weakened assertions and skipped tests.
- Static checks on the diff: secrets scan, no new dependencies unless allowed, and no disabled tests.
- On failure, retry up to K times with the failure output, then escalate with a summary.

### Stage E: PR and communication
- Branch `agent/issue-<n>-<slug>`. Open a **draft** PR or a regular PR, as the repo chooses.
- The PR body includes: `Fixes #n`, root cause, the change, test evidence, risks, and what the agent is unsure about.
- Label it `agent-authored`. Request review from the CODEOWNERS or the area owner.
- **Respond to review comments.** Apply requested changes within budget, and hand off to the human if there is disagreement or more than 3 rounds.
- Comment on the issue with a link to the PR. Keep comments concise and avoid noise.

## 4. Tooling and context

- **GitHub API tools:** get issue, list comments, search issues, add labels, comment, create branch, open PR, read check runs.
- **Repo intelligence:** an index of the code (symbol search and embeddings), the CODEOWNERS file, and recent commits touching the localized files.
- **Repo config file** (`.github/issue-agent.yml`) so each repo controls behavior:
  ```yaml
  auto_fix: { enabled: true, max_files: 5, max_lines: 200 }
  deny_paths: [".github/**", "**/migrations/**", "**/auth/**"]
  labels: { map: {...} }
  test_command: "make test"
  escalate_to: ["@team/maintainers"]
  ```
- **Memory:** per-issue state in a DB. Per-repo learnings, such as maintainer corrections to labels, go into few-shot examples.

## 5. Autonomy levels (phased rollout)

| Phase | Behavior | Exit criteria |
|---|---|---|
| 0. Shadow | Produces triage decisions privately and compares them to human decisions | ≥ 90% label agreement; dedupe precision ≥ 95% |
| 1. Triage live | Labels, needs-info requests, and dedupe suggestions are posted | Few maintainer reversals; no complaints |
| 2. Fix as draft PR | Opens draft PRs for low-risk bugs, on an allowlist of labels (e.g. `good first issue`, `docs`, `typo`) | PR acceptance rate ≥ 50%; no regressions |
| 3. Broader fixes | Expand scope and difficulty gradually | Sustained quality metrics |

A **kill switch** (a repo variable or label) pauses the agent instantly.

## 6. Safety and security

- **Prompt injection.** Issue bodies, comments, and code can contain malicious instructions.
  - Keep untrusted text in clearly delimited data sections.
  - Stage permissions are enforced by tooling, not by the prompt.
  - The sandbox has no secrets and limited egress, so an injected instruction can't exfiltrate anything.
- **Who can trigger it.** Only auto-fix issues from trusted authors, or ones a maintainer approves with a label such as `agent:go`. Otherwise triage only.
- **Security reports** are never discussed publicly by the agent. They go to the private channel.
- **Supply chain.** No new dependencies and no workflow edits. PR CI runs with the normal untrusted-PR permissions.
- **Honesty.** The agent must disclose that it is a bot, and must never claim to have tested something it didn't.
- **Audit log** of every tool call, decision, and model prompt and response, with retention.

## 7. Evaluation

- **Offline benchmark.** Replay historical issues: triage against the actual labels, and fixes against the commits that closed them (in the style of SWE-bench, built from the repo's own history). Run it on every prompt or model change.
- **Online metrics**
  - Triage: label accuracy, duplicate precision and recall, time to first response.
  - Fix: PR merge rate, review iterations, CI pass rate on first push, revert rate, maintainer time saved.
  - Ops: cost per issue, escalation rate, and latency per stage.
- **Feedback loop.** A maintainer removing or changing a label, or closing a PR, is logged as a correction signal. Review it weekly.

## 8. Failure handling

- Idempotent handlers. Webhooks can be redelivered.
- Rate limiting and backoff on the GitHub API, and a per-repo concurrency cap.
- Hard timeouts, with sandbox teardown on every run.
- Every failure path ends in a visible state: `needs-human` with a short summary of what was tried.
- Loop detection: don't re-trigger on the agent's own comments or labels.

## 9. Implementation milestones

1. **Week 1–2:** GitHub App, webhook receiver, queue, state store, and sandbox runner.
2. **Week 3–4:** Triage stage (classify, label, dedupe, needs-info), plus the shadow-mode harness and eval set.
3. **Week 5–6:** Repro and Fix loop with budgets and the verification pipeline.
4. **Week 7:** PR stage, review-response loop, and config file.
5. **Week 8:** Security hardening (injection tests and red-teaming), dashboards, and the kill switch.
6. **Week 9+:** Staged rollout per the phases above.

## 10. Open questions

- Which repos and languages come first? That determines the sandbox images and test commands.
- Who are the maintainers and reviewers, and what SLA do they expect?
- Which model or provider, and what is the per-issue cost ceiling?
- Should the agent run as a hosted service or as a GitHub Action? An Action is simpler to start with, and a service scales better.
- Are the repos public (greater injection risk) or private?
