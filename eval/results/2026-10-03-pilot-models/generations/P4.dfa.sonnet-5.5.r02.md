# BUILD PLAN: Autonomous GitHub issue triage and resolution agent

## 1. Classification and constraints
- **What:** An agent that reads new GitHub issues, labels them, flags duplicates, and asks for missing info. For issues a maintainer opts in, it drafts a fix as a pull request (PR) that a human reviews and merges.
- **Type:** AI-agentic plus software. The agent is greenfield, but it attaches to existing repos and CI (brownfield-lite). Humans doing triage today is the fallback path. This is not a small build: outside users author the input, it spends money, and it acts on code.
- **Dominant constraint:** Correctness and security (containment of untrusted input).
- **Worst failure:** Attacker-authored issue text, comments, or repo content steers the agent into leaking secrets or private code, or into landing malicious code on a protected branch. V2 and V3 guard this, and human-only merge enforced by GitHub branch protection backs them up.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Webhook acknowledgment | Respond within GitHub's webhook timeout, then process async | REQUIREMENT (GitHub webhook docs) | V0 |
| Triage latency | p95 ≤ 5 min from issue opened to proposal | ASSUMPTION (typical "fast first response" goal; owner to confirm) | V4 |
| Throughput | Pilot repo only, low volume; real rate UNKNOWN (see Missing inputs) | UNKNOWN | V0 baseline |

| Resource use | Sandbox: ≤ 15 min wall-clock and ≤ 4 vCPU per run | ASSUMPTION (design parameter, tune in V5) | V3, V5 |

**Missing inputs** (none changes the phase order, so I'm proceeding on the assumptions below):
- **Repo scope:** Assumed one pilot repo with CI and reasonable tests, where public or external users can file issues. If none has tests, Phase 3 resolution moves to deferred. The owner supplies this before Phase 0.
- **Model provider and data terms:** Assumed a hosted provider under enterprise no-training, zero-retention terms (see V1). The security or legal owner supplies this before Phase 0.
- **Numbers:** Issue volume, the monthly budget, and maintainers' review-time tolerance are needed before the Phase 0 cap and V5. The engineering owner supplies them.
- **GitHub org admin:** An admin must approve the GitHub App install. Request this first because it has lead time.

## 3. Tradeoff gates

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Autonomy and trust boundary | R3 (trust boundary; a bad merge is harm that can't be undone) | The agent only comments, labels, and opens draft PRs on `agent/*` branches. A human merges. Branch protection, CODEOWNERS, and required CI are enforced by GitHub, not by the agent. The agent cannot touch `.github/`, lockfiles, or secrets paths. | Maintainer review is affordable | V2, V3 | Auto-merge is considered only after V5 plus months of measured history. See §10. |
| Data-privacy boundary and hosting (hosted API vs self-host) | R3 (code leaves the org; data gravity at a vendor) | Hosted model API under zero-retention enterprise terms. Pilot repo contents only, no secrets. | The security owner accepts the terms | V1 | V1 fails, or the repo is classified too sensitive. Then self-host or restrict to issue text only. |
| Execution isolation | R3 (trust boundary; untrusted code runs) | Ephemeral microVM or gVisor container per run. Egress only through an allow-listed package proxy. No agent or GitHub credentials inside. Repo mounted in and the diff returned out. | Isolation holds against malicious repo content | V3 | V3 fails. Then no code execution and triage only. |
| Identity and hosting | R2 (permission changes need org re-approval per repo) | A GitHub App with least privilege: issues write, pull requests write, contents write limited to `agent/*` branches, metadata read. No PATs and no Actions-with-secrets. The service runs outside the repo's CI. | Those permissions suffice | Phase 0 permission review (named reviewer, pass/fail) | The App can't be scoped to a branch prefix. | Prompt+RAG vs fine-tune | R2 | Prompt plus retrieval (issue history, code search). No fine-tuning. Never train on repo or user data (R3). | Retrieval closes the quality gap | V4 | V4 fails after retrieval tuning and enough reviewed labels exist. Revisit with a privacy review. |
| Eligibility to resolve | R2 (changes the workflow of maintainers and contributors) | Resolution runs only on issues a maintainer labels `agent-ok`. An issue's author can't trigger code execution. | Opt-in is acceptable to maintainers | V2 | Maintainers want wider triggers. Re-run V2 with the new trigger. |

**R1 defaults:**
- **Monolith vs services:** modular monolith (API, worker) plus a separate sandbox runner.
- **Sync vs async:** acknowledge the webhook, enqueue, and process async with idempotency keys on the delivery ID (at-least-once, duplicate-safe writes).
- **Consistency vs availability:** favor availability, since GitHub is the source of truth and the agent is additive.
- **State store:** Postgres plus a queue (SQS or Redis).
- **Build vs buy:** build on an agent SDK. Spend one day comparing against an off-the-shelf coding agent. If one meets V4 and V5 thresholds inside V1–V3 constraints, buy instead.

**N/A:** Brownfield migration, cutover, and system-of-record transfer. Nothing is migrated, and GitHub stays the system of record.

## 4. Walking skeleton (Phase 0)
- **Request:** A real issue opened by a maintainer on the allow-listed pilot repo. GitHub sends a webhook (signature verified) to the API, which enqueues it. The worker fetches the issue and calls the model with issue text wrapped as untrusted data. The model returns a structured triage proposal (label, duplicate candidates, missing-info question). The agent writes the proposal to the trace and an internal channel (dry run) and performs no GitHub write.
- **Tiers:** GitHub → webhook API → queue → worker → model API → Postgres audit log → internal channel.
- **Deploy and rollback:** The pipeline builds a container image and deploys from IaC (Terraform). Rollback redeploys the previous image. A feature flag or kill switch disables the agent without a deploy. Both are exercised once.
- **Logging and monitoring:** OpenTelemetry trace per issue from webhook to model call. Structured logs with issue text redacted or classified like the repo data. Metrics for tokens, cost, latency, and errors. Alerts on queue age, error rate, and the daily cost cap.
- **Hard caps:** Per-run token cap and the $20/day org cap (ASSUMPTION, §1). The cap is enforced in the model-access seam, which cuts off runs.
- **Who can reach it:** Only the allow-listed pilot repo, with maintainer-authored issues, behind the flag. Nothing is written back and no code is executed. Repo content leaves the org only after V1.

**Exit check (V0):** A real issue yields one trace across every tier. A deploy and a rollback succeed through the pipeline. An injected failure (model API down, or the cap breached) fires an alert. Baseline floor values are recorded for latency, cost per issue, and queue delay.

## 5. Phases

- **Phase 1: Guardrails before capability**
  - Unlocks: Any write to GitHub, any code execution, and non-maintainer input.
  - Depends on: Phase 0 and V1.
  - Tasks, widest blast radius first:
    1. Tool executor with a tool allow-list and argument validation.
    2. Approval binding: a write runs only with an approval bound to that exact action. The executor enforces it, not the model, and logs it.
    3. Author trust tiers (maintainer, member, external), with untrusted content fenced as data.
    4. No outbound URLs, images, or other egress from model output.
    5. Sandbox runner (V3).
    6. Injection suite in CI (V2).
    7. Per-run iteration limits and a per-repo kill switch.
  - Rollback: Flip the flag to dry run. The executor denies all writes by default.
  - Exit check: V2 and V3 pass.

- **Phase 2: Triage (retrieval, model access, run state)**
  - Unlocks: Live labels and comments on the pilot repo, then external-author issues.
  - Depends on: Phase 1, and the triage eval set from maintainers.
  - Tasks:
    1. Finalize the run-state schema and audit log (widest rework).
    2. Retrieval: issue-history duplicate search and code search. Pin the embedding model in the index version. Retrieval honors repo visibility.
    3. Harden model access: a provider abstraction, a tested fallback model, and schema-validated output.
    4. Shadow mode: proposals go to the internal channel only.
    5. Per-item maintainer approval to post labels and comments.
    6. After V4, auto-apply labels only. Duplicate closes and comments stay approved.
  - Rollback: Return to shadow mode or dry run by flag. Remove agent labels by a script keyed on the audit log.
  - Exit check: V4 passes.

- **Phase 3: Resolution as draft PRs**
  - Unlocks: Maintainer-opted-in fixes on the pilot repo.
  - Depends on: Phase 2, V2, V3, and the resolution benchmark.
  - Tasks:
    1. Orchestration: the simplest workable shape is a single agent loop of plan, edit, run tests in the sandbox, and iterate under iteration, time, and cost caps. Each step is traced and failures surface.
    2. Per-run scratch memory only (no long-term memory).
    3. PR opening restricted to `agent/*` branches, with a path deny-list and a diff-size limit.
    4. The PR body links the trace and the issue. A human reviews and merges.
    5. Benchmark on closed issues first, then live on `agent-ok` issues.
  - Rollback: Disable the flag and delete the `agent/*` branches. Nothing merges without a human.
  - Exit check: V5 passes for the pilot.

- **Phase 4: Widen and improve**
  - Unlocks: More repos and cheaper routing.
  - Depends on: Phase 3 and V5.
  - Tasks:
    1. Onboard repos one at a time, each with its own shadow period and canary metrics.
    2. Routing is built only if V5 shows cost is over target. Use a cheaper model for triage and the strong model for resolution, and verify the quality margin on the eval sets.
    3. Feedback: maintainer accept and reject signals enter the eval sets through review, not directly into prompts.
  - Rollback: Per-repo uninstall or flag.
  - Exit check: Each new repo meets the V4 and V5 thresholds on its own canary. Any regression on earlier repos is zero or explained.

## 10. Deliberately deferred
- **Auto-merge of agent PRs:** pulled forward only after a sustained V5 history, an explicit risk acceptance by the repo owner, and a fresh V2/V3 run.
- **Auto-closing duplicates or stale issues:** pulled forward when duplicate precision has held above the V4 bar on live data and closing can be undone.
- **Security-vulnerability reports and private advisories:** excluded from scope. Pulled forward only with a separate privacy and risk review.
- **Triggering resolution from external authors:** pulled forward if maintainers reject the opt-in label as too slow, after a re-run of V2.
- **Long-term memory across issues:** pulled forward if V5 failures trace to re-learning the same repo conventions.
- **Fine-tuning or self-hosted models:** pulled forward if V1 fails, or if V4 fails after retrieval tuning, with a privacy review (training on repo data is R3).
- **Multi-agent orchestration:** pulled forward if single-loop completion stalls below the V5 bar for identifiable step types.
- **Cross-repo or multi-org deployment:** pulled forward after Phase 4 canaries pass.
