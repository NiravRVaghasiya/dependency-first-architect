# BUILD PLAN: Real-time collaborative document editor

## 1. Classification and constraints
- **What:** A multi-tenant web editor where several people edit one rich-text document at once. Edits show up live for everyone, with presence, sharing, and persistence.
- **Type:** Software. Greenfield. Not small: it will have outside users, user content that may include personal data, and a consistency model that is hard to reverse.
- **Dominant constraint:** Correctness, meaning convergence and no lost edits. Latency is second.
- **Worst failure:** Silent loss or corruption of a user's document after the UI showed "Saved". Unauthorized read or write of another tenant's document is a close second. Neither can be undone after the fact.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency | Local echo p95 < 50 ms. Remote apply p95 < 200 ms and p99 < 500 ms, same region | ASSUMPTION: common "feels live" thresholds; product owner to confirm | V0 records the floor; V2 at load |
| Throughput / scale | 10,000 concurrent editors, at most 50 per document, about 5 ops/s per active typist | ASSUMPTION: typical team-document tool at launch; product owner to confirm | V2 at 2× |
| Availability / SLO | No number | UNKNOWN: product owner must supply the commitment before Phase 5 | SLIs and burn-rate alerts from Phase 3 |
| RPO / RTO | RPO: 0 acknowledged ops lost. RTO: no number | RPO is an ASSUMPTION, because "Saved" is shown only after a durable append. RTO is UNKNOWN: product owner, before Phase 5 | V4 (restore time is recorded now and compared to RTO once supplied) |
| Storage | Compacted encoded document ≤ 5× its plain-text size | ASSUMPTION: typical for CRDT documents after garbage collection | V1 |
| Cost | Infrastructure cost per monthly active editor: no number | UNKNOWN: price per seat and target margin from product/finance, before Phase 6 | V5 |
| Operational complexity | One app service, managed Postgres, object storage. No self-run cluster and no Redis until V2 demands it | ASSUMPTION: team of 5–8 engineers | Phase 3 exit check |

**Missing inputs** (none changes the phase order, but each changes a threshold or blocks a phase):
- Availability and RTO commitments (product owner, before Phase 5).
- Price per seat (finance, before Phase 6).
- Whether any launch customer requires data residency or dedicated isolation (product/sales, before Phase 1 freezes the data contract). I assume not and use a single region. If this is false, tenancy becomes cell-based, which is the flip in the data-model row of §3.
- A named security reviewer, a named deletion approver, and signed customer terms and DPA (organizational, see §2).
- Whether offline editing beyond short disconnects is required. I assume not (§10).

## 4. Walking skeleton (Phase 0)
- **Request:** An allow-listed internal user signs in through OIDC and opens a document in the browser. They type one character. A second browser session sees it. After a reload, the character is still there.
- **Tiers:** Browser (ProseMirror + Yjs), then CDN/load balancer with TLS and WebSocket upgrade, then the app service (auth, room, append), then managed Postgres, then back out to the second browser. Each WebSocket message carries a trace ID, so one trace covers every tier.
- **Deploy:** Infrastructure as code and a container image, through the CI/CD pipeline to production. Expand/contract migrations only.
- **Log and monitor:** Structured logs and OpenTelemetry traces. Metrics for connections, ops/s, ack latency, remote-apply latency, and error rate. An alert on error rate and on gateway down. A background check replays the log and compares its hash to the live document, so divergence is visible from day zero.
- **Roll back:** Redeploy the previous image through the pipeline. Rollback is exercised once.
- **Who can reach it:** Allow-listed internal accounts in a synthetic test tenant, behind a feature flag and SSO/IP allow-list. There is no real customer data. Defaults are unvalidated and nothing is hardened.
- **Organizational items started here:** cloud account, OIDC tenant, domain, and naming the V3 security reviewer.

**Exit check (V0):** The real request succeeds with one trace across every tier. A deploy and a rollback succeed through the pipeline. An injected failure (killing the gateway) fires an alert. Baselines are recorded as floors at near-zero load: local echo, remote apply, and append latency. A canary string typed into the document is absent from all logs, traces, and metrics.

## 5. Phases

- **Phase 1: Convergence core and data contract** (widest rework first)
  - Unlocks: a frozen persisted format and protocol.
  - Depends on: Phase 0.
  - Tasks:
    1. Build the V1 harness: randomized multi-client fuzz with partitions, reordering, and duplicates, plus recorded human editing traces.
    2. Run V1.
    3. Freeze the schema v1, the message envelope, and the log/snapshot layout.
    4. Add tenant ID and row-level security to the schema, with expand/contract migrations.
    5. Add compaction and garbage collection.
    6. Add an open-format export (HTML/Markdown/JSON) with a tested round-trip, as the seam against lock-in.
  - Rollback: internal-only and behind the flag. Migrations are expand/contract. The old image is redeployed.
  - Exit check: V1 passes. The export round-trips the fuzz corpus. If V1 fails, re-plan per §3 row 1.

- **Phase 2: Authorization and tenant isolation**
  - Unlocks: anything that might touch another tenant's data.
  - Depends on: Phase 1 and V1 (the ACL rides on the frozen contract).
  - Tasks:
    1. Implement roles and ACL.
    2. Check authorization at connect and on every message, so viewers' updates are rejected.
    3. Implement revocation that closes live sockets.
    4. Add a per-request tenant context, and make unscoped queries fail.
    5. Add an audit log of ACL changes, with no document text.
    6. Add an authz matrix test in CI.
    7. Hand V3 to the security reviewer.
  - Rollback: the flag stays off. Deny-by-default means a bad release fails closed.
  - Exit check: the V3 CI matrix is green. The reviewer's sign-off (the rest of V3) is pending.

- **Phase 3: Durability, scale, and resilience**
  - Unlocks: a capacity and recovery design that is safe to harden.
  - Depends on: Phase 1, Phase 2, V1.
  - Tasks:
    1. Build room ownership: a document routes to one owner node by hash, with a Postgres lease.
    2. Add failover with client resync from state vectors.
    3. Add reconnect with a buffered local queue.
    4. Add backpressure and per-connection and per-tenant rate limits.
    5. Add the client ack ledger used by V4.
    6. Set up backups and PITR.
    7. Run V2 and V4.
    8. Define SLIs and burn-rate alerts.
  - Rollback: single-owner mode is retained behind a flag. Routing changes are redeployable.
  - Exit check: V2 and V4 pass. The operational-complexity budget holds (no new self-run systems). If V2 fails, apply the monolith and sync/async flips.

- **Phase 4: Editing features on the validated core**
  - Unlocks: a product that is worth a design partner's time.
  - Depends on: Phase 3, V2, V4.
  - Tasks:
    1. Add rich-text formatting within schema v1.
    2. Add presence and remote cursors (ephemeral, never persisted).
    3. Add per-user undo/redo.
    4. Add named version history on snapshots.
    5. Add soft delete with a 30-day restore window (ASSUMPTION: typical recovery window; confirm with the product owner).
    6. Prepare the V6 purge rehearsal.
  - Rollback: features are flag-gated per feature. Schema changes are additive only.
  - Exit check: V1's cross-version test passes again with the new features. The V2 latency SLIs hold with presence on.

- **Phase 5: Staged exposure**
  - Unlocks: real users.
  - Depends on: V3, V4, V2; signed terms and DPA; a named on-call rota; availability and RTO supplied (§1); the restore drill (V4) compared to RTO.
  - Tasks, widening only after each check passes:
    1. Start with one design-partner tenant.
    2. Widen to about 5 tenants.
    3. Widen to a waitlist cohort.
    4. Enable hard-delete and retention purge only after V6.
    5. Start V5 metering from the first cohort.
  - Rollback: the per-tenant flag can disable collaboration and fall back to read-only. Documents are exportable (Phase 1 seam). The purge is a point of no return, guarded by V6.
  - Exit check: at each widening step, no lost-op reconciliation mismatches, the SLO burn rate is within budget, and there are no open high-severity security findings.

- **Phase 6: Open availability and scale commitments**
  - Unlocks: self-serve signup and capacity commitments.
  - Depends on: Phase 5 and V5.
  - Tasks:
    1. Open self-serve signup in steps.
    2. Tune autoscaling against the V2 profile.
    3. Add cost dashboards and per-tenant limits.
  - Rollback: signup is gated by a flag and can be closed. Capacity commitments are not made until V5 passes.
  - Exit check: V5 passes. Thirty days of SLO attainment are recorded.

## 10. Deliberately deferred
- **Long-lived offline editing.** Pull it forward when a customer needs edits across days of disconnection. The CRDT choice already allows it, but testing and UX are not built.
- **Comments and suggestion mode.** Pull them forward when the design partner requires them. Suggestion mode that needs server-enforced rules triggers the §3 row 1 flip.
- **Share-by-link and public documents.** Pull forward after V3, and only when a customer asks.
- **Multi-region active-active and regional cells.** Pull forward on a residency requirement or when V2 shows cross-region latency is a problem.
- **Dedicated tenant isolation or customer-managed keys.** Pull forward on an enterprise contract that requires it.
- **Full-text search, DOCX import/export, native mobile apps, and enterprise SSO/SCIM.** Pull each forward on a signed customer need.
- **Redis or a dedicated log store.** Pull forward only if V2 fails on the Postgres lease or append path.
