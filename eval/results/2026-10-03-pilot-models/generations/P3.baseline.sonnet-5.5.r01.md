# Sequencing a CI/CD platform for 50 microservices

The main principle is to build a thin end-to-end path first, prove it on a few services, then widen it. Don't build each stage for all 50 services before moving on.

## Phase 0: Discovery and decisions (weeks 1–2)
1. **Inventory the 50 services.** Record language, build tool, runtime, data stores, deploy target, owner, and criticality.
2. **Group them into archetypes.** Most services usually fall into 3–5 (for example Java/Gradle API, Node service, Python worker, or frontend). You'll build templates per archetype, not per service.
3. **Make the core decisions.**
   - Source control and branching model (trunk-based is preferred).
   - CI engine, such as GitHub Actions, GitLab CI, or Jenkins.
   - CD model: GitOps (Argo CD or Flux) or push-based.
   - Artifact registry, secrets manager, and target platform (Kubernetes or other).
4. **Define success metrics.** Use the DORA metrics (lead time, deploy frequency, change failure rate, MTTR) and record baselines.

## Phase 1: Foundations (weeks 2–5)
These are prerequisites for everything after them.
1. **Infrastructure as code** for the platform itself: clusters, networking, and IAM.
2. **Environments:** dev, staging, prod, with a promotion model.
3. **Artifact and container registry** with retention policies.
4. **Secrets management** and workload identity. Use short-lived credentials, not static keys.
5. **Runner/agent infrastructure** that is autoscaled and has cache support.

## Phase 2: Walking skeleton on 2–3 pilot services (weeks 4–8)
Choose one simple service, one typical service, and one awkward one. Build the whole path thinly:
1. **CI:** build, unit test, lint, and container image build.
2. **Versioning and tagging:** immutable images tagged by commit SHA, with SBOM generation.
3. **Deploy to dev** automatically on merge.
4. **Promote to staging, then prod,** with an approval gate for prod only.
5. **Rollback** that is proven to work.
6. **Basic observability:** pipeline metrics, deploy markers on dashboards.

The exit criterion is that a merge reaches production with no manual steps apart from the approval.

## Phase 3: Reusable templates (weeks 7–10)
1. **Extract shared pipeline templates** (reusable workflows or shared libraries) per archetype. Services should consume them with about 10 lines of config.
2. **Standardize deployment manifests** with a Helm chart or Kustomize base.
3. **Set up a service scaffold/catalog** (such as Backstage or a cookiecutter template) so new services start with the pipeline already in place.
4. **Version the templates,** so you can roll out changes to them safely.

## Phase 4: Quality and security gates (weeks 9–13)
Add these after the pipeline is stable. Start in **report-only mode,** then move to enforcing.
1. SAST, dependency scanning, secret scanning, and container image scanning.
2. Image signing and admission policy (Cosign and Kyverno/OPA).
3. Integration and contract tests (Pact or similar), which matter a lot with 50 services.
4. Smoke tests after deploy, and automated rollback on failed health checks.
5. Build only what changed in monorepos (path filters or affected-graph builds).

## Phase 5: Progressive delivery and observability (weeks 12–16)
1. Canary or blue-green deployments (Argo Rollouts or Flagger) with metric-based analysis.
2. Feature flags to separate deploy from release.
3. DORA dashboards and pipeline health (flakiness, duration, queue time).
4. Alerting tied to deployments.

## Phase 6: Migration waves (weeks 8–24, overlapping with phases 3–5)
Migrate in waves. Each wave has a go/no-go check and gives feedback for the templates.
| Wave | Services | Purpose |
|---|---|---|
| 0 | 2–3 pilots | Validate the design |
| 1 | ~7 low-risk services | Shake out templates |
| 2 | ~15 services | Main archetypes at scale |
| 3 | ~15 services | Includes stateful or complex ones |
| 4 | Remaining, and the most critical | Highest-risk services go last, with the mature platform |

Run the old and new pipelines in parallel for each service until it has had several successful production deploys. Then decommission the old one.

## Phase 7: Operate and improve (ongoing)
- Set platform SLOs and an on-call rotation.
- Add cost controls and FinOps for runners and registries.
- Write documentation and golden-path guides, and run a feedback channel.
- Run regular template upgrade campaigns.
- Add drift detection and compliance audit reports.

## Dependency summary
```
Decisions → IaC/registry/secrets/runners → Pilot skeleton → Templates
   → Security/quality gates → Progressive delivery
                 ↘ Migration waves (start once templates are usable)
```

## Common sequencing mistakes
- **Building gates before the basic path works.** Developers then route around the platform.
- **Enforcing security gates on day one.** Start with reporting, or you'll block all 50 teams at once.
- **Migrating the most critical services first,** or all services at once.
- **Skipping rollback and observability** until later.
- **Treating the platform as a project** instead of a product with users, support, and a roadmap.

## Team
A typical setup is 3–5 platform engineers, plus a representative from each pilot service team. The platform team should treat service teams as customers.
