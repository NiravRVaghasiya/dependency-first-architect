## Build order

**Phase 0: Decisions that shape everything (days)**
1. **Pick the concurrency model.** The choice is CRDT (Yjs or Automerge) or OT (ShareDB, or a custom server).
   - Default to **Yjs**. It has offline support, mature editor bindings, and no central transform server.
   - Choose OT only if you need strict server-authoritative ordering.
2. **Pick the editor framework.** Choose ProseMirror/Tiptap, Lexical, or Slate. Tiptap plus Yjs is the fastest route for rich text.
3. **Set the scope.** Decide what v1 includes: rich text, cursors/presence, comments, version history, permissions.

**Phase 1: Single-user editor (week 1–2)**
4. Document schema (paragraphs, headings, lists, marks).
5. Basic editor UI and toolbar.
6. Local persistence (IndexedDB) and a document CRUD API.

Build this first so you can tell editor bugs from sync bugs later.

**Phase 2: Core collaboration (week 2–4)**
7. WebSocket server (for example Hocuspocus or y-websocket) with a room per document.
8. Bind the editor to the shared document type.
9. Server-side persistence of document state (snapshots plus incremental updates in Postgres or S3).
10. Reconnect and offline handling, with resync on reconnect.
11. **Two-client convergence tests.** Add randomized and fuzz tests here, before anything else is built on top.

**Phase 3: Identity and access (week 3–5)**
12. Authentication.
13. Per-document permissions (owner, editor, commenter, viewer), enforced in the WebSocket handshake.
14. Share links and invitations.

**Phase 4: Presence and UX (week 4–6)**
15. Awareness: live cursors, selections, and user colors.
16. Connection-status indicator and a "saving/synced" state.

**Phase 5: Collaboration features (week 6–9)**
17. Comments and suggestions, anchored to relative positions so they survive edits.
18. Version history (snapshots, diff, restore).
19. Undo/redo scoped per user. Use the CRDT's undo manager, not the browser's.

**Phase 6: Scale and hardening (week 8–11)**
20. Horizontal scaling. Use sticky routing by document ID, or a Redis pub/sub between server nodes.
21. Compaction and garbage collection of update history.
22. Rate limiting, payload limits, and audit logging.
23. Load tests, for example 50+ editors in one document and thousands of concurrent documents.
24. Observability: sync latency, connection drops, and error tracking.

**Phase 7: Polish (ongoing)**
25. Import/export (Markdown, DOCX, PDF).
26. Images and embeds.
27. Mobile and accessibility.

## Why this order
- Phases 1 and 2 are sequenced to reduce risk early. Convergence correctness is the hardest part, so test it before adding features.
- Permissions come before presence and comments because retrofitting access control into a running sync layer is painful.
- Scaling comes late, but keep the server stateless-ish from the start so it stays possible.
