# Plan: Autonomous GitHub Issue Triager and Resolver

## 1. Classification and Constraints

**What:** An autonomous agent that ingests GitHub issues, triages them (classifies, prioritizes, tags, assigns), and resolves them (generates responses, suggests or applies fixes, closes issues).

**Type:** AI-agentic system (greenfield).

**Scale assumption:** Small: single team, pilot phase, internal use on a curated set of public/internal repos; <100 issues/day initially. (Changes if: production serving multiple orgs, >1k issues/day, SLA-bound.)

**Dominant constraints (in order):**
1. **Safety & correctness:** AI hallucination or injection leading to wrong labels, misclassified severity, or harmful auto-responses.
2. **Cost:** LLM inference per issue, especially if retrieval+classification+generation triple-calls the model.
3. **Auditability:** Every decision must be traceable (which facts led to which triage? who approved a close?).

**One failure that would hurt most:** Agent closes valid bug reports as duplicates or wontfix, or applies AI-generated patches that break user code.

**Budgets that matter:**
- **Cost per issue:** ASSUMPTION — ~$0.01–$0.05 (gpt-4-turbo or equivalent), confirmed by first 100 live runs.
- **Latency:** ASSUMPTION — triage <30s per issue (acceptable for async batch); resolve suggestions <10s (must not block PR feedback).
- **Accuracy:** REQUIREMENT (inferred) — human review rate <20% on triage, <100% on closes (never auto-close without human gate for first 1k issues).
- **Availability:** ASSUMPTION — 99% (runs on-demand, no hard SLA until production scale).

**Missing inputs that would change the plan:**
- Which GitHub orgs and repos? (scope determines API quotas, data access, compliance.)
- Types of issues to handle? (bugs, features, docs, questions; changes ML model and guardrails.)
- Approval workflow? (triage-only vs auto-resolve?; changes gate design.)
- Privacy: does agent see user names, commit history? (affects data handling, prompt injection risk.)

**Assumption for this plan:** Pilot on internal/trusted repos, triage-only with human review required for closes; all issues use public GitHub API; no PII extraction. Resolves to full auto-resolution after V1 gate passes.

**Declared exception:** None yet. Skeleton replaces the typical spike-first for AI systems because the cost is low and guardrails (injection defense, budget cap) are enforced from day one.

## 4. First end-to-end slice (Phase 0)

**Skeleton:** Fetch one real open GitHub issue (from internal test repo), ingest its title + first 100 words of body, call LLM (gpt-4-turbo via API) with a prompt to classify severity (P0–P4) and category (bug/feature/doc), log the call and response, store result in a local trace file, and roll back (delete trace) without modifying the issue.

**Request path:**
1. GitHub API client: read issue via REST API (requires OAuth token, read-only scope).
2. Input sanitizer: truncate title, bound body to 1024 chars.
3. Prompt template: inject issue into predefined triage prompt (with injection defense: no user code exec, no secrets leakage).
4. LLM API call: send prompt to OpenAI (or Anthropic), record token usage and cost.
5. Response parser: extract classification from JSON (structured output).
6. Logger: write (issue_id, classification, model_version, cost, latency, timestamp) to local file + observability system.
7. Rollback: no-op (read-only on GitHub; local trace is disposable).

**Who can reach it:** Internal use only; agent runs in CI/CD environment or laptop for developer testing; no production GitHub account access until Phase 1.

**Hardening:** None in Phase 0; runs on defaults (no retry, no budget ceiling, no injection test).

**Exit check V0:** 
- Issue fetched from GitHub API without error.
- Classification generated by model (latency recorded).
- Trace logged with issue_id, predicted_severity, predicted_category, model_used, cost_$, latency_ms, timestamp.
- Rollback succeeds (trace deleted, no side effects on GitHub).
- No alerts fired (baseline: zero failures on a single issue).

**Budgets recorded as baselines:**
- Latency: <10s for full round-trip (read + call + parse).
- Cost: ~$0.003–$0.01 per call (gpt-4-turbo typical: 4k + 500 output tokens ~= $0.02).
- Model output: structured JSON with fields `{"severity": "P1", "category": "bug", "confidence": 0.92}`.

**Tasks:**

- Unlocks: Phase 3 (auto-close).

**Rollback:** If V2 fails, revert write permissions, stop posting; retune prompt or expand train set; re-run Phase 2.

### **Phase 3: Auto-Close Pilot (V3 gate)**
**Unlocks:** Phase 4 (scaling & hardening).

**Depends on:** Phase 2 (V2 passes).

**Tasks:**
1. Extend GitHub API: add `issues:write` to allow closes (not deletes).
2. Define close rules: agent may auto-close only if:
   - Category = "duplicate" AND confidence > 95% (reference issue linked in comment).
   - Category = "wontfix" AND severity = P4 AND P0–P2 bugs exist in backlog (prevents closure of critical items).
   - Category = "question" AND already answered in response comment (wait 24h for user input).
3. Implement close workflow: candidate issues placed in queue; human approver (repo maintainer) has 6h to review; auto-close if approved, else skip.
4. Dry-run on past 500 closed issues: simulate which would have been auto-closed; count "correct" closes (matches actual closure reason). Report accuracy.
5. Pilot: enable auto-close on new issues in ONE internal repo for 2 weeks; monitor reopens (rate <5%) and user complaints (none).
6. Gate V3: (close accuracy) accuracy from dry-run + pilot reopens ≤ 5% + zero escalations to support.

**Exit check V3:**
- Hypothesis: auto-close decisions are correct 95%+ of the time; users do not reopen or complain.
- Method: dry-run accuracy on past data + 2-week live pilot.
- Acceptance: dry-run accuracy >95%; pilot reopen rate <5%; zero complaints.
- Evidence: dry-run report (correct/total), pilot metrics (closes, reopens, feedback), exported weekly.
- Unlocks: Phase 4 (scale to multi-repo, monitor production).

**Rollback:** If V3 fails (>5% reopen rate or complaints), disable auto-close, revert to Phase 2 (responses only). Keep trace logs for analysis.
