# BUILD PLAN: CI/CD platform for 50 microservices

## 1. Classification and constraints
- **What:** A shared build, test, sign, deploy and rollback platform that replaces per-service pipelines for 50 microservices.
- **Type:** Infra plus software (pipeline templates and policy). It is brownfield, because the 50 services already ship through existing pipelines. It is not a small build: 50 teams depend on it, and it holds production credentials.
- **Dominant constraint:** Security of the delivery path (correctness of what reaches production), then availability of the ability to deploy.
- **Worst failure:** An unauthorized or tampered artifact reaches production across many services. A close second is the platform being down during an incident, so no one can ship a hotfix. Gate V1 guards the first failure. The break-glass path in Phase 3 covers the second.

**Budgets**

|---|---|---|---|

| Operational complexity | Managed or OSS components only, with no custom orchestrator | ASSUMPTION: the platform team is small | Phase 3 exit |

**Missing inputs** (the phase order rests on the assumptions marked here):
- ASSUMED: the SCM is GitHub, workloads run on Kubernetes, and the old pipelines are Jenkins or scripted `helm`/`kubectl`. If services are not containerized or Kubernetes-based, the Phase 0 and Phase 3 tool choices change, but the order does not.
- ASSUMED: each service has a criticality tier (customer-facing or payment-critical versus internal). Phase 0 confirms this. The wave order depends on it.
- Organizational: a named platform owner; a named security reviewer for V1; a change-board slot for production access; a service owner for each of the 50 services; the runner budget.

**R1 defaults:**
- Sync vs async: builds queue asynchronously, and deploys gate synchronously on health checks.
- Monolith vs services: the platform is composed of off-the-shelf components, and no custom service is built.
- Telemetry stack: OpenTelemetry to the existing observability backend.
- Secrets: Vault or the cloud secret manager, with masking in logs.
- IaC: Terraform.

**N/A:** Data-privacy boundary — no personal data is processed by the platform. Build logs and telemetry are treated as potentially secret-bearing and are masked (see §7). Inherited constraints: the existing repo layout, language stacks, SCM, and cluster topology are not changed.

## 4. Walking skeleton (Phase 0)
- **Request:** One real change to one low-tier internal service (not customer-facing, ideally with a staging twin) moves commit → build → test → image → push → deploy to production → health check → a deliberate rollback.
- **Tiers crossed:** SCM, ephemeral runner, registry, Git desired-state repo, Argo CD, production cluster, service, observability backend.
- **Deployed:** By the new pipeline, using the minimum identity model: OIDC short-lived credentials, with no long-lived keys in CI. Platform infrastructure is in Terraform from the first commit.
- **Logged and monitored:** The trace and build ID link commit → image digest → rollout. Dashboards show pipeline duration, queue time, and deploy success. An alert fires on a failed rollout.
- **Rolled back:** By a Git revert (Argo CD sync to the previous digest), and separately by re-enabling the old pipeline through the ownership flag.
- **Who can reach it:** Only the platform team and the internal service's allow-listed consumers. Nothing customer-facing is touched.
- **Baseline work in Phase 0:** Through the existing change process, inventory what depends on the old pipelines (CONFIRMED or ASSUMED). Measure the old pipelines' lead time, failure rate, queue time, and peak-hour concurrency. Classify all 50 services by tier and stack. Start the organizational items (production access, security reviewer, runner budget).

**Exit check (V0):** A real request succeeds with one trace across every tier. A deploy and a rollback both succeed through the pipeline. An injected failure (a broken image or failing health check) fires an alert. The first budget values are recorded as baselines, not capacity.

## 5. Phases

- **Phase 1 — Trust substrate**
  - Unlocks: Safe exposure of anything beyond the skeleton.
  - Depends on: V0, the security reviewer, and change-board approval.
  - Tasks:
    1. OIDC workload identity per environment, with the PR/protected-branch split.
    2. Secrets management and log masking.
    3. Registry with immutable digests.
    4. Signing (cosign) and SLSA provenance in the pipeline.
    5. Kyverno admission in audit mode, then enforce on the pilot namespaces.
  - Rollback: Set admission back to audit mode. Credential changes revert through Terraform.
  - Exit check: V1 passes.

- **Phase 2 — Paved-road CI contract and runner capacity**
  - Unlocks: Specifying the migration waves.
  - Depends on: V1, the runner budget, and the Phase 0 baseline.
  - Tasks:
    1. Define the versioned template interface (build, test, scan, publish) and the service config schema.
    2. Onboard 3 pilot services with different stacks. The Phase 0 service counts as one.
    3. Size and autoscale the ephemeral runners from baseline concurrency.
    4. Add dependency and vulnerability scanning in report-only mode.
  - Rollback: Pilot services return to their old pipelines through the ownership flag.
  - Exit check: V2 and V3 pass.

- **Phase 3 — Progressive delivery and platform resilience**
  - Unlocks: Migrating customer-facing services.
  - Depends on: V1, V2.
  - Tasks:
    1. Argo Rollouts canary with metric analysis.
    2. Automated rollback.
    3. Environment promotion through Git.
    4. The Argo CD scale check (see §3).
    5. HA and backup of platform state, with restore tested.
    6. Break-glass path and drill.
    7. SLIs and burn-rate alerts on the deploy path.
  - Rollback: Disable canary analysis and fall back to the rolling update. Break-glass remains available.
  - Exit check: V4 passes, the break-glass drill passes, and restore of platform state is tested against the availability commitment (once supplied).

- **Phase 4 — Migration waves (exposure smallest first)**
  - Unlocks: Full fleet on the platform.
  - Depends on: V2, V3, V4, and the confirmed dependency inventory.
  - Tasks, in order:
    1. Wave A: about 5 low-tier internal services.
    2. Wave B: about 15 mid-tier services. Scanner findings move from report-only to blocking for criticals.
    3. Wave C: about 20 remaining services.
    4. Wave D: the tier-1, customer-facing, and payment-critical services, last, each with its owner present.
    - Each service goes through the ownership flag, so exactly one deployer owns it.
  - Rollback: Per service, re-enable the old pipeline and disable the Argo sync. Per wave, pause onboarding.
  - Exit check: Each wave shows no incident attributable to the migration, and change-failure rate and lead time are no worse than the Phase 0 baseline. Targets are set by engineering leadership (UNKNOWN until then).

- **Phase 5 — Decommission the old pipelines (point of no return)**
  - Unlocks: Removing the old credentials and the dual-run cost.
  - Depends on: Phase 4 complete and V5.
  - Tasks:
    1. Freeze old pipelines (read-only).
    2. Archive configs.
    3. Revoke the old credentials.
    4. After the 90-day window, delete the old CI server. That deletion is the point of no return.
  - Rollback: Until the deletion, re-enable the archived configs. After it, only the new platform's break-glass path remains.
  - Exit check: V5 passes.

## 10. Deliberately deferred
- Developer portal and service catalog: pulled forward when teams report that discovering templates or status is a bottleneck after Wave B.
- Per-PR preview environments: pulled forward when V3 passes with headroom and teams ask for them.
- Multi-region or multi-cluster platform: pulled forward when the availability commitment (UNKNOWN) requires it or the Argo CD scale check fails.
- Cost chargeback per team: pulled forward when the runner budget is exceeded or finance requires it.
- Blocking on all scanner severities (not just criticals): pulled forward when false-positive rates from Waves A and B are known and acceptable.
- Self-service infrastructure provisioning: pulled forward after Phase 5, if service teams are still waiting on infra tickets.
