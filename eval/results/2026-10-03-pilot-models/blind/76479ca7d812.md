# BUILD PLAN: Customer-support RAG chatbot over the help-center docs

## 1. Classification and constraints
- **What:** A chat widget on the help center that answers customer questions from the help-center articles. It cites its sources and hands off to a human when it can't answer.
- **Type:** AI-agentic (RAG, single model call, no autonomous actions). Brownfield: the help center and the existing contact or ticket path stay in place. Not small: outside users, personal data typed into chat, and a paid model API.
- **Dominant constraint:** correctness (grounded answers), with cost per resolved conversation second.
- **Worst failure:** a customer acts on a confident wrong answer, such as a wrong refund, security, or billing instruction, or the bot invents a policy commitment. V3 guards this, with V1 and V4 covering injection and personal-data exposure.

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency | p95 time-to-first-token ≤ 2.5 s; full answer ≤ 10 s | ASSUMPTION (typical chat UX; confirm with product owner) | V0 baseline, Phase 3 load test |
| Throughput | UNKNOWN: peak concurrent chats. Support/analytics lead supplies help-center peak traffic, needed before Phase 3 load test | UNKNOWN | Phase 3 |

| Operational complexity | ≤ 2 deployables (API, ingestion job) + 1 managed Postgres | ASSUMPTION | Phase 2 |

**Missing inputs** (the first two could change the phase order):
1. **Are all help-center articles public?** I assume yes. If any are gated or per-customer, retrieval needs per-caller access control, which is R3, and it moves ahead of Phase 2.
2. **Does the help-center vendor already offer a native AI agent?** The build-vs-buy check in Phase 0 settles this.
3. Help-center platform and export API or webhook.
4. Language scope (assumed English only).
5. Ticketing or handoff system.
6. Privacy and legal reviewer, and the model vendor's data terms.
7. Historical tickets for the eval set.

**R1 defaults:**
- Build vs buy → build thin on a hosted LLM. The one-day Phase 0 check of the help-center vendor's native AI agent is a kill-or-continue call. If it meets V3 at lower cost, buy it and this plan shrinks to evaluation and rollout.
- Monolith vs services → one API service + one ingestion job.
- Sync vs async → streamed (SSE) chat replies; async ingestion.
- Consistency vs availability → availability. The index may lag the docs by ≤ 24 h, and the sync propagates deletions.
- Widget framework → whatever the help-center theme supports.

**N/A:** tenancy and multi-region, since there is no customer-specific data and one region is enough. Migration strategy and cutover, since nothing is migrated. The help center stays the system of record for content, sync is one-way (docs → index), and the existing contact path is the fallback and the system of record for cases.

## 4. Walking skeleton (Phase 0)
- **Request:** a support staff member asks a real customer question in the widget, embedded on the live help center behind a feature flag. Only SSO or allow-listed staff can see it.
- **Tiers:** widget → API (auth check, flag, token cap) → retrieval over the full corpus with naive heading-based chunking in pgvector → hosted LLM → streamed answer with citation links → transcript and trace store.
- **Treating text as data:** retrieved and user text sit in delimited data blocks, separate from the system instruction. Per-request token cap, per-session cap, and a provider-side daily spend cap are set from day one.
- **Deploy and rollback:** CI/CD deploys the image. Rollback is the flag off plus redeploying the previous image, exercised once.
- **Logging and monitoring:** a trace ID runs from widget to model. Metrics cover latency, tokens and cost per turn, and error rate. An alert fires on error rate or spend. Transcripts are classed as potential personal data: restricted access, 30-day retention.
- **Failure behavior:** if the LLM fails, the widget shows the "contact support" fallback.
- **Parallel starts:** eval-set labeling, V4 paperwork, the docs-owner public-corpus confirmation, and the build-vs-buy check.

**Exit check (V0):**
- A real request succeeds with one trace across every tier.
- A deploy and a rollback succeed through the pipeline.
- An injected failure (revoking the LLM key) fires an alert and shows the fallback.
- Baselines are recorded for the latency floor and cost per turn.

## 5. Phases

- **Phase 1: Defenses and budgets**
  - Unlocks: safe internal testing with real queries.
  - Depends on: V0.
  - Tasks:
    1. Add the injection suite to CI. It plants injections in user input and in retrieved docs.
    2. Render only plain text and links to the help-center domain. No images or arbitrary URLs, which closes the exfiltration paths.
    3. Add PII redaction before the model call and before logs.
    4. Enforce single-call, no-loop, timeouts, and a degraded response.
    5. Build the handoff: the bot's only action is "create a ticket or hand off", and it needs an explicit user click, enforced in the API and not by the model.
    6. Refuse account actions.
  - Rollback: flag off.
  - Exit check: V1, and a forced runaway or oversized prompt is cut off at the cap with a metric emitted.

- **Phase 2: Retrieval**
  - Unlocks: a specifiable answer layer.
  - Depends on: Phase 1, and the labeled eval set.
  - Tasks:
    1. Do section-aware ingestion with URL, title, and updated-at metadata.
    2. Build hybrid search and version the index with the pinned embedding model.
    3. Sync via webhook or nightly, with deletions propagating.
    4. Build the eval harness and run V2.
    5. Run an index-rebuild drill.
  - Rollback: point to the previous index version.
  - Exit check: V2, a seeded draft or internal article is never retrieved, and the rebuild drill finishes in ≤ 4 h (ASSUMPTION).

- **Phase 3: Model access, answer behavior, session memory**
  - Unlocks: the canary.
  - Depends on: V2.
  - Tasks:
    1. Add the provider abstraction, fallback model, and structured output (answer, citations, abstain flag).
    2. Specify the prompt: ground in context, abstain, and never commit to refunds or policy outcomes.
    3. Keep in-session memory of the last N turns only.
    4. Run the throughput load test at 2× peak, once the peak is supplied.
  - Rollback: config switch to the previous prompt or model version.
  - Exit check: V3, switching to the fallback model is a config change that passes the eval at the V3 bar, and latency meets its budget under load.

- **Phase 4: Staged exposure**
  - Unlocks: production use.
  - Depends on: V1, V3, V4, Phase 1 handoff, and V5 to go past 25%.
  - Tasks, smallest exposure first:
    1. Shadow mode on live ticket questions from support staff only. Nothing is shown to customers, and this measures cost per turn.
    2. Customer canary at 5% of help-center traffic, with AI-disclosure text and a visible human-handoff option.
    3. Weekly human review of 100 sampled conversations.
    4. Widen to 25%, then 100%, only if the check passes. V5 must have passed before going beyond 25%.
  - Stop conditions, which turn the flag off: thumbs-down rate or escalation rate above its threshold (UNKNOWN, since there is no baseline yet, so set it from the shadow phase), or any sampled wrong confident answer on a safety or billing topic.
  - Rollback: flag off hides the widget, and the help center and contact path are unchanged.
  - Exit check: V5, and 7 days at each step with alerts quiet.

- **Phase 5: Feedback**
  - Unlocks: continuous improvement.
  - Depends on: Phase 4.
  - Tasks:
    1. Capture thumbs and free-text feedback, subject to the same PII redaction.
    2. Report content gaps to the docs team.
    3. Send reviewed failures into the eval set.
    4. Keep the loop manual. Nothing feeds training or prompts automatically.
  - Rollback: disable collection.
  - Exit check: a reviewed correction improves the target eval metric with no regression elsewhere.

## 10. Deliberately deferred
- **Account-aware actions** (order lookup, refunds, cancellations): pulled forward when V3 passes in production for a full quarter, there is a decided tool allow-list, and a human-approval design exists.
- **Multi-language support:** pulled forward when the support lead supplies the language share of volume, and a per-language eval set exists.
- **Long-term memory or personalization:** pulled forward when V4 covers persistent per-user data and a clear write policy exists.
- **Routing across models:** pulled forward when V5 fails on cost and an eval shows a cheaper model within the quality margin for an easy class of queries.
- **Fine-tuning:** pulled forward only if V3 fails for reasons that retrieval and prompt tuning can't fix.
- **Automated learning from feedback:** pulled forward when reviewed feedback volume makes manual review the bottleneck and a poisoning defense exists.
- **Other channels** (email, in-app, voice): pulled forward when the web canary meets V3 and V5 at 100%.
