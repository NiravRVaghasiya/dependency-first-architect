# Build order: real-time collaborative document editor

The order below puts the riskiest and most foundational decisions first. Each phase produces something you can test before the next one starts.

## Phase 0: Decisions that are expensive to reverse
1. **Scope the product.** Decide whether it is plain text, rich text, or structured blocks. Decide how many concurrent editors you expect, and whether you need offline support.
2. **Choose the conflict-resolution model.**
   - **CRDT** (Yjs, Automerge, Loro). It works offline and peer-to-peer and the server can be simple, but documents carry metadata overhead.
   - **OT** (ShareDB, ot.js). It is compact and proven, but it needs a central server and the transform logic is tricky.
   - For most new projects, use **Yjs** unless you have a specific reason not to.
3. **Choose the editor framework.** TipTap/ProseMirror, Lexical, Slate, or CodeMirror for code. Pick one with an existing binding for your CRDT or OT library.
4. **Pick the stack.** For example TypeScript, React, Node, WebSocket, Postgres, and Redis.

## Phase 1: Single-user editor (no networking)
5. Set up the editor with its schema: paragraphs, headings, lists, and marks.
6. Add the core toolbar and keyboard shortcuts.
7. Add undo/redo. You will redo this later to be per-user, so keep it isolated.

## Phase 2: Document model and persistence
8. Create the data model for documents, versions, and metadata.
9. Add save and load through a REST API.
10. Store the document as a binary CRDT state plus incremental updates, not as rendered HTML.

## Phase 3: Identity and access (minimum)
11. Add authentication.
12. Add per-document permissions (owner, editor, viewer). Build this before realtime so the sync layer can enforce it from the start.

## Phase 4: Real-time sync core
13. Build a WebSocket server with a room per document.
14. Connect the editor to the sync layer, with a two-client local test.
15. Implement the handshake: authenticate, then exchange state vectors and send the missing updates.
16. Handle reconnection with exponential backoff and resync.
17. Add server-side persistence: debounced snapshots plus an update log, with periodic compaction.

## Phase 5: Collaboration UX
18. **Awareness/presence:** who is online, plus live cursors and selections with names and colors.
19. Make undo/redo per-user, so you don't undo other people's edits.
20. Add connection status indicators and "saving/saved" states.

## Phase 6: Offline and resilience
21. Add local persistence in IndexedDB.
22. Queue edits while offline and merge them on reconnect.
23. Add tests for conflicts: concurrent edits, split-brain, and long offline sessions.

## Phase 7: Scale out
24. Add a pub/sub layer such as Redis so multiple server instances can share a document room.
25. Route clients for document affinity (sticky or consistent hashing).
26. Add rate limiting and update-size limits.
27. Load test with many clients on a single document and with many documents.

## Phase 8: Features on top
28. Comments and suggestions, anchored with relative positions so they survive edits.
29. Version history with named snapshots and restore.
30. Sharing links, import/export (Markdown, DOCX, PDF), and images/attachments.
31. Search.

## Phase 9: Hardening and launch
32. Add observability: metrics for sync latency, connection counts, and document size. Add error tracking too.
33. Do a security review: WebSocket auth, authorization on every update, XSS in content, and input validation.
34. Add backups and a restore drill.
35. Run fuzz and property-based tests for convergence. Run end-to-end tests with multiple browsers.
36. Roll out with feature flags and a beta group.

## Suggested milestones
| Milestone | Phases | Result |
|---|---|---|
| M1 | 0–2 | Solo editor that saves |
| M2 | 3–5 | Two or more users editing live with cursors |
| M3 | 6–7 | Works offline and scales horizontally |
| M4 | 8–9 | Feature-complete and production-ready |
