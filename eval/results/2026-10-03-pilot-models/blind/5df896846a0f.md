## 4. Walking Skeleton (Phase 0)

**Goal:** One real request from developer → commit → build → artifact store → canary deploy → live service → log entry in observability backend → rollback succeeds, all in one day on day zero.

**Request flow:**
1. Developer pushes commit to git repo (simulated with a test commit to a test service repo).
2. Webhook triggers Tekton pipeline.
3. Tekton clones repo, runs build (compile, test, lint).
4. Build succeeds; image pushed to Harbor with signed digest.
5. Image deploy to canary replica set (5% of traffic on one test service).
6. Canary health check passes (request succeeds, latency & error rate within threshold).
7. Canary promotes to full rollout (100% traffic).
8. Log entries appear in Loki/ELK (pipeline start, build time, deploy time, canary promotion).
9. Metrics (pipeline duration, deployment latency) recorded in Prometheus.
10. Operator rolls back the deploy via Git revert + re-apply (or via deployment rollback API).
11. Rollback verified: old version live, logs record rollback event, no orphaned resources.

**Who can reach it:** 
- Internal only: Tekton runs within the cluster; Harbor, observability, and Git are internal or VPN-only.
- Deployment target: one test service (not a real customer-facing microservice).
- No production secrets: test keys and images used; no customer data touched.

**Not yet hardened:** Registry auth uses dev credentials (to be hardened); secrets are read from a ConfigMap (not from KMS); canary thresholds are loose (e.g., 50% error rate tolerance; to be tightened); audit logging is basic (to be expanded in Phase 1); RBAC is permissive (to be restricted in Phase 1).

**Deployment & rollback through the pipeline:**
- Deploy: Git commit triggers Tekton, which applies Kube manifests (canary first, then full).
- Rollback: Git revert commit, re-push; Tekton re-runs, rolling back the deployment. Or: kubectl rollout undo.

**Exit check (V0):** 
- ✓ One commit → Tekton pipeline runs end-to-end (build, push, deploy).
- ✓ Artifact appears in Harbor with a reproducible image digest.
- ✓ Canary deploys to Kubernetes, health check passes.
- ✓ Full deploy follows canary promotion.
- ✓ Log entries from all tiers appear in observability backend with proper traces.
- ✓ Rollback succeeds; old version is live.
- ✓ Baseline metrics recorded: build time (target < 5 min), deploy time (target < 2 min), pipeline availability (should be ~100% on day 0).

**Blocker for Phase 1:** Passes V0 exit check; if any step fails, Phase 1 does not start until the skeleton runs end-to-end once.

## 9. Methodology Exceptions

**None.** The canonical order (Phase 0 skeleton → Phase 1 hardening → Phase 2 safety → Phase 3+ scale) follows principle 1 (build what blocks first) and principle 6 (walking skeleton first). No real users or regulated data touched until Phase 3; Phase 0 and Phase 1 are internal-only. No exception needed.

## 10. Deliberately Deferred

| Capability | Rationale | Pull-Forward Condition |
|---|---|---|
| **Multiregion deployment** | Single region (Phase 5) is sufficient for 50 services until demand grows (new services > 75) or business requires redundancy. | Q2 planning or explicit new requirement. |
| **AI-powered anomaly detection** | Manual observability and alerting (Phase 3+) covers current use cases. AI model would add latency, cost, and explainability burden. | After 6 months of production metrics; if manual tuning of alert thresholds becomes bottleneck. |
| **Federated identity (OAuth/OIDC)** | RBAC + MFA sufficient for internal platform (Phase 1). Federated identity needed only if external teams or CI/CD-as-a-service multi-tenant use case emerges. | When first external customer or SaaS model is planned. |
| **Advanced deployment strategies** (A/B testing, shadow traffic) | Canary (Phase 2) + blue-green (Phase 6, if needed) cover standard release strategies. A/B testing is application-level, not platform-level. | When feature-flagging or advanced traffic splitting is a business priority. |
| **Cost optimization (spot instances, reserved instances)** | Cost tracking (Phase 5) will surface optimization opportunities. Implement after data-driven analysis. | After Phase 5 observability shows cost drivers; e.g., spot instances reduce agent cost by 60%. |
| **Self-service secrets UI** | Teams manage secrets via API/CLI (Phase 1). Self-service UI is convenience, not critical path. | After 3+ months of API-based usage; if operator support load is high. |

## Self-Check

✓ **Phase 0 is a production walking skeleton:** One real commit through all tiers, deployed, logged, monitored, and rolled back on day zero. Internal-only (test service, no customer data). Unvalidated defaults accepted; hardening deferred to Phase 1.

✓ **Task order follows dependencies:** Phase 0 (skeleton) → Phase 1 (control plane & hardening) → Phase 2 (safety validation) → Phase 3 (production exposure) → Phase 4 (full rollout) → Phase 5 (optimization). Nothing reaches users, data, or money until Phase 3, and Phase 3 is gated by V7, V8, V11 (safety passed).

✓ **Tradeoff gates all have tiers and flip conditions:** Registry (R2, flip on cost or scaling failure). Orchestrator (R2, flip on UX or scaling failure). Deploy strategy (R3, flip on canary failure rate or stateful service needs). State consistency (R3, flip on drift detection failure). Multi-tenancy (R2, flip on RBAC bypass or scalability).

✓ **All gates have five fields and consumers:** V0–V15 each have hypothesis, method, threshold, evidence, and unlocks. Each gate cited in a phase; nothing gates nothing (no orphan gates).

✓ **Cross-cutting concerns in every phase:** Security hardens from dev credentials → Vault + audit logging → image signing enforcement. Observability starts day 0 (basic) → cardinality & schema (Phase 1) → SLI dashboards (Phase 3). Reproducibility: git-source, SBOM, artifacts signed. Resilience: single → HA → multiregion.

✓ **No AI component; no exceptions; nothing the request doesn't need.** Deferred items have pull-forward conditions.

✓ **No score, rubric, or compliance claim.** This is a build sequence, not a compliance matrix.

---

This plan prioritizes **what blocks what**, not what is flashiest. The skeleton runs first (Phase 0), control plane hardens next (Phase 1), safety is proven (Phase 2), then production exposure widens (Phase 3–4). Every validation gate blocks downstream work until it passes; every risk control guards before real users see it. Costs and latencies are labeled as REQUIREMENT, ASSUMPTION, or UNKNOWN—no silent guesses.
