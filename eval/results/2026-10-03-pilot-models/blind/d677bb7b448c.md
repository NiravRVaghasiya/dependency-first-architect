# BUILD PLAN: CI/CD platform for 50 microservices

## 1. Classification and constraints
- **What:** A shared CI/CD platform that builds, tests, signs, promotes, and deploys 50 microservices through one versioned pipeline contract.
- **Type:** Infra + software. **Brownfield (ASSUMED):** the 50 services already ship through existing per-team pipelines. It is **not a small build**: it is multi-team, it holds prod deploy credentials, and it carries R3 trust-boundary decisions. If this is actually greenfield, Phase 3 becomes onboarding and there is no decommission (V4 drops out). The phase order is otherwise unchanged, so I'm planning on the assumption.
- **Dominant constraint:** Correctness and security of the delivery path, with availability of hotfixes a close second.
- **Worst failure:** A compromised or misconfigured pipeline deploys an unverified artifact to prod across many services at once. The second worst is a platform outage that blocks an emergency hotfix. V3 guards the first and V4 guards the second.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Commit→artifact time, p50/p95 per service | ≤ the service's current pipeline | BASELINE (measured read-only from the old pipelines in Phase 0) | Phase 3 wave exit checks |
| Runner queue time p95 | ≤ baseline at 2× observed peak concurrent builds | BASELINE for queue time; ASSUMPTION for 2× (growth headroom) | V1 |
| Change failure rate and rollback rate | ≤ pre-migration rate per service | BASELINE (Phase 0) | Phase 3 wave exit checks |
| Platform availability SLO | — | UNKNOWN: needs the availability engineering leadership commits to, before Phase 3 | SLIs and burn-rate alerts (Phase 4) |
| Hotfix RTO with the platform down | — | UNKNOWN: same owner, before Phase 4 | V4 |
| Runner compute cost | — | UNKNOWN: needs the monthly budget from the platform owner or finance, before Phase 2 | V1 |
| Release-freeze windows | — | UNKNOWN: needs the change-management calendar, before Phase 3 | Wave scheduling |
| Operational complexity | No self-hosted CI control plane; runners are ephemeral and autoscaled | ASSUMPTION: avoids a new on-call burden; confirm platform team size | Phase 4 exit check |

**Missing inputs (ranked by plan impact):**
1. Service inventory: language, build tool, deploy target, stateful or not, criticality tier.
2. The existing CI system(s) and the deploy targets. The plan assumes Kubernetes, and this drives the deploy-model row.
3. Change-approval or audit obligations on prod deploys (SOX-like segregation of duties).
4. Platform team size and on-call capacity.
5. Whether source code may leave the corporate network. This drives hosted versus self-hosted runners.
6. The UNKNOWN budget inputs above.

## 3. Tradeoff gates

| Decision | Reversibility | Default | Assumption | Validated by | Flip condition |
|---|---|---|---|---|---|
| Artifact trust and identity model | **R3**: trust boundary; prod admission and every service's credentials rest on it | OIDC-federated short-lived CI credentials (no long-lived secrets); cosign-signed images with provenance and SBOM; admission policy (Kyverno or policy-controller) pins the platform build identity | The security reviewer accepts keyless or KMS-backed signing; no existing org PKI mandate | V3 | V3 fails, or the org mandates an existing PKI or HSM-backed signing |
| Deploy model (push vs pull) | R2: credential model and templates across 50 services | GitOps pull (Argo CD): CI commits to a config repo and clusters pull, so CI holds no cluster credentials | Targets are mostly Kubernetes | V0, then V2 pilots | A V2 archetype can't be expressed under pull, or many services are non-K8s (VMs, serverless) |
| Pipeline contract shape | R2: 50 consumers, coordinated change | Central versioned reusable templates plus a thin per-service config file; semver pins; expand/contract changes | Services fall into a few archetypes | V2 | V2 fails, or pilots need per-service forks of the template |
| Build vs buy (CI engine) | R2: CI system swap | Adopt the org's existing or a managed CI engine and GitOps controller; build only the templates and policy layer | Managed engine meets queue time and cost; source may leave the network | V1 | V1 fails on queue time or cost, or source can't leave the network (then self-hosted runners on the same engine) |
| Fail-closed admission vs hotfix availability | R2: a wrong policy either blocks fixes or admits bad artifacts | Normal path fails closed; a separate audited break-glass path exists | A break-glass path can be built without becoming the normal path | V4 | V4 drill misses the hotfix RTO, or break-glass use exceeds 1 per service per quarter (design parameter) |
| (Brownfield) Migration: replatform per service, per wave | R2: coordination across 50 teams; double-deploy risk | Service-by-service flag cutover (`use_new_pipeline`), old pipeline kept as fallback. **Exactly one deployer per service.** The old pipeline is system of record for release history until a service flips, then the config repo plus Argo. Sync is one-way, with no dual deploy. | Old deploy jobs can be disabled per service | Phase 3 wave exit checks; V4 for decommission | A service can't meet parity, so it stays on the old path with a named owner and date |

**Inherited constraints (not changing):** the existing VCS, container registry, and clusters (ASSUMED). Changing any of these is a re-platform of its own.
**R1 defaults:** Sync vs async → async queued builds, synchronous status checks gating promotion; runners → ephemeral and autoscaled; build cache → per-service remote cache; notifications and dashboards → the org's existing chat and Grafana.
**N/A:** Data-privacy boundary. The platform holds source and build logs, not personal data (ASSUMED). Logs and traces are classified confidential, with secret masking from Phase 0. Tests must not pull prod data, enforced by a template lint in Phase 1.

## 4. Walking skeleton (Phase 0)
**Prerequisites, started first because of lead time:**
- Accounts and approvals.
- A read-only inventory of the 50 services and their consumers.
- A baseline of the old pipelines' timing and failure rates, taken through their own change process.
- Named owners for the Missing inputs.

**The one real request:**
1. A real commit to one low-risk internal canary service lands in the new platform's CI.
2. CI builds, tests, generates the SBOM, pushes the image, and signs it.
3. CI commits the new tag to the config repo.
4. Argo CD syncs it to that service's prod namespace.
5. A real health-check request reaches the new version through the service.

**Tiers crossed:** VCS → CI runner → registry → config repo → GitOps controller → cluster → service → telemetry backend.

**Day-zero operation:**
- **Deployed:** The platform is Terraform/IaC from the first commit. The canary service deploys through the pipeline itself.
- **Logged and monitored:** One trace ID runs from commit to running pod. Pipeline and platform metrics and alerts are live. The admission policy runs in **audit mode**.
- **Rolled back:** Revert the config-repo commit. If needed, flip the flag to put the old pipeline back in charge.

**Who can reach it:**
- Only the platform team and the canary service's team.
- Only the canary service's namespace, with a credential scoped to that namespace.
- The old pipeline stays the default.
- The blast radius is one internal service until V3.

**Exit check V0:**
- A real commit reaches prod with one trace across every tier.
- A deploy and a rollback both succeed through the pipeline.
- An injected failure (a broken test, a failing health check) fires an alert.
- The floors are recorded as baselines, not capacity: queue time, build time, and sync time.

## 5. Phases

- **Phase 1: Trust and identity controls** (widest blast radius first)
  - Unlocks: Prod deploys beyond the canary service.
  - Depends on: V0.
  - Tasks:
    1. Per-service scoped OIDC roles and namespaces (trust boundary).
    2. Provenance and signing enforced for the platform's build identity.
    3. Admission moves audit → **enforce**, staging first, then the canary namespace, then prod namespaces.
    4. Secret scanning, log masking, and an audit log of every deploy and approval.
    5. The break-glass path, built and access-controlled.
    6. Scaffold contract v0 (config schema, template stubs). It is not specified until V2.
    7. Run V3.
  - Rollback: Admission reverts to audit mode. Scoped roles are additive. Break-glass is itself audited.
  - Exit check: V3 passes.

- **Phase 2: Pipeline contract and capacity** (V1, V2)
  - Unlocks: Wave migration.
  - Depends on: V3 for any prod pilot. V1 starts in Phase 0 with the baseline and the cost input.
  - Tasks:
    1. Cluster the inventory into archetypes.
    2. Migrate one pilot per archetype (≥3), including one stateful or migration-heavy service, through staging and then prod. Each keeps the old-pipeline fallback.
    3. Run V2, then freeze template v1.0 with semver and the deprecation policy.
    4. Load-test runners at 2× peak and record the cost per build. Meter cost per team and service.
    5. Run V1.
  - Rollback: Per-pilot flag flip. Template versions are pinned, so a bad release means re-pinning.
  - Exit check: V1 and V2 pass.

- **Phase 3: Migration waves** (exposure smallest first)
  - Unlocks: Full coverage.
  - Depends on: V1, V2, V3, the SLO input, and the freeze calendar. Tier-1 services also depend on the change-approval owner's acceptance.
  - Tasks:
    1. Wave 1: ~5 non-critical services.
    2. Wave 2: ~15 services.
    3. Wave 3: the rest, tier-1 last.
    - Per service: shadow-run builds against the old pipeline and compare image digests and test results. Then flip the flag, disable the old deploy job, and watch.
  - Rollback: Per-service flag flip and re-enable the old deploy job.
  - Exit check per wave, before widening:
    - Change failure rate, rollback rate, and build time are each within BASELINE for every service in the wave.
    - Zero double deploys.
    - Alerts verified.

- **Phase 4: Resilience, SLO, and decommission**
  - Unlocks: Retiring the old pipelines.
  - Depends on: Phase 3, the hotfix RTO input, and V4.
  - Tasks:
    1. SLIs and burn-rate alerts against the SLO.
    2. Platform backup/restore and DR drill.
    3. Break-glass drill.
    4. Archive the old pipeline configs to VCS and keep them read-only for 30 days (design parameter).
    5. Run V4, then decommission.
  - Rollback: The **point of no return** is revoking the old credentials and deleting the old runners. It is guarded by V4. Before that point, re-enabling the old pipeline is a flag flip.
  - Exit check: V4 passes, on-call load is acceptable to the platform team (the operational-complexity ASSUMPTION), and the SLO is being measured.

## 10. Deliberately deferred
- **Progressive delivery (automated canary analysis, feature-flag rollout):** Pulled forward if the change failure rate after Phase 3 stays above its BASELINE, or if tier-1 owners require it.
- **Multi-region or multi-cluster platform HA:** Pulled forward if the SLO input exceeds what single-region meets, or if a DR drill misses the RTO.
- **Internal developer portal and self-service scaffolding:** Pulled forward once more than ~10 new services a quarter (ASSUMPTION) are being created.
- **Ephemeral per-PR environments:** Pulled forward if integration-test contention shows up as the top wave-exit failure cause.
- **Cost chargeback to teams:** Metering is in Phase 2. Chargeback is pulled forward if the budget in V1 is exceeded.
- **Migrating off the inherited VCS, registry, or clusters:** Pulled forward only by a separate business decision.
