# Plan: Customer-support RAG chatbot over the help-center docs

## 1. Classification and constraints
- **What:** A chat widget on the help center. It answers customer questions from the public help-center articles, cites its sources, and hands off to a human agent when it can't answer.
- **Type:** AI-agentic (RAG, no tools or actions). Greenfield component beside an existing help center and ticketing system (fallback is the existing search and contact form). Not a small build: it faces outside users and may see PII in chat text.
- **Dominant constraint:** correctness (answers grounded in the docs). Cost per resolved conversation is second.
- **Worst failure:** a confident wrong answer about billing, refund, security, or policy that a customer relies on. A close second is leaking non-public content or a system prompt through injection. V3 guards the first and V1 guards the second.

**Missing inputs** (none changes the phase order, but each changes a threshold or scope):
1. Help-center platform and export API (Zendesk, Intercom, Confluence, custom), and whether any non-public or internal articles sit in the same space. From the docs owner, needed in Phase 2.
2. Whether the bot must answer account-specific questions. **Assumed no:** anonymous visitors, public docs only, no account data, no actions, English only. If this is false, add an authentication and authorization phase, treat data as R3, and add human-approval gating for any write. The plan would be re-planned after Phase 1.
3. Ticketing system and handoff API (Zendesk, Salesforce, and so on). From the support-ops lead, needed in Phase 1.
4. Approved model vendor, data-processing terms, and residency rules. From security and privacy counsel, needed to start V5.
5. A named support SME to label the eval set and review answers, and a named approver for launch.

## 3. Key decisions (resolved up front)
| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Build vs buy | R2: a vendor switch means weeks of re-integration and re-eval | Build a thin service on a hosted model API and a managed vector store | Your helpdesk has no bundled bot that meets your answer-quality and cost bar | Phase 0 spike: run the V2 and V3 eval set against the helpdesk vendor's bot and compare cost per resolution | A vendor bot meets the V3 bar at ≤ build cost, or V2 fails and ingestion proves to be the hard part |
| Data-privacy boundary (chat text may contain PII) | R3: data gravity at a vendor and legal commitment; exposed PII can't be recalled | Redact PII before logging and before the model call. Vendor on no-training, zero or minimal retention. Chat logs kept 30 days (ASSUMPTION; confirm with counsel). The index holds public docs only. | Users rarely need to share PII to get help, and redaction catches the common patterns | V5 (named privacy counsel sign-off) | V5 fails, residency requires a region or self-hosted model, or scope grows to account data (Missing input 2) |
| Corpus boundary and retrieval access | R3: once non-public text is in the index and answered, the leak can't be undone | Allow-list indexing: only articles with an explicit public flag. No per-user ACL because there is no user data. | The help-center platform exposes a reliable public/internal flag | V2 (the eval set includes a planted non-public canary doc that must never be retrieved) | Any canary doc is retrieved, or the platform has no reliable flag (then add a manual publish list) |
| Prompt+RAG vs fine-tune | R2: retraining is weeks of work | Prompt+RAG with citations and abstention | Answers are in the docs, and docs change often | V3 | V3 fails on style or tone after retrieval is fixed (V2 passed), and labeled data rights are cleared |
| Hosted API vs self-host | R3: residency or data gravity if forced to move later | Hosted API with a thin provider interface and one config-switchable fallback model | Vendor terms (V5) and the latency budget are met | V5, Phase 3 fallback check | V5 fails on residency, or sustained volume makes self-hosting cheaper (V4) |

**minor defaults:**
- Consistency vs availability: availability first. Re-index on doc publish (webhook plus nightly full sync). Each citation shows the article's last-updated date. If the bot is down, show the help-center search and the contact form.
- Monolith vs services: one API service plus a separate ingestion job.
- Sync vs async: streamed sync chat path; async ingestion.
- Vector store: managed (pgvector or a hosted service, whichever the team already runs).
- Chunking: by article heading, with hybrid BM25 plus embedding search.
- Session state: keep the last 6 turns in Redis or in memory, with a 30-minute TTL.

**N/A:** Brownfield migration, cutover, and system-of-record rows do not apply. Nothing is replaced, and the existing help-center search stays as the fallback.

## 4. First end-to-end slice (Phase 0)
- **Request:** A staff member opens an allow-listed, SSO-gated staging-in-production page of the widget. They ask a real question, such as "How do I change my billing email?". They get a streamed answer with a citation to the real article.
- **Tiers:** Widget (web) → API gateway or edge (rate limit, feature flag) → chat service → query embedding → vector store (the real public corpus, naive heading chunks) → model API → streamed response with a citation.
- **Deploy:** CI/CD builds a container image and deploys it to the org's existing container platform. Infrastructure is defined in Terraform or the org's equivalent. The index is versioned behind an alias. Secrets live in the secrets manager.
- **Safety at day zero:** Retrieved and user text go in delimited data sections, never in the system instructions. The chat service has no tools and no outbound calls. There is a hard per-request and per-session token cap and a vendor-side daily spend cap. Logs are PII-redacted.
- **Observability:** One OpenTelemetry trace from widget request to model call, with token and cost metrics per request. Alerts on error rate and on spend.
- **Rollback:** Feature flag off (kill switch), redeploy the previous image, or swap the index alias back.
- **Who can reach it:** Internal staff via SSO only, behind the flag. No public traffic.

**Exit check (V0):** A real question succeeds with one trace across every tier. A deploy and a rollback succeed through the pipeline. An injected failure (model API key revoked) fires an alert. Baseline latency, tokens, and cost per request are recorded at near-zero load.

## 5. Phases

- **Phase 1: Defenses, budgets, and human handoff**
  - Unlocks: anything that handles untrusted input beyond staff; the base for every later phase.
  - Depends on: V0.
  - Tasks:
    1. Get the Missing inputs with lead time (ticketing API, finance/support-ops cost figures, SME name). Start V5.
    2. Separate instructions from untrusted content at the API boundary.
    3. Add input and output filters (PII, jailbreak patterns).
    4. Render output as plain text, with links allowed only to the help-center domain. Render no images and no arbitrary URLs.
    5. Build the injection suite (user input, poisoned article text, and attempts to extract the system prompt), running in CI.
    6. Add per-IP and per-session rate limits, enforce token, iteration, and timeout caps, and define a degraded response.
    7. Build the human handoff: a "talk to a person" path that creates a ticket with the transcript. The bot takes no other action.
    8. Add a cost dashboard and a spend alert.
  - Rollback: flag off; the previous image.
  - Exit check: V1 passes. A runaway loop is cut at the cap and emits a cost metric. Handoff creates a real ticket (test queue). The UNKNOWN budget inputs have named owners and dates.

- **Phase 2: Retrieval**
  - Unlocks: an answer prompt that can be specified.
  - Depends on: Phase 1; the corpus-boundary row; SME named.
  - Tasks:
    1. Build the ingestion job: pull from the help-center API, index only articles with the public flag, and keep metadata (URL, title, last-updated). Pin the embedding model in the index version.
    2. Add hybrid search plus an optional reranker.
    3. Build the labeled set: ≥ 150 real queries sampled from past tickets and search logs. Include ≥ 50 with no answer in the docs, ≥ 30 in high-risk topics (billing, refunds, security), and planted non-public canary docs.
    4. Run the retrieval eval in CI.
    5. Add doc-publish webhook re-indexing.
  - Rollback: swap the index alias to the previous version.
  - Exit check: V2 passes. A full re-index completes in a time that fits a nightly window, and a failed sync leaves the previous index serving.

- **Phase 3: Model access, answer policy, and session memory**
  - Unlocks: exposure to a canary, once V5 and legal are also in hand.
  - Depends on: V2; Phase 1.
  - Tasks:
    1. Write the answer prompt: answer only from retrieved passages, always cite, and abstain or hand off when retrieval confidence is low or the topic is high-risk.
    2. Wrap the model behind a thin provider interface with retries, timeouts, and a configured fallback model.
    3. Add the eval harness (groundedness, abstention, citation correctness) in CI, with SME review of sampled outputs.
    4. Add short-term session memory (last 6 turns) with PII redaction and a TTL.
    5. Run the load and latency check against the Throughput input.
  - Rollback: revert the prompt or model config version; switch to the fallback model by config.
  - Exit check: V3 passes. Switching to the fallback model is a config change and the eval suite still passes on it at V3's bar. Latency meets the budget at the agreed load.

- **Phase 4: Staged exposure and feedback capture**
  - Unlocks: full launch.
  - Depends on: V1, V3, V5; legal sign-off on the AI disclosure and the launch approver; the V4 threshold has a number.
  - Tasks:
    1. Staff dogfood at 100% of staff traffic.
    2. Canary at 1–5% of visitors on one help-center section (smallest exposure first).
    3. Add thumbs up/down, a "did this solve it?" prompt, and an unanswered-question report to the docs team.
    4. Widen 5% → 25% → 100% only after each step's checks hold: error rate, handoff rate, no critical wrong-answer reports after SME review of the sample, spend within cap.
    5. Measure V4 on the canary.
  - Rollback: flag off returns everyone to the existing search and contact form at any step.
  - Exit check: V4 passes before any step beyond the canary. The availability SLO holds for 2 weeks at 100%.

- **Phase 5: Feedback loop**
  - Unlocks: continuous improvement.
  - Depends on: Phase 4.
  - Tasks:
    1. Move reviewed failures into the eval set, and doc gaps into docs-team tickets.
    2. Tune retrieval and prompts only through the eval suite.
  - Rollback: revert to the previous prompt or index version.
  - Exit check: the next eval run improves the target metric with no regression elsewhere. Nothing enters the eval set, prompts, or index without review.

## 10. Deferred
- **Account-specific answers and actions** (order lookups, refunds): pulled forward when the business asks for them. This needs authentication, per-user retrieval access, human-approved writes, and a new R3 review.
- **Fine-tuning:** pulled forward if V3 fails on tone or format after V2 passes and data rights are cleared.
- **Long-term memory and personalization:** pulled forward if repeat-contact data shows value, and only after a privacy review.
- **Routing and multi-model cost optimization:** pulled forward if V4 fails or cost at scale exceeds the finance threshold.
- **Multi-agent orchestration:** pulled forward if labeled tasks need multi-step work that a single call can't do.
- **Other languages and channels** (in-app, email, voice): pulled forward when the Missing input on languages or channels is confirmed, and after Phase 4 is stable.
- **Self-hosted model:** pulled forward if V5 fails on residency or V4 shows self-hosting is cheaper at sustained volume.
