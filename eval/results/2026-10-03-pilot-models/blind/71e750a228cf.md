# Plan: Real-Time Collaborative Document Editor

## 1. Classification and constraints

**What is being built**: A real-time collaborative document editor (synchronous multi-user editing, e.g., Google Docs / Notion style).

**Type**: Software (distributed system: frontend + backend + database).

**Greenfield or brownfield**: Greenfield (new system).

**Scale**: Assumed not-small. Collaborative editors face high concurrency: typical assumption is 100–1000 concurrent users, documents with 10k–1M characters, 10–100 edits per second under peak. Conflict resolution and network partition handling are mandatory.

**Dominant constraint**: **Correctness > Availability > Latency > Cost**. Concurrent edits must merge without data loss; network partitions and crashes must not corrupt the document. Latency matters (users expect <200ms end-to-end), but data integrity is non-negotiable.

**Worst failure**: Data corruption or loss during concurrent edits; or unauthorized access to private documents.

## 4. First end-to-end slice (Phase 0)

**Who can reach it**: Internal developers and QA only. Behind feature flag `editor_v1`. No real user data. No production database access until V0 passes.

**One real request end-to-end**:
1. **Client**: Open browser, navigate to `http://localhost:3000/editor?doc_id=test123`
2. **Client**: JavaScript initiates WebSocket upgrade to `ws://localhost:3001/sync`
3. **Server**: Receives upgrade, creates session, verifies internal (no auth yet, but request is from internal IP)
4. **Server**: Fetches doc state from database (initial CRDT state = empty)
5. **Server**: Sends initial state to client: `{ type: "init", state: {...} }`
6. **Client**: Receives state, initializes local CRDT, renders empty editor
7. **User**: Types "hello world" (6 keystrokes)
8. **Client**: For each keystroke, generates CRDT insert operation, sends to server: `{ type: "update", op: { pos: X, content: "c" } }`
9. **Server**: Receives update, applies to document CRDT, broadcasts to all connected clients (including sender), persists to `document_updates` table
10. **All clients**: Receive broadcast, apply op to local CRDT, re-render (should show "hello world" live)
11. **Server**: Logs trace: `session:open → update:received → crdt:apply → db:write → broadcast:sent`
12. **Latency**: <100ms local (keystroke to own client render), <200ms remote (keystroke to other client render)

**Deployment**:
- Docker Compose (`docker-compose.yml`):
  - `server` (Node.js + Express + `ws` library + Yjs)
  - `db` (PostgreSQL 14)
  - `adminer` (for local DB inspection)
- GitHub Actions pipeline:
  1. `npm ci` (install exact versions)
  2. `npm test` (unit tests)
  3. `docker build` (server image)
  4. `docker push` (to ECR, or local registry for local CI)
  5. Deploy to `localhost:3000` (for local dev) or ECS/K8s cluster (for staging)

**Logging (structured, JSON)**:
- Session lifecycle: `{ ts, event: "session:open", session_id, user_id:"internal", doc_id }`
- Update received: `{ ts, event: "update:received", op_count, op_size_bytes }`
- CRDT apply: `{ ts, event: "crdt:apply", op_id, latency_ms, merge_conflict: false }`
- DB write: `{ ts, event: "db:write", latency_ms, table: "document_updates" }`
- Broadcast: `{ ts, event: "broadcast:sent", client_count, latency_ms }`
- Errors: `{ ts, level: "error", component, message, stack_trace }`

**Monitoring (dashboards in CloudWatch / Datadog)**:
- **Latency histogram**: keystroke → server receive (network) + server apply (CRDT) + server broadcast (network) + client render. P50, P95, P99.
- **WebSocket status**: active connections, disconnected, reconnect rate.
- **Database metrics**: write latency (p99), connection pool utilization.

- **Memory / CPU**: per-connection baseline (should be <1MB/conn for skeleton).
- **Errors**: exception rate, error type breakdown.

**Rollback**:
1. Feature flag `editor_v1` set to false → all requests route to old (or no-op) editor.
2. Database schema rolled back (migration reversible; schema only adds `document_updates` table, does not alter existing).
3. Docker image reverted: `docker pull old_image_sha` → re-deploy.
4. Verification: old clients continue to work; no data loss.

**Exit check V0** (all must pass):

### **Phase 8: Security audit and public launch**

**What it unlocks**: External users, public marketing.

**Depends on**: Phase 7 complete, V10 passes.

**Tasks**:
1. **Security audit (internal or external)**
   - Code review: injection (SQL, JavaScript), XSS, CSRF, authentication bypass
   - Dependency scan: `npm audit`, check for known CVEs
   - Encryption audit: TLS 1.3, certificate management, key rotation
   - Data handling audit: encryption at rest, retention, deletion, access logs
   - V11 gate: zero critical/high CVEs, TLS 1.3 for all transport, encryption at rest, audit trail complete
2. **Privacy policy and compliance**
   - Document: what data is collected, how long retained, who can access
   - If GDPR applies: DPA with any processor, data subject rights (access, delete), breach notification process
   - If SOC2 applies: audit controls (access, change management, monitoring)
   - If HIPAA applies: BAA with any processor, encryption, audit logging
3. **Onboarding and documentation**
   - User guide: how to create doc, invite users, use editor
   - Admin guide: how to manage users, permissions, backups
   - API documentation: if exposing API to partners
4. **Support and escalation**
   - Support email / chat
   - Incident response playbook: what to do if system down, data corrupted, data breached
   - On-call rotation: schedule SRE on-call, escalation path
5. **Feature flag removal**
   - Enable for all users (remove `editor_v1` flag)
   - Public documentation live
6. **V11 gate: Security audit passes**
   - Test: penetration test (attempt injection, XSS, CSRF, auth bypass), result: all attacks blocked
   - Success: zero critical/high vulns, privacy policy matches data handling, audit controls in place

**Rollback**: Keep internal-only flag available; if critical issue found, re-enable flag to limit exposure.

**Exit check**:
- ✅ V11 passes (security gate)
- ✅ Team ready for on-call rotation
- ✅ Incident playbook tested
