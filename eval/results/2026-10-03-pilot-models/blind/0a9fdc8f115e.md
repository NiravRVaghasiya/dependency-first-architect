# BUILD PLAN: CI/CD Platform for 50 Microservices

## 1. Classification and Constraints

**What is being built:** A CI/CD platform capable of orchestrating build, test, and deployment workflows for 50 microservices across multiple environments.

**Type:** Infrastructure + software (platform-as-a-service). Greenfield, but assumes existing containerized microservices.

**Scale:** Not small. Affects all service teams daily; data includes build artifacts, deployment logs, and credentials; money flows through infrastructure cost. One failure (credential leak, widespread deploy failure) compromises the whole platform.

**Dominant constraint:** **Availability/SLO** (the platform must not be a bottleneck; all 50 services depend on it). Secondary: **correctness** (deploy the right artifact to the right place, reproducibly); **observability** (teams must trust the logs and see failures). Cost is tertiary (infrastructure, storage for artifacts).

**One failure that hurts most:** Credential/secret leak during artifact build or deployment (security blast radius: all 50 services, all environments). Second: simultaneous failure of all deployments (availability impact).

**Budgets and labels:**

| Budget | Label | Value / Basis |
|--------|-------|--------------|
| Pipeline latency (commit to deployment ready) | ASSUMPTION | ≤ 10 min for a simple service (no external build deps); ≤ 30 min for a monolithic build with multiple services |
| Build artifact storage retention | REQUIREMENT | 30 days; retained by service + version + build ID |
| Concurrent pipelines per team (at 50 services) | ASSUMPTION | 3–5 concurrent builds per team; total capacity ~15 builds/min across platform |
| Availability SLO | REQUIREMENT | 99.5% (4.4 hours downtime/month); degraded mode allows manual override |
| Secret rotation cycle | REQUIREMENT | < 30 days; audit trail required |
| Deployment recovery time (RTO) | REQUIREMENT | ≤ 5 min for a failed deploy; ≤ 15 min for full platform restart |
| Disaster recovery RPO | ASSUMPTION | 1 hour (build logs, deployment state); production artifact store backed up every 15 min |

**Missing inputs that would change the plan:**

- **Who** supplies the microservices' build configs? (Docker files, build scripts, dependency lists.) *Assumed:* supplied by service teams; platform provides templates and validation.
- **Multi-region or single region?** *Assumed:* single region to start; multi-region gates later.
- **Who owns secrets** (DB passwords, API keys, OAuth tokens)? *Assumed:* a separate secrets-management layer (e.g., Vault); CI/CD reads, does not generate or store.
- **Blast test phase required?** (e.g., canary deploy to 1 service before opening to all.) *Assumed:* yes; treat as a validation gate, not optional.
- **Artifact repository (Docker Registry, artifact store)?** *Assumed:* exists; we integrate with it, do not build it.

**Methodology exceptions:** None declared yet. The walking skeleton will be internal (one test service, no real external traffic) until Phase 1.

## 4. Walking Skeleton (Phase 0)

**Goal:** One real build-and-deploy request, end-to-end, through the full pipeline, on a test service, to a test cluster, logged, monitored, and rolled back.

**The request:** Git push to branch `main` of a test service → build triggered → artifact tagged and pushed to registry → deploy manifests written to deployment repo → GitOps detects change → deployment to test K8s cluster → 3 smoke tests (pod ready, health check pass, HTTP 200 on /health) → monitor 5 min for errors → success logged → manual rollback triggered (old artifact deployed, verified).

**Who can reach it:** Only internal (test cluster behind VPN or private subnet; no internet-facing endpoint). No real traffic, no real users, no real data.

**Tiers crossed:**
1. **Git** (GitHub, GitLab, or internal): push trigger
2. **CI orchestrator** (e.g., Jenkins, GitLab CI, or GitHub Actions): build job
3. **Build agent** (Docker daemon, or Kaniko for rootless): compile, test, build image
4. **Artifact registry** (ECR, GCR, or Artifactory): push image, tag with git-sha
5. **Secrets manager** (Vault): fetch registry credentials, service account token
6. **GitOps controller** (ArgoCD or Flux): detect change in deployment repo, trigger sync
7. **Kubernetes cluster** (test): deploy pod, run probes
8. **Observability** (ELK, Prometheus, or equivalent): ingest logs, metrics, traces
9. **Rollback step:** GitOps re-sync to previous commit, pod replaced

**Infrastructure as code:**
- Skeleton pipeline defined in YAML (Jenkinsfile, .gitlab-ci.yml, GitHub Actions, or Argo Workflows).
- Deployment manifests in Git (Kustomize or Helm).
- Cluster config (RBAC, namespaces, secrets) in IaC (Terraform or Helm).
- All code in version control; skeleton repo is read-only until Phase 1 (no manual tweaks).

**Observability in Phase 0:**
- **Logs:** All pipeline steps emit structured logs (JSON with timestamp, step name, status, error if any) → ELK.
- **Metrics:** Build time (s), artifact size (MB), deploy latency (s), pod startup time (s) → Prometheus or CloudWatch.
- **Traces:** Skeleton pipeline instrumented with Jaeger or Datadog (optional but encouraged for 30 min review cycles).
- **Alerts:** Any step failure → Slack / PagerDuty (test-only; no page-on-call yet).

**Security in Phase 0:**
- Secrets (registry auth, cluster token, Vault credentials) passed via environment variables from a secret store; never logged or committed.
- Image signed with a test key (Notary or sigstore, simple self-signed for skeleton); deploy verifies signature (fail if unsigned or invalid).
- Audit log entry for every artifact build, push, and deploy (who, what, when, where); immutable append-only log in S3 or managed service.
- RBAC in place: test service account can only deploy to test namespace; no prod access.

**Reproducibility in Phase 0:**
- Build is deterministic (same input → same artifact hash). Dockerfile is pinned (base image digest, not "latest"); all deps frozen.
- Rollback is idempotent (re-deploy old artifact, same config, same outcome).
- Skeleton runs twice; both deploys succeed; both roll back.

**Resilience in Phase 0:**
- If build fails, pipeline stops; developer is notified.
- If artifact push fails (registry down), pipeline retries 3 times with exponential backoff; fails after 3 attempts.
- If deploy fails (K8s not reachable), GitOps sync retries every 30 sec for 5 min, then alerts.
- If a probe fails, pod is restarted; if restart fails repeatedly, pod is evicted and alarm fires.

**Exit check V0:**
- A real commit (not a mock) to test service triggers a complete pipeline.
- Artifact is built, signed, pushed, and retrievable by digest.
- Deployment succeeds; all 3 probes pass; no errors in logs.
- Rollback succeeds; old artifact is live again.
- Observability: at least one trace/log entry visible in ELK for each step; baseline latency recorded (total time commit → live ≤ 30 min).
- Repeating the skeleton 2 hours later: same build artifact hash (reproducibility passes).

**What is NOT in Phase 0:**
- No multi-region, no canary, no staged deploy, no approval gates.
- No integration with production cluster (test cluster only).
- No load test or performance validation.
- No second service (parallel builds not yet tested).
- No secrets rotation or compliance audit (hardening deferred).

## 5. Phases

### Phase 1: Platform Foundation (Weeks 1–4)

**What it unlocks:** Ability to add real microservices (Phase 2), safely deploy to prod with canary (Phase 2), and measure platform stability (Phase 3).

**Depends on:** V0 passes (skeleton works). Organizational: infra team trained on pipeline engine, cluster, and secrets manager (Lead time: recruiting, onboarding; assume week 0). Git, K8s cluster, Vault, artifact registry exist and are stable.

**Tasks:**

#### Phase 1a: Schema, RBAC, and infrastructure hardening (Weeks 1–2)

1. **Artifact naming and versioning contract** (Day 1–2)
   - Define naming scheme: `{service-name}:{git-branch}-{git-sha}-{build-number}`. Example: `payment-api:main-abc123-42`.
   - Tag also with semver if service publishes one: `payment-api:v1.2.3`.
   - Document and commit to platform wiki.
   - Validation: template enforced in build pipeline (Phase 1b).

2. **Deployment manifest schema** (Day 1–2)
   - Define what a deployment manifest must contain: service name, Docker image (with exact tag, no "latest"), resource requests (CPU, memory), liveness/readiness probes, RBAC ServiceAccount, namespace.
   - Kustomize or Helm template for each service (teams customize, not invent).
   - Validate manifests before GitOps sync (Phase 1b gate).

3. **RBAC and service accounts** (Day 2–3)
   - Create Kubernetes namespaces: one per service (or per team; decide based on team structure).
   - Create ServiceAccount per namespace; bind to deployment role (can deploy/update deployments, cannot delete PVCs or secrets).
   - Bind cluster role to infra-team (admin on test namespace, limited deploy on prod).
   - Bind teams to their own namespace (RBAC tests in Phase 1b).
   - Audit logging: all RBAC decisions logged (API server audit).

4. **Secrets manager integration** (Day 3–4)
   - Vault unsealed, policies written: service-specific policies (team A's builds can only read team A's secrets).
   - Workload Identity or OIDC configured (if using AWS/GCP): no long-lived credentials in environment variables.
   - Test: build job acquires token from Vault, uses it to fetch a secret, token expires after 1 hour.
   - Audit every fetch: log token ID (not value), service, timestamp, success/fail.
   - **Validation gate V1:** Secrets manager integration (below).

5. **Artifact repository hardening** (Day 4–5)
   - Registry configured with read-write access control (teams can push to their own repos, pull public images).
   - Image signing: set up Notary or Cosign; build signs every image.
   - Registry policy: reject unsigned images (for prod namespace later; test namespace allows unsigned for iteration).
   - Test: push unsigned image → reject (dry-run first, log but do not block).
   - Audit: every push/pull logged (image, tag, user, timestamp, success/fail).

6. **Observability baseline** (Day 5–6)
   - ELK cluster running; pipeline and infra logs flowing in.
   - Prometheus targets scraping: CI orchestrator metrics (job duration, success rate), K8s metrics (pod startup, resource use).
   - Baseline established: Phase 0 latency recorded, error rate at ~0%.
   - Dashboards created: "Platform Health" (build success rate, deploy success rate, average latency), "Security" (secret fetches, unsigned images rejected, RBAC denials).
   - Alert rules: build failure → Slack; deploy failure → PagerDuty (test-only).

7. **Disaster recovery baseline** (Day 6–7)
   - Artifact store backed up every 15 min (to S3 or equivalent).
   - GitOps state (deployment manifests) backed up every 1 hour.
   - Vault backed up daily (or per Vault best practices).
   - Restore test: simulate artifact loss, restore from backup, verify integrity (Phase 2 dry-run).
   - RTO documented: artifact restore < 5 min, GitOps re-sync < 2 min, total platform recovery < 15 min.

#### Phase 1b: Multi-service pipeline and canary validation (Weeks 2–4)

1. **Pipeline engine template** (Day 8–11)
   - Declarative pipeline template in Git (one per service; teams copy and customize).
   - Stages: Git trigger → lint (Shellcheck, Dockerfile linter) → build → security scan (Snyk, Trivy) → push → test deploy (canary to test cluster) → emit artifact metadata.
   - Security scan gate: fail if critical CVE found; warn if high; pass otherwise (gate V2 in Phase 1b).
   - Retry logic: transient errors (registry timeout, network blip) retry 3x with exponential backoff; fail-fast on logic errors.
   - Template in repo `platform-templates/` (read-only; version-controlled).

2. **Artifact build reproducibility validation** (Day 8–10)
   - Build same commit twice, compare artifact digests; must match (V1 detailed: see Validation gates).
   - Test on 3 sample services; measure success rate (target: 100%).
   - Document: Dockerfile must be deterministic (pinned base image digest, no timestamps in build).
   - Linter enforces: reject Dockerfile with "latest" tag or current date in RUN.

3. **Secret scanning in artifacts and logs** (Day 9–11)
   - Artifact scanning: scan built images for hardcoded secrets (regex for AWS keys, DB passwords, API keys; entropy check).
   - Log scanning: all pipeline logs scanned for secrets before ingestion into ELK.
   - Action: if secret found, build fails; artifact deleted; developer notified; audit logged.
   - Test: inject fake secret into build, verify detection and rejection (V2 gate).

4. **Canary deploy validation on test cluster** (Day 11–14)
   - Deploy test service to test cluster using canary strategy: 5% traffic (or 1 pod of 10) → wait 5 min → 25% (3 pods) → wait 5 min → 100% (10 pods).
   - Metrics collected: error rate (target: < 5%), latency P99 (target: < 2 sec baseline), memory/CPU use.
   - Auto-rollback trigger: if error rate > 5% for 1 min, or latency P99 > baseline × 1.5, rollback to previous version.
   - Measure rollback time (target: < 2 min from trigger to success).
   - Repeat 5 times with different service versions (stable, new, unstable mock).
   - **Validation gate V3:** Canary deploy test (below).

5. **Deploy authorization RBAC test** (Day 12–13)
   - Team A tries to deploy team B's service: deny (RBAC policy blocks).
   - Team A deploys team A's service to test namespace: allow.
   - Infra team deploys anything to prod: allow (or gated by separate approval; decide policy now).
   - Log each attempt (success and failure); audit trail must show who, what, when, result.
   - Test RBAC failures trigger alerts (detect privilege escalation attempts).
   - **Validation gate V2:** RBAC and audit (below).

6. **Multi-service parallel build test** (Day 13–14)
   - Trigger builds for 10 test services simultaneously.
   - Measure: build success rate (target: ≥ 99%), build time (target: ≤ 10 min per service), artifact conflicts (target: 0).
   - If conflicts, add dependency DAG logic (Phase 1b extension or Phase 2 task).
   - If success, confirm parallel build is safe for Phase 2.

7. **Runbook and documentation** (Day 14)
   - Write runbooks: "How to deploy my service," "How to check deployment status," "How to rollback," "How to read logs."
   - Publish wiki (linked from team onboarding).
   - Templates ready for service teams to copy and adapt.

**Rollback:** If a validation gate fails (V1, V2, V3), the specific feature is not hardened; deployments continue on Phase 0 capabilities (manual deploy, no canary, no auto-rollback) until gate passes. No data loss or production impact; test cluster revert to previous pipeline version (easy, no state change).

**Exit check for Phase 1:**
- V1: Secrets manager integration works; token scope and audit logged.
- V2: RBAC blocks unauthorized deploys; audit trail complete; secret scanning rejects hardcoded secrets.
- V3: Canary deploy succeeds; rollback < 2 min; error detection works.
- All 10 test services build in parallel, < 10 min per service, ≥ 99% success.
- Observability baseline recorded; platform dashboard green.
- Runbooks exist and pass review by 2 service teams (dry-run of deploy).

### Phase 2: Prod Rollout (Weeks 5–8)

**What it unlocks:** All 50 microservices can be deployed to production with safety controls in place.

**Depends on:** Phase 1 complete; all V1–V3 gates passed. Organizational: service teams onboarded; runbooks read; at least 1 team has done a trial deploy to test cluster.

**Tasks:**

#### Phase 2a: Prod RBAC and controls (Week 5)

1. **Production namespace and RBAC** (Day 1–2)
   - Create prod namespaces (one per service or team).
   - Create ServiceAccounts with lower privileges than test (read-only secrets, deploy updates only to own deployment, cannot delete PVCs, cannot access other namespaces).
   - Infra team RBAC: can deploy, cannot delete; audit all actions.
   - Bind service teams to their prod namespaces (read-only except for their own deployments).

2. **Prod deployment policy** (Day 2–3)
   - Policy: all deploys to prod go through canary (no all-at-once).
   - Canary percent: 5% → wait 5 min → 25% → wait 5 min → 100%.
   - Auto-rollback triggers: error rate > 5% for 1 min, latency P99 > baseline × 1.5, or pod crash loop.
   - Approval gates: team can trigger deploy; infra team is auto-paged if rollback fires (not blocking deploy; informing).
   - Team can manually rollback without approval (deploy previous version, go through canary again).

3. **Secrets rotation prod policy** (Day 3–4)
   - Prod secrets (DB passwords, API keys, OAuth tokens) rotated every 30 days (or per compliance requirement).
   - Rotation is zero-downtime: new secret in Vault, Workload Identity fetches new token on next build, old secret evicted after 1 hour.
   - Audit every secret rotation (who, what, when, old value hash [not value itself], new value hash).
   - Test: rotate a prod-like secret, verify no deploy interrupted.

4. **Prod incident playbook** (Day 4–5)
   - Scenarios: single service deploy fails → canary catches it → auto-rollback (or team manual rollback).
   - Scenario: multiple services deploy at once, one fails → canary catches one, others proceed independently.
   - Scenario: artifact registry down → deploys queued; when registry back, queued deploys proceed automatically.
   - Scenario: Vault unsealed → all builds pause; Vault sealed by on-call; resumes after.
   - Each scenario: who is notified, what is the response, what is measured, what is the rollback.
   - Tested (dry-run) by infra team + 2 service teams.

#### Phase 2b: First service prod deploy (Week 5–6)

1. **Select a low-risk service for pilot** (Day 1)
   - Criteria: no critical dependencies (internal-only, non-financial), low traffic (< 1 req/sec), team confident in their code.
   - Example: internal logging service, non-critical dashboard.

2. **Deploy pilot to prod with canary** (Day 2–4)
   - Run full canary deploy: 5% → 5 min → 25% → 5 min → 100%.
   - Infra team monitors; team on call during deploy (5–15 min total).
   - Measure: error rate, latency, pod startup, resource use.
   - Success: all metrics green, canary proceeds smoothly, team confident.
   - Audit: deploy event logged; team, approval, artifact version, canary progress, final status.

3. **Trial rollback** (Day 4–5)
   - Manually trigger rollback (even though deploy is stable).
   - Verify old version comes back.
   - Measure time: < 2 min.
   - Confirm logs show rollback event.
   - Test: deploy again to re-enable new version (practice).

#### Phase 2c: Rollout to all 50 services (Weeks 6–8)

1. **Wave 1: 10 services (Week 6)**
   - Select 10 non-critical services (internal tools, non-financial, low traffic).
   - Stagger deploys: 2–3 per day, 1 hour apart.
   - Same canary policy, same monitoring.
   - Exit: all 10 green, 0 unplanned rollbacks, teams confident using runbooks.

2. **Wave 2: 20 services (Week 7)**
   - Mix: internal and customer-facing (but non-critical to customer experience).
   - Stagger: 3–5 per day.
   - If any rollback, pause wave; debug; retrace in Phase 2c extension (not a blocker, but learning).
   - Exit: all 20 green.

3. **Wave 3: 15 services (Week 7–8)**
   - Mix: more critical services, higher traffic.
   - Canary windows extended if traffic > 10 req/sec (wait 10 min instead of 5 min between stages).
   - Exit: all 15 green, 0 unplanned rollbacks.

4. **Wave 4: Final 5 critical services (Week 8)**
   - Highest-risk: financial, customer-critical, 100+ req/sec traffic.
   - Canary windows: 10 min each stage.
   - Infra team + service team + on-call manager present.
   - Exit: all 5 green, system stable for 24 hours at 100% new version.

**Rollback:** If unplanned rollback at any wave, pause; debug; fix (usually pipeline bug or service bug, not platform bug); re-test on Wave 0 service (not in prod yet); resume wave.

**Exit check for Phase 2:**
- All 50 services deployed to prod via canary.
- 0 critical incidents caused by deploy mechanism (service bugs ok, infra bugs not ok).
- All teams have deployed once; at least 1 team manual rollback succeeded.
- Audit trail shows all deploys and rollbacks; RBAC blocked unauthorized attempts.
- Observability: "Platform" dashboard shows 50 active services, < 0.5% deploy failure rate, canary latency < 5 min end-to-end.

### Phase 3: Observability, Compliance, and Optimization (Weeks 9–12)

**What it unlocks:** Production hardening, audit compliance, cost optimization, multi-region readiness.

**Depends on:** Phase 2 complete; platform stable on all 50 services for 2 weeks.

**Tasks:**

1. **Compliance audit and hardening** (Week 9)
   - Audit trail: full retention (90 days hot, 1 year cold in S3).
   - RBAC audit: all actions logged, compliance-readable.
   - Secrets audit: all fetches logged (token ID, service, timestamp); rotation history.
   - Check against compliance requirement (SOC2, HIPAA, PCI DSS, or internal policy); map controls.
   - Remediation if gaps (e.g., if PCI DSS requires encryption at rest, enable EBS encryption, KMS).

2. **Platform SLO measurement and alerting** (Weeks 9–10)
   - Measure: uptime (availability of pipeline), error rate (failed deploys), latency (commit → deployed).
   - Target SLO: 99.5% uptime, deploy error rate < 1%, latency P99 < 15 min.
   - Alerting: trigger if any metric crosses SLO band (not just outage; also degradation).
   - On-call rotation: infra team rotates; SLA for response < 15 min.

3. **Cost optimization** (Weeks 10–11)
   - Review artifact storage cost (target: < 200 USD/month for 50 services × 30 days retention).
   - Review CI orchestrator cost (if managed: AWS CodePipeline, GitHub Actions, etc.; if self-hosted: K8s pods, storage).
   - If cost > budget, implement compression, archival, or retention policy tuning.
   - Re-baseline: new cost vs. assumed cost; adjust Phase 3b.

4. **Multi-region readiness** (Weeks 11–12)
   - Plan: how to deploy same 50 services to a second region (replication, artifact distribution, secrets sync).
   - Design: artifact registry replicated? Separate clusters? GitOps per cluster?
   - No rollout yet (Phase 4); design and tests only.

**Exit check for Phase 3:**
- Compliance gaps identified and remediated.
- SLO targets met (or exceptions documented).
- Cost within budget (or tuning plan for Phase 4).
- Multi-region design approved.

### Phase 4: Scale, Multi-Region, and Continuous Improvement (Quarter 2+)

**What it unlocks:** Multi-region deployment, advanced features (blue-green, traffic splitting, gradual darkening), cost optimization at scale.

**Depends on:** Phase 3 complete; platform stable and proven on single region with 50 services.

**Tasks:**
- Multi-region rollout (same pipeline, separate artifact caches per region).
- Advanced deploy strategies (blue-green for zero-downtime, traffic splitting for A/B testing).
- CI/CD platform as a product: offer to other teams, charge-back model for cost allocation.
- Continuous improvement: automate runbook scenarios, add self-healing for common failures, reduce on-call load.

## Summary

This plan sequences building a CI/CD platform for 50 microservices by dependency, not visibility:

1. **Phase 0 (Weeks 1–2):** Walking skeleton: one service, end-to-end pipeline, test cluster, fully observed, reproducible, and rolled back. Internal-only; no prod exposure. Exit check: V0.

2. **Phase 1 (Weeks 3–10):** Platform foundation: schema, RBAC, secrets, observability, and multi-service validation. Canary strategy validated on test cluster. Service teams onboarded. Exit check: V1–V3, runbooks, multi-service parallel builds.

3. **Phase 2 (Weeks 11–18):** Prod rollout in 4 waves (10 → 20 → 15 → 5 services). Canary deploy, auto-rollback, incident playbook. All 50 services live; zero critical incidents caused by infra.

4. **Phase 3 (Weeks 19–26):** Compliance audit, SLO measurement, cost optimization, multi-region design. Platform stable and hardened.

5. **Phase 4+ (Quarter 2+):** Multi-region rollout, advanced strategies, self-healing, cost chargeback.

**Key principles applied:**
- Build what everything else stands on first (schema, RBAC, secrets, observability).
- Validate hard-to-reverse decisions upfront (pipeline engine, registry, rollout strategy, secrets rotation, auth).
- Thread security, observability, reproducibility, and resilience from Phase 0; never tacked on.
- Lead with a walking skeleton (Phase 0): one real request through every tier, deployed and rolled back.
- Order by blast radius: schema and RBAC (widest impact) hardened in Phase 1a before multi-service pilots in Phase 1b–2.
- Exposure runs smallest first: 1 pilot service, then 10, 20, 15, 5 in waves; pause if issues.
- Nothing proceeds until its blocker is met: no prod deploy before canary validation (V3); no multi-service before reproducibility validated (V1); no self-service without RBAC (V2).
