# Plan: Real-time collaborative document editor

## 1. Classification and constraints
- **What:** A web editor where several users edit the same rich-text document at once. Edits show up live for everyone, and documents persist, are shared by permission, and belong to tenants (workspaces).
- **Type:** Software, greenfield, not small. It serves outside users, holds their content, and has R3 decisions.
- **Dominant constraint:** Correctness (all replicas converge and no acknowledged edit is lost). Latency is second.
- **Worst failure:** Silently losing or corrupting an edit the user saw acknowledged. The next worst is one tenant reading or writing another's documents. V2 guards the first and V3 the second.

**Budgets**

| Budget | Target | Label | Checked by |
|---|---|---|---|
| Latency | Remote edit visible to other editors p95 < 200 ms, same region, 10 editors per doc. Local echo is immediate. | ASSUMPTION: common bar for "feels live"; confirm with the product owner | V0 records the floor; V4 checks it |
| Scale per document | 50 concurrent editors, state ≤ 2 MB | ASSUMPTION: typical mid-size collaboration limits; product owner to confirm | V1, V4 |
| Scale overall | Total concurrent connections and documents | UNKNOWN: product owner supplies the 12-month projection before Phase 3 starts | V4 cannot pass without it |
| Availability / SLO | — | UNKNOWN: product owner supplies the committed availability before Phase 5 | SLIs and burn-rate alerts from Phase 5 |
| RPO / RTO | RPO = 0 for acknowledged edits. RTO: UNKNOWN. | RPO is an ASSUMPTION (correctness is dominant, so ack only after a durable write). RTO: product owner supplies it before Phase 3. | V2 (RPO), V4 (RTO) |
| Storage cost | Update log compacts to ≤ 3× snapshot size | ASSUMPTION: starting value, to be replaced by the V2 measurement | V2 |
| Operational complexity | One stateful app service, managed Postgres, managed identity provider. No Redis or self-run cluster until V4 flips. | ASSUMPTION: small team | Phase 3 exit check |

**Missing inputs** (the phase order rests on these assumptions):
- **Server-readable content.** The order assumes the server can read document content, so there is no end-to-end encryption. If that is false, the convergence model, authorization, search and storage all have to be re-planned, so confirm it first.
- **Clients and region.** The order assumes a web client only and a single region. Residency requirements would change V5.
- **Rich text.** The order assumes rich text with a small schema (headings, lists, marks, links). If plain text only, V1 shrinks.
- **Offline editing.** The order assumes a reconnect that resyncs, with no long offline editing.
- **Organizational items** (owner and need-by date are unconfirmed, so none is assumed to be in hand):
  - production cloud account;
  - identity provider (OIDC) tenant;
  - domain and TLS;
  - named security reviewer and privacy/legal reviewer.

## 3. Key decisions (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Convergence model and document schema | R3: persisted format and wire protocol, and clients hold copies | CRDT (Yjs) with a ProseMirror/Tiptap schema. Each doc carries a schema version, and migrations use expand/contract. | Yjs stays within memory and load-time bounds at 2 MB and 50 editors. Rich-text semantics merge acceptably. | V1 | V1 fails, or product needs server-authoritative range permissions: switch to server-ordered OT (ProseMirror collab style) before Phase 2 |
| Consistency vs availability | R3: consistency model | Eventual convergence. Server acks only after a durable commit (group commit). Peers get the update immediately, and idempotent CRDT merge makes resends safe. | Group commit adds little latency | V2 | V2 ack overhead exceeds the bar, or lost acknowledged edits: ack-then-persist is not allowed; tune batching or change the store |
| Data model, identifiers, storage | R3: identifiers and data model once real data exists | Postgres. Append-only update log plus periodic snapshots. UUIDv7 `doc_id`. `tenant_id` on every row. Raw binary update kept, with an open-format export (HTML/Markdown). | One Postgres primary suffices at the projected scale. Compaction keeps replay fast. | V2, V4 | Replay or compaction misses its bar at projected scale: partition by `tenant_id`/`doc_id` |
| Tenancy, authn/authz | R3: tenancy and trust boundary | Workspace tenant. Per-document roles (owner/editor/commenter/viewer). Short-lived OIDC-derived token. Server checks at connect and on every inbound update, and rejects updates from viewers. | Clients hold full state, so revocation cannot claw back data already seen. The server is the enforcement point. | V3 | V3 finds a cross-tenant or viewer-write path: fix before any exposure. Revocation latency over the bar: add forced disconnect on role change. |
| Data-privacy boundary | R3: trust boundary, residency, deletion | Content is user data. Telemetry carries IDs, sizes and timings, never content. Encrypted at rest and in transit. Single region. | Server-side content access is acceptable | V3 (telemetry scan), V5 | V5 refuses, or a customer requires residency or E2EE: re-plan Phases 1–2 |
| Monolith vs services | R2: internal service boundary | Modular monolith: one TypeScript service with REST and a WebSocket sync endpoint. Document "rooms" live in memory, one owner node per `doc_id`. | One node group handles projected load | V4 | V4 fails: split out a sync service and add Redis pub/sub and consistent-hash routing |
| Sync vs async | R2: protocol between client and server | Live edits over WebSocket. Compaction, snapshots and export run as async jobs. | Async jobs do not disturb live latency | V4 | Jobs breach the latency bar: isolate them in a worker |
| Build vs buy | R2: library and vendor choice, but vendor data gravity would be R3 | Build on open-source Yjs and Tiptap, self-hosted. Buy Postgres, identity and the load balancer. No hosted collaboration vendor. | The team can operate the sync tier | V1 | V1 fails, or ops load exceeds the complexity budget: evaluate a hosted sync service behind an interface and with a tested open-format export |

**minor defaults:** transport is WebSocket, falling back to long-poll only if a client network blocks it. Presence and cursors are ephemeral messages, never persisted. Snapshot every 500 updates or 5 minutes. Language is TypeScript. Test runner is Vitest with Playwright for two-browser tests.
**N/A:** AI decisions, brownfield migration and cutover. This is greenfield with no AI component.

## 4. First end-to-end slice (Phase 0)
- **Real request.** An allow-listed staff user signs in through OIDC and opens a document at the production URL. They type in the Tiptap editor. The edit becomes a Yjs update over WebSocket. The server validates the token, writes the update to the Postgres log, acks, and broadcasts. A second browser session shows the edit, and a reload shows it persisted.
- **Tiers crossed.** Browser, CDN/TLS and load balancer, app service (HTTP and WebSocket), Postgres.
- **Deploy.** The CI pipeline builds an image and runs infrastructure as code (Terraform) and Postgres migrations (expand/contract). It deploys to production, then rolls back by redeploying the previous image.
- **Logging.** Structured logs with no document content.
- **Tracing.** OpenTelemetry trace context travels in the WebSocket message envelope, so one trace covers browser, server, DB write and peer delivery.
- **Monitoring.** Dashboards and an error-rate alert. Metrics are connection count, ack latency, remote-apply latency and update-log write time.
- **Reach.** Staff identities only, behind a flag, with synthetic documents only and no customer data. The skeleton runs on the unvalidated defaults in §3 and is not hardened.
- **V0 exit check.** A real edit succeeds with one trace across every tier. A deploy and a rollback both succeed through the pipeline. An injected Postgres failure fires the alert. Baselines are recorded for remote-apply latency, ack latency and log write time, measured at near-zero load as floors.

## 5. Phases

- **Phase 1: Convergence, schema and storage** (widest rework first)
  - Unlocks: specifying and hardening everything that reads or writes document state.
  - Depends on: Phase 0 (V0).
  - Tasks:
    1. Lock the document schema, including a version field and a migration framework.
    2. Build the update-log and snapshot schema, with `tenant_id` and UUIDv7 on every row.
    3. Build the open-format export.
    4. Build the compaction job, including a check that deleted content is gone afterward.
    5. Add a property-based convergence fuzz harness to CI.
    6. Build the kill/failover durability harness.
    7. Measure storage growth.
  - Rollback: schema changes are expand/contract. The data is synthetic, so a reset is allowed until Phase 5.
  - Exit check: V1 and V2 pass.

- **Phase 2: Identity, tenancy and authorization**
  - Unlocks: any real tenant data, sharing, and Phase 5 exposure.
  - Depends on: V1 (protocol and schema fixed) and the IdP tenant.
  - Tasks:
    1. Tenant and user model.
    2. Per-document ACL.
    3. Token issuance and short lifetimes.
    4. Server-side enforcement at connect and on every update, including viewer write rejection.
    5. Forced disconnect on revocation.
    6. Audit log of access and permission changes, metadata only.
    7. Authorization test matrix in CI.
    8. Telemetry content scan.
  - Rollback: ACL changes are behind the flag. Deny-by-default is the fallback.
  - Exit check: V3 passes.

- **Phase 3: Sync-tier scale and failure behavior**
  - Unlocks: a committed capacity and RTO. The scaling design is specified only after the inputs and V4.
  - Depends on: V2, V3, and the scale figures and RTO from the product owner.
  - Tasks:
    1. Owner-node routing per `doc_id`.
    2. Reconnect with state-vector resync.
    3. Backpressure and per-connection and per-document limits.
    4. Load and soak tests.
    5. Node-kill and rolling-deploy tests.
    6. Add Redis pub/sub only if V4 demands it.
  - Rollback: scale-out is behind config and the previous image is kept.
  - Exit check: V4 passes, and operational complexity is within the budget.

- **Phase 4: Editor features (leaf work)**
  - Unlocks: a usable product for the internal cohort.
  - Depends on: V1, V3, Phase 3.
  - Tasks:
    1. Formatting set.
    2. Presence and cursors.
    3. Sharing and permissions UI.
    4. Read-only version history from snapshots.
    5. Export.
  - Rollback: per-feature flags.
  - Exit check: two-browser Playwright scenarios pass. The convergence fuzz (V1) still passes with the new schema features.

- **Phase 5: Staged exposure** (smallest first)
  - Unlocks: general availability.
  - Depends on: V3, V4, V5, the availability figure, and Phase 4.
  - Tasks:
    1. Internal cohort on real work documents.
    2. One allow-listed design-partner tenant.
    3. Widen in tenant batches, each only after SLIs stay within the budgets for 14 days (a chosen parameter).
    4. Set the retention policy from the V2 measurements.
  - Rollback: a per-tenant flag sets editing to read-only, with export available. The new system is the system of record (greenfield), and there is no point of no return before GA.
  - Exit check: V5 is held, availability is measured against the figure the product owner supplied, and a restore drill succeeds in production.

## 10. Deferred
- **Long offline editing (IndexedDB persistence).** Pull forward if offline is a stated requirement or reconnect data shows long disconnects.
- **Comments, suggestions and named versions.** Pull forward once V1 and Phase 4 are stable and users ask for review workflows.
- **End-to-end encryption.** Pull forward on a customer or regulatory requirement. It would reopen the authorization, storage and search decisions (§1 Missing inputs).
- **Multi-region active-active.** Pull forward on a residency requirement or a measured latency need from distant users.
- **Redis, sharding and a separate sync service.** Pull forward if V4 fails.
- **Full-text search.** Pull forward on a product request, after V3 and the privacy boundary are settled.
- **Public API and webhooks.** Pull forward on the first integration request. The API contract then becomes R3 and needs its own gate.
- **Mobile native clients and Word/Docs import.** Pull forward on demand evidence from the pilot tenants.
