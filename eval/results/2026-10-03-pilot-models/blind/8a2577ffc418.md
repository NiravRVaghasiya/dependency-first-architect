# Plan: Multi-tenant SaaS billing system

## 1. Classification and constraints
- **What:** A billing platform that meters each tenant's usage, rates it against plans, issues invoices, collects card payments through a hosted PSP, and keeps an auditable ledger.
- **Type:** Software with a money flow. **Greenfield (ASSUMED).** Not small: it moves money, holds tenant data, and faces outside users.
- **Dominant constraint:** Correctness, meaning amounts, idempotency, and tenant isolation. Availability matters second, and only for not losing usage events.
- **Worst failure:** Customers are charged a wrong or duplicate amount, or a tenant sees another tenant's billing data. Both are hard to undo once they happen. V5 and V6 guard the first, V2 the second.

**Missing inputs** (assumptions stated; each changes the plan if false):
- **Who is billed and by whom:** I assumed the SaaS company bills its own tenants. If tenants bill their own end customers (a marketplace or Connect model), that is a different compliance and ledger scope and the plan is re-done from Step 1.
- **Pricing model:** I assumed flat subscription, seats, and metered usage. If it is flat subscription only, buy a billing engine (see §3, Build vs buy).
- **Existing billing (spreadsheets, Stripe subscriptions):** I assumed none. If it exists, add a migration phase with a cutover gate and name the system of record.
- **Currencies, tax jurisdictions, data residency, and the identity provider (OIDC assumed):** All UNKNOWN. Residency changes §3's isolation row.
- **Named finance owner and approver:** Required for V1, V5, and V6.

## 3. Key decisions (resolved up front)

| Decision | Reversibility | Default (chosen now) | Assumption | Validated by | Revisit trigger |
|---|---|---|---|---|---|
| Tenancy and isolation | R3: real customer data and contracts cannot be re-partitioned cheaply | Shared Postgres. `tenant_id` on every row and in every composite key. Row-level security that fails closed. Tenant comes from the token claim, never the request body. A tenant-routing seam is built so a dedicated DB can be added per tenant | Shared isolation is acceptable to customers, and there is no residency or contract demand for dedicated storage | V2 | V2 fails, or a contract or residency rule requires dedicated storage: move that tenant tier to DB-per-tenant via the seam |
| Ledger and data model, identifiers, privacy boundary | R3: data model, identifiers, and retention law once real data exists | Append-only double-entry ledger in integer minor units with a currency on every entry. Corrections are reversals, never edits. UUIDv7 IDs. Idempotency key on every write. PII (billing contacts, tax IDs) in a separate table under per-subject keys so erasure is crypto-shredding while ledger rows stay. **No PAN is ever stored.** Telemetry carries IDs only, never PII | Legal retention of financial records and erasure requests can coexist this way | V1 | V1 fails on invariants, or finance or the DPO rejects the design: redesign before any dependent is specified |
| Consistency vs availability | R3: the consistency model | Ledger, invoice finalization, and payment state are strongly consistent (single primary, serializable where needed). Usage ingest is available-first: accept, persist durably, dedupe later | One primary sustains the projected load | V3 | V3 fails: open the partitioning/sharding decision |
| Build vs buy | R3: data gravity at the PSP (card tokens) and whether to build at all | Buy payments (hosted fields, Stripe or Adyen class) and tax calculation. Build metering, rating, invoicing, and the ledger. Keep an interface in front of the PSP and a tested token-export path | Pricing is usage-based enough that a hosted billing engine (Stripe Billing, Chargebee, Lago) would not fit | V4 (vendor terms, token portability) | Pricing turns out to be flat subscription only: buy the whole engine and build only the ledger export. Or V4 shows tokens are not portable: narrow the PSP dependency |
| Public API shape | R3 once outside consumers exist, R2 while callers are internal | Ingest API versioned `/v1`, idempotency keys required, OpenAPI contract tests in CI. Internal callers only until the contract has held through Phase 3 | Only internal services call ingest at first | Contract tests, cheap check | An external consumer appears before the contract has held through Phase 3: freeze `/v1` and gate changes |
| Sync vs async | R2: queue technology, because the raw usage table (not the queue) is the system of record | Ingest is async: write to a Postgres event table through an outbox, with a queue as transport. Payments are async by webhook. Invoice finalization is an idempotent batch job | At-least-once plus dedupe is enough | V3 | V3 shows lost or duplicate counts the dedupe cannot fix: change the transport |
| Monolith vs services | R2: internal boundaries | Modular monolith (ingest, rating, invoicing, payments, ledger as modules) plus one worker. Module boundaries enforced by a CI dependency lint | A small team does not need separate services | Phase 3 exit check | V3 shows ingest needs independent scaling: split ingest only |

## 4. First end-to-end slice (Phase 0)
- **Real request and response:** An internal service sends one real usage event to `POST /v1/usage` for an internal "house" tenant. The event is ingested, deduped, aggregated, rated by a stub single-plan rule, and turned into a **draft** invoice. A payment intent is created in **PSP test mode** and its webhook comes back and posts a ledger entry. The draft is readable through an authenticated `GET /v1/invoices/{id}`.
- **Tiers crossed:** API gateway and auth, ingest module, Postgres (event table, ledger), queue and worker, rating/invoice module, PSP sandbox and webhook receiver, read API.
- **Deploy, log, monitor, roll back:**
  - The pipeline builds a container and runs IaC-defined deploys from the first commit. Rollback is to the previous image. Database migrations are expand/contract.
  - Structured logs and one OpenTelemetry trace per request go through every tier. Logs carry IDs only.
  - Dashboards and alerts cover ingest error rate, queue depth, and webhook failures.
- **Who can reach it:** Allow-listed internal services and the house tenant only, behind a feature flag. **No real charge is possible:** the PSP is in test mode and invoices stay draft.
- **Organizational work starts here:** PSP account and sandbox, the acquirer or QSA conversation for V4, the finance owner and approver, tax registration inputs, and the usage-event schema agreed with product teams.

**Exit check (V0):**
- A real request succeeds with one trace across every tier.
- A deploy and a rollback succeed through the pipeline.
- An injected failure (a killed worker, a broken webhook) fires an alert.
- Baseline values are recorded as floors, not capacity: ingest ack latency, end-to-end event-to-draft-invoice time, and queue lag.

## 5. Phases

- **Phase 1 — Tenancy, identity, ledger, and data contracts** (the widest rework impact)
  - Unlocks: specifying metering, rating, and payments; admitting any non-house tenant's data.
  - Depends on: Phase 0 / V0.
  - Tasks:
    1. Tenancy model and row-level security, with `tenant_id` in every key.
    2. Token-derived tenant context and service-to-service identity.
    3. Append-only ledger, idempotency framework, and the PII table with per-subject keys.
    4. OpenAPI `/v1` contracts and contract tests.
    5. Negative isolation test matrix, run in CI from now on.
  - Rollback: expand/contract migrations; the flag keeps the house tenant only.
  - Exit check: V1 and V2 pass.

- **Phase 2 — Metering pipeline**
  - Unlocks: trustworthy usage totals for rating.
  - Depends on: Phase 1, V1, V2. The usage-event schema is agreed with product teams, and the peak-rate input has arrived.
  - Tasks:
    1. Durable ingest with the outbox.
    2. Idempotent dedupe by event ID.
    3. Late and out-of-order handling, with a watermark that closes the billing period.
    4. Aggregation.
    5. Daily count reconciliation against the producers' own counters.
    6. Per-tenant rate limits.
    7. Load and failure-injection test.
  - Rollback: the flag stops producers emitting; the raw events stay in place.
  - Exit check: V3 passes.

- **Phase 3 — Rating and invoicing, in shadow mode**
  - Unlocks: correct invoices computed for internal and dogfood usage, with nothing sent or charged.
  - Depends on: Phase 2, V1, V3, and the pricing model (input).
  - Tasks:
    1. Plan and price catalog, versioned and immutable once used.
    2. Rating, with proration and credits.
    3. Tax through the bought engine.
    4. Invoice state machine: draft → finalized → voided by credit note only.
    5. Shadow run beside an independent recomputation maintained by finance.
  - Rollback: shadow invoices are deletable; no customer sees them.
  - Exit check: V5 passes and the module-boundary lint is green.

- **Phase 4 — Payments, dunning, and reconciliation, in PSP test mode**
  - Unlocks: collecting money.
  - Depends on: Phase 3; V4 **starts in Phase 0 and must pass before Phase 5**. The PSP fee schedule is in hand.
  - Tasks:
    1. Hosted card fields only, so no card data touches our servers.
    2. Idempotent charge and refund.
    3. Signed and replay-safe webhooks.
    4. Payment state machine and dunning schedule.
    5. Daily ledger-to-PSP settlement reconciliation.
    6. Refund, void, and reversal rehearsal in test mode.
  - Rollback: payment flag off; the PSP stays in test mode.
  - Exit check: V4 passes, and the test-mode reconciliation shows zero differences for the rehearsal set.

- **Phase 5 — Live charging, widened by canary** (the point of no return is the first real charge)
  - Unlocks: production billing.
  - Depends on: Phase 4, V2, V4, V5.
  - Tasks:
    1. Customer invoice and email delivery.
    2. Widen in order: house tenant with a real small charge, then one friendly external tenant, then about 5% of tenants, then all. Each stage ends in a V6 go/no-go.
    3. Tenant-facing invoice and payment-method pages.
  - Rollback: charging flag off; void or credit-note invoices; refund charges. The first live charge cannot be unmade, only compensated, so it is guarded by V5 and V6.
  - Exit check: V6 passes at each stage.

- **Phase 6 — Scale and recovery hardening**
  - Unlocks: operating at full load with a known recovery time.
  - Depends on: Phase 5 and the RTO input.
  - Tasks:
    1. Event-table partitioning if V3's headroom requires it.
    2. Restore and failover drill against the RPO/RTO targets.
    3. Finance exports and audit report.
    4. Access reviews and key rotation.
  - Rollback: each change is independently reversible via its own flag or migration.
  - Exit check: the restore drill meets RPO 0 and the RTO target, which must be set first.

## 10. Deferred
- **Multi-currency and FX:** Pull forward when the first tenant is contracted in a non-base currency. The ledger already carries a currency on every entry.
- **Multiple PSPs or regional acquirers:** Pull forward when V4 shows a region the primary PSP cannot serve, or when PSP concentration is judged a risk.
- **DB-per-tenant tier:** Pull forward when V2 fails, a contract requires it, or a residency rule applies. The routing seam is already built.
- **Automated revenue recognition (ASC 606 / IFRS 15):** Pull forward when finance needs it for audit, or a contract has non-trivial deferral. For now the finance export carries the ledger.
- **Tenants billing their own end customers (marketplace model):** Pull forward only if the product decision changes. It restarts Step 1 (see §1).
- **Self-serve plan editor UI:** Pull forward when catalog changes exceed what finance and engineering can review by hand, roughly more than a few per month (ASSUMPTION).
- **Sharded or separately scaled ingest service:** Pull forward when V3 fails or production ingest exceeds the measured headroom.
