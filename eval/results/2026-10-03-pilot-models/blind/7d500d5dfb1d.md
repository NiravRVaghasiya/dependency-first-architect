## 4. First end-to-end slice (Phase 0)

**What runs:** One developer pushes to a Git branch → webhook fires → agent pulls code → single test runs → agent builds a container image → image pushed to registry (with a tag) → deployment manifest updated → K8s admission controller checks it → pod created in a *test* namespace → service endpoint responds to a probe → log entries are written and scrubbed of secrets → rollback deletes the pod. All of this happens in <10 min wall-clock time.

**The real request (data flow):**
1. Developer pushes commit to `feature/add-auth-endpoint` (a real microservice in test environment).
2. Git webhook → CI agent.
3. Agent: clone, run `go test ./...` (synthetic test data, no real database).
4. Agent: build image `registry/svc:feature-xyz-abc123` (short commit SHA).
5. Agent: push image to registry; registry notifies K8s via webhook.
6. K8s admission controller validates image signature (stub: warn only in V0).
7. K8s spins up pod in `test-v0` namespace with the new image.
8. Agent runs HTTP GET on `http://svc:8080/health` from a pod-internal initiator (no external route yet).
9. Health check succeeds; pod becomes Ready.
10. Agent logs: `{ "timestamp": "2026-10-03T...", "event": "deploy_success", "service": "auth", "image": "sha256:...", "namespace": "test-v0" }` (no secrets in any log field).
11. Auditor: sample the logs; confirm no API key, password, or registry pull token appears.
12. Rollback: agent runs `kubectl delete pod` on test-v0 pod → pod terminates → no data loss (test data is ephemeral).
13. Redeploy (inverse rollback): same push again; pod re-created; confirms reproducibility.

**Who can reach it:**
- Only the CI agent and internal test-cluster network (K8s pod-to-pod traffic).
- No external route, no real customer traffic.
- No real secrets (test data is synthetic; registry credentials are test pull tokens with minimal scope).

**Deployment, logging, monitoring, rollback:**
- **Deploy:** Agent runs via a cron or webhook in a containerized executor (no state stored locally); logs to stdout; CI system persists logs to object storage (S3, GCS, or K8s-native) immediately.
- **Logging:** Structured JSON; every log entry tagged with `deployment_id`, `service_name`, `phase` (build, test, deploy, rollback). Log sink: object storage + local ringbuffer (last 1000 entries) for quick replay.
- **Monitoring:** Probe fires every 5 sec; hits `http://svc:8080/metrics` (Prometheus-format). Metrics ingested into in-memory time-series (InfluxDB, Prometheus, or similar) running on a separate pod. Alert rule: if health check fails 3 times in a row, log `ERROR: health check failed`.
- **Rollback:** kubectl delete; state is declarative (Kustomize or Helm overlay); no manual steps. Rollback is tested in V0 exit check; if it fails, V0 does not pass.

**Unvalidated defaults in V0 (not yet hardened):**
- Container image is unsigned (stub admission controller warns only).
- RBAC: all agents have broad cluster-admin scope (tightened in Phase 1).
- Secret leakage: logs are checked manually, not yet masked by policy.
- Approval chain: none; any push deploys (Phase 1 gates this).
- Audit trail: logged but not tamper-proofed (Phase 2).
- High-availability: single agent, single K8s node (Phase 2).

**Exit check (V0):**
- ✓ Real request (push → pod ready) completes in <10 min.
- ✓ Logs are captured and accessible; random sampling finds no secrets.
- ✓ Rollback executes and pod terminates.
- ✓ Re-deploy creates a new pod with same image; health check passes.
- ✓ One trace (deployment_id) ties all events together.
- ✓ Metrics recorded: build time, test time, deploy time, pod startup time, health-check latency. Baseline recorded (near-zero load, single service).

## 9. Exceptions

# Summary

This plan builds a CI/CD platform for 50 microservices in three phases plus a first end-to-end slice:

- **Phase 0 (Day 1):** One end-to-end deploy on a test service; first end-to-end slice; baseline latency and security posture.
- **Phase 1 (Weeks 1–3):** Secrets, RBAC, approval gates, agent hardening. 12 validation checks gate each phase.
- **Phase 2 (Weeks 4–8):** Multi-environment promotion, canary, HA, audit, cost validation.
- **Phase 3 (Weeks 9–12):** Production rollout: 3 services (pilot), then 5, 15, 20 (waves). Observability, feedback, decommissioning.

**Principle 1 (dependency order):** Every task follows what blocks it. Secrets and RBAC are Phase 1 (load-bearing). Production exposure is Phase 3 (only after V0–V9 pass). Canary is smallest-first (3 services → all 50).

**Principle 3 (hard-to-reverse tradeoffs up front):** R3 decisions (hosted vs. self-hosted, sync secrets) are decided early with V-gates; R2 decisions (single template, artifact store) are spiked in Phase 1. Revisit triggers are explicit.

**Principle 5 (observability day-zero):** Every phase logs structure (JSON + deployment_id), metrics (build_time, latency), and audit events (approval, secret access, RBAC denial). Phase 0 has basic logs; Phase 2 adds audit to tamper-proof sink; Phase 3 adds dashboards and alerts.

**Principle 6 (first end-to-end slice first):** Phase 0 is a one-request skeleton: code → test → build → deploy → health check → rollback. It validates nothing is broken before hardening begins.

**Principle 7 (canary first, then wider):** Phase 3 exposure: 3 services → 5 → 15 → 20, with a validation check (V10) between pilot and Wave 2. Each wave is rolled back if errors exceed threshold.

The plan is **not small** (three phases, 12 gates, 50 services, multiple teams), so all constraints are honored: no silent assumptions, budgets are labeled, reversibility is declared (R1/R2/R3), and deferred work is visible.
